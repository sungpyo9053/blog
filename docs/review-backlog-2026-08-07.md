# 2026-08-07 데이터 기반 개선 검토 백로그

## 리뷰 목적

HuntLab의 목표는 `글을 만드는 시스템`에서 `검색 자산을 축적하는 시스템`으로
전환됐다. 성공 기준은 일일 발행량이 아니라 검색 가능한 유효 콘텐츠 자산이
증가하는 속도다.

8월 7일 리뷰는 코드 리뷰가 아니라 운영 리뷰로 시작한다.

1. 발행→색인→노출→클릭 퍼널과 검색 자산 증가 속도를 확인한다.
2. 성공 글과 이탈 글의 차이를 검색어·제목·도입부·H2·이미지·행동 흐름으로 비교한다.
3. 확인된 병목이 코드나 정책 변경으로 해결될 때만 최소 수정한다.
4. 수정 자체를 성과로 간주하지 않고 이후 검색 자산 비율의 변화를 다시 측정한다.

## 동결 원칙

- 2026년 8월 7일까지 Agent 구조, Workflow, Prompt와 SEO 정책을 변경하지 않는다.
- 발행 실패, 인증 오류, 이미지 누락, 타이머 장애와 검증기 오탐 같은 운영 버그만 즉시 수정한다.
- Reviewer의 품질 거부는 발행 장애로 간주하지 않고 우회하지 않는다.
- 아래 항목은 자동 적용 목록이 아니라 실측 데이터가 뒷받침할 때만 적용하는 검토 후보다.

## 8월 7일 확인할 데이터

### 최우선 KPI: 검색되는 글의 비율

8월 7일에 가장 먼저 보는 지표는 CTR이나 평균 순위가 아니라 다음 비율이다.

> 비브랜드 검색 노출이 1회 이상 발생한 글 수 ÷ 분석 가능한 공개 글 수

계산 원칙:

- 글(Post)만 포함하고 홈, 소개, 개인정보처리방침, 태그·카테고리·페이지네이션은 제외한다.
- Search Console 데이터 지연을 고려해 발행 후 최소 3일이 지난 글을 기본 분석 대상으로 삼는다.
- `huntlab`과 명백한 운영자 테스트 검색은 비브랜드 검색 성과에서 분리한다.
- URL이 색인되지 않은 글과 색인됐지만 노출이 없는 글을 따로 집계한다.
- 노출 1회는 검색 진입 신호로 기록하되 성공 공식이나 지속 성과로 일반화하지 않는다.
- 전체 비율과 함께 Tech·AI·Build Log·비기술 카테고리별 비율도 표본이 허용하는 범위에서 비교한다.

보조 지표는 다음 순서로 본다.

1. 검색되는 글의 비율
2. 비브랜드 검색어가 붙은 글의 비율
3. 클릭이 발생한 글의 비율
4. 노출이 반복되는 글의 비율
5. 그 다음에 CTR과 평균 순위

### 콘텐츠 검색 퍼널

8월 7일 실측 결과를 다음 전체 운영 퍼널로 표시한다.

```text
발행 대상 생성
  ↓ Reviewer 통과율
Reviewer 통과·공개 발행
  ↓ Google 색인율
Google 색인
  ↓ 검색 진입률
비브랜드 검색 노출
  ↓ 검색 CTR
클릭
  ↓ 참여율·체류·이탈
클릭 후 행동
  ↓ 광고·전환율
광고 수익·전환
```

예시 형식이며 아래 숫자를 현재 실측으로 간주하지 않는다.

```text
발행 글 19개
  ↓
색인 17개
  ↓
노출 발생 12개
  ↓
클릭 발생 5개
```

각 단계에서 전체 수, 이전 단계 대비 전환율과 이탈 URL을 함께 기록한다.

- 생성→Reviewer 통과 병목: 검색 의도, 근거, 제목 계약, 고유 가치와 품질 기준 확인
- Reviewer 통과→공개 발행 병목: Publisher 검증, 인증, 이미지와 WordPress 운영 오류 확인
- 발행→색인 병목: sitemap, robots, canonical, 크롤링과 콘텐츠 중복 확인
- 색인→노출 병목: 검색 수요, Primary Keyword, 언어와 검색 의도 확인
- 노출→클릭 병목: 순위, 제목, Meta Description과 SERP 경쟁 확인
- 클릭→참여 병목: 첫 답변, H2 흐름, 이미지, 체류·이탈과 내부 링크 이동 확인
- 참여→광고·전환 병목: 광고 노출·CTR·RPM, CTA와 전환 이벤트 확인

단계별 기본 측정값:

- 발행 대상 생성: TOP2 선정 수와 콘텐츠 완성 수
- Reviewer 통과: 승인·거부 수, 통과율과 반복 거부 사유
- 공개 발행: 성공·실패·재시도 수와 운영 오류
- Google 색인: 색인 URL 수와 색인까지 걸린 시간
- 검색 노출: 비브랜드 노출 글 수, 검색어 수와 반복 노출
- 클릭: 클릭 글 수, CTR과 평균 순위
- 체류·이탈: 자연 검색 랜딩의 참여 세션, 평균 참여 시간과 내부 이동
- 광고·전환: 데이터가 실제 연결된 뒤 광고 노출·CTR·RPM과 정의된 전환 이벤트

광고·전환 측정이 아직 연결되지 않았으면 `0`이나 낮은 등급이 아니라 `N/A`로
표시한다. GA4의 표본이 작을 때 체류·이탈을 콘텐츠 품질로 단정하지 않는다.

퍼널 전체 숫자만 보지 않고 카테고리와 발행 후 경과일을 함께 표시한다. 최신 글의
데이터 지연을 오래된 글의 실패로 섞지 않으며, 단계별 병목에 맞지 않는 처방을
적용하지 않는다.

1. 공개 글 수와 일별 발행 성공·거부·실패 건수
2. URL별 색인 상태와 마지막 크롤링 시각
3. 브랜드·비브랜드 Search Console 검색어 수
4. 글별 노출, 클릭, CTR과 평균 순위
5. GA4 자연 검색 세션과 랜딩 페이지
6. 기술 글을 다음 상태로 구분
   - 미색인
   - 색인됐지만 노출 없음 또는 수요 부족
   - 노출되지만 순위 밖
   - 노출은 있으나 클릭 없음 또는 CTR 부족
   - 색인 + 노출 + 클릭 발생
7. Reviewer 거부 사유와 운영 실패 사유의 반복 여부
8. HTTPS apex canonical로 `http`·`www` 검색 결과가 통합되는지

### Google·Naver 검색 퍼널 비교

한국어 검색 자산의 도달 범위를 Google 하나로 한정하지 않는다. 네이버 데이터가
연결돼 있으면 같은 기간과 URL 집합으로 다음 항목을 별도 집계하고, 연결되지
않았으면 성과를 `0`으로 기록하지 말고 `N/A`와 연결 필요 조건을 보고한다.

- 네이버 서치어드바이저의 `huntlab.app` 등록·소유 확인 여부
- sitemap 제출·수집 상태와 `robots.txt`의 Yeti 접근 허용 여부
- 네이버에 색인된 공개 글 수와 색인까지 걸린 시간
- 네이버 비브랜드 검색어의 노출 글 수, 노출, 클릭과 CTR
- Google과 Naver의 `검색되는 글의 비율` 및 단계별 병목 비교

네이버 노출을 위해 동일 글을 네이버 블로그에 복제하거나 네이버 전용 Agent,
Workflow와 별도 제목 규칙을 만들지 않는다. 기존 단일 URL, HTTPS apex canonical,
문제 해결형 콘텐츠와 Helpful Content 기준을 유지하고 검색엔진별 관측 차이만
운영 데이터로 활용한다.

## Planner 우선 개선 후보

### 기술 키워드 선정

기술 주제의 Primary Keyword는 가능하면 다음 조합으로 선정한다.

> 제품·기술명 + 실제 오류·문제·해결 행동

예시:

- `Cloudflare Workers 메모리 지표` → `Cloudflare Workers Exceeded Memory 해결`
- `WordPress REST API 재시도` → `WordPress REST API 429 오류 재시도`
- `GitHub Actions 워크플로 승인` → `GitHub Actions 의심 워크플로 실행 차단`
- `Cloudflare Tunnel connections 제거` → `Cloudflare Tunnel API connections 필드 제거 대응`

검토 기준:

- 사용자가 실제 화면에서 보는 오류 문구인가
- 원인·확인·해결·설정 중 분명한 행동 의도가 있는가
- 한국어 설명과 영문 제품명·오류 메시지를 자연스럽게 함께 다룰 수 있는가
- 내부 기획 용어가 아니라 사용자가 검색할 표현인가
- 검색량 수치를 확인하지 못했다면 임의로 만들지 않는가

HuntLab의 장기 방향 후보는 `기술 주제 소개`보다 `기술 문제 해결`을 우선한다.
실제 운영에서 관찰한 증상, 오류 메시지, 실패 조건과 선택 기준을 개념 설명과
함께 다루되 경험하지 않은 장애를 창작하지 않는다.

### 키워드 발굴 절차

Planner는 키워드를 자유 생성하기 전에 관측 가능한 문제 흔적을 다음 순서로
확인한다. 모든 출처를 매번 강제하지 않고, 후보마다 실제 확인한 발견 출처와
확인 시점을 남긴다.

1. Google Search Console과 네이버 서치어드바이저의 실제 비브랜드 검색어
2. Google·Naver 자동완성·연관 검색어에서 반복되는 문제 표현
3. HuntLab 서버 로그, 배포 실패와 기존 Build Log의 실제 증상·오류 문구
4. 공식 문서의 Troubleshooting, Known Issues와 제품 Changelog
5. 기술 후보는 Stack Overflow에서 반복되는 오류 문구·질문·해결 행동
6. GitHub Issues는 특정 제품의 실제 버그, 회귀와 버전 영향을 확인하는 보조 근거
7. 비기술·시사·생활 후보는 Threads와 X에서 반복되는 질문·불편·표현

기술 토픽은 Stack Overflow를 핵심 수요 발견처로 사용한다. 질문 제목, 오류 원문과
반복되는 해결 의도를 키워드 후보로 삼되 답변의 정확성은 공식 문서와 실제 재현으로
검증한다. GitHub Issues는 검색 수요의 크기보다 제품별 결함과 버전 조건을 확인하는
용도로 구분한다.

Threads와 X는 실시간 관심과 독자가 사용하는 표현을 발견하는 보조 출처로만 쓴다.
단일 바이럴 게시물이나 좋아요 수를 검색 수요로 간주하지 않고, Google·Naver 검색
흔적과 서로 독립적인 여러 게시물에서 반복되는지 교차 확인한다. 게시물의 주장이나
숫자는 사실 근거로 사용하지 않으며 공식 발표, 원문과 신뢰할 수 있는 자료로 별도
검증한다. 로그인·유료 API가 필요해 확인하지 못한 경우 수요를 추정하지 않는다.

후보 채택 전 다음을 확인한다.

- 작성자가 흥미를 느끼는 주제가 아니라 사용자가 해결하려고 검색하는 문제인가
- 제품명만 있는 개념 키워드가 아니라 증상·오류·확인·해결 행동이 포함되는가
- 일회성 질문 하나가 아니라 여러 출처 또는 반복 관측으로 수요 흔적이 있는가
- HuntLab이 실제 테스트, 로그, 설정값, 실패 사례 또는 공식 근거를 제공할 수 있는가
- 기존 공개 글과 검색 의도가 겹치면 새 글보다 통합·후속 관점이 적절한가

검색량·경쟁도 수치를 확인할 수 없으면 숫자를 추정하지 않는다. 자동완성이나
커뮤니티 질문 하나만으로 수요가 크다고 단정하지 않으며, 발견 출처는 후보 근거일
뿐 발행을 보장하는 점수나 할당량으로 사용하지 않는다.

문제 중심 조합 예시:

- Cloudflare Workers Memory → `Exceeded Memory`
- Datadog → `CPU Spike`
- FastAPI → `Timeout`
- PostgreSQL → `Deadlock`
- AWS ALB → `502`
- OpenTelemetry → `Trace 누락`

제목 후보 예시:

- `FastAPI BackgroundTasks가 실행되지 않는 이유와 Celery를 써야 하는 경우`
- `Datadog SLO가 계속 깨질 때 Golden Signals로 원인 찾는 방법`

각 예시는 실제 Search Console 수요와 HuntLab의 검증 가능한 경험·근거가 있을
때만 주제로 선정한다. 특정 도구나 장애 조합을 할당량처럼 강제하지 않는다.

### 하네스 Build Log Pillar 후보

HuntLab이 실제로 구축·운영한 콘텐츠 하네스를 설명하는 대표 Build Log를 검토한다.
이 글은 검색량을 채우기 위한 일반 글이 아니라 직접 경험, 전문성 증명과 기존 문제
해결 글을 연결하는 내부 링크 허브 역할로 평가한다.

제목 후보:

> AI WordPress 블로그 자동화 하네스 설계: Planner부터 Reviewer·Publisher까지

포함할 내용:

- 단순 프롬프트 체인 대신 단계별 하네스가 필요했던 운영 문제
- Planner→Researcher→Writer→Reviewer→Image→Publisher의 책임과 데이터 흐름
- Reviewer 품질 거부와 시스템·발행 장애를 분리한 이유
- 중복 발행, 근거 부족, 대표 이미지 누락을 막는 품질 게이트
- 예약 실행, 조건부 재시도, 로그와 발행 후 관측 구조
- 실제 실패 사례, 최소 수정과 검증 결과
- 현재 한계, 적합하지 않은 환경과 다음 운영 과제

내부 프롬프트 전문, 비밀값, 서버 주소와 공격에 활용될 수 있는 세부 구성은 공개하지
않는다. 기존 글의 제목·본문을 복제하지 않고 중복 발행 방지, Reviewer 거부 처리,
WordPress REST API 재시도와 내부 링크 검증 글을 Hub & Spoke로 연결한다.

### 검색 의도 범위

> 검색 의도는 하나, 관련 키워드는 여러 개

- 글 하나가 해결하는 핵심 문제는 하나로 유지한다.
- 관련 오류 문구, 지표, 원인과 해결 행동은 동일한 문제를 설명하는 범위에서만 확장한다.
- 여러 제품·오류·검색 의도를 한 제목에 나열하지 않는다.
- 서로 다른 해결 결과를 요구하는 질의는 별도 글 또는 기존 글의 후속 후보로 분리한다.
- Related Keywords는 Primary Keyword의 의도를 넓히는 용도가 아니라 같은 문제를 다른 표현으로 찾는 독자를 연결하는 용도로 사용한다.

### 제목 계약

제목의 기본 구조 후보:

> 제품·기술명 + 실제 오류·문제 + 독자가 얻는 해결 결과

예시:

> Cloudflare Workers Exceeded Memory 원인과 메모리 사용량 확인법

- 제목에 모든 연관 키워드를 나열하지 않는다.
- P50·P99·Memory Usage 같은 세부 의도는 본문에서 실제로 다룰 때만 H2와 FAQ로 확장한다.
- Planner의 최종 제목과 Primary Keyword가 Reviewer에서 서로 충돌하지 않게 함께 검증한다.
- 본문이 약속하지 않는 오류·결과를 제목에 추가하지 않는다.

## 적용 판단 조건

- 기술 글이 색인됐지만 비브랜드 노출이 거의 없고 검색 표현 불일치가 반복되면 Planner 기준을 최소 수정한다.
- 기술 글이 미색인이라면 제목보다 sitemap, robots, canonical과 크롤링 상태를 먼저 점검한다.
- 노출은 있는데 CTR이 낮으면 제목·Meta Description 보강을 검토한다.
- 평균 순위가 낮으면 검색 의도, 본문 깊이와 내부 링크를 먼저 검토한다.
- `색인 + 노출 + 클릭 발생` 글은 초기 성공군으로 분류하고 성급하게 수정하지
  않는다. 검색어·순위·클릭의 지속 여부를 관찰해 이후 글의 비교 기준으로 쓴다.
- 표본이 부족하면 기존 글 일괄 수정이나 Agent 추가를 하지 않는다.

## 변경 실험 원칙

> 한 번에 하나의 가설, 하나의 행동 변화, 하나의 검증

- 퍼널에서 우선 병목 하나만 선택한다.
- 변경 전에 관측값, 가설, 기대 효과와 성공·실패 판정 기준을 기록한다.
- 선택한 병목과 직접 관련된 최소 변경만 적용한다.
- 같은 주기에 Topic Planner, Writer, SEO Guide의 서로 다른 행동을 동시에 바꾸지 않는다.
- 하나의 계약을 일관되게 적용하기 위해 여러 파일을 수정해야 한다면 동일한 행동
  변화의 연계 수정으로 기록하고, 다른 최적화는 섞지 않는다.
- 변경 후 충분한 관찰 기간을 두고 같은 지표로 전후를 비교한다.
- 효과가 없거나 부작용이 확인되면 되돌릴 수 있도록 커밋과 측정 시점을 남긴다.
- 첫 실험이 끝나기 전에 다음 병목 수정으로 넘어가지 않는다.

### 실험 종료 조건(Stop Rule)

기본 실험은 다음 조건 중 먼저 도달한 시점에 평가한다.

- 변경 적용 후 14일 경과
- 실험 대상의 Search Console 누적 노출 1,000회 이상

평가 원칙:

- Search Console 데이터 지연을 고려해 종료일 직후의 미반영 데이터를 성급하게 누락으로 판단하지 않는다.
- 종료 조건은 평가 시점을 정할 뿐 성공을 보장하는 최소 표본을 뜻하지 않는다.
- 14일이 지났지만 노출이 너무 적으면 `성공` 또는 `실패`를 강제하지 않고 `판정 보류`로 기록한다.
- 1,000회 노출에 먼저 도달하면 CTR·순위·검색되는 글의 비율과 부작용을 평가한다.
- 최신 이슈의 수요 급증과 운영자의 테스트 클릭은 별도로 표시한다.
- 종료 후 유지·롤백·추가 관찰 중 하나를 명시하고 다음 실험 시작 여부를 결정한다.

실험 기록 형식:

```text
병목:
기준 데이터:
가설:
단일 행동 변화:
수정 파일:
기대 지표:
관찰 기간:
Stop Rule 도달 조건:
결과:
유지·롤백 판단:
```

## 성공 글 분석

실패한 글의 원인만 찾지 않고 다음 질문을 함께 검토한다.

> 왜 이 글은 클릭이 발생했는가?

8월 7일부터 성공 글끼리 다음 퍼널을 비교한다.

```text
실제 검색어
  ↓
제목
  ↓
도입부의 첫 답변
  ↓
H2의 문제 해결 순서
  ↓
이미지의 이해 보조 역할
  ↓
검색 노출·클릭과 클릭 후 행동
```

비교 시 각 단계에서 확인할 질문:

- 검색어: 사용자가 입력한 문제·오류·확인 행동은 무엇인가
- 제목: 검색어를 반복하지 않으면서 어떤 해결 결과를 약속했는가
- 도입부: 핵심 답, 적용 조건과 한계를 얼마나 빨리 제시했는가
- H2: 원인→확인→해결 또는 판단 순서가 검색 의도와 맞았는가
- 이미지: 장식이 아니라 비교·절차·수치·구조 이해를 도왔는가
- 클릭 후 행동: GA4 랜딩, 체류와 관련 글 이동이 관측됐는가

성공 글이 두 개 이상 쌓이면 공통점과 차이점을 표로 비교하고, 서로 다른 주제
에서도 반복되는 패턴만 Topic Planner와 Writer의 개선 후보로 채택한다.

성공군에서 확인할 항목:

- 실제 검색어와 제목의 일치 정도
- 검색 의도가 정보 확인, 문제 해결, 비교 또는 실행 중 무엇이었는지
- 최신 이슈·Evergreen·오류 메시지 등 수요가 발생한 계기
- 검색 결과에서 보인 제목과 Meta Description의 답변 명확성
- 첫 화면에서 답을 제시하는 속도
- 경쟁 결과의 수와 강도
- 실제 경험, 비교, 수치와 공식 출처 중 클릭 후 만족에 기여한 요소
- 내부 링크와 후속 행동으로 이어졌는지

Planner 반영 후보:

- 실제 클릭 검색어와 같은 문제 유형·검색 의도를 가진 후보를 우선 평가한다.
- 성공 글의 제목 문구를 복제하지 않고 검색 의도와 문제 구조만 재사용한다.
- 일회성 최신성 효과와 반복 가능한 문제 해결 수요를 구분한다.

Writer 반영 후보:

- 클릭을 만든 제목의 약속에 첫 화면에서 바로 답한다.
- 성공 글의 H2 개수나 문장 템플릿을 복제하지 않고 답변 순서와 근거 배치만 참고한다.
- 검색어와 직접 관련 없는 키워드를 성공 패턴이라는 이유로 추가하지 않는다.

클릭 1~2회나 운영자의 테스트 클릭은 성공 공식의 근거로 일반화하지 않는다.
비브랜드 검색에서 반복 노출·클릭이 확인되거나 서로 다른 글에서 같은 패턴이
재현될 때만 Planner·Writer의 최소 규칙 변경 후보로 채택한다.

검색 결과 클릭은 주로 검색어·제목·스니펫·순위의 영향을 받으므로 본문 H2와
이미지가 클릭을 직접 만들었다고 단정하지 않는다. H2와 이미지는 클릭 후 만족,
재검색 감소와 내부 이동에 기여했는지를 별도로 평가한다.

## 수익화 후속 검토 후보

이 항목은 8월 7일 검색 퍼널의 첫 병목을 해결한 뒤 검토한다. 외부 자연 유입과
반복 방문이 확인되기 전에는 광고·제휴·뉴스레터를 발행 목표로 강제하지 않는다.

### 8월 7일 AdSense 신청 게이트

8월 7일 운영 리뷰에서 다음 준비 상태를 확인하고 모두 충족하면 같은 날 AdSense
사이트 심사를 신청한다. 트래픽이나 글 수에 임의의 최소 기준을 만들지는 않는다.

- 사이트가 로그인 없이 정상 접근되고 HTTPS apex canonical과 주요 탐색 메뉴가 동작한다.
- 소개, 문의, 개인정보처리방침과 편집 정책 페이지가 공개돼 있다.
- Google이 사이트 전체를 평가할 수 있는 고유 콘텐츠가 있고 빈 카테고리, 깨진 링크와 명백한 중복 글이 없다.
- 모바일 본문, 대표 이미지와 내부 링크가 정상 표시된다.
- `robots.txt`, Cloudflare와 보안 설정이 AdSense 크롤러를 차단하지 않는다.
- WordPress에 사이트 확인 코드를 삽입하고 소유권을 검증할 수 있다.

하나라도 충족하지 않으면 승인 우회를 시도하지 않고 원인과 증거를 기록한 뒤 필요한
항목만 수정한다. 신청 후에는 심사 상태를 운영 지표와 분리해 기록하며, 승인 전 광고
수익은 `0`이 아니라 `N/A`로 보고한다.

- 콘텐츠 역할을 `검색 유입용 문제 해결`, `신뢰 형성용 Build Log`, `비교·선택용 전환`으로 구분하되 카테고리나 발행량 할당을 강제하지 않는다.
- 비교·선택 글은 무료·유료 플랜의 경계, 적합하지 않은 사용자와 실제 사용 근거를 함께 제시할 수 있을 때만 후보로 삼는다.
- 제휴 링크를 사용하는 경우 수수료 관계, 직접 사용 여부, 무료 대안과 추천하지 않는 조건을 명확히 공개한다.
- 뉴스레터는 외부 자연 유입과 재방문이 반복해서 관측된 뒤 검색 의존도를 낮추는 수단으로 검토한다.
- 광고, 제휴, 구독과 자체 상품을 동시에 도입하지 않고 전환 퍼널의 병목 하나에 대응하는 수익화 가설 하나만 시험한다.

## 하지 않는 것

- 기존 글 일괄 수정
- Agent 추가
- Workflow 변경
- 대규모 리팩토링

8월 7일 검토의 기본 범위는 Search Console 실측에 근거한 Topic Planner의
키워드·제목 선정 기준 최소 수정이다. 기존 글의 개별 수정도 노출·CTR·순위 등
구체적인 근거와 별도 검토 없이 자동으로 수행하지 않는다.

## 현재 확인된 기준점

- `석유 최고가격제 8차 가격`은 개별 글 색인과 첫 페이지 롱테일 노출을 확인했다.
- 이 노출은 검색 수요, 최신성, 제한된 경쟁 범위와 제목·검색어 일치의 영향을 받았을 가능성이 크다.
- 기술 글은 영문 오류 메시지 중심 수요와 한국어 검색량 부족 가능성이 있으므로 콘텐츠 품질과 검색 수요를 분리해 평가한다.
- Search Console의 초기 `huntlab` 클릭은 운영자의 회사 검색 테스트가 포함돼 외부 자연 유입으로 단정하지 않는다.
- Cloudflare에서 HTTP→HTTPS, `www`→apex 301, `Full (strict)`와 apex canonical을 적용·검증했다.
