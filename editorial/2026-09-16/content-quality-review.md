## 우선 수정할 실제 결함

### P1 — 373: 가상환경 설치 안내와 실행기가 다르다

공개 글은 가상환경에 requirements를 설치하라고 안내하면서 실제 긴 heredoc은 `python3 - <<'PY'`를 사용한다. 가상환경 활성화 명령도 없다. 이 머신의 기본 `python3`는 3.8.2이며 아래 import가 실제로 실패했다.

```text
python3 -c 'from scripts.run_daily_pipeline import Stage'
ImportError: cannot import name 'UTC' from 'datetime'
```

반면 `.venv/bin/python` 3.12.9로 같은 공개 예제는 다음 결과를 냈다.

```text
missing_twice: status=FAIL calls=2 artifact=False error=missing after retry
created_on_retry: status=PASS calls=2 artifact=True retry_prompt=True
bounded_contract: status=PASS max_calls=2 third_call=False exit_contract=PipelineError
```

수정: 독자용 명령을 `.venv/bin/python`으로 통일한다. 실제 과거 캡처의 명령/버전은 바꾸지 말고, 새 복사 실행 블록과 역사 로그를 구분한다. `datetime.UTC`를 import하는 저장소이므로 Python 3.11 이상 필요, 재검증 환경은 3.12.9라고 명시한다. 가상환경 생성 전 `python3 --version`을 확인하고 3.11 미만이면 검증된 3.12 인터프리터를 선택하게 한다.

완료 기준: 새 독자 명령으로 예제 단언이 통과하고, 본문에서 별도 활성화 없이 시스템 Python으로 빠지는 경로가 없어야 한다.

### P1 — 698: ‘전체 구현’ 링크가 강화 전 ID 검사기를 가리킨다

본문은 ‘양의 정수 ID’를 생성 응답 조건으로 설명하지만 전체 구현과 테스트 링크는 `601ac6386f7ad20168ef450e47ca6c1a71daea9e`를 가리킨다. 해당 역사 구현은 `isinstance(id, int)`만 검사해 bool과 0/음수를 허용한다. 역사 함수를 추출해 같은 입력으로 대조한 결과다.

```text
id=True  pinned_passed=True  current_passed=False
id=0     pinned_passed=True  current_passed=False
id=-1    pinned_passed=True  current_passed=False
```

수정: 역사 실험 링크는 당시 증거로 보존하고, ‘현재 적용할 전체 검사기’와 `test_invalid_post_identifiers_are_rejected`의 수정 후 고정 커밋 링크를 별도로 제공한다. 본문의 발췌 경고만으로 전체 구현 링크의 계약 불일치가 해결되지는 않는다. 현재 구현의 `type(id) is int and id > 0` 의미를 간결히 설명하고, 역사 실험 4개/현재 재실행 5개의 테스트 수도 구분한다.

완료 기준: 권장 고정 코드와 본문 양의 정수 계약이 일치하며 True/0/-1 거절 및 양의 정수 성공을 같은 실행기에서 재현한다.

### P2 — 공통 준비 조건이 생략되거나 글 끝에 있다

50/290/698/699는 `python3 -m venv .venv`를 안내하지만 최소 버전을 명시하지 않는다. 698/699는 첫 실행 명령보다 설치 설명이 뒤에 있다. 독자는 앞에서 실패한 뒤 글 끝을 찾아야 한다.

수정: 실행 예제 바로 앞에 짧은 준비 안내를 둔다. 저장소 루트, Python 3.11 이상/검증 3.12.9, 가상환경 인터프리터, 의존성 설치, 외부 WordPress에 쓰지 않는 범위를 한 번만 명시한다. 기존 역사 실행시간과 현재 재현 기대 조건은 분리한다.

698/699의 고정 `/tmp/*.json` 결과 파일은 기존 파일이 있으면 실행기가 `FileExistsError`로 재실행을 거부한다. 증거를 덮어쓰지 않는 의도는 좋지만 반복 실행 안내가 없다. `mktemp -d`로 생성한 실행별 디렉터리를 사용하거나 새로운 결과 경로를 지정하라고 안내한다. 기존 파일을 자동 삭제하는 안내는 불필요하다.

### P2 — 706은 현행 계약과 역사 설명이 교차해 독자 판단 비용이 높다

초기 설명은 ‘공개 감사 뒤 체크포인트’, 중간 보정은 ‘발행 확인 뒤 체크포인트, 그 뒤 공개 감사’이며 후반에 다시 초기 흐름을 설명한다. 역사 구분은 있지만 현행 적용을 찾는 독자는 같은 조건을 여러 번 재해석한다. 실제 실행 가능한 최소 테스트 명령도 없고 테스트 링크와 이름만 있다.

수정: 첫 부분에서 현행 실행 순서와 불확실 발행 상태를 먼저 답하고, 역사 순서 변경은 한 절로 모은다. 현재 수정 중인 결과 파일 누락/timeout/unknown 발행 차단을 새로운 운영 관측인 것처럼 쓰지 말고, 실제 재현·수정·테스트 결과 확보 후 후속 보정으로 추가한다. 관련 집중 unittest 명령과 정상/실패 결과를 붙인다.

완료 기준: 새 독자가 본문 하나로 발행 전 실패, 발행 확인, 발행 불확실, 공개 감사 실패를 구분하고 재시도/보류 판단을 실행할 수 있어야 한다.

## 새 주제 판정

이번 확인 범위에서 **새 독립 글 READY를 만들지 않는다.**

현재 수정 중인 `result.json` 누락/unknown/timeout 후 중복 발행과 일일 한도 문제는 기존 706의 핵심 의도 및 ‘프로세스 중단 시 wordpress_write_count="unknown" 미해결’과 직접 겹친다. 50도 POST 응답 유실 중복 위험을 설명하며, 초안 388은 timeout과 중복 발행, 초안 352는 부분 산출물과 프로세스 종료, 초안 277은 결과 불확실과 멱등 처리를 다룬다. 새 제목으로 분리하기 전에 706의 후속 정정·보강이 적합하다.

공개 감사기가 9편으로 고정돼 새 글을 거절하는 문제 역시 그 자체로 사이트 개편 일지나 테스트 수를 늘린 독립 글로 만들지 않는다. 범용 독자가 재사용할 뚜렷한 새 판단과 실제 증거가 생기면 재평가할 수 있으나 현재는 기존 발행 검증 설명 보강에 가깝다.

새 후보가 없는 것은 정상 결과다. 새 글 발행 E2E를 채우기 위해 이 판단을 뒤집으면 편집 컨셉과 모순된다. 실제 AI 작성부터 공개 반영까지 검증이 필요하면 검토된 기존 글의 근거 기반 업데이트 흐름을 별도 계약으로 수행하고, ‘새 독립 글 발행 전체 E2E’와 구분해 보고한다.

## 수정안 산출과 독립 검토 인계

이 검토 후 승인된 작성 범위 안에서 50/290/373/698/699의 제한된 수정안을 만들었다. `content-corrections.json`과 각 `post-ID.before.html`/`post-ID.after.html`이 승인 대상이다. 최종 before는 운영자가 별도 확보한 인증된 GET `content.raw`를 사용했고, 공개 필터링 본문을 raw 대신 덮어쓰지 않도록 전체 원문 해시를 대조했다. ID·제목·slug 변경은 없다.

수정안은 글별로 짧고 다른 준비 설명을 사용한다. 373은 과거 환경/캡처와 새 가상환경 명령을 구분하며, 긴 예제는 하나만 보여 준다. 698은 역사 링크와 강화된 고정 SHA `deff84730558152c9290a9ef36af325adaf002dd`의 적용용 링크를 분리했다. 고정 링크 2개는 비로그인 HTTP 200으로 확인했다. 698/699의 반복 실험은 `mktemp -d` 결과 디렉터리를 사용하며 기존 증거를 삭제하지 않는다.

after HTML에서 373/698/699의 독자용 shell 블록을 추출해 `bash -eu`로 실행했다. 세 명령 모두 종료 코드 0, 373 최대 호출 2회 단언 통과, 두 Lab의 예상 실패/성공 비교 통과와 WordPress 쓰기 0회가 확인됐다. 모든 manifest before/after SHA를 다시 계산해 일치 확인했다. Reviewer가 별도 검토하며, 이 작성 검증은 Reviewer 승인이나 운영 공개 반영을 뜻하지 않는다. 706 수정은 확정된 파이프라인 근거가 전달되기 전까지 만들지 않았다.
