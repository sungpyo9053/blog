sequence size exceeds remaining buffer

That is the whole message. No node name, no log level, no timestamp. In my runs a Humble process printed it once when a Jazzy or Lyrical node was on the same ROS_DOMAIN_ID. It printed it again each time another Jazzy process joined. Humble talking to Humble, Jazzy to Jazzy, Jazzy to Lyrical and Lyrical to Lyrical never printed it.

Short answer: the line means your network mixes Humble with a newer distro. Humble's Fast DDS type support tried to read something it couldn't fit into its own message layout. One clear layout change is rmw_dds_common/msg/Gid, which is char[24] on Humble and char[16] on Jazzy and Lyrical. The message itself does no harm. Topic data with the same message definition still arrived, and so did a direct service call. What breaks is the ROS graph. Humble's ros2 node list came back empty, and ros2 param get said Node not found. The same happened in reverse from Jazzy and Lyrical, which saw no Humble nodes and printed no error at all. The only fix that made everything work was running one distro on every machine. Jazzy with Lyrical worked fully in every test. If you must keep a Humble machine, stay on one RMW vendor everywhere, call services by name, and don't rely on node-based tools across the distro line.

What I ran

Everything ran in Docker on a 2 vCPU Linux host, using the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images. I didn't use --net=host. Each container sat on a user-defined bridge network with its own IP and no shared /dev/shm, so Fast DDS used UDP between them, the same as two machines on a LAN. All containers used ROS_DOMAIN_ID=32 unless noted.

The talker is a short rclpy script, so it runs the same on all three distros:

import sys, rclpy
from rclpy.node import Node
from std_msgs.msg import String
from std_srvs.srv import Trigger

rclpy.init()
name = sys.argv[1]
n = Node(name)
pub = n.create_publisher(String, 'chatter', 10)
count = [0]

def tick():
    count[0] += 1
    m = String(); m.data = '%s %d' % (name, count[0]); pub.publish(m)

def trig(req, res):
    res.success = True; res.message = 'from ' + name; return res

n.create_timer(0.1, tick)
n.create_service(Trigger, 'trigger', trig)
rclpy.spin(n)

For each pair, one container ran the talker and a second container ran these probes in order:

timeout 10 ros2 topic echo /chatter std_msgs/msg/String
ros2 node list --no-daemon --spin-time 3
ros2 topic list --no-daemon --spin-time 3
ros2 service call /trigger std_srvs/srv/Trigger
ros2 param get --no-daemon --spin-time 3 /talker_jazzy use_sim_time

I counted data: lines from the echo and "sequence size exceeds" lines from each command's stderr and from the talker's log. I ran all nine Fast DDS pairs, then Cyclone DDS pairs and cross-vendor pairs, then a few fix attempts. --no-daemon --spin-time 3 matters for a fair test. Without --spin-time, even Humble-to-Humble ros2 param get --no-daemon returned Node not found in my first attempt, because the CLI node hadn't finished discovery.

Why Humble can't read the newer graph data

There are two layers of discovery. DDS discovery tells every participant which topics exist and which types they carry. That part still works across distros, and it is why ros2 topic list and the topic data were fine. Node names live a layer above DDS. Each ROS 2 context publishes a graph message on a hidden topic, and that message lists its nodes and the GIDs of their publishers and subscriptions. The message types are in rmw_dds_common, and ros2 interface show gave this on each image:

# Humble
rmw_dds_common/msg/Gid:  char[24] data
# Jazzy and Lyrical
rmw_dds_common/msg/Gid:  char[16] data

NodeEntitiesInfo holds arrays of Gid, so the byte layout differs between distros. When Humble deserializes a Jazzy graph message, the fields don't line up. A length field ends up pointing past the end of the buffer, and the type support rejects the sample with "sequence size exceeds remaining buffer". The sample is dropped, so Humble never learns the newer distro's node names. When Jazzy or Lyrical reads Humble's longer message, it printed nothing in my runs but also listed no Humble nodes.

That explanation fits everything I measured: the Gid sizes, which side prints the line, and node lists that come back empty while topics work. I didn't trace the bytes of the hidden topic itself, so treat the exact field that fails as an inference.

What breaks and what still works

Topics with the same definition: work

Humble received 90 messages in 10 seconds from the Jazzy talker and 83 from the Lyrical talker, against 90 from a Humble talker. The first message received was number 38 from Jazzy and 37 from Lyrical, against 40 from Humble, so all three started delivering at about the same point. That was std_msgs/String, whose definition didn't change. A custom or core message whose fields changed between distros wasn't part of this test.

Services called by name: work, on one vendor

ros2 service call /trigger succeeded in every Fast DDS pair: Humble to Jazzy, Humble to Lyrical, and back. It took 0.57 to 0.75 seconds, against 1.73 seconds for the Humble-to-Humble run. Each call starts a new process, so these times are mostly discovery and not service latency. I also called a Jazzy node's parameter service directly from Humble:

ros2 service call /talker_jazzy/get_parameters rcl_interfaces/srv/GetParameters '{names: [use_sim_time]}'

It returned bool_value=False. The parameter itself is reachable. Only the tool that first looks the node up fails.

Node-based tools: broken

ros2 node list was empty across the Humble line in both directions. ros2 param get returned Node not found and exit code 1, because it checks the node list before it calls anything. Anything else that builds on node names (node info, rqt_graph and lifecycle tools are the usual ones) depends on the same graph data. I only ran node list and param get, so the other tools are an expectation, not a measurement.

rclcpp nodes print it too

The line comes from the RMW layer, not from rclpy. A Humble robot_state_publisher, which is rclcpp, ran for 10 seconds next to the Jazzy talker and printed it once. Next to a Humble talker it printed nothing. Its normal log lines (got segment a) were the same in both runs.

How often it appears

It isn't printed per message. A Humble ros2 topic echo left running for 30 seconds next to the Jazzy talker printed it once, in the first second, and never again. In a second 20-second run I started an extra Jazzy process (ros2 topic pub) at second 12. The count was 1 before that process started and 6 by the end. New Jazzy participants and their graph updates bring the line back. A steady system prints it once per Humble process. A busy domain where people keep running Jazzy CLI commands prints it constantly. That matches the Stack Exchange report of the message "repeatedly" in every console.

Mixing vendors across the distro line is worse

With a Cyclone Jazzy talker and a Fast DDS Humble client, topic data arrived (89 messages) but ros2 service call /trigger stayed at waiting for service to become available... until timeout killed it after 20 seconds. The reverse pair (Fast DDS Jazzy talker, Cyclone Humble client) also timed out, and the Jazzy talker logged:

RTPS_READER_HISTORY Error] Change payload size of '24' bytes is larger than the history payload size of '11' bytes and cannot be resized.

If some machines must stay on Humble, pick one RMW vendor for every machine on that domain.

A separate domain ID only isolates

Putting Humble on domain 33 and Jazzy on 32 removed the error line. It also removed all communication: 0 messages, an empty node list, and a service call that timed out. That's useful for keeping a Humble robot quiet next to a Jazzy lab, but it isn't a way to connect them. Bridging two domains with a tool such as domain_bridge wasn't part of this test.

What I'd do

  1. Put every machine that has to talk on one distro. The Humble vs Jazzy vs Lyrical comparison covers which one to pick before Humble's EOL. Jazzy and Lyrical together passed every check here.
  2. If one board can't leave Humble (Ubuntu 22.04 only, vendor drivers), run Humble in a container on the newer machines for anything that has to talk to it. Keep the rest on another ROS_DOMAIN_ID.
  3. If you have to mix, keep one RMW vendor on all machines, use topics and services by name, and expect empty node lists and failing ros2 param across the line. Call /node_name/get_parameters or /node_name/set_parameters directly if you need parameters.
  4. Don't try to filter the message out. It's a symptom of the graph data being dropped, and hiding it leaves the empty node list in place.

  • Humble (rmw_fastrtps_cpp 6.2.10, Fast DDS 2.6.12, rmw_dds_common 1.6.0, rosidl_typesupport_fastrtps_cpp 2.2.4) is the only distro that printed the line. Its Gid is char[24].
  • Jazzy (rmw_fastrtps_cpp 8.4.4, Fast DDS 2.14.7, rmw_dds_common 3.1.1) and Lyrical (rmw_fastrtps_cpp 9.4.10, Fast DDS 3.6.2, rmw_dds_common 6.0.0) both use char[16]. They interoperated fully with each other on Fast DDS and on Cyclone DDS, even though Lyrical ships Fast DDS 3.x and Cyclone DDS 11.0.1 while Jazzy ships Fast DDS 2.14 and Cyclone DDS 0.10.5.
  • In the Jazzy-to-Lyrical Fast DDS pair, the Lyrical echo got 63 messages instead of about 88, and the first one was talker_jazzy 67. Discovery took a few seconds longer in that one run. The Lyrical echo also printed !rclpy.ok() once when timeout stopped it. Node list and param get still worked.
  • Default RMW was rmw_fastrtps_cpp on all three images.

FAQ

What does "sequence size exceeds remaining buffer" mean in ROS 2 Humble?

A Humble process using Fast DDS received a sample it couldn't deserialize, and dropped it. In my runs this happened only when a Jazzy or Lyrical node was on the same domain. Humble's graph types differ from the newer ones (Gid is 24 bytes on Humble, 16 on Jazzy and Lyrical), so the newer distro's node information is lost on the Humble side.

Is the message harmful? My topics still work.

The line itself is harmless, and topic data with an unchanged definition arrived at full rate. But it signals that node discovery across the distro line is broken. ros2 node list was empty and ros2 param get returned Node not found in both directions.

Can ROS 2 Humble and Jazzy communicate?

Partly, and not officially. Topics and direct service calls worked when both sides used the same RMW vendor. Node lists and ros2 param did not. With Fast DDS on one side and Cyclone DDS on the other, service calls timed out after 20 seconds. Running one distro everywhere was the only setup where every check passed.

Does switching to Cyclone DDS fix it?

No. With Cyclone DDS on both sides the "sequence size" text was gone. Humble's ros2 node list then failed with "empty node name returned by the RMW layer", and the Humble node logged "invalid data size" errors instead.

Why does Jazzy show no error but also no Humble nodes?

Jazzy and Lyrical didn't print anything when they received Humble's graph data, but they didn't list the Humble nodes either. The error line shows up on the Humble processes, including a Humble node that was only publishing.
