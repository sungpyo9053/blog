The same launch file can also stop with one of these, depending on what is wrong:

[ERROR] [launch]: Caught exception in launch (see debug for traceback): executable '[<launch.substitutions.text_substitution.TextSubstitution object at 0x715d6d7d47c0>]' not found on the PATH

...
AttributeError: module 'xml' has no attribute 'parsers'

Short answer: all three come from the line that builds robot_description from xacro. For the first one, wrap the Command in ParameterValue(..., value_type=str). Without it, launch_ros runs the URDF text through a YAML parser, and a URDF that contains : or # anywhere (a comment is enough) fails. The second one means the xacro program isn't installed. The official ros-base images don't include it, so install ros-<distro>-xacro. The third one means xacro itself failed. The real reason is in the Captured stderr output below it. If that output ends with module 'xml' has no attribute 'parsers', the file path is wrong.

This works on Humble, Jazzy and Lyrical:

from launch import LaunchDescription
from launch.substitutions import Command, FindExecutable, PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue
from launch_ros.substitutions import FindPackageShare

def generate_launch_description():
    xacro_file = PathJoinSubstitution([FindPackageShare('my_robot_description'), 'urdf', 'robot.urdf.xacro'])
    robot_description = ParameterValue(
        Command([FindExecutable(name='xacro'), ' ', xacro_file]),  # note the ' '
        value_type=str)
    return LaunchDescription([
        Node(package='robot_state_publisher', executable='robot_state_publisher',
             parameters=[{'robot_description': robot_description}]),
    ])

In an XML launch file, add type="str" to the <param> tag.

Unable to parse the value of parameter robot_description as yaml

When a parameter value is a substitution such as Command and you don't give it a type, launch_ros evaluates the substitution and passes the resulting text to a YAML parser. That way '5' becomes an integer and 'true' becomes a bool. A URDF is XML, not YAML, but most of it still happens to parse as one long YAML string. It breaks on the two things YAML treats as syntax inside plain text: a colon followed by a space, and a space followed by #.

Running yaml.safe_load on the xacro output gave these errors, the same on PyYAML 5.4.1 (Humble), 6.0.1 (Jazzy) and 6.0.3 (Lyrical):

colon: YAMLError ScannerError mapping values are not allowed here |   in "<unicode string>", line 7, column 12: |       <!-- Note: base frame --> |                ^
hash: YAMLError ParserError expected '<document start>', but found '<scalar>' |   in "<unicode string>", line 8, column 3: |       <link name="base_link"/> |       ^

That's why the error seems to come and go. A URDF works until someone adds a comment like Note: ... or link #1, or a xacro include brings one in, and then launch stops. The xacro banner at the top of every output file (This document was autogenerated by xacro from ...) didn't trigger it. Neither did xmlns:xacro="http://...", because there's no space after those colons.

The URDFs that pass don't come through unchanged, either. With no type given, the plain URDF reached robot_state_publisher as one line. YAML folded every line break into a space. robot_state_publisher still parsed it and logged got segment base_link and got segment wheel on Humble, and Robot initialized on Jazzy and Lyrical. But the parameter isn't the file xacro wrote. With value_type=str it came back as 22 lines, the same text xacro printed.

The fix is the one the error message names. ParameterValue(Command([...]), value_type=str) skips the YAML step. It worked for both the colon and the # files on all three distros. A Python string, such as the result of open().read() or xacro.process_file(path).toxml(), isn't a substitution, so it doesn't go through YAML either. Both worked without ParameterValue. toxml() returns the XML without line breaks, so that one also showed as one line. Note that Command(['cat ', file]) on a plain .urdf failed like the xacro case. The YAML step is about Command, not about xacro.

executable '[<...TextSubstitution object at 0x...>]' not found on the PATH

This one means FindExecutable(name='xacro') searched PATH and found nothing. The odd part is the message. It prints the internal list of substitutions instead of the name xacro, so it isn't obvious what is missing. I got the same text with plain FindExecutable and with PathJoinSubstitution([FindExecutable(name='xacro')]), the pattern the ros2_control demos use. It didn't change between launch 1.0.15 (Humble), 3.4.12 (Jazzy) and 3.9.8 (Lyrical).

In my containers the cause was plain: which xacro printed nothing, because none of the three ros-base images ships xacro. After apt-get install ros-<distro>-xacro, xacro 2.1.1 was at /opt/ros/<distro>/bin/xacro and both FindExecutable forms worked. If xacro is installed and you still get this, the shell that runs ros2 launch probably hasn't sourced /opt/ros/<distro>/setup.bash, since that's what puts /opt/ros/<distro>/bin on PATH. I didn't test that variant separately.

Without FindExecutable, the same missing program shows up as file not found: [Errno 2] No such file or directory: 'xacro'. That message is clearer. It names the program, not the file you passed.

No such file or directory: 'xacro/w/plain.urdf.xacro'

Command joins its list without adding spaces. Command(['xacro', path]) became the single word xacro/w/plain.urdf.xacro, and launch tried to run that as a program. Put the space in the first string ('xacro ') or add a separate ' ' item, as in the fix above. The message looks like a path problem, but the path is fine.

executed command failed and module 'xml' has no attribute 'parsers'

executed command failed. Command: ... means xacro ran and exited with an error. launch shows xacro's stderr under Captured stderr output:, and the cause is there, not in the launch error line. In my runs, an undefined property printed error: name 'wheel_radius' is not defined and a broken closing tag printed XML parsing error: mismatched tag: line 7, column 2. Both made xacro exit with code 2. ParameterValue doesn't help here. With value_type=str the undefined-property file failed the same way.

A wrong file path looks scarier. xacro 2.1.1 (the version on all three distros) first raises FileNotFoundError: [Errno 2] No such file or directory: '/w/missing.urdf.xacro'. While handling that, it trips over its own except xml.parsers.expat.ExpatError line, so the last line of the traceback is:

  File "/opt/ros/humble/local/lib/python3.10/dist-packages/xacro/__init__.py", line 1143, in _process
    except xml.parsers.expat.ExpatError as e:
AttributeError: module 'xml' has no attribute 'parsers'

Running xacro by hand on the missing file printed the same traceback on Humble, Jazzy and Lyrical, and exited with code 1. The AttributeError is a side effect. Scroll up to the first FileNotFoundError and check the path. This is the error in the urdf_tutorial question, where the file turtlebot2.urdf wasn't in the urdf_tutorial share directory.

FAQ

How do I fix "Unable to parse the value of parameter robot_description as yaml"?

Wrap the value as the message says: ParameterValue(Command([FindExecutable(name='xacro'), ' ', path]), value_type=str), imported from launch_ros.parameter_descriptions. In an XML launch file, add type="str" to the <param>. In my run this fixed URDFs containing a colon plus space or a space plus # on Humble, Jazzy and Lyrical.

Why did my URDF work before and now fails with this error?

Without a type, the URDF text goes through a YAML parser. A URDF without a colon plus space or a space plus # passes. A comment like Note: ... or link #1 is enough to make the parser fail. The ones that pass are folded into a single line.

What does "executable '[<launch.substitutions.text_substitution.TextSubstitution object ...>]' not found on the PATH" mean?

FindExecutable(name='xacro') didn't find xacro on PATH. The ros-base Docker images don't include it. Install ros-<distro>-xacro and source /opt/ros/<distro>/setup.bash. The message showed the substitution object instead of the name on all three distros.

Why does xacro end with "AttributeError: module 'xml' has no attribute 'parsers'"?

In xacro 2.1.1 this was the last line when the input file didn't exist. The real error is the FileNotFoundError higher up in the same traceback. Check the path you pass to xacro.

What does "executed command failed. Command: xacro ..." mean?

xacro ran and returned an error. Read the Captured stderr output lines below it. In my runs they showed an undefined property name, a mismatched XML tag, or a missing file.
