(Timestamps removed.) In my runs this line repeated about 9 to 10 times a second, once per scan at 10 Hz, and no map was ever published. RViz then shows "No map received", even though the map frame exists.

Short answer: slam_toolbox looks up odom to base_frame at the time stamp of every scan, and base_frame defaults to base_footprint. If your robot's odometry publishes odom to base_link and you have no base_footprint, that lookup fails on every scan. In my runs that was the one setup that printed this exact warning, apart from a tree where base_link had two parents. Set base_frame in the params file you pass to the launch file:

slam_toolbox:
  ros__parameters:
    odom_frame: odom
    base_frame: base_link     # the child frame your odometry actually publishes
    map_frame: map
    scan_topic: /scan
ros2 launch slam_toolbox online_async_launch.py use_sim_time:=false slam_params_file:=/path/to/my_params.yaml

Passing base_frame:=base_link directly to ros2 launch does not work. The launch file doesn't declare that argument, so launch accepts it without a warning and the node keeps base_footprint. I measured that on Humble, Jazzy and Lyrical. Publishing a static base_link to base_footprint transform also fixed it.

If you see no warning at all and still get no map, the cause is somewhere else. Missing odometry, odometry on a namespaced /tf, a missing laser transform and late odometry stamps all ended in the same Message Filter dropping message ... queue is full line instead. Those are covered below.

What I ran

On 2026-11-21 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one container per distro, with ros-<distro>-slam-toolbox installed from apt (2.6.10 on Humble, 2.8.5 on Jazzy, 2.10.0 on Lyrical). After the install I disconnected each container from the network, so only loopback was left. A small rclpy node played the robot. It published a LaserScan of a 4 by 3 m rectangular room on /scan at 10 Hz in frame laser, an odometry transform at 20 Hz, and a static transform from the base to laser. The robot didn't move. A second node subscribed to /map with transient local QoS and to /tf. It recorded when the first map arrived and whether map to odom was published.

Each of the 24 cases changed one thing: the frame names, which transforms existed, how late the odometry stamps were, or how slam_toolbox was started and configured. Each ran for 15 seconds, or 25 seconds for the ros2 run case with lifecycle calls. I counted the warnings in the log. Everything ran with the default RMW (Fast DDS).

Cause 1: base_frame names a frame you don't have

The shipped mapper_params_online_async.yaml sets odom_frame: odom, base_frame: base_footprint and map_frame: map. This was identical on all three distros. Many robots, and most hobby setups like the one in this question, publish odometry as odom to base_link and have no base_footprint. With that tree, every scan produced one warning. 150 warnings in 15.5 seconds on Humble works out to every scan.

Asking tf directly shows the missing frame. ros2 run tf2_ros tf2_echo odom base_footprint printed this on all three distros:

Waiting for transform odom ->  base_footprint: Invalid frame ID "base_footprint" passed to canTransform argument source_frame - frame does not exist

The first attempt said Invalid frame ID "odom" instead, because tf2_echo's own buffer hadn't received anything yet. Wait a second before you trust the first line. To read the frame slam_toolbox is really using, ask the node: ros2 param get /slam_toolbox base_frame returned String value is: base_footprint.

The warning comes from slam_toolbox's scan callback. Before it uses a scan, it transforms an identity pose in base_frame into odom_frame at the scan's stamp. If tf can't do that, it logs the warning and drops the scan. The message filter in front of the callback only checks odom to laser, and here odom to base_link to laser was complete, so every scan reached the callback and then failed. That is also why map to odom was still being published (656 to 736 messages in 15 s) while /map got nothing. The map frame existed, but there was no map.

Launch arguments that aren't declared are ignored

ros2 launch slam_toolbox online_async_launch.py --show-args lists only use_sim_time and slam_params_file on Humble. Jazzy and Lyrical add autostart and use_lifecycle_manager. There is no base_frame, odom_frame or scan_topic argument. When I added base_frame:=base_link to the command, launch printed no warning. The node still reported base_footprint and logged the same warning 136 to 152 times. The command in slam_toolbox issue #678 passes all its frames that way.

Frame names have to go into the params file. I copied the shipped file, changed only base_frame to base_link and passed it with slam_params_file:=. The warning dropped to 0 and the first map arrived after 5.0, 5.6 and 6.1 s on Humble, Jazzy and Lyrical. Copy the whole file and don't write a short one with only the frames. The launch file loads only the file you give it, so a short file leaves every other parameter at the code default. Those defaults are different from the shipped file: map_update_interval is 10 s in the Humble and Jazzy source, against 5.0 in the file.

Cause 2: base_link with two parents

A common setup has the URDF define base_footprint as the parent of base_link, while the odometry node publishes odom to base_link. In tf a frame can have only one parent, and here base_link had two. I published a static base_footprint to base_link next to the dynamic odom to base_link, with default params. The result was the same warning, 137, 136 and 146 times, and no map. The fix is to make the odometry publish to the root of your URDF (odom to base_footprint), or to set base_frame to the frame the odometry actually publishes. Turning the static transform around (base_link to base_footprint, so base_footprint hangs below base_link) also worked. That gave 0 warnings on Humble and Lyrical, 1 on Jazzy at startup, and a map after 5.2 to 5.5 s on all three.

The silent cases: the scan never gets through

slam_toolbox receives scans through a tf2_ros::MessageFilter that waits until odom to laser can be computed at the scan's stamp. If that never happens, the scan is dropped before the callback, and "Failed to compute odom pose" never prints. Three different setups looked exactly the same:

  • No odometry transform at all, only the static base to laser.
  • Odometry published on /robot1/tf, as namespaced multi-robot setups do, while slam_toolbox listened on /tf.
  • Odometry present, but no transform from the base to laser.

In all three, the log had 6 lines like this in 15 seconds, while no scan at all reached the callback:

[INFO] [slam_toolbox]: Message Filter dropping message: frame 'laser' at time 1795252952.311 for reason 'discarding message because the queue is full'

This line is printed at INFO, not WARN. There was also no map to odom transform, so RViz says the map frame doesn't exist. Check the chain with tf2_echo odom laser. If that works and the drops continue, look at the stamps. The Message Filter dropping message post shows how to read the two times in this line and separate a clock mismatch from a normal wait.

Late odometry stamps and scan_queue_size

Here the frames were right, but the odometry was stamped some time before "now", as it is when odometry is computed on another machine or behind a filter. The shipped params set transform_timeout: 0.2, and scan_queue_size isn't in the file, so the code default of 1 applies. With a queue of one, a scan that has to wait for tf is pushed out when the next scan arrives 0.1 s later. I changed the lag and the two parameters:

"Updates stopped" means the last map to odom stamp was 11 or 13 seconds older than the end of the run. slam_toolbox stamps that transform from the last scan it accepted, so the old stamp shows that only a few early scans got in. Close to the limits the outcome changed from run to run and from distro to distro. Leave a margin.

Raising only the timeout didn't help, because the queue of one still pushed every scan out. With scan_queue_size: 10 and the timeout too short, the drop reason changed to 'the timestamp on the message is earlier than all the data in the transform cache'. Setting both helped: a queue that covers the lag at your scan rate, and a timeout longer than the lag. The better fix is to stamp odometry with the time it describes and keep it close to the scan clock. Two other setups worked without changes. Odometry at only 2 Hz with correct stamps gave a map on all three distros, with 6 queue-full lines. So did scans stamped a full second in the past.

The same timing rules apply to your own code that looks up transforms. The lookup_transform timing post measured that asking for "now" failed 1,800 times out of 1,800 at 10, 50 and 100 Hz.

Jazzy and Lyrical: ros2 run leaves it unconfigured

From Jazzy on, slam_toolbox is a lifecycle node. online_async_launch.py configures and activates it because autostart defaults to true. ros2 run slam_toolbox async_slam_toolbox_node --ros-args -p base_frame:=base_link -p use_sim_time:=false doesn't. On Jazzy and Lyrical the node logged nothing. After 4 seconds ros2 lifecycle get /slam_toolbox said unconfigured [1], and no map came in 15 seconds. On Humble the same command worked and the first map arrived after 10.0 s (code default map_update_interval of 10 s). On Jazzy and Lyrical, these two calls fixed it:

ros2 lifecycle set /slam_toolbox configure
ros2 lifecycle set /slam_toolbox activate

Both returned Transitioning successful. The first map arrived 15.7 s (Jazzy) and 17.0 s (Lyrical) after the node started, which includes the 3-second wait and the two CLI calls.

Version notes

The warning text, the shipped frame names, transform_timeout: 0.2 and the missing scan_queue_size were the same in slam_toolbox 2.6.10 (Humble), 2.8.5 (Jazzy) and 2.10.0 (Lyrical). Jazzy and Lyrical print three more lines before the first warning (the lifecycle "Configuring" and "Activating" messages). They also need the lifecycle transitions when started with ros2 run. The launch file's use_sim_time defaults to true on all three. With no /clock publisher and correct frames, that default still gave a map after 5.2 s, 5.5 s and 6.1 s. In my setup it was not a cause of this warning. Simulated time with a real /clock is a separate case that I didn't run. If you replay a bag instead, the ros2 bag play /tf_static post measured when static transforms go missing during playback, which ends in the same "frame does not exist" state.

FAQ

What does "Failed to compute odom pose" mean in slam_toolbox?

The scan reached slam_toolbox, but tf couldn't transform base_frame into odom_frame at the scan's stamp, so the scan was dropped. In my runs this happened when base_frame (default base_footprint) wasn't in the same chain as the odometry, for example because the robot only had base_link.

Why doesn't ros2 launch slam_toolbox online_async_launch.py base_frame:=base_link work?

The launch file only declares use_sim_time and slam_params_file (plus autostart and use_lifecycle_manager on Jazzy and Lyrical). Other arguments are accepted silently and not passed to the node. Put base_frame in a copy of the params file and pass it with slam_params_file:=.

Why do I get "No map received" in RViz with no warning?

Scans were dropped before slam_toolbox's callback. Missing odometry, odometry on a namespaced tf topic, a missing laser transform and odometry stamps 0.25 s or more late all gave only INFO lines saying Message Filter dropping message and "queue is full", and no map.

slam_toolbox on Jazzy does nothing when started with ros2 run. Why?

It is a lifecycle node and stays unconfigured. Run ros2 lifecycle set /slam_toolbox configure and then activate, or start it with online_async_launch.py, which does both because autostart defaults to true.

Does increasing transform_timeout fix Message Filter dropping message?

Not alone. With 0.6 s of odometry lag and transform_timeout: 1.0, every scan was still dropped, because scan_queue_size defaults to 1. Setting scan_queue_size: 10 together with the longer timeout gave a map at 0.6 and 1.0 s of lag.
