Short answer: the warning is harmless. Every build that printed it finished, and ros2 run started the node every time, on Humble and Jazzy. You only see it if your colcon is old. colcon-core 0.16.0 and later start setup.py with -W ignore:setup.py install is deprecated, and 0.18.4 added -W ignore:easy_install command is deprecated. The current ROS images ship colcon-core 0.21.3, and none of their builds printed either warning. So the fix is to update colcon (sudo apt update && sudo apt install python3-colcon-core) rather than downgrade setuptools. If you can't update, this filter hid both warnings on Humble and Jazzy:

export PYTHONWARNINGS="ignore:setup.py install is deprecated,ignore:easy_install command is deprecated"

Don't run pip install setuptools==58.2.0 on Jazzy or Lyrical. On Python 3.12 and 3.14 that version can't even be imported, and the build fails. With the colcon that ships in the images, every build failure in this test came from a setuptools installed with pip. After pip uninstall setuptools, all three distros built again.

What I ran

On 2026-10-29 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another. The script makes a package with ros2 pkg create --build-type ament_python --node-name stl_node stl_pkg. The generated setup.cfg already uses script_dir and install_scripts with underscores. Each case does three builds:

  1. a plain colcon build in a clean workspace
  2. colcon build --symlink-install in a clean workspace
  3. a plain build on top of that symlink build, which makes colcon undo the old develop install

After each build I ran ros2 run stl_pkg stl_node, which prints Hi from stl_pkg.. I counted the warnings and checked for an .egg-link file to see if the symlink install was real. I changed one thing per case:

  • the apt setuptools, untouched
  • eight PYTHONWARNINGS values
  • a setup.cfg with dash keys
  • no setup.cfg
  • 17 pinned setuptools versions from pip plus the latest (84.2.1), each installed in front of the apt one, and then removed again
  • colcon-core 0.15.2 from pip, which predates the filter, so I could see the warning at all
  • a newer packaging from pip on Humble
  • a workspace carried over from the apt setuptools to pip setuptools 84.2.1

Why a current colcon shows nothing

With the apt setuptools and colcon-core 0.21.3, all three distros built without any deprecation warning, plain or with --symlink-install. The same held for every pip setuptools that could build. The reason shows up in one of the failing runs, where colcon printed the command it had started: ['/usr/bin/python3', '-W', 'ignore:setup.py install is deprecated', '-W', 'ignore:easy_install command is deprecated', 'setup.py', '--help-commands']. colcon filters the two messages itself. In the colcon-core history, the first filter came in 0.16.0 ("Suppress setup.py deprecation warnings during build", #626). The easy_install one came in 0.18.4 (#676).

To see the warning I installed colcon-core 0.15.2 from pip. On Humble and Jazzy it showed up as shown at the top of this post. Every build still finished, and the node ran after each one. With setuptools 58.2.0 on Humble, the old colcon printed neither warning. 59.6.0, 65.5.0 and 69.5.1 all printed both. That fits the common advice that 58.2.0 is the last quiet version, but it only matters with an old colcon.

On Lyrical, colcon-core 0.15.2 didn't work at all. The extensions that build Python packages failed to load with cannot import name 'OVERRIDE_OPT' from 'em', and colcon said No task extension to 'build' a 'ros.ament_python' package. So I couldn't reproduce the warning on Lyrical.

If you see the warning, check your version with python3 -c "import colcon_core; print(colcon_core.__version__, colcon_core.__file__)". A path under /usr/local or ~/.local means a pip install is shadowing the apt one.

Which setuptools version you have and why

You get the version apt installed (59.6.0, 68.1.2 or 78.1.1 above) unless something put a newer one in front of it with pip. That something is often pip install -U setuptools, or a requirements.txt that pulls it in. To check, run python3 -c "import setuptools; print(setuptools.__version__, setuptools.__file__)". A path in /usr/local/lib or ~/.local/lib is a pip copy. This is what each pip version did with colcon-core 0.21.3:

None of the builds that worked printed a deprecation warning, and the node ran after each one. A failure stopped all three builds in the case: plain, symlink and the switch back. In each case the node wasn't installed (Package 'stl_pkg' not found).

The failures have different causes.

  • 58.2.0 to 65.5.0 on Jazzy and Lyrical. These versions call pkgutil.ImpImporter, which Python 3.12 removed. The error comes from pkg_resources as soon as setup.py imports setuptools. The popular pip install setuptools==58.2.0 fix only works on Humble.
  • 68.2.0 everywhere. colcon-python-setup-py 0.2.9 reads the package metadata by evaluating what setup.py prints. With 68.2.0 that output isn't a valid Python literal, and ast.literal_eval raises SyntaxError. 68.1.2 and 69.5.1 were fine. This is the failure from colcon-python-setup-py issue 56.
  • 71.1.0 and newer on Humble. These setuptools versions use the packaging already installed, and Humble's apt packaging is 21.3. Its canonicalize_version() doesn't accept strip_trailing_zero. After pip install packaging (26.3), all of 71.1.0, 75.8.0, 79.0.1, 80.0.0, 80.9.0 and 84.2.1 built on Humble, and the node ran.
  • 80.0.0 and newer with --symlink-install. The build said nothing, but no stl-pkg.egg-link was written. colcon-core 0.21.3 found no --editable option in setup.py develop and did a normal install. In the 84.2.1 run, the only trace was in log/latest_build/logger_all.log: INFO:colcon.colcon_core.task.python.build:No '--editable' capability in setuptools, falling back to full install. Edits to your Python files then need a rebuild. colcon-core 0.15.2 has no such check. On Jazzy, with 84.2.1, it failed with error: option --editable not recognized.

One more trap shows up when you upgrade setuptools under an existing workspace. On all three distros, I built with --symlink-install under the apt setuptools, then installed 84.2.1 with pip (plus packaging 26.3 on Humble). After that, both colcon build --symlink-install and a plain colcon build failed with error: option --uninstall not recognized. colcon tries to undo the old develop install first, and the new setuptools no longer has that option. The old install was still there, so ros2 run kept working. After rm -rf build install log the build passed.

To go back to the apt setuptools, run python3 -m pip uninstall setuptools. On Jazzy and Lyrical my script set PIP_BREAK_SYSTEM_PACKAGES=1 for every pip command. On all three distros, the apt version was active again after that, and the plain, symlink and switch builds all passed with the node running. The apt package files were untouched. dpkg -V python3-setuptools listed only documentation files that the image itself doesn't ship.

Dash-separated keys in setup.cfg

The other stderr block you can still get with a current colcon comes from setup.cfg. With script-dir and install-scripts instead of script_dir and install_scripts, every build printed a --- stderr: stl_pkg block. On Humble the warning was a UserWarning: Usage of dash-separated 'install-scripts' will not be supported in future versions. Please use the underscore name 'install_scripts' instead. Jazzy printed SetuptoolsDeprecationWarning: Invalid dash-separated options. Lyrical, and pip setuptools 80.9.0 and 84.2.1 on Jazzy, named the key: Invalid dash-separated key 'script-dir' in 'develop' (setup.cfg), please use the underscore name 'script_dir' instead. Each build still finished and the node ran. Changing the dashes to underscores removes the block.

Don't delete setup.cfg to get rid of it. Without the file the build was clean, but ros2 run said No executable found. I covered that case, and how entry points and script_dir decide where the script lands, in ros2 run "No executable found" for ament_python.

Version notes

The three distros differed in four ways.

  • Warning text. On Humble, with setuptools 59.6.0, the warning is one line ending in "Use build and pip and other standards-based tools." Jazzy's 68.1.2 prints the boxed version.
  • Old pins. Old setuptools pins break on Jazzy and Lyrical because of their Python version.
  • New pip setuptools on Humble. Only Humble breaks on a new pip setuptools, because of its old packaging.
  • Old colcon on Lyrical. The old colcon I used to show the warning doesn't run on Lyrical at all.

colcon-python-setup-py issue 58 reports No module named 'setuptools.extern.packaging' with setuptools 72.2.0. I didn't get that error. 72.2.0 built on Jazzy and Lyrical with colcon-python-setup-py 0.2.9, and on Humble it failed earlier with the canonicalize_version() error.

Not tested

Foxy, Iron, Kilted and Rolling. colcon or setuptools inside a venv or conda env. pip installs to ~/.local (--user). colcon-core versions between 0.15.2 and 0.21.3. setuptools 66.x, 67.x, 73.x, 76.x, 77.x and the 81 to 84 releases other than 84.2.1. FAQ

Is "SetuptoolsDeprecationWarning: setup.py install is deprecated" an error?

No. In every build that printed it, colcon reported the package as finished and ros2 run started the node. It is printed in colcon's --- stderr block, which looks alarming but doesn't fail the build.

Why do I see this warning when others don't?

Your colcon-core is probably older than 0.16.0. Newer versions start setup.py with -W filters for both messages, and colcon-core 0.21.3 on Humble, Jazzy and Lyrical printed nothing with any setuptools that could build. Update colcon, and check that no pip copy in /usr/local or ~/.local shadows the apt one.

Should I run pip install setuptools==58.2.0?

Not on Jazzy or Lyrical. There, 58.2.0 failed every build with module 'pkgutil' has no attribute 'ImpImporter'. On Humble it built, and with an old colcon it was the only version I tested that printed no warning. With a current colcon you don't need it on any distro.

Which PYTHONWARNINGS value hides it?

ignore:setup.py install is deprecated,ignore:easy_install command is deprecated hid both warnings on Humble and Jazzy. Module-based values such as ignore:::setuptools.command.install worked on Humble but not on Jazzy, where the warning is reported from setuptools._distutils.cmd.

Why does colcon build fail with error: option --uninstall not recognized?

The workspace was built with --symlink-install under an older setuptools, and you upgraded setuptools with pip. colcon tries to undo the old develop install, and setuptools 84.2.1 no longer accepts --uninstall. Delete build, install and log and build again, or remove the pip setuptools.
