--- stderr: py_pkg
error: can't copy 'models/': doesn't exist or not a regular file
---
Failed   <<< py_pkg [0.80s, exited with code 1]

After a --symlink-install build you may see the same error with a path inside build/, for example error: can't copy '/w3/build/py_pkg/launch/b.launch.py': doesn't exist or not a regular file. An ament_cmake package that switches from a plain build to --symlink-install can fail with a related message: failed to create symbolic link '.../build/cm_pkg/ament_cmake_python/cm_pkg/cm_pkg' because existing path cannot be removed: Is a directory.

Short answer: setuptools prints this error when an entry in data_files in setup.py is not a regular file. In my runs that happened for three reasons. The path was wrong, the list held a folder, or the file was deleted or renamed after a --symlink-install build, which leaves a broken symlink in build/. Read the path in quotes and match it to a case:

  • A short relative path ('worlds/my_world.wbt', 'my_world.wbt'): the file isn't at that path relative to the folder with setup.py. Fix the path.
  • A folder ('models/', 'launch/include'): your glob() matched a directory. Build one data_files entry per folder and list only files (code below).
  • A path under build/ that names a file you deleted or renamed: remove the stale package folders and rebuild:
rm -rf build/my_pkg install/my_pkg
colcon build --symlink-install --packages-select my_pkg

For the ament_cmake "Is a directory" error, rm -rf build/my_pkg fixed it. --cmake-clean-cache and --cmake-clean-first didn't.

What I ran

I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, with no extra packages. The script makes a fresh workspace for each case. py_pkg is an ament_python package with two launch files, a.launch.py and b.launch.py, installed with glob('launch/*.launch.py'). cm_pkg is an ament_cmake package that installs a Python module with ament_python_install_package(), a launch folder with install(DIRECTORY ...) and a script with install(PROGRAMS ...). For each build I logged the exit code, wall time and error lines. After each build I listed the build/ and install/ folders and marked every entry as file, directory, symlink or dangling symlink.

The baseline package built without errors with both colcon build and colcon build --symlink-install on all three distros. Exit codes were identical on Humble and Jazzy for every step. Lyrical differed only in the ament_cmake switch and in two message details, covered below.

Cause 1: the path is wrong

Each data_files entry is a pair: the destination folder under install/<pkg>, then a list of source files. The source paths are relative to the package folder, the one that holds setup.py, and they have to include the subfolder. If my_world.wbt sits in worlds/, then ['my_world.wbt'] failed and ['worlds/my_world.wbt'] built. This is the mix-up in the Stack Overflow question listed at the end, but in reverse. That user wrote the correct worlds/... path and was told to drop the folder. In my run, dropping the folder is what broke the build.

No shell runs here, so ~ is not expanded. ['~/my_world.wbt'] failed with the literal ~ in the message. Keep data files inside the package and use relative paths.

This cause fails the same way with or without --symlink-install, and deleting build/ doesn't help. The message names the exact string from setup.py, so search for it there.

Cause 2: a folder in the file list

data_files takes files, not folders. The common way to "install a folder with subfolders" is glob('models/**', recursive=True), and it returns the folders too. In my run it returned:

['models/', 'models/robot', 'models/robot/model.sdf', 'models/robot/meshes', 'models/robot/meshes/base.dae']

setuptools stopped at the first entry: can't copy 'models/'. On Lyrical (Python 3.14.4) the first entry had no trailing slash, so the message read can't copy 'models'. Search for both forms.

The same thing happened with a plain glob('launch/*') when launch/ held a subfolder named include. The pattern *.launch.py doesn't match a folder, so it didn't hit this.

I compared two fixes. Filtering the glob with os.path.isfile built, but it flattened the tree. model.sdf and base.dae both landed directly in share/py_pkg/models/, and the robot/ and meshes/ levels were lost. If the files reference each other by relative path, that breaks them. The fix that kept the tree adds one data_files entry per folder:

import os
from glob import glob
from setuptools import setup

package_name = 'my_pkg'

def tree(src, dst):
    out = []
    for d, _, files in os.walk(src):
        out.append((os.path.join(dst, d), [os.path.join(d, f) for f in files]))
    return out

setup(
    name=package_name,
    packages=[package_name],
    data_files=[
        ('share/ament_index/resource_index/packages', ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
        ('share/' + package_name + '/launch', glob('launch/*.launch.py')),
        *tree('models', 'share/' + package_name),
    ],
    # ...
)

With tree(), install/py_pkg/share/py_pkg/models held robot/model.sdf and robot/meshes/base.dae in their folders. That held for a plain build (copies) and for --symlink-install (symlinked files inside real folders). An empty folder models/empty was installed as an empty folder in the plain build.

Cause 3: you deleted or renamed a file after --symlink-install

This cause produces the confusing version of the error, with a path in build/ that points at a file you know you removed. With --symlink-install, colcon fills build/py_pkg/ with symlinks to your source files and runs setup.py from there. When I deleted src/py_pkg/launch/b.launch.py, its link stayed behind:

build/py_pkg/launch:
  a.launch.py (symlink)
  b.launch.py (DANGLING-symlink)

Python's glob('launch/*.launch.py'), run in build/py_pkg, still returned both names. A dangling symlink matches the pattern, but it isn't a regular file, so the next colcon build --symlink-install failed with exit code 1:

error: can't copy '/w3/build/py_pkg/launch/b.launch.py': doesn't exist or not a regular file

Renaming behaved the same way. After mv b.launch.py c.launch.py, the glob in build/ returned a, b and c, and the build failed on the old name b.launch.py. This matches colcon-core issues #633 and #692, which were both still open when I checked.

Some variations didn't fail, but they still left something stale behind:

SequenceBuild resultWhat install/.../launch held afterwards
Symlink build, delete b, plain colcon buildexit 0a.launch.py as a copied file, b.launch.py as a dangling symlink
Symlink build, rename b to c, plain buildexit 0a and c as files, b dangling
Plain build, delete b, plain buildexit 0a and the old b, both still regular files
Explicit list instead of glob: symlink build, delete b and remove it from setup.py, symlink buildexit 0a symlink, b dangling
Symlink build, delete a Python module (py_pkg/old_mod.py), symlink buildexit 0not checked

So switching to a plain build "fixes" the error but leaves the dangling link in install/. colcon doesn't delete installed files that are no longer part of the package. A plain build doesn't either: after a delete, the old copied b.launch.py stayed installed as a regular file.

Fix options compared

Each fix started from the same state. I did a --symlink-install build, deleted b.launch.py, applied the fix, then ran colcon build --symlink-install. The result was the same on all three distros.

Nothingexit 1, can't copya, b dangling

find build/py_pkg -xtype l -deleteexit 0 (it deleted build/py_pkg/launch/b.launch.py)a, b dangling
rm -rf build/py_pkg install/py_pkgexit 0a only
rm -rf build install logexit 0a only

The leftover link in install/ matters when something tries to use it. With only build/py_pkg removed, ros2 launch py_pkg b.launch.py still found the name, then failed with Caught multiple exceptions when trying to load file of format [py] and FileNotFoundError: [Errno 2] No such file or directory: '/w3/install/py_pkg/share/py_pkg/launch/b.launch.py'. ros2 launch py_pkg a.launch.py worked. Removing both build/<pkg> and install/<pkg> for the one package is the smallest fix that left nothing stale. You don't need to wipe the whole workspace.

Cost: for this one small package, a --symlink-install rebuild after rm -rf build/py_pkg took about as long as a no-op rebuild. On Humble that was 1669, 1659 and 1686 ms against 1678, 1653 and 1673 ms over three runs. On Jazzy and Lyrical every run was between about 2.0 and 2.5 s. The time is mostly colcon's own startup. For a package with compiled code, removing build/<pkg> means compiling it again. I didn't measure that.

The ament_cmake version: "Is a directory"

ament_python_install_package() in an ament_cmake package keeps a staging copy of your Python package in build/<pkg>/ament_cmake_python/<pkg>/<pkg>. A plain build makes it a real directory. On Humble and Jazzy, a later --symlink-install build tried to replace it with a symlink to src/. CMake refuses to delete a directory there, so the target ament_cmake_python_symlink_cm_pkg failed:

The CMake cache options don't touch that staging folder, so they didn't help. Deleting the staging folder alone fixed the build. Deleting build/cm_pkg is easier to remember, but it forces a full reconfigure.

The failed build also leaves a trap. On Humble and Jazzy, after the failed switch, the installed __init__.py was still a copy in install/, not a link to src/. When I changed x=1 to x=2 in the source, import cm_pkg still gave x=1. After rm -rf build/cm_pkg and a symlink build, the installed file resolved to src/cm_pkg/cm_pkg/__init__.py and the edit showed up without a rebuild.

The reverse switch was fine. A --symlink-install build, then a plain build, then --symlink-install again all exited 0 on every distro. In every ament_cmake sequence, my source files stayed regular files with their original content. One side effect: after the plain build, the installed launch file was still a symlink. For ament_python, plain to symlink and back also built without errors on all three distros.

Version notes

  • The ament_python errors were identical on Humble (setuptools 59.6.0, Python 3.10.12), Jazzy (setuptools 68.1.2, Python 3.12.3) and Lyrical (setuptools 78.1.1, Python 3.14.4). The one difference was 'models/' vs 'models' from the recursive glob.
  • All three used colcon-core 0.21.3 and colcon-python-setup-py 0.2.9, so I couldn't compare colcon versions.
  • The "Is a directory" error appeared on Humble (ament_cmake_python 1.3.14, CMake 3.22.1) and Jazzy (2.5.6, CMake 3.28.3), but not on Lyrical (2.8.8, CMake 4.2.3). On Lyrical the staging path stayed a real directory even in a fresh --symlink-install build. The installed __init__.py still resolved to src/, and edits showed up without a rebuild after every sequence I tried.
  • One Lyrical anomaly: in the glob('launch/*') case, the plain build failed first. The --symlink-install build after it then failed earlier with a different error: error: [Errno 17] File exists: '/w2b/build/py_pkg/resource/py_pkg' -> '/w2b/install/py_pkg/share/ament_index/resource_index/packages/py_pkg'. The failed plain build had left a copied resource marker in install/. Humble and Jazzy reported the folder error in the same sequence. If you see [Errno 17] File exists after a failed build, remove install/<pkg> and fix the setup.py problem from the earlier failure.

Not tested

I didn't test Windows, where symlinks need extra permissions and fail with other messages. I also didn't test merged installs (--merge-install), packages with compiled C++ code (rebuild cost after removing build/), pyproject.toml-only packages, colcon versions other than 0.21.3, Foxy, Iron or Rolling. I didn't check what package_data or MANIFEST.in do with folders either.

FAQ

What does "can't copy ... doesn't exist or not a regular file" mean?

setuptools tried to install an entry from data_files and it wasn't a regular file. In my runs the entry was a wrong path, a folder returned by glob, or a dangling symlink in build/ left by a file deleted after a --symlink-install build.

I deleted a launch file and now colcon build fails. How do I fix it?

Run rm -rf build/my_pkg install/my_pkg and build again. Removing only build/my_pkg made the build pass, but a dangling link stayed in install/, and launching that file then failed with a FileNotFoundError.

How do I install a folder with subfolders from setup.py?

Add one data_files entry per folder, for example with os.walk, and list only files in each entry. glob('models/**', recursive=True) includes the folders and fails. Filtering it with os.path.isfile builds, but it installs every file into one flat folder.

Does --cmake-clean-cache fix "failed to create symbolic link ... Is a directory"?

No. On Humble and Jazzy it failed with the same error, and so did --cmake-clean-first. Removing build/my_pkg, or just build/my_pkg/ament_cmake_python, fixed it. Lyrical didn't show the error.

Is it safe to switch between colcon build and colcon build --symlink-install?

Symlink to plain worked for both build types on all three distros, and my source files weren't changed. Plain to symlink failed for ament_cmake packages with ament_python_install_package() on Humble and Jazzy until build/<pkg> was removed. It worked for ament_python packages.
