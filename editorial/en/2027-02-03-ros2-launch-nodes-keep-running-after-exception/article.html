The prompt is back and the exit code is 1, so it looks like launch stopped. But the two nodes that started before the bad one are still running. In my container their parent was now PID 1. Nothing in the log says they were ever started.

Short answer: this is a known bug in launch (ros2/launch#747). When an action throws after some processes were started, launch shuts down before it has handled the "process started" events. The processes it already spawned never get a signal. In my runs it happened in 34 of 34 failing launches on Humble and in 31 of 34 on both Jazzy and Lyrical. The upstream fix (PR #996) is merged in Rolling only. Until it reaches your distro, the cleanup that worked every time was to kill the launch's process group after it exits:

#!/bin/bash
# run_launch.sh: start ros2 launch in its own process group, then clean that group up
setsid ros2 launch "$@" &
pid=$!
wait $pid
rc=$?
kill -TERM -- -$pid 2>/dev/null   # every orphan is still in this group
exit $rc

If the nodes are already orphaned, find their group and kill it the same way: ps -eo pid,pgid,ppid,cmd | grep -- --ros-args, then kill -TERM -- -PGID. In my runs the orphans always kept the process group of the ros2 launch that started them, and killing that group left 0 of them alive 1.5 seconds later, on all three distros.

What I ran

On 2026-11-21 I ran the same script in ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base, one container at a time, with --init and --network none. One launch file built a different description depending on an environment variable: two good nodes plus one of the failures in the table. For each run the script:

  • started ros2 launch in a new session, with SIGINT at its default action, the way a terminal starts it;
  • waited for it to exit (30 seconds at most) and recorded the exit code and time;
  • counted live node processes 1 second and 3 seconds after the exit by reading /proc, skipping zombies;
  • on the first run of each case, ran ros2 node list --no-daemon;
  • sent SIGTERM to the launch's process group, waited 1.5 seconds and counted again;
  • killed anything left before the next run.

I repeated each case 3 to 6 times. Then I sent Ctrl+C (SIGINT to the process group) to a healthy launch after 0.1, 0.3, 1 and 3 seconds, sent SIGINT, SIGTERM and SIGKILL to the launch PID alone, and tried ros2 launch --print-description. Last, I patched the installed launch_service.py with the change from PR #996 and ran the failing cases again. That added up to 120 launches per distro.

My first attempt gave misleading results. A background job of a non-interactive bash starts with SIGINT ignored, and children inherit that. Ctrl+C at 0.1 seconds then looked like it hung launch for 30 seconds. I threw that run away and started every launch through a small wrapper that resets SIGINT. The script in the evidence folder is the corrected one.

Why the nodes survive

Launch spawns processes in the background. It learns that one has started from an event, which runs later in its event loop. When the next action throws, launch catches the exception and starts its shutdown. In the stock code, shutdown checks whether the loop is idle by looking at its entity futures and the event queue. It doesn't look at the asyncio tasks that are still spawning processes. One commenter on the issue traced it to this check: launch "waits till it is 'idle' to shutdown, but the way it decides if it's idle is flawed: It doesn't take into account async tasks still running". So launch decides there's nothing left to stop and exits.

The log shows this. In the failing runs, the stock log contained the ERROR line and nothing else. It had no process started with pid lines for the nodes that were running. With the patch, the same launch logged the ERROR line, then both process started lines, then sending signal 'SIGINT', then process has died [pid ..., exit code -2, ...] for each node.

After ros2 launch exits, the orphans are re-parented. In the container their parent PID was 1. Their process group didn't change, which is why killing the group works. They kept running: the counts 1 and 3 seconds after the exit were always the same. Whenever the first run of a case left orphans, ros2 node list --no-daemon listed them by name. The rclpy nodes were orphaned the same way as the C++ ones.

Failures that left nothing behind

Three kinds of failure never left orphans in my runs.

A bad node listed first fails before anything is spawned, so there's nothing to orphan. The error text was the same as in the bad-last case.

A typo in a keyword argument (Node(ackage='tf2_ros', ...)) fails while generate_launch_description() is building the list. Nothing has started yet. The message was Caught multiple exceptions when trying to load file of format [py]: - TypeError: Action.__init__() got an unexpected keyword argument 'ackage'. A comment on the issue reports orphans from this typo. That would need the typo to be in a description built after other nodes have started, for example in an included file. I didn't test that layout.

A failure that came 2 seconds later, from a bad node inside a TimerAction, shut the earlier nodes down every time. Launch exited after 2.51 to 2.72 seconds, and no nodes were left. By then the start events had been handled. So the bug is about failures that come while processes are still being spawned, which in practice means a mistake in the launch file itself.

Includes leave the child's nodes too

This is the case in the Stack Exchange question about zombie nodes from a child launch file. The parent started two nodes and included a child file. The child started one node and then hit the bad executable. All three nodes survived in every run on all three distros: ros2 node list showed /pk66a, /pk66b and /pk66child. An include that pointed at a missing file failed with [Errno 2] No such file or directory: '/w/does_not_exist.launch.py'. It left the parent's two nodes running in 4 of 4 runs.

SIGTERM and SIGKILL to ros2 launch also leave orphans

A healthy launch stopped with Ctrl+C never left anything behind. I sent SIGINT to its process group after 0.1, 0.3, 1 and 3 seconds, 4 times each, and got 0 survivors on all three distros. At 0.1 seconds launch hadn't started any nodes yet. It exited with code 130 in 207 to 277 ms. From 0.3 seconds on, it logged user interrupted with ctrl-c (SIGINT) and the nodes exited. SIGINT sent to the launch PID alone after 3 seconds also stopped both nodes. A comment on the issue says it "might happen when you press Ctrl+C too quickly after launching". I didn't reproduce that at these four delays.

Signals other than SIGINT were different. kill -TERM on the ros2 launch PID ended it with exit code 143, and both nodes kept running in 3 of 3 runs on every distro. It printed nothing. That's odd, because the installed launch_service.py has a SIGTERM handler that logs using SIGTERM can result in orphaned processes, and that line never appeared. kill -KILL left both nodes too, which is expected, because a killed process can't clean up. If a supervisor, IDE or script stops launch this way, signal the process group or use SIGINT. The node shutdown post measured how rclpy nodes react to Ctrl+C and SIGTERM, and launch's 5-second escalation from SIGINT to SIGTERM.

FAQ

Why are my ROS 2 nodes still running after ros2 launch failed?

Launch caught an exception while it was still starting processes, then shut down without signalling the ones it had already spawned (ros2/launch#747). In my runs this happened in 34 of 34 such failures on Humble and 31 of 34 on Jazzy and Lyrical. The nodes keep running with PID 1 as their parent.

How do I kill nodes left over from a failed launch?

They stay in the process group of the ros2 launch that started them. Find it with ps -eo pid,pgid,cmd, then run kill -TERM -- -PGID. That left none alive after 1.5 seconds in every run. Starting launch with setsid and killing the group after it exits does the same automatically.

Is this fixed in Jazzy or Lyrical?

Not in the images I measured (launch 3.4.12 on Jazzy, 3.9.8 on Lyrical, 1.0.16 on Humble). The fix, ros2/launch PR #996, is in Rolling. Backports for Jazzy and Lyrical were open on 2026-11-21. Applying the same change by hand removed every orphan on all three.

Does Ctrl+C leave orphaned nodes too?

Not in my runs. Ctrl+C at 0.1, 0.3, 1 and 3 seconds after start left 0 nodes on all three distros. SIGTERM or SIGKILL sent only to the ros2 launch process did leave both nodes running, every time.

Which launch errors leave nodes running?

Errors raised after the first processes were spawned: a bad executable in a later node, an exception in an OpaqueFunction, an undeclared LaunchConfiguration, and a broken or missing included file. An error in the first action, a typo caught while the description is built, and a failure 2 seconds later left nothing.
