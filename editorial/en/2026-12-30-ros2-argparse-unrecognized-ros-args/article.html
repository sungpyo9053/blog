usage: argnode.py [-h] [--speed SPEED]
argnode.py: error: unrecognized arguments: --ros-args -r __node:=renamed --params-file /tmp/launch_params_vtai2416
[ERROR] [argnode.py-1]: process has died [pid 221, exit code 2, cmd '/ws/install/argp/lib/argp/argnode.py --speed 2.0 --ros-args -r __node:=renamed --params-file /tmp/launch_params_vtai2416'].

From ros2 run the same error ends with [ros2run]: Process exited with failure 2.

Short answer: your Python node hands all of sys.argv to argparse, and sys.argv also holds the ROS arguments. ros2 launch adds --ros-args to every Node it starts, even one with no name, remaps or parameters. ros2 run passes on whatever you type after the executable. argparse doesn't know these flags, so it prints the usage line and exits with code 2 before your node exists. Strip the ROS block before parsing, and give the full list to rclpy.init:

import sys
import argparse
import rclpy
from rclpy.utilities import remove_ros_args

parser = argparse.ArgumentParser()
parser.add_argument('--speed', type=float, default=1.0)
args = parser.parse_args(remove_ros_args(args=sys.argv)[1:])   # your flags only

rclpy.init(args=sys.argv)    # the full list, so -p, -r and --params-file still apply

With this change the same launch file printed RESULT mode=remove speed=2.0 node=/renamed rate=5 on Humble, Jazzy and Lyrical. The user flag, the node rename and the parameter all arrived. In C++, rclcpp::init_and_remove_ros_arguments(argc, argv) does the same job and returns only your arguments.

What I ran

One ament_cmake package, argp, built with colcon inside the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images. It installs two nodes.

  • argnode.py, an rclpy node with one argparse flag, --speed (float, default 1.0), and one ROS parameter, rate (default 1). It prints sys.argv[1:], parses it in one of three modes chosen by an environment variable, and then prints the speed, its own full name and rate. The modes are strict (parse_args()), known (parse_known_args()) and remove (parse_args(remove_ros_args(args=sys.argv)[1:])). An optional second flag, -r/--repeat, tests a user flag that shares a letter with a ROS flag.
  • cppnode, an rclcpp node that calls either rclcpp::init or rclcpp::init_and_remove_ros_arguments and prints the arguments it is left with.

Four launch files start these nodes. plain.launch.py sets only arguments=['--speed', '2.0']. named.launch.py adds name='renamed' and parameters=[{'rate': 5}]. rosargs.launch.py uses ros_arguments=['-p', 'rate:=7']. cpp.launch.py starts the C++ node with a name and a parameter. Each case ran once per distro under timeout 40. I recorded the exit code and the wall time, which includes the startup of ros2 run or ros2 launch. The default RMW was used. The script is repro.sh in the evidence folder.

All three distros gave the same results. Only the version strings, PIDs, temp file names and timings changed, plus the line numbers in one Python traceback.

What ros2 run and ros2 launch put in sys.argv

With no ROS arguments, plain parse_args() works. ros2 run argp argnode.py --speed 2.0 printed ARGV ['--speed', '2.0'] and exited 0. ros2 run adds nothing of its own.

Add any ROS argument and it fails. All three of these exited with code 2:

Command (strict parser)argparse said
--speed 2.0 --ros-args -p rate:=5unrecognized arguments: --ros-args -p rate:=5
--ros-args -r __node:=renamedunrecognized arguments: --ros-args -r __node:=renamed
--speed 2.0 --ros-args --log-level warnunrecognized arguments: --ros-args --log-level warn

ros2 launch always adds something. Even plain.launch.py, with no name, remaps or parameters, started the node as argnode.py --speed 2.0 --ros-args. A bare --ros-args was enough to kill it:

[argnode.py-1] ARGV ['--speed', '2.0', '--ros-args']
[argnode.py-1] usage: argnode.py [-h] [--speed SPEED]
[argnode.py-1] argnode.py: error: unrecognized arguments: --ros-args
[ERROR] [argnode.py-1]: process has died [pid 214, exit code 2, cmd '/ws/install/argp/lib/argp/argnode.py --speed 2.0 --ros-args'].

Your own arguments always came first, and launch put its ROS block at the end. name= became -r __node:=renamed. parameters= became --params-file with a temp file under /tmp/launch_params_*. ros_arguments=['-p', 'rate:=7'] produced two blocks, --ros-args -p rate:=7 --ros-args. That happened on Humble too, so ros_arguments exists there (launch_ros 0.19.14).

One more thing to know when you debug this in CI. In every launch case where the node died with code 2, ros2 launch itself exited 0. The only sign was the process has died line. If a script checks only the exit code of ros2 launch, it will pass.

Fix 1: remove_ros_args (the one that worked everywhere)

rclpy.utilities.remove_ros_args(args=sys.argv) returns the list without the ROS block. The first item is still the program name, so slice it off with [1:] before you hand it to parse_args.

CaseLeft for argparseResult
ros2 run ... --speed 2.0 --ros-args -p rate:=5['--speed', '2.0']speed=2.0 node=/argnode rate=5, exit 0
named.launch.py['--speed', '2.0']speed=2.0 node=/renamed rate=5, finished cleanly
Typo: --sped 2.0 --ros-args -p rate:=5['--sped', '2.0']unrecognized arguments: --sped 2.0, exit 2

The typo row matters. With remove_ros_args, argparse still rejects a flag it doesn't know. You keep strict checking for your own arguments and lose it only for the ROS block.

Pass the full list to rclpy.init

The cleaned list is for argparse only. I called rclpy.init twice in one script with ['prog', '--speed', '2.0', '--ros-args', '-p', 'rate:=5']. Once I passed the cleaned list, once the full one:

init(cleaned) rate = 1
init(full) rate = 5

Passing the cleaned list raised no error. The parameter just never arrived. The same would happen to remaps, --params-file and __node:=. Call rclpy.init(args=sys.argv), or rclpy.init(), which reads sys.argv itself.

Fix 2: parse_known_args (works, with two traps)

parse_known_args() returns your parsed flags plus a list of everything it didn't recognize. It fixed the crash. The leftover list in the launch case was ['--ros-args', '-r', '__node:=renamed', '--params-file', '/tmp/launch_params_c8c07ijb'], and the node came up as /renamed with rate=5.

Trap one: typos pass silently. --sped 2.0 --ros-args -p rate:=5 exited 0 with speed=1.0. The typo landed in the leftover list next to the ROS block, and the default stayed.

Trap two: a user flag that shares a name with a ROS flag takes the ROS value. I added -r/--repeat to the parser and ran --speed 2.0 --ros-args -r __node:=renamed. argparse treated -r as --repeat:

EXTRA ['--ros-args']
RESULT mode=known speed=2.0 node=/renamed rate=1 repeat=__node:=renamed

The node was still renamed, because rclpy read the full sys.argv. But your program got repeat=__node:=renamed. remove_ros_args removes the block before argparse sees it, so the same command gave repeat=none. ROS uses -r and -p inside the block. Avoid those short flags in your own parser, or use remove_ros_args.

Order on the command line: your flags first, or close the block with --

Everything after --ros-args belongs to ROS until a -- or another --ros-args. If you put your own flag inside the block, the ROS parser rejects it:

CommandModeResult
--ros-args -p rate:=5 -- --speed 2.0removespeed=2.0 rate=5, exit 0
--ros-args -p rate:=5 --speed 2.0removerclpy._rclpy_pybind11.UnknownROSArgsError: ['--speed', '2.0'], exit 1
--ros-args -p rate:=5 --speed 2.0strictunrecognized arguments: --ros-args -p rate:=5, exit 2
--ros-args -p rate:=5 --speed 2.0rclcpp, init_and_remove_ros_argumentsfound unknown ROS arguments: '--speed', '2.0', Aborted

In the strict row, argparse listed only the ROS block as unknown. It had parsed --speed 2.0 without trouble. So the message shows what argparse rejected, not where the real ordering mistake is. In the remove row, remove_ros_args raised the error itself, before argparse ran. The rclcpp case ended in terminate called after throwing an instance of 'rclcpp::exceptions::UnknownROSArgsError', and ros2 run printed [ros2run]: Aborted. My wrapper recorded exit status 250 for it on all three distros.

Launch files don't have this problem. Launch always put arguments before its own --ros-args. The ordering trap only appears when you type the command yourself. The same scoping rule, applied to --params-file and -p placed before --ros-args, is covered in the params YAML and -p errors post.

rclcpp: argv still holds the ROS block

C++ nodes don't crash on their own, because nothing parses argv unless you write code that does. But rclcpp::init(argc, argv) leaves argv unchanged. After ros2 run argp cppnode --speed 2.0 --ros-args -p rate:=5, the node saw five arguments:

ARGS_SEEN 5: [--speed] [2.0] [--ros-args] [-p] [rate:=5]
RESULT cpp node=/cppnode rate=5

Any hand-written loop over argv, or a library such as getopt, gets the ROS block too. rclcpp::init_and_remove_ros_arguments(argc, argv) returned a std::vector<std::string> with the program name plus [--speed] [2.0], and it still applied the parameter (rate=5). Under cpp.launch.py it gave node=/cpp_renamed rate=5 and finished cleanly.

Another fix is to drop the command-line flag and declare a ROS parameter instead. Then -p speed:=2.0 and parameters=[{'speed': 2.0}] work with no argument handling at all. I didn't measure this as a separate case, but the rate parameter took that path in every run above.

Timing

The failure is immediate. In single runs, a strict ros2 run that hit the argparse error took 337 to 344 ms on Humble, 430 to 436 ms on Jazzy and 581 to 646 ms on Lyrical. That includes starting ros2 run. The successful remove_ros_args run of the same command took 487, 587 and 718 ms. These are one run each on a shared 2 vCPU machine, so treat them as rough.

FAQ

Why does ros2 launch pass --ros-args when my Node has no parameters?

launch_ros adds it to every Node. With only arguments=['--speed', '2.0'], the command was argnode.py --speed 2.0 --ros-args on Humble, Jazzy and Lyrical. A bare --ros-args was enough to make strict argparse exit with code 2.

Should I use parse_known_args or remove_ros_args?

remove_ros_args. Both stopped the crash. But parse_known_args silently ignored the typo --sped, and it gave a user -r flag the value __node:=renamed. remove_ros_args still rejected the typo and kept -r safe.

Why are my -p parameters ignored after the fix?

You probably passed the cleaned list to rclpy.init. With the cleaned list, rate stayed at 1. With the full list, it was 5. Give argparse the cleaned list and rclpy.init the full sys.argv.

What does UnknownROSArgsError with my own flag in it mean?

Your flag is inside the --ros-args block. --ros-args -p rate:=5 --speed 2.0 failed in rclpy and rclcpp. --speed 2.0 --ros-args -p rate:=5 and --ros-args -p rate:=5 -- --speed 2.0 both worked.

Why does ros2 launch exit 0 when my node died?

In these runs launch reported process has died [pid ..., exit code 2, ...], and ros2 launch still returned 0. Check for the process has died line, not only for the exit code.
