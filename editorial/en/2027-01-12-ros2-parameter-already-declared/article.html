terminate called after throwing an instance of 'rclcpp::exceptions::ParameterAlreadyDeclaredException'
  what():  parameter 'speed' has already been declared
[ros2run]: Aborted

In Python the same mistake ends in a traceback. On Jazzy and Lyrical the last line is rclpy.exceptions.ParameterAlreadyDeclaredException: Parameter(s) already declared: ['speed']. On Humble it reads ('Parameter(s) already declared', ['speed']).

Short answer: something declared the same parameter name twice on the same node. A node can declare each name only once. The second declare_parameter call throws, and if nothing catches it, a C++ node aborts and a Python node exits with status 1. Find the second declaration. Then delete it, give it a different name, or guard it so it only runs when the name doesn't exist yet:

if not self.has_parameter('speed'):
    self.declare_parameter('speed', 1.0)
speed = self.get_parameter('speed').value
if (!node->has_parameter("speed")) {
  node->declare_parameter("speed", 1.0);
}
double speed = node->get_parameter("speed").as_double();

The guard worked in rclpy and rclcpp on Humble, Jazzy and Lyrical. The "second declaration" is often not in your own code. It comes from the node itself (use_sim_time), from a node option (automatically_declare_parameters_from_overrides), from a second plugin or helper object, or from a lifecycle on_configure that runs a second time. The table below maps each of these to what I saw.

What I ran

On 2026-11-13 (KST) I ran one script inside the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro after another, on a 2 vCPU Ubuntu host. Each container had --network none and ROS_DOMAIN_ID=88, so no DDS traffic left it. The script builds one ament_cmake package with two executables, a Python node and a C++ node. Each takes a mode name as its first argument, runs one case and exits. Every case ran as its own ros2 run process: 13 Python cases, 15 C++ cases (the two helper cases are C++ only), one extra Python case and one ros2 launch run. The script captured the last 12 lines and the exit status of each run.

The C++ node uses rclcpp::Node and, for the lifecycle cases, rclcpp_lifecycle::LifecycleNode. The Python node uses rclpy.node.Node and rclpy.lifecycle.Node. The parameter is named speed with a default of 1.0 unless stated. Exit statuses below are what the shell saw from ros2 run: 1 for an uncaught Python exception, and 250 for the C++ abort, with [ros2run]: Aborted printed by ros2 run.

Cause 1: the same name declared twice in your code

This is the plain case. Two lines, same name, same node:

n.declare_parameter('speed', 1.0)
n.declare_parameter('speed', 1.0)

The second line threw on all three distros, even with the same default value. In rclpy the traceback ends inside declare_parameters, because declare_parameter is a thin wrapper around it. The last line of your own file in the traceback is the second declaration. That line is the one to fix.

In C++, terminate called after throwing an instance of 'rclcpp::exceptions::ParameterAlreadyDeclaredException' gives no file or line. When the name alone doesn't point you to the code, grep for it in your package and in any library code that receives your node handle.

The usual fix is to declare every parameter once, in the constructor, and read it with get_parameter everywhere else. Declaring is a setup step, not a way to read the value.

Cause 2: you declared use_sim_time

Every node declares use_sim_time for itself when it is created. Declaring it again in your constructor threw the same exception on all three distros, in both languages:

rclpy.exceptions.ParameterAlreadyDeclaredException: Parameter(s) already declared: ['use_sim_time']
what():  parameter 'use_sim_time' has already been declared

Passing -p use_sim_time:=true didn't change this. The override sets the value of the existing parameter. It doesn't stop your second declaration from failing.

The fix is to delete the declaration and read it:

use_sim = self.get_parameter('use_sim_time').value

Set it from outside, with -p use_sim_time:=true, a params file, or parameters=[{'use_sim_time': True}] in a launch Node action. I didn't measure launch's SetParameter action here.

Cause 3: automatically_declare_parameters_from_overrides

With this node option set, the node declares every parameter it finds in its overrides (from -p, --params-file or launch) as soon as it is created. If your code then declares one of those names, it is the second declaration.

n = Node('decl_node', automatically_declare_parameters_from_overrides=True)
n.declare_parameter('speed', 1.0)   # throws if -p speed:=... was given

What I saw:

That middle row is why this cause is confusing. The node runs fine in testing, then crashes the first time someone passes that parameter from a YAML file. A file you add later can break a node that used to work.

Pick one approach per node. Either drop the option and declare everything yourself, or keep the option and read values with get_parameter_or (or a has_parameter guard before declaring). rclcpp issue #2189 discusses whether this option should be deprecated at all.

Cause 4: two plugins or helpers on the same node

Plugins, costmap layers, controller helpers and image_transport publishers often get your node handle and declare their own parameters on it. If two of them use the same short name, the second one fails. I reproduced this in C++ with a small helper class that declares enabled in its constructor, created twice on one node:

[INFO] [decl_node]: RESULT helper declared enabled=1
terminate called after throwing an instance of 'rclcpp::exceptions::ParameterAlreadyDeclaredException'
  what():  parameter 'enabled' has already been declared

Giving each instance a prefix fixed it. With left. and right. the same class declared left.enabled and right.enabled, and the node ran to the end on all three distros. This is the reason so many packages put a plugin name before every parameter, as in voxel_layer.enabled. If you see an already-declared error with a dotted name like that, check whether the same plugin name is loaded twice.

Cause 5: a lifecycle node declares in on_configure

Declaring parameters in on_configure works the first time. After cleanup the parameters are still declared, so the next configure declares them again. I ran configure, cleanup, configure on a lifecycle node that declares rate in on_configure.

In rclcpp the lifecycle machinery caught the exception:

[ERROR] [lc_node]: Caught exception in callback for transition 10
[ERROR] [lc_node]: Original error: parameter 'rate' has already been declared
[WARN] [lc_node]: Callback returned ERROR during the transition: configure

The node stayed unconfigured and the process kept running with exit status 0. Nothing crashes, so the error is easy to miss in a busy log. In rclpy the second trigger_configure() returned TransitionCallbackReturnType.ERROR and the node also stayed unconfigured. Whether you see a traceback depends on the distro (see version notes).

Two fixes work. Declare the parameters in the constructor and only read them in on_configure, or guard the declaration with has_parameter. With the guard, the second configure reached inactive in both languages on all three distros. ros/diagnostics made the same change in PR #227.

Catching the exception keeps the first declaration's value. The default in your second call is ignored. In the test, the first call set 1.0 and the caught second call asked for 2.0, and the parameter stayed 1.0. If the two defaults differ, catching hides a real disagreement, so the guard or a rename is usually better.

The undeclare route behaves differently in the two client libraries. In rclcpp, a parameter declared with a plain default is statically typed and can't be undeclared:

parameter 'speed' has invalid type: cannot undeclare a statically typed parameter

rclpy undeclared the same statically typed parameter without complaint and let me declare it again with a new default. Code that relies on that won't port to C++.

The guard costs almost nothing. 100,000 has_parameter checks took 10.3 to 15.3 ms in rclpy and 7.8 to 11.3 ms in rclcpp across the three distros, one run each. That is in the range of 0.1 microseconds per check, so there's no reason to avoid it in a callback.

FAQ

What does "parameter has already been declared" mean in ROS 2?

The node tried to declare a parameter name it already has. Each name can be declared once per node. The second declare_parameter call throws ParameterAlreadyDeclaredException. Uncaught, it aborted the C++ node and exited the Python node with status 1.

Why does declaring use_sim_time throw this error?

Every node already declares use_sim_time when it is created. Don't declare it. Read it with get_parameter('use_sim_time') and set it from outside with -p use_sim_time:=true or launch parameters. Passing the override did not prevent the error.

Why does my node crash only when I pass a parameter from YAML?

The node probably uses automatically_declare_parameters_from_overrides. With that option, any parameter in the overrides is declared at startup, so your own declare_parameter becomes the second one. Without an override for that name, the same code ran fine. Use get_parameter_or or a has_parameter guard.

Why does my lifecycle node fail on the second configure?

Parameters declared in on_configure are still declared after cleanup. The next configure declares them again, the transition returns ERROR, and the node stays unconfigured. Declare in the constructor, or guard with has_parameter.

Can I undeclare a parameter and declare it again?

In rclcpp only if it was declared with dynamic_typing set to true. A statically typed parameter gave "cannot undeclare a statically typed parameter". rclpy allowed it either way in my runs.
