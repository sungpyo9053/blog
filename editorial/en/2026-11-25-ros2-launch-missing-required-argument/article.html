[INFO] [launch]: Default logging verbosity is set to INFO
[ERROR] [launch]: Caught exception in launch (see debug for traceback): Included launch description missing required argument 'x' (description: 'the x value'), given: []

The process exits with code 1. You get this exact text in two situations: you ran a launch file with a required argument and didn't set it, or a parent file included that file and didn't pass the argument. The word "Included" shows up in both cases. When you run a file directly, ros2 launch still includes it internally.

Short answer: a DeclareLaunchArgument with no default_value only counts as given when the IncludeLaunchDescription that loads its file passes it in launch_arguments. The parent declaring the same name doesn't count, and neither does putting x:=... on the command line of the parent. Pass it explicitly:

IncludeLaunchDescription(
    PythonLaunchDescriptionSource(child_path),
    launch_arguments={'x': LaunchConfiguration('x')}.items(),   # .items() is required
)

In XML, put an <arg name="x" value="..."/> inside the <include>. Both forms worked on Humble, Jazzy and Lyrical. Optional arguments behave the other way round. An argument that has a default quietly picks up whatever value the parent or the command line already set, even when nobody passed it. Most of the surprises below come from those two rules.

Required arguments are checked against launch_arguments only

This is the case behind most "missing required argument" questions. My parent file declared x with a default of parent_x and included the child without passing anything. It failed. Running the bare parent with x:=cli also failed. The required check only looks at what the include passes, so both values were invisible to it. The same thing is reported in ros2/launch#907 and ros2/launch#749, both still open.

Passing it explicitly fixed every case:

The last row matters. A value written into launch_arguments beats the command line. If you want the user to be able to override it, pass LaunchConfiguration('x') and declare x in the parent, as in the third row.

launch_arguments needs pairs

The launch_arguments doesn't work question uses .items() correctly, and the code samples you copy from usually do too. But if you drop .items(), the error doesn't mention it. Iterating a dict gives only the keys, and launch expects (name, value) pairs. What you see depends on the child and the distro:

  • Child argument required, Humble or Jazzy: 'NoneType' object is not iterable. With ros2 launch -d the traceback ends in launch/actions/include_launch_description.py at argument_names.extend(ild_action._try_get_arguments_names_without_context()).
  • Child argument required, Lyrical: the normal missing required argument 'x' message with given: []. That makes it look like you never passed anything.
  • Child argument has a default, all three: not enough values to unpack (expected 2, got 1).

A list of tuples works the same as .items(). Values have to be strings or substitutions. An int ({'x': 5}.items()) failed with 'int' object is not iterable. Write '5' or str(5).

Optional arguments leak in both directions

The launch argument scope when nesting launch files question and ros2/launch#689 both describe values crossing file boundaries. I measured it with child_y.launch.py. Here's what the child printed for y and u, and what the parent printed for z after the include:

Three things follow from this:

  • Down: a parent's value overrides the child's default_value. The child's default is only used when nothing above it set the name. A CLI value even reached u, which neither file declared.
  • Up: with a plain include, the child's declared z was still set in the parent afterwards. GroupAction(scoped=True) stopped that and nothing else.
  • Isolation: only forwarding=False stopped values from flowing down, and then the CLI values didn't reach the child either. launch_configurations={...} on the same GroupAction is how you pass selected values through.

A required argument behind forwarding=False still needs explicit passing. The parent declared x, and the child inside the non-forwarding group failed with the usual missing required argument 'x'. The XML case in #689, where the child has no <arg> at all and still sees the parent's value, matches the plain-include rows above. I measured it with Python launch files, not that exact XML pair.

A misspelled argument is silently ignored

ros2 launch larg sim.launch.py use_sim_tme:=true exited 0 with no warning. The file printed SIM use_sim_time=false, its default. ros2 launch accepted the unknown name and set a configuration nobody reads. The spelling only gets checked when the misspelled name leaves a required argument unset. Then you see the stray name in given:, as with X:=1. Argument names are case-sensitive. To catch typos, run --show-args first and compare the names.

LaunchConfiguration default vs DeclareLaunchArgument default

I declared w with default_value='from_declare' and read it with LaunchConfiguration('w', default='from_lc_default') once before the declaration and once after it:

The order is CLI, then DeclareLaunchArgument default, then the LaunchConfiguration default. But the declare default only applies once that action has run, so the position in the list matters. The LaunchConfiguration default is a fallback for "not set yet". It isn't an argument, and --show-args doesn't know about it:

v isn't listed. A required argument is listed with no (default: ...) line. --show-args on a parent also lists the arguments of the files it includes. For the parent that includes the required-x child without passing it, the output listed 'x' as if you could set it from the command line, and setting it there still failed. That's the question in what is different between DeclareLaunchArgument and LaunchConfiguration. Both read the same value, but only the declaration makes it an argument.

IfCondition ignores case for true and false and accepts 1 and 0. As a node parameter, 1 doesn't become a bool. It arrives as an INTEGER, so a node that declared flag as a bool would reject it. The message text, exit codes, leak behavior, --show-args output and boolean handling matched on Humble (launch 1.0.15), Jazzy (launch 3.4.12) and Lyrical (launch 3.9.8). Two things differed:

  • A bare dict in launch_arguments with a required child argument gave 'NoneType' object is not iterable on Humble and Jazzy, and Included launch description missing required argument 'x' (description: 'the x value'), given: [] on Lyrical. FAQ

Why does "Included launch description missing required argument" appear when I pass the argument on the command line?

Because the file that declares it is included by another launch file, and that include didn't pass it. In my run x:=cli on the parent didn't satisfy the child's required x. Add launch_arguments={'x': LaunchConfiguration('x')}.items() to the include and declare x in the parent.

What happens if I forget .items() on launch_arguments?

Launch gets the dict's keys instead of name and value pairs. On Humble and Jazzy that gave 'NoneType' object is not iterable. On Lyrical it gave the missing required argument error. When the child argument had a default, all three gave not enough values to unpack (expected 2, got 1).

Do launch arguments from the parent leak into included files?

Yes. A parent or CLI value overrode the child's default_value, and the child's declared values were visible in the parent after a plain include. GroupAction(scoped=True) stopped the upward leak only. forwarding=False stopped the downward one too.

Does ros2 launch warn about a misspelled argument name?

No. use_sim_tme:=true exited 0 with no message, and use_sim_time kept its default false. Check names with --show-args.

Which strings count as true for IfCondition?

true, True, TRUE and 1. yes and on aborted the launch with invalid condition expression. As a node parameter, 1 became an INTEGER, not a bool.
