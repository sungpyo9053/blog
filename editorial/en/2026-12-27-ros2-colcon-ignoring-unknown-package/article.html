$ colcon build --packages-select pkg_aa
[0.291s] WARNING:colcon.colcon_core.package_selection:ignoring unknown package 'pkg_aa' in --packages-select

Summary: 0 packages finished [0.22s]
$ echo $?
0

Short answer: colcon looked for a package whose <name> in package.xml is exactly pkg_aa, under the folder you ran it from, and found none. It then builds nothing and still exits with code 0. The name has to match the <name> tag, not the folder name, and the package has to be visible from where you run colcon. Ask colcon what it can see, then select one of those names:

cd ~/ros2_ws                 # the workspace root, the folder that contains src/
colcon list --names-only     # every package colcon found
colcon build --packages-select pkg_a

If the name you want isn't in the colcon list output, the problem is discovery, not spelling. The usual causes in my runs were a COLCON_IGNORE file in a parent folder, a package placed inside another package's folder, a folder starting with a dot, or a package in a different workspace. All of these behaved the same on Humble, Jazzy and Lyrical.

Because the exit code is 0, a script or CI job that runs colcon build --packages-select with a wrong name passes without building anything. Two ways to make it fail are covered below: --packages-up-to, which exits 1 for an unknown name, and a grep on colcon's output.

What I ran

On 2026-11-06 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, as root. The script builds a workspace at /ws with small packages: pkg_a (ament_cmake), my_py_pkg (ament_python), and one package for each broken layout in the table. Then it runs 37 colcon commands. Before each one it deletes build/, install/ and log/. After each one it records the output, the exit code, the time in seconds and the folders in install/.

First, colcon list printed what colcon discovered. It found 8 packages. pkg_ign, inner_pkg, pkg_hid and other_ws_pkg were missing, and those four later gave the warning:

bad_xml	src/bad_xml	(cmake)
my_py_pkg	src/my_py_pkg	(ros.ament_python)
outer	src/outer	(ros.ament_cmake)
pkg_a	src/pkg_a	(ros.ament_cmake)
pkg_link	src/pkg_link	(ros.ament_cmake)
plain_proj	src/plain_cmake	(cmake)
py_nosetup	src/py_nosetup	(ros.ament_python)
real_name	src/folder_name	(ros.ament_cmake)

A correct colcon build --packages-select pkg_a took 1.248 s on Humble, 1.545 s on Jazzy and 1.479 s on Lyrical, and left install/pkg_a. Each run that ended with the warning took between 0.395 and 0.623 seconds and created no package folders in install/. It's fast, which is part of why it's easy to miss.

The name comes from package.xml, exactly

colcon matches the string you pass against the <name> in each package.xml. The match is exact. Pkg_A didn't match pkg_a, and my-py-pkg didn't match my_py_pkg. The folder name doesn't count. A folder called src/folder_name holding <name>real_name</name> was unknown as folder_name and built fine as real_name. This is the cause in the "colcon can not find my package" ROS Answers thread, where a copied package.xml still had the old name.

For a plain CMake folder with no package.xml, colcon took the name from project(). The folder src/plain_cmake with project(plain_proj NONE) was listed as plain_proj.

To see every name at once without trusting folder names:

colcon list --names-only
grep -rho --include=package.xml '<name>[^<]*</name>' src | sort

The grep found 8 names in my workspace, including pkg_ign, inner_pkg and pkg_hid, which colcon didn't list. It missed the symlinked pkg_link and the broken bad_xml, so treat it as a cross-check, not a full list. A name that grep finds but colcon list doesn't is a discovery problem. The next section covers those.

colcon didn't find the package at all

By default colcon searches from the current directory down. Four layouts hid a package that was there on disk:

  • An ignore marker in a parent folder. src/ignored/COLCON_IGNORE hid src/ignored/pkg_ign. If you copied an old workspace, or someone parked a package there on purpose, check for COLCON_IGNORE, AMENT_IGNORE or CATKIN_IGNORE files with find src -name '*_IGNORE'. The COLCON_IGNORE build-time test covers when you'd want one.
  • A package inside another package. With src/outer/package.xml and src/outer/inner_pkg/package.xml, colcon found outer and stopped looking below it. inner_pkg was unknown. Packages placed side by side under src/ were all found.
  • A hidden folder. src/.hidden/pkg_hid was never listed.
  • Another workspace. /ws2/src/other_ws_pkg was unknown from /ws. colcon build --base-paths src /ws2/src --packages-select other_ws_pkg built it, exit 0. Passing only --base-paths /ws2 made pkg_a unknown in turn, because --base-paths replaces the default search path instead of adding to it.

A symlinked package folder was fine. src/pkg_link pointing to /elsewhere/pkg_link was listed and built.

Where you run colcon

From an empty folder, colcon build --packages-select pkg_a gave the warning and exit 0. From /ws/src and from /ws/src/pkg_a, the same command found pkg_a and built it, because the package was below the current directory. But it put build/, install/ and log/ in that folder. In the /ws/src run the result landed in /ws/src/install/pkg_a. Your /ws/install/setup.bash won't see that copy. So the build "worked" and your change still won't show up. Run colcon from the workspace root.

Comma lists and flags after --packages-select

--packages-select takes names separated by spaces. pkg_a,my_py_pkg was treated as one package name, and nothing was built. Use --packages-select pkg_a my_py_pkg.

A wrong name next to a good one doesn't stop the build. --packages-select pkg_a pkg_aa printed the warning for pkg_aa, built pkg_a, and exited 0. In a long build log that warning is easy to scroll past.

Mistyped flags after --packages-select behaved differently from the old colcon-core issue #325, where words with a leading hyphen were taken as package names. In my runs, --packages-select pkg_a -symlink-install (one dash) was rejected:

colcon build: error: argument --packages-select: unrecognized argument: -symlink-install

That printed the usage text and exited with code 2. A shortened flag, --symlink-instal, was accepted as --symlink-install. The build exited 0 and install/pkg_a/share/pkg_a/package.xml was a symlink, the same as with the full flag.

Missing setup.py and broken package.xml fail differently

In colcon-core issue #208 (2019), an ament_python package without setup.py produced has no 'setup.py' file, then the unknown-package warning. That's not what I got. With colcon-core 0.21.3 and colcon-ros 0.5.0, py_nosetup was listed as ros.ament_python, the build started, and it failed with exit 1:

AssertionError: Expected ['/usr/bin/python3', '-W', 'ignore:setup.py install is deprecated', '-W', 'ignore:easy_install command is deprecated', 'setup.py', '--help-commands'] to pass: /usr/bin/python3: can't open file '/ws/src/py_nosetup/setup.py': [Errno 2] No such file or directory

A package.xml with a mismatched tag (</nam>) wasn't hidden either. colcon listed it as a plain (cmake) package, named from project(). The build then failed in ament_package() with exit 1:

catkin_pkg.package.InvalidPackage: Error(s) in package '/ws/src/bad_xml/package.xml':
The manifest contains invalid XML:
mismatched tag: line 2, column 35

If your folder name and project() name differ from the broken <name>, you would select by the old name and get the unknown-package warning instead. I didn't test that combination.

Version notes

Behavior and message text were the same on all three distros. All three images had the same colcon packages: colcon-core 0.21.3, colcon-package-selection 0.2.10 and colcon-ros 0.5.0. Lyrical had colcon-output 0.2.14 and colcon-parallel-executor 0.4.0, where Humble and Jazzy had 0.2.15 and 0.3.0. Two differences showed up on Lyrical only:

  • The time prefix on log lines was a large negative number, for example [-1793925401641418752.000s] WARNING:colcon.colcon_core.package_selection:ignoring unknown package 'pkg_aa' in --packages-select. Humble and Jazzy printed [0.291s]-style values. The rest of the line was identical, so search for the text after the bracket.
  • CMake 4.2.3 printed CMake Deprecation Warning ... Compatibility with CMake < 3.10 will be removed for my cmake_minimum_required(VERSION 3.8), so each CMake build on Lyrical also reported 1 package had stderr output. That didn't change any exit code.

Not tested

Older colcon-core and colcon-ros versions (including the ones in issue #208), pyproject.toml-only Python packages, --paths, colcon.meta and defaults.yaml files, mixins, --packages-select-by-dep, packages over network or bind mounts, Windows and macOS, Foxy, Iron and Rolling.

FAQ

Why does colcon say ignoring unknown package when the folder is right there?

colcon selects by the <name> in package.xml, not the folder name. If the name matches, the package wasn't discovered: a COLCON_IGNORE file in a parent folder, a package nested inside another package, a hidden folder or another workspace all gave this warning in my runs. colcon list --names-only shows what colcon can see.

Does colcon build fail when the package name is wrong?

No. It printed the warning, Summary: 0 packages finished and exited 0 on Humble, Jazzy and Lyrical. --packages-up-to with a wrong name exits 1, and so does a grep for ignoring unknown package on the output.

Can I pass several packages with commas?

No. pkg_a,my_py_pkg was treated as one unknown name. Separate names with spaces: --packages-select pkg_a my_py_pkg.

Is a dash the same as an underscore in a package name?

No. my-py-pkg was unknown when the package was named my_py_pkg, and Pkg_A was unknown for pkg_a. The match is exact.

My ament_python package has no setup.py. Will colcon ignore it?

Not with colcon-core 0.21.3 and colcon-ros 0.5.0. The package was found and its build failed with exit 1 and can't open file ... setup.py. The 2019 report in colcon-core issue #208 showed the unknown-package warning instead.
