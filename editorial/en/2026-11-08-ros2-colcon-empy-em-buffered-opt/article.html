Short answer: CMake built your interfaces with the Python from your active venv or conda env, not with /usr/bin/python3. Look at the path inside execute_process(...). If it is your venv, that interpreter is missing the build-time modules ROS needs, or has the wrong version of one. BUFFERED_OPT means empy 4.x on Humble. Humble's rosidl_adapter only works with empy 3.x. The fix that worked on Humble, Jazzy and Lyrical was the simplest one: build in a shell where the venv is not active.

deactivate            # or: conda deactivate
cd ~/ros2_ws
rm -rf build install log
colcon build

If you need the venv active while you build, pin the old empy in it on Humble and add the other missing modules:

pip install empy==3.3.4 catkin_pkg lark
# Jazzy and Lyrical venvs also needed:
pip install numpy setuptools

This post is about build time. If the build works but ros2 run can't import a package from your venv, that's the shebang problem covered in ros2 run ignores my conda or venv Python.

Why the venv Python gets used

The colcon command itself is not the problem. Its shebang is #!/usr/bin/python3 on all three images, so it runs on the system Python even with a venv active. The problem is CMake. When VIRTUAL_ENV is set, CMake's FindPython3 picks the venv interpreter. In CMakeCache.txt the empty-venv build had Python3_EXECUTABLE:FILEPATH=/venv/bare/bin/python3. The no-venv build had /usr/bin/python3. Every rosidl step that runs Python then runs that interpreter.

The ROS Python packages (rosidl_adapter, rosidl_parser and the others) still load in the venv, because setup.bash puts /opt/ros/<distro> on PYTHONPATH. Their third-party dependencies come from apt and live in /usr/lib/python3/dist-packages, which a normal venv doesn't see. That's why the errors name em, catkin_pkg, lark and numpy and never a ROS package. To check which interpreter your build used, read the path at the start of execute_process(...) in the error, or run:

grep -E '^(Python3_EXECUTABLE|PYTHON_EXECUTABLE)' build/<your_pkg>/CMakeCache.txt

BUFFERED_OPT: empy 4 on Humble

empy 4 removed options that empy 3 had. Humble's rosidl_adapter 3.1.9 still passes em.BUFFERED_OPT to em.Interpreter (line 51 of rosidl_adapter/resource/__init__.py). With empy 4.2.1 in the venv the build fails, and a second traceback follows: AttributeError: 'NoneType' object has no attribute 'shutdown'. That second error comes from the cleanup code. It isn't a separate problem.

Jazzy (rosidl_adapter 4.6.9) and Lyrical (5.2.1) built with both empy 4.2.1 and 3.3.4. Lyrical's own apt package is 4.2.1. So BUFFERED_OPT only showed up on Humble in my runs. On Jazzy and Lyrical, a venv build that fails will hit one of the other rows first.

How you get empy 4 matters on Humble:

  • pip install empy in a normal venv installs the newest version (4.2.1 on the test date).
  • pip install empy in a --system-site-packages venv did nothing on Humble, because the apt 3.3.4 already satisfies it. The build kept working.
  • pip install -U empy in that same venv installed 4.2.1 over it, and the build failed with BUFFERED_OPT.

The fix is pip install empy==3.3.4 in that interpreter. In the venv that had failed with BUFFERED_OPT, that one command was enough on Humble.

No module named 'em', 'catkin_pkg', 'lark'

These three mean the module isn't in the venv at all. In an empty venv em failed first on every distro, because rosidl_generate_interfaces runs rosidl_adapter before it parses package.xml. With empy present and catkin_pkg missing, package_xml_2_cmake.py failed on its import at line 22. lark is used by rosidl_parser, which only runs during the make step. That's why its exit code was 2, not 1, and why it printed twice: once from rosidl_generator_cpp and once from rosidl_generator_rs, which run in parallel.

Install the PyPI name, not the import name. The package is empy, not em. They share the em namespace. Then add catkin_pkg and lark.

No module named 'numpy' and 'setuptools' (Jazzy, Lyrical)

On Jazzy and Lyrical, rosidl_generator_py calls find_package(Python3 ... NumPy) at configure time. Without numpy in the venv, the message is CMake's, not Python's:

  version "3.12.3")

  ...
  /opt/ros/jazzy/share/rosidl_generator_py/cmake/rosidl_generator_py_generate_interfaces.cmake:22 (find_package)

After numpy, the venvs on these two distros were missing setuptools. That error came from the setup.py that ament_cmake_python generates in the build directory:

  File "/ws/build/my_interfaces/ament_cmake_python/my_interfaces/setup.py", line 1, in <module>
    from setuptools import find_packages
ModuleNotFoundError: No module named 'setuptools'

On Humble the venv built with empy 3.3.4, catkin_pkg and lark, and I didn't install numpy or setuptools. Neither was asked for.

-DPython3_EXECUTABLE works on Jazzy and Lyrical, not alone on Humble

Pointing CMake back at the system Python is the other way to keep the venv active:

colcon build --cmake-args -DPython3_EXECUTABLE=/usr/bin/python3

On Jazzy and Lyrical that was enough, both with an empty venv and with the empy 4.2.1 venv. On Humble it failed. With the empy 4.2.1 venv the error was Error processing idl file: .../Num.idl followed by the same BUFFERED_OPT traceback, this time from rosidl_generator_py during make (exit code 2). With the empty venv it was:

ImportError: cannot import name 'generate_py' from 'rosidl_generator_py' (/opt/ros/humble/local/lib/python3.10/dist-packages/rosidl_generator_py/__init__.py)

The cache shows why. On Humble there is a second variable, PYTHON_EXECUTABLE, and it still held the venv path. Humble's rosidl_generator_py step ran with it. Setting both fixed Humble:

colcon build --cmake-args -DPython3_EXECUTABLE=/usr/bin/python3 -DPYTHON_EXECUTABLE=/usr/bin/python3

The same two flags also worked on Jazzy and Lyrical. If you script one command for all distros, use both.

The reason is that an ament_python build only runs setup.py. rosidl_generate_interfaces is a CMake function, and nothing in that build calls it. The dependencies in package.xml don't change that. The fix is a separate ament_cmake package for the interfaces, with the Python node depending on it:

    CMakeLists.txt        # find_package(rosidl_default_generators REQUIRED)
                          # rosidl_generate_interfaces(${PROJECT_NAME} "msg/Num.msg")
    package.xml           # buildtool_depend rosidl_default_generators,
                          # exec_depend rosidl_default_runtime,
                          # member_of_group rosidl_interface_packages
    msg/Num.msg
  py_node/                # ament_python
    package.xml           # exec_depend my_interfaces
    py_node/talker.py     # from my_interfaces.msg import Num

colcon builds my_interfaces first because of the dependency. On all three distros it printed Summary: 2 packages finished, and the node printed:

OK my_interfaces.msg.Num(num=5)

Build this interfaces package without a venv, or with the fixes above. It's a normal rosidl_generate_interfaces package, so every error in the first table applies to it.

Version notes

The error texts matched across distros where the same step failed. Line numbers in the call stack differ: ament_package_xml is called from rosidl_generate_interfaces.cmake:226 on Humble and :220 on Jazzy and Lyrical. Humble needs empy 3.x. Jazzy and Lyrical accepted 3.3.4 and 4.2.1. Only Jazzy and Lyrical needed numpy and setuptools in the venv, and only Humble needed -DPYTHON_EXECUTABLE in addition to -DPython3_EXECUTABLE. Lyrical's CMake 4.2.3 also printed a CMake Deprecation Warning for cmake_minimum_required(VERSION 3.8). That warning is harmless.

Not tested

Conda environments (I used venv only; the same check on execute_process(...) applies, but I didn't run it). uv, pyenv and Python versions different from the distro's. colcon installed with pip inside the venv. The unrelated PyPI package em, and an em.py under /opt/ros breaking colcon itself (cannot import name 'OVERRIDE_OPT' from 'em'). A stale CMakeCache.txt from an earlier build (I deleted build/ every time). A single ament_cmake package that holds both messages and Python nodes. Windows, macOS, Iron, Kilted and Rolling.

FAQ

How do I fix module 'em' has no attribute 'BUFFERED_OPT'?

You have empy 4.x in the Python that CMake used, and you are on Humble. Run pip install empy==3.3.4 in that venv, or deactivate the venv and build again. Both worked. Jazzy and Lyrical built fine with empy 4.2.1.

Which empy version does ROS 2 need?

The apt package was empy 3.3.4 on Humble and Jazzy and 4.2.1 on Lyrical. Humble failed with 4.2.1. Jazzy and Lyrical built with both 3.3.4 and 4.2.1.

Why does colcon build fail with No module named 'em' when empy is installed?

It's installed for a different Python. With a venv active, CMake used the venv's interpreter, which can't see the apt packages in /usr/lib/python3/dist-packages. Check the path in execute_process(...). Either deactivate the venv, install empy==3.3.4 into it, or create it with --system-site-packages.

Does -DPython3_EXECUTABLE=/usr/bin/python3 fix it?

On Jazzy and Lyrical, yes. On Humble, not by itself. PYTHON_EXECUTABLE kept the venv path, and the Python generator still failed. Pass both -DPython3_EXECUTABLE=/usr/bin/python3 and -DPYTHON_EXECUTABLE=/usr/bin/python3 in --cmake-args.

Can an ament_python package have custom messages?

No. colcon finished it with exit code 0 but generated nothing, and the import failed with No module named 'py_with_msg.msg'. Put the .msg files in a separate ament_cmake package and add it as a dependency of the Python package.
