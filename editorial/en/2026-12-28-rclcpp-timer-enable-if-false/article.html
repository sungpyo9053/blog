/opt/ros/humble/include/rclcpp/rclcpp/node_impl.hpp:110:1: error: no type named ‘type’ in ‘struct std::enable_if<false, void>’
  110 | Node::create_wall_timer(
      | ^~~~

With rclcpp::create_timer the same error points at create_timer.hpp instead (line 44 on Humble, line 146 on Jazzy and Lyrical). Just above it, g++ prints error: no matching function for call to ‘N::create_wall_timer(...)’.

Short answer: rclcpp rejected your timer callback's signature. A timer callback can take no arguments, or exactly one rclcpp::TimerBase &. Anything else fails this template check. That includes a ROS 1 style _1 for a TimerEvent, a TimerBase::SharedPtr parameter, a std::function<void(int)>, and even a std::bind that fills in an extra argument for you. Wrap the call in a lambda that takes nothing:

using namespace std::chrono_literals;

// in the constructor of a class derived from rclcpp::Node
timer_ = create_wall_timer(500ms, [this]() { feedback(handle_); });

// sim-time aware version, same rule for the callback
timer_ = rclcpp::create_timer(this, get_clock(), rclcpp::Duration(1, 0),
                              [this]() { feedback(handle_); });

Keep the returned SharedPtr in a member. In C++, a timer you don't store never fires.

The callback can take nothing or a TimerBase reference

The enable_if in create_wall_timer and create_timer is a test on the callback type. In my runs it passed for two shapes only: a callable with no parameters, and one whose single parameter is rclcpp::TimerBase &. The TimerBase & form is useful. In the runtime test a callback that called t.cancel() on its third call ran exactly 3 times in 1.05 seconds on all three distros. A lambda taking rclcpp::TimerBase::SharedPtr looks close, but it failed with the enable_if error.

This is why ROS 1 code breaks when you port it. ros::NodeHandle::createTimer called you with a const ros::TimerEvent &, so people wrote boost::bind(&Robot::cb, this, _1). In ROS 2 there is no event argument. std::bind(&N::cb_int, this, std::placeholders::_1) failed on all three distros. Remove the parameter from the callback, or change it to rclcpp::TimerBase &.

The question in the Stack Exchange thread on this error builds a std::function whose parameter is a goal handle and passes it to rclcpp::create_timer. My std::function<void(int)> case gave the same error at the same spot, create_timer.hpp:44:60 on Humble. The parameter type doesn't matter. Any parameter that isn't a TimerBase & fails.

Binding an extra value fails too, until you wrap it

This one surprised me. std::bind(&N::cb_int, this, 5) has every argument filled, and calling it with no arguments is valid C++. rclcpp still rejected it on all three distros with the same enable_if<false, void> error. My reading of the failure: rclcpp's function_traits looks at the bound member function, void (N::*)(int), and sees one int parameter. It doesn't count the bound value. A bind of void cb() with only this has nothing to miscount, and that case compiled.

Two fixes worked everywhere:

  • A lambda: [this]() { cb_int(5); }.
  • Store the bind in a std::function<void()> first, then pass that. The std::function has a plain no-argument signature, so the check passes.

The lambda is shorter, and you can see what it captures. For a value that changes (a goal handle, an index), capture it by value or keep it in a member.

A missing this is a different error

Three ways of leaving out the object fail before rclcpp's check, so they don't print the enable_if line first:

  • create_wall_timer(500ms, &N::cb) passes a member function pointer. rclcpp's function_traits.hpp:52 looks for operator() and reports ‘operator()’ is not a member of ‘void (N::*)()’.
  • std::bind(&N::cb) fails inside the standard library: static assertion failed: Wrong number of arguments for pointer-to-member.
  • []() { cb(); } fails with ‘this’ was not captured for this lambda function.

std::bind(&N::cb_int, this), with the int left unbound, printed both: first the standard library's static assertion, then rclcpp's enable_if.

The period must be a std::chrono duration

create_wall_timer is a template on std::chrono::duration<Rep, Period>. A bare number doesn't match it. 0.5 and 500 both gave no matching function for call to ‘N::create_wall_timer(double, ...)’ or (int, ...). rclcpp::Duration isn't a chrono type either, and it failed the same way. These forms worked:

  • 500ms or 0.5s, with using namespace std::chrono_literals; in scope. Without that line, 500ms gave unable to find numeric literal operator ‘operator""ms’.
  • rclcpp::Duration(1, 0).to_chrono<std::chrono::nanoseconds>(), if the value is already an rclcpp::Duration.

The free function rclcpp::create_timer(node, clock, period, callback) took both rclcpp::Duration(1, 0) and 500ms on all three distros.

The local-variable case is the one that compiles and then says nothing. As I understand rclcpp, the node's callback group keeps only a weak reference to the timer, so when your SharedPtr goes out of scope the timer is destroyed. In my run that meant zero callbacks and no warning. rclpy differs here: the node itself holds the timer, so a forgotten local variable still fired 10 times. Code ported from Python to C++ can hit this.

In rclpy the timer period is in seconds and accepts an int. create_timer(100, cb) is valid, but nothing fires for 100 seconds. A wrong callback signature doesn't fail at create_timer in rclpy. It fails the first time the timer fires, inside spin_once, so it shows up as a traceback from your spin loop.

With use_sim_time set and nothing on /clock, the timer created by rclcpp::create_timer with the node's clock fired 0 times, and the wall timer fired 10 times. That's expected, and it's the reason to pick create_timer for code that must follow a bag or a simulator. What happens around the first /clock message, when now() is still 0, is covered in Subtraction leads to negative time in ROS 2 rclpy.

Only two results changed between distros. Node::create_timer doesn't exist on Humble, where it failed with ‘class N’ has no member named ‘create_timer’, and it compiled on Jazzy and Lyrical. The std::function<void(int)> case through rclcpp::create_timer gave a different error chain. On Humble the enable_if error sat at create_timer.hpp:44:60. On Jazzy and Lyrical a no matching function for call to ‘create_timer(rclcpp::Clock::SharedPtr&, ...)’ at create_timer.hpp:117:22 came first, then the enable_if error at create_timer.hpp:146:1.

The line numbers moved: node_impl.hpp:110 on Humble and Jazzy, node_impl.hpp:111 on Lyrical. The standard library lines differ with the compiler: g++ 11.4.0 on Humble, 13.3.0 on Jazzy and 15.2.0 on Lyrical. FAQ

What does "no type named 'type' in 'struct std::enable_if<false, void>'" mean for a ROS 2 timer?

rclcpp's create_wall_timer or create_timer rejected the callback type. In my tests only callbacks with no parameters or one rclcpp::TimerBase & parameter passed. Change the callback to a lambda with no parameters.

How do I pass an extra argument to a timer callback in rclcpp?

Capture it in a lambda: [this]() { cb_int(5); }. A plain std::bind(&N::cb_int, this, 5) failed on Humble, Jazzy and Lyrical. Wrapping the same bind in a std::function<void()> compiled.

Why does create_wall_timer(0.5, ...) not compile?

The period must be a std::chrono duration. 0.5, 500 and rclcpp::Duration(1, 0) all gave "no matching function". 0.5s or 500ms with using namespace std::chrono_literals; compiled, and so did Duration::to_chrono.

My rclcpp timer compiles but the callback is never called. Why?

Two causes gave zero callbacks in my runs. Either the timer's SharedPtr was a local variable that went out of scope, or the timer used the node clock with use_sim_time on and nothing published /clock. Store the timer in a member. For sim time, check that /clock is being published.

What replaces ROS 1 createTimer with ros::Duration in ROS 2 C++?

rclcpp::create_timer(this, get_clock(), rclcpp::Duration(1, 0), callback) compiled on all three distros and follows ROS time. On Jazzy and Lyrical this->create_timer(period, callback) also works. Drop the TimerEvent parameter from the callback.
