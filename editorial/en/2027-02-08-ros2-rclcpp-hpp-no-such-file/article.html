/root/ws/src/c03_no_link/src/node.cpp:1:10: fatal error: rclcpp/rclcpp.hpp: No such file or directory

The CMake-side cousin of this error stops the build one step earlier:

CMake Error at /opt/ros/humble/share/ament_cmake_target_dependencies/cmake/ament_target_dependencies.cmake:42 (message):
  ament_target_dependencies() the first argument must be a valid target name

Short answer: the compiler can't find rclcpp/rclcpp.hpp because the target that includes it was never linked to rclcpp. find_package(rclcpp REQUIRED) alone doesn't add any include path. You need a link line, and it has to come after both find_package and add_executable (or add_library). This order built and ran on Humble, Jazzy and Lyrical:

find_package(ament_cmake REQUIRED)
find_package(rclcpp REQUIRED)

add_executable(node src/node.cpp)
target_link_libraries(node rclcpp::rclcpp)   # works on every distro I tested
# ament_target_dependencies(node rclcpp)     # works on Humble and Jazzy, gone in Lyrical

install(TARGETS node DESTINATION lib/${PROJECT_NAME})
ament_package()

"the first argument must be a valid target name" means the name you passed to ament_target_dependencies() doesn't exist yet at that line. Either the call is above add_executable, or the name is spelled differently. CMake names are case-sensitive, so Node is not node.

What I ran

On 2026-11-22 I ran the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images one after another, with networking off. A script wrote 13 packages into a fresh workspace. Each package had the same package.xml (with <depend>rclcpp</depend>) and differed only in CMakeLists.txt. The node creates an rclcpp::Node, logs one line and exits. The two library packages add a header that includes rclcpp and a small .cpp file.

For each package the script ran colcon build --packages-select <pkg> --parallel-workers 1 --cmake-args -DCMAKE_EXPORT_COMPILE_COMMANDS=ON, saved the exit code and wall time, grepped the log for the error lines, and counted the rclcpp include flags in build/<pkg>/compile_commands.json. When the build passed, it ran the node with ros2 run. The compilers were g++ 11.4.0 with CMake 3.22.1 (Humble), g++ 13.3.0 with CMake 3.28.3 (Jazzy) and g++ 15.2.0 with CMake 4.2.3 (Lyrical).

Cause 1: nothing links the target to rclcpp

This is the most common case in the questions I found. The package calls find_package(rclcpp REQUIRED), adds the executable, and stops. In compile_commands.json this package had 0 rclcpp include flags on every distro. The working packages had one, -isystem /opt/ros/<distro>/include/rclcpp.

That path is the reason the error looks the way it does. In all three images rclcpp's headers sit one folder deeper than the include prefix, under include/rclcpp/rclcpp/. The #include "rclcpp/rclcpp.hpp" only works when the compiler gets include/rclcpp as a search path, and the only thing that adds it is a link to the rclcpp target. Sourcing /opt/ros/<distro>/setup.bash doesn't add it, and neither does the <depend> in package.xml. Every package in my run had both and still failed.

The fix is one line after add_executable: target_link_libraries(node rclcpp::rclcpp). It built in 5.3 s on Humble, 5.7 s on Jazzy and 7.0 s on Lyrical, and the node printed pk71 node ok on all three.

Cause 2: the right lines in the wrong order

CMake runs the file from top to bottom. Two orderings broke the build, and they failed in different ways.

With add_executable and target_link_libraries(node ${rclcpp_LIBRARIES}) above find_package, CMake raised no error. ${rclcpp_LIBRARIES} was still empty at that line, so the link call linked nothing. The build reached the compiler and stopped with rclcpp/rclcpp.hpp: No such file or directory. That is the layout in the most viewed question on this error, with 3,297 views. Moving every find_package to the top fixes it.

With ament_target_dependencies(node rclcpp) above add_executable(node ...), the build stopped at configure time with the first argument must be a valid target name. The call stack points to the line: CMakeLists.txt:5 (ament_target_dependencies). A typo gives the same text. ament_target_dependencies(Node rclcpp) for a target called node failed identically on Humble and Jazzy. Look at the line number in the call stack, then compare the first argument with the name in add_executable or add_library above it. In one of the questions below, the call used ${library_name} before add_library created that target, which is the same mistake as calling it above add_executable.

Cause 3: rclcpp is in a library header

This one shows up when you split code into a library. The error points at your own header, not at a .cpp file:

/root/ws/src/c11_lib_private/include/c11_lib_private/mylib.hpp:2:10: fatal error: rclcpp/rclcpp.hpp: No such file or directory

The library itself compiled. Its compile_commands.json entry had the rclcpp include flag. The executable didn't, because the library linked rclcpp with PRIVATE. Private dependencies don't pass their include paths on, so any target that includes mylib.hpp lost the path. Changing that one word to PUBLIC made the package build on all three distros, in 8.5 s (Humble), 9.1 s (Jazzy) and 11.1 s (Lyrical).

The rule is simple: if a public header includes rclcpp, the library must link rclcpp PUBLIC. If only the .cpp includes it, PRIVATE is fine. When the library lives in another package, the same idea applies across packages, and that package also needs to export its targets. That part wasn't in this test.

Cause 4: include directories without the link

Some answers suggest adding ${rclcpp_INCLUDE_DIRS} by hand. On its own this got past rclcpp/rclcpp.hpp and failed on the next header that rclcpp itself includes. The missing header was different on each distro: rmw/init.h on Humble, service_msgs/msg/detail/service_event_info__struct.hpp on Jazzy and rosidl_buffer/buffer.hpp on Lyrical. In all three images the variable gave the compiler rclcpp's own folder (-I/opt/ros/<distro>/include/rclcpp), but that wasn't enough to reach the headers of rclcpp's dependencies.

The old style with both variables, ${rclcpp_INCLUDE_DIRS} and target_link_libraries(node ${rclcpp_LIBRARIES}), did build and run on all three. So the link line, not the include line, is what brought in the rest of the include paths. It works, but it is two lines for what rclcpp::rclcpp does in one.

Linking the plain name, target_link_libraries(node rclcpp), failed on all three distros with the original error. Use the name with ::. The plain-name package had 0 rclcpp include flags in compile_commands.json.

Cause 5: find_package(rclcpp) is missing

Without find_package(rclcpp REQUIRED), the two link styles fail with two different messages. ament_target_dependencies said the passed package name 'rclcpp' was not found before. target_link_libraries(node rclcpp::rclcpp) got through configure and failed at the generate step with Target "node" links to target "rclcpp::rclcpp" but the target was not found. Both are fixed by adding the find_package line.

A different message, Could not find a package configuration file provided by "rclcpp", means find_package ran but the package wasn't there, usually because /opt/ros wasn't sourced. My earlier post "Could not find a package configuration file provided by" in colcon build measured five causes of that one, from packages that aren't installed to find_package with the wrong case.

VS Code says rclcpp.hpp is missing, but colcon builds

That is a different problem. VS Code's IntelliSense doesn't read CMakeLists.txt, so its red squiggle says nothing about your build. One way to give it the real flags is the file CMake already writes. With --cmake-args -DCMAKE_EXPORT_COMPILE_COMMANDS=ON, every package that configured got a build/<pkg>/compile_commands.json. In every working package it contained the rclcpp include path. The four packages that failed on rclcpp.hpp in their own .cpp file had 0 rclcpp entries, which makes the file a quick way to check a CMakeLists.txt without reading the compiler log. I didn't test the VS Code side itself. Pointing the C/C++ extension at that file is a common approach, but I didn't measure it.

Version notes

  • Humble (rclcpp 16.0.23, ament_cmake 1.3.15) and Jazzy (rclcpp 28.1.22, ament_cmake 2.5.6) behaved the same in every case. Only the wording of the missing-target CMake error changed. CMake 3.22 on Humble prints links to target "rclcpp::rclcpp" but the target was not found and blames the add_executable line. CMake 3.28 on Jazzy puts the target name on its own line and blames the target_link_libraries line.
  • Lyrical (rclcpp 32.0.3, ament_cmake 2.8.8) has no ament_target_dependencies. All four packages that used it stopped with Unknown CMake command "ament_target_dependencies"., so on Lyrical you never see "the first argument must be a valid target name". The image still lists a package ros-lyrical-ament-cmake-target-dependencies 2.8.8, but the command wasn't defined in my build.
  • The header that fails after rclcpp.hpp, when you add include folders by hand, differs per distro: rmw/init.h, then service_msgs/..., then rosidl_buffer/buffer.hpp. If you see one of these, the cause is the same as Cause 4.
  • On Lyrical the PUBLIC library package built, but ros2 run failed with error while loading shared libraries: libmylib.so: cannot open shared object file and exit code 127. My test installed only the executable, not mylib. On Humble and Jazzy the same package ran. I didn't check why the two older images behaved differently. If you hit this, add mylib to your install(TARGETS ...) line.

FAQ

Why does colcon say rclcpp/rclcpp.hpp: No such file or directory when rclcpp is installed?

Because nothing linked your target to rclcpp. find_package(rclcpp REQUIRED), sourcing setup.bash and the package.xml tag don't add the include path. In my run the include path appeared only after target_link_libraries(node rclcpp::rclcpp) (or ament_target_dependencies on Humble and Jazzy), placed after find_package and add_executable.

What does "ament_target_dependencies() the first argument must be a valid target name" mean?

The first argument isn't the name of a target that exists at that line. In my test it happened when the call came before add_executable and when the name differed in case (Node vs node). Move the call below add_executable or add_library and copy the exact name.

My library builds, but the executable fails on rclcpp.hpp inside my header. Why?

The library links rclcpp PRIVATE, so its include path doesn't reach targets that include its header. Change it to target_link_libraries(mylib PUBLIC rclcpp::rclcpp). That one change made the package build on Humble, Jazzy and Lyrical.

Is include_directories with rclcpp_INCLUDE_DIRS enough?

No. On its own it fixed rclcpp.hpp and then failed on the next header: rmw/init.h on Humble, a service_msgs header on Jazzy and rosidl_buffer/buffer.hpp on Lyrical. Link the target instead.

Which line works on Humble, Jazzy and Lyrical?

target_link_libraries(node rclcpp::rclcpp) after find_package(rclcpp REQUIRED) and add_executable. It built and ran on all three. ament_target_dependencies worked on Humble and Jazzy and was an unknown command on Lyrical.
