[0.325s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/ws/install/cpp_b' in the environment variable AMENT_PREFIX_PATH doesn't exist
[0.326s] WARNING:colcon.colcon_ros.prefix_path.catkin:The path '/ws/install/cpp_b' in the environment variable CMAKE_PREFIX_PATH doesn't exist

When the whole sourced workspace is gone or moved, a third line shows up first:

[0.318s] WARNING:colcon.colcon_core.prefix_path.colcon:The path '/ws/install' in the environment variable COLCON_PREFIX_PATH doesn't exist

Short answer: this is a warning, not an error. Your shell sourced install/setup.bash at some point, and that put one path per package into AMENT_PREFIX_PATH (and, for ament_cmake packages, into CMAKE_PREFIX_PATH). Then that directory was deleted or moved. colcon checks every entry when it starts and prints one line for each entry that is missing. In my runs the build still finished (exit code 0 where I checked it), and the packages worked afterwards. To get rid of it, open a new terminal and source again:

# new terminal
source /opt/ros/humble/setup.bash      # or jazzy, lyrical
cd ~/ros2_ws
colcon build
source install/setup.bash

Sourcing again in the same terminal did not help. That surprised me, so it gets its own section below. Neither did sourcing /opt/ros/<distro>/setup.bash again. The stale entry stayed in the variable both times.

Find your case

Every row behaved the same on Humble, Jazzy and Lyrical. All three images ship the same colcon (colcon-core 0.21.3, colcon-ros 0.5.0), which explains why.

The count tells you what happened. Two lines for one package name means one ament_cmake package is gone. One line means an ament_python package is gone. A COLCON_PREFIX_PATH line means the whole install directory of a workspace you sourced is gone or somewhere else.

These lines are separate from any real failure. The CMake error in the moved-workspace row comes from the old build/ directory, not from the prefix paths. Treat it as a different problem.

What I ran

On 2026-11-02 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images on a 2 vCPU Linux VM, one distro after another. The test workspace /ws had three packages:

  • py_pkg, an ament_python package with one console script, hello
  • cpp_a and cpp_b, two minimal ament_cmake packages

Each test case starts a fresh bash -c that sources only /opt/ros/<distro>/setup.bash, then runs the commands for that case, including any source install/setup.bash. So "same shell" below means one bash process that sourced the workspace and then deleted or moved something. The script counts lines containing doesn't exist in the output and records the exit code and wall time. For the scale test I built a second workspace with 10, then 30, empty ament_cmake packages.

After sourcing a clean build, the variables looked like this on all three distros (with the distro name changed):

AMENT_PREFIX_PATH=/ws/install/py_pkg:/ws/install/cpp_b:/ws/install/cpp_a:/opt/ros/humble
CMAKE_PREFIX_PATH=/ws/install/cpp_b:/ws/install/cpp_a
COLCON_PREFIX_PATH=/ws/install

That explains the counts. Every package is its own entry in AMENT_PREFIX_PATH. Only the CMake packages are in CMAKE_PREFIX_PATH. COLCON_PREFIX_PATH holds the install directory once.

Cause 1: you deleted build, install and log in a sourced terminal

This is the most common way to see the warning. You run rm -rf build install log to start clean, then colcon build in the same terminal. The shell still remembers every path from the last source install/setup.bash. colcon checks those paths when it starts. On Humble all five warnings were stamped 0.325s:

[0.325s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/ws/install/py_pkg' in the environment variable AMENT_PREFIX_PATH doesn't exist
[0.325s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/ws/install/cpp_b' in the environment variable AMENT_PREFIX_PATH doesn't exist
[0.325s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/ws/install/cpp_a' in the environment variable AMENT_PREFIX_PATH doesn't exist
[0.325s] WARNING:colcon.colcon_ros.prefix_path.catkin:The path '/ws/install/cpp_b' in the environment variable CMAKE_PREFIX_PATH doesn't exist
[0.325s] WARNING:colcon.colcon_ros.prefix_path.catkin:The path '/ws/install/cpp_a' in the environment variable CMAKE_PREFIX_PATH doesn't exist

The catkin in the logger name is just the colcon-ros module that checks CMAKE_PREFIX_PATH. It doesn't mean anything is using catkin.

In this case the warning fixes itself. The build recreates exactly the same directories. A second colcon build in the same terminal printed nothing. In that same shell, after the rebuild, ros2 pkg list showed all three packages and ros2 run py_pkg hello printed HELLO from py_pkg. A new shell that sourced the rebuilt workspace also ran hello and found cpp_a.

No COLCON_PREFIX_PATH line appeared in this case, even though /ws/install had been deleted too. That line only showed up when I built in a different directory than the one I had sourced (causes 3 and 4).

Cause 2: you removed a package from the workspace

This matches the most viewed question on this warning: a package was deleted from src, its install folder was removed by hand, and every later build warned about it. I deleted src/cpp_b, build/cpp_b and install/cpp_b, then built in the same shell:

[0.323s] WARNING:colcon.colcon_ros.prefix_path.ament:The path '/ws/install/cpp_b' in the environment variable AMENT_PREFIX_PATH doesn't exist
[0.323s] WARNING:colcon.colcon_ros.prefix_path.catkin:The path '/ws/install/cpp_b' in the environment variable CMAKE_PREFIX_PATH doesn't exist

Unlike cause 1, this one doesn't go away on its own. Nothing will recreate install/cpp_b, so every build in that terminal warns again. For the ament_python package the same steps gave one line, because Python packages are not added to CMAKE_PREFIX_PATH.

The ros2 command didn't warn. In that shell, ros2 pkg list no longer listed cpp_b, and ros2 pkg prefix cpp_b printed Package not found with exit code 1. ros2 pkg prefix cpp_a still worked. The stale entry only bothers colcon.

Deleting only src leaves a ghost package

If you delete src/cpp_b and leave install/cpp_b alone, you get no warning at all. colcon doesn't delete install folders of packages that are no longer in src. After the rebuild, install/cpp_b was still there. Even in a new shell, ros2 pkg list listed cpp_b and ros2 pkg prefix cpp_b returned /ws/install/cpp_b.

So when you remove a package, delete build/<pkg> and install/<pkg> as well, then start a new terminal. Doing only the deletion gives you the warning. Doing nothing gives you a package that still looks installed.

Cause 3: you moved or renamed the workspace

I sourced /ws/install/setup.bash, ran mv /ws /ws_moved and built inside /ws_moved. colcon printed six lines: COLCON_PREFIX_PATH for /ws/install, three AMENT_PREFIX_PATH lines and two CMAKE_PREFIX_PATH lines. All of them point to the old location.

That build also failed, but not because of the warnings. cpp_a stopped with CMake Error: The current CMakeCache.txt directory /ws_moved/build/cpp_a/CMakeCache.txt is different than the directory /ws/build/cpp_a where CMakeCache.txt was created. The old build directory still remembers the old path. After a move, delete build and install, open a new terminal, and build again.

Cause 4: you sourced another workspace and then deleted it

Overlays add up. If you sourced workspace A and then build workspace B in the same terminal, A's paths are still in the variables. I sourced /ws, deleted it, and built a separate /ws2. colcon printed the same six lines, all for /ws, a workspace that /ws2 never used. The /ws2 build finished normally.

The same thing happens if your ~/.bashrc sources a workspace you have since deleted. Every new terminal then starts with stale entries. Check for a source .../install/setup.bash line pointing at a folder that no longer exists.

Why sourcing again in the same terminal doesn't help

This was the most useful result. After deleting cpp_b, I ran source install/setup.bash again in the same shell and printed the variable:

AMENT_PREFIX_PATH=/ws/install/py_pkg:/ws/install/cpp_b:/ws/install/cpp_a:/opt/ros/humble

/ws/install/cpp_b is still there, and the next build printed both warnings again. Sourcing /opt/ros/humble/setup.bash first, then install/setup.bash, gave the same variable and the same two warnings. Jazzy and Lyrical behaved the same way. The setup scripts add their own paths and skip ones that are already there. They don't remove paths that someone else added, even when those paths no longer exist.

A new shell that sourced the same install/setup.bash got this instead:

AMENT_PREFIX_PATH=/ws/install/py_pkg:/ws/install/cpp_a:/opt/ros/humble

That shell's build printed nothing. A fresh shell builds the list from what is in install now. Your old shell keeps the list it built before.

Fix options compared

All fixes started from cause 2: cpp_b deleted from src, build and install in a shell that had sourced the workspace. "Lines" is the number of doesn't exist lines from the next colcon build. Results were identical on all three distros.

FixLinesNotes
Nothing (control)2Repeats on every build
source install/setup.bash again, same shell2Stale path stays in the variable
source /opt/ros/<distro>/setup.bash, then install/setup.bash, same shell2Stale path stays in the variable
New shell, only /opt/ros/<distro> sourced, then build0The recommended way to build
New shell, source install/setup.bash, then build0Variable lists only existing packages
export AMENT_PREFIX_PATH=/opt/ros/<distro> and unset CMAKE_PREFIX_PATH COLCON_PREFIX_PATH, same shell0Works, but also drops any other overlay you had sourced
env -i HOME=$HOME PATH=/usr/bin:/bin bash -c 'source /opt/ros/<distro>/setup.bash; colcon build'0A clean environment for one command, without leaving the terminal
colcon --log-level error build0Hides the lines, doesn't fix the variable. Also hides every other colcon warning.

Open a new terminal. It's the simplest fix, and it also clears whatever else the old shell picked up. I wouldn't use --log-level error for this. The warning is often the first sign that you are building against an overlay you didn't mean to use, and hiding it hides that too.

A good habit that avoids the warning: build in a terminal that sourced only /opt/ros/<distro>/setup.bash, and run nodes from a terminal that sourced install/setup.bash. In my runs, a build from a shell like that never printed the warning, even after rm -rf build install log. If ros2 itself stops working after you change what you source, the difference between setup.bash and local_setup.bash is explained in ros2: command not found on Jazzy? local_setup.bash vs setup.bash.

Does the warning slow down or break the build?

It didn't break anything I tested. I recorded the exit code for the rm -rf build install log case, and it was 0 on all three distros. In every other case colcon reported no failed package, apart from the moved-workspace build, which failed on its CMake cache. The packages built by a warned build ran in a new shell. The warning is about what is already in your environment, not about what is being built.

Timing was single runs, so treat the numbers as rough. With 30 packages, the warned build and the clean-shell build took 14.70 s and 14.59 s on Humble, 17.11 s and 14.93 s on Jazzy, and 30.07 s and 17.18 s on Lyrical. With 10 packages: 5.18 s and 4.95 s (Humble), 5.78 s and 5.38 s (Jazzy), 7.84 s and 6.11 s (Lyrical). The warned run was slower every time on Jazzy and Lyrical, and once by a lot. I can't tell from one run each whether that comes from the warning itself or from noise on a shared 2 vCPU VM. On Humble and Jazzy the warnings were all stamped within 0.4 s of colcon starting.

The line count grows with the workspace. 30 ament_cmake packages gave 60 lines, and those can push a real error off the screen. That's a better reason to fix it than speed.

  • Humble, Jazzy and Lyrical all had colcon-core 0.21.3, colcon-ros 0.5.0 and colcon-cmake 0.2.30, and gave the same warnings, counts and fix results.
  • Logger format: all three images printed [0.325s] WARNING:colcon.colcon_ros.prefix_path.ament:The path .... Some posts show colcon.colcon_ros.prefix_path.ament WARNING The path ... instead. That's the same check with a different colcon log format, so search for the part from The path on.
  • Lyrical printed a broken timestamp in front of the warnings: [-1793604232554663936.000s] WARNING:colcon.colcon_ros.prefix_path.ament:.... The rest of the line was correct.   • ros2 pkg list and ros2 pkg prefix ignored the missing paths silently on all three distros.

FAQ

Is "The path ... in the environment variable AMENT_PREFIX_PATH doesn't exist" an error?

No. It's a colcon warning. In my runs on Humble, Jazzy and Lyrical the builds that printed it finished, with exit code 0 where I checked, and the packages ran afterwards. It means your shell still lists a directory that has been deleted or moved.

Why do I still get the warning after sourcing install/setup.bash again?

Sourcing again in the same terminal doesn't remove stale paths. I measured it: AMENT_PREFIX_PATH still contained the deleted /ws/install/cpp_b after re-sourcing install/setup.bash, and also after re-sourcing /opt/ros/<distro>/setup.bash first. Open a new terminal, or reset the variables.

Why are there two lines for every package?

ament_cmake packages are added to both AMENT_PREFIX_PATH and CMAKE_PREFIX_PATH, so colcon reports each one twice. ament_python packages only appear in AMENT_PREFIX_PATH and give one line. A COLCON_PREFIX_PATH line means a whole install folder is gone or moved.

I deleted a package but ros2 pkg list still shows it. Why?

colcon doesn't delete install/<pkg> when a package disappears from src. In my test, install/cpp_b stayed after the rebuild, and ros2 pkg list and ros2 pkg prefix still found it. Delete build/<pkg> and install/<pkg> too, then open a new terminal.

Can I just hide the warning?

colcon --log-level error build printed none of the lines in my test. But the variable stays wrong, and the flag hides every other colcon warning as well. A new terminal fixed it with no lines on all three distros.
