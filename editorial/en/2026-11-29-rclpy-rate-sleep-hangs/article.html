A hung rate.sleep() doesn't print an error. The program just stops. The traceback above is what you get when you press Ctrl-C on it: the main thread was waiting inside threading.Event.wait(), and nothing was ever going to set that event.

Short answer: in rclpy, node.create_rate() creates a timer, and rate.sleep() waits until that timer's callback runs. Timer callbacks only run while an executor is spinning the node. If your loop calls rate.sleep() and nothing spins the node, it blocks forever. I measured this on Humble, Jazzy and Lyrical: at 10 Hz and 100 Hz the first rate.sleep() was still blocked after 5 seconds every time. The fix that worked is to spin the node in a background thread:

import threading
import rclpy
from rclpy.node import Node
from rclpy.executors import SingleThreadedExecutor

rclpy.init()
node = Node('loop')
executor = SingleThreadedExecutor()
executor.add_node(node)
threading.Thread(target=executor.spin, daemon=True).start()

rate = node.create_rate(10)   # 10 Hz
while rclpy.ok():
    # do work here
    rate.sleep()

With that, 200 iterations at 10 Hz took 20.000 s, with a median period of 99.999 ms on Humble. If you don't need a loop, a create_timer callback is simpler and was just as accurate. Two other causes produce the same hang: calling rate.sleep() inside a callback of a SingleThreadedExecutor, and use_sim_time:=true with nothing publishing /clock.

What I ran

On 2026-11-02 I ran one Python script, rate.py, in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images. The host was a 2 vCPU Linux server, and each container was limited to 1.5 CPUs. The distros ran one after another. Each scenario ran in its own process. Any call that could block had a watchdog thread that printed a line and exited the process after a fixed deadline, so a hang shows up as a WATCHDOG line in the output instead of a stuck run.

The scenarios were:

  • rate.sleep() called three times with no executor, at 10 Hz and 100 Hz, with a 5 s deadline.
  • 200 iterations each of rate.sleep() with a SingleThreadedExecutor or a 4-thread MultiThreadedExecutor spinning in a background thread, a create_timer callback, time.sleep(1/hz), get_clock().sleep_for(period) and get_clock().sleep_until(next_deadline). Periods were measured with time.perf_counter().
  • rate.sleep() inside a 10 Hz timer callback, under each executor type.
  • A node with use_sim_time=True: 3 s with no /clock, then 5 s with a separate process publishing /clock at 100 Hz starting from 1000 s at 1x speed, then 3 s after that process was stopped.
  • A thread blocked in rate.sleep() on a 0.2 Hz rate (5 s period) while the main thread called rate.destroy(), node.destroy_node() or rclpy.shutdown(), with and without a spinning executor.
  • SIGINT sent to a process 2 s after its main thread entered rate.sleep(). With no spin thread this ran once per distro. With a daemon spin thread it ran 11 times per distro.

Cause 1: nothing is spinning the node

The rclpy source explains the hang. Node.create_rate builds a timer with no callback of its own (the comment says "Rate will set its own callback") and wraps it in a Rate. In Rate.__init__:

# Set event when timer fires
self._timer.callback = self._event.set

and sleep() does self._event.wait(). The timer is an ordinary rclpy timer. Its callback runs only when an executor takes it from the wait set, so with no rclpy.spin, spin_once or executor.spin anywhere, the event is never set. This code was the same on all three distros. Lyrical only added type hints and docstrings.

This is the main difference from ROS 1. rospy.Rate.sleep() computed the remaining time and slept. The rclpy version waits for a callback. Code ported line by line from ROS 1, like a while loop in main() followed by rclpy.spin(node) that the loop never reaches, hangs on its first sleep().

Calling rclpy.spin_once(node, timeout_sec=0.5) first and then rate.sleep() returned in 0.0001 s on every distro. The timer had fired during spin_once and the event was already set. That only covers one sleep. You'd have to call spin_once before every rate.sleep(), and a background spin thread is the cleaner way to do that.

Cause 2: rate.sleep() inside a callback

The Rate.sleep docstring warns about this: "This may block forever if called in a callback in a SingleThreadedExecutor." It did block. A 10 Hz timer callback that called rate.sleep() was still blocked after 5 s on all three distros. The single executor thread is busy running your callback, so it can't run the rate's timer.

With MultiThreadedExecutor(num_threads=4), three rate.sleep() calls inside the callback returned after 0.1994 to 0.2000 s, the expected two periods after the first aligned sleep. This worked even when the calling timer was in the node's default callback group. create_rate puts the rate's timer in a separate group (self._rate_group, "Rates get their own group so timing is not messed up by other callbacks"), so another executor thread can run it. A ReentrantCallbackGroup on the calling timer gave the same result. Still, sleeping inside a callback ties up an executor thread for the whole loop. If the loop exists only to run code at a fixed rate, make that code a timer callback.

Cause 3: use_sim_time with no /clock

With use_sim_time=True the node clock is ROS_TIME driven by /clock. Before any /clock message arrived, get_clock().now() returned 0 ns. Over 3 s the rate, the 0.1 s timer and get_clock().sleep_for(0.1 s) each had 0 wakeups. The executor was spinning in a background thread the whole time, so this is a different hang from cause 1, and the spin thread fix doesn't help here.

When a separate process started publishing /clock, everything resumed. The first wakeup came this long after that process was launched, including its Python startup and DDS discovery:

My publisher sent a message about every 10 ms, so sim time moved in steps and wakeups landed on those steps. When I stopped the publisher, all three had 0 wakeups in the next 3 s, and now() stayed at about 1004.7 to 1004.8 s. A paused simulator or a finished ros2 bag play without --loop causes the same freeze, though I only tested a stopped publisher.

If your loop hangs only in simulation, check that ros2 topic echo /clock shows messages and that the node really has use_sim_time set. Gazebo, or ros2 bag play --clock, has to be running and not paused.

Stopping a thread that is blocked in rate.sleep()

A thread sat in rate.sleep() on a 5 s rate while the main thread tried to stop it. Results were the same with and without a spinning executor, on all three distros:

  • rate.destroy(): the sleeper woke within 1 ms and raised RuntimeError('Rate cannot sleep because it has been destroyed').
  • rclpy.shutdown(): the sleeper woke within 3 ms and raised rclpy.exceptions.ROSInterruptException: rclpy.shutdown() has been called. Rate registers context.on_shutdown(self._on_shutdown), which sets the event.
  • node.destroy_node(): the call returned, but the sleeper was still blocked 12 s later. Destroying the node doesn't wake rates created from it.

So if a worker thread loops on rate.sleep(), end it with rclpy.shutdown() or rate.destroy() and catch the exception in that thread. Don't rely on destroy_node().

Ctrl-C while blocked

When SIGINT arrived while the main thread was in rate.sleep(), Python raised KeyboardInterrupt from waiter.acquire() (the traceback at the top). With no spin thread the process ended 0.064 s after the signal on Humble and Jazzy and 0.114 s after it on Lyrical. My script let the exception propagate, so the exit status was "killed by SIGINT" (-2).

With a daemon spin thread, most runs ended the same way, but not all of them:

Both aborts came from the interpreter shutting down while the daemon thread was still inside executor.spin(). What the numbers say:

  • Spin thread plus rate and create_timer hold a fixed schedule. Both totals matched the ideal to the millisecond on every distro. When one period runs long, the next one is shorter.
  • MultiThreadedExecutor also held the schedule but had more spread on Jazzy and Lyrical. Median absolute error was 0.188 to 0.251 ms there, against 0.019 to 0.046 ms for the single-threaded spin thread. Jazzy's 10 Hz run had one period of 67.510 ms and one of 132.834 ms. It doesn't make rate.sleep() more accurate. It's only needed when a callback must sleep.
  • time.sleep and sleep_for don't block, because they don't need an executor (under wall-clock time). But each call sleeps a full period after your work finishes, so the loop drifts. At 100 Hz, time.sleep ran 1.3% slow and sleep_for 2.3% slow, and that's with no work in the loop. Real work adds to every period.
  • sleep_until with a deadline you advance by one period each time (next = next + period) kept the schedule with no executor. Clock.sleep_for and Clock.sleep_until exist in rclpy on Humble, Jazzy and Lyrical. This was the one blocking-loop option that needed no spin thread. Under sim time it still needs /clock messages to be processed, and I only tested that with a spin thread running.

Single spikes showed up in a few runs: a Humble sleep_until period of 109.127 ms, a Lyrical 10 Hz spin thread rate period of 106.953 ms, and a Lyrical 100 Hz timer with a 15.580 ms maximum. The host was shared, so treat the maximums as what a busy machine can do. The medians and totals were consistent across distros.

My order of preference: use create_timer when the work fits in a callback. Use a spin thread plus rate.sleep() when you need a loop in main(). Use sleep_until with an advancing deadline when you can't spin at all. Avoid time.sleep and sleep_for for fixed-rate work.

FAQ

Why does rate.sleep() block forever in ROS 2 Python?

Because nothing is spinning the node. rclpy's Rate waits for its own timer callback, and timer callbacks only run inside an executor. With no executor, the first rate.sleep() was still blocked after 5 s on Humble, Jazzy and Lyrical. Spin the node in a background thread or use create_timer.

Can I call rate.sleep() inside a callback?

Not with a SingleThreadedExecutor. It blocked for at least 5 s, as the rclpy docstring warns. With a MultiThreadedExecutor it returned on time, because rates get their own callback group. A timer callback is usually the better design.

Why do my rclpy timers never fire with use_sim_time true?

With no /clock publisher, now() stays at 0 and the rate, timer and sleep_for had 0 wakeups in 3 s. They resumed 0.20 to 0.38 s after a /clock publisher started and stopped again when it stopped. Make sure the simulator or ros2 bag play --clock is running.

How do I stop a thread that is blocked in rate.sleep()?

Call rclpy.shutdown() or rate.destroy(). The sleeper woke within a few milliseconds with ROSInterruptException or RuntimeError. node.destroy_node() left it blocked for at least 12 s.

Is time.sleep() a good replacement for rate.sleep()?

It doesn't hang, but it drifts. With an empty loop, 200 iterations at 100 Hz took 2.026 s with time.sleep and 2.046 s with get_clock().sleep_for. A spin thread plus rate, create_timer and sleep_until with an advancing deadline all took 2.000 s.
