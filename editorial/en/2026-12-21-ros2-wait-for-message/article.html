Those three lines come from my test runs. The first is rclpy.wait_for_message.wait_for_message() giving up on a topic whose publisher clearly exists. The second is the same function with no timeout, which only came back when the process was killed. The third is what a MultiThreadedExecutor thread died with on Humble, after wait_for_message was called on the node it was spinning.

Short answer: ROS 2 does have a rospy.wait_for_message equivalent. In Python it's from rclpy.wait_for_message import wait_for_message, and in C++ it's rclcpp::wait_for_message. Both exist on Humble, Jazzy and Lyrical. When it returns (False, None) or hangs, the cause in my runs was one of three things. There was no timeout, the subscription's QoS didn't fit the publisher, or the node passed in was also being spun by an executor. This version worked on all three distros in every run:

import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, DurabilityPolicy, qos_profile_sensor_data
from rclpy.wait_for_message import wait_for_message
from std_msgs.msg import String

rclpy.init()
helper = Node('waiter_helper')      # not added to any executor
ok, msg = wait_for_message(
    String, helper, '/chatter',
    time_to_wait=3.0,               # keyword only, seconds; default -1 waits forever
    qos_profile=QoSProfile(depth=1, durability=DurabilityPolicy.TRANSIENT_LOCAL))
    # latched topic: TRANSIENT_LOCAL; sensor topic: qos_profile_sensor_data
if not ok:
    helper.get_logger().warn('no message within 3 s')

In C++ the timeout and the QoS are the 4th and 5th arguments: rclcpp::wait_for_message(msg, node, "/chatter", 3s, rclcpp::QoS(1).reliable().transient_local()). It returns bool and fills msg.

No timeout means it waits forever

The signature was the same on all three distros: (msg_type, node, topic, *, qos_profile=1, time_to_wait=-1). Lyrical only adds type hints. The * makes qos_profile and time_to_wait keyword-only, so write time_to_wait=3.0, not a fourth positional argument. The default -1 means no timeout. With no publisher, the call blocked until timeout 5 killed the process. It did return (False, None) at about 4.75 to 4.79 seconds, because the source adds a signal-handler guard condition to its wait set and returns False when it fires. A plain script without a timeout can still hang forever if nothing ever publishes and nobody signals it.

With time_to_wait=1.0 and no publisher, the call returned (False, None) after 1.002 to 1.003 seconds. That's close enough to treat the value as a deadline in seconds.

It waits for the next message, not the last one

This is the main difference from what many people expect. wait_for_message creates a new subscription, waits once, takes one message and destroys the subscription. The source is short:

sub = node.create_subscription(msg_type, topic, lambda _: None, qos_profile=qos_profile)
...
wait_set.wait(timeout_nsec)
...
msg_info = sub.handle.take_message(sub.msg_type, sub.raw)
if msg_info is not None:
    return True, msg_info[0]
...
finally:
    node.destroy_subscription(sub)
return False, None

Nothing is cached between calls. With the 10 Hz publisher, five calls in a row got five consecutive messages (for example hello 25 to hello 29 on Lyrical), and after the first call most calls took 0.100 seconds, one publish period. Some calls were slower: 0.374 s on Humble and 0.340 s on Jazzy. One Jazzy run jumped from hello 21 to hello 24, so two messages went by during that call. If your topic publishes at 1 Hz, expect each call to cost up to a second. If you need the latest value often, a normal subscription that stores the last message is cheaper.

The fresh subscription matters for QoS too. The default qos_profile=1 means depth 1, reliable, volatile. A volatile subscription doesn't get messages published before it existed.

Latched topics: (False, None) after the full timeout

Topics like /map, /robot_description or /tf_static are usually published once with TRANSIENT_LOCAL durability. To test that, the publisher sent hello 1 once and kept running. Two seconds later, wait_for_message with the default QoS waited the full 3 seconds and returned (False, None) on all three distros. Passing a transient-local profile returned hello 1 in 0.013 to 0.174 seconds:

from rclpy.qos import QoSProfile, DurabilityPolicy
ok, msg = wait_for_message(String, node, '/map_like_topic', time_to_wait=3.0,
                           qos_profile=QoSProfile(depth=1, durability=DurabilityPolicy.TRANSIENT_LOCAL))

C++ behaved the same. The default rclcpp::SystemDefaultsQoS() returned false after 3.001 to 3.002 seconds. rclcpp::QoS(1).reliable().transient_local() returned hello 1 in 0.012 s (Humble), 1.384 s (Jazzy) and 0.181 s (Lyrical). How many old messages a late subscriber gets in general is covered in transient_local and late subscribers.

Best-effort topics: (False, None) almost at once

Sensor drivers often publish with BEST_EFFORT reliability. A reliable subscription doesn't match a best-effort publisher. With the default QoS, wait_for_message didn't wait the 3 seconds I asked for. It returned (False, None) early: after 0.375, 0.042 and 0.002 s on Humble, 0.067 s three times on Jazzy, and 0.093 to 0.094 s on Lyrical. The source waits only once, and when the wait set wakes up without a message to take, the function returns False. I didn't trace what woke the wait set. So a fast False is not a "no data" answer. It can mean a QoS mismatch. With qos_profile=qos_profile_sensor_data the call returned a message in 0.077 to 0.137 seconds. The QoS rules behind this are in Requesting incompatible QoS.

If you don't know the publisher's QoS, run ros2 topic info -v /topic and copy reliability and durability from the publisher's block.

Wrong type: a silent timeout

I waited for std_msgs/Int32 on a topic that carries std_msgs/String. No exception and no warning were printed. The call returned (False, None) after 3.002 to 3.003 seconds, which looks exactly like "nobody is publishing". Check the type with ros2 topic info /topic before you suspect anything else.

A node that is already spinning

The common ROS 1 pattern is to call wait_for_message in the middle of a program that also has callbacks running. In ROS 2 that means the node you pass in is often spun by an executor in another thread. The subscription that wait_for_message creates belongs to that node, so the executor sees it too. The Humble failure is the worst one, because it's silent for your main thread. Every wait_for_message call succeeded. Meanwhile the executor thread printed a traceback ending in _take_subscription, with sub.handle: and InvalidHandle: cannot use Destroyable because destruction was requested, and then it stopped. The likely reason is that the executor took the message before wait_for_message could. I didn't instrument that, so treat it as a guess. The 10 Hz timer kept firing (20 ticks in the next 2 s) in every single-threaded run.

The fix that was clean on all three distros is a separate node used only for waiting:

helper = Node('waiter_helper')   # create once, never add it to an executor
ok, msg = wait_for_message(String, helper, '/chatter', time_to_wait=2.0)

Calling wait_for_message inside a timer callback of a spinning node also worked: True in 0.050 to 0.194 seconds on all three. It doesn't use the executor, so it doesn't deadlock the way a service call inside a callback can. It does block that callback, and every other callback in the same group, for up to time_to_wait. Callback groups and the service-call deadlock are in generator already executing and callback groups.

Repeated calls

An rclpy issue from 2023 reported CPU load growing with repeated calls. I called wait_for_message 400 times against a 100 Hz publisher on a node that wasn't spinning. The mean call time was 11.82, 11.93 and 10.43 ms for the first 200 calls, and 9.99 to 10.00 ms for the last 200, on Humble, Jazzy and Lyrical. Process CPU time grew linearly, about 1.3 ms per call on Humble and 1.5 ms on Jazzy and Lyrical. After the loop the node had 0 subscriptions and the graph showed 0 subscribers on /chatter, so nothing leaked in this setup. Each call still creates and destroys a subscription, which costs discovery work. In a loop that runs all the time, a normal subscription is the better tool.

Version notes

rclpy's wait_for_message had the same keyword arguments and the same logic on Humble (rclpy 3.3.22), Jazzy (7.1.12) and Lyrical (10.0.11). Lyrical adds type hints and raises RuntimeError('Cannot create Waitset without a context.handle') if the context has no handle. The current Humble package accepts qos_profile too. In C++, all three headers have wait_for_message(out, node, topic, time_to_wait, qos) with SystemDefaultsQoS() as the default. Lyrical (rclcpp 32.0.3) adds an overload that takes NodeParametersInterface and NodeTopicsInterface pointers instead of a Node::SharedPtr. The executor crash with InvalidHandle happened only on Humble. ros2 topic echo --timeout exists on Jazzy (ros2cli 0.32.13) and Lyrical (0.40.9), not on Humble (0.18.20).

FAQ

What is the ROS 2 equivalent of rospy.wait_for_message?

from rclpy.wait_for_message import wait_for_message, called as ok, msg = wait_for_message(MsgType, node, '/topic', time_to_wait=3.0). In C++ it's rclcpp::wait_for_message(msg, node, "/topic", 3s) from rclcpp/wait_for_message.hpp. Both were present on Humble, Jazzy and Lyrical.

Why does wait_for_message return (False, None) when the topic is publishing?

In my runs it was a QoS mismatch or a wrong type. A latched (transient local) publisher gave False after the full timeout, a best-effort publisher gave False within 0.4 s, and a wrong message type gave False after the timeout with no error. Pass a matching qos_profile and check the type with ros2 topic info -v.

Why does wait_for_message hang forever?

time_to_wait defaults to -1, which means no timeout. If no message arrives, the call blocks until a signal or shutdown. Pass time_to_wait= as a keyword argument in seconds. A 1.0 s timeout returned after 1.002 to 1.003 s.

Can I call wait_for_message on a node that is spinning?

It worked inside a timer callback, but on a node spun by an executor in another thread it caused trouble. On Humble a MultiThreadedExecutor thread died with InvalidHandle, and on Jazzy and Lyrical up to 3 of 20 calls returned False. A separate helper node that no executor spins returned 20 of 20 on all three distros.

Does wait_for_message return the last message on the topic?

No. It creates a new subscription and waits for the next message, then destroys the subscription. With a 10 Hz publisher most calls took 0.1 s. Only a transient local subscription to a transient local publisher gets a message published before the call.
