$ kill -9 12345          # the talker is gone
$ ros2 node list
/talker                  # still listed
$ ros2 node list --no-daemon
                         # empty

The same happens the other way round: you start a node, run ros2 node list right away, and the node isn't there yet. A topic from a dead node stays in ros2 topic list the same way.

Short answer: the stale entry comes from the ros2 daemon's cache, not from a live process. A node that shuts down cleanly (Ctrl-C, kill, docker stop) disappeared from ros2 node list within a second in my runs. A node killed with kill -9 or docker kill stayed listed for about 20 seconds with the default Fast DDS, and about 6 seconds with Cyclone DDS. Use one of these, all measured on Humble:

ros2 node list --no-daemon                 # asks the network directly, no cache
ros2 daemon stop && ros2 daemon start      # throws the cache away (0.85 s)

Or wait about 20 seconds. Adding --spin-time doesn't help while the daemon is running: it was ignored. And --no-daemon has its own catch: with a running node, it missed that node in 2 of 5 calls.

What I ran

On 2026-11-01 I used the official ros:humble-ros-base Docker image on a 2 vCPU Linux host. The node was a small rclpy talker, written like the tutorials: it publishes on its own topic every 0.5 s, and on KeyboardInterrupt it calls destroy_node() and rclpy.try_shutdown(). I started it directly with python3, not with ros2 run, so each signal reached the node itself.

For each case I started a fresh daemon, started the talker, waited until it showed up, then sent the signal. After that a loop ran ros2 node list (daemon), ros2 node list --no-daemon and ros2 topic list -v about once a second, for up to 60 seconds, and logged the time since the signal. One loop pass took about 1.7 s because each ros2 call starts a Python process, so the times below have that resolution: "gone at 20.75 s" means it was still listed at the previous check, 19.04 s.

Cross-container tests used a second container on the same Docker bridge network, with the talker as the container's main process. For Cyclone DDS I installed ros-humble-rmw-cyclonedds-cpp with apt and set RMW_IMPLEMENTATION=rmw_cyclonedds_cpp for both the daemon and the talker.

The split is clean. If the node gets to run its shutdown code, it tells the other participants it's leaving, and the daemon drops it at once. If the process dies without that, nobody tells the daemon. It keeps the entry until the DDS participant's lease runs out, which was close to 20 seconds with Fast DDS and close to 6 seconds with Cyclone DDS here. A crash, an out-of-memory kill or a power cut on another machine behaves like kill -9. I didn't test those directly.

Two details from the logs. With SIGINT the talker didn't get a KeyboardInterrupt: rclpy's own signal handler shut the context down first, so rclpy.spin() raised ExternalShutdownException. SIGTERM did the same on Humble. The finally block still ran and the log ended with my "clean exit" line. And docker stop didn't hang for the 10-second grace period, even though the talker was PID 1 in its container. rclpy handled the SIGTERM, so the container stopped in 0.33 s and the node left the list normally.

The --no-daemon column never showed a stale node. A new process starts its own DDS participant, and a dead participant isn't announcing itself any more, so the new one never learns about it.

A node that just started, or a daemon that just started

Without a daemon running, the first ros2 node list took 0.96 s. It starts the daemon in the background and answers that one call itself. The next calls went through the daemon and took 0.30 to 0.31 s. Each --no-daemon call took 0.94 to 0.95 s, every time, because it does the discovery from scratch. ros2 daemon status printed "The daemon is not running" or "The daemon is running" and exited with 0 in both cases, so don't use its exit code in a script.

The "my node isn't listed" case showed up right after the daemon started. With the talker already running, I stopped the daemon and called ros2 node list every 0.5 s:

rep 1 call 1 at +0.96 s after daemon stop, took 0.97 s -> [/talker_pre ]
rep 1 call 2 at +1.79 s after daemon stop, took 0.32 s -> []
rep 1 call 3 at +2.63 s after daemon stop, took 0.33 s -> [/talker_pre ]

The first call found the node because it did its own discovery. The second call asked the new daemon, whose cache was still empty, and printed nothing. In the second repetition the second call was empty too, and the node was back by the third call at 2.65 s. So if you restart the daemon and the list is empty, wait a few seconds before you conclude the node is down.

A node that starts while the daemon is already running needs to be discovered too. The first daemon check, about 0.5 s after start, missed the node in 1 of 4 starts, and it was there on the next check at 2.37 s. A talker in another container wasn't in the daemon's list at 1.09 s, was in --no-daemon at 2.14 s and in the daemon's list at 2.99 s.

--no-daemon and --spin-time

--no-daemon always gave a fresh view, but not always a complete one. With one talker running the whole time, five --no-daemon calls in a row printed the node, then nothing, then the node twice, then nothing. Each call waited less than a second for discovery, and sometimes that wasn't enough.

--spin-time sets how long the CLI waits for discovery when it does the discovery itself. With the daemon stopped:

Command (daemon stopped)TimeTalker listed?
ros2 node list --spin-time 00.85 sno
ros2 node list --spin-time 12.07 syes
ros2 node list --spin-time 33.78 syes

With the daemon running, the option did nothing. Right after a kill -9, ros2 node list --spin-time 5 returned in 0.30 s and still listed the dead node. This matches ros2cli issue #164, which reports that --spin-time behaves differently with the daemon started or stopped. If you want a slower, more complete look, combine it with --no-daemon.

ROS_DOMAIN_ID and RMW mismatches

The daemon is per domain. With a talker on domain 0 and a daemon already running for domain 0, the shell with ROS_DOMAIN_ID=5 printed an empty list, with and without --no-daemon, and ros2 daemon status said "The daemon is running" in both shells. When I then started a second talker on domain 5, each shell listed only its own talker: /talker_d0 on domain 0 and /talker_d5 on domain 5. So the daemon never showed nodes from another domain, and changing the domain id in your shell doesn't make the CLI read the old domain's cache. If a node is missing, compare echo $ROS_DOMAIN_ID in both terminals first.

For RMW I tried one mismatch. A daemon started with the default Fast DDS listed a talker running on Cyclone DDS, and so did a shell set to Cyclone, with and without the daemon. In this setup the RMW mismatch didn't hide anything.

Pick by what you need. For a quick look after a crash, --no-daemon is the simplest. In a script that must not miss a live node, use --no-daemon --spin-time 1 or more and accept the extra second. Restarting the daemon clears dead entries, but the next few calls can come back empty until discovery has run again. The best fix is upstream of the CLI: shut nodes down with SIGINT or SIGTERM so they announce they're leaving, and leave kill -9 for processes that don't respond.

Restarting the daemon is also the most common answer on the forums, for example in ROS2 topic list only working once and ros2 humble to kill the zombie node. If a node is still listed long after 20 seconds and a restart doesn't clear it, the process is probably still running somewhere, on another machine or in another container in the same domain. A stale cache alone never lasted longer than the timeouts above in my runs.

Version notes

All numbers on this page are from Humble (ros2cli 0.18.20, rclpy 3.3.22, rmw_fastrtps_cpp 6.2.10 with Fast DDS 2.6.12, rmw_cyclonedds_cpp 1.3.5 with Cyclone DDS 0.10.5). Jazzy and Lyrical: not tested yet, see below.

Not tested

Jazzy and Lyrical. Nodes started with ros2 run or ros2 launch, where Ctrl-C reaches a wrapper process too. C++ nodes. Nodes on another physical machine, a network cable pulled, a real crash or out-of-memory kill. Changed lease durations in a Fast DDS XML profile or Cyclone DDS config. Discovery Server, ROS_LOCALHOST_ONLY and ROS_AUTOMATIC_DISCOVERY_RANGE. The daemon's 2-hour inactivity timeout.

If nodes on different machines or containers don't see each other at all, that's a discovery range problem rather than a cache problem. I measured it in ROS 2 nodes can't see each other.

FAQ

Why does ros2 node list still show a node I killed?

The ros2 daemon caches the graph. A node killed with kill -9 or docker kill can't announce that it's leaving, so the daemon keeps it until the DDS lease times out: about 20 s with Fast DDS and about 6 s with Cyclone DDS on Humble. A node stopped with Ctrl-C or kill was gone at the first check.

How do I remove a stale node from ros2 node list?

Run ros2 node list --no-daemon for a view without the cache, or ros2 daemon stop and ros2 daemon start to clear it. Both removed a kill -9'd node in my run. Waiting about 20 seconds works too.

Why is my node missing from ros2 node list right after I start it?

Discovery takes time. The daemon missed a new node in 1 of 4 starts at the first check, about 0.5 s after start, and had it by 2.4 s. Right after a daemon restart, the next call printed an empty list. Run the command again after a few seconds.

Does --spin-time fix stale entries?

No, not while the daemon is running. ros2 node list --spin-time 5 returned in 0.30 s and still listed the dead node. With the daemon stopped or with --no-daemon, --spin-time 1 made discovery reliable; --spin-time 0 missed a running node.

Is --no-daemon always correct?

It never showed a dead node, but it missed a live one in 2 of 5 calls because its discovery wait is short. Use --no-daemon --spin-time 1 when the list has to be complete.
