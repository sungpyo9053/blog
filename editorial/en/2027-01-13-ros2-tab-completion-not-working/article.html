Short answer: in zsh, sourcing setup.zsh does not leave ros2 registered for completion on Humble, Jazzy or Lyrical. ros2cli registers it, then the next completion file in the same setup, rosidl-argcomplete.zsh, runs compinit again and the registration is gone. Re-register it yourself after the source line. This worked on all three distros, with or without your own compinit:

# ~/.zshrc
source /opt/ros/jazzy/setup.zsh
autoload -Uz compinit && compinit                     # optional, oh-my-zsh does this for you
eval "$(register-python-argcomplete ros2)"             # Jazzy, Lyrical
# eval "$(register-python-argcomplete3 ros2)"          # Humble: only the 3 name exists
source /usr/share/colcon_argcomplete/hook/colcon-argcomplete.zsh   # for colcon

In bash, completion worked as soon as .bashrc sourced setup.bash. It failed when the ROS environment came from a parent process and the shell itself never sourced anything. colcon needs its own hook in both shells.

Why zsh loses the registration

With AMENT_TRACE_SETUP_FILES=1, setup.zsh showed that it sources two completion files in this order: share/ros2cli/environment/ros2-argcomplete.zsh and then share/rosidl_cli/environment/rosidl-argcomplete.zsh. I checked the table after each step:

ros2-argcomplete.zsh alone: comps[ros2]=_ros2_argcomplete
setup.zsh: comps[ros2]=<none> comps[rosidl]=_python_argcomplete

That's the Jazzy output. Lyrical was identical, and Humble showed the same pattern with its older bash-style function. The rosidl file starts with these two lines on all three distros:

autoload -U +X compinit && compinit
autoload -U +X bashcompinit && bashcompinit

Running compinit again rebuilds the completion table, so the ros2 entry added a moment earlier is dropped. Then rosidl registers itself, so only rosidl survives. On Jazzy and Lyrical, ros2cli's own file already avoids this. It only runs compinit when _comps doesn't exist yet (if (( ! ${+_comps} ))), the change proposed in ros2cli issue 534. Humble's ros2cli file still calls compinit unconditionally. Either way, the rosidl file runs last and undoes it. That's why moving your own compinit line around never helped. Any line that registers ros2 after setup.zsh fixes it, because nothing runs compinit after it. If oh-my-zsh or your own .zshrc runs compinit later, put the eval line after that.

bash: the shell has to source it

Completion in bash is a shell function plus a complete rule. Both live only in the shell that sourced setup.bash. Environment variables are passed to child processes, but functions and complete rules aren't. In my run, a bash -i that got PATH, AMENT_PREFIX_PATH, PYTHONPATH and the rest from a parent that sourced setup.bash could run ros2, but Tab did nothing. ros2 ver stayed ros2 ver. You get this setup with docker exec -it container bash into an image whose entrypoint sourced ROS, or with an IDE terminal started from a shell that sourced ROS. The fix is to source setup.bash in that shell, or in its ~/.bashrc. Sourcing local_setup.bash instead of setup.bash is a different problem, covered in local_setup.bash vs setup.bash.

Which register command exists

The thread fixes say register-python-argcomplete3. That name only existed on Humble:

ros2cli's ros2-argcomplete.bash tries both names, so bash works either way. If one .zshrc has to work on several machines, the same test works there: if (( $+commands[register-python-argcomplete3] )); then eval "$(register-python-argcomplete3 ros2)"; else eval "$(register-python-argcomplete ros2)"; fi. I didn't run that exact line, only each branch on its own distro.

The complete -o nospace -o default -F _python_argcomplete ros2 line from the same issue worked on Humble. On Jazzy and Lyrical it printed the bad math expression errors at the top of this page. In those versions _python_argcomplete is a native zsh function, and zsh's complete wrapper calls it as if it were a bash one. compdef _ros2_argcomplete ros2 worked on Jazzy and Lyrical. It uses ros2cli's own zsh function, which also keeps a leading ~ unquoted (ros2cli issue 1279). On Humble it failed, because __python_argcomplete_run only exists in argcomplete 3.

pip argcomplete did not break it

Older reports blame a pip-installed argcomplete in ~/.local. I installed argcomplete 3.7.2 with pip into a separate user base and set PYTHONUSERBASE to use it. The apt shell glue stayed in place. In bash, and in zsh with the eval line, completion still worked on all three distros, including Humble, where the apt version is 1.8.1. I didn't test the zsh 5.4 versions from Ubuntu 18.04 that the original issue was about.

colcon needs its own hook

After sourcing setup.bash or setup.zsh, colcon bu<TAB> stayed as typed. After adding source /usr/share/colcon_argcomplete/hook/colcon-argcomplete.bash (or .zsh in zsh), it completed to colcon build. The hook files were at that path on Ubuntu 22.04, 24.04 and 26.04, from python3-colcon-argcomplete 0.3.3 in all three images. The path didn't change on 24.04.

Launch file names that don't complete

I made a fake installed package my_bringup with these files in share/my_bringup/launch/: robot.launch.py, robot_launch.py, robot.py, view.launch.xml, sim.launch.yaml, bringup_launch.xml, params.yaml, plus top.launch.py directly in share/my_bringup/. ros2 launch my_bringup <TAB><TAB> listed seven of the eight files, in both shells, on all three distros. robot.py was missing. params.yaml was listed. The completer keeps files whose name ends with one of these suffixes (printed from ros2launch.api.api.is_launch_file.extensions):

('launch.py', 'launch.xml', 'yaml', 'xml', 'launch.yaml', 'launch', 'launch.yml', 'yml')

A Python launch file must end in launch.py to be offered, so robot.launch.py and robot_launch.py both work. Any YAML or XML file in the package's share folder is offered too, parameter files included. The completer only sees what's installed in share/, so a launch file that's still only in src/ won't show up. Install it with data_files in setup.py or install(DIRECTORY launch ...) in CMake, rebuild, and source again.

The zsh failure and the eval fix behaved the same on Humble, Jazzy and Lyrical. The differences were the argcomplete version (1.8.1, 3.1.4, 3.6.3), the register command name, and two zsh lines from forum answers. complete -F _python_argcomplete worked only on Humble, and compdef _ros2_argcomplete worked only on Jazzy and Lyrical. Humble's ros2-argcomplete.zsh runs compinit unconditionally. Jazzy's and Lyrical's check _comps first. All three ros2cli zsh files already contain the ~ fix. FAQ

Why does ros2 tab completion not work in zsh?

In my run, sourcing setup.zsh left ros2 unregistered on Humble, Jazzy and Lyrical. ros2cli registers it, then rosidl-argcomplete.zsh runs compinit again and the entry is dropped. Add eval "$(register-python-argcomplete ros2)" after the source line, or the register-python-argcomplete3 version on Humble.

Does the order of compinit and source setup.zsh matter?

No. Running compinit before or after setup.zsh both failed, because setup.zsh runs compinit itself after registering ros2. What matters is that something registers ros2 after the last compinit.

register-python-argcomplete3: command not found. What do I use?

Use register-python-argcomplete. Only Humble's Ubuntu 22.04 package had the 3 name. Jazzy on 24.04 and Lyrical on 26.04 only had register-python-argcomplete.

Why does ros2 completion not work in docker exec bash?

The shell got the ROS environment variables from its parent but never sourced setup.bash. Completion functions aren't inherited, so ros2 ran but Tab did nothing. Source setup.bash in that shell or in ~/.bashrc.

Why are my launch files not shown by ros2 launch tab completion?

The completer only lists installed files whose names end in launch.py, launch.xml, launch.yaml, launch.yml, launch, xml, yaml or yml. robot.py was not listed. robot.launch.py and robot_launch.py were. The file also has to be installed into the package's share folder.
