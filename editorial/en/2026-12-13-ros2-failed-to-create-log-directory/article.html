terminate called after throwing an instance of 'rclcpp::exceptions::RCLError'
  what():  failed to configure logging: Failed to create log directory: /home/u/.ros/log, at ./src/rcl_logging_spdlog.cpp:138
Aborted (core dumped)

In Python the same failure ends in rclpy._rclpy_pybind11.RCLError: failed to initialize logging: Failed to create log directory: /home/u/.ros/log. On Jazzy and Lyrical the path is quoted and followed by an errno, for example Failed to create log directory '/home/u/.ros/log': 13. A close relative is Failed to get logging directory, which shows up when HOME is unset or empty.

Short answer: every ROS 2 node writes a log file to disk when it starts. By default the file goes in ~/.ros/log, and if the process can't create or write that directory, rclcpp::init or rclpy.init fails and the node never starts. This usually happens in Docker, where a non-root user has a HOME it can't write to, no HOME at all, or a ~/.ros owned by root. The fix that worked both with an unwritable HOME and with no HOME, for Python nodes, C++ nodes and ros2 launch, on Humble, Jazzy and Lyrical, was to point ROS_LOG_DIR at a directory the user can write:

export ROS_LOG_DIR=/tmp/ros_logs    # created on first start, nested paths too
ros2 run my_pkg my_node

If you don't need log files at all, a single node also starts with --ros-args --disable-external-lib-logs. That flag doesn't help ros2 launch, because launch writes its own launch.log through a separate code path.

The number after the path is the errno. 13 is EACCES (permission denied) and 20 is ENOTDIR (the path exists but isn't a directory). In C++ every row ended with exit code 134, meaning the process aborted. In Python every row ended with exit code 1 and a traceback through rclpy_logging_configure.

The ~/.ros/log owned by root case is the one people miss. The directory exists, so creating it isn't the problem. Opening a file inside it is, and the message no longer says "log directory" at all. You get it after a container ran a node once as root and later runs as a normal user, or when ~/.ros is a volume created by root on the host.

Why a node needs a writable directory at all

ROS 2 logging has three outputs: the console, the /rosout topic, and a file written by an external logging library. On these images that library is spdlog, loaded through rcl_logging_spdlog. The file output is set up during init, before your node object exists. If it fails, init fails with it. Nothing in your own code runs, so you can't catch it in the node.

Every process writes its own file. Twenty runs of the Python node left twenty files named like python3_1005_1793749551727.log, and twenty runs of the C++ node left twenty named like cpp_node_1253_1793749559504.log. The name is the executable, the process ID and a millisecond timestamp. Each file held one line, the same [INFO] ... NODE-OK line the console showed.

The About Logging page gives the lookup order. ROS_LOG_DIR "If non-empty, use the exact directory as specified in this variable". If it's empty, ROS uses ROS_HOME, and ROS_HOME defaults to ~/.ros. It also says "In all cases, the ~ character is expanded to the user's HOME directory." That last part explains the HOME unset case. Every default path starts with ~, so with no HOME the expansion fails, and the error says Failed to get logging directory instead of naming a path. In my run, setting ROS_LOG_DIR or ROS_HOME to an absolute path fixed that case too. No ~ was left to expand.

The same page writes the ROS_HOME path as $ROS_HOME/.log. What I measured on all three distros was $ROS_HOME/log, without the dot.

Cause 1: a HOME the user can't write

This is the case in the Robotics Stack Exchange question about Docker and rviz2. A Dockerfile creates /home/user as root, or docker run --user gives a uid whose HOME is still /root or /. Then ~/.ros/log can't be created. The C++ node printed the exact message from the top of this page and aborted. The Python node raised RCLError. The ros2 CLI hit it too. ros2 topic list --no-daemon and ros2 topic pub --once both printed failed to initialize logging: Failed to create log directory '/home/u/.ros/log': 13 and exited with code 1, because they create a node internally.

A HOME that doesn't exist fails the same way unless the parent is writable. With HOME=/nonexistent the message named /nonexistent/.ros/log. With HOME=/tmp/hb, a path that didn't exist either, the node created /tmp/hb/.ros/log and started, because /tmp is writable. Creation is recursive, so a missing parent is fine as long as some ancestor can be written.

Fixes, in the order I'd try them:

  • Set ROS_LOG_DIR to a writable absolute path, for example ENV ROS_LOG_DIR=/tmp/ros_logs in the Dockerfile. It worked for every node type I tried.
  • Give the user a real, writable home: create it with the right owner in the Dockerfile (useradd -m, or chown after mkdir), or pass -e HOME=/tmp/somewhere.
  • Set ROS_HOME instead if you also want other ROS files out of ~/.ros. Logs then go to $ROS_HOME/log.

Cause 2: HOME unset or empty

This is the case in ros2/ros2#1332 (a node started from Python's subprocess) and ros2/rcl_logging#72 (rclpy inside a Django server under supervisor). Both are environments that may not pass HOME through. On Humble and Jazzy the output starts with an rcutils warning block, which looks like the main error but isn't:

>>> [rcutils|error_handling.c:108] rcutils_set_error_state()
This error state is being overwritten:
  'rcutils_expand_user failed, at ./src/logging_dir.c:81'
with this new error message:
  'Failed to get logging directory, at ./src/rcl_logging_spdlog.cpp:131'
rcutils_reset_error() should be called after error handling to avoid this.
terminate called after throwing an instance of 'rclcpp::exceptions::RCLError'
  what():  failed to configure logging: Failed to get logging directory, at ./src/rcl_logging_spdlog.cpp:131

Lyrical prints one line instead: Failed to get logging directory: rcutils_expand_user failed, at ./src/logging_dir.c:82, at ./src/rcl_logging_spdlog.cpp:198. An empty HOME= gave the same output as an unset one on all three distros.

The fix is to pass HOME to the child process, or to set ROS_LOG_DIR or ROS_HOME to an absolute path. Both worked with HOME unset. With subprocess, the usual mistake is passing env={...} without copying os.environ. I didn't run that variant, but the effect on the child is the same: no HOME.

Cause 3: ~/.ros/log left behind by root

When ~/.ros/log already exists and belongs to root, the directory check passes and the file open fails. spdlog throws its own exception, so the text differs from the other cases:

terminate called after throwing an instance of 'spdlog::spdlog_ex'
  what():  Failed opening file /home/r/.ros/log/cpp_node_357_1793749465490.log for writing: Permission denied

In Python it's RuntimeError: Failed opening file ... for writing: Permission denied, not RCLError. This matches the comment under the Stack Exchange question that chown -R user /home/user fixed it. Either change the owner of ~/.ros or point ROS_LOG_DIR somewhere else. I tested ROS_LOG_DIR with an unwritable and an unset HOME, not with this exact case.

ros2 launch fails earlier, with a Python traceback

ros2 launch doesn't use the rcl logging path for its own log. The launch library creates a timestamped directory for launch.log with Python's os.makedirs, before any node starts. With the unwritable HOME, all three distros failed with a traceback ending in:

  File ".../launch/logging/__init__.py", line 81, in _make_unique_log_dir
PermissionError: [Errno 13] Permission denied: '/home/u/.ros'

On Lyrical the traceback goes through _get_logging_directory() and os.makedirs, and ends with the same PermissionError. With HOME unset, launch failed with PermissionError: [Errno 13] Permission denied: '~'. The ~ wasn't expanded, so launch tried to create a directory with that literal name in the current directory, which wasn't writable.

ROS_LOG_DIR fixed launch on all three distros. With ROS_LOG_DIR=/tmp/lc, launch created a timestamped subdirectory holding launch.log. The Python node's own python3_...log went directly into /tmp/lc, not into that subdirectory. The --disable-external-lib-logs flag is a node argument, so it can't stop launch from creating its directory. An open issue, ros2/launch#761, asks for an option to turn that off.

I also tried to reproduce the "about 20% of the time" failure from a comment on the Stack Exchange question as a race. Ten C++ nodes started at once into a log directory that didn't exist yet. In 5 rounds per distro, all 50 starts created their log files and none printed a log directory error. Version notes

  • Humble prints Failed to create log directory: /home/u/.ros/log, at ./src/rcl_logging_spdlog.cpp:138. Jazzy and Lyrical print Failed to create log directory '/home/u/.ros/log': 13 with the errno, at rcl_logging_spdlog.cpp:154 on Jazzy and :214 on Lyrical. Drop the quotes, errno and line number when you search.
  • For HOME unset, Humble and Jazzy print the "error state is being overwritten" block first. Lyrical folds both messages into one line.
  • Lyrical ships a package called rcl_logging_implementation, which its package.xml describes as "Provides the ability to load logging implementations at runtime." Only rcl_logging_spdlog was installed in the image, and I didn't try another backend.
  • The launch traceback differs only in line numbers and file paths. On all three distros it ends in PermissionError.

Not tested

Read-only root filesystems (docker run --read-only), switching the logging backend (rcl_logging_noop, rcutils or syslog), ROS_HOME or a writable HOME with ros2 launch, the ros2 CLI with any of the fixes, nodes started from Python subprocess with a stripped environment, the ros2 daemon, Foxy, Iron and Rolling, and other RMW implementations than the default.

If your node starts but can't find Python packages in the same container, see ros2 run ignores your conda or venv. It's another case where the environment the node gets differs from your shell.

FAQ

What does "Failed to create log directory" mean in ROS 2?

The node tried to create its log directory, ~/.ros/log by default, and the user running it didn't have permission. Init fails, so the node never starts. In my runs that happened when HOME pointed to a root-owned or missing directory, or when ROS_LOG_DIR pointed somewhere unwritable.

How do I fix it in a Docker container running as a non-root user?

Set ROS_LOG_DIR to a writable absolute path such as /tmp/ros_logs. It doesn't need to exist yet. That fixed Python nodes, C++ nodes and ros2 launch on Humble, Jazzy and Lyrical. Giving the user a writable HOME also fixed the nodes.

Why do I get "Failed to get logging directory"?

HOME was unset or empty, so ~ couldn't be expanded. That happens with some process managers and with subprocess when the environment isn't passed through. Pass HOME, or set ROS_LOG_DIR or ROS_HOME to an absolute path. Both worked with HOME unset.

Can I disable ROS 2 log files?

For a single node, yes: --ros-args --disable-external-lib-logs started the node with no log file even when HOME wasn't writable. It didn't help ros2 launch, which creates its own launch.log directory first and fails there.

Why does it say "Failed opening file ... Permission denied" instead?

~/.ros/log already exists but belongs to another user, usually root from an earlier run or a volume. Change its owner or set ROS_LOG_DIR to another path.
