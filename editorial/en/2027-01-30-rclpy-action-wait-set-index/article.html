rclpy._rclpy_pybind11.RCLError: Failed to get number of ready entities for action client: wait set index for status subscription is out of bounds, at ./src/rcl_action/action_client.c:623

The same crash also shows up as wait set index for feedback subscription is out of bounds, wait set index for result client is out of bounds, or, from a plain Python wait set, IndexError: wait set index too big. The traceback always ends in an executor's _wait_for_ready_callbacks, inside is_ready(wait_set).

Short answer: one node is being waited on by two wait sets at the same time. That happens when two threads spin the same executor (Humble), or when the node gets moved into a second executor while the first one is still spinning it. rclpy.spin_until_future_complete(node, ...) and rclpy.spin_once(node) do that move: they put the node into the global executor. The fix is to spin each node in exactly one place, and to wait for action results without spinning again:

import threading

def wait_for(future, timeout_sec):
    """Block this thread until the future is done. Never spins."""
    done = threading.Event()
    future.add_done_callback(lambda f: done.set())
    return done.wait(timeout_sec)

# one executor, spun by one thread, for the whole life of the node
executor = rclpy.executors.SingleThreadedExecutor()
executor.add_node(node)
threading.Thread(target=executor.spin, daemon=True).start()

# any other thread:
goal_future = action_client.send_goal_async(goal)
if wait_for(goal_future, 5.0):
    result_future = goal_future.result().get_result_async()
    if wait_for(result_future, 5.0):
        result = result_future.result().result

In my runs this pattern finished 509 to 598 goals per 6-second run with zero errors on Humble, Jazzy and Lyrical. Every pattern that moved the node between executors raised the error on all three distros.

What I ran

One Python process per run. An action server node (type tf2_msgs/action/LookupTransform, because ros-base has no example_interfaces) got its own SingleThreadedExecutor in its own thread. It accepted every goal and succeeded right away. The client node held the action client, a service client for the server's list_parameters service, a 100 Hz timer publishing std_msgs/Empty, and 3 subscriptions to that topic.

The main thread sent goals in a loop for 6 seconds. It waited for the goal response and then the result, and counted completed goals. A background thread spun the client's executor. In most cases the spinner called spin_once(timeout_sec=0.05) in a loop and caught exceptions, so I could count every error instead of stopping at the first one. The cases ending in _spin used a plain executor.spin() instead, the way most code does. Each case ran 3 times on each distro, inside ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base, with --network none and default RMW (Fast DDS). The machine had 2 vCPUs. The script is ws.py and the driver is repro.sh.

Why the index goes out of bounds

Every time an executor waits, it builds a new wait set and asks each entity to add itself. An action client adds its goal, cancel and result service clients and its status and feedback subscriptions. rcl_action stores the slot numbers it got inside the action client itself. After the wait, the executor calls is_ready(wait_set), and the action client reads its stored slot numbers back.

Now let a second wait set add the same action client before the first one checks it. The stored slot numbers now belong to the second wait set. When the first executor wakes up and asks, the numbers can point past the end of its own wait set. rcl_action reports wait set index for ... is out of bounds. Subscriptions and QoS event handlers in rclpy keep their slot number in Python the same way. They report IndexError: wait set index too big. On Humble that came from rclpy/qos_event.py and on Jazzy from rclpy/event_handler.py. It's the same race.

I first expected the size of the second wait set to matter, so I ran each moving case twice: once with an extra node holding 30 subscriptions in the second executor, and once without. It didn't decide it. Without the extra node, Humble still had 142, 135 and 134 errors when both executors spun, Jazzy 4, 4 and 7, and Lyrical 13, 12 and 17. Two wait sets on one node at the same moment is enough.

Two threads spinning one executor (Humble)

On Humble, nothing stops two threads from spinning the same executor. With a MultiThreadedExecutor, a background spin_once() loop plus executor.spin_until_future_complete() in the main thread gave 68, 102 and 71 errors per 6-second run. The first one came after 0.025, 0.029 and 0.198 seconds. Most were status subscription (202 in total), the rest feedback subscription (39). Still, 368 to 414 goals finished per run.

With a SingleThreadedExecutor the same pattern produced only 2 errors in 3 runs: one status subscription error and one ValueError: generator already executing.

The real damage shows up when the background thread uses executor.spin(). spin() doesn't catch the error, so the thread ends. On Humble that happened after 0.015, 0.428 and 0.084 seconds. My main thread kept spinning, so goals still finished. In a node where only that background thread spins, every timer and subscription would stop at that point.

I also put the same pattern on a service client. The node still had its action client, and the errors came from the action client: 3,056 to 3,101 per run, mostly wait set index for result client is out of bounds. So one action client on a node is enough to make a service-call pattern crash.

Jazzy and Lyrical refuse a second spin

From Jazzy on, the executor has a lock and a flag. A second spin(), spin_once() or spin_until_future_complete() on an executor that is already spinning raises RuntimeError: Executor is already spinning right away. I found the check in executors.py of rclpy 7.1.12 (Jazzy) and 10.0.11 (Lyrical); Humble's rclpy 3.3.22 has no such check. In my runs every such call raised it. The same-executor goal and service cases hit it 1,986 to 76,281 times per run, and no goal or service call finished. So on Jazzy and Lyrical the same-executor version of this bug turns into a different, clearer error. If you see the wait set error on Jazzy or Lyrical, look for a second executor.

Moving a node into another executor

This is how the error reaches Jazzy and Lyrical. A node belongs to one executor at a time. executor.add_node(node) takes it away from the executor it was in. rclpy.spin_until_future_complete(node, future) and rclpy.spin_once(node) call add_node on the global executor. If another thread is spinning the old executor at that moment, it may be inside a wait with the node's entities in its wait set. The global executor then builds its own wait set with the same entities, and the old executor's next is_ready check fails.

When the node was moved on every goal (global executor, then back to the background executor), the errors came quickly. The first one appeared after 0.001 seconds in all 3 Humble runs. On Jazzy the runs had 26, 20 and 18 errors, and on Lyrical 0, 2 and 6. With rclpy.spin_once(node) in a loop instead, Humble had 1, 26 and 2, Jazzy 25, 25 and 21, Lyrical 0, 2 and 1. With a plain spin() in the background thread, that thread died in every run: after 0.001 seconds on Humble (3 of 3), after 0.011, 0.001 and 0.485 seconds on Jazzy, and after 3.418, 0.011 and 0.010 seconds on Lyrical.

Two executors that both spin, with the node handed back and forth, gave the most errors on Humble: 136, 128 and 124 per run. Jazzy had 9, 4 and 7, Lyrical 34, 51 and 17.

The case with no error is a trap

Calling rclpy.spin_until_future_complete(node, future) on a node that a background executor spins, and never adding it back, gave 0 errors on every distro. Over 500 goals finished per run. That looks like a fix. It isn't. After the first call I printed where the node was. On all three distros it was no longer in the background executor, and node.executor pointed to the global SingleThreadedExecutor. From then on the background thread spins an empty executor. Anything that depends on that executor stops, unless your code keeps spinning the global one. The race only had one chance to hit, at the first call. A program that does this gets a crash now and then, right after startup. rclpy issue 1133 describes the error "early in node lifetime".

All of them avoid the crash for the same reason: no node is in two wait sets at once. Pick by how your code is shaped:

  • Wait on the future, don't spin. The threading.Event helper at the top works from any thread that isn't an executor callback. With a SingleThreadedExecutor it was the fastest option in the table on every distro.
  • Use coroutines inside the node. If the goal is sent from a callback, make the callback async def and await the futures. The executor keeps spinning while the coroutine waits.
  • Give the worker its own node. If a library insists on calling spin_until_future_complete, let it do that on a separate node and executor that nothing else spins. Don't pass it your main node.
  • Don't call rclpy.spin_once(node) or rclpy.spin_until_future_complete(node, ...) on a node that already has an executor. Both move the node.

One anomaly I didn't explain. With MultiThreadedExecutor, Jazzy and Lyrical finished far fewer goals than Humble in this setup: 8 to 13 per run on Jazzy against 439 to 486 on Humble, for the same code. With SingleThreadedExecutor all three were close (509 to 598). I didn't look into why, so treat the low numbers as specific to this test: a 100 Hz timer, 3 subscriptions and 2 vCPUs. If you need throughput and don't need parallel callbacks, measure a SingleThreadedExecutor first.

If your symptom is a blocking call that never returns rather than a crash, the executor is probably not spinning at all while you wait. rclpy and asyncio: hung service calls and the thread bridge that works covers that case.

FAQ

What does "wait set index for status subscription is out of bounds" mean?

The executor checked an action client against its wait set. The action client's stored slot numbers came from a different wait set, built by another executor or thread at the same moment. The node is being spun from two places. In my runs this happened with two threads spinning one executor on Humble, and with a node moved into a second executor on all three distros.

Is "IndexError: wait set index too big" the same bug?

Yes. It's the same race, hitting a subscription or QoS event handler instead of the action client. It came from qos_event.py on Humble and event_handler.py on Jazzy, in the same runs and patterns as the action client errors. Lyrical showed only the action client form.

Why does it happen when I call rclpy.spin_until_future_complete from another thread?

Without an executor= argument, it adds your node to the global executor. That takes the node away from the executor your other thread is spinning, while that executor may still be inside a wait. After the first call the node stayed in the global executor on Humble, Jazzy and Lyrical, so the background executor stopped spinning it.

How do I wait for an action result in rclpy without this error?

Spin the node in one thread only. In any other thread, attach a done callback that sets a threading.Event and wait on the event. Inside a callback, use async def and await the goal and result futures. Both had 0 errors on all three distros.

Does upgrading from Humble to Jazzy fix it?

Partly. Jazzy and Lyrical raise RuntimeError: Executor is already spinning instead of racing when two threads spin one executor. Moving a node between executors still raised the wait set error on both. The upstream fix was still an open pull request on 2026-11-17.
