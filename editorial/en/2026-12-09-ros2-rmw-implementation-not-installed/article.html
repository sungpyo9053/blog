[ERROR] [1793679325.990231649] [rcl]: Error getting RMW implementation identifier / RMW implementation not installed (expected identifier of 'rmw_cyclonedds_cpp'), with error message 'failed to load shared library 'librmw_cyclonedds_cpp.so' due to dlopen error: librmw_cyclonedds_cpp.so: cannot open shared object file: No such file or directory, at ./src/shared_library.c:99, at ./src/functions.cpp:65', exiting with 1., at ./src/rcl/rmw_implementation_identifier_check.c:139

That is a Python node on Humble with RMW_IMPLEMENTATION=rmw_cyclonedds_cpp set in a container that only has Fast DDS. A C++ node, ros2 run, ros2 topic list and ros2 topic list --no-daemon printed the same line, and so did Jazzy and Lyrical, apart from the source line numbers.

Short answer: RMW_IMPLEMENTATION names a middleware library that the process can't load. The official ros-base images ship only rmw_fastrtps_cpp, so any other value fails. The useful part of the message is the text after dlopen error:. If it names librmw_<your value>.so, the package isn't installed or the name is misspelled. If it names a different library, the RMW package is installed but one of its dependencies can't be found. The fix that worked on Humble, Jazzy and Lyrical:

sudo apt install ros-$ROS_DISTRO-rmw-cyclonedds-cpp   # or ros-$ROS_DISTRO-rmw-zenoh-cpp
source /opt/ros/$ROS_DISTRO/setup.bash                # needed for Zenoh, harmless for Cyclone
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ros2 daemon stop

Or unset the variable to go back to the default: unset RMW_IMPLEMENTATION. An empty value also gave Fast DDS in my runs.

What I ran

On 2026-11-03 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images on a 2-vCPU Ubuntu server, one distro at a time. In all three, /opt/ros/$ROS_DISTRO/lib held one RMW library, librmw_fastrtps_cpp.so, and ros2 doctor --report showed middleware name : rmw_fastrtps_cpp. One script ran every case in order:

  • A Python probe that prints a line before import rclpy, before rclpy.init() and before create_node, then prints the RMW identifier. It catches any Python exception and exits with code 3 if one occurs.
  • ros2 run rclcpp_components component_container as a stock C++ node, stopped after 4 seconds.
  • A one-file rclcpp package, built with colcon build, that prints rmw_get_implementation_identifier().
  • ros2 topic list with the daemon stopped and with --no-daemon.

Each was run with RMW_IMPLEMENTATION unset, empty, set to uninstalled names, misspelled and wrongly capitalised. Then the script installed ros-$ROS_DISTRO-rmw-cyclonedds-cpp and ran the cases again. It also removed libddsc.so.0 for one run, ran a Fast DDS talker against a Cyclone DDS listener (and the reverse) at 10 Hz, started the daemon under one RMW and queried it from a shell set to the other, and finally installed rmw_zenoh_cpp.

It fails at import, and you can't catch it

The probe printed stage: import rclpy and nothing after it. The error came while import rclpy was loading the C extension, before rclpy.init() ran. The process exited with code 1, not the 3 my exception handler would have returned, so no Python exception was raised. rcl prints the message and ends the process itself. That is what exiting with 1. in the message means. A try/except around rclpy.init() won't help, and neither will one around the import.

It is also fast. The Python probe failed in 0.05 s on Humble, 0.08 s on Jazzy and 0.07 s on Lyrical, wall time. A C++ node, a ros2 CLI command and the built rclcpp probe all failed in 0.40 s or less. So if a launch file shows a process that died at once with exit code 1, look in its output for this line.

Cause 1: the package isn't installed

This is the common case. A tutorial says export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp, often in ~/.bashrc, and the machine or container doesn't have Cyclone DDS. The MoveIt 2 tutorials do this, and one question below hit the error right after that step. Every RMW name I tried that wasn't installed gave the same line: rmw_cyclonedds_cpp, rmw_connextdds and rmw_zenoh_cpp.

Installing the package fixed it on all three distros:

After the install, the same shell worked without sourcing setup.bash again. The probe printed OK identifier = rmw_cyclonedds_cpp and the component container ran until it was stopped. The rclcpp package I had built before the install also worked with Cyclone without a rebuild. In a binary install, the RMW is picked when the process starts, not when you compile, so you don't need to rebuild your workspace after adding an RMW.

Cause 2: a typo or the wrong case

rcl takes the value as it is and loads lib + value + .so. rmw_cyclone_dds_cpp became librmw_cyclone_dds_cpp.so, and RMW_CycloneDDS_cpp became libRMW_CycloneDDS_cpp.so. Neither exists, so you get the same "not installed" message as for a missing package. Compare the file name in the dlopen part with what ls /opt/ros/$ROS_DISTRO/lib/librmw_*.so shows. The correct names are all lowercase: rmw_fastrtps_cpp, rmw_cyclonedds_cpp, rmw_connextdds, rmw_zenoh_cpp.

An empty value is not an error. RMW_IMPLEMENTATION= gave rmw_fastrtps_cpp on all three distros, the same as unsetting it.

Cause 3: installed, but a library it needs isn't found

This is the case in GitHub issue rmw_cyclonedds #478. The headline still says "RMW implementation not installed", but the dlopen part names a different file. I reproduced it in two ways.

Zenoh, right after apt install ros-$ROS_DISTRO-rmw-zenoh-cpp, in the shell that had already sourced setup.bash:

[ERROR] [1793679693.799044504] [rcl]: Error getting RMW implementation identifier / RMW implementation not installed (expected identifier of 'rmw_zenoh_cpp'), with error message 'failed to load shared library 'librmw_zenoh_cpp.so' due to dlopen error: libzenohc.so: cannot open shared object file: No such file or directory, at ./src/shared_library.c:99, at ./src/functions.cpp:65', exiting with 1., at ./src/rcl/rmw_implementation_identifier_check.c:143

That is Jazzy. Humble and Lyrical printed the same thing. librmw_zenoh_cpp.so was found, but the Zenoh C library it links to was not on LD_LIBRARY_PATH yet. Running source /opt/ros/$ROS_DISTRO/setup.bash again fixed it on all three. Cyclone didn't need this because its libddsc.so.0 goes into /opt/ros/$ROS_DISTRO/lib/x86_64-linux-gnu, which was already on the path. If you just installed an RMW and get this error, open a new terminal or source the setup file again before you try anything else.

Cyclone with its DDS library missing. I moved /opt/ros/$ROS_DISTRO/lib/x86_64-linux-gnu/libddsc.so.0 away for one run. On Humble and Jazzy the message became failed to load shared library 'librmw_cyclonedds_cpp.so' due to dlopen error: libddsc.so.0: cannot open shared object file. On Lyrical my script found no libddsc.so.0 to move, because Lyrical ships Cyclone DDS 11.0.1, so that case is untested there.

Not this error: setup.bash not sourced

If the environment isn't sourced at all, you get a different error. With LD_LIBRARY_PATH removed and the default RMW, Python failed with ImportError: librcl_action.so: cannot open shared object file, followed by "The C extension ... failed to be imported while being present on the system". The C++ container failed with error while loading shared libraries: libcomponent_manager.so and exit code 127. Both happen before rcl gets a chance to check the RMW. So the "RMW implementation not installed" line means ROS itself loaded, and the problem is only the middleware library.

Mixing RMWs after the fix

Once two RMWs are installed, it's easy to end up with nodes on different ones. The two DDS implementations talked to each other on one host. A Fast DDS talker sent 100 messages at 10 Hz for 10 seconds, and a Cyclone DDS listener started 1 second later and listening for 8 seconds received 71 on Humble and 70 on Jazzy and Lyrical. In the other direction the Fast DDS listener received 81, 80 and 80. Each listener also saw the other process's node name. I didn't run the same timing with both sides on one RMW, so don't read those counts as a loss rate.

Zenoh did not talk to DDS. With a Zenoh router running, a Zenoh listener got 0 messages from a Fast DDS talker and saw only itself, on all three distros. A Zenoh talker to a Zenoh listener worked: 50, 50 and 49 messages in 5 seconds. If nodes are running but can't see each other, check that they all use the same RMW_IMPLEMENTATION before you look at discovery range and network settings.

Without a router, Zenoh didn't fail. It printed Unable to connect to a Zenoh router. Have you started a router with `ros2 run rmw_zenoh_cpp rmw_zenohd`?, then Proceeding with initialization but other peers will not discover or receive data from peers in this session until a router is started. The probe took 0.67 to 0.72 s instead of 0.18 to 0.23 s with a router, and exited 0.

The daemon kept its old RMW

The ROS docs say to check that the daemon isn't running with the previous RMW, because "the ROS 2 command line tools will fail". My run showed something quieter. I started the daemon with RMW_IMPLEMENTATION=rmw_fastrtps_cpp, started a Cyclone talker, then ran ros2 node list from a shell set to rmw_cyclonedds_cpp. It returned /talker_py with exit code 0, as did --no-daemon. Only one daemon process was running, and its command line still ended in --rmw-implementation rmw_fastrtps_cpp. ros2 daemon status printed only The daemon is running, without the RMW. So the CLI used a Fast DDS daemon for a Cyclone shell and gave no sign of it. That worked here only because the two DDS implementations interoperate. Run ros2 daemon stop whenever you change the variable. You can see which RMW the daemon has with ps -eo args | grep ros2-daemon.

Version notes

The message was word for word the same on Humble, Jazzy and Lyrical. Only the source locations moved: shared_library.c:99, functions.cpp:65 and rmw_implementation_identifier_check.c:139 on Humble; :99, :65 and :143 on Jazzy; :96, :67 and :143 on Lyrical. Drop them when you search. The CMake error was at get_default_rmw_implementation.cmake:60 on all three. Jazzy's call stack showed only CMakeLists.txt:4 (find_package), while Humble and Lyrical listed the chain through rcl and rclcpp. The docs also show a second form, Expected RMW implementation identifier of '...' but instead found 'rmw_fastrtps_cpp', exiting with 102, for installs with a single RMW. I never got it from the binary packages, only the "not installed" form. rmw_zenoh_cpp was in apt for all three: 0.1.11 on Humble, 0.2.11 on Jazzy and 0.10.6 on Lyrical.

Not tested

The "rmw_implementation was built only with support for" error from source builds, the "exiting with 102" form, Connext and GurumDDS installs, Windows and macOS, snaps, conda and RoboStack, RMW mixing across machines, a daemon left on Zenoh, the missing libddsc case on Lyrical, and setting RMW_IMPLEMENTATION inside a launch file.

FAQ

What does "RMW implementation not installed (expected identifier of ...)" mean?

RMW_IMPLEMENTATION names a middleware library that couldn't be loaded. Read the text after dlopen error:. If it names librmw_<value>.so, the package is missing or the name is misspelled. If it names another library, the package is installed but a dependency isn't on the library path.

How do I install rmw_cyclonedds_cpp?

sudo apt install ros-$ROS_DISTRO-rmw-cyclonedds-cpp. In my runs it added 8 packages, about 2 MB to download, and worked in the same shell right away, with no rebuild of the workspace, on Humble, Jazzy and Lyrical.

I installed the RMW and still get the error. Why?

Check the dlopen part. After installing rmw_zenoh_cpp it named libzenohc.so until setup.bash was sourced again. With Cyclone's libddsc.so.0 missing it named that file. Also check the spelling and case. rmw_cyclone_dds_cpp and RMW_CycloneDDS_cpp both failed.

Why does colcon build fail with "Could not find ROS middleware implementation"?

The variable was set at build time to an RMW that isn't installed. The error lists the valid values after "Choose one of the following". Unset the variable or install that RMW. Both made the build pass on all three distros.

Can I catch this error in Python?

No. In my runs it happened during import rclpy, and rcl ended the process with exit code 1 without raising a Python exception. Fix the environment before the process starts.
