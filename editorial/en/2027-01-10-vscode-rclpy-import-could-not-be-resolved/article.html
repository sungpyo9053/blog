node.py:1:8 - error: Import "rclpy" could not be resolved (reportMissingImports)
node.py:3:6 - error: Import "std_msgs.msg" could not be resolved (reportMissingImports)
node.py:6:6 - error: Import "my_interfaces.msg" could not be resolved (reportMissingImports)

In VS Code the same text shows up as a yellow or red squiggle under the import, tagged Pylance(reportMissingImports). The node still runs with ros2 run. Only the editor is confused.

Short answer: Pylance can't see ROS 2 Python packages because they aren't in the interpreter's normal site-packages. Sourcing setup.bash puts them on PYTHONPATH, and the checker only finds them if it gets that PYTHONPATH or the same folders in extraPaths. The fix that worked on Humble, Jazzy and Lyrical in every case: source your workspace, print PYTHONPATH, and copy every entry into python.analysis.extraPaths. Don't type the paths by hand. On Humble, rclpy isn't in the folder most answers tell you to add.

source /opt/ros/humble/setup.bash
source ~/ws/install/setup.bash
python3 -c "import json,os; print(json.dumps({'python.analysis.extraPaths': [p for p in os.environ['PYTHONPATH'].split(':') if p]}, indent=2))"

The list it prints is the same PYTHONPATH list I put in extraPaths for the passing cases. Paste the output into .vscode/settings.json. For plain pyright, put the list under "extraPaths" in pyrightconfig.json. Starting code . from a terminal where you already sourced the workspace should also work, because the checker reads PYTHONPATH from its environment. I tested that with the pyright CLI, not with the VS Code app.

A note on what I measured. Pylance is closed source, but its type checker is pyright. I ran the pyright 1.1.389 command line inside the official ROS 2 Docker images and gave it the same inputs Pylance gets: a Python file, an environment, and an extraPaths list. I did not run VS Code itself.

What I ran

On 2026-11-08 I started one container per distro from ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base. I downloaded Node.js 20.18.0 and installed pyright 1.1.389 from npm, then disconnected the container from the network before any test. In each container I built a small workspace twice, once with plain colcon build and once with --symlink-install. It had two packages:

  • my_interfaces, an ament_cmake package with one message, msg/Point2.msg (float64 x, float64 y), built by rosidl_generate_interfaces.
  • my_py_pkg, made with ros2 pkg create --build-type ament_python, with one module my_py_pkg/helpers.py that defines add(a, b).

The test file, node.py, sits outside the workspace and imports all seven modules. It creates a node, a Point2 and a String. For each case I ran pyright node.py under env -i, so no stray variables leaked in. Then I either sourced a setup file or wrote a pyrightconfig.json with an extraPaths list. I also asked Python where each module came from. Each check took 1.0 to 2.7 seconds.

Cause 1: VS Code doesn't have your sourced environment

With nothing sourced, all seven imports failed on all three distros. That's what you get when VS Code starts from a desktop icon or a dock. It never ran setup.bash, so PYTHONPATH is empty, and /usr/bin/python3 on its own knows nothing about /opt/ros.

Sourcing only /opt/ros/<distro>/setup.bash fixed the five ROS imports and left two errors, my_interfaces.msg and my_py_pkg.helpers. Sourcing install/setup.bash from the workspace brought it to 0 errors on all three distros, for both plain and symlink builds. So the checker did use PYTHONPATH from its environment. That's why "launch code from a sourced terminal" works for some people and not for others. It depends on how VS Code was started, and whether a VS Code window was already running when you typed code .. I didn't test that last part.

The sourced setup has two weak points. It breaks when you open the folder another way. It also breaks after you add a package and rebuild, because the new package is only on PYTHONPATH in shells that sourced the workspace after the build. A settings file doesn't depend on how the editor was started, so I'd use one.

Cause 2: on Humble, rclpy isn't in lib/python3.10/site-packages

Suppose you add just one folder to python.analysis.extraPaths: /opt/ros/<distro>/lib/python3.X/site-packages. On Jazzy and Lyrical that was enough for every ROS import. On Humble it left 5 of 7 imports broken. Python showed why:

rclpy /opt/ros/humble/local/lib/python3.10/dist-packages/rclpy/__init__.py
std_msgs /opt/ros/humble/local/lib/python3.10/dist-packages/std_msgs/__init__.py
launch /opt/ros/humble/lib/python3.10/site-packages/launch/__init__.py
launch_ros /opt/ros/humble/lib/python3.10/site-packages/launch_ros/__init__.py

On Humble, packages built with CMake (rclpy, every message package) go to local/lib/python3.10/dist-packages. Pure Python packages built with setuptools (launch, launch_ros) go to lib/python3.10/site-packages. After sourcing, Humble's PYTHONPATH had both:

/opt/ros/humble/lib/python3.10/site-packages
/opt/ros/humble/local/lib/python3.10/dist-packages

Jazzy and Lyrical had one folder each, /opt/ros/jazzy/lib/python3.12/site-packages and /opt/ros/lyrical/lib/python3.14/site-packages, and rclpy, std_msgs and launch were all in it. If you're on Humble and only launch resolves while rclpy stays underlined, this is why. Add the local/.../dist-packages folder too.

Cause 3: your own packages are in install/, under a path you have to look up

With only /opt/ros in the config, my_interfaces.msg and my_py_pkg.helpers failed on every distro. Each workspace package gets its own folder under install/, and the path differs by build type and distro. These are the files colcon produced:

FileHumbleJazzy / Lyrical
Message module _point2.py (ament_cmake)install/my_interfaces/local/lib/python3.10/dist-packages/install/my_interfaces/lib/python3.12/site-packages/ (3.14 on Lyrical)
helpers.py (ament_python, plain build)install/my_py_pkg/lib/python3.10/site-packages/install/my_py_pkg/lib/python3.12/site-packages/ (3.14 on Lyrical)
ament_python, --symlink-installonly my-py-pkg.egg-link in install/my_py_pkg/lib/python3.X/site-packages/, and the code is found through build/my_py_pkg

Guessing install/<pkg>/lib/python3.X/site-packages for every package gave 0 errors on Jazzy and Lyrical. On Humble it gave 4: the three rclpy/std_msgs imports, because the guess left out local/ under /opt/ros too, and my_interfaces.msg, because message packages also use local/.../dist-packages on Humble.

Adding the source folder, src/my_py_pkg, made the ament_python import resolve. It can't work for message packages, because their Python code is generated at build time and doesn't exist under src/. my_interfaces.msg stayed unresolved on all three distros with that config. For custom messages you need the install/ path, and you need to build first.

Cause 4: --symlink-install hides your code behind build/

With --symlink-install, colcon doesn't copy an ament_python package into install/. It writes a my-py-pkg.egg-link file there and puts build/my_py_pkg on PYTHONPATH. That folder holds symlinks back to src/. Python then loaded the package from:

my_py_pkg /ws_sym/build/my_py_pkg/my_py_pkg/__init__.py

The sourced symlink workspace and the full symlink PYTHONPATH in extraPaths both gave 0 errors. Removing just the /ws_sym/build/my_py_pkg entry left one error, Import "my_py_pkg.helpers" could not be resolved, on all three distros. The checker didn't follow the .egg-link in install/. If you filtered "build" paths out of your list because they looked temporary, put them back. If you switch between plain and symlink builds, regenerate the list. The two builds produce different PYTHONPATH entries.

Cause 5: paths for the wrong Python version

Each distro uses a different Python: 3.10 on Humble, 3.12 on Jazzy, 3.14 on Lyrical. A settings file copied from a Humble tutorial into a Jazzy setup points at python3.10 folders that don't exist. I ran the same mismatch on each distro. Jazzy and Lyrical got python3.10 paths and Humble got python3.12 paths. All seven imports failed every time, with no warning that the folders were missing. If a config that "should work" gives you errors on every import, check the Python version in each path against python3 --version.

Version notes

  • Humble (Python 3.10, setuptools 59.6.0): two folders under /opt/ros/humble, and local/lib/python3.10/dist-packages for message packages in your workspace.
  • Jazzy (Python 3.12, setuptools 68.1.2) and Lyrical (Python 3.14, setuptools 78.1.1): one lib/python3.X/site-packages folder for everything, in /opt/ros and in each install/<pkg>.
  • All three wrote a .egg-link and put build/<pkg> on PYTHONPATH for ament_python packages built with --symlink-install. The results matched on every distro.

FAQ

Why does VS Code say Import "rclpy" could not be resolved when my node runs fine?

The node runs in a shell that sourced setup.bash, so rclpy is on PYTHONPATH. The editor's checker usually doesn't have that environment. In my runs, with nothing sourced and no config, all seven ROS and workspace imports failed on Humble, Jazzy and Lyrical.

Which path do I add to python.analysis.extraPaths for rclpy?

On Jazzy it's /opt/ros/jazzy/lib/python3.12/site-packages, and on Lyrical /opt/ros/lyrical/lib/python3.14/site-packages. On Humble you need both /opt/ros/humble/lib/python3.10/site-packages and /opt/ros/humble/local/lib/python3.10/dist-packages, because rclpy and message packages are in the second one.

Why can't Pylance find my custom message package?

Its Python code is generated at build time and only exists in install/, at install/<pkg>/lib/python3.X/site-packages on Jazzy and Lyrical and install/<pkg>/local/lib/python3.10/dist-packages on Humble. Adding the src/ folder doesn't help. Build, source the workspace, and copy the PYTHONPATH entries into extraPaths.

Does --symlink-install break Pylance imports?

Only if you leave out the build/<pkg> folder. With --symlink-install the ament_python package was found through build/my_py_pkg, not install/. Without that entry, my_py_pkg.helpers was unresolved on all three distros.

Does python.analysis.extraPaths replace PYTHONPATH?

Not in my test. With the workspace sourced and a config listing only the /opt/ros folder, pyright resolved all seven imports on all three distros. The two sources were added together.
