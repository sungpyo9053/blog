$ ros2 param list /nospin
Exception while calling service of node '/nospin': None

That is Humble. On Lyrical the same node gives a different line, and on Jazzy you get no line at all, because the command just waits:

Timed out waiting for list_parameters response from node NodeName(name='nospin', namespace='/', full_name='/nospin') (timeout: 5.0s)

Short answer: the node is in the graph and its parameter services exist, but nothing in that process is answering them. A ROS 2 node only answers list_parameters and get_parameters while an executor is spinning it. The None isn't a hidden exception. On Humble, ros2 param list waits about one second for each node's reply, and if no reply arrives it prints the future's exception, which is empty. In my runs four things caused it: a node that never spins, a callback that blocks the only executor thread, a second node that was never added to an executor, and a CLI on a different RMW than the node. The fix for the first one, the teleop_twist_keyboard pattern of a loop that never spins, is to spin in a thread:

import threading, time, rclpy
from rclpy.node import Node

rclpy.init()
node = Node('nospin_fixed')
node.declare_parameter('speed', 0.5)
threading.Thread(target=rclpy.spin, args=(node,), daemon=True).start()
while True:          # your own loop keeps running
    time.sleep(0.1)

With that one line, ros2 param list /nospin_fixed printed speed and use_sim_time in 0.98 s on Humble and 2.81 s on Jazzy and Lyrical. ros2 param get returned Double value is: 0.5 in about 1.1 s on all three.

What I ran

I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images on a 2 vCPU Linux host, one distro at a time. I installed rmw_cyclonedds_cpp in each container, then disconnected the container from the network and used ROS_DOMAIN_ID=88 with localhost-only discovery. Every node was a short rclpy script that declares one parameter, speed = 0.5. For each case the script started the node, waited 4 s, then ran ros2 node list, ros2 param list /name and ros2 param get /name speed, each timed and capped at 30 s. Between cases it stopped the node and restarted the daemon, so no case saw a leftover node from the one before.

For the rows where the command never returned, I also ran it under a small wrapper that sends Ctrl+C (SIGINT) after 10 s, to see whether the interrupt prints the error. It didn't. On Humble ros2 param get, and on Jazzy both list and get, exited with code 2 and printed nothing. So in these versions the None message doesn't come from pressing Ctrl+C. It comes from Humble's own one-second wait.

Why the message says None

The source of each version explains it. In Humble (ros2param 0.18.20), verb/list.py sends a request to every node, then calls rclpy.spin_until_future_complete(node, future, timeout_sec=1.0) for each one. If the future isn't done after that second, future.result() is None, and the code prints 'Exception while calling service of node ' ... {e} with e = future.exception(). There was no exception, so you see None.

Jazzy (ros2param 0.32.13) still has that message in list.py, but it calls spin_until_future_complete with no timeout. A node that never answers keeps the command waiting forever, with no output. Lyrical (ros2param 0.40.9) adds --service-timeout N to list (default 5.0) and to get (default "waits indefinitely"), and the message for a missed reply is now Timed out waiting for list_parameters response from node ... (timeout: 5.0s).

The first wait is separate. get on all three versions, and list on Jazzy and Lyrical, first wait up to 5 s for the parameter services to appear (wait_for_service(timeout_sec=5.0) in Humble, wait_for_services(timeout_sec=5.0) in Jazzy and Lyrical). When the services don't exist, you get Wait for service timed out at about 6 s instead. Humble's list skips that wait, which is why it printed nothing for a node without parameter services. So the text tells you which half failed:

  • Wait for service timed out: the services aren't there. The node turned them off, died, or is on a different discovery path.
  • Exception while calling service ...: None, Timed out waiting for list_parameters response, or a silent hang: the services are there, but no reply came back.

The node never spins

This is the pattern behind the teleop_twist_keyboard question, where the node runs its own key-reading loop. I didn't install teleop_twist_keyboard. My nospin.py copies the pattern: a publisher and a while True: time.sleep(0.1) loop that never spins. The node showed up in ros2 node list in 0.31 s on Humble, and its services were all listed, but neither list nor get ever got a reply.

ros2 param get is worse than list here. It doesn't time out on any of the three distros by default, so it just sits there. When timeout stopped it with SIGTERM after 30 s, Lyrical printed !rclpy.ok(). Humble and Jazzy printed nothing.

The fix is to spin the node somewhere. The thread in the short answer worked on all three distros. If you control the loop, you can also call rclpy.spin_once(node, timeout_sec=0) in it, or move the loop body into a timer and call rclpy.spin(node). I measured only the thread version. Rate-based loops have a related trap: rate.sleep() in rclpy needs a spinning executor too, which I covered in rclpy rate.sleep() blocks forever.

A callback blocks the executor

blocked.py spins normally, but its 0.5 s timer callback sleeps for 8 s. With the default single-threaded executor, parameter requests have to wait until that callback returns. Each distro handled the wait differently:

HumbleJazzyLyrical
ros2 param list /blockedException ... None at 3.99 slisted at 12.53 sTimed out ... at 6.07 s
ros2 param get /blocked speed0.5 at 16.68 s0.5 at 16.00 s0.5 at 14.54 s
Node logRuntimeWarning: failed to send response (timeout): client will not receive responsenothingsame warning as Humble

The warning in the node's own output is a useful clue. On Humble and Lyrical the node did answer, but after the CLI had given up, and the reply had nowhere to go. If your node log shows failed to send response (timeout) next to this error, look for a slow callback.

The fix is to give the slow work its own callback group and use a multi-threaded executor, so the parameter services, which stay in the node's default group, have a free thread:

from rclpy.executors import MultiThreadedExecutor
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup

node.create_timer(0.5, slow_callback, callback_group=MutuallyExclusiveCallbackGroup())
ex = MultiThreadedExecutor()
ex.add_node(node)
ex.spin()

With the same 8 s callback, list answered in 0.98 s on Humble, 2.81 s on Jazzy and 2.82 s on Lyrical, and get in 0.98 s, 3.06 s and 1.07 s. Moving the work out of the callback also fixes it, but I didn't measure that.

A second node nobody spins

This is the shape of an older question about a node created inside another node. subnode.py creates outer and inner, declares the parameter on inner, and calls rclpy.spin(outer). Both names showed up in ros2 node list. ros2 param list /outer worked on all three distros. /inner failed the same way as the node that never spins: None on Humble at 1.99 s, a hang on Jazzy, Timed out on Lyrical at 6.08 s, and get hung everywhere.

rclpy.spin(node) spins one node. To serve both, add both to one executor:

ex = SingleThreadedExecutor()
ex.add_node(outer)
ex.add_node(inner)
ex.spin()

Then list /inner_f answered in 1.32 s, 3.06 s and 1.10 s, and get in 1.73 s, 1.07 s and 2.25 s (Humble, Jazzy, Lyrical).

The CLI and the node use different RMWs

The ros2cli issue on multiple RMW implementations reports this error with a Cyclone DDS talker and a Fast DDS ros2 param list. All three images default to rmw_fastrtps_cpp. I started the node with RMW_IMPLEMENTATION=rmw_cyclonedds_cpp and ran the CLI without it. Discovery works across the two, so ros2 node list showed /healthy on every distro. The service calls didn't work:

  • Humble: list printed Exception while calling service of node '/healthy': None after 4.98 s (9.98 s on a second try). get printed Wait for service timed out after 5.98 s.
  • Jazzy: list and get both hung.
  • Lyrical: list printed Timed out ... after 6.13 s, and get hung.

Setting the same RMW on the CLI side, and restarting the daemon with it, fixed it on Humble (1.07 s) and Jazzy (1.16 s). On Lyrical, the first attempt with both sides on Cyclone still timed out, and get hung. I reran it in a fresh shell, with no Fast DDS process in the container at all. Then list answered in 1.15 s, get in 1.17 s, and a direct ros2 service call /healthy/list_parameters returned the names in 0.65 s. I don't know why the first Lyrical attempt failed, so take that row as "worked after a clean restart". In practice: export one RMW_IMPLEMENTATION in every shell, run ros2 daemon stop, and try again.

Parameter services turned off, or a dead node

These two cases end in Wait for service timed out instead, because the services aren't there to call. A node created with start_parameter_services=False had only /noservices/get_type_description left on Jazzy and Lyrical. On Humble, ros2 param list /noservices printed nothing at all and exited with 0, which is easy to read as "no parameters". ros2 param get reported Wait for service timed out on all three.

When I killed a node with kill -9, the daemon kept listing it one second later. ros2 param list /healthy then hung on Humble and gave Wait for service timed out on Jazzy and Lyrical. With --no-daemon, all three said Node not found in about 1 s. If a node appears in the list but every call to it fails, check that it's still running.

One bad node and plain ros2 param list

Without a node name, ros2 param list asks every node. With a healthy node and a non-spinning node both running, Humble printed the healthy node's parameters and then the None line for /nospin (4.98 s). Lyrical did the same with its Timed out line (6.11 s). Jazzy printed the healthy node's parameters and then hung on the other one. On Jazzy, query nodes one at a time to find the one that isn't answering.

Version notes

  • Humble, ros2cli/ros2param 0.18.20: list waits 1 s per node, then prints Exception while calling service of node '...': None. get has no timeout option and waits without a limit for the reply. ros2 param get --help showed no timeout flag.
  • Jazzy, 0.32.13: list waits for the reply without a limit, so an unanswered node hangs it silently. get has --timeout N, but that is "Wait for N seconds until node becomes available (default 1 sec)", not a reply timeout.
  • Lyrical, 0.40.9: list has --service-timeout N (default 5.0) and prints Timed out waiting for list_parameters response from node NodeName(...) (timeout: 5.0s). get has both --timeout and --service-timeout, and the second one defaults to waiting indefinitely.

Not tested

C++ (rclcpp) nodes, lifecycle nodes, Nav2 and rqt (the setups in several of the linked questions), rmw_zenoh_cpp, nodes on another machine, --service-timeout values other than the default, ros2 param set, dump and describe, get on a dead node, and Foxy, Iron, Kilted and Rolling.

FAQ

What does "Exception while calling service of node ... : None" mean?

On Humble, ros2 param list sent a list_parameters request and got no reply within about one second. None means no exception was set. The node exists, but nothing in it processed the request. Usually it isn't spinning, or a callback is blocking its only executor thread.

Why does ros2 param list hang on Jazzy instead of printing the error?

Jazzy's ros2 param list waits for the reply without a time limit. The same non-spinning node that gives the None message on Humble in 2 s left Jazzy printing nothing for 30 s. Lyrical added --service-timeout, with a 5 s default for list.

Why can I see the node in ros2 node list but not its parameters?

Node discovery and service replies are separate. ros2 node list showed every failing node, and ros2 service list showed the services of the non-spinning and blocked ones. Only a spinning executor sends the reply. A different RMW on the CLI side caused the same symptom.

How do I list the parameters of teleop_twist_keyboard?

If the version you run reads keys in a loop that never spins, it can't answer parameter requests. I didn't test teleop_twist_keyboard itself, but my test node built that way never answered on any distro. The fix is in the node's code: spin it in a background thread.

Does pressing Ctrl+C cause the None message?

Not in my runs. Ctrl+C on a waiting ros2 param get (Humble) or ros2 param list (Jazzy) exited with code 2 and printed nothing. The message came from Humble's one-second wait.
