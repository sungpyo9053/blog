tf2.ConnectivityException: Could not find a connection between 'map' and 'laser' because they are not part of the same tree.Tf has two or more unconnected trees.

From C++ the text is the same. tf2_echo printed it as [tf2_echo]: Waiting for transform map -> laser: Could not find a connection between 'map' and 'laser' because they are not part of the same tree.Tf has two or more unconnected trees. Nav2 and other tools add their own prefix, such as Timed out waiting for transform from base_link to map to become available, tf error:, but the part after it is the same.

Short answer: both frames exist in your tf buffer, but no chain of parent and child links joins them. At least one link between them never reached this buffer. Find the missing link and publish it. In my runs the fix was always one of three things: start the node that publishes the missing link (usually odom to base_link), add a static transform that joins two names for the same body (base_footprint to base_link), or make the publishers and the listener use the same /tf and /tf_static topics. For the name mismatch, this one command fixed it on Humble, Jazzy and Lyrical:

ros2 run tf2_ros static_transform_publisher --x 0 --frame-id base_footprint --child-frame-id base_link

This is a different error from "odom" passed to lookupTransform argument target_frame does not exist. That one means a frame name is not in the buffer at all. "Not part of the same tree" means both names are there, in two separate trees.

What I ran

On 2026-11-22 I ran one script, repro.sh, in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro after the other, with no network and the default RMW (Fast DDS). It has two parts.

Part 1 fills a tf2_ros.Buffer by hand with set_transform and set_transform_static, then calls lookup_transform. No DDS is involved, so the results don't depend on timing. Part 2 uses real traffic. static_transform_publisher publishes the fixed links, and a small rclpy node with a TransformBroadcaster publishes the moving link at 20 Hz. A listener node with a TransformListener waits 1 second, then calls lookup_transform(target, source, Time()) every 0.1 s for 3 or 4 seconds and counts each result. For C++ I ran tf2_echo and tf2_monitor from tf2_ros. The frame names follow a mobile robot: map, odom, base_footprint, base_link and laser.

What "two or more unconnected trees" means

tf2 stores, for each frame, which frame is its parent. A lookup walks up from both frames until the two paths meet. If they reach two different roots, there is no answer, and tf2 raises this error. In Part 1, with only map to odom and base_link to laser in the buffer, all_frames_as_yaml() listed two entries:

odom: parent: 'map' ...
laser: parent: 'base_link' ...

map and base_link appear only as parents, never as entries of their own. Each one is a root, so this buffer holds two trees. Every lookup that crossed between them failed: map to laser, laser to map, and also odom to base_link. Lookups inside one tree worked (map to odom, base_link to laser). So when you read the YAML from all_frames_as_yaml(), look for names that appear as a parent but never have an entry. More than one of those means more than one tree.

The exception class matters if you catch it. In rclpy it was tf2.ConnectivityException. Its class chain was ConnectivityException, TransformException, Exception. isinstance(e, tf2_ros.LookupException) was False. Code that catches only LookupException doesn't catch this error, and the exception ends the callback. Catch tf2_ros.TransformException, the base class in that chain, instead.

Cause 1: the link is never published

Something should publish odom to base_link: wheel odometry, a simulator plugin, robot_localization. It isn't running, it crashed, or it is publishing somewhere else. The fixed parts of the tree are there, so both frames exist, and the lookup gives the connectivity error instead of "does not exist". With only the two static transforms, the listener got the error in 30 of 30 polls on all three distros. When I started the 20 Hz odom to base_link publisher, the same lookup worked 30 of 30 times with x=1.30, the sum of the 1.0 m odometry offset and the 0.3 m laser offset.

A link that stops is different from a link that never came. In Part 1 I kept map to odom updating up to stamp 140 and stopped odom to base_link at stamp 110. The lookup failed with Lookup would require extrapolation into the past. Requested time 110.000000 but the earliest data is at time 129.000000. tf2 still knew the parent of base_link, so the trees were still joined. A stopped publisher gave extrapolation errors in my run, not this one. Timing errors like that are measured in the extrapolation post, which measured why get_clock().now() fails at every publish rate and what a lookup timeout costs.

Cause 2: two names for the same body

Odometry often publishes odom to base_footprint, while the URDF and robot_state_publisher start at base_link. Both names exist, nothing joins them, and you have two trees. In Part 1 odom to laser and odom to base_link both failed with the connectivity error, while odom to base_footprint worked. With real traffic the result was 30 of 30 failures. After I added the static base_footprint to base_link transform from the top of this article, the lookup worked 30 of 30 times on every distro.

Cause 3: the robot's /tf is on another topic

Multi-robot setups and some robot bringups publish tf under a namespace. A TransformListener subscribes to /tf and /tf_static by default. I started the odometry node with -r __ns:=/robot1 -r /tf:=tf -r /tf_static:=tf_static, so its odom to base_link went to /robot1/tf. The static transforms stayed on the global /tf_static. ros2 topic list showed exactly that: /robot1/tf and /tf_static, with no /tf.

The listener has to subscribe to the same pair of topics the publishers use, and the pair can be split. The static parts came through and the moving link did not. That is why the error said "not part of the same tree" and not "does not exist". Static transforms on a separate topic have their own timing trap: the /tf_static bag play post measured how /tf_static goes missing after ros2 bag play and the QoS override that restores it.

Cause 4: parent and child swapped in a static transform

If you swap the parent and child in a static transform, the child of that transform gets a second parent. I published laser to base_link (swapped) as a static transform while odom to base_link came from odometry at 20 Hz. Every odom to laser lookup failed, 30 of 30, and odom to base_link worked. The frame list on the listener had one entry, base_link: parent: 'odom'. laser was gone from the frame list entirely. The odometry updates had replaced the static parent.

Part 1 showed that the most recent call decides which parent wins. Static first and odometry after gave the same result as the real traffic. Odometry first and the swapped static after made base_link a child of laser. After that, odom to base_link failed too, and only laser to base_link worked (x=0.3). The static_transform_publisher post measured the other effect of a swapped transform: with no rotation, the child lands at twice the offset when the frame has no other parent. If you see this error right after adding a sensor, check the order of --frame-id (parent) and --child-frame-id (child).

Two parents don't give this error, they give wrong numbers

When two dynamic sources both publish a parent for base_link, tf2 doesn't complain. I ran odometry (odom to base_link, x=1.0) and a second node (map to base_link, x=5.0), both at 20 Hz, with a static identity map to odom. Every lookup returned a transform. There was no exception and no warning, and the values were inconsistent:

With an identity map to odom, both lookups should give the same number. They didn't. The split changed from run to run and is not a difference between distros. Jazzy simply had no wrong polls this time. In Part 1, with the second source written last at every stamp, odom to base_link came back as x=4.0, a value neither node published. The usual cause is two localization nodes, or an EKF and a simulator plugin, both publishing the same link. Each frame should have exactly one publisher for its parent link.

How to see which link is missing

tf2_echo shows the error as it changes. With the two static transforms running, it first printed Invalid frame ID "map" passed to canTransform argument target_frame - frame does not exist. About 2 seconds later (1.97 s on Humble, 1.96 s on Jazzy, 1.98 s on Lyrical, from the log timestamps), once data had arrived, it switched to the connectivity error. Don't give up on the first line it prints.

tf2_monitor was less helpful here. After 10 seconds it listed Frame: laser and Frame: odom with their delays, and said nothing about two trees or about base_link having no parent. It listed only the two frames that had a parent entry, so the missing link didn't show up at all. In Python, buffer.all_frames_as_yaml() gives the same list with each parent named, and that's enough to find the roots by eye. tf2_tools (for view_frames) is installed in all three ros-base images, but I didn't run it.

A timeout doesn't help

A lookup with a timeout waits the full time before it raises this error. With the two-tree setup and a listener spinning in its own thread, lookup_transform('map', 'laser', Time(), timeout=Duration(seconds=2.0)) took 2.005 to 2.014 s on every run and distro, then raised ConnectivityException. can_transform with the same timeout returned 0 after 2.005 to 2.006 s. A frame that didn't exist cost the same, 2.004 to 2.006 s. A connected lookup returned in 0.000 s. So a longer timeout only makes a broken tree fail more slowly. Raise the timeout if data is arriving late, not if a link is missing.

FAQ

What does "not part of the same tree. Tf has two or more unconnected trees" mean?

Both frames are in the tf buffer, but no chain of parent and child links connects them, so tf2 can't compute the transform. At least one link between them never arrived. In my runs that was a missing odometry link, a base_footprint and base_link name mismatch, tf published on a namespaced topic, or a static transform with parent and child swapped.

How is it different from "frame does not exist"?

"Does not exist" means one of the names isn't in the buffer at all. It was a LookupException in rclpy. "Not part of the same tree" means both names are there, in separate trees, and it was a ConnectivityException. tf2_echo printed "does not exist" first and switched to the connectivity error about 2 seconds later, once data arrived.

How do I fix "Could not find a connection between odom and base_link"?

Check that the node that publishes odom to base_link is running, and that it uses the same frame names as your URDF. If it publishes base_footprint, add a static base_footprint to base_link transform. Both fixes changed 30 of 30 failed lookups into 30 of 30 successful ones on Humble, Jazzy and Lyrical.

Will a longer lookup timeout fix it?

No. With a 2.0 s timeout the lookup waited 2.005 to 2.014 s and then raised the same error on every distro. A timeout only helps when the missing link is about to arrive.

Why doesn't except LookupException catch it in rclpy?

The error is raised as tf2.ConnectivityException, whose parent class is TransformException, not LookupException. Catch tf2_ros.TransformException, the base class, instead.
