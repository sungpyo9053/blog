[FATAL] [spawner_joint_state_broadcaster]: Failed loading controller joint_state_broadcaster
[ros2run]: Process exited with failure 1

From ros2 control load_controller the same failure reads Error loading controller, check controller_manager logs on Humble and Failed loading controller ddc check controller_manager logs on Jazzy and Lyrical. Both exit with code 1.

Short answer: the spawner never says why. It asked the controller manager to load the controller, got "no" back, and printed that one line. The reason is in the controller manager's output, usually one line above or below the spawner's. In my runs it was almost always one of these two:

[controller_manager]: The 'type' param was not defined for 'joint_state_broadcaster'.
[controller_manager]: Loader for controller 'ddc' (type 'diff_drive_controller/DiffDriveController') not found.

The first means the manager has no type for that controller name. Put the controller under the manager's node name, next to update_rate, and pass that file to ros2_control_node:

controller_manager:            # the manager's node name; /controller_manager also works
  ros__parameters:
    update_rate: 50
    joint_state_broadcaster:     # must match the name you give the spawner
      type: joint_state_broadcaster/JointStateBroadcaster
    fwd:
      type: forward_command_controller/ForwardCommandController

fwd:                           # the controller's own parameters
  ros__parameters:
    joints: [j1]
    interface_name: position
ros2 run controller_manager ros2_control_node --ros-args --params-file ctl.yaml
ros2 run controller_manager spawner fwd --param-file ctl.yaml

The second means the type string is misspelled or the package that provides it isn't installed. The manager prints the list of types it can load right after the error, so compare against that list. Passing the same file to the spawner with --param-file worked on all three distros, and on Lyrical it's required. Lyrical didn't hand the manager's file to the controllers, so fwd failed to load there without it.

What I ran

On 2026-11-15 I ran one script in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one distro at a time. In each container I installed controller_manager, ros2controlcli, joint_state_broadcaster, forward_command_controller and robot_state_publisher from apt. I did not install diff_drive_controller, so I could test a type whose package is missing. There was no Gazebo. The robot is a one-joint URDF whose <ros2_control> tag uses mock_components/GenericSystem.

For each group of cases I started robot_state_publisher and ros2_control_node with a params file, waited 5 seconds, then ran the spawner. I timed each spawner run and saved the lines the manager printed during it. The manager file declared six controllers: two good ones, one with a misspelled type, one diff_drive_controller, one with no joints, and one with a joint that isn't in the URDF. A second pass checked whether giving the same file to the spawner with --param-file fixes things.

Every failed load ended quickly. With the manager running, the spawner gave up after 0.58 to 2.82 s on Humble, 0.99 to 2.99 s on Jazzy and 1.14 to 3.65 s on Lyrical. The one exception is the Humble crash in the params_file case, below.

"The 'type' param was not defined": the manager can't find the type

The controller manager reads the controller's type from its own parameter <controller_name>.type. If that parameter doesn't exist, it logs this line and refuses the load. Five different mistakes led to it, on all three distros:

  • Name mismatch. The spawner asked for joint_state_broadcastr, and the YAML said joint_state_broadcaster. The name you pass to the spawner has to match the key under controller_manager: ros__parameters:. The match is exact.
  • Type in the wrong section. I put type under jsb_owntype: ros__parameters:, the controller's own section. The manager doesn't read that section. The type belongs under the manager.
  • Wrong top-level key. With /controller_manger: as the top key, the manager started normally and printed no warning. It just had no controllers. If you rename the manager with -r __node:= or put it in a namespace, the top key has to follow. A key without the leading slash (controller_manager:) worked on all three.
  • No params file at all. A manager started without --params-file runs fine and loads nothing.
  • Manager file given only to the spawner. With the manager started bare, spawner joint_state_broadcaster --param-file ctl.yaml still failed. The spawner looks for the type under the controller's name in that file, not under controller_manager.

"Loader for controller ... not found": the plugin isn't there

Here the manager has a type, but pluginlib can't find a plugin with that exact name. A misspelled type and an uninstalled package gave the same line. Right after it the manager prints Available classes: and the full list:

[controller_manager]: Loader for controller 'typo_ctrl' (type 'joint_state_broadcaster/JointStateBroadcast') not found.
[controller_manager]: Available classes:
[controller_manager]:   forward_command_controller/ForwardCommandController
[controller_manager]:   forward_command_controller/MultiInterfaceForwardCommandController
[controller_manager]:   joint_state_broadcaster/JointStateBroadcaster

That's the Jazzy and Lyrical list. On Humble the list had 8 entries, because controller_manager 2.54.3 also registers four controller_manager/test_controller... classes. ros2 control list_controller_types printed the same list (8 types on Humble, 3 on Jazzy and Lyrical). If your type isn't in it, either fix the spelling or install the package, for example sudo apt install ros-$ROS_DISTRO-diff-drive-controller. Then restart the controller manager. I did not test whether a running manager picks up a package installed after it started.

The manager names a type as package/ClassName. Copy it from the list rather than typing it.

params_file empty or wrong: the "--params-file --param" error

On Jazzy and Lyrical the manager starts each controller node with the arguments in the controller's params_file parameter, and logs them. The spawner's --param-file sets that parameter. In the linked issues, the Gazebo plugin set it too. If the value is an empty string, the argument list ends in a bare --params-file:

[controller_manager]: Controller 'jsb_emptypf' node arguments: --ros-args --params-file /t/ctl_emptypf.yaml --params-file
[controller_manager]: Caught exception of type : N6rclcpp10exceptions22RCLInvalidROSArgsErrorE while initializing controller 'jsb_emptypf': failed to parse arguments: Couldn't parse params file: '--params-file '. Error: Error opening YAML file, at ./src/parser.c:271, at ./src/rcl/arguments.c:415

That's Jazzy. Lyrical printed the same exception with the arguments in quotes. A path to a file that doesn't exist gave the same error with the path in place of the empty string. In both cases the manager stayed up and the spawner failed in 0.99 to 2.81 s.

Humble behaved differently. The same YAML crashed the whole controller manager with terminate called after throwing an instance of 'rclcpp::exceptions::RCLInvalidROSArgsError' and a stack trace. The spawner never got an answer. It printed Failed getting a result from calling /controller_manager/load_controller in 10.0. (Attempt 1 of 3.) three times and ended with RuntimeError: Could not successfully call service /controller_manager/load_controller after 3 attempts. after 30.59 s (30.67 s for the missing-file case). So on Humble this cause doesn't show up as "Failed loading controller" at all.

The fix is to find what sets the empty path. In the gz_ros2_control issue linked below, users traced it to the <parameters> tag of the Gazebo plugin in the URDF, where the path came out empty. Their log shows --params-file --param use_sim_time:=true. Look at the node arguments: line and check that every --params-file is followed by a real file. The text after Error: comes from the same rcl params parser that ros2 run uses, so the messages in this guide to ROS 2 params YAML errors apply here too.

Lyrical: the manager's file doesn't reach the controller

This one surprised me. On Jazzy, the manager added its own params file to each controller's arguments: node arguments: --ros-args --params-file /t/ctl.yaml. On Humble, controller nodes picked up the manager's --params-file without it showing in the log. Either way, the fwd: ros__parameters: joints: [j1] section reached the controller and spawner fwd worked.

On Lyrical (controller_manager 6.10.1) the manager passed nothing. The same spawner fwd failed:

[controller_manager]: Loading controller 'fwd'
Exception thrown during init stage with message: parameter 'joints' is not initialized
[fwd]: Calling shutdown transition of controller node 'fwd' due to init failure.
[controller_manager]: Could not initialize the controller named 'fwd'
[FATAL] [spawner_fwd]: Failed loading controller fwd

joint_state_broadcaster still loaded on Lyrical, because it has no required parameters. That makes the cause easy to miss. The broadcaster works, and the first controller that needs joints fails.

Adding --param-file ctl.yaml to the spawner fixed it on Lyrical. The log showed node arguments: '--ros-args --params-file /t/ctl.yaml', then Configured and activated fwd. The same flag also worked on Humble and Jazzy. On Jazzy the file then appeared twice in the arguments, which did no harm. If you write launch files for more than one distro, pass the file to every spawner.

Loaded, then failed to configure or activate

These print a different message, but people often search for them under "failed loading".

Missing required parameter. forward_command_controller needs joints. On Humble and Jazzy the load worked. Configure failed with 'joints' parameter was empty in the manager log and Failed to configure controller from the spawner, and the controller stayed listed as unconfigured. On Lyrical the check happens at init, so it's a load failure with parameter 'joints' is not initialized, even with --param-file. On Lyrical the controller then didn't appear in ros2 control list_controllers at all.

Joint not in the URDF. With joints: [j9] the controller loaded and configured. Activation failed with Failed to activate controller : fwd_badjoint, and the controller stayed inactive. Jazzy and Lyrical named the problem directly: the command interface 'j9/position' is not available. Humble printed a Not acceptable command interfaces combination block with j9/position under Not existing:. The fix is in the URDF's <ros2_control> tag or in the joint names, not in the spawner.

Spawning the same controller twice. A second spawner joint_state_broadcaster printed Controller already loaded, skipping load_controller and then failed with exit code 1. Humble and Jazzy tried to configure an active controller. Lyrical tried to activate it and logged Aborting, no controller is switched! (::STRICT switch). The first copy kept running in every case. If a launch file restarts only part of the system, this is what you see.

Version notes

  • Humble (controller_manager 2.54.3): controllers got the manager's params file without it being logged. An empty or missing params_file crashed the manager, and the spawner timed out after about 30 s with a RuntimeError. The spawner has -t. The available-classes list includes four test controllers.
  • Jazzy (4.48.1): the manager logs Loading controller : 'x' of type 'y' and a node arguments: line, and adds its own params file to them. A bad params_file is caught and logged, and the manager stays up. No -t.
  • Lyrical (6.10.1): the manager doesn't pass its own file to controllers. Use --param-file. Required-parameter errors happen at init, so they show up as "Failed loading controller", and the controller isn't listed afterwards. The spawner gains --reconfigure and has no -n.

FAQ

What does "Failed loading controller" mean in ros2_control?

The controller manager refused the spawner's load request. The spawner doesn't say why. Look at the controller manager's log. In my runs it said either The 'type' param was not defined or Loader for controller ... not found.

How do I fix "The 'type' param was not defined"?

Add <name>: type: package/ClassName under controller_manager: ros__parameters:, with the same name you give the spawner. Pass that file to ros2_control_node. A misspelled name, a misspelled top key, a type in the controller's own section, or a missing params file all gave this error.

Why does it say "Loader for controller not found" when the package is installed?

The type string has to match a registered class exactly. A typo gave the same error as a missing package. Copy the type from ros2 control list_controller_types.

joint_state_broadcaster loads on Lyrical, but my other controllers fail. Why?

On Lyrical the controller manager didn't pass its own params file to controllers, so joints and other parameters never arrived. Add --param-file with your controllers YAML to each spawner. That worked on Humble, Jazzy and Lyrical.

What causes "Couldn't parse params file: '--params-file '"?

The controller's params_file was empty, so the manager passed --params-file with no path. On Jazzy and Lyrical this showed up as "Failed loading controller". On Humble it crashed the controller manager, and the spawner timed out after about 30 seconds.
