Your package defines a custom message, a C++ node includes it, and colcon build stops on that line. The header path changes with your package and message name, but the text is the same on Humble, Jazzy and Lyrical.

Short answer: two causes produced this error in my test. First, the include used the message's CamelCase name. Leg.msg generates leg.hpp, and IMUData.msg generates imu_data.hpp. Second, the node was in the same package as the message and was never linked to the generated code. For the second cause, add these two lines after rosidl_generate_interfaces():

rosidl_generate_interfaces(${PROJECT_NAME} "msg/Leg.msg")

rosidl_get_typesupport_target(cpp_typesupport_target ${PROJECT_NAME} rosidl_typesupport_cpp)
target_link_libraries(node "${cpp_typesupport_target}")

That pair built and ran on Humble, Jazzy and Lyrical. The older rosidl_target_interfaces() still worked on Humble and Jazzy, with a deprecation warning. On Lyrical it failed with Unknown CMake command "rosidl_target_interfaces". Running colcon build a second time didn't fix either cause.

What I ran

On 2026-11-03 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images on a 2 vCPU Linux server, one distro at a time. The script writes one ament_cmake package per case. Each package defines a message with three fields (string name, int16[] id, float32[] pos) and has a C++ node that includes the header, publishes one message and logs RESULT published name=front_left ids=2. Only the CMake line, the include line, the message file name or package.xml changes between cases. I built each package on its own with colcon build --executor sequential --packages-select <pkg> and MAKEFLAGS=-j1. Then I ran every package that built with ros2 run.

The working package (c1_ok) holds five messages: Leg, MotorCmd, IMUData, Pose2D and WheelRPM. It built in 23.6 s on Humble, 27.6 s on Jazzy and 35.3 s on Lyrical, and its node printed the RESULT line on all three. The broken cases failed in 1.5 to 6.2 s. The CMake errors came out at configure time, before anything compiled.

Cause 1: the header name is snake_case

The C++ generator turns the message name into a snake_case file name. These are the headers it wrote into build/c1_ok/rosidl_generator_cpp/c1_ok/msg/, the same on all three distros:

Message fileHeader to include
Leg.msgc1_ok/msg/leg.hpp
MotorCmd.msgc1_ok/msg/motor_cmd.hpp
IMUData.msgc1_ok/msg/imu_data.hpp
Pose2D.msgc1_ok/msg/pose2_d.hpp
WheelRPM.msgc1_ok/msg/wheel_rpm.hpp

A run of capitals stayed together (IMUData became imu_data, WheelRPM became wheel_rpm), and Pose2D got an underscore between the 2 and the D. If you can't guess the name, build the package and list that directory. The C++ type keeps the CamelCase name: you include leg.hpp and write c1_ok::msg::Leg.

The CamelCase include failed on all three distros, with the message linked correctly. This is the cause in the ROS Answers question where messages/msg/AttitudeEstimation.hpp wasn't found. The poster found that "the msg files get renamed when they turn into hpp files" and that the right path was messages/msg/attitude_estimation.hpp.

The message name itself must start with a capital letter. A file called leg.msg stopped the build at configure time with rosidl_adapter.parser.InvalidResourceName: 'leg' is an invalid message on Humble and Jazzy. On Lyrical the build failed at the same rosidl_adapter step, and the source line in the log reads "'{}' is an invalid message name. It should have the pattern '{}'". The question about naming message files shows the full pattern: '^[A-Z][A-Za-z0-9]*$'. Rename the file to Leg.msg and list it that way in rosidl_generate_interfaces().

Cause 2: the node is not linked to the generated code

When the message and the node live in the same package, rosidl_generate_interfaces() creates the code, but your executable knows nothing about it. Without a link, nothing adds the generated include path to the node, and nothing tells CMake to generate the headers before it compiles node.cpp. In my run the compile came first. After the failed build, build/c3_nolink/rosidl_generator_cpp/c3_nolink/msg/leg.hpp didn't exist on any distro.

That also explains why a rebuild didn't help. I ran colcon build on the unlinked package a second time, then deleted its build folder and built it twice more with MAKEFLAGS=-j2. All four builds failed on every distro with the same fatal error, and the header was still missing afterwards.

The fix is to link the node to the C++ type support target of your own package:

find_package(ament_cmake REQUIRED)
find_package(rclcpp REQUIRED)
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/Leg.msg"
)

add_executable(node src/node.cpp)
target_link_libraries(node rclcpp::rclcpp)

rosidl_get_typesupport_target(cpp_typesupport_target ${PROJECT_NAME} rosidl_typesupport_cpp)
target_link_libraries(node "${cpp_typesupport_target}")

install(TARGETS node DESTINATION lib/${PROJECT_NAME})
ament_export_dependencies(rosidl_default_runtime)
ament_package()

And in package.xml:

<buildtool_depend>ament_cmake</buildtool_depend>
<buildtool_depend>rosidl_default_generators</buildtool_depend>
<depend>rclcpp</depend>
<exec_depend>rosidl_default_runtime</exec_depend>
<member_of_group>rosidl_interface_packages</member_of_group>

This is the setup from the official single-package interface tutorial. It built and ran on all three distros. The link gives the node the include path and makes CMake generate the headers first.

Adding the include directory by hand doesn't work

A common attempt is to point the compiler at the generated folder yourself. I added include_directories(${CMAKE_CURRENT_BINARY_DIR}/rosidl_generator_cpp) and no link. The build failed exactly like the unlinked package, on all three distros, including the second build and both -j2 builds. The path was right, but the header still wasn't there when node.cpp compiled. You need the target link, not just the path.

The installed header also sits one folder deeper than you might expect: install/c1_ok/include/c1_ok/c1_ok/msg/leg.hpp, with the package name twice. That was the same on Humble, Jazzy and Lyrical. Your include stays c1_ok/msg/leg.hpp. Linking the target sets the right search path, so don't hard-code this one.

Order matters

rosidl_get_typesupport_target() looks up a target that rosidl_generate_interfaces() creates. Called first, it stopped at configure time on all three distros with c5_order is not a CMake target. Maybe rosidl_generate_interfaces was given a different target name?. Move it below rosidl_generate_interfaces(). The name you pass must also be the one given to rosidl_generate_interfaces(), which is ${PROJECT_NAME} in the usual setup.

ament_target_dependencies on your own package fails

Another attempt is ament_target_dependencies(node ${PROJECT_NAME}). On Humble and Jazzy it failed with ament_target_dependencies() the passed package name 'c8_atd' was not found before. On Lyrical the function itself is gone, and the error was Unknown CMake command "ament_target_dependencies". Your own messages need the type support link above.

Use rosidl_get_typesupport_target() for a single package. It is the only same-package form that built on all three distros, so you don't have to change it when you move to Lyrical. If you are still on rosidl_target_interfaces(), the Humble and Jazzy warning tells you the replacement: Use rosidl_get_typesupport_target() and target_link_libraries() instead of rosidl_target_interfaces().

The separate interface package is what most answers recommend. It also built and ran on all three distros. The consumer needs <depend>leg_interfaces</depend>, find_package(leg_interfaces REQUIRED) and target_link_libraries(node rclcpp::rclcpp ${leg_interfaces_TARGETS}). With this setup the same header error comes from a missing target_link_libraries entry, and Lyrical changes how you write that line. My ament_target_dependencies on Lyrical post covers it. The split pays off when other packages, or Python nodes in other packages, need the same messages.

Version notes

  • rosidl_target_interfaces: deprecated on Humble and Jazzy, removed on Lyrical. On Jazzy the warning adds i.e: and an example after the text.
  • find_package(rosidl_default_generators): on Humble, a package without it still built and ran. On Jazzy and Lyrical it failed with Unknown CMake command "rosidl_generate_interfaces". Code that skips this line may work on Humble and break when you move to Jazzy, so keep it.
  • ament_target_dependencies: removed on Lyrical, as above.
  • CMake on Lyrical: Lyrical ships CMake 4.2.3. Every configure step with cmake_minimum_required(VERSION 3.8) printed Compatibility with CMake < 3.10 will be removed from a future version of CMake. It's only a warning and didn't stop any build, but it shows up next to the real error in the log. Humble had CMake 3.22.1 and Jazzy 3.28.3, and neither printed it.
  • Header names and install path: identical on all three.
  • Python: from c1_ok.msg import Leg, IMUData worked on all three. Python uses the CamelCase class name and doesn't need any CMake link, which is why some people find the message works from Python but not from C++.

FAQ

Why does my custom message header say No such file or directory in ROS 2?

In my test there were two causes. The include used CamelCase (Leg.hpp) instead of the generated snake_case name (leg.hpp). Or the node was in the same package as the message and wasn't linked with rosidl_get_typesupport_target() and target_link_libraries().

What is the header name for a message like IMUData.msg?

The generator wrote imu_data.hpp. MotorCmd became motor_cmd.hpp, Pose2D became pose2_d.hpp and WheelRPM became wheel_rpm.hpp. The C++ type keeps the original name, for example my_pkg::msg::IMUData.

Does rosidl_target_interfaces still work?

On Humble and Jazzy it built and ran, with a deprecation warning. On Lyrical it failed with Unknown CMake command "rosidl_target_interfaces". Use rosidl_get_typesupport_target() and target_link_libraries(), which worked on all three.

Will running colcon build again fix it?

Not in my test. The unlinked package failed on the second build, and twice more from a clean build folder with -j2, on all three distros. The generated header never appeared, because the compile failed before generation started.

What does "Packages installing interfaces must include member_of_group" mean?

Your package.xml is missing <member_of_group>rosidl_interface_packages</member_of_group>. Every package that calls rosidl_generate_interfaces() needs it. Without it, configure failed on Humble, Jazzy and Lyrical.
