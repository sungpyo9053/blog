rclpy._rclpy_pybind11.InvalidHandle: cannot use Destroyable because destruction was requested

The last frames before that line tell you which object it was. These are the three chains I logged (innermost frame first):

_take_subscription: with sub.handle: <- handler: arg = take_from_wait_list(entity)        (Humble, subscription)
add_to_wait_set: with self.__event: <- _wait_for_ready_callbacks: waitable.add_to_wait_set(wait_set)   (Jazzy, Lyrical, subscription)
send_response: with self.handle: <- _execute_service: srv.send_response(response, header)   (Humble, service; Jazzy says _execute)

Short answer: rclpy raises this when code touches an object after destroy_*() was called on it. That covers your own code, like a publish() after destroy_publisher(), and the executor, when it still holds the object in its wait set. The exception comes out of executor.spin(), so the thread that was spinning ends, and with it every callback on that executor. Inside the executor, my runs found two triggers. A service that destroys itself inside its own callback failed 15 out of 15 times. The fix is to let the callback return and destroy the service from a one-shot timer:

def srv_cb(self, req, res):
    # don't call self.destroy_service(self.srv) here; the response hasn't been sent yet
    self.kill_timer = self.create_timer(0.0, self.finish)
    res.success = True
    return res

def finish(self):
    self.destroy_timer(self.kill_timer)
    self.destroy_service(self.srv)

That version answered the call and removed the service in 15 out of 15 runs on Humble, Jazzy and Lyrical. The other trigger is a subscription that one thread creates and destroys while a MultiThreadedExecutor spins in another. On Humble that killed the executor in all 5 runs when each subscription got its own callback group. If you can, use a SingleThreadedExecutor for nodes that create and destroy subscriptions at runtime. It had 0 failures in every subscription, timer and publisher case I ran.

What I ran

I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, with the default RMW (Fast DDS) and one container per distro, run one after another. A small talker.py published std_msgs/String on /chatter from a 2 ms timer for the whole session. race.py took a case name and ran as a fresh process five times per case. Each run counted the cycles it finished. It also recorded whether the executor thread was still alive and, if spin() raised, the exception and its last three frames. In the background-thread cases each cycle was create_subscription, time.sleep(0.02), destroy_subscription. The C++ test did the same with create_subscription and reset() on a shared pointer. The container had 1.5 CPUs and 1200 MB, and the 1-minute load on the host stayed under 2.0 for the whole session.

A service that destroys itself in its callback

This was the only case that failed on the first try every time. The callback calls destroy_service() and returns a response. Then the executor tries to send that response through the service it just lost. The frames show it: send_response: with self.handle: called from _execute_service on Humble and from _execute on Jazzy. Lyrical failed the same way in 5 of 5 runs, but my script didn't capture its frames. The same report is open as ros2/ros2#1351, which was filed on Galactic.

The fix moves the destroy out of the callback. A zero-period timer created inside the callback fires on the next pass of the executor. That's after the response went out, so the destroy is safe there. Each run printed response received=True success=True service destroyed=True server still visible to client=False. So the client got its answer, and one second later it no longer saw the server. The timer has to destroy itself too, or it will fire again on every spin.

Timers and subscriptions didn't have this problem. A timer that destroyed itself in its own callback ran over 200 cycles without an error on all three distros. So did a subscription callback that destroyed its own subscription. Only the service failed, because the executor still has work to do with the service after your callback returns.

Subscriptions destroyed from another thread

This is the pattern from the Robotics Stack Exchange question and from rclpy#1206. One thread spins the executor. Another thread, often a state machine or a test, creates a subscription, waits for a message, and destroys it. The executor may still hold that subscription in its wait set, so when it reaches it, it gets InvalidHandle.

On Humble the callback group decided the outcome. With a new MutuallyExclusiveCallbackGroup for each subscription, as in rclpy#1206, the MultiThreadedExecutor died in 5 of 5 runs. It got through 17, 103, 97, 102 and 106 cycles. Keeping every group object alive in a list didn't help (5/5, after 101 to 106 cycles). Reusing one group created once dropped it to 1/5 (after 49 cycles). With the node's default group it was 0/5 at 200 cycles, and 1/5 at 1000 cycles with a 1 ms gap. So the default group made the error rarer, but it didn't remove it.

Jazzy and Lyrical failed much less often, but they still failed. Jazzy failed once with the default group (after 134 cycles), and Lyrical failed once with a new group per subscription (after 121 cycles). Their frames were different from Humble's. The error came from add_to_wait_set: with self.__event: while the executor was building its wait set, not from taking a message. So the newer executor still has a window where a destroy from another thread can land. It's just smaller.

The SingleThreadedExecutor didn't fail in any background-thread subscription, timer or publisher case on any distro. That was 5 runs of 200 cycles, 5 runs of 1000 cycles with 1 ms gaps, plus timers and publishers, and one extra run of 400 cycles. Publishers never failed at all. The executor doesn't wait on them, so destroying one from another thread doesn't race with spin(). It only hurts if your own code publishes on it afterwards.

destroy_node() while spinning

A node destroyed from the main thread while the executor spun in another thread didn't raise in 30 runs (5 per executor type per distro). The executor thread kept running with nothing left to do. That doesn't make the node usable. Every later call on that node or its publishers raised InvalidHandle right away. If you see the error at shutdown, look for a timer or another thread that publishes after destroy_node(). The order that worked for me at shutdown is in my Ctrl+C and SIGTERM measurements.

The catch-and-continue loop kept the executor alive on all three. On Humble it caught dozens of exceptions per run, so treat it as a crash guard, not a fix. I didn't measure whether a callback was lost each time it caught one.

from rclpy._rclpy_pybind11 import InvalidHandle

while rclpy.ok():
    try:
        executor.spin_once(timeout_sec=0.1)
    except InvalidHandle:
        pass  # an entity was destroyed under the executor; keep spinning

The import path was the same on all three distros. rclpy._rclpy_pybind11.InvalidHandle printed as the class name on Humble, Jazzy and Lyrical.

rclcpp doesn't have this error

In C++ a subscription is a shared_ptr. Calling reset() on it from the main thread while a SingleThreadedExecutor spun in another thread finished 200 cycles in 5 of 5 runs on every distro, and every run exited with code 0. The executor keeps its own reference until it's done with the entity, so there's nothing to race with. That's my reading of why. The counts are what I measured. If you hit this error in a mixed system, it comes from the Python nodes.

Version notes

Humble (rclpy 3.3.22) was much worse than Jazzy (rclpy 7.1.12) and Lyrical (rclpy 10.0.11) in the multi-threaded cases. Four multi-threaded Humble cases failed 5/5. No Jazzy or Lyrical case did, apart from the service. The failing frame changed too. Humble failed while taking a message (_take_subscription), and Jazzy and Lyrical failed while building the wait set (add_to_wait_set, self.__event). The service failure had the same innermost frame on Humble and Jazzy, apart from the caller's name (_execute_service on Humble, _execute on Jazzy). The exception class and message text were identical on all three.

One side observation. In the default-group MultiThreadedExecutor case (200 cycles, no failures on Humble), Humble delivered only 5 to 35 messages per run. Jazzy delivered 126 to 616 and Lyrical 92 to 520. The single-threaded version of the same case delivered 738 to 2036 on all three. I didn't look into why.

FAQ

What does "cannot use Destroyable because destruction was requested" mean?

Something used an rclpy object after destroy_*() was called on it. Either your code did, for example publish() after destroy_publisher() or after destroy_node(), or the executor did because it still had the object in its wait set. The last frames above the message name the object.

Why does my executor stop calling callbacks after this error?

The exception is raised inside spin(), and nothing catches it, so the thread running spin() ends. In my subscription runs that thread was no longer alive at the end of the run. Either fix the destroy, or spin with a spin_once() loop that catches InvalidHandle.

How do I destroy a service from inside its own callback?

Don't do it in the callback itself. Create a zero-period timer in the callback, return the response, and in the timer callback destroy the timer and then the service. This worked in 15 of 15 runs. Destroying the service inside its callback failed in 15 of 15.

Is it safe to destroy a subscription from another thread?

With a SingleThreadedExecutor it never failed in my runs. With a MultiThreadedExecutor it failed on all three distros, most on Humble. There a new callback group per subscription failed 5 of 5 runs. Do the create and destroy in a callback of a single-threaded executor, or keep the subscription.

Does rclcpp have the same problem?

Not in my test. Resetting the subscription pointer from another thread while spinning finished 200 cycles in all 15 runs, with exit code 0 every time.
