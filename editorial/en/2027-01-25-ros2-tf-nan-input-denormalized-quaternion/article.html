Error:   TF_NAN_INPUT: Ignoring transform for child_frame_id "base_link" from authority "direct_test" because of a nan value in the transform (0.000000 0.000000 0.000000) (-nan -nan -nan -nan)
         at line 237 in ./src/buffer_core.cpp
Error:   TF_DENORMALIZED_QUATERNION: Ignoring transform for child_frame_id "base_link" from authority "direct_test" because of an invalid quaternion in the transform (-nan -nan -nan -nan)
         at line 256 in ./src/buffer_core.cpp

That pair came from Humble when a transform had the rotation (0, 0, 0, 0). On Jazzy and Lyrical each line starts with [ERROR] [timestamp] []: instead of Error:, and there is no at line part. The authority is whatever name the receiver records: default_authority for a Python TransformListener, Authority undetectable for tf2_echo, and direct_test above because my test passed that name.

Short answer: tf2 threw the transform away. The node that prints the error is the one receiving /tf (rviz2, tf2_echo, your listener), not the one publishing it. Fix the publisher. Send a real unit quaternion, never all zeros. For "no rotation" that is x=0, y=0, z=0, w=1. If you compute a rotation, check for NaN and normalize it before you publish:

import math

def safe_quat(x, y, z, w):
    n = math.sqrt(x*x + y*y + z*z + w*w)
    if n == 0.0 or math.isnan(n) or math.isinf(n):
        return None          # skip this transform, don't publish it
    return (x / n, y / n, z / n, w / n)

# from a yaw angle in radians, no library needed:
t.transform.rotation.z = math.sin(yaw / 2.0)
t.transform.rotation.w = math.cos(yaw / 2.0)

The guard matters because normalizing a zero quaternion in plain Python raised ZeroDivisionError: float division by zero in my run. One version difference changes which inputs fail. Humble and Jazzy normalized any non-zero quaternion silently and accepted it. Lyrical did not normalize. It rejected any quaternion whose squared length was more than about 0.01 away from 1. A hand-typed 0 0 0.7 0.7 worked on Humble and Jazzy and failed on Lyrical.

What I ran

On 2026-11-16 I ran one script in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one distro after another, with no network. It had three parts.

  • Direct: build a geometry_msgs/TransformStamped, pass it to tf2_ros.Buffer.set_transform(), then call lookup_transform('odom', 'base_link', Time()). This was done for 29 rotations and translations, including a sweep of the squared length.
  • Over DDS: a Python node published 40 messages on /tf at 20 Hz (or 1 on /tf_static), and a Python Buffer plus TransformListener listened for 6 seconds. I counted the error lines on the listener and on the publisher. I repeated some cases with ros2 run tf2_ros tf2_echo odom base_link as the listener.

Zero quaternions: the most common cause

An all-zero quaternion is not a rotation, and both errors in the opening block come from it. On Humble and Jazzy, tf2 normalized the quaternion first. Zero divided by zero is NaN, so the NaN check fired and printed the rotation as -nan, and the quaternion check fired after it. That is why a zero rotation shows up as a "nan value" even though the publisher sent no NaN. Lyrical printed the real values, (0.000000 0.000000 0.000000 0.000000), and only the quaternion line.

Where do zeros come from? In my run, a Python TransformStamped() whose rotation was never set had w=1.0, so the default is safe. Zeros came from code that set all four fields from something that was zero. Two other ways I measured:

  • static_transform_publisher 1 0 0 0 0 0 0 odom base_link. Seven numbers are read as x y z qx qy qz qw, so this is a zero quaternion. On Humble and Jazzy it logged rotation: ('0.000000', '0.000000', '0.000000', '0.000000') and every listener printed both errors once. Six numbers (1 0 0 0 0 0 odom base_link) are read as x y z yaw pitch roll and gave the identity.
  • static_transform_publisher --x 1 --qx 0 --qy 0 --qz 0 --qw 0 .... On all three distros the listener printed the error once (the pair on Humble and Jazzy, one line on Lyrical) and the frame was missing.

The questions linked at the end show two more sources that I did not reproduce: a URDF revolute joint with axis 0 0 0, and a misspelled diff drive parameter (wheel_seperation) that left a divisor at zero.

NaN and inf

A NaN anywhere in the translation or rotation made tf2 drop the transform on every distro. A NaN in the translation produced only TF_NAN_INPUT, with the translation printed as (nan 0.000000 0.000000). Check which group holds the nan: the first three numbers are the translation, the last four are the rotation.

Infinity was treated differently. inf in the translation passed on all three distros and lookup_transform returned it. inf in the rotation was dropped. Don't count on tf2 to catch every bad number. Check with math.isfinite() before you publish.

Unnormalized quaternions: silent on Humble and Jazzy, rejected on Lyrical

On Humble and Jazzy any non-zero quaternion was scaled to unit length and accepted without a message. That hides a real bug. A common mistake is to put the yaw angle into z, as in (0, 0, 1.57, 1). Humble and Jazzy accepted it, and tf2_echo printed:

- Rotation: in Quaternion (xyzw) [0.000, 0.000, 0.843, 0.537]
- Rotation: in RPY (radian) [0.000, -0.000, 2.007]

That is a yaw of 2.007 rad, not 1.57. There was no warning. On Lyrical the same message gave 40 TF_DENORMALIZED_QUATERNION lines in tf2_echo, one per message, and the frame never appeared. If you move to Lyrical and this error starts on a transform that worked before, the publisher was probably always sending an unnormalized quaternion.

Who prints it, how often, and what lookups return

  • The publisher printed nothing. In every DDS case the publishing node's output had zero TF_ lines. You will see the error in rviz2, tf2_echo, Nav2 or your own listener, so start by finding which node publishes the child_frame_id it names.
  • It goes to stderr. With 20 bad messages the listener's stdout had 0 lines and its stderr had 20.
  • There was no rate limit. tf2_echo printed 40 lines for 40 messages on all three distros. A bad /tf_static message printed once.
  • --ros-args --log-level error on the listener did not hide it. It is an ERROR, and 20 of 20 still printed.
  • An earlier good transform survives. I stored a good transform at t=100 and a zero-quaternion one at t=101. lookup_transform(..., Time()) returned the old one (x=1.0 stamp=100), and a lookup at t=101 raised ExtrapolationException: Lookup would require extrapolation at time 101.000000, but only time 100.000000 is in the buffer. When bad messages arrive in a stream, frames freeze or go stale. They don't disappear at once. Timing errors of that kind are covered in the tf2 extrapolation post.
  • tf2_echo with only bad input printed Invalid frame ID "odom" passed to canTransform argument target_frame - frame does not exist every one to two seconds, along with the error lines.

Version notes

  • Humble (tf2 0.25.24) and Jazzy (tf2 0.36.23) normalized non-zero quaternions and printed both errors for a zero quaternion. Lyrical (tf2 0.45.10) stored quaternions as given, rejected |q|²-1 beyond about ±0.01, and printed only TF_DENORMALIZED_QUATERNION for a zero quaternion.
  • Log format: Humble printed Error: TF_... followed by at line 237 in ./src/buffer_core.cpp (NaN check) or at line 256 (quaternion check). Jazzy and Lyrical printed [ERROR] [timestamp] []: TF_... on one line.
  • Humble and Jazzy accepted old-style static_transform_publisher arguments with Old-style arguments are deprecated; see --help for new-style arguments. Lyrical refused them with error parsing command line arguments: Frame id must not be empty and printed the usage, so no transform was sent.
  • Lyrical returned a negated identity (0, 0, 0, -1) unchanged. Humble and Jazzy returned (0, 0, 0, 1). Both are the same rotation.
  • Jazzy anomaly: the Python listener printed 28 error pairs for 40 zero-quaternion messages, and 15 for 100. Humble and Lyrical printed 40 for 40, and tf2_echo printed 40 for 40 on Jazzy. I didn't find the reason. The lookup failed in every case.

FAQ

What does TF_DENORMALIZED_QUATERNION mean?

The receiving node got a transform whose rotation is not a usable unit quaternion and dropped it. On Humble and Jazzy that meant zero, NaN or infinite values. On Lyrical it also meant any quaternion whose squared length was more than about 0.01 away from 1.

Why does a zero quaternion also print TF_NAN_INPUT?

On Humble and Jazzy, tf2 normalized the rotation before checking it. Zero divided by zero is NaN, so the NaN check fired first and printed -nan values, and the quaternion check followed. On Lyrical a zero quaternion printed only TF_DENORMALIZED_QUATERNION.

Which node is publishing the bad transform?

Not the one printing the error. The publisher printed nothing in every case. Look for the node that publishes the child_frame_id named in the message, and check every place it sets transform.rotation.

My transform worked on Humble but fails on Lyrical. Why?

Humble normalized unnormalized quaternions silently, and Lyrical didn't. 0 0 0.7 0.7 and static_transform_publisher --qz 1 --qw 1 passed on Humble and Jazzy and were dropped on Lyrical. Normalize before publishing, or use --yaw.

Can I turn this error off?

--log-level error did not hide it, and the transform was dropped either way. Fix the data. Send w=1 for no rotation, build rotations with sin/cos or normalize them, and skip messages that contain NaN.
