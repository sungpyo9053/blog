$ python3 rm_node.py --ros-args -r __ns:=/robot1 -r /scan:=/scan_front
# no error, no warning, and the node still publishes /robot1/scan

$ python3 rm_node.py --ros-args -r '**/scan:=scan_front'
rclpy._rclpy_pybind11.RCLError: failed to initialize rcl: Couldn't parse remap rule: '-r **/scan:=scan_front'. Error: Wildcard '**' is not implemented, at ./src/rcl/arguments.c:1167, at ./src/rcl/arguments.c:371

Both are from my Humble run. The second one, Couldn't parse remap rule, is the only kind of remap error you will see. The first case is the usual one: no error at all, and the old name stays.

Short answer: a remap rule only applies when its left side matches the node's name after expansion. Relative names expand with the node's namespace before the match, so scan:=scan_front follows the node into any namespace. An absolute rule like /scan:=/scan_front matches only a node in the root namespace. If you push the node into /robot1, the topic becomes /robot1/scan and the rule is skipped without a word. Use a relative rule, or write the full expanded name:

ros2 run my_pkg my_node --ros-args -r __ns:=/robot1 -r scan:=scan_front
# or
ros2 run my_pkg my_node --ros-args -r __ns:=/robot1 -r /robot1/scan:=/robot1/scan_front

Both gave /robot1/scan_front on Humble, Jazzy and Lyrical. In a launch file, the same applies to remappings=[('scan', 'scan_front')]. A pair with leading slashes did nothing once the node had a namespace.

What I ran

On 2026-11-07 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one after another on a 2 vCPU Linux host. Each container ran with --network none and ROS_DOMAIN_ID=77, so no outside traffic could reach the graph. The test node is one rclpy script, rm_node. It creates publishers on scan, /abs_scan, ~/priv and /tf, a subscription on cmd_vel, a service reset and an action server fib (type tf2_msgs/action/LookupTransform). Then it asks the graph which names belong to it, with get_publisher_names_and_types_by_node() and the matching subscriber and service calls, prints them and exits. So the results show what other nodes would see, not what the code asked for.

The script ran the node 35 times with different -r rules. It then started five nodes from one launch file with remappings, PushRosNamespace and SetRemap. It recorded about 50 messages on /scan into a bag and played the bag back with four ways of remapping, while ros2 topic echo --once /scan_front listened. Last, it started a node that recreates its subscription when a parameter changes. Remap rules added no visible startup time. The 29 runs that started had a median of 0.47 s on Humble, 0.56 s on Jazzy and 0.58 s on Lyrical, from start to exit.

Why an absolute rule stops matching in a namespace

rcl expands both sides of a rule before it compares anything. A relative left side gets the node's namespace in front. A relative right side does too. The name your code passes to create_publisher is expanded the same way. Then rcl compares the two full strings, and only an exact match counts.

In the root namespace, scan in code and /scan in a rule both end up as /scan, so either form works. That is why many examples use absolute rules and seem fine. Add -r __ns:=/robot1, or namespace='robot1' in launch, and the code's scan becomes /robot1/scan, while the rule still says /scan. No match, and nothing tells you. The rule order doesn't matter here. -r scan:=scan_front -r __ns:=/robot1 gave /robot1/scan_front, the same as putting the namespace first.

The opposite case is a name that is absolute in code, like tf2's /tf or my /abs_scan. It never moves into a namespace. A relative rule abs_scan:=front expands to /robot1/abs_scan and misses it. The left side has to be absolute: /abs_scan:=front. The right side may be relative, and then it lands in the node's namespace. That gave /robot1/front.

This is how multi-robot setups move tf. -r /tf:=tf in /robot1 gave /robot1/tf, in both ros2 run and launch. It's the remap the multi-robot tf questions below come down to. By the same rules, /tf_static needs its own /tf_static:=tf_static, and nodes that read tf need the rules too, not only the ones that publish it. I only measured publisher names. I didn't run /tf_static or a tf listener.

Private ~/ names

A name like ~/priv expands to the node's full name plus the rest, here /rm_node/priv. The rule priv:=priv2 expands to /priv and misses. Two forms worked: ~/priv:=priv2 and the full /rm_node/priv:=/priv2. Both gave /priv2, not /rm_node/priv2. The right side of a rule expands against the namespace, not the node name. If you want the result under the node's name, write that full name on the right side. I didn't run that form.

Driver nodes often publish on ~/scan. That gives topics like /ldlidar_node/scan, and a plain scan:=/scan rule won't move them. Remap from the full name you see in ros2 topic list.

Node-specific rules and renamed nodes

A rule can start with a node name and a colon: rm_node:scan:=scan_front. It worked, and other_node:scan:=scan_front was ignored, again without a warning. The prefix is checked against the node's name after renaming. With -r __node:=lidar, the rule rm_node:scan:=scan_front stopped working and the topic stayed /scan, while a plain scan:=scan_front still applied. If you rename a node in launch with name=, use the new name in node-specific rules.

Rules don't combine. With two rules for the same name, the first one wins: -r scan:=first -r scan:=second gave /first. They don't chain either: -r scan:=a -r a:=b gave /a, not /b.

ros2 bag play --remap, and recording under another name

A bag stores the topic name it recorded. To get it under another name, remap at playback. Playing a 51-message bag on Humble (50 on Jazzy and Lyrical):

CommandMessage on /scan_front
ros2 bag play bag1 --remap /scan:=/scan_frontreceived
ros2 bag play bag1 --remap scan:=scan_frontreceived
ros2 bag play bag1 -m /scan:=/scan_frontreceived
ros2 bag play bag1 --ros-args -r /scan:=/scan_frontexit code 2: argument -r/--rate: /scan:=/scan_front is not the valid type (float)
ros2 bag play bag1 (control)nothing, the listener timed out

The --ros-args -r form is the trap. ros2 bag play has its own -r, short for --rate, and argparse takes it first. Use --remap or -m. I didn't test renaming while recording. To store /scan_filtered as /scan, the measured path is to record it as is, then play it with --remap /scan_filtered:=/scan.

Changing a topic at runtime

Remap rules are read once, when the node starts. No ros2 command remaps a running node. If you need to switch topics without a restart, make the topic name a parameter and recreate the subscription when it changes. My dyn_node does that in an add_on_set_parameters_callback: destroy the old subscription, create a new one. The graph showed /scan for six one-second checks. Then ros2 param set /dyn_node in_topic scan_front printed Set parameter successful, and every later check showed only /scan_front. That held on all three distros. Messages published between the destroy and the create are lost, and I didn't measure how many.

FAQ

Why is my ROS 2 remapping not working?

Most often the rule doesn't match the node's expanded name, and rcl doesn't report that. In my runs that happened with an absolute rule on a namespaced node, a relative rule for a name that is absolute in code, a ~/ name remapped without ~/, a node-specific rule with the old node name, and an action on Humble. Check ros2 topic list for the real name, then remap from exactly that name.

Should I write remappings with or without a leading slash?

Without, if the name in code is relative. scan:=scan_front worked in the root namespace and in /robot1. /scan:=/scan_front worked only in the root namespace. For a name that is absolute in code, such as /tf, the left side must have the slash.

Can I remap a topic at runtime in ROS 2?

Not with remap rules. They're read when the node starts. Make the topic a parameter and recreate the subscription in a parameter callback. After ros2 param set the node's subscription moved from /scan to /scan_front on Humble, Jazzy and Lyrical.

Do wildcards work in ROS 2 remap rules?

No. */scan:=... and **/scan:=... made the node fail at startup with Couldn't parse remap rule ... Wildcard '*' is not implemented (or '**') on all three distros. Use a namespace or one rule per topic.

How do I play a bag with a different topic name?

Use ros2 bag play bag --remap /old:=/new or -m /old:=/new. Both worked on all three distros. --ros-args -r failed with exit code 2, because -r is --rate for ros2 bag play.
