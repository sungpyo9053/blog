File "/opt/ros/humble/lib/python3.10/site-packages/tf2_ros/buffer_interface.py", line 278, in get
    raise TypeException('Type %s is not loaded or supported' % str(key))
tf2_ros.buffer_interface.TypeException: Type <class 'geometry_msgs.msg._pose_stamped.PoseStamped'> is not loaded or supported

The second error people hit right after the first one is this, from tf2_geometry_msgs.do_transform_pose():

AttributeError: 'PoseStamped' object has no attribute 'position'

Short answer: add import tf2_geometry_msgs to the file that calls tf_buffer.transform(). Nothing you call uses that module by name. Importing it is what registers the PoseStamped, PointStamped, Vector3Stamped, PoseWithCovarianceStamped and PolygonStamped conversions with the buffer, and import tf2_ros doesn't do it for you. Also catch TypeException, or fix the import before you rely on except TransformException. TypeException is not a TransformException, so it passed through that handler and stopped rclpy.spin() on all three distros I tested. For the AttributeError, pass a Pose to do_transform_pose(), or use do_transform_pose_stamped() for a PoseStamped:

import tf2_ros
import tf2_geometry_msgs  # noqa: F401  registers the geometry_msgs conversions
from tf2_ros import TransformException
from tf2_ros.buffer_interface import TypeException
from rclpy.duration import Duration

# Option 1: let the buffer look up the transform from the message header
try:
    out = self.tf_buffer.transform(pose_stamped, 'world', timeout=Duration(seconds=0.1))
except (TransformException, TypeException) as e:
    self.get_logger().warn(f'transform failed: {e}')

# Option 2: look up once, then apply it yourself
t = self.tf_buffer.lookup_transform('world', pose_stamped.header.frame_id, rclpy.time.Time())
out = tf2_geometry_msgs.do_transform_pose_stamped(pose_stamped, t)   # PoseStamped in, PoseStamped out
pose_out = tf2_geometry_msgs.do_transform_pose(pose_stamped.pose, t)  # Pose in, Pose out

This behaved the same on Humble, Jazzy and Lyrical. The messages, the registered types and the function signatures were identical. Only the line number in the traceback and the way Lyrical prints numbers differed.

What I ran

On 2026-11-22 I ran the same scripts in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one distro after another, each container with --network none and ROS_DOMAIN_ID=88. All three images already include tf2_ros_py, tf2_geometry_msgs and tf2_sensor_msgs, so nothing was installed.

The first script uses a tf2_ros.Buffer with no node and no DDS traffic. I stored one static transform, world to child, with a translation of (1, 2, 0) and a 90 degree rotation about z. Then I called buffer.transform() and the do_transform_* functions with different message types, before and after import tf2_geometry_msgs. It also prints the buffer's internal registry, the dictionary that maps a message class to its conversion function, so you can see exactly which types are loaded. At the end it times 20,000 calls of each method.

The second script is a real node. It runs a TransformListener next to static_transform_publisher and calls buffer.transform() on a PoseStamped from a 10 Hz timer for 3 seconds, which gives 30 calls. I ran it once without the import and once with it. A third script checks the exception classes and what happens when the error reaches rclpy.spin().

Cause 1: the conversions load only when you import tf2_geometry_msgs

buffer.transform() doesn't know how to move a PoseStamped. It looks up the message's class in a registry and calls whatever function was registered for it. Right after import tf2_ros the registry was an empty list on every distro, and tf2_geometry_msgs wasn't in sys.modules. The first buffer.transform() on a PoseStamped raised the TypeException, and a PointStamped raised the same error with its own class name.

After import tf2_geometry_msgs the registry held five types on Humble, Jazzy and Lyrical:

['geometry_msgs/PointStamped', 'geometry_msgs/PolygonStamped', 'geometry_msgs/PoseStamped',
 'geometry_msgs/PoseWithCovarianceStamped', 'geometry_msgs/Vector3Stamped']

The same buffer.transform() call then returned a PoseStamped in world at pos=(1.000,3.000,0.000) with the rotation q=(0,0,0.707,0.707), which is the correct answer for a pose at x=1 in the rotated child frame.

The form of the import didn't matter. I tried four in fresh interpreters, and each one registered the same five types: import tf2_geometry_msgs, from tf2_geometry_msgs import do_transform_pose, import tf2_geometry_msgs.tf2_geometry_msgs and from tf2_geometry_msgs.tf2_geometry_msgs import do_transform_pose. The registry is shared by the whole process, so the import can sit in any module that runs before the first transform. Put it in the file that calls transform(), though, because a linter or a teammate will happily delete an import that looks unused. The # noqa: F401 comment in the short answer is there for that reason.

This is the situation in ros2/geometry2 issue 701 (Humble, 2024). A reply there from a ROS 2 core developer gives the same fix and says it is "really non-obvious that this is what is required". The older transform pose in tf2 question reports that commenting out the import brings the error back, which matches my run. That question was on Eloquent, where the Python module wasn't installed at all. On the three current distros it was there in every image.

Cause 2: the type isn't one of the five

Even with the import, buffer.transform() raised the same TypeException for a bare Pose, a PoseArray, a TwistStamped and a nav_msgs/Odometry. A bare Pose has no header, so the buffer has no source frame to look up. The other three just have no registered conversion.

That covers the case in Transforming a non-frame pose with TF2, a point some distance in front of the robot. You don't need a new frame for it. Put the pose in a PoseStamped with header.frame_id = 'base_link' and transform that, or look up the transform once and call do_transform_pose(pose, t), which takes a plain Pose and returned a plain Pose in my run. For a PoseArray, loop over poses with do_transform_pose() and set the new frame on the array's header yourself.

Point clouds need a different module. import tf2_sensor_msgs registered exactly one type, PointCloud2, on all three distros. The cloud post Transform PointCloud2 frame in ROS 2 Python, keep intensity measured that path. It found that do_transform_cloud() kept the intensity field and that rebuilding the cloud from xyz alone dropped it.

Why except TransformException doesn't catch it

Most tutorials wrap the lookup in except TransformException. That doesn't work for this error. On all three distros the classes were:

TypeException MRO: ['tf2_ros.buffer_interface.TypeException', 'builtins.Exception', ...]
issubclass(TypeException, TransformException): False
TransformException MRO: ['tf2.TransformException', 'builtins.Exception', ...]

I put buffer.transform() inside try: ... except TransformException in a timer callback. The exception went straight past the handler on the first callback and out of rclpy.spin(). A plain node with no handler printed the traceback above and exited with code 1. The issue 701 report has exactly this code: an except TransformException block and a node that crashed anyway.

The type check also runs before the lookup. In the listener node without the import, all 30 of 30 calls raised TypeException, starting at 0.10 s, before any transform had arrived. So the error hides frame problems. Once the import is in, the next error you see may be a different one. With the import, Humble returned 30 of 30 transforms. On Jazzy the first 10 calls and on Lyrical the first 9 raised LookupException: "world" passed to lookupTransform argument target_frame does not exist, and the first success came at 1.10 s and 1.00 s. That's the static transform still on its way from the publisher. The timing post Lookup would require extrapolation into the future measured that family of errors. There, a lookup at now() failed 1,800 of 1,800 times, while Time() or a timeout worked. buffer.transform() uses the stamp in your message header, so the same rules apply to it.

do_transform_pose takes a Pose, not a PoseStamped

On all three distros the signature in the installed source was do_transform_pose(pose: Pose, transform: TransformStamped) -> Pose. The stamped version is a separate function. These calls used the TransformStamped from lookup_transform('world', 'child', Time()):

Only do_transform_pose takes the unstamped type. The others take the stamped message. ros2/geometry2 issue 707 (Jazzy, 2024) is this AttributeError, and the reply there was to use do_transform_pose_stamped.

Two results that surprised me

A vector only gets the rotation. Vector3Stamped (1, 0, 0) came out as (0, 1, 0) through both buffer.transform() and do_transform_vector3(), with no part of the (1, 2, 0) translation added. That's correct for directions and velocities, but wrong if you stored a position in a Vector3Stamped. Use PointStamped for positions. A point (1, 0, 0) came out as (1, 3, 0).

The new_type argument didn't convert anything. buffer.transform(pose_stamped, 'world', new_type=PointStamped) returned a PoseStamped on all three distros, with no error or warning. If you want a point, take out.pose.position yourself.

A wrong result is harder to spot when the frames themselves are wrong. The static transform post ROS 2 tf Frame Offset Doubled? Check static_transform_publisher measured a backwards static transform. With no rotation, it put the child at exactly twice the intended offset. Check the frame order before you suspect the math.

Version notes

  • The error text was identical on all three distros: Type <class '...'> is not loaded or supported. Older questions quote if not loaded or supported, and the issue 701 report quotes is not loaded or suported. Search for not loaded or to match every version.
  • The line in the traceback was buffer_interface.py:278 on Humble and Jazzy and buffer_interface.py:290 on Lyrical.
  • Package versions: Humble tf2_ros_py and tf2_geometry_msgs 0.25.24, Jazzy 0.36.23, Lyrical 0.45.10. The registered types and the six function names were the same in all three.
  • On Lyrical (Python 3.14) the results print as Point(x=np.float64(1.0), ...). On Humble and Jazzy the same fields print as plain floats such as x=1.0000000000000002. The values agreed to the printed precision. I didn't test whether publishing those messages behaves differently.
  • On Humble, tf2_geometry_msgs was installed under /opt/ros/humble/local/lib/python3.10/dist-packages, while tf2_ros was under lib/python3.10/site-packages. Sourcing setup.bash put both on the path. On Jazzy and Lyrical both were under lib/python3.x/site-packages.

FAQ

How do I fix "TypeException: Type ... PoseStamped is not loaded or supported"?

Add import tf2_geometry_msgs to the Python file that calls tf_buffer.transform(). Importing it registers the conversions for PoseStamped, PointStamped, Vector3Stamped, PoseWithCovarianceStamped and PolygonStamped. Without it the registry was empty on Humble, Jazzy and Lyrical.

Why doesn't except TransformException catch it?

TypeException comes from tf2_ros.buffer_interface and inherits straight from Exception, not from tf2.TransformException. In my run it passed through an except TransformException block and stopped rclpy.spin(). Import TypeException from tf2_ros and catch both.

Why does do_transform_pose say 'PoseStamped' object has no attribute 'position'?

In ROS 2, do_transform_pose() takes a Pose and returns a Pose. For a PoseStamped, call do_transform_pose_stamped(ps, t), or call do_transform_pose(ps.pose, t). Pass the whole TransformStamped, not t.transform.

How do I transform a Pose that has no frame?

Give it one. Put it in a PoseStamped with the frame it's relative to, such as base_link, then call buffer.transform(). Or look up the transform and call do_transform_pose(pose, t). A bare Pose passed to buffer.transform() raised TypeException even with the import.

Can buffer.transform handle Odometry, PoseArray or TwistStamped?

Not in my run. All three raised TypeException after import tf2_geometry_msgs, because none of them is registered. Transform the poses inside them one by one with do_transform_pose(). For PointCloud2, import tf2_sensor_msgs.
