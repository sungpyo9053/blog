/usr/bin/ld: CMakeFiles/app.dir/src/app.cpp.o: in function `main':
app.cpp:(.text+0x13): undefined reference to `mylib::add(int, int)'
collect2: error: ld returned 1 exit status

The same broken link can also show up at run time instead, after the build has passed:

install/app/lib/app/app: symbol lookup error: install/app/lib/app/app: undefined symbol: _ZN5mylib3addEii
[ros2run]: Process exited with failure 127

Short answer: the linker found the declaration of your function in a header, but no library it was given contains the compiled code. In a ROS 2 workspace that comes down to one missing CMake line in most cases. Inside one package, add target_link_libraries(app mylib). Across two packages, the library package has to export itself, and the setup that worked on Humble, Jazzy and Lyrical was this:

# library package (mylib)
add_library(mylib SHARED src/mylib.cpp)
target_include_directories(mylib PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<INSTALL_INTERFACE:include>)
install(DIRECTORY include/ DESTINATION include)
install(TARGETS mylib EXPORT export_mylib
  LIBRARY DESTINATION lib ARCHIVE DESTINATION lib RUNTIME DESTINATION bin
  INCLUDES DESTINATION include)
ament_export_targets(export_mylib HAS_LIBRARY_TARGET)
# ament_export_dependencies(rcutils)   # for every package mylib links PUBLIC
ament_package()

# executable package (app)
find_package(mylib REQUIRED)
add_executable(app src/app.cpp)
target_link_libraries(app mylib::mylib)

And if you changed the library's function signatures, rebuild everything that uses it, not only the library. colcon build --packages-select mylib leaves the old executable in install/, and that executable is what prints symbol lookup error.

Whenever a build passed, I ran the program with ros2 run.

There were three groups of tests:

  • Twelve two-package builds, with mylib and app as separate packages, where app has <depend>mylib</depend>.
  • A stale-binary test. I built both packages, changed add to take long, then tried several rebuild commands. I repeated that 10 more times per distro.

Inside one package: four ways to get it

No target_link_libraries

This is the most common one in a package that builds a helper library and a node. target_include_directories(app PRIVATE include) lets the compiler find the header, so app.cpp compiles. The linker is never told about libmylib.so, so it fails. Adding target_link_libraries(app mylib) fixed it, and the program printed add(2,3)=5. Use the target name from add_library, not a file name or a path.

The source file isn't in add_library

I listed a different, empty source file in add_library and left mylib.cpp out. The library still built, because a shared library may contain nothing. The error showed up one step later, when app linked, and it was word for word the same as the missing-link case. If target_link_libraries is already there, check that the .cpp with the definition is in the add_library list. Also check that the definition's namespace and parameter types match the header. The linker looks for the exact signature it prints.

A C function called from C++

This happens with vendor sensor drivers and other C code. The function is defined in cfun.c, which CMake compiles as C, and the header has no extern "C". The C++ caller then looks for the mangled C++ name and the linker reports undefined reference to `c_add(int, int)'. The parameter list in the message is the hint. Plain C symbols don't carry parameter types, so a message with types in it means C++ was looking. Wrapping the declarations fixed it:

#pragma once
#ifdef __cplusplus
extern "C" {
#endif
int c_add(int a, int b);
#ifdef __cplusplus
}
#endif

A template defined in the .cpp file

I declared template <typename T> T twice(T x); in the header and defined it in mylib.cpp. The call mylib::twice(4) compiled and then failed with undefined reference to `int mylib::twice<int>(int)'. Nothing in mylib.cpp used twice<int>, so the compiler never generated it. One line at the end of mylib.cpp, template int twice<int>(int);, fixed it, and the program printed twice(4)=8. The other fix is to move the template body into the header. I didn't build that variant.

In most of them the library package still told app nothing useful, because finding the package isn't the same as getting its include path and library.

Three things stand out.

First, exporting only the include directory is the trap that gives you undefined reference rather than a missing header. The header is found and the code compiles, but mylib_LIBRARIES is empty, so ament_target_dependencies and the variable form both link nothing. This matches the second question above, where the client package couldn't use the library until ament_export_libraries was added.

Second, ament_target_dependencies(app mylib) isn't the cause on Humble and Jazzy. It linked correctly whenever the library exported either its libraries or its targets. It can only pass along what the upstream package exported. On Lyrical the command doesn't exist, which is covered in Unknown CMake command "ament_target_dependencies" in ROS 2 Lyrical.

Third, a namespaced name like mylib::mylib only exists if the library package exported targets. With ament_export_libraries alone, CMake treated mylib::mylib as a target name, found no such target and stopped at the generate step. The old variable style and the target style don't mix. Pick one on both sides. The target style is the one that worked unchanged on all three distros.

I expected HAS_LIBRARY_TARGET to matter at run time. It didn't in my run. Without it the program still ran, and after sourcing install/setup.bash, LD_LIBRARY_PATH contained mylib/lib in both variants. The executable had no RPATH or RUNPATH entry, so it found the library through LD_LIBRARY_PATH. I kept the flag in the recommended setup because it's what the ament_cmake docs show for libraries. I didn't measure what it changes.

The library's own dependencies

When mylib linked rcutils::rcutils with PUBLIC and exported its targets, the exported file referred to rcutils::rcutils. My app never called find_package(rcutils), so CMake couldn't resolve that name and stopped. Adding ament_export_dependencies(rcutils) to mylib fixed it without touching app. In real packages app often calls find_package(rclcpp) anyway, which can hide a missing export until someone uses the library from a package that doesn't. Export every dependency that appears in your public link interface.

"symbol lookup error" after rebuilding only the library

This is the case in [ROS2] symbol lookup error and undefined symbol while using image transport cpp. The build passes and the program fails when it starts. I built both packages and ran app. Then I changed int add(int a, int b) to long add(long a, long b) in the header and the source and ran colcon build --packages-select mylib. The library now exported mylib::add(long, long). The old app binary still asked for mylib::add(int, int):

<ws>/install/app/lib/app/app: symbol lookup error: <ws>/install/app/lib/app/app: undefined symbol: _ZN5mylib3addEii
[ros2run]: Process exited with failure 127

_ZN5mylib3addEii is the mangled form of mylib::add(int, int). Pipe it through c++filt to read it, or compare it with nm -D --defined-only libmylib.so | c++filt for the library you have now. If the names differ only in parameter types, the executable is older than the library. That happened in all 33 rebuilds of this kind across the three distros. The same thing happens when apt updates a ROS package and your workspace was built against the old version. I didn't test the apt case.

The fix is to rebuild everything that uses the library. colcon build --packages-above mylib rebuilds mylib and every package that depends on it. colcon build --packages-up-to app --cmake-clean-first also worked every time. Each rebuild took under a second here.

One result surprised me. The edits came from a script, and I first ran --packages-above within the same second as the previous build. In that case it didn't always help. Out of 15 such tries (5 per distro), 3 rebuilt correctly. 6 relinked app without recompiling app.cpp and failed with undefined reference to `mylib::add(int, int)'. The other 6 finished with colcon exit code 0 and left the stale binary, so ros2 run still exited 127. The object file's dependency list did include mylib.hpp. In one Jazzy failure, the installed header and app.cpp.o had the same whole-second timestamp. When the script waited 2 seconds before the edit, --packages-above worked in 15 of 15 tries. A person editing a file won't hit this, but a script or CI job can. If it does, --cmake-clean-first rebuilt app correctly every time I used it.

Version notes

  • The linker messages (undefined reference to, collect2: error: ld returned 1 exit status) were the same on GCC 11.4.0, 13.3.0 and 15.2.0. The offsets, such as app.cpp:(.text+0x13), were the same too.
  • CMake 3.22.1 on Humble prints the missing target on one line: Target "app" links to target "mylib::mylib" but the target was not found. CMake 3.28.3 on Jazzy and 4.2.3 on Lyrical split it into Target "app" links to:, the target name, and but the target was not found. Possible reasons include:. Search for the target name, not the whole line.
  • For the missing ament_export_dependencies, Humble reported the error at CMakeLists.txt:5 (add_executable) in app. Jazzy and Lyrical reported it inside the library's generated export_mylibExport.cmake:61, which makes the library look broken when the missing line is in its CMakeLists.txt.
  • Lyrical has no ament_target_dependencies, so every variant that used it stopped with Unknown CMake command, whatever the library exported.
  • The exported include path reached app as -isystem <ws>/install/mylib/include on all three distros.

Not tested

  • Prebuilt third-party .so files linked with find_library, and cannot open shared object file at run time.
  • Static libraries, -fPIC relocation errors and link order between static libraries.
  • Libraries that use messages generated in the same package (rosidl_typesupport link errors).
  • Plugins and components loaded with dlopen.
  • Symbol lookup errors after an apt upgrade of ROS packages.
  • The Ninja generator, --symlink-install, clang, and the other RMW implementations. The RMW doesn't take part in linking.
  • Moving template bodies into the header.

FAQ

What does "undefined reference to" mean in a ROS 2 colcon build?

The compiler found a declaration of the function, usually in a header, and the linker found no compiled definition in any library it was given. In my tests that was a missing target_link_libraries, a source file left out of add_library, a C function without extern "C", a template defined in a .cpp, or a library package that exported only its include directory.

How do I link a library from another package in ROS 2?

In the library package, install the target with EXPORT export_mylib and call ament_export_targets(export_mylib HAS_LIBRARY_TARGET). In the other package, call find_package(mylib REQUIRED) and target_link_libraries(app mylib::mylib). That built and ran on Humble, Jazzy and Lyrical.

Why doesn't ament_target_dependencies link my own library?

It links only what the upstream package exported. With just ament_export_include_directories, the header was found but nothing was linked, which gave undefined reference. Exporting the library with ament_export_libraries or ament_export_targets made ament_target_dependencies work on Humble and Jazzy. Lyrical doesn't have the command at all.

What does "symbol lookup error: undefined symbol" mean when I run a node?

The executable was built against an older version of a library. In my run, changing a function's parameter types and rebuilding only the library gave this error and exit code 127 every time. Rebuild the dependent packages with colcon build --packages-above mylib, or with --cmake-clean-first if a build in the same second skipped them.

What does "links to target mylib::mylib but the target was not found" mean?

The executable links a namespaced CMake target, and the library package didn't export targets. Add install(TARGETS mylib EXPORT export_mylib ...) and ament_export_targets(export_mylib HAS_LIBRARY_TARGET) to the library. If the missing name is a dependency such as rcutils::rcutils, add ament_export_dependencies(rcutils).
