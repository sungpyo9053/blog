terminate called after throwing an instance of 'std::runtime_error'
  what():  Node '/my_node' has already been added to an executor.
[ros2run]: Aborted

The same family has three more messages: Callback group has already been added to an executor., spin_some() called while already spinning (also spin_once() and spin_until_future_complete()), and, in a MultiThreadedExecutor, a bare terminate called without an active exception.

Short answer: an rclcpp node can belong to one executor at a time, and an executor can only be spun from one place at a time. The error usually comes from rclcpp::spin_until_future_complete(node, future) or rclcpp::spin_some(node) inside a callback of a node that is already spinning. Those functions add the node to a second, temporary executor, and rclcpp refuses. Don't spin inside a callback. Send the request with a response callback and return:

// inside a timer, subscription or service callback
client_->async_send_request(request,
  [this](rclcpp::Client<std_srvs::srv::Trigger>::SharedFuture f) {
    RCLCPP_INFO(get_logger(), "reply: %s", f.get()->message.c_str());
  });
// return right away; the executor delivers the reply later

If the callback really has to wait for the answer, put the client in its own callback group, spin the node with a MultiThreadedExecutor, and block with future.wait_for(...). Both of these, and a third option with a separate client node, completed 20 out of 20 calls on Humble, Jazzy and Lyrical. Details and timings are below.

Two quick checks tell you which kind you have. "Node has already been added" or "Callback group has already been added" means the node or group is going into a second executor. "called while already spinning" means the same executor is being spun again from inside itself.

What I ran

On 2026-11-03 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro after another, on a 2 vCPU Linux VM. One ament_cmake package held two executables. uncaught is the plain mistake with no try: add a node to an executor, then call rclcpp::spin(node). cases takes a case name, runs one pattern from the table, and catches the exception in main() so it can print what() and the time since start.

The service cases use a std_srvs/srv/Trigger server on a second node, srv_node, in the same process, spun by its own SingleThreadedExecutor in a separate thread. The calling node has a 100 ms wall timer. For the fixes, the timer sends one request per tick until 20 have been sent, and the program records the time from async_send_request to the reply. Because client and server share one process, these times show the cost of each pattern, not network latency.

The package built with no warnings on Humble and Jazzy. On Lyrical, both uses of the free function rclcpp::spin_some(node) printed a deprecation warning (see Version notes).

Cause 1: the node goes into a second executor

rclcpp::spin(node), rclcpp::spin_some(node) and rclcpp::spin_until_future_complete(node, ...) are convenience functions. Each one creates an executor, adds your node to it, spins, and removes it again. If the node already belongs to another executor, the add fails. In my runs that happened in every one of these cases:

  • exec.add_node(node) followed by rclcpp::spin(node). It threw at startup, 12.7 to 18.7 ms into the program.
  • add_node of the same node to two executors, or twice to the same one.
  • A timer callback that called rclcpp::spin_some(node) or rclcpp::spin_until_future_complete(node, f, 2s) while main() was in rclcpp::spin(node). It threw on the first tick, 114.0 to 129.8 ms in.

The last one is the pattern in most of the questions linked below: someone calls a service from inside a callback the same way the client tutorial does from main(). The tutorial code works because nothing is spinning yet when main() calls spin_until_future_complete. I ran that too. 20 out of 20 calls completed, with a median of 0.070 ms (Humble), 0.090 ms (Jazzy) and 0.068 ms (Lyrical) per call. The same line inside a timer callback threw on the first call.

The message is the same wherever it comes from. A shell that ends in terminate called after throwing doesn't tell you which line did it. Look for any call that takes the node itself (rclcpp::spin*, spin_until_future_complete, a SyncParametersClient built from the node) and runs while the node is already spinning.

SyncParametersClient hits it too

SyncParametersClient(node, "srv_node") created and used inside a timer callback threw Node '/my_node' has already been added to an executor. on all three distros. It never got to call get_parameters(). The same client created in main() before spinning worked and read use_sim_time=false from srv_node. This matches rclcpp issue #2940, where the reporter found that get_parameters calls spin_node_until_future_complete internally. Inside a callback, use AsyncParametersClient with a callback, or build the sync client on a separate node (fix 3 below).

Callback groups follow the same rule

A callback group can also belong to only one executor. Adding the same group to two executors with add_callback_group threw Callback group has already been added to an executor. So did a quieter variant. I created the group with the default automatically_add_to_executor_with_node=true, added the node to executor A, then added the group to executor B. The group had already gone into A with the node. If you want to give a group its own executor, create it with false as the second argument to create_callback_group.

remove_node frees the node

After exec.add_node(node) and exec.remove_node(node), rclcpp::spin_some(node) ran without an error on all three distros. Calling remove_node in the middle of a spin is not something I tested, and I wouldn't use it as a fix.

Cause 2: the same executor is spun again from inside

If you hold the executor yourself and call its own spin methods from one of its callbacks, the node isn't added anywhere new. The executor sees that it is already spinning and throws:

  • exec.spin_some() gave spin_some() called while already spinning.
  • exec.spin_all(10ms) gave the same text, spin_some(), not spin_all(). Search for the spin_some message even if your code calls spin_all.
  • exec.spin_once(0ms) gave spin_once() called while already spinning.
  • exec.spin_until_future_complete(f, 2s) gave spin_until_future_complete() called while already spinning.

In a SingleThreadedExecutor all four threw on the first timer tick, and the exception came out of exec.spin() in main(), where a try could catch it.

The MultiThreadedExecutor aborts

With a MultiThreadedExecutor the same spin_until_future_complete call killed the process every time, and the try in main() never caught it. The callback runs in a worker thread, and the exception doesn't come back to the thread that called spin(). What gets printed varies. I ran this case 10 more times per distro:

So if a multithreaded node dies with terminate called without an active exception and nothing else, a nested spin in a callback is one possible cause. With a try/catch around the call inside the callback, the real message showed up every time on all three distros: spin_until_future_complete() called while already spinning.

All three fixes worked, and their per-call times were within about 0.05 ms of each other on every distro. Pick by code shape, not by speed:

  • Option 1 is the smallest change and needs no extra threads. The cost is that the code after the call moves into the response callback.
  • Option 2 keeps straight-line code that waits for the reply. Both parts are needed. With the client in the same group as the timer, the reply can't be handled while the timer callback is running, and every wait_for(1s) timed out. With a separate group but only one thread, it timed out too, because the only thread was busy waiting. I always waited with a timeout, which is what turned these mistakes into counted timeouts. After each timeout my code called client->remove_pending_request(future.request_id) to drop the request.
  • Option 3 keeps spin_until_future_complete and the code you copied from the tutorial. The client lives on a second node, here my_node_client, that isn't added to the main executor, so spinning its private executor from a callback is allowed. Like option 2, it holds the timer callback until the reply arrives.

Making the node a member of a second executor doesn't help. That is the error itself.

Version notes

  • Every error text in the first table was the same on Humble (rclcpp 16.0.21), Jazzy (rclcpp 28.1.22) and Lyrical (rclcpp 32.0.3). All three include the node's full name, '/my_node'. Older questions show Node has already been added to an executor. without a name. The name was added by rclcpp PR #1686. Drop the name when you search.
  • Lyrical deprecates the free function rclcpp::spin_some(node): 'void rclcpp::spin_some(const Node::SharedPtr&)' is deprecated: use SingleThreadedExecutor::spin_some instead [-Wdeprecated-declarations]. It still compiled and behaved as on the other distros. rclcpp::spin(node) and the free rclcpp::spin_until_future_complete gave no warning on Lyrical.
  • For option 2 the script passes rmw_qos_profile_services_default to create_client on Humble and rclcpp::ServicesQoS() on Jazzy and Lyrical, chosen with RCLCPP_VERSION_MAJOR. If you copy it to Humble, use the rmw_qos_profile_t form.
  • How often the MultiThreadedExecutor abort printed the real message differed between distros (table above). With 10 runs each, I wouldn't read more into that than "either can happen".

The rclpy version of this problem has different messages. If you see Executor is already spinning or a stalled spin_until_future_complete from Python, see rclpy and asyncio: no running event loop, hung service calls.

FAQ

What does "Node has already been added to an executor" mean?

Your node was added to a second executor while it still belonged to the first. Usually a rclcpp::spin_until_future_complete(node, ...), rclcpp::spin_some(node) or SyncParametersClient(node, ...) call ran inside a callback of the spinning node. Each of those threw on Humble, Jazzy and Lyrical.

How do I call a service from inside a callback in rclcpp?

Send it with async_send_request(request, callback) and return, or put the client in its own callback group, use a MultiThreadedExecutor and wait with future.wait_for. A separate client node with its own executor also worked. All three completed 20 of 20 calls on every distro I tested.

What does "spin_some() called while already spinning" mean?

Your code called a spin method on an executor from inside one of that executor's callbacks. spin_all reports it with the same spin_some() text. spin_once and spin_until_future_complete have their own versions of the message.

Why does my multithreaded node die with "terminate called without an active exception"?

One cause I measured is a nested spin_until_future_complete in a MultiThreadedExecutor callback. The process aborted every time, and in most runs on Humble and Lyrical the real message was not printed. Wrap the call in try/catch inside the callback to see it.

Why does future.wait_for time out inside my callback?

The reply can't be handled while your callback holds the thread or the callback group. In my runs, a client in the timer's group or a SingleThreadedExecutor gave 20 timeouts out of 20. A separate group for the client plus a MultiThreadedExecutor fixed it.
