ModuleNotFoundError: No module named 'tf_transformations'

Code ported from ROS 1 often fails one step earlier, with ModuleNotFoundError: No module named 'tf' from from tf.transformations import euler_from_quaternion.

Short answer: tf_transformations is a separate apt package. It is not part of ros-base, tf2_ros or the tf2 Python packages, and installing transforms3d alone doesn't provide it. Install the ROS package, declare it in package.xml, and pass the quaternion as [x, y, z, w]:

sudo apt update
sudo apt install ros-$ROS_DISTRO-tf-transformations
<exec_depend>tf_transformations</exec_depend>
from tf_transformations import euler_from_quaternion, quaternion_from_euler

q = msg.pose.pose.orientation
roll, pitch, yaw = euler_from_quaternion([q.x, q.y, q.z, q.w])   # radians

x, y, z, w = quaternion_from_euler(roll, pitch, yaw)              # returns x, y, z, w

That worked on Humble, Jazzy and Lyrical. The package was there for all three, and apt pulled in python3-transforms3d as a dependency. The import worked right away in a shell that was already sourced. If you can't install it, transforms3d and SciPy give the same angles, but each one has an ordering trap.

What I ran

On 2026-11-18 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images on a 2 vCPU Ubuntu server, one distro after the other. Each container had network access for apt and rosdep. ROS traffic was kept local with ROS_DOMAIN_ID=88 and localhost-only discovery. The script, repro.sh, did this in order:

  1. Tried the imports people report (tf_transformations, tf.transformations, tf2, tf2_ros, transforms3d, scipy), before and after sourcing ROS.
  2. Ran apt-get update, then checked the apt candidates, the package's dependencies and the rosdep keys. It also ran rosdep install --simulate on a small package that declares tf_transformations.
  3. Installed python3-transforms3d alone and tried the import again. Then it installed ros-$ROS_DISTRO-tf-transformations and SciPy.
  4. Ran compare.py, which converts seven roll, pitch and yaw sets with four methods: tf_transformations, transforms3d, SciPy's Rotation and a hand-written formula that is copied around a lot. It also tries the common mistakes and times each method.
  5. Published a static transform with roll 10°, pitch 20° and yaw 30°, and read it back with tf2_echo.

Cause 1: the package isn't installed

None of the three base images had it. ros2 pkg list | grep -c tf_transformations printed 0, and the import failed the same way with or without sourcing. NumPy was present (1.21.5 on Humble, 1.26.4 on Jazzy, 2.3.5 on Lyrical). transforms3d and SciPy were not. On Lyrical's Python 3.14 the traceback also shows the import line itself, so the message has one extra line there.

After apt-get update, apt had a candidate on every distro:

An old answer says transforms3d isn't in Ubuntu's apt and must come from pip. On these three distros that's no longer true: apt-cache depends lists python3-transforms3d, so apt install brings it in.

If apt says Unable to locate package ros-humble-tf-transformations, the package isn't the problem. Your apt sources are. That happens when the ROS apt repository isn't configured, when you haven't run apt update, or when the OS isn't the Ubuntu release the distro targets (one of the questions below is Raspberry Pi OS). I didn't reproduce the non-Ubuntu case.

Cause 2: only transforms3d was installed

This is the advice in many older answers, and on its own it doesn't fix the error. After apt-get install python3-transforms3d, import transforms3d worked on all three distros, but import tf_transformations still raised the same ModuleNotFoundError. transforms3d is a general-purpose library. tf_transformations is a small ROS package that wraps it with the old ROS 1 function names, and you have to install it separately.

Cause 3: the process doesn't see the ROS Python path

The module is installed to /opt/ros/<distro>/lib/python3.X/site-packages/tf_transformations/ (python3.10, python3.12 and python3.14 on Humble, Jazzy and Lyrical). I installed the package in a shell that I had sourced before the install. The import worked right away, with no re-sourcing, because that directory was already on PYTHONPATH. Running the same command with PYTHONPATH unset gave the original error again.

So if ros2 pkg list shows tf_transformations and your script still can't import it, check how the script is started: an IDE run configuration, a systemd unit, cron, or a different Python. The same thing happens with rclpy itself. My post on No module named 'rclpy' covers the same two causes for rclpy: a terminal that wasn't sourced with the setup file for your shell, and a conda Python instead of the system python3.

Cause 4: package.xml doesn't declare it

This one doesn't break your machine. It breaks the next machine. The rosdep key is the package name with an underscore, tf_transformations. With the exec_depend line from the short answer, rosdep resolve tf_transformations returned ros-humble-tf-transformations on Humble, and the matching name on Jazzy and Lyrical. rosdep install --from-paths src --ignore-src -y --simulate printed:

#[apt] Installation commands:
  apt-get install -y ros-humble-tf-transformations

After the install, rosdep check printed All system dependencies have been satisfied. If you call transforms3d or SciPy directly, their keys are python3-transforms3d and python3-scipy. Both resolved to apt packages of the same names on all three distros. If rosdep gives you a different name or an error, your ROS_DISTRO may be unset. My rosdep "Cannot locate rosdep definition" post measured that case along with wrong keys and pip keys.

Cause 5: the ROS 1 import and tf2

from tf.transformations import euler_from_quaternion failed with No module named 'tf' on all three distros. In ROS 2 the only change you need is the import: from tf_transformations import euler_from_quaternion. The function names and argument order are the same. The module exposes 48 public names, and quaternion_multiply and euler_matrix are among them.

import tf2 failed with No module named 'tf2'. import tf2_ros worked, but it contains nothing with "euler" or "quat" in the name, and tf2_ros.transformations doesn't exist. tf2 in Python handles buffers, listeners and broadcasters. It doesn't convert angles.

The silent mistakes: component order and message objects

Once the import works, the most common bug doesn't raise anything. The three libraries don't use the same component order:

LibraryQuaternion orderEuler call
tf_transformationsx, y, z, weuler_from_quaternion([x, y, z, w])
transforms3dw, x, y, ztransforms3d.euler.quat2euler([w, x, y, z])
SciPyx, y, z, wRotation.from_quat([x, y, z, w]).as_euler('xyz')

For roll 10°, pitch 20° and yaw 30°, all three returned the same numbers when I used the right order. With the wrong order:

  • tf_transformations given [w, x, y, z] returned [150.000, -20.000, 10.000] degrees. SciPy with the same mistake returned the same values.
  • transforms3d given [x, y, z, w] returned [30.000, -20.000, 170.000].
  • The identity quaternion written as [1, 0, 0, 0] (w first) and passed to tf_transformations came back as roll 180°. If a robot sitting flat on the floor reports a roll near 180°, check the order first.

Passing the message object fails loudly, which is better. tf_transformations.euler_from_quaternion(msg) and transforms3d both raised TypeError: cannot unpack non-iterable Quaternion object. SciPy raised TypeError: float() argument must be a string or a real number, not 'Quaternion'. In the other direction, Quaternion(x=q[0], y=q[1], z=q[2], w=q[3]) accepted the NumPy float64 values that quaternion_from_euler returns, with no conversion.

SciPy has one more trap. Lowercase 'xyz' is the extrinsic convention. It matched tf_transformations in every case. Uppercase 'XYZ' is intrinsic, and for the same 10°, 20°, 30° quaternion it returned [-1.116, 22.242, 28.452].

The hand-written formula is the one you find in tutorials: atan2 for roll and yaw, and a clamped asin for pitch. It was the fastest, and it agreed with the libraries for normal, unit-length quaternions. It went wrong in two cases. At exactly pitch 90° it returned roll 90° and yaw 90°, which is a different orientation, 10.0° away from the input. And it assumes the quaternion is unit length. [0, 0, 1, 1] is a 90° yaw that was never normalized, and the formula returned 116.565°. A 60° yaw scaled by four came back as 116.802°. The three libraries normalize first and returned 90° and 60°. If you copy that formula, normalize the quaternion first, and don't use it near pitch ±90°.

At pitch 90° the libraries don't return the roll and yaw you put in. They return [-10, 90, 0] for an input of 30, 90 and 40. That's not a bug. At that pitch, roll and yaw act on the same axis, so only their difference is defined. All three libraries put the whole difference into roll and returned exactly the same rotation (error below 10-14 degrees). If you need yaw near that pitch, keep the quaternion and don't go through Euler angles.

For speed, a single tf_transformations call took 14 to 21 µs. For a whole array, SciPy's vectorized call was the fastest on Jazzy and Lyrical. On Humble's SciPy 1.8.0 it took 4.64 µs per quaternion, less than 2 times faster than transforms3d called in a loop (8.2 µs). These numbers come from one run on a shared 2 vCPU machine, so treat them as rough sizes.

My pick: use tf_transformations when the code came from ROS 1 or you want x, y, z, w everywhere. Call transforms3d directly if you're comfortable writing w first. Use SciPy if it's already installed or you convert arrays.

One more caution. On Humble, tf_transformations runs on the apt transforms3d 0.3.1, and that version only works with the NumPy versions it was built for. My NumPy 2 and cv_bridge post measured it failing with no attribute 'float' after pip upgraded NumPy to 1.26.4, and failing again with NumPy 2. In this run every distro used its apt NumPy, and nothing failed.

Checking angles without Python: tf2_echo

If you only want to see the angles of a transform that's already in TF, you don't need any of these libraries. tf2_echo prints the rotation three ways. For a static transform published with --roll 0.17453293 --pitch 0.34906585 --yaw 0.52359878, all three distros printed:

- Rotation: in Quaternion (xyzw) [0.038, 0.189, 0.239, 0.952]
- Rotation: in RPY (radian) [0.175, 0.349, 0.524]
- Rotation: in RPY (degree) [10.000, 20.000, 30.000]

Those match quaternion_from_euler for the same angles ([0.0381, 0.1893, 0.2393, 0.9515]), and the label shows the order is xyzw. This is also a quick way to check the direction of a static transform. My static_transform_publisher offset post measured that publishing a transform backwards puts the child at exactly twice the offset when there's no rotation.

Version notes

  • All three had tf_transformations 1.1.1 in apt. The apt transforms3d was 0.3.1 on Humble, 0.4.1 on Jazzy and 0.4.2 on Lyrical. With each distro's apt NumPy, every conversion gave the same results.
  • SciPy was 1.8.0, 1.11.4 and 1.16.3.
  • On Lyrical, tf2_echo first failed with pthread_create failed: Resource temporarily unavailable. That was my own container limit (--pids-limit 40, and threads count against it), not ROS. With a higher limit it printed the same output as the other distros. If you limit PIDs in Docker, leave room for DDS threads.

Not tested

pip installs of tf_transformations or transforms3d, building tf_transformations from source, Raspberry Pi OS, Debian or any non-Ubuntu host, arm64, Windows, virtual environments, NumPy versions other than each distro's apt NumPy, C++ (tf2::Matrix3x3::getRPY), quaternions that are both near pitch 90° and slightly unnormalized (like 0, 0.707, 0, 0.707), axis conventions other than sxyz/'xyz', Iron, Kilted and Rolling.

FAQ

How do I install tf_transformations in ROS 2?

Run sudo apt update, then sudo apt install ros-$ROS_DISTRO-tf-transformations. On Humble, Jazzy and Lyrical this installed version 1.1.1 and pulled in python3-transforms3d from apt, so pip wasn't needed. Add <exec_depend>tf_transformations</exec_depend> to package.xml so rosdep installs it on other machines.

I installed transforms3d but still get No module named 'tf_transformations'. Why?

transforms3d is only the library underneath. The tf_transformations module comes from the ROS package ros-$ROS_DISTRO-tf-transformations. With only python3-transforms3d installed, the import still failed on all three distros.

What replaces tf.transformations from ROS 1?

tf_transformations. Change from tf.transformations import euler_from_quaternion to from tf_transformations import euler_from_quaternion. The function names and the [x, y, z, w] order are the same. Neither tf nor tf2 exists as a Python module in ROS 2, and tf2_ros has no Euler functions.

Why does euler_from_quaternion give a roll of 180 degrees for a level robot?

The quaternion was probably passed in w, x, y, z order. tf_transformations and SciPy expect x, y, z, w, and transforms3d expects w, x, y, z. The identity quaternion written w-first came back as roll 180 in my run. Pass [q.x, q.y, q.z, q.w].

Why are roll and yaw wrong when pitch is 90 degrees?

At pitch 90 only the difference between roll and yaw is defined. All three libraries returned roll -10, pitch 90 and yaw 0 for an input of 30, 90 and 40, which is the same rotation. The common hand-written formula returned 90, 90 and 90, which was 10 degrees off. Keep quaternions if you need yaw near pitch 90.
