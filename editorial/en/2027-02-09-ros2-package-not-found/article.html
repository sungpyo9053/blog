$ ros2 run demo_py talker
Package 'demo_py' not found

$ ros2 launch demo_py t.launch.py
Package 'demo_py' not found: "package 'demo_py' not found, searching: ['/opt/ros/humble']"

$ ros2 pkg prefix demo_py
Package not found

In Python code the same lookup ends in ament_index_python.packages.PackageNotFoundError: "package 'nope_pkg' not found, searching: [...]", raised from get_package_prefix or get_package_share_directory.

Short answer: ros2 doesn't look in your workspace folder. It looks at the prefixes listed in AMENT_PREFIX_PATH, and inside each one for the file share/ament_index/resource_index/packages/<name>. "Package not found" means no listed prefix has that file. The searching: [...] list in the launch error is that variable, so read it first. If your install/<pkg> isn't in it, the fix is to source the setup file that colcon wrote in the same shell, after the build:

cd ~/ws                      # the folder that contains src/, not src/ itself
colcon build
source install/setup.bash    # again after every build that adds a package
ros2 run demo_py talker

If the build succeeded, the shell is sourced and the package is still missing, check the <build_type> line in package.xml. An ament_cmake package marked cmake or catkin, or with no build_type at all, built with exit code 0 in my run on every distro. Sourcing then left AMENT_PREFIX_PATH without the package, and ros2 pkg list didn't show it.

What I ran

On 2026-11-22 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, each container with --network none. Inside each, ros2 pkg create made an ament_python package demo_py with a talker node (it prints Hi from demo_py. and exits) and an empty ament_cmake package demo_cmake. I added a launch file t.launch.py that starts the talker. colcon build finished both packages in 1.9 s on Humble, 2.2 s on Jazzy and 2.3 s on Lyrical. Then I broke the setup one way at a time and ran ros2 run, ros2 launch, ros2 pkg prefix, ros2 pkg executables and ros2 pkg list, printing AMENT_PREFIX_PATH each time.

The failure is fast. Five failing ros2 run calls took 144 to 146 ms each on Humble, 195 to 198 ms on Jazzy and 301 to 401 ms on Lyrical. Five working calls took 207 to 210 ms, 280 to 282 ms and 364 to 375 ms. So ros2 doesn't wait or retry before it gives up. It reads the index once and stops.

Not sourced, or sourced before the build

With only /opt/ros/<distro>/setup.bash sourced, AMENT_PREFIX_PATH was just /opt/ros/humble (or /opt/ros/jazzy, /opt/ros/lyrical). All four commands failed with exit code 1. After source /ws/install/setup.bash it was /ws/install/demo_py:/ws/install/demo_cmake:/opt/ros/jazzy, and ros2 pkg prefix demo_py printed /ws/install/demo_py. colcon's default install layout gives every package its own prefix, so each new package adds one entry.

That is why a package you create later is missing in a shell you sourced earlier. I sourced the workspace, created new_pkg, built it with colcon build --packages-select new_pkg (exit 0) and ran it in the same shell: Package 'new_pkg' not found. After sourcing install/setup.bash again, the same command printed Hi from new_pkg.. Sourcing is a snapshot of the install folder at that moment. It doesn't follow later builds.

The opposite case also fails. I built, sourced, then deleted install/. AMENT_PREFIX_PATH still listed /ws6/install/demo_py, but the marker file was gone, so ros2 said not found. A path in the variable doesn't help if the folder behind it no longer exists.

Which setup file you source matters too. With a clean environment, install/local_setup.bash alone put the workspace in AMENT_PREFIX_PATH but left no ros2 on the PATH. The earlier post on local_setup.bash vs setup.bash measured that difference on Jazzy in detail, including the 127 exit code you get from the missing ros2 command.

The package isn't in install/

A successful build doesn't mean the package you want was built. In a fresh workspace with both packages in src/, colcon build --packages-select demo_cmake finished with exit 0, and install/ held only demo_cmake. ros2 run demo_py talker then failed after sourcing. ls install is the fastest check: no folder named after your package means it was never installed.

The other common way to end up there is running colcon build from the wrong folder. colcon writes build/, install/ and log/ into the current directory. When I ran it inside /ws7/src, it built the package into /ws7/src/install, and /ws7/install didn't exist. source /ws7/install/setup.bash printed No such file or directory, and the next ros2 run said Package 'demo_py' not found. Sourcing /ws7/src/install/setup.bash worked. Delete the three folders inside src/ and build from the workspace root instead.

build_type in package.xml

This is the case that survives "I sourced it, I promise". The template from ros2 pkg create --build-type ament_cmake ends with:

<export>
  <build_type>ament_cmake</build_type>
</export>

I made three copies of demo_cmake: one with <build_type>cmake</build_type>, one with catkin, and one with the line removed. CMakeLists.txt was unchanged and still called ament_package(). All three built with exit code 0 and Finished <<< demo_cmake, and all three installed the marker file install/demo_cmake/share/ament_index/resource_index/packages/demo_cmake. After source install/setup.bash, though, AMENT_PREFIX_PATH was still only /opt/ros/<distro>. CMAKE_PREFIX_PATH was /ws8/install/demo_cmake. ros2 pkg prefix demo_cmake printed Package not found and ros2 pkg list had 0 matching lines.

So the marker was there, but nothing told ros2 to look in that prefix. For these three variants the setup script only extended the CMake search path. The answer on the 2024 Package not found after sourcing with ROS 2 Humble question gives the same fix: "you also need to set ament_cmake for build_type in the export section of the package.xml". An old ROS 1 package.xml copied into a ROS 2 workspace hits the same thing, which is what the answer on Why doesn't ros2 pkg list show the packages that I built? found. I didn't test changing format="2" to format="3" on its own.

After you fix build_type, rebuild that package and source again. A shell sourced while the package was still a plain CMake package won't pick up the change.

Two setup.py edits that did not cause it

The ament_python template installs the marker through data_files:

('share/ament_index/resource_index/packages',
    ['resource/' + package_name]),

Some askers suspect a missing marker behind "Package not found". With these two lines deleted, the build still passed and ros2 run demo_py talker printed Hi from demo_py. on all three distros. The marker was in install anyway. colcon-ros 0.5.0, the version in all three images, checks whether the package installs it and creates the file when it doesn't: colcon_ros/task/ament_python/build.py calls create_file(args, 'share/ament_index/resource_index/packages/' f'{self.context.pkg.name}'). The template has the lines and they cost nothing, so keep them. Deleting the resource/demo_py file while leaving the lines in is worse. The build failed with error: can't copy 'resource/demo_py': doesn't exist or not a regular file.

The second edit was renaming the package in package.xml to demo_pkg while setup.py kept package_name = 'demo_py'. The build passed and produced install/demo_pkg, which held two markers, demo_pkg and demo_py. ros2 run demo_pkg talker said No executable found, because the script went to lib/demo_py. ros2 run demo_py talker worked. Keep the two names the same and you avoid both puzzles.

Package not found vs No executable found

The two errors mean different things. Package 'x' not found stops at the index lookup. No executable found means the package was found and ros2 looked in its lib/<pkg> folder for a file with that name. A wrong executable name (ros2 run demo_py talkr) gave the second one, while a misspelled package name (demo_pyy) gave the first. If you have "No executable found", the earlier post on No executable found and not found on the libexec directory measured the entry point, setup.cfg and --symlink-install causes. If ros2 launch finds the package but not the file, that's the error covered in file was not found in the share directory of package, where the launch file never made it into install/<pkg>/share.

FAQ

Why does ros2 run say Package not found after colcon build succeeded?

In my run, the usual reason was the shell. ros2 only searches AMENT_PREFIX_PATH, and the build doesn't change it. Source install/setup.bash in the same terminal after the build, and again after any build that adds a new package.

I sourced install/setup.bash and the package is still not found. What else?

Check that install/<pkg> exists. It was missing after --packages-select picked another package, and after colcon build ran inside src/. If it exists, check <build_type> in package.xml. With cmake, catkin or no build type, the build passed but sourcing didn't add the package.

What does "searching: ['/opt/ros/humble']" mean?

That list is AMENT_PREFIX_PATH. If it only shows /opt/ros/<distro>, your workspace isn't sourced in that shell. A working shell listed /ws/install/demo_py before the distro path.

Does a missing resource marker in setup.py cause Package not found?

Not with colcon-ros 0.5.0. With the resource_index lines removed from data_files, colcon still created the marker and the node ran on all three distros. Deleting the resource/<pkg> file while keeping the lines made the build fail instead.

Is Package not found the same as No executable found?

No. "Package not found" means the index lookup failed. "No executable found" means the package was found but no matching file was in lib/<pkg>. A package.xml name that differed from setup.py gave the second one.
