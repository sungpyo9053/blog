Short answer: rclpy got something that isn't a generated ROS 2 interface class. The hint about ROS 1 is only one of the causes. In my runs the same error came from a node class with the same name as its service type, from from PIL import Image replacing sensor_msgs.msg.Image, from a type name passed as a string, from a module, and from a hand-written Python class used as an action type. The word in quotes tells you which. 'type' means a plain Python class, 'module' means a module and 'str' means a string. Print the object you pass and its type, right before the failing call:

print(Image, type(Image))
# good:  <class 'sensor_msgs.msg._image.Image'> <class '...Metaclass_Image'>
# bad:   <module 'PIL.Image' from '/usr/lib/python3/dist-packages/PIL/Image.py'> <class 'module'>

A real ROS 2 class has a metaclass named Metaclass_<Name>. Anything else fails. Fix the name (an import alias, or rename your own class), or fix the environment so the ROS 2 package is the one Python imports. All of these fixes worked on Humble, Jazzy and Lyrical.

What I ran

On 2026-11-08 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images on a 2 vCPU Linux host, one distro at a time. The base images have neither example_interfaces (for AddTwoInts and Fibonacci) nor PIL, so the script installs ros-<distro>-example-interfaces and python3-pil first. DDS stayed on domain 88, localhost only.

A Python file holds 18 small cases. Each case creates one node and then one publisher, subscription, service, client, action client or action server with a wrong "type". Each case runs in its own process, so a crash in one doesn't hide the others. The script prints the exception, the file and line that raised it, and the exit code. For the ROS 1 case I didn't install ROS 1. Noetic doesn't install on Ubuntu 22.04, 24.04 or 26.04. Instead I made a small stand-in. It's a std_msgs package whose String is a plain Python class, like a genpy message, and I put it first on PYTHONPATH. That gives rclpy what a sourced Noetic would give it: a class with the right name and no ROS 2 type support. A real Noetic install is in "Not tested".

All three distros raised the same exception classes in the same cases. Only the wording changed, and so did one result, the instance case.

Cause 1: ROS 1 packages ahead of ROS 2 on PYTHONPATH

This is the cause the message has in mind. If you source a ROS 1 setup file after a ROS 2 one, ROS 1's Python folders go to the front of PYTHONPATH. Then from std_msgs.msg import String finds the ROS 1 package first. The import works and the name is right, but the class is a genpy class with no Metaclass_String. The first create_publisher or create_subscription with it fails.

With my stand-in first on the path, Python reported /tmp/fake_ros1/std_msgs/msg/__init__.py as the source of std_msgs.msg. Both create_subscription and create_publisher failed with the error at the top of this page. The CLI failed too. ros2 topic pub --once /chatter std_msgs/msg/String "{data: hi}" and ros2 topic echo /chatter std_msgs/msg/String both printed only The passed message type is invalid, on all three distros.

Two fixes worked. Moving the stand-in to the end of PYTHONPATH was enough, because Python takes the first match. Removing it from the path also worked. On a real machine that means:

# which std_msgs does Python import?
python3 -c "import std_msgs.msg as m; print(m.__file__)"
# should be under /opt/ros/<ros2 distro>/ or your ROS 2 install/, not /opt/ros/noetic/

echo $PYTHONPATH | tr ':' '\n'      # ROS 2 folders must come before any ROS 1 folder

Then remove source /opt/ros/noetic/setup.bash from ~/.bashrc and open a new terminal. Or source ROS 2 last in a shell that needs both. In the rosgpt issue the user had exactly this problem, with Noetic sourced in .bashrc. The fix there was to source Foxy instead. If you see ROS_DISTRO was set to 'noetic' before when you source a ROS 2 workspace, both distros are in that shell.

Some messages have no ROS 2 version at all, for example a custom ROS 1 message from a catkin workspace. For those, the fix is a ROS 2 interface package with the same .msg file, built with colcon. Sourcing order can't fix it.

Cause 2: a name in your file replaced the message class

This cause has nothing to do with ROS 1. Python names are just variables, and the last import or class definition wins. Three versions of it failed in my runs.

An import with the same name. Image code often needs both sensor_msgs.msg.Image and PIL's Image. If both are imported as Image, the later import wins. With PIL imported second, Image was <module 'PIL.Image' ...> and create_subscription(Image, ...) failed with type object 'module'. Importing PIL with an alias fixed it on all three distros:

from sensor_msgs.msg import Image
from PIL import Image as PILImage    # not "from PIL import Image"

Your own class with the same name. If you name the node class after its service, the class statement replaces the import:

from example_interfaces.srv import AddTwoInts

class AddTwoInts(Node):               # now AddTwoInts is the node class
    def __init__(self):
        super().__init__('adder')
        self.create_service(AddTwoInts, 'add', self.cb)   # fails

This failed with type object 'type' on Humble and Jazzy and type object 'AddTwoInts' on Lyrical. The fix is to give the node class another name, such as AdderNode, or to import the service with an alias. In the WhereGo question the node class and the .srv file were both named WhereGo, and renaming the service fixed it. That fits the same rule.

A module instead of a class. from std_msgs import msg followed by create_publisher(msg, ...) failed with type object 'module'. Import the class, from std_msgs.msg import String, and pass String.

Cause 3: a string or an instance instead of the class

rclpy takes the class object, not its name. create_publisher('std_msgs/msg/String', 'chatter', 10) failed with type object 'str'. So did ActionClient(node, 'example_interfaces/action/Fibonacci', 'fibonacci'), the mistake a commenter describes on the same question. Import the class and pass it:

from example_interfaces.action import Fibonacci
client = ActionClient(node, Fibonacci, 'fibonacci')

If you only have the type name as a string, for example from a parameter, rosidl_runtime_py.utilities.get_message('std_msgs/msg/String') returns the class. I didn't time or test that helper in these runs.

An instance (String() instead of String) behaved differently across versions. On Humble and Jazzy, create_publisher(String(), ...) worked and returned a publisher. The first publish() then failed with TypeError: isinstance() arg 2 must be a type, a tuple of types, or a union, from rclpy/publisher.py line 69. On Lyrical the call failed right away with 'String' object has no attribute '_TYPE_SUPPORT'. Either way, remove the parentheses.

Cause 4: a plain Python class as an action, service or message

ROS 2 types come from .msg, .srv and .action files, which rosidl turns into Python and C code at build time. A Python class with the same fields isn't enough. With class MotorsGoal holding one target_pwm field, ActionServer(node, MotorsGoal, 'motors', cb) failed with type object 'type' on Humble and Jazzy and type object 'MotorsGoal' on Lyrical. That is what happened in the simple action implementation question.

The fix is an interface package: an ament_cmake package with an action/Motors.action file and rosidl_generate_interfaces. Build it with colcon, source the install, then from my_interfaces.action import Motors. For a quick test, the existing example_interfaces types (Fibonacci, AddTwoInts) work.

Version notes

  • Humble (rclpy 3.3.22) and Jazzy (rclpy 7.1.12) run msg_or_srv_type.__class__._TYPE_SUPPORT at line 20 of type_support.py. Because the check looks at __class__, the message names the type of what you passed: 'type', 'module' or 'str'.
  • Lyrical (rclpy 10.0.11) runs msg_or_srv_type._TYPE_SUPPORT at line 93. The message names the object itself ('AddTwoInts', 'PIL.Image', 'str' object). The extra frame _create_publisher_handle (or _create_service_handle) shows up in the traceback.
  • Because of that change, Lyrical rejects a message instance at create_publisher. Humble and Jazzy accept it and fail at the first publish().
  • The text about ROS 1 is the same in all three, even though no supported ROS 1 distro installs next to Jazzy or Lyrical.
  • ActionClient with a message type crashed the process with a segmentation fault (exit code 139) on all three. Look for that if a Python node dies with no traceback.
  • ros2 topic pub and ros2 topic echo with the shadowed std_msgs printed The passed message type is invalid on ros2cli 0.18.20, 0.32.13 and 0.40.9.

FAQ

What does "has no attribute '_TYPE_SUPPORT'" mean in rclpy?

rclpy checks that the type you pass to create_publisher, create_subscription, create_service, create_client or an action class is a generated ROS 2 interface class. Anything else fails that check. In my runs that included ROS 1 style classes, modules, strings, hand-written classes and, on Lyrical, message instances.

I never installed ROS 1. Why does the error mention it?

The text is the same for every cause. Most often a name in your own file points to the wrong object. Examples are from PIL import Image after sensor_msgs.msg.Image, or a node class named like its service. Print the object and type() of it right before the call.

What does type object 'module' mean?

You passed a module. In my runs this happened with from PIL import Image replacing sensor_msgs.msg.Image, and with from std_msgs import msg. Import the message class, using an alias where names clash.

How do I check which std_msgs Python is using?

Run python3 -c "import std_msgs.msg as m; print(m.__file__)". It should point into your ROS 2 install. If it points into a ROS 1 folder, take ROS 1 out of ~/.bashrc or put the ROS 2 paths first on PYTHONPATH.

Can I define an action with plain Python classes?

No. A plain class failed in ActionServer on Humble, Jazzy and Lyrical. Write a .action file in an interface package, generate it with rosidl_generate_interfaces, build it with colcon and import the generated class.
