The same message with .hpp at the end (tf2_geometry_msgs/tf2_geometry_msgs.hpp: No such file or directory) has a different cause. I reproduced both on Humble, Jazzy and Lyrical.

Short answer: there are two separate problems. The .h header is gone on Jazzy and Lyrical. Humble still ships it, but it prints #warning This header is obsolete. The .hpp error means your CMake target isn't linked to tf2_geometry_msgs. On all three distros the header lives in a nested folder, /opt/ros/<distro>/include/tf2_geometry_msgs/tf2_geometry_msgs/. That folder only reaches the compiler through the link line. Calling find_package alone isn't enough. This combination built and ran on all three distros:

#include <tf2_geometry_msgs/tf2_geometry_msgs.hpp>
find_package(tf2_geometry_msgs REQUIRED)
add_executable(node src/node.cpp)
target_link_libraries(node rclcpp::rclcpp ${geometry_msgs_TARGETS} tf2_geometry_msgs::tf2_geometry_msgs)
<depend>tf2_geometry_msgs</depend>

cv_bridge works the other way round on Humble. ros-humble-cv-bridge 3.2.1 ships only cv_bridge/cv_bridge.h, so cv_bridge.hpp fails there. Jazzy and Lyrical ship only cv_bridge.hpp.

Cause 1: the .h header is gone on Jazzy and Lyrical

The header survey printed the following file lists:

Humble:
tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.h
tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.hpp
Jazzy:
tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.hpp
Lyrical:
tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.hpp

On Humble the .h file still works. It includes the .hpp and adds one line:

/opt/ros/DISTRO/include/tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.h:35:2: warning: #warning This header is obsolete, please include tf2_geometry_msgs/tf2_geometry_msgs.hpp instead [-Wcpp]

The Humble build succeeded and the node gave the right answer. With target_compile_options(node PRIVATE -Werror) the same code failed with error: #warning This header is obsolete ... [-Werror=cpp]. If your CI builds with -Werror on Humble, that's the failure you'll see.

The rename comes from ros2/geometry2 PR #418, which moved the code to tf2_geometry_msgs.hpp and left a deprecated .h. Humble still has that stub. Jazzy and Lyrical don't, so tutorials written for Foxy or ROS 1 break on them at the first line.

Humble prints the same #warning for tf2_eigen/tf2_eigen.h and tf2_sensor_msgs/tf2_sensor_msgs.h. Two of the 35 .h files under tf2, tf2_ros, tf2_geometry_msgs and tf2_eigen carry it, and tf2_sensor_msgs.h is the third. On Jazzy none of the 33 .h files in those packages had a #warning or #pragma message. On Lyrical 13 of the 15 remaining .h files did, all in tf2_ros, for example tf2_ros/buffer.h: #pragma message(BUFFER_HEADER_DEPRECATION). If you still include tf2_ros/buffer.h or tf2_ros/transform_listener.h, Lyrical's deprecation messages are the next thing you'll hit. I didn't test whether they fail a -Werror build.

Cause 2: the .hpp exists but the target isn't linked

This is the one that confuses people, because the file is right there on disk. The header is not at /opt/ros/<distro>/include/tf2_geometry_msgs/tf2_geometry_msgs.hpp. It's one level deeper, under include/tf2_geometry_msgs/tf2_geometry_msgs/. For #include <tf2_geometry_msgs/tf2_geometry_msgs.hpp> to resolve, the compiler needs -I/opt/ros/<distro>/include/tf2_geometry_msgs. I read the include flags CMake wrote into flags.make for three of the cases:

t01_ok_hpp:      /opt/ros/DISTRO/include/tf2_geometry_msgs
t05_find_nolink: (nothing for tf2_geometry_msgs)
t08_opt_include: -I/opt/ros/DISTRO/include

That output explains three failures in the table:

  • No find_package, no link (t04). Nothing adds the path. The result is the .hpp fatal error.
  • find_package but no link (t05). find_package(tf2_geometry_msgs REQUIRED) succeeds and defines the target, but nothing attaches it to your executable. Same fatal error. This is the case in the Stack Overflow question with 7,294 views and no accepted answer.
  • include_directories(/opt/ros/$ROS_DISTRO/include) (t08). This adds the parent folder, so the compiler looks for /opt/ros/<distro>/include/tf2_geometry_msgs/tf2_geometry_msgs.hpp. That file doesn't exist, and you get the same fatal error.

Copying the real on-disk path into the include (t13, tf2_geometry_msgs/tf2_geometry_msgs/tf2_geometry_msgs.hpp) also failed on all three. The doubled folder is part of the install layout, not part of the include name.

Cause 3: include dirs without the library

The probe printed what find_package exports, and it was the same on all three distros:

tf2_geometry_msgs_INCLUDE_DIRS=/opt/ros/DISTRO/include/tf2_geometry_msgs;/opt/ros/DISTRO/include/geometry_msgs;/usr/include/eigen3;/opt/ros/DISTRO/include/tf2;/opt/ros/DISTRO/include/tf2_ros
tf2_geometry_msgs_TARGETS=tf2_geometry_msgs::tf2_geometry_msgs
target tf2_geometry_msgs::tf2_geometry_msgs exists

In t07 I added ${tf2_geometry_msgs_INCLUDE_DIRS} to the target with target_include_directories. The .hpp error went away and compilation finished, but linking failed:

undefined reference to `KDL::Rotation::Quaternion(double, double, double, double)'
collect2: error: ld returned 1 exit status

The header is not header-only. tf2::doTransform for a PointStamped goes through tf2::gmTransformToKDL, which needs orocos_kdl at link time. Linking the target brings in the include path and the libraries together. That's why the cases that link with tf2_geometry_msgs::tf2_geometry_msgs (t01) or ${tf2_geometry_msgs_TARGETS} (t09) both worked.

Cause 4: buffer.transform() without the header

t10 included only the tf2_ros buffer header and called buffer.transform(point, "base_link"). It compiled with no error. The linker then failed inside tf2_ros::BufferInterface::transform<geometry_msgs::msg::PointStamped>, three lines of /usr/bin/ld: node.cpp:(.text._ZNK7tf2_ros15BufferInterface9transformIN13geometry_msgs3msg13PointStamped... followed by collect2: error: ld returned 1 exit status. My log cut those lines at 260 characters, so I can't quote the missing symbol name. What matters is that the template is declared but its PointStamped version lives in tf2_geometry_msgs.hpp. t11 added that include and the link, and it built and ran on all three. If you hit an undefined reference that mentions BufferInterface::transform or doTransform, the fix is the same .hpp include and link.

One side note from t11. On Humble the run printed [ERROR] [tf2_buffer]: Do not call canTransform or lookupTransform with a timeout unless you are using another thread for populating data. before the correct result. Jazzy and Lyrical didn't print it. The transformed value was the same, x=1.50, on all three.

cv_bridge.h and cv_bridge.hpp

cv_bridge.h not found ROS2 (1,940 views) is the same kind of problem with a twist. Here is what each distro shipped after apt-get install:

Humble  ros-humble-cv-bridge 3.2.1    cv_bridge/cv_bridge/cv_bridge.h
Jazzy   ros-jazzy-cv-bridge 4.1.0     cv_bridge/cv_bridge/cv_bridge.hpp
Lyrical ros-lyrical-cv-bridge 4.1.0   cv_bridge/cv_bridge/cv_bridge.hpp

On Humble only .h exists, and there was no deprecation warning in it. So on Humble #include <cv_bridge/cv_bridge.hpp> fails with fatal error: cv_bridge/cv_bridge.hpp: No such file or directory, even when find_package(cv_bridge REQUIRED) and target_link_libraries(node ... cv_bridge::cv_bridge) are correct. On Jazzy and Lyrical cv_bridge.h fails the same way. In my runs cv_bridge 3.2.1 had only the .h and 4.1.0 had only the .hpp. Use .h on Humble and .hpp on Jazzy and Lyrical, or wrap it in __has_include.

The other cv_bridge failures looked like the tf2 ones:

  • Not installed, with find_package(cv_bridge REQUIRED): CMake Error at CMakeLists.txt:7 (find_package): By not providing "Findcv_bridge.cmake" in CMAKE_MODULE_PATH ... on all three.
  • Not installed, no find_package: fatal error: cv_bridge/cv_bridge.hpp: No such file or directory on all three.
  • Installed, find_package but not linked: the same fatal error on all three.
  • Installed, linked, right suffix for the distro: built and printed RESULT 6x4 bgr8.

ros-base doesn't include cv_bridge. In a Dockerfile or CI image, install it with apt-get install ros-$ROS_DISTRO-cv-bridge or rosdep install --from-paths src --ignore-src -y.

FAQ

Why does tf2_geometry_msgs.h work on Humble but not on Jazzy?

Humble still ships a deprecated tf2_geometry_msgs.h that includes the .hpp and prints #warning This header is obsolete. Jazzy and Lyrical only ship tf2_geometry_msgs.hpp. Change the include to .hpp and it builds on all three.

The .hpp file exists in /opt/ros. Why can't the compiler find it?

It's installed one folder deeper, in include/tf2_geometry_msgs/tf2_geometry_msgs/. That folder is added only when your target links tf2_geometry_msgs::tf2_geometry_msgs (or ${tf2_geometry_msgs_TARGETS}). find_package without a link, or include_directories(/opt/ros/$ROS_DISTRO/include), gave the same fatal error in my runs.

Is find_package(tf2_geometry_msgs REQUIRED) enough?

No. It only defines the target. With find_package and no target_link_libraries or ament_target_dependencies, all three distros failed with tf2_geometry_msgs.hpp: No such file or directory.

I fixed the include and now get undefined reference to KDL::Rotation::Quaternion. Why?

You added the include directories but didn't link the library. tf2_geometry_msgs.hpp uses orocos_kdl, so the linker needs the target. Replace the include-directory line with target_link_libraries(node tf2_geometry_msgs::tf2_geometry_msgs).

Should I include cv_bridge.h or cv_bridge.hpp?

On Humble, cv_bridge.h. Version 3.2.1 has no .hpp. On Jazzy and Lyrical (4.1.0), cv_bridge.hpp, because there is no .h. cv_bridge isn't in ros-base, so install ros-$ROS_DISTRO-cv-bridge first.
