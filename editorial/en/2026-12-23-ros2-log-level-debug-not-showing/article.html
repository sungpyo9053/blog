RCLCPP_DEBUG(get_logger(), "MARK node debug %d", i);   // prints nothing
self.get_logger().debug('MARK node debug %d' % i)      # prints nothing

terminate called after throwing an instance of 'rclcpp::exceptions::RCLInvalidROSArgsError'
  what():  failed to initialize rcl: Couldn't parse log level: '--log-level verbose'. Error: Argument does not use a valid severity level, at ./src/rcl/arguments.c:1858, at ./src/rcl/arguments.c:441

ros2: error: unrecognized arguments: --ros-args --log-level debug

The first two lines are the usual symptom: no error, just no output. The other two are what you get on the way to fixing it, from an invalid level name and from putting --ros-args on ros2 launch itself.

Short answer: every ROS 2 logger starts at INFO, so RCLCPP_DEBUG and get_logger().debug() are dropped until you lower the level for that logger. Pass the logger's name, not the node's code name, after --ros-args:

ros2 run my_pkg my_node --ros-args --log-level my_node:=debug

In a launch file, give each flag its own list item:

Node(package='my_pkg', executable='my_node', output='screen',
     arguments=['--ros-args', '--log-level', 'my_node:=debug'])
# or, the same thing:
Node(package='my_pkg', executable='my_node', output='screen',
     ros_arguments=['--log-level', 'my_node:=debug'])

The logger name is the node's name after remapping, with the namespace in front and dots instead of slashes. A node started with name='my_name' in launch logs as my_name. A node in namespace /robot1 logs as robot1.my_node. If the name in --log-level doesn't match, nothing tells you. The node just stays at INFO. Both rules held in rclcpp and rclpy on Humble, Jazzy and Lyrical.

What I ran

On 2026-11-05 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, with the default RMW (Fast DDS). One ament_cmake package held three executables:

  • lv_cpp, an rclcpp node named lv_cpp.
  • lv_py.py, an rclpy node named lv_py.
  • lv_cpp_min, the same C++ source built with RCLCPP_LOG_MIN_SEVERITY=RCLCPP_LOG_MIN_SEVERITY_INFO.

Each node logs one INFO line with its logger name and whether DEBUG is enabled. Then it logs four marker lines: a DEBUG and an INFO on the node logger, a DEBUG on a child logger (get_child("plugin")), and a DEBUG on an unrelated logger named my_lib. The child logger stands in for a plugin or a helper class. The unrelated one stands in for a library that gets its logger with rclcpp::get_logger("my_lib"). I started each node with ros2 run under 18 argument and environment variants. Then I ran 13 launch files and a runtime test through the logger services, and counted the marker lines on stdout, stderr and in the log file under ROS_LOG_DIR.

Results for ros2 run, counts of marker lines (node debug / child debug / my_lib debug), the same in C++ and Python on all three distros:

The logger name is not always the name in your code

The node logger is named after the node, and the namespace and remaps are applied before the name is built. My C++ node printed logger_name=lv_cpp when run plain, logger_name=robot1.lv_cpp with -r __ns:=/robot1, and logger_name=my_name with -r __node:=my_name. The Python node did the same. A launch name='my_name' works the same way. Launch passes it as a -r __node:= remap, which you can see in the command line quoted in this question. With name='my_name' and --log-level lv_cpp:=debug, the node printed logger_name=my_name debug_enabled=0 and no debug line. Changing it to my_name:=debug fixed it.

For a namespace, write the name with dots: robot1.lv_cpp. The slash form /robot1/lv_cpp:=debug was accepted without any error and did nothing. So did the bare node name when the node had a namespace.

If you are not sure of the name, log it once at INFO. In rclcpp that's get_logger().get_name(), and in rclpy get_logger().name. Or use the global form --log-level debug to confirm that your debug lines exist, then narrow it down.

This matters for the RCLCPP_DEBUG question from someone working on a Nav2 controller plugin. Plugins and helper classes often log through a logger they got from the node. In my run, a child logger followed its parent: lv_cpp:=debug also enabled lv_cpp.plugin. A logger made with rclcpp::get_logger("my_lib") did not follow the node. It needed its own my_lib:=debug. I didn't run Nav2 itself, so check which logger your plugin actually uses.

Global --log-level debug works, but it is noisy

The global form turns on every logger in the process, including the ROS client libraries. Apart from my four marker lines, the C++ node printed 85 DEBUG lines on Humble, 98 on Jazzy and 96 on Lyrical. The Python node printed 72, 81 and 88. All of that came from a node that only starts and exits.

You can combine levels. A Foxy question reports an error from --log-level DEBUG --log-level rcl:=INFO. On Humble, Jazzy and Lyrical that line worked. It cut the C++ extras from 85 to 30 on Humble, from 98 to 34 on Jazzy and from 96 to 41 on Lyrical. The reverse also worked: --log-level debug --log-level lv_cpp:=info kept my node at INFO and let my_lib through. A named level beat the global one in both directions.

Level names are case-insensitive: debug and DEBUG gave identical counts. A name that isn't a level stops the node before your code runs:

rclpy._rclpy_pybind11.RCLError: failed to initialize rcl: Couldn't parse log level: '--log-level verbose'. Error: Argument does not use a valid severity level, at ./src/rcl/arguments.c:1858, at ./src/rcl/arguments.c:441

The line numbers were arguments.c:1806 and :432 on Humble, :1858 and :441 on Jazzy, and :1860 and :441 on Lyrical. C++ printed the same text after terminate called after throwing an instance of 'rclcpp::exceptions::RCLInvalidROSArgsError', and ros2 run reported [ros2run]: Aborted with exit code 250.

--ros-args is required, and ros2 launch doesn't take it

ros2 run lv lv_cpp --log-level debug, without --ros-args, started normally, logged at INFO and gave no warning. rcl treats anything before --ros-args as the program's own arguments.

ros2 launch is the other way around. It is not a node, and ros2 launch file.launch.py --ros-args --log-level debug failed before anything launched:

ros2: error: unrecognized arguments: --ros-args --log-level debug

Exit code 2 on all three distros. On Lyrical the message ended at --log-level, without debug. This is the case in ros2/launch issue #383, which is still open. To set node levels from the command line, declare a launch argument and pass it through, as shown below.

ros2 launch -d is not a node log level either. It printed Default logging verbosity is set to DEBUG and then 16 to 19 [DEBUG] [launch] lines about launch itself. My node's debug line still didn't appear.

In a launch file: one list item per flag

arguments is a list of separate command-line words, and a string with spaces in it did not work as several words. The form from this question, arguments=['--ros-args --log-level DEBUG --'], didn't crash in my run. The process started, printed INFO only and process has finished cleanly, on all three distros. The question reports exit code -6 on an older distro, which I didn't test. Either way, the level isn't applied.

These worked on every distro, including Humble with launch_ros 0.19.14:

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        DeclareLaunchArgument('log_level', default_value='info'),
        Node(package='lv', executable='lv_cpp', output='screen',
             arguments=['--ros-args', '--log-level', LaunchConfiguration('log_level')]),
    ])

With no argument this logged at INFO. With ros2 launch ... log_level:=debug, all four marker lines appeared. ros_arguments=['--log-level', 'debug'] gave the same result as the arguments form for both the C++ and the Python node. With namespace='robot1', robot1.lv_cpp:=debug worked. With name='my_name', only my_name:=debug worked.

One thing to know when you look for the lines: with output='screen', all of the node's log lines came out on ros2 launch's stdout. Under ros2 run they went to stderr, INFO included. Setting RCUTILS_LOGGING_USE_STDOUT=1 moved every line to stdout under ros2 run. If you pipe output through grep, use 2>&1, or you'll see nothing and think the level is wrong. The -p and --params-file rules in the params YAML and -p errors post follow the same --ros-args placement as --log-level.

RCLCPP_LOG_MIN_SEVERITY is a compile-time switch

The same question mentions setting RCLCPP_LOG_MIN_SEVERITY=RCLCPP_LOG_MIN_SEVERITY_DEBUG in the shell. As an environment variable it changed nothing: the node stayed at INFO in C++ and Python. It is a preprocessor macro for rclcpp's logging header, so it only matters when your code is compiled.

In the other direction it can hide debug lines for good. lv_cpp_min was built with target_compile_definitions(lv_cpp_min PRIVATE RCLCPP_LOG_MIN_SEVERITY=RCLCPP_LOG_MIN_SEVERITY_INFO). Run with --log-level debug, it printed debug_enabled=1 for its own logger, plus the 85 to 98 DEBUG lines from the ROS libraries, and none of its own RCLCPP_DEBUG lines. The macro had compiled the calls out. If --log-level debug shows library debug lines but not yours, look for this definition in your CMakeLists.txt or a parent CMake file.

Changing the level in code or at runtime

In code, set the level on the node's logger:

node->get_logger().set_level(rclcpp::Logger::Level::Debug);   // rclcpp
self.get_logger().set_level(rclpy.logging.LoggingSeverity.DEBUG)  # rclpy

Both worked on all three distros. The child logger followed, my_lib stayed at INFO. It's a code change you have to remember to take out, so I'd use it only while debugging.

Jazzy and Lyrical can change levels on a running node through two services, if the node enables them. In rclcpp that's rclcpp::NodeOptions().enable_logger_service(true), in rclpy Node('name', enable_logger_service=True). With that on, ros2 service list showed /lv_cpp/get_logger_levels and /lv_cpp/set_logger_levels, and this call worked:

ros2 service call /lv_cpp/set_logger_levels rcl_interfaces/srv/SetLoggerLevels "{levels: [{name: lv_cpp, level: 10}]}"

Level 10 is DEBUG. The reply was successful=True. get_logger_levels returned level=0 (unset) before the call and level=10 after. My test node logged once every 0.2 s for 40 rounds. Its first debug line appeared at round 25 (C++ on Jazzy and Lyrical), 26 (Python on Jazzy) or 27 (Python on Lyrical). After that the node and its child logger printed debug lines, and my_lib didn't. The ros2 service call command took 1.0 s on Jazzy and 1.0 to 1.7 s on Lyrical.

On Humble none of this exists. rclpy 3.3.22 rejected the option with Node.__init__() got an unexpected keyword argument 'enable_logger_service'. For the C++ node I compiled the option out on Humble, guarded by RCLCPP_VERSION_MAJOR >= 21, and no logger services appeared in ros2 service list. ros2 service call answered The passed service type is invalid for rcl_interfaces/srv/SetLoggerLevels and GetLoggerLevels. On Humble, change levels with --log-level at startup or with set_level in code.

FAQ

Why doesn't RCLCPP_DEBUG print anything?

The default level for every logger is INFO. Run the node with --ros-args --log-level <logger>:=debug, where the logger is the node's name after remapping, with dots for the namespace. If even --log-level debug doesn't show your lines while library debug lines appear, check for RCLCPP_LOG_MIN_SEVERITY in your CMake files.

How do I set the log level of a node in a ROS 2 launch file?

Use arguments=['--ros-args', '--log-level', 'my_node:=debug'] or ros_arguments=['--log-level', 'my_node:=debug'] on the Node. Both worked on Humble, Jazzy and Lyrical. A single string like '--ros-args --log-level DEBUG' was silently ignored. To choose the level at launch time, pass a LaunchConfiguration in place of the level.

Why does --log-level my_node:=debug do nothing?

The name doesn't match the logger. With a namespace the logger is namespace.my_node, and with a launch name= or __node remap it's the new name. A wrong name gives no error. Log get_logger().get_name() once to see the real one.

Can I pass --ros-args --log-level to ros2 launch?

No. ros2 launch rejected it with ros2: error: unrecognized arguments and exit code 2. ros2 launch -d only turns on launch's own debug output. Declare a log_level launch argument and pass it to each node instead.

Can I change the log level while the node is running?

On Jazzy and Lyrical, yes. Enable the logger service in the node and call set_logger_levels with level 10 for DEBUG. My test node then printed debug lines for the rest of its run. On Humble the service doesn't exist, so use set_level() in code.
