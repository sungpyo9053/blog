for topic in ['/robot1/pose', '/robot2/pose', '/robot3/pose']:
    self.create_subscription(
        String, topic,
        lambda msg: self.listener_callback(msg, topic),
        10)

# what the callback reported after 20 messages on each topic:
sent_per_topic 20 received 60 label_matches_source 20 label_wrong 40
labels_seen {'/robot3/pose': 60}

There is no error message. Every message arrives, but every callback says it came from the last topic in the list. That's the output above, and it was the same on Humble, Jazzy and Lyrical.

Short answer: the lambda doesn't store the topic name. It looks up the variable topic when the callback runs, and by then the loop has finished and topic holds the last value. This is plain Python late binding, not a ROS bug. Bind the value when you create the subscription. Any of these gave 60 out of 60 correct labels on all three distros:

import functools

for topic in topics:
    # 1. default argument: the value is copied when the lambda is created
    self.create_subscription(String, topic,
        lambda msg, t=topic: self.listener_callback(msg, t), 10)

    # 2. functools.partial: also copies the value now
    self.create_subscription(String, topic,
        functools.partial(self.listener_callback, topic=topic), 10)

In C++ the trap is different. A subscription you don't keep a SharedPtr to is destroyed at once and never receives anything. In rclpy you don't need to keep the return value, but you do need it later if you want to unsubscribe with destroy_subscription().

What I ran

One Python script creates a subscriber node with three std_msgs/String subscriptions in a loop, on /robot1/pose, /robot2/pose and /robot3/pose. A publisher node in the same process sends 20 messages on each topic. Each message carries the name of the topic it was sent on. The callback records that name and the topic name it was given. If the two match, the label is right. I ran six ways of building the callback: the plain lambda, a lambda with a default argument, a lambda with a keyword-only default, functools.partial, a small factory function, and the partial version without keeping the return value.

A second script tests destroy_subscription() in the same process, three runs per distro. A third splits publisher and subscriber into two processes. The publisher prints its matched subscription count with a wall-clock time every time it changes, polling every 10 ms. The subscriber listens for 3 s, destroys its subscription, and keeps spinning for 3 s more. About 0.8 s after the subscriber process exits, I ran ros2 topic info with the daemon and with --no-daemon. Three runs per distro.

The C++ test is one rclcpp package with three modes: subscriptions created in a loop without storing them, stored in a std::vector, and stored then released with reset() after 1 s of traffic. Each container ran with --network none, ROS_DOMAIN_ID=88 and localhost-only discovery, 1.5 CPUs and 1500 MB of memory, using the default RMW (Fast DDS).

Why every callback gets the last topic

A Python lambda, like any nested function, keeps a reference to the variable, not a copy of its value. The three lambdas in the loop all point to the same topic variable. When a message arrives, the loop is long finished and topic is '/robot3/pose'. So every callback passes that string to listener_callback.

The subscriptions themselves are fine. Each one is on the right topic and gets its own messages. In the measured run all 60 messages were received, 20 from each topic. Only the label was wrong. The 20 "correct" labels were the messages that really came from /robot3/pose. The other 40 were mislabeled.

This matters for debugging. If you log only the label, it looks like two of the three topics are silent and the third is getting three times the traffic. Before you suspect QoS or discovery, log something from the message itself, such as msg.header.frame_id for a stamped type, or print the subscription's topic name. If the messages really don't arrive at all, the cause is somewhere else, and an incompatible QoS between publisher and subscriber is a common one.

Passing the topic name into the callback: fixes compared

Every fix binds the value at the moment the subscription is created. Here are the results, 60 messages sent each time:

The numbers were identical on Humble, Jazzy and Lyrical.

I tested the default-argument form on purpose. It gives the callback two parameters, and I wanted to see whether rclpy would fill the second one with something else. It didn't. On all three distros the default value stayed in place and every label was correct. The keyword-only version, with * before t, did the same. If you want to be safe from a caller ever passing a second positional argument, the keyword-only form or functools.partial with a keyword (topic=topic) protects you. Those values can't be overwritten by position.

Which one to pick is a matter of style. functools.partial is the clearest when the callback is a method. The factory function is the most explicit, because the value lives in its own scope. The default-argument lambda is the shortest, but it's the one a later reader is most likely to "clean up" into the broken form. If you go with it, add a comment.

Python 3.10, 3.12 and 3.14 shipped with the three images, and all behaved the same. Late binding is part of the language, so no distro or rclpy version changes it.

Do you need to store the subscription?

In rclpy, no. The last row of the table above dropped the return value of create_subscription and still got all 60 messages. The node keeps every subscription it creates until you destroy it or the node.

In rclcpp, yes. create_subscription returns a SharedPtr, and the node doesn't keep a strong reference. If you drop the return value, the subscription is destroyed at the end of that statement:

for (const auto & topic : topics) {
  // dropped: destroyed right away
  node->create_subscription<String>(topic, 10, cb);

  // kept: works
  subs_.push_back(node->create_subscription<String>(topic, 10, cb));
}

Measured results for the C++ modes, the same on all three distros:

Nothing is printed when this happens. No warning, no error, just a subscription that isn't there. If a C++ subscriber created in a loop or in a helper function never fires, check this first.

C++ doesn't have the late binding problem. My callback was [&, topic](const String & msg) {...}, which copies topic into each lambda when it is created, and all 60 labels were right. If you capture the loop variable by reference instead, each lambda refers to a variable that no longer exists after the loop. I didn't measure that case, because what it does is undefined behavior and not something to rely on either way.

Unsubscribing: destroy_subscription and reset()

ROS 2 has no unsubscribe(). In rclpy you call node.destroy_subscription(sub), which is why you keep the return value after all. In rclcpp you release the SharedPtr, for example with sub.reset() or by erasing it from your container. The subscription goes away when the last copy is released.

It never showed a stale subscription count of 1. But four of the 18 CLI calls printed Unknown topic '/xproc_topic' instead, even though the publisher was still running. That was Jazzy run 1 (with and without the daemon), Jazzy run 2 with --no-daemon, and Lyrical run 1 with the daemon. That's the CLI not finishing discovery in time, not the topic being gone. If ros2 topic info or ros2 topic list gives a strange answer right after nodes start or stop, run it again before you draw conclusions.

One more thing about "topics that persist". A topic exists in the graph while any publisher or subscription on it exists, anywhere. After you destroy your subscription, the topic is still listed as long as the other side is alive. In my test, Publisher count: 1 stayed because the publisher process was still running. That isn't a leaked subscriber.

All my tests created, used and destroyed subscriptions on the thread that spins the executor.

FAQ

Why do all my rclpy subscriptions created in a loop report the same topic?

The lambda reads the loop variable when the callback runs, not when it was created. By then it holds the last topic. In my test, 60 messages from three topics were all labeled with the third topic. Bind the value with lambda msg, t=topic:, functools.partial or a factory function.

How do I pass the topic name to a ROS 2 Python callback?

Use functools.partial(self.callback, topic=topic), or a lambda with a default argument, lambda msg, t=topic: self.callback(msg, t). Both gave 60 of 60 correct labels on Humble, Jazzy and Lyrical. rclpy left the default argument alone.

How do I unsubscribe from a topic in ROS 2?

In rclpy, call node.destroy_subscription(sub). In rclcpp, release the last SharedPtr, for example with sub.reset(). In both cases no message arrived afterwards, and the publisher's matched count was 0 at the next check.

Why does my rclcpp subscription never receive messages?

If you didn't store the SharedPtr that create_subscription returns, the subscription is destroyed right away. It received 0 of 60 messages and the publisher saw 0 subscribers. Keep it in a member variable or a container.

Does an rclpy subscription get garbage collected if I don't keep it?

No. With the return value thrown away, the subscriptions still received all 60 messages on every distro. The node holds a reference until you destroy the subscription or the node.
