[WARN] [1795311336.163220434] [fib_server.action_server]: Goal state not set, assuming aborted. Goal ID: [ 88 227 164  57 211 177  78 136 191 214  37 106 177 195 185 224]

That warning comes from an rclpy action server whose execute callback returned without calling succeed(), abort() or canceled(). The client gets status 6, ABORTED. The same server code often has a second problem: goals that keep running after the client cancels them. The cancel response then shows up seconds late, with return_code=3 and an empty goals_canceling list.

Short answer: a cancel only works in rclpy when three things are true. The server passes a cancel_callback that returns CancelResponse.ACCEPT, because the default one returns REJECT on Humble, Jazzy and Lyrical. The server spins with a MultiThreadedExecutor, so the cancel request can be served while the execute callback is still running. And the execute loop checks goal_handle.is_cancel_requested, then calls goal_handle.canceled() and returns a result. Every execute path has to end with one of succeed(), abort() or canceled(), and has to return a result object, never None. This is a trimmed version of the test server variant that canceled within half a second in every run:

import time
import rclpy
from rclpy.action import ActionServer, CancelResponse
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor
from rclpy.node import Node
from tf2_msgs.action import LookupTransform as Act   # any action type works the same way

class Server(Node):
    def __init__(self):
        super().__init__('fib_server')
        ActionServer(self, Act, 'fib', self.execute,
                     cancel_callback=lambda goal_handle: CancelResponse.ACCEPT,
                     callback_group=ReentrantCallbackGroup())

    def execute(self, goal_handle):
        for i in range(10):
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()
                return Act.Result()
            goal_handle.publish_feedback(Act.Feedback())
            time.sleep(0.5)                 # the real work
        goal_handle.succeed()
        return Act.Result()

rclpy.init()
ex = MultiThreadedExecutor(num_threads=4)
ex.add_node(Server())
ex.spin()

What I ran

On 2026-11-22 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one container per distro, with networking off. The base images ship only one action type, tf2_msgs/action/LookupTransform, so the test server uses it as a generic action. The result's frame_id carries the number of finished steps, so I could tell a canceled goal from a finished one.

One Python script, ac.py, is either the server or the client. The server runs in one process, the client in another, in the same container. The execute callback does 10 steps of time.sleep(0.5) and publishes feedback after each step, so a goal takes 5 s. The client sends a goal and, depending on the case, sends cancel_goal_async() 1 s later or a second goal 1 s later. It logs the goal response, the cancel response and the result with timestamps, and how long each response took after its request. I ran 14 server variants twice per distro, 84 runs in total. The two repetitions gave the same outcome in every case.

I also printed the source of rclpy's default callbacks on each distro. All three contain the same body:

def default_cancel_callback(cancel_request):
    """No cancellations."""
    return CancelResponse.REJECT

On Lyrical the parameter is named goal_handle and has type hints. The return value is the same.

Cause 1: the server can't see the cancel request

This is the case behind most "cancel does nothing" questions. With a plain rclpy.spin(node), one thread runs every callback of the node. The execute callback holds that thread for the whole goal. The cancel request is a service call to the server, and it waits in the queue until execute returns.

I tested three server versions on a single-threaded executor: no cancel_callback, a cancel_callback that accepts and a loop that never checks, and the full version that accepts and checks is_cancel_requested every step. All three gave the same result in all 18 runs (3 versions, 3 distros, 2 repetitions):

  • The cancel callback never ran while the goal was executing. My log line inside it never printed.
  • is_cancel_requested stayed False, so the loop ran all 10 steps.
  • The goal ended with status 4, SUCCEEDED, after 10 steps and 10 feedback messages.
  • The cancel response reached the client 4.00 to 4.25 s after it was sent, at the same moment as the result. It said return_code=3, which is ERROR_GOAL_TERMINATED, with an empty goals_canceling list.

So code that looks right can't cancel anything on a single-threaded executor. The return code also points in the wrong direction. It says the goal was already finished, which is true by the time the request was read. If you see code 3 for a goal that was clearly still running when you canceled it, check the executor first.

The fix is a MultiThreadedExecutor. I tried it with the action server in a ReentrantCallbackGroup and with no group argument at all (the node's default group). Both canceled. The cancel callback ran on a second thread about 1 s after the goal started, the cancel response arrived within 0.01 s with return_code=0 and goals_canceling=1, the loop saw is_cancel_requested at step 3, and the client got status 5, CANCELED, 0.50 s after it sent the cancel. That held on all three distros in both repetitions. I use the reentrant group anyway, because it's the setting that also lets a second goal run, as shown below.

This is the same family of problems as service calls that hang inside callbacks. My rclpy and asyncio post measured that an awaited call_async() hung on a single-threaded executor in every setup except one with a ReentrantCallbackGroup. The pattern is the same here. One thread can't serve a request while it waits inside another callback.

Cause 2: the default cancel callback rejects

On a MultiThreadedExecutor with no cancel_callback, the cancel response came back at once, 0.00 s after sending. It said return_code=0, which is ERROR_NONE, with goals_canceling=0. The goal ran on and ended SUCCEEDED after 10 steps.

Note that the code was not 1. The action_msgs service defines ERROR_REJECTED = 1, and my client printed that constant on every distro. But the rclpy server answered with code 0 in all 6 runs. The only sign of the rejection was the empty list. A client that checks only return_code == 0 reports success for a cancel that never happened. Check len(response.goals_canceling) instead.

The fix is a one-line callback:

from rclpy.action import CancelResponse

ActionServer(node, Act, 'fib', execute,
             cancel_callback=lambda goal_handle: CancelResponse.ACCEPT)

Without a callback, every cancel is refused.

Cause 3: accepted, but the loop never checks

Accepting the cancel only moves the goal to CANCELING. Nothing stops your code. In the variant with a multithreaded executor, an accepting callback and no is_cancel_requested check, the cancel response said goals_canceling=1 within 0.01 s. The loop still ran all 10 steps, and succeed() worked from the CANCELING state. The client got status 4, SUCCEEDED, about 5 s after the goal started.

Lyrical differed in one detail. After the cancel was accepted, every publish_feedback() call printed this warning, and the client stopped getting feedback:

[WARN] [1795311893.841319032] [fib_server.action_server]: publish_feedback() called on a goal handle not in executing state, ignoring

The Lyrical client received 3 feedback messages in this case, against 10 on Humble and Jazzy. So on Lyrical a goal that ignores the cancel goes silent and then reports SUCCEEDED. That can look like a hang from the client side.

The fix is the check in the short answer. Read goal_handle.is_cancel_requested at least once per step, stop the work, call goal_handle.canceled() and return a result. In my runs the check fired at step 3, and the partial result (steps=3) reached the client with status CANCELED.

Cause 4: one goal at a time

Several questions describe an action server that "doesn't accept new goals". In my runs the second goal was never rejected. It waited. On a single-threaded server the second goal's response came 4.00 to 4.01 s after it was sent, which is when the first goal finished. Both results then arrived together, 10.01 to 10.02 s after the first goal was accepted. The second goal ran only after the first one was done.

With a MultiThreadedExecutor and a ReentrantCallbackGroup, the second goal was accepted within 0.01 s, both execute callbacks ran at once on different threads, and the two results arrived 1 s apart, matching the 1 s gap between the goals. If your server should run only one goal at a time, that's a policy you write in a goal_callback or handle_accepted_callback. I didn't test those.

A related surprise is two servers with one action name. My post on duplicate node names measured that two copies of the same action server both executed most of 10 goals. If goals seem to run twice, or a cancel reaches the wrong copy, check ros2 action info for more than one server.

Cause 5: "Goal state not set, assuming aborted"

rclpy prints this warning when the execute callback returns and the goal is still EXECUTING. It then sets ABORTED itself. I hit it in three ways, on all three distros:

Execute callback did thisServer logClient got
Returned a result without any state callGoal state not set, assuming abortedstatus 6 ABORTED, with the returned result (steps=10)
Called canceled() with no cancel requestRCLError: Failed to update goal state: goal_handle attempted invalid transition from state EXECUTING with event CANCELED, then the warningstatus 6 ABORTED
Raised RuntimeErrorError raised in execute callback: boom in execute with the traceback, then the warningstatus 6 ABORTED, empty result

The client always got its result. The status is what changed. If your client reports ABORTED and the server code never calls abort(), search the server log for this warning. Then look for a return path without a state call, or for an exception just before it.

The second row is a common mistake. canceled() is only allowed after the client asked for a cancel and your callback accepted it. To stop a goal for your own reasons, such as a sensor failure or a timeout, call goal_handle.abort().

Calling succeed() twice raised invalid transition from state SUCCEEDED with event SUCCEED on the second call. The client still got SUCCEEDED, because the first call had already set it. The rcl source line in the message differed by distro: goal_handle.c:95 on Humble, :100 on Jazzy and :101 on Lyrical. The logger name differed too: [fib_server] on Humble, [fib_server.action_server] on Jazzy and Lyrical. Search for the message text, not the full line.

Cause 6: returning None kills the server

This one is worse than the warning. The execute callback called succeed() and then returned None. On Jazzy and Lyrical the server process died on a C assertion in the generated message code:

python3: ./.obj-x86_64-linux-gnu/rosidl_generator_py/tf2_msgs/action/_lookup_transform_s.c:337: tf2_msgs__action__lookup_transform__result__convert_from_py: Assertion `strncmp("tf2_msgs.action._lookup_transform.LookupTransform_Result", full_classname_dest, 56) == 0' failed.

That's the Jazzy text. Lyrical failed a different strncmp at line 326 of the same file. On Humble, executor.spin() raised AssertionError and the server stopped spinning. In all three the client got no result within 12 s. A forgotten return at the end of execute is enough to cause it, and nothing in the error names your callback. Always return the action's Result() object, even an empty one.

Version notes

  • The default cancel callback returns REJECT on Humble (rclpy 3.3.22), Jazzy (rclpy 7.1.12) and Lyrical (rclpy 10.0.11). Lyrical renamed its parameter to goal_handle.
  • A rejected cancel came back as return_code=0 with an empty list on all three, not as ERROR_REJECTED.
  • Only Lyrical drops feedback from a goal in CANCELING state and warns on every publish_feedback().
  • Returning None killed the process on Jazzy and Lyrical (C assertion). Humble raised AssertionError out of spin().
  • Logger name and rcl line numbers in the transition error differ, as listed above. The message text is the same.

FAQ

What does "Goal state not set, assuming aborted" mean?

The rclpy execute callback returned while the goal was still executing, so rclpy set it to ABORTED. In my runs that happened after a return without succeed(), after a failed canceled() call, and after an exception in the callback. The client got status 6 each time.

Why does my rclpy action goal not cancel?

Three causes, in the order I'd check them. The server spins a single-threaded executor, so the cancel request isn't served until the goal ends. The server has no cancel_callback, and the default rejects. Or the execute loop never reads is_cancel_requested. Fixing all three canceled the goal 0.50 s after the request on Humble, Jazzy and Lyrical.

Why does cancel_goal_async return code 3 for a running goal?

Code 3 is ERROR_GOAL_TERMINATED. On a single-threaded server the cancel request waited 4.00 to 4.25 s until the goal had finished, so by then it really was terminated. Use a MultiThreadedExecutor on the server.

Why does my action server not accept a second goal?

In my runs it accepted it later. A single-threaded server answered the second goal only after the first one finished, 4.00 s later. With a MultiThreadedExecutor and a ReentrantCallbackGroup, both goals were accepted at once and ran in parallel.

Can I call goal_handle.canceled() to stop a goal from the server?

Only after a cancel request was accepted. Without one, rclpy raised invalid transition from state EXECUTING with event CANCELED and the goal ended ABORTED. Use abort() to stop a goal on the server's own decision.
