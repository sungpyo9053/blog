rclpy._rclpy_pybind11.RCLError: Failed to publish: publisher's context is invalid, at ./src/rcl/publisher.c:389

If you log from the same place, you get a second line too: Failed to publish log message to rosout: publisher's context is invalid, at ./src/rcl/publisher.c:389. The line number is 389 on Humble, 423 on Jazzy and 427 on Lyrical. The rest of the text is the same.

Short answer: by the time your except KeyboardInterrupt: block runs, rclpy's own signal handler has already shut the context down, so any publish fails. If you want to send a last message, such as a zero velocity command, you have to keep the context alive yourself. In Python, start rclpy without its signal handlers, publish in the except block, wait for the message to be acknowledged, and then shut down. This worked in every run on Humble, Jazzy and Lyrical:

import signal
import rclpy
from rclpy.duration import Duration
from rclpy.signals import SignalHandlerOptions

def main():
    rclpy.init(signal_handler_options=SignalHandlerOptions.NO)
    # with NO, SIGTERM (kill, docker stop, launch) would kill the process outright
    def on_term(signum, frame):
        raise KeyboardInterrupt
    signal.signal(signal.SIGTERM, on_term)

    node = MyNode()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        node.pub.publish(stop_msg)                         # context is still valid here
        node.pub.wait_for_all_acked(Duration(seconds=1))   # let it leave the process
    finally:
        node.destroy_node()
        rclpy.try_shutdown()

In C++ the same fix is rclcpp::init(argc, argv, rclcpp::InitOptions(), rclcpp::SignalHandlerOptions::None) plus your own signal flag. A pre-shutdown callback also works there. C++ has a worse trap, though: a publish after Ctrl+C throws nothing, prints nothing and sends nothing.

What I ran

On 2026-11-04 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one container per distro, run one after another. A Python talker and a C++ talker each publish std_msgs/String "tick" on cmd at 10 Hz and try to publish "STOP" when they are stopped. A Python listener in a second process subscribes to cmd (reliable, depth 100) and prints every STOP it receives.

For each run the script starts the listener, waits 1.5 s, starts the talker, waits 2.5 s and sends SIGINT (what Ctrl+C sends) or SIGTERM (what kill, docker stop and launch's escalation send) to the talker. It then waits for the talker to exit, gives the listener 1 more second, and counts the STOP lines. The talker prints what happened at each step: which exception reached it, whether rclpy.ok() was still True, and whether publish() raised. The script runs 129 runs per distro: 14 variants, mostly 10 runs each, plus 20 runs of a 1 kHz timer case.

The script uses bash job control (set -m). Without it, bash starts background processes with SIGINT ignored, and Python then doesn't install its KeyboardInterrupt handler. A process started from a terminal behaves like the job control case. Keep this in mind if you test shutdown code from a script.

Why the publish fails in Python

When you call rclpy.init() with no options, rclpy installs handlers for SIGINT and SIGTERM. On Ctrl+C its handler shuts down the default context. Python's own handler then raises KeyboardInterrupt out of rclpy.spin(). Your except block runs after the context is gone. Every publisher, and the /rosout publisher that logging uses, belongs to that context, so publish() raises RCLError. My talker printed CAUGHT KeyboardInterrupt ok=False in 29 of 30 default runs across the three distros.

Logging behaves a little differently. get_logger().info("stopping") still printed [INFO] [...] [talker]: stopping on the console in every run. Only the copy to /rosout failed, which is the Failed to publish log message to rosout line. It is a message, not an exception, so your code keeps running. If all you want is a log line on Ctrl+C, you can ignore it. If you need the line in a bag or in rqt_console, it won't be there.

SIGTERM takes a different path. With the default handlers, SIGTERM made rclpy.spin() raise ExternalShutdownException on all three distros (3 of 3 each). It is not a KeyboardInterrupt, so a stop message placed in except KeyboardInterrupt is never even tried. Ctrl+C, kill and ros2 launch shutdown all take different paths through the same code. The earlier HuntLab article on Ctrl+C, SIGTERM and "rcl_shutdown already called" covers those exit paths and exit codes. This article only covers getting a message out.

context.on_shutdown() does not run on Ctrl+C

The obvious hook is node.context.on_shutdown(callback). In my runs the callback never ran: no publish attempt, no error, 0 of 10 on each distro. The talker still exited with code 0, so nothing tells you it was skipped. This matches ros2/rclpy#532, "rclpy Context.on_shutdown callbacks are not called when Ctrl-C is pressed". It was opened in 2020 and was still open when I checked on 2026-11-04. Even if it did run, the callback is tied to the shutdown itself, so it would be too late to publish.

Fix 1 (Python): SignalHandlerOptions.NO

rclpy.init(signal_handler_options=SignalHandlerOptions.NO) tells rclpy not to install its handlers. Python's default SIGINT handler is then the only one. Ctrl+C raises KeyboardInterrupt out of spin(), the context is still valid, and you decide when to shut it down. In every run with this option the talker printed ok=True, publish() succeeded, and the listener received the STOP message: 10 of 10 on each distro.

There is a catch. NO means no SIGTERM handler either, and Python doesn't install one. In my SIGTERM runs with NO and nothing else, the talker died at once with exit code 143. It printed nothing after READY. Its finally block never ran, and no stop message was sent (3 of 3, every distro). That is the signal you get from docker stop, systemd and launch's escalation. So add a SIGTERM handler. The one in the short answer raises KeyboardInterrupt, so both signals end up in the same except block. With it, SIGTERM runs delivered 10 of 10 on Jazzy and Lyrical and 9 of 10 on Humble. The tenth Humble run is the next section.

Fix 2 (Python): wait for the ack before you shut down

A successful publish() only means the message was handed to the middleware. If the process tears the node down right after, the message can still be lost. In one Humble run (SIGTERM, own handler) the talker printed PUBLISH_OK and exited cleanly, but the listener got nothing. Across the three SignalHandlerOptions.NO variants without an ack wait (30 runs per distro), 29 of 30 messages arrived on Humble and 30 of 30 on Jazzy and Lyrical.

Publisher.wait_for_all_acked(timeout) blocks until every reliable subscriber has acknowledged what was sent, or until the timeout. With it, 10 of 10 arrived on every distro and the call returned True every time. It took 0.675–0.806 s on Humble, 0.005–0.110 s on Jazzy and 0.005–0.006 s on Lyrical. I didn't look into why Humble is so much slower. Either way it fits inside launch's default 5 s SIGINT timeout. Use a timeout so a missing subscriber can't block your shutdown. The rcl documentation says it returns at once for a best-effort publisher. My publisher and listener were both reliable, so I didn't test that case.

The C++ trap: publish() after shutdown is silent

The same pattern in C++ (default rclcpp::init, publish after rclcpp::spin() returns) gave no exception and no error message in 30 of 30 runs. publish() returned normally. The listener received nothing in any of them. rclcpp does this on purpose. In publisher.hpp (Humble branch), when rcl_publish returns RCL_RET_PUBLISHER_INVALID and the context is no longer valid, it returns without throwing. The comment there reads // publisher is invalid due to context being shutdown. A C++ node that "publishes a stop command on Ctrl+C" this way has never sent one, and nothing in its output says so.

The only visible sign is the log line. RCLCPP_INFO right after the publish printed Failed to publish log message to rosout: publisher's context is invalid in 7 of 10 runs on Humble, 1 of 10 on Jazzy and 0 of 10 on Lyrical. So the warning is not reliable. On Lyrical you get no warning at all.

Fix options in C++

rclcpp::on_shutdown(callback) ran 10 of 10 times on each distro, but its publish reached the listener 0 times. The header says why: these callbacks run "as the second to last step in shutdown()", after the context is no longer usable for publishing.

add_pre_shutdown_callback on the context runs before that. Registered on the global context, it delivered 10 of 10 on all three distros, including Humble (rclcpp 16.0.21):

rclcpp::contexts::get_global_default_context()->add_pre_shutdown_callback(
  [pub]() {
    std_msgs::msg::String m;
    m.data = "STOP";
    pub->publish(m);
  });

The header notes that when shutdown comes from the signal handler, "these callbacks are run asynchronously in the dedicated signal handling thread". Your executor may still be running a callback on another thread at that moment, so protect shared state.

The other option matches the Python fix. Call rclcpp::init(argc, argv, rclcpp::InitOptions(), rclcpp::SignalHandlerOptions::None), set an atomic flag from std::signal handlers for SIGINT and SIGTERM, and loop on exec.spin_once(100ms) until the flag is set. Then publish, call pub->wait_for_all_acked(1000ms) and call rclcpp::shutdown(). That delivered 10 of 10 for SIGINT and 3 of 3 for SIGTERM on every distro. The ack returned true in 0.575–0.605 s on Humble and in 0.005–0.006 s on Jazzy and Lyrical. Of the two, this gives you the most control: the publish runs in your main thread, after the executor has stopped.

The timer race I couldn't reproduce

One archived ROS Answers question shows the same RCLError coming from inside a timer callback during rclpy.spin(), not from cleanup code. The theory is that a timer callback runs between the context shutdown and spin() returning. I tried to provoke it with a 1 kHz timer that publishes on every tick and a SIGINT after 2.5 s. In 20 runs per distro the traceback never appeared. That doesn't prove it can't happen, only that it was rare or absent in this setup. In 3 of 20 runs on Humble and Jazzy and 2 of 20 on Lyrical, rclpy.ok() was already False when KeyboardInterrupt reached the except block. In the rest it was still True. So the order of those two steps is not fixed. If a sensor callback in your node publishes, wrapping that one publish() in a try that ignores RCLError during shutdown is a reasonable guard. With SignalHandlerOptions.NO the context can't go away under a running callback, because only your code shuts it down.

Version notes

Every variant gave the same outcome on all three distros, with a few small differences, all on Humble. One default Python run on Humble got its message through by the race described above. Delivery without an ack wait lost 1 of 30 messages on Humble and none on Jazzy or Lyrical. Acknowledgements on Humble took about 0.6–0.8 s, against about 5 ms on the newer distros (one Jazzy Python run took 0.110 s). The C++ rosout warning showed up in 7, 1 and 0 of 10 runs. Some text changed too: the rcl line number in the error (389, 423, 427). And rclcpp's own signal log reads signal_handler(SIGINT/SIGTERM) on Humble and Jazzy but signal_handler(signum=2) on Lyrical. SignalHandlerOptions.NO, wait_for_all_acked and add_pre_shutdown_callback all existed and worked on Humble, so the fixes above don't need a newer distro.

One difference from the earlier HuntLab shutdown article: there, SIGTERM on Lyrical gave an RCLError about the wait set instead of ExternalShutdownException. In this setup Lyrical gave ExternalShutdownException in 3 of 3 SIGTERM runs. The nodes differ, and 3 runs is a small sample, so I don't read much into it.

Not tested

Nodes started through ros2 launch or ros2 run (signals were sent straight to the process), a real Ctrl+C in a terminal (the script used kill -INT with job control), Cyclone DDS and Zenoh, best-effort subscribers, SignalHandlerOptions.SIGINT or SIGTERM (install only one handler), lifecycle nodes, the multi-threaded executor, a stop message sent with wait_for_all_acked after SIGTERM in Python, SIGTERM for the C++ pre_shutdown and on_shutdown variants, and whether a robot driver acts on a single stop message. Don't rely on a stop message alone for safety. Use a command timeout in the driver as well.

FAQ

What does "publisher's context is invalid" mean?

The rcl context that owns the publisher has been shut down, usually by rclpy's signal handler after Ctrl+C or SIGTERM. Nothing created from that context can send messages. In my runs it happened in 29 of 30 default Python runs when publishing from except KeyboardInterrupt.

How do I publish a zero velocity command when my ROS 2 Python node is stopped?

Call rclpy.init(signal_handler_options=SignalHandlerOptions.NO), add a SIGTERM handler that raises KeyboardInterrupt, then publish in the except block, call wait_for_all_acked with a timeout, and only then shut down. That delivered the message in every run on Humble, Jazzy and Lyrical.

Why is my rclpy on_shutdown callback not called?

On Ctrl+C, context.on_shutdown callbacks did not run at all in 30 runs. This is the open rclpy issue #532. Put the cleanup in your own except or finally block instead.

Why does my C++ node not send its stop message, with no error?

After the context is shut down, rclcpp's publish() returns without throwing and without sending. Publish from add_pre_shutdown_callback, or use SignalHandlerOptions::None with your own signal flag. Publishing from rclcpp::on_shutdown delivered nothing in 30 runs.

Can I ignore "Failed to publish log message to rosout"?

Usually yes. The log line still printed on the console in every run. Only the copy to /rosout failed, so the line won't show up in bags or rqt_console.
