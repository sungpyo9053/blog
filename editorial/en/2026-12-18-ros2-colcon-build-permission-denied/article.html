Short answer: some or all of your workspace's log/, build/ and install/ folders belong to root. That's what sudo colcon build leaves behind, and so does a Docker container that builds as root on a bind-mounted workspace. Your normal user can't write there anymore. Give the workspace back to your user and build again without sudo:

cd ~/ros2_ws
sudo chown -R $USER:$USER .
colcon build

If the path in the CMake error starts with /lib/ or /share/ instead of your workspace, the cause is different. An install() line in your CMakeLists.txt uses an absolute path. Change DESTINATION /lib/${PROJECT_NAME} to DESTINATION lib/${PROJECT_NAME}, without the leading slash. Running sudo again "fixes" both cases in the sense that the build passes. But it leaves everything owned by root, and in the absolute-path case it puts your executable outside the workspace, where ros2 run can't find it.

What I ran

On 2026-11-04 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another. Each container ran as root and created a normal user dev (uid 1500). Root stood in for sudo colcon build: both run colcon as uid 0, so the files they create belong to root. The test workspace had two small packages. perm_cpp is ament_cmake with a one-file C++ executable. perm_py is ament_python with one console script. Every case started from a fresh copy of the workspace owned by dev. Then I changed one thing and ran colcon build --parallel-workers 1.

Cause 1: log/ belongs to root

This is the error most people hit, and it's the one in the rosflight and Isaac ROS issues. The first thing colcon build does is create a folder for this run's log, log/build_<date>. If log/ was created by root, that os.makedirs call fails and colcon stops. No Starting >>> line is printed and no package is touched. Running it again gives the same traceback.

A full sudo build makes all three folders root-owned, so you see the log/ error first. Delete log/ on its own and the build gets one step further, then fails on build/ and install/. That's why "I deleted the log folder and now there's a different error" is common. Each folder fails in its own place.

The root-built result is still readable. As dev, source install/setup.bash and ros2 run both worked in the root-owned workspace. The problem shows up only when you build again, which is why it often appears days after the sudo build.

Cause 2: build/ or install/ belongs to root

With only build/ root-owned, colcon couldn't write build/perm_cpp/colcon_command_prefix_build.sh. That file holds the environment for the CMake call. It's the same line as in the Livox driver issue. colcon then printed Could not find a shell extension for the command environment, which sounds like a broken colcon install but isn't one. It also couldn't write build/perm_cpp/colcon_build.rc, the file where it records the package's result.

With only install/ root-owned, the failure is in install/perm_cpp/share/colcon-core/packages/perm_cpp and in each install/local_setup.* file (.ps1, .sh, .bash, .zsh). Each of those gets its own traceback, so the output is long. The useful line is the last one, printed after the summary. In the Humble output the CMake step also printed file INSTALL cannot set permissions on "/ws3/install/perm_cpp/lib/perm_cpp/hello": Operation not permitted. The Jazzy and Lyrical output I kept is cut before that point, so I can't say if it appeared there too.

Cause 3: the workspace folder itself belongs to root

If you made the workspace with sudo mkdir, or copied it in with sudo, the user can read src/ but can't create anything next to it. colcon fails before any package with PermissionError: [Errno 13] Permission denied: 'log'. That's the path without a date, which is how you tell it apart from Cause 1. The fix is the same chown -R, run on the workspace folder.

Cause 4: an absolute install path

The Robotics Stack Exchange question shows file INSTALL cannot copy file ".../build/gesture_recognition/image_publisher_node" to "/lib/gesture_recognition/image_publisher_node": Permission denied. The target is /lib/..., not ~/ros2_ws/install/.... I reproduced exactly that text at the same line, cmake_install.cmake:60, by writing:

install(TARGETS hello DESTINATION /lib/${PROJECT_NAME})   # wrong: absolute
install(TARGETS hello DESTINATION lib/${PROJECT_NAME})    # right: relative to install/<pkg>

The error text depended on the history of /lib/perm_cpp:

  • Never built as root: file cannot create directory: /lib/perm_cpp. Maybe need administrative privileges.
  • Built once as root with the same source: file INSTALL cannot set permissions on "/lib/perm_cpp/hello": Operation not permitted.
  • Built once as root, then the source changed: file INSTALL cannot copy file ... Permission denied., the text from the question.

So "cannot copy file" to a system path points to the sequence in that question. The absolute path was there already, and a sudo build at some point created the target folder. As root the build "works". It wrote /lib/perm_cpp/hello, install/perm_cpp/lib did not exist, and ros2 run perm_cpp hello printed No executable found. A relative DESTINATION is the only fix. Delete the stray files in /lib/<pkg> afterwards.

The ament_python version of this mistake behaves differently. With ('/share/perm_py', ['package.xml']) in data_files, colcon-core fails at assert not os.path.isabs(dest) in colcon_core/task/python/__init__.py with a bare AssertionError, for root and for dev. It never gets to a permission check. Use 'share/' + package_name, no leading slash.

To avoid the problem with Docker, build as the same user that owns the bind-mounted folder, for example docker run --user $(id -u):$(id -g). Otherwise run the chown once at the end of the container's build step. If sudo colcon build also triggered "listing git files failed", that's a separate ownership check by git, covered in listing git files failed in ament_python packages.

All three images ship the same colcon: colcon-core 0.21.3, colcon-cmake 0.2.30 and colcon-ros 0.5.0. Every case passed or failed the same way on all three distros, with the same final error line. The differences:

  • CMake is 3.22.1 on Humble, 3.28.3 on Jazzy and 4.2.3 on Lyrical.   • Python is 3.10 on Humble and 3.14 on Lyrical, so Lyrical tracebacks have the ~~~^^^ markers and <frozen os> frames. The PermissionError line at the bottom is identical.

FAQ

Why does colcon build say Permission denied: 'log/build_...'?

The workspace's log/ folder was created by root, usually by sudo colcon build or a root Docker container. colcon makes a new log folder before it builds anything and can't do it there. Run sudo chown -R $USER:$USER on the workspace and build again without sudo.

Is it safe to run sudo colcon build?

The build passes, but every file in build/, install/ and log/ then belongs to root. The next build as your own user fails, and in my run it failed every time. There is no reason to build a normal workspace with sudo.

How do I fix "file INSTALL cannot copy file ... to /lib/...: Permission denied"?

An install() call in CMakeLists.txt uses an absolute path such as /lib/${PROJECT_NAME}. Remove the leading slash so the file goes into install/<pkg>/lib/<pkg>. Then delete the files that an earlier sudo build left in /lib/<pkg>. chown does not fix this one.

I deleted the log folder and now get a different Permission denied error. Why?

build/ and install/ are still root's. With log/ gone, colcon starts the package and fails on colcon_command_prefix_build.sh, colcon_build.rc or install/.../colcon-core/packages. Change the owner of the whole workspace, not one folder.

Can I build without sudo when I can't change the owner?

Yes. Give colcon fresh folders: colcon --log-base log_dev build --build-base build_dev --install-base install_dev, then source install_dev/setup.bash. That worked on all three distros. --log-base by itself did not.
