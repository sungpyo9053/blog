$ ros2 run cam_node cam
<ws>/install/cam_node/lib/cam_node/cam: error while loading shared libraries: libvendor.so.4: cannot open shared object file: No such file or directory
[ros2run]: Process exited with failure 127

Short answer: colcon build succeeded because the linker could see the library, and the copy of your node in build/ still knows where it is. ros2 run starts the copy in install/, and CMake strips that path when it installs the executable. The usual fix is to install every file of the prebuilt library into your package's lib folder, including the versioned ones, and to source the workspace again:

file(GLOB VENDOR_FILES ${PROJECT_SOURCE_DIR}/thirdparty/lib/libvendor.so*)
install(FILES ${VENDOR_FILES} DESTINATION lib)
colcon build && source install/setup.bash && ros2 run cam_node cam
[INFO] [t] [cam]: vendor_read()=42

If the node must also start without sourcing the workspace (a systemd unit, a copied install/ folder), add set_target_properties(cam PROPERTIES INSTALL_RPATH "$ORIGIN/..") as well. If the library lives outside your package, for example an SDK in /opt or libtorch in your home folder, set(CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE) worked. A library copied to /usr/local/lib needs sudo ldconfig. All of this behaved the same on Humble, Jazzy and Lyrical.

What I ran

On 2026-11-08 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, with no network. The script first builds a small "vendor SDK" with g++, laid out the way real SDKs ship. There is one real file and two symlinks:

libvendor.so -> libvendor.so.4
libvendor.so.4 -> libvendor.so.4.6.0
libvendor.so.4.6.0
vendor SONAME: [libvendor.so.4]

The ament_cmake package cam_node has one rclcpp executable, cam. It calls vendor_read() from the library, logs the result (42) and exits. Each case is its own workspace with a different CMakeLists.txt. The base version looks like the ones in the questions below:

find_library(VENDOR_LIB vendor HINTS ${PROJECT_SOURCE_DIR}/thirdparty/lib NO_DEFAULT_PATH)
add_executable(cam src/cam.cpp)
target_include_directories(cam PRIVATE ${PROJECT_SOURCE_DIR}/thirdparty/include)
target_link_libraries(cam rclcpp::rclcpp ${VENDOR_LIB})
install(TARGETS cam DESTINATION lib/${PROJECT_NAME})

For every case I recorded the RUNPATH of the build/ and install/ binaries with readelf -d, the files in install/cam_node/lib, and the result of ros2 run. I also ran the installed binary directly, both with the workspace sourced and with only /opt/ros sourced. Every colcon build succeeded, in 5.1 to 6.7 seconds. That matters: no case produced a build error, and every failure showed up only at run time.

Why build/ works and install/ doesn't

In the base case, the two copies of the same executable differ in one field:

-- RUNPATH build/:   /opt/ros/humble/lib:<ws>/src/cam_node/thirdparty/lib:
-- RUNPATH install/:
-- NEEDED vendor:    libvendor.so.4

CMake writes the library's folder into the build/ binary so you can run it in place. When it installs the binary it clears that path, unless you set an install RPATH. Running build/cam_node/cam directly printed vendor_read()=42. ros2 run started install/cam_node/lib/cam_node/cam and failed with exit code 127. Every failing ros2 run in this test returned in 0.15 to 0.52 seconds. ldd on the installed file shows the same thing without starting the node:

$ ldd install/cam_node/lib/cam_node/cam | grep 'not found'
	libvendor.so.4 => not found

To see where the loader looked, set LD_DEBUG=libs. It tried the folders in LD_LIBRARY_PATH (only /opt/ros/humble/lib/x86_64-linux-gnu:/opt/ros/humble/lib), then /etc/ld.so.cache, then the system folders. The workspace wasn't in any of them. After sourcing install/setup.bash, LD_LIBRARY_PATH had no entry for the workspace at all, because install/cam_node/lib held no library.

Under ros2 launch the same failure looked like this:

[INFO] [cam-1]: process started with pid [...]
[ERROR] [cam-1]: process has died [pid 248, exit code 127, cmd '<ws>/install/cam_node/lib/cam_node/cam --ros-args'].
[cam-1] <ws>/install/cam_node/lib/cam_node/cam: error while loading shared libraries: libvendor.so.4: cannot open shared object file: No such file or directory

The library error came after the "process has died" line, and ros2 launch itself exited with code 0. If you only look at the exit status of a launch command, you will miss it. Exit code 127 from a C++ node is the hint to look for this line.

Installing only libvendor.so isn't enough

The obvious first fix is install(FILES .../libvendor.so DESTINATION lib). It built, and this is what landed in install/cam_node/lib:

lrwxrwxrwx libvendor.so -> libvendor.so.4

CMake copied the symlink as a symlink, and its target wasn't installed. The executable asks for libvendor.so.4 anyway, because the linker records the soname, not the file name you linked. ros2 run failed with the same libvendor.so.4 error. This matches the Xsens question below: the asker's lib folder had libxsensdeviceapi.so -> libxsensdeviceapi.so.4 -> libxsensdeviceapi.so.4.6.0, and the error named the .so.4 file.

Installing all three files with the file(GLOB ...) from the short answer worked:

lrwxrwxrwx libvendor.so -> libvendor.so.4
lrwxrwxrwx libvendor.so.4 -> libvendor.so.4.6.0
-rw-r--r-- libvendor.so.4.6.0
-- ros2 run cam_node cam: exit=0
     [INFO] [t] [cam]: vendor_read()=42

The installed binary still had an empty RUNPATH. It worked because the loader now had a place to look. colcon had written an ld_library_path_lib hook for the package, and after sourcing, LD_LIBRARY_PATH included <ws>/install/cam_node/lib. In the base case, with no library in that folder, LD_LIBRARY_PATH had no workspace entry. The installed copy is independent of the source tree. I deleted src/cam_node/thirdparty/lib, and ros2 run still worked. The file lost its execute bit on install (-rw-r--r--), which didn't stop it from loading.

This fix depends on the workspace being sourced. With only /opt/ros/humble/setup.bash sourced, the same installed binary failed again with exit 127. That is the case when you start a node from a systemd unit, from a script that sources only ROS, or from a shell that sourced local_setup.bash of another workspace. If you mix up those two setup files, see local_setup.bash vs setup.bash.

Making the binary find the library itself

An RPATH stored in the binary works without any environment variable. I tried two ways to set one.

$ORIGIN/.. together with the install rule

file(GLOB VENDOR_FILES ${PROJECT_SOURCE_DIR}/thirdparty/lib/libvendor.so*)
install(FILES ${VENDOR_FILES} DESTINATION lib)
set_target_properties(cam PROPERTIES INSTALL_RPATH "$ORIGIN/..")

$ORIGIN is the folder of the executable, install/cam_node/lib/cam_node, so $ORIGIN/.. is install/cam_node/lib. The installed RUNPATH was the literal text $ORIGIN/... It worked through ros2 run and when I ran the binary directly with only /opt/ros sourced. It also worked after I deleted the source copy of the library and ran a copy of the whole install/ tree from another folder. Of everything I tried, only this one passed all of those runs.

CMAKE_INSTALL_RPATH_USE_LINK_PATH

This variable is often suggested for this error. It tells CMake to keep link folders in the installed RPATH. For the library inside the package it did nothing useful:

-- RUNPATH install/: /opt/ros/humble/lib

CMake kept /opt/ros/humble/lib and dropped <ws>/src/cam_node/thirdparty/lib. The CMake documentation says the variable adds folders "outside the project", and a folder inside your package's source tree doesn't count. ros2 run failed exactly as before.

It did work when the library lived outside the project. I copied the SDK to /opt/vendor_sdk/lib and pointed find_library there. Without the variable, ros2 run failed with the same error. With set(CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE) the installed RUNPATH became /opt/ros/humble/lib:/opt/vendor_sdk/lib. The node ran through ros2 run and without the workspace sourced. This is the libtorch case from the Stack Overflow question below. The library stays where it is, and the binary remembers the absolute path. That ties the binary to that path, so on another machine the library has to be in the same place.

A library in /usr/local/lib needs ldconfig

The ORB-SLAM3 question below fails on libpango_vars.so from Pangolin, a library built from source outside the workspace. A library like that usually ends up in its own folder (the section above) or in /usr/local/lib after make install. I copied the vendor files to /usr/local/lib to test the second case. /usr/local/lib is listed in /etc/ld.so.conf.d/libc.conf in all three images, but the loader reads /etc/ld.so.cache, not that list. Before running ldconfig, ldconfig -p | grep vendor found 0 entries:

  • The build/ binary ran, because its RUNPATH included /usr/local/lib.
  • ros2 run failed with the same libvendor.so.4 error.
  • After ldconfig, the cache listed libvendor.so.4 => /usr/local/lib/libvendor.so.4, and ros2 run worked without rebuilding.

On a normal machine that is sudo ldconfig. In a Dockerfile, put RUN ldconfig after the step that installs the library.

Your own library: install(TARGETS) for the library too

The same error shows up with a library you build yourself. I used add_library(own SHARED src/own.cpp) and linked it to the executable, with install(TARGETS cam ...) only. It built, install/own_pkg/lib held only the executable's folder, and ros2 run failed:

<ws>/install/own_pkg/lib/own_pkg/cam: error while loading shared libraries: libown.so: cannot open shared object file: No such file or directory
[ros2run]: Process exited with failure 127

Adding install(TARGETS own LIBRARY DESTINATION lib) put libown.so into install/own_pkg/lib, and the node printed own_read()=7. Like the vendor case, it failed again when only /opt/ros was sourced. Link errors at build time (undefined reference to) are a different problem and weren't part of this test.

Version notes

Every case gave the same result on Humble, Jazzy and Lyrical, with the same error text, exit code 127 and the same fixes. The toolchains differ a lot: CMake 3.22.1, 3.28.3 and 4.2.3, GCC 11.4.0, 13.3.0 and 15.2.0, glibc 2.35, 2.39 and 2.43. The only differences I saw:

  • On Lyrical, the RUNPATH also contained /opt/ros/lyrical/lib/x86_64-linux-gnu, in the build/ binary and in the installed one with CMAKE_INSTALL_RPATH_USE_LINK_PATH. On Humble and Jazzy it was only /opt/ros/<distro>/lib.
  • On Jazzy every node that started printed two [rcl] warnings about ROS_LOCALHOST_ONLY being deprecated. That came from my script, which set both ROS_LOCALHOST_ONLY and ROS_AUTOMATIC_DISCOVERY_RANGE to keep DDS traffic local. It has nothing to do with the library error.
  • The process has died pid differed between runs, as you'd expect.

Not tested

Gazebo plugins (Failed to load plugin libgazebo_ros2_control.so), pluginlib and component libraries loaded with dlopen, colcon build --merge-install, --symlink-install, IMPORTED CMake targets, static libraries, rviz2 failing on its own system libraries after a partial apt upgrade, ARM64, Windows, and Foxy, Iron or Rolling. FAQ

Why does colcon build succeed but ros2 run says "cannot open shared object file"?

The linker found the library at build time, and the build/ copy of your node keeps its folder in its RUNPATH. CMake clears that path when it installs the node. ros2 run starts the installed copy, which can't find the library unless it was installed into install/<pkg>/lib or an install RPATH was set. In my run the build/ binary worked and the install/ one failed on all three distros.

I installed libfoo.so but the error asks for libfoo.so.4. Why?

The executable records the library's soname, here libvendor.so.4, not the file you linked. Installing only libvendor.so copied a symlink pointing at libvendor.so.4, which wasn't installed. Install every libfoo.so* file. Check the name with readelf -d on your executable (the NEEDED line).

Does CMAKE_INSTALL_RPATH_USE_LINK_PATH fix this?

Only for a library outside your project. For a library in /opt/vendor_sdk/lib it added that folder to the installed RUNPATH, and the node ran. For a library inside the package's source folder, CMake left the folder out and the error stayed.

The library is in /usr/local/lib. Why can't the node find it?

The loader looks in /etc/ld.so.cache, and a library copied there without ldconfig isn't in the cache yet. Before ldconfig, ros2 run failed. After it, the node ran without a rebuild. Run sudo ldconfig, or RUN ldconfig in a Dockerfile.

It works in my terminal but not from systemd. What's different?

Your terminal sourced install/setup.bash, which adds install/<pkg>/lib to LD_LIBRARY_PATH. With only /opt/ros sourced, the installed node failed with exit 127 even with the library installed. Source the workspace in the service, or set INSTALL_RPATH "$ORIGIN/..", which worked without any sourcing.
