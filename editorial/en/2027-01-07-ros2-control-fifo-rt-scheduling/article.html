[INFO] [controller_manager]: update rate is 100 Hz
[INFO] [controller_manager]: Spawning controller_manager RT thread with scheduler priority: 50
[WARN] [controller_manager]: Could not enable FIFO RT scheduling policy: with error number <1>(Operation not permitted). See [https://control.ros.org/master/doc/ros2_control/controller_manager/doc/userdoc.html] for details on how to enable realtime scheduling.

Short answer: this is a warning, not a crash. ros2_control_node tried to move its update loop thread to the SCHED_FIFO real-time policy at priority 50. The kernel said no, so the thread stayed on the normal scheduler and the controller manager kept running. In my Docker tests it disappeared with either of two flags, and neither one needed a real-time kernel:

# root inside the container (the default for ros images)
docker run --cap-add SYS_NICE ... ros2 run controller_manager ros2_control_node ...

# root or a non-root user
docker run --ulimit rtprio=99 ... ros2 run controller_manager ros2_control_node ...

With either flag the log said Successful set up FIFO RT scheduling policy with priority 50. and chrt showed one thread of the process on SCHED_FIFO priority 50. --cap-add SYS_ADMIN, a common suggestion, did not help. Neither did --cap-add SYS_NICE for a non-root user. On a desktop install without Docker the same rule applies: the user needs an rtprio limit of at least 50. The ros2_control docs describe this with a realtime group in /etc/security/limits.conf. I measured Docker only.

What I ran

On 2026-11-08 I ran the tests on a 2 vCPU cloud VM with Docker on cgroup v2, kernel 7.0.0-1009-aws. That is a normal kernel, not PREEMPT_RT: /sys/kernel/realtime does not exist. The host's /proc/sys/kernel/sched_rt_runtime_us was 950000, the default. For each distro I installed controller_manager, ros2controlcli, joint_state_broadcaster and robot_state_publisher from apt into the official ros:<distro>-ros-base image and committed it. Then I ran 13 containers one after another with different flags. Each one ran with --network none and ROS_DOMAIN_ID=88.

Inside each container the script printed the user ID, ulimit -r (the rtprio limit), ulimit -l (memlock) and the effective capability mask from /proc/self/status. It then started the controller manager with this file:

/controller_manager:
  ros__parameters:
    update_rate: 100
    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

After six seconds it ran chrt -p on every thread of ros2_control_node, read VmLck from /proc/<pid>/status, ran the spawner, echoed one /joint_states message and measured its rate with ros2 topic hz for about nine seconds. All of the controller manager's WARN and ERROR lines were collected at the end.

Why the default container gets "Operation not permitted"

Linux lets a thread switch to SCHED_FIFO in two cases. The process has the CAP_SYS_NICE capability, or the requested priority is at or below its RLIMIT_RTPRIO limit (ulimit -r). A default Docker container has neither. Root in the container had the capability mask 00000000a80425fb, which leaves out CAP_SYS_NICE, and ulimit -r was 0. The controller manager asked for priority 50, the call failed with errno 1 (EPERM), and the log printed error number <1>(Operation not permitted).

Being root inside the container does not help by itself, because Docker drops CAP_SYS_NICE from root. That is why the default container failed even though id -u printed 0.

--cap-add SYS_NICE: works for root only

With --cap-add SYS_NICE the mask became 00000000a88425fb, and the log changed to:

[INFO] [controller_manager]: Spawning controller_manager RT thread with scheduler priority: 50
[INFO] [controller_manager]: Successful set up FIFO RT scheduling policy with priority 50.

Only one thread moved. On Humble chrt listed 14 threads named ros2_control_no. One was SCHED_FIFO priority 50 and the other 13 were SCHED_OTHER. On Jazzy and Lyrical the DDS threads (dds.udp.*, dds.shm.*, dds.ev.0) and the executor threads also stayed on SCHED_OTHER. Only the update loop that calls read(), update() and write() gets real-time priority. Your service callbacks and the spawner's requests don't.

The same flag did nothing for --user 1000:1000. The effective capability mask of that user was 0000000000000000. Docker adds the capability to the container's bounding set, but a non-root process does not get it as an effective capability. If your image switches to a non-root user, which many dev containers do, --cap-add SYS_NICE alone leaves the warning in place.

--ulimit rtprio: works for any user

With --ulimit rtprio=99, ulimit -r printed 99 inside the container and the capability mask stayed the default. That worked for root, and it also worked for --user 1000:1000 with an all-zero mask. It is the only flag in my tests that fixed the non-root case without --privileged.

The limit has to cover the priority that ros2_control asks for. With --ulimit rtprio=40 the default request of 50 failed with the same Operation not permitted warning. Adding -p thread_priority:=40 to the controller manager changed the log line to Spawning controller_manager RT thread with scheduler priority: 40, then Successful set up FIFO RT scheduling policy with priority 40.. chrt showed priority 40. So either raise the limit to at least 50, or lower thread_priority to fit the limit you have. The thread_priority parameter was accepted on all three distros.

SYS_ADMIN, --privileged and --cpu-rt-runtime

The pull request that added FIFO scheduling to ros2_control says a container needs CAP_SYS_ADMIN and root. Its example command also passes --privileged. In my run --cap-add SYS_ADMIN changed the mask to 00000000a82425fb, but the warning stayed and every thread stayed on SCHED_OTHER. The capability that matters is SYS_NICE.

--privileged worked (mask 000001ffffffffff), because it grants every capability, SYS_NICE included. That is why the pull request's example works. It also turns off most of the container's isolation, so it's a heavy fix for one warning.

Docker's documentation for real-time containers also mentions --cpu-rt-runtime. On this cgroup v2 host Docker refused to start the container:

docker: Error response from daemon: kernel does not support CPU real-time scheduler
docker exit 125

That flag needs the kernel's real-time group scheduling (CONFIG_RT_GROUP_SCHED), which this kernel doesn't have. You don't need it. SYS_NICE or rtprio alone gave FIFO scheduling here.

You don't need a real-time kernel to remove the warning

The test kernel was a stock cloud kernel with no PREEMPT_RT patch. None of the runs printed anything about a missing real-time kernel, and SCHED_FIFO was set whenever the permission was there. The warning is about permission. A PREEMPT_RT kernel improves worst-case latency for a FIFO thread, but it is a separate decision. Installing one without fixing the permission would leave the same warning.

The reverse also matters. On this normal kernel the FIFO thread did not stop overruns. Jazzy and Lyrical print Overruns handling is : enabled at startup and warn when a cycle runs late. In my runs these appeared once each around the spawner, with or without FIFO:

Memory locking made no visible difference

Real-time guides often add --ulimit memlock=-1 next to rtprio. I ran --cap-add SYS_NICE --ulimit memlock=-1, where ulimit -l printed unlimited, and --cap-add SYS_NICE with -p lock_memory:=false. Both gave FIFO priority 50, the same as SYS_NICE alone. No line in any log mentioned memory locking, and VmLck was 0 kB in every case on every distro, including the default memlock of 8192 KB. With these package versions the controller manager didn't lock its memory, so the memlock limit had no effect I could see.

FAQ

Is "Could not enable FIFO RT scheduling policy" an error?

No. The controller manager logs it as a warning and keeps running on the normal scheduler. In every run with this warning the spawner exited 0 and /joint_states came in at about 100 Hz.

Do I need a real-time kernel to fix it?

No. My test kernel was a stock kernel without PREEMPT_RT, and SCHED_FIFO priority 50 was set as soon as the container had --cap-add SYS_NICE (as root) or --ulimit rtprio=99. The warning is about permission, not the kernel type.

Why does it fail even though I am root in Docker?

Docker removes CAP_SYS_NICE from root, and the default rtprio limit is 0. Root in the default container had neither, so the request for priority 50 returned EPERM.

I added --cap-add SYS_NICE and still get the warning. Why?

Your process probably runs as a non-root user. With --user 1000:1000 the effective capability mask was all zeros and the warning stayed. Use --ulimit rtprio=99 instead. That worked for the non-root user.

What does thread_priority do?

It sets the FIFO priority the controller manager asks for (default 50). With --ulimit rtprio=40 the default failed, and -p thread_priority:=40 made it succeed at priority 40. Keep it at or below your rtprio limit.
