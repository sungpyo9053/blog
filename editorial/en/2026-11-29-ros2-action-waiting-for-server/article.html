$ ros2 action send_goal /fibonacci example_interfaces/action/Fibonacci "{order: 5}"
Waiting for an action server to become available...

In Python the same problem shows up as ActionClient.wait_for_server() returning False, or as a goal or result future that never completes.

Short answer: ros2 action send_goal prints this line every time, even when the server is up. It only means something when nothing follows it. Then the client can't see a server with that exact name, type and ROS_DOMAIN_ID, and by default it waits forever. I stopped it after 60 seconds and it was still waiting. Check what the graph has, then copy the name and type from it:

ros2 action list -t
ros2 action info /fibonacci -t
ros2 action send_goal /fibonacci example_interfaces/action/Fibonacci "{order: 5}" --timeout 10

--timeout was in ros2 action send_goal on Humble, Jazzy and Lyrical in the images I tested. It turns an endless wait into Action server is not available after waiting 3 seconds. or Timed out waiting for result after 5 seconds. The exit code was 0 in both cases, so scripts have to read the text. In rclpy, spin the node while you wait, and don't block inside a callback on a single-threaded executor. That deadlocked every time.

The "never spins" row is the one that confuses people. Discovery is done by the middleware, so the server looks healthy in every CLI tool, but nobody answers the goal request. If ros2 action info shows your server and the client still stalls after Sending goal:, look at the server's executor.

What I ran

On 2026-11-02 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images on a 2 vCPU Linux host, one distro at a time. None of the three ros-base images ships example_interfaces. The only action type in them was tf2_msgs/action/LookupTransform, so the script installs ros-<distro>-example-interfaces first. Before that install, send_goal with example_interfaces/action/Fibonacci printed The passed action type is invalid.

The server is a small rclpy Fibonacci action server on a MultiThreadedExecutor. It can accept, reject, abort or run slowly (1 s per step) so it can be canceled or killed mid-goal. The client is a short rclpy script with a few modes. Each case ran the CLI under timeout so a hang ends and gets measured. For the domain test, I also ran server and client in two separate containers on the default Docker bridge network.

send_goal waits forever unless you pass --timeout

With no server, ros2 action send_goal printed one Waiting for an action server to become available... line and nothing else for 60 seconds. It doesn't repeat the line, so a 10-second run also showed exactly one. When timeout sent SIGTERM, it printed Failed to check if action server is available: rcl node's context is invalid, at ./src/rcl/node.c:428 (the line number differs per distro). That message is about the shutdown. It isn't the cause. Ctrl+C (SIGINT) exited with code 2 and printed nothing extra.

With --timeout 3 it gave up after 3.47 to 3.57 s with Action server is not available after waiting 3 seconds. and exit code 0. The rclpy equivalent behaves as documented. wait_for_server(timeout_sec=0.0) returned False immediately, and 0.5, 2 and 5 seconds returned False after 0.50, 2.00 and 5.00 to 5.01 s.

The waiting line isn't an error in itself. Against a server that was already running, the CLI still printed it once and then Goal accepted 0.57 to 1.05 s after the command started.

Name, namespace and remapping

Action names follow the same rules as topics. A server created with the relative name fibonacci in a node under /robot1 became /robot1/fibonacci. send_goal /fibonacci hung, and send_goal /robot1/fibonacci succeeded. An rclpy client in the same namespace found it with the relative name fibonacci (True after 0.00 to 2.50 s). The same client with the absolute name /fibonacci returned False after its 3 s timeout.

Remapping is where the distros differed. With the server started as --ros-args -r fibonacci:=fib2, Humble ignored the rule. The action stayed at /fibonacci and the goal succeeded. On Jazzy the list showed /fib2, and /fibonacci hung. On Lyrical /fibonacci also hung. If a launch file remaps an rclpy action server, check ros2 action list on the distro you actually run.

The type has to match exactly

The CLI resolves the type locally before it waits. If the type can't be imported (a typo like Fibonaci, or a package that isn't installed or sourced in that shell), you get The passed action type is invalid right away. The type example_interfaces/Fibonacci, without /action/, was accepted and worked.

A type that exists but isn't the server's type is worse. With the server on example_interfaces/action/Fibonacci and the CLI sending tf2_msgs/action/LookupTransform to the same name, the CLI printed the waiting line and hung. There's no "type mismatch" message. ros2 action list -t shows the real type in brackets, so compare it with what you typed.

ROS_DOMAIN_ID, in one container or two

A server on ROS_DOMAIN_ID=7 and a client on the default domain don't see each other. ros2 action list -t was empty and send_goal hung. That was true in one container and with two containers on the default bridge network. Setting ROS_DOMAIN_ID=7 in the client container fixed it, and the goal finished in 1.02 to 1.87 s including startup. Check printenv ROS_DOMAIN_ID in both containers, along with their compose files and entrypoints.

Discovery delay: starting both at once

When the server and send_goal started at the same moment, the server logged ready after 0.38 to 0.50 s, and the CLI reached Goal accepted after 0.54 to 0.97 s (5 runs per distro). An rclpy client started at the same moment saw the server and had its goal accepted after 0.41 to 0.76 s. Discovery delay on one host is under a second. If your client waits longer than a few seconds, the cause is one of the mismatches above, not slow discovery. A fixed sleep before the first goal doesn't help. wait_for_server() with a timeout does the same job and ends sooner.

rclpy: futures that never complete

An rclpy future only completes when an executor processes the response. In the no-spin case, wait_for_server returned True and send_goal_async returned a future. After 5 s of time.sleep it was still done=False. One rclpy.spin_until_future_complete(node, future, timeout_sec=5.0) completed it right away with accepted=True. wait_for_server itself worked without spinning. It returned True in this client and also against the server that never spun.

Inside callbacks it depends on the executor and the callback groups. A timer callback sent the goal and then waited for the result. The executor ran in a thread, and a watchdog gave up after 10 s:

Pattern in the timer callbackExecutor and groupsResult (all three distros)
send_goal_async().add_done_callback(), then get_result_async().add_done_callback(), return at onceSingleThreadedExecutorWorked. Result 0.4 s after the goal
Busy-wait on the send_goal_async futureSingleThreadedExecutorDeadlock. Still done=False after 8 s

Blocking send_goal()MultiThreadedExecutor, default group for timer and clientDeadlock

A MultiThreadedExecutor alone doesn't fix it. The node's default callback group is mutually exclusive, which fits what I saw: the client's response callbacks can't run while the timer callback in the same group is blocked. They need a group the blocked callback isn't holding. The fully asynchronous version needed neither and was the fastest. The blocking versions took several seconds for a goal that otherwise finished in 0.4 s. I didn't look into why.

Rejected, aborted, canceled, or server gone

Rejected: the CLI printed Goal was rejected. and exited 0 in under a second. In rclpy the goal future completes and goal_handle.accepted is False. Calling get_result_async() on a rejected goal makes no sense, so check accepted first.

Aborted: the CLI printed the partial result and Goal finished with status: ABORTED, exit 0. In rclpy the result arrives normally with status=ABORTED.

Canceled from rclpy: cancel_goal_async() returned return_code=0 and goals_canceling=1. The result came about 0.5 s later with status=CANCELED, on all three distros. The server has to accept the cancel and check is_cancel_requested in its loop. Mine did.

Ctrl+C on the CLI during a goal: on Humble the CLI printed the partial result and Goal finished with status: CANCELED, exit 0. On Jazzy and Lyrical it printed Canceling goal..., then Executor is already spinning, and exited with code 1. The server still received the cancel and canceled the goal. On Lyrical the server also logged RuntimeWarning: failed to send response (timeout): client will not receive response. So on Jazzy and Lyrical the error comes from the CLI's own exit path. The cancel went through.

Server killed with SIGKILL mid-goal: nothing tells the client. The CLI sat after Goal accepted with ID: ... until my 40 s limit. With --timeout 5 it printed Timed out waiting for result after 5 seconds. after 5.73 to 5.83 s, exit 0. In rclpy the result future never completed within 25 s. server_is_ready() stayed True until 22.3 s into the client run, about 19 s after the kill.

Server stopped with SIGTERM mid-goal: server_is_ready() turned False about a second after the signal. The result future still never completed. In both cases the client has to notice on its own, with a timeout on the result or a check on server_is_ready().

Version notes

Most results were identical across Humble, Jazzy and Lyrical. These were the differences:

  • --timeout was present on all three. Jazzy and Lyrical also had --stdin. Lyrical's help adds that the timeout "Also applies to goal cancellation if interrupted".
  • -r fibonacci:=fib2 on an rclpy action server was ignored on Humble and worked on Jazzy.
  • Ctrl+C during a goal ended with CANCELED and exit 0 on Humble, and with Executor is already spinning and exit 1 on Jazzy and Lyrical.
  • The rcl node's context is invalid line pointed at node.c:428 on Humble, node.c:404 on Jazzy and node.c:409 on Lyrical. On Lyrical a killed CLI sometimes also printed failed to initialize wait set: the given context is not valid. Drop the line numbers when you search.
  • Discovery was a little slower on Jazzy and Lyrical (CLI goal accepted after 0.89 to 0.97 s) than on Humble (0.54 to 0.80 s).

One thing to watch on Jazzy and Lyrical: right after ros2 daemon stop, the first ros2 action list -t sometimes printed nothing, even though ros2 action info showed the server in the same case. If the list is empty, run it again or check with ros2 action info before you assume the server is gone.

FAQ

Why does ros2 action send_goal hang at "Waiting for an action server to become available..."?

The client can't see a server with that exact name and type on its ROS_DOMAIN_ID. By default it waits forever. In my run it was still waiting after 60 seconds. Compare your name and type with ros2 action list -t, and check the domain ID on both sides.

Does ros2 action send_goal have a timeout?

Yes, --timeout N (or -t N) on Humble, Jazzy and Lyrical in my images. It printed Action server is not available after waiting 3 seconds. or Timed out waiting for result after 5 seconds. and exited with code 0, so check the text in scripts.

Why does my rclpy action client never get the result?

Either nothing spins the node, or a callback blocks the executor. A send_goal_async future stayed undone after 5 s without spinning. Blocking inside a callback deadlocked on a SingleThreadedExecutor, and also on a MultiThreadedExecutor with the default callback group. Use add_done_callback chains, or a reentrant or separate callback group.

What happens to the client if the action server dies mid-goal?

Nothing tells it. The CLI waited past 40 s after Goal accepted, and an rclpy result future never completed. server_is_ready() turned False about 1 s after SIGTERM and about 19 s after SIGKILL. Put a timeout on the result.

What does "The passed action type is invalid" mean?

The CLI couldn't import the type you typed. It was misspelled, or its package isn't installed or sourced in that shell. The ros-base images don't include example_interfaces, so the tutorial's Fibonacci type gives this error until you install it.
