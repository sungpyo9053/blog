[WARN] [rosbag2_player]: Ignoring a topic '/reading', reason: package 'my_msgs' not found, searching: [/opt/ros/humble].

The recording side prints a different line, and the bag ends up without the topic:

[WARN] [ROSBAG2_TRANSPORT]: Topic '/reading' has unknown type 'my_msgs/msg/Reading' . Only topics with known type are supported. Reason: 'package 'my_msgs' not found, searching: [/opt/ros/humble]

Short answer: ros2 bag can only record or play a custom message type if the shell running it has sourced the workspace that built that type. Your nodes can work fine in one terminal while ros2 bag runs in another terminal that only sourced /opt/ros/<distro>. The searching: [...] list in the message tells you exactly which install prefixes it looked in. If your workspace isn't in that list, source it in the same terminal and run the command again:

source /opt/ros/humble/setup.bash
source ~/ws/install/setup.bash        # the workspace that built my_msgs
ros2 bag record /reading -o my_bag    # Jazzy and later: --topics /reading also works
ros2 bag play my_bag

In my run that was the whole fix on Humble, Jazzy and Lyrical. Every message in the bag reached a subscriber. Without it, recording stored 0 messages for the topic and playback delivered 0, and both commands still exited normally. MCAP storage didn't change this. A bag recorded with an MCAP file, which stores the message schema, was ignored the same way when the player shell wasn't sourced.

What I ran

I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, each with --network none and ROS_DOMAIN_ID=88. The stock Humble image has no MCAP plugin. ros2 bag record --help listed only sqlite3 and a test plugin, and -s mcap stopped at the argparse usage message with exit code 2. So for Humble I installed ros-humble-rosbag2-storage-mcap and measured on that image.

Each container built four small workspaces with one message type each:

  • ws1: my_msgs/msg/Reading with int32 seq, float64 value, string note.
  • ws2: the same package name, but with value and seq swapped and an extra float64 extra field. This is the "I changed the .msg file after recording" case.
  • ws3: the same message in a package whose package.xml has no member_of_group line.
  • ws4: the same message with <architecture_independent/> in the package.xml export block.

Each workspace built in 8 to 12 seconds, except ws3, which failed on every distro (more below). A Python publisher, with the workspace sourced, sent Reading messages on /reading at 20 Hz for 7 seconds (138 or 139 sent). For each case, ros2 bag record ran for 5 seconds, from a shell that either had or hadn't sourced ws1. Then ros2 bag play ran against a Python subscriber, and the subscriber counted what arrived. A last step read the bags with rosbag2_py.

The subscriber was always sourced. Only the player's shell changed. Every unsourced playback printed the Ignoring a topic warning once, with the distro's own prefix in the search list, then "played" the bag for its full length (about 5 seconds) and exited with code 0. On Jazzy it added Publisher for topic '/reading' not found about 100 ms later. Naming the topic with --topics /reading didn't turn the warning into an error.

The MCAP rows matter because of a common hope: MCAP files carry the message definition, so maybe the player doesn't need the package. It does. ros2 bag play creates a real ROS publisher for each topic, and that needs the compiled type support libraries, not a text schema. A long-running rosbag2 feature request, Store message definition in bag, is about the definitions, and in this version the player still needs the package installed.

ros2 bag info works without the workspace

From an unsourced shell, ros2 bag info printed the right type and count on all three distros, for example Topic: /reading | Type: my_msgs/msg/Reading | Count: 94 | Serialization Format: cdr. That's because info reads only the metadata. So a correct ros2 bag info doesn't prove that playback will work. Run ros2 bag play in the same shell and look for the warning.

Half-sourced workspaces give a different error

Some setups only export AMENT_PREFIX_PATH, for example a hand-written Dockerfile ENV line or a launcher script. I tried exactly that: AMENT_PREFIX_PATH pointing at ws1/install/my_msgs, with no setup.bash. The package was now found, and loading its libraries failed instead:

# Humble
Ignoring a topic '/reading', reason: could not create publisher: Type support not from this implementation. Got:
    Handle's typesupport identifier (rosidl_typesupport_cpp) is not supported by this library, ...
    Could not load library libmy_msgs__rosidl_typesupport_fastrtps_cpp.so: dlopen error: libmy_msgs__rosidl_typesupport_fastrtps_cpp.so: cannot open shared object file: No such file or directory

# Jazzy and Lyrical
Ignoring a topic '/reading', reason: dlopen error: libmy_msgs__rosidl_generator_c.so: cannot open shared object file: No such file or directory

The subscriber again received 0 messages. The fix is the same: source the workspace's install/setup.bash and don't rebuild the environment by hand. Sourcing also sets the library path and PYTHONPATH.

Changed message definitions: no warning, no messages

This is the quiet one. I played the ws1 bags from a shell that sourced ws2, where the package name is the same but the fields are different. The subscriber also used ws2. The player found the package, printed no warning, and ran for the full length. The subscriber received 0 messages on all three distros, with both sqlite3 and MCAP bags. Neither process printed an error.

rosbag2_py showed what was happening. With ws2 sourced, reading the raw bytes worked (all 94, 88 and 80 records), and deserializing the first one failed:

RMWError failed to deserialize ROS message: Fast CDR exception deserializing message of type my_msgs::msg::dds_::Reading_., at ./src/type_support_common.cpp:118

On Lyrical the same message ended in type_support_common.cpp:139. Jazzy and Lyrical bags store a hash of the definition. The metadata.yaml had type_description_hash: RIHS01_6e686bae... next to the type, and metadata version 9. Humble's bag used metadata version 5 with no hash. Even on Jazzy and Lyrical, the player didn't warn that the hash differed from the sourced package. If a bag plays without warnings but your subscriber stays silent, compare the .msg file with the one used at recording time. The fix is to check out or rebuild the old definition, play the bag from that workspace, and convert the data if you need it in the new layout. I didn't measure the conversion step.

package.xml: member_of_group matters, architecture_independent doesn't

One ROS Answers thread ends with the asker fixing has unknown type through a package.xml change. I tested the two changes that usually come up. Without <member_of_group>rosidl_interface_packages</member_of_group>, colcon build failed in about 1 to 2 seconds on all three distros:

CMake Error at /opt/ros/humble/share/rosidl_cmake/cmake/rosidl_generate_interfaces.cmake:229 (message):
  Packages installing interfaces must include
  '<member_of_group>rosidl_interface_packages</member_of_group>' in their
  package.xml

Jazzy and Lyrical reported the same error at line 223. With that build failing, there's no installed package, so recording that type produced 0 messages, and in my script the publisher couldn't even import it. Adding <architecture_independent/> to the export block changed nothing. That package built and recorded 92, 89 and 80 messages. If your build log for the message package is clean and the package shows up in install/, package.xml isn't your problem.

In practice, record and play from the same terminal you use for ros2 run. Put the workspace source line in the script or launch wrapper that starts the recorder. And after a test recording, check that your topic appears in ros2 bag info with a non-zero count. If the bag also needs converting between distros or formats, see how to convert a .db3 bag to MCAP and play Jazzy bags in Humble. A converter needs the same sourced workspace for custom types, though I didn't run ros2 bag convert here.

Version notes

  • Humble: the stock ros-base image has no MCAP plugin (-s {sqlite3,my_test_plugin}), so you need ros-humble-rosbag2-storage-mcap. The recorder repeats the unknown-type warning about every 100 ms. Topics are positional arguments, and record --help has no --topics flag. Bag metadata is version 5, with no type hash.
  • Jazzy: MCAP is included. The unknown-type warning prints once. Playback adds Publisher for topic ... not found. Metadata version 9 stores type_description_hash.
  • Lyrical: MCAP is listed first among storage plugins. The recorder logs No input serialization format specified, using default rmw serialization format: 'cdr' on every start. Bag file names start with an index and a timestamp, for example 0_bag_src_db3_2026_11_07-02_23_17.db3. The player draws a progress block with terminal escape codes, and the Ignoring a topic line is printed inside it.

FAQ

Why does ros2 bag play say Ignoring a topic, package not found?

The terminal running ros2 bag play hasn't sourced the workspace that built the message package. The searching: [...] list shows where it looked. Source that workspace's install/setup.bash in the same terminal. In my run the topic then played in full on Humble, Jazzy and Lyrical.

Why is my custom topic missing from the bag after ros2 bag record?

The recorder shell didn't know the type, so it printed has unknown type and skipped the topic. It still wrote a valid bag and exited normally. Humble repeats the warning about every 100 ms, while Jazzy and Lyrical print it once. Source the workspace before recording.

Does MCAP storage let me play custom messages without the package?

No. A bag recorded with MCAP was ignored by an unsourced player on all three distros, just like sqlite3. The player needs the compiled message libraries to create a publisher.

ros2 bag info shows my type. Why does playback still fail?

ros2 bag info only reads metadata, so it worked without the workspace. Playback and deserialization need the package, and in a half-sourced setup they also need its libraries.

The bag plays with no warning but my subscriber gets nothing. What now?

Check whether the message definition changed after recording. With the same package name and different fields, the player printed nothing and the subscriber received 0 messages. rosbag2_py showed a Fast CDR exception deserializing message error. Play from a workspace that has the original definition.
