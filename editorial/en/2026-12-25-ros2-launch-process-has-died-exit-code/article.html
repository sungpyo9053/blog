[INFO] [crasher-1]: process started with pid [396]
[crasher-1] [INFO] [1793863089.383107129] [crasher]: started, mode=segv, crashing in 1 s
[crasher-1] [INFO] [1793863090.383371749] [crasher]: about to crash (segv)
[ERROR] [crasher-1]: process has died [pid 396, exit code -11, cmd '/ws/install/crash_demo/lib/crash_demo/crasher --ros-args -r __node:=crasher --params-file /tmp/launch_params_0lbkxxkd'].

Short answer: "process has died" is ros2 launch telling you that one of its processes exited with a code other than 0. Launch didn't cause it, and the line doesn't say why it happened. The number is the clue. A negative exit code means the process was killed by a signal: -11 is a segmentation fault, -6 is an abort (in C++ usually an uncaught exception), -9 is SIGKILL, which in my run came from going over the container's memory limit. A positive code is a normal exit: 1 from a Python traceback or exit(1), and 127 from a missing shared library. Look at the lines just above the "process has died" line, prefixed with the same [name-1]. For an exception or a missing library the real error is there. For a segfault nothing is printed at all, so run the node under gdb to get a backtrace:

Node(
    package='my_pkg', executable='my_node', output='screen',
    prefix=['gdb -batch -ex run -ex bt --args'],   # prints a backtrace when it crashes
)

For a Python node that segfaults, set additional_env={'PYTHONFAULTHANDLER': '1'} on the Node instead. It prints the Python stack at the moment of the crash.

Two things surprised me. ros2 launch exited with code 0 after every crash, even when on_exit=Shutdown() stopped the whole launch. And the other processes kept running until they finished on their own. If a script or CI job checks the launch exit code, it won't see a crash.

The mapping is simple once you see it. Launch reports a signal as a negative number. A shell reports the same death as 128 plus the signal number, so -11 becomes 139 and -6 becomes 134. ros2 run gave a third form, 256 minus the signal number: 245 and 250. All three numbers point to the same crash. If you search for help, search with the signal name (SIGSEGV, SIGABRT, SIGKILL), not with the number.

A -2 or -15 right after you press Ctrl+C is usually not a crash. Launch sends SIGINT and later SIGTERM to processes that don't stop. The 5-second escalation is covered in my measured post on Ctrl+C, SIGTERM and launch shutdown.

What I ran

On 2026-11-05 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one container per distro, limited to 1.5 CPUs and 1200 MB of memory, with core dumps off. One ament_cmake package held three programs:

  • crasher, an rclcpp node that logs a line, waits 1 second in a timer, then crashes in the way set by its mode parameter: segv, throw, abort, exit1 or oom.
  • py_crasher.py, an rclpy node that does the same with raise, segv or exit2.
  • needs_lib, a plain C++ program linked to a small shared library in the same package.

Each case was one launch file with two processes. The node under test, and a companion sleep 6 started with ExecuteProcess, so I could see whether the rest of the launch survives. An OnProcessExit handler logged the return code that launch received. I also ran every C++ mode as a bare binary and with ros2 run. The script, repro.sh, is in the evidence folder and runs one distro per call.

The rest of the launch keeps running, and launch exits 0

In every crash case the companion printed process has finished cleanly about 5 seconds after the crash, when its sleep 6 ended. Only then did ros2 launch exit, after about 6.3 to 6.7 seconds, with exit code 0. That held for segfaults, aborts, the OOM kill, exit(1) and the missing library, on all three distros.

So a crashed node in a launch file doesn't stop anything else. If the crashed node was your driver, the rest of the system keeps running without it, and the exit status of the launch command won't tell you. To find out what happened, read the "process has died" line, or attach your own handler:

from launch.actions import LogInfo, RegisterEventHandler
from launch.event_handlers import OnProcessExit

RegisterEventHandler(OnProcessExit(
    target_action=my_node,
    on_exit=lambda event, context: LogInfo(msg=f'my_node exited with {event.returncode}'),
))

In my runs event.returncode was always the same number as in the "process has died" line: -11, -6, -9, 1, 2 or 127.

Where the real error text goes

Whatever the crashing process wrote to stdout or stderr shows up on the screen, each line prefixed with [crasher-1] or [py_crasher.py-1]. With the default output setting, those lines were also saved in ~/.ros/log/<run>/launch.log. For example, terminate called and sensor driver returned -1 each matched once on the screen and once in the log directory.

With output='screen' the error text was printed to the screen as before, but launch.log had 0 matches for it. Only the "process has died" line itself was saved. If you set output='screen' everywhere and only look at the log files afterwards, the exception message is gone. In every case the log directory held one file, launch.log, with no separate per-node file.

Watch the order for exit code 127. The loader's message, error while loading shared libraries: libcrash_helper.so, appeared after the "process has died" line and after my handler's line, on all three distros. If you only read up from "process has died", you miss it. Read a few lines below as well.

Python's print() output is a separate problem: it is buffered, and the last lines before a crash can be lost. This post measures print() and std::cout in ros2 launch. My nodes used the ROS logger, which writes to stderr, so every log line before the crash arrived.

Exit code -11: a segfault prints nothing

This is the hard one. For the C++ null write and for the Python ctypes crash, the last thing on the screen was the node's own about to crash (segv) log line, then "process has died ... exit code -11". There's no message, no stack and no file name. Three ways to get more:

gdb as a launch prefix (C++)

I installed gdb in the container (apt-get install gdb) and added prefix=['gdb -batch -ex run -ex bt --args'] with output='screen'. On a default colcon build, which had 0 debug_info sections, gdb still printed the function names, because the symbols weren't stripped:

[gdb-1] Thread 1 "crasher" received signal SIGSEGV, Segmentation fault.
[gdb-1] 0x0000572e775fcc99 in write_through_null(int*) ()
[gdb-1] #0  0x0000572e775fcc99 in write_through_null(int*) ()
[gdb-1] #1  0x0000572e775fe621 in Crasher::tick() ()
[gdb-1] #2  0x0000572e775fddd3 in Crasher::Crasher()::{lambda()#1}::operator()() const ()

After a rebuild with colcon build --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo, Humble's backtrace had file names and line numbers too: write_through_null (p=p@entry=0x0) at /ws/src/crash_demo/src/crasher.cpp:8, and Crasher::tick at line 20.

For the uncaught exception (-6), gdb stopped at SIGABRT. The frames went down through std::terminate() and __cxa_throw () to read_sensor() (), the function that threw. That is the frame you want. The terminate called after throwing message tells you what was thrown. The backtrace tells you where. One common cause of that abort, std::bad_weak_ptr from shared_from_this(), has its own measured post.

Three side effects. gdb printed warning: Error disabling address space randomization: Operation not permitted in Docker, and the backtrace still worked. Launch then reported [gdb-1]: process has finished cleanly and my handler got returncode=0, because gdb itself exits 0 in batch mode. So under gdb, on_exit actions and respawn never see the crash. And the process is named gdb-1, not after your node.

PYTHONFAULTHANDLER=1 (Python)

With additional_env={'PYTHONFAULTHANDLER': '1'} on the Python node, the same segfault printed this before the "process has died" line. This is Humble. Jazzy and Lyrical printed the same frames with their own Python paths:

[py_crasher.py-1] Fatal Python error: Segmentation fault
[py_crasher.py-1] Current thread 0x000070277183f480 (most recent call first):
[py_crasher.py-1]   File "/usr/lib/python3.10/ctypes/__init__.py", line 517 in string_at
[py_crasher.py-1]   File "/ws/install/crash_demo/lib/crash_demo/py_crasher.py", line 16 in tick

The exit code stayed -11, so respawn and handlers behave as before. It costs nothing until the crash, so it is a reasonable default for Python nodes that use C extensions.

Core dumps

I ran with core dumps turned off, so I didn't test reading a core file. Bash still printed Segmentation fault (core dumped) for the bare binary, because the kernel's core pattern pipes to apport. That text alone doesn't mean a core file exists.

Exit codes 1, 2 and 127

A positive exit code means the process ended on its own, and it nearly always printed why. For an uncaught Python exception that was the full traceback, ending at py_crasher.py, line 14, in tick and ValueError: sensor driver returned -1. For C++ exit(1) it was whatever the node logged before exiting. Search the lines prefixed with the process name.

Exit code 127 came from the dynamic loader. The program started, couldn't find libcrash_helper.so, and quit before main ran. In a real workspace that means a library that isn't installed, a workspace that isn't sourced, or a LD_LIBRARY_PATH that doesn't include the library's folder. With the library back in install/crash_demo/lib, the same launch reported process has finished cleanly and return code 0. If the program itself doesn't exist, launch doesn't report 127. It raises FileNotFoundError, as in the last row of the table. For a Node with the wrong executable name, see "No executable found" in ros2 run and launch.

Version notes

The exit codes, the order of the lines, the log file contents, the respawn timing and the Shutdown behavior were the same on Humble (launch 1.0.15, launch_ros 0.19.14), Jazzy (launch 3.4.12, launch_ros 0.26.13) and Lyrical (launch 3.9.8, launch_ros 0.29.9). On Jazzy and Lyrical the respawn run logged 4 handler calls in 9 seconds, against 5 on Humble. The restart interval was the same, so I put that down to where the 9-second cut fell.

One real difference showed up with the optimizer. With RelWithDebInfo (which builds with -O2), the Humble build (GCC 11.4) still crashed on the null write. The Jazzy (GCC 13.3) and Lyrical (GCC 15.2) builds didn't crash at all: the timer kept logging about to crash (segv) every second until my 60-second timeout. Writing through a null pointer is undefined behavior, and the compiler may drop it. I didn't inspect the generated code. The practical point: a segfault that disappears when you change the build type or the compiler is still a bug in your code. It is not fixed.

Not tested

  • Composable nodes in a component_container. A crash there kills the container, and every component in it, with one "process has died" line.
  • Reading core dumps (they were disabled), valgrind, AddressSanitizer and backward_ros.
  • Exit codes from ros2 run and the shell for the OOM and missing-library cases.
  • Cyclone DDS or Zenoh instead of the default Fast DDS. Nothing here should depend on the RMW, but I didn't check.
  • XML and YAML launch files. All cases used Python launch files.
  • Making ros2 launch exit non-zero after a crash.

FAQ

What does exit code -11 mean in ros2 launch?

The process got signal 11, SIGSEGV, a segmentation fault. In my runs nothing else was printed. Run the node with prefix=['gdb -batch -ex run -ex bt --args'] to get a backtrace, or set PYTHONFAULTHANDLER=1 for a Python node.

What does exit code -6 mean?

Signal 6, SIGABRT. In C++ it most often comes from an uncaught exception, and then the lines just above show terminate called after throwing an instance of ... and what():. A plain abort() or a failed assertion prints less or nothing.

Why does ros2 run show 245 or 250 instead of -11 or -6?

Different tools write the same signal death differently. Launch printed -11 and -6, bash printed 139 and 134, and ros2 run returned 245 and 250 with [ros2run]: Segmentation fault or [ros2run]: Aborted.

Does one crashed node stop the other nodes in the launch file?

No. The other processes kept running and ros2 launch exited 0 when they finished. Add on_exit=Shutdown() to the node if the launch should stop, or respawn=True if it should restart.

Why is the exception message not in the launch log file?

With output='screen', my run had the message on the screen but 0 copies in launch.log. With the default output setting it was in both.
