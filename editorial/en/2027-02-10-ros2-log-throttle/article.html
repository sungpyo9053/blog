bad.cpp:5:3: error: invalid 'static_cast' from type 'rclcpp::Duration' to type 'rcutils_duration_value_t' {aka 'long int'}

ValueError: Logger severity cannot be changed between calls.
ValueError: Logging filter parameters cannot be changed between calls.

The first two lines are what g++ prints on Humble and Jazzy when you pass get_clock() to RCLCPP_INFO_THROTTLE. The third comes from passing an rclcpp::Duration as the period. The last two are rclpy, raised when one throttled log line is called with a different severity or a different throttle_duration_sec than the first time.

Short answer: in C++, pass the clock object and an integer number of milliseconds. In Python, pass seconds as a float:

// C++: clock by reference (*get_clock()), period in milliseconds
RCLCPP_INFO_THROTTLE(get_logger(), *get_clock(), 1000, "speed %.2f", speed);
# Python: period in seconds
self.get_logger().info(f'speed {speed:.2f}', throttle_duration_sec=1.0)

Both printed 5 lines in 5 seconds from a loop running at about 100 Hz, on Humble, Jazzy and Lyrical. Three more things caught me out in the measurements. With use_sim_time on and no /clock, the C++ macro with the node clock printed nothing at all, not even the first line. In C++ the throttle timer belongs to the line of code, not to the node, so a second node instance using the same line printed 0 lines. And rclpy throttles by system time unless you pass a clock, so it ignores sim time by default.

C++: the clock argument is a reference

The macro signature is RCLCPP_INFO_THROTTLE(logger, clock, duration, ...). The clock has to be an rclcpp::Clock object, not a pointer to one. get_clock() returns an rclcpp::Clock::SharedPtr, so you write *get_clock() or *this->get_clock(). The error doesn't say "pointer" anywhere. On Humble and Jazzy it said:

error: cannot capture 'rclcpp::Node::get_clock()()' by reference
error: 'c' was not declared in this scope

The macro wraps the clock in a lambda that captures it by reference, and you can't capture a function call result that way. The second error, about 'c', is a follow-on from the first. On Lyrical the first line was much longer and named the full std::__shared_ptr_access<rclcpp::Node, ...> expression, but it starts with the same cannot capture text. Older code that builds a local rclcpp::Clock clock; just to throttle comes from before rclcpp issue 969, which made the node clock usable here. With *get_clock(), the node clock built and worked on all three distros.

C++: the period is milliseconds, as a plain integer

The third argument is an integer number of milliseconds. The rcutils macro converts it with RCUTILS_MS_TO_NS(RCUTILS_CAST_DURATION(duration)), which I printed from logging_macros.h in the Humble and Jazzy images. My grep found nothing in the Lyrical image, so I can't quote its header, but it behaved the same. That has two effects.

First, a number in seconds is silently wrong. RCLCPP_INFO_THROTTLE(..., 1, ...) compiled and printed every single call, 483 to 485 lines in 5 s, because the period was 1 ms and the loop ran every 10 ms. Write 1000 for one second.

Second, duration types don't compile. Both rclcpp::Duration::from_seconds(1.0) and std::chrono::seconds (1s) failed:

Humble, Jazzy:
error: invalid 'static_cast' from type 'rclcpp::Duration' to type 'rcutils_duration_value_t' {aka 'long int'}
error: invalid 'static_cast' from type 'std::chrono::seconds' {aka 'std::chrono::duration<long int>'} to type 'rcutils_duration_value_t' {aka 'long int'}

Lyrical:
error: cannot convert 'rclcpp::Duration' to 'rcutils_duration_value_t' {aka 'long int'} in initialization
error: cannot convert 'std::chrono::duration<long long int, std::ratio<1> >' to 'rcutils_duration_value_t' {aka 'long int'} in initialization

If you already have an rclcpp::Duration, pass d.nanoseconds() / 1000000. That printed 5 lines, the same as 1000. Accepting a Duration directly is still an open request, rclcpp issue 1929, and the Lyrical images I used still rejected it.

C++: one timer per line of code, shared by every instance

The throttle state lives in static variables inside the macro expansion. The Humble and Jazzy headers hold static rcutils_time_point_value_t __rcutils_logging_last_logged = 0;. A static variable inside a member function exists once for the whole process. So I created two instances of the same node class, ct and ct2, and called one member function containing RCLCPP_INFO_THROTTLE(get_logger(), *get_clock(), 1000, ...) on both in every iteration. ct printed 5 lines and ct2 printed 0, on all three distros. The two loggers have different names, but that doesn't matter. In my loop ct always reached the line first, so it took every slot. RCLCPP_INFO_ONCE behaved the same way: one line for the whole process, from ct, and nothing from ct2.

This is what rclcpp issue 2587 describes for plugins. Load the same plugin class twice and only one instance's throttled messages appear. If you need one throttle per instance, keep the time in a member and check it yourself:

// member: rclcpp::Time last_warn_{0, 0, RCL_ROS_TIME};
auto now = get_clock()->now();
if ((now - last_warn_).seconds() >= 1.0) {
  last_warn_ = now;
  RCLCPP_WARN(get_logger(), "speed %.2f", speed);
}

I did not run this snippet. It is the workaround the per-line design leaves you with, and the measured part is the 5 + 0 result above.

Python: throttle state belongs to the logger object

rclpy keeps its throttle state on the logger object, per call site. A shared helper function that logs through two different node loggers printed 5 lines for each, and so did two child loggers from get_child('a') and get_child('b'). So the C++ problem above did not happen in Python.

The flip side: if you get a fresh logger object for every call, the state is thrown away each time. With rclpy.logging.get_logger('pt').info(..., throttle_duration_sec=1.0) inside the loop, the throttle did nothing. It printed 453 to 459 lines, which was every call. self.get_logger() on a node returns the same object each time, and it throttled normally.

The two ValueError messages come from the same per-call-site state. rclpy remembers the severity and filter values used the first time a call site runs. If a helper such as def log(level): logger.log(msg, level, throttle_duration_sec=1.0) is called with INFO and then WARN, the second call raises ValueError: Logger severity cannot be changed between calls. The same helper called with throttle_duration_sec=1.0 and then 2.0 raised ValueError: Logging filter parameters cannot be changed between calls. Both happened on the second call, after one line had printed, on all three distros. The fix is a separate call site for each severity or period, for example one logger.info(...) line and one logger.warning(...) line.

The period is in seconds. throttle_duration_sec=1000, a value copied from C++ milliseconds, printed the first line and then nothing for the rest of the run. throttle_duration_sec=0 printed every call. once=True combined with a throttle printed one line.

Sim time: zero lines, or more lines than you expect

The clock decides what "1 second" means, and the two client libraries pick different clocks by default.

rclpy throttles with a plain Clock() unless you pass throttle_time_source_type. I printed the source in each image: Humble and Jazzy have 'throttle_time_source_type': Clock(), Lyrical has BaseClock(). That clock reads system time, so a Python node with use_sim_time set to true still throttled on wall time. It printed 5 lines with no /clock at all, and 5 lines with /clock running 10 times faster. If you pass the node clock (throttle_time_source_type=self.get_clock()), it follows sim time, with the same results as C++ below. The docstring in all three images lists this argument as str, but the code checks isinstance(..., Clock) (BaseClock on Lyrical), and passing the node clock worked.

In C++ you always choose the clock, and *get_clock() is the node clock. With use_sim_time true and nothing publishing /clock, the node clock stays at 0. The throttle check is "now is at least last logged plus period", and with now stuck at 0 that is never true. Not even the first message printed: 0 lines in 5 seconds in C++, and 0 in Python with the node clock. The RESULT line confirmed sim_now_ns=0 at the end of those runs. The same zero clock causes other trouble. My earlier post on "Subtraction leads to negative time" in rclpy measured now() returning 0 until the first /clock message arrives, even when the simulator starts at 100 s.

With /clock running at 10x, the node clock throttle printed many more lines than wall-clock seconds. That is correct for sim time, but it can surprise you. The count varied a lot between runs: 28 to 46 lines in Python and 26 to 49 in C++, over 12 runs of each across the three distros, where 50 would be one line per sim second. I don't know why some runs printed fewer. My guess is that /clock messages were handled in bunches, so the sim clock skipped past some of the 1-second marks. I didn't measure that.

If you want wall-clock throttling in a sim-time node, give C++ a steady clock:

rclcpp::Clock steady_clock_{RCL_STEADY_TIME};   // member
RCLCPP_WARN_THROTTLE(get_logger(), steady_clock_, 1000, "no data");

That printed 5 lines with no /clock and 5 lines with the 10x /clock, on all three distros. In Python, leaving out throttle_time_source_type already gives you that behavior. Clock types cause other mix-ups too: my post on "Can't subtract times with different clock types" measured that rclpy.time.Time() is a 0 ns SYSTEM_TIME value, while get_clock().now() is ROS_TIME.

Version notes

The line counts were the same on Humble, Jazzy and Lyrical, apart from the run-to-run spread in the 10x sim-time cases. The C++ error text changed only with the compiler. Humble's g++ 11.4 and Jazzy's g++ 13.3 printed invalid 'static_cast'. Lyrical's g++ 15.2 printed cannot convert ... in initialization, and its cannot capture line spelled out the full shared_ptr access expression. rclpy's two ValueError texts were identical on all three. On Lyrical the rclpy log() signature has type hints (**kwargs: 'Unpack[LoggingFilterArgs]') and the default throttle clock is BaseClock() instead of Clock(). It behaved the same in every case I ran.

FAQ

What units does RCLCPP_INFO_THROTTLE use?

Milliseconds, as an integer. 1000 printed 5 lines in 5 seconds. 1 printed every call. rclcpp::Duration and std::chrono::seconds didn't compile on Humble, Jazzy or Lyrical. Python's throttle_duration_sec is in seconds.

How do I fix "cannot capture get_clock() by reference"?

Pass the clock object, not the pointer: RCLCPP_INFO_THROTTLE(get_logger(), *get_clock(), 1000, "..."). That compiled and throttled correctly on all three distros.

Why does my throttled log never print with use_sim_time?

With use_sim_time true and no /clock, the node clock stays at 0 and the throttle condition is never met. The C++ macro with *get_clock() printed 0 lines, not even the first one. Publish /clock, or throttle on rclcpp::Clock(RCL_STEADY_TIME), which printed 5 lines in 5 s.

Why does only one instance of my node or plugin print its throttled message?

In C++ the throttle timer is a static variable per line of code, shared by every object in the process. Two node instances calling the same line printed 5 and 0 lines. rclpy keeps the state per logger, and two loggers printed 5 each.

What does "Logger severity cannot be changed between calls" mean in rclpy?

One throttled or once-filtered call site was used with two severities, for example a helper that receives the level as an argument. rclpy raised the ValueError on the second call. Changing throttle_duration_sec at the same site raised "Logging filter parameters cannot be changed between calls." Use one call site per severity and period.
