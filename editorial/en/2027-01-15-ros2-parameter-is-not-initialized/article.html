rclpy.exceptions.ParameterUninitializedException: The parameter 'name' is not initialized

terminate called after throwing an instance of 'rclcpp::exceptions::UninitializedStaticallyTypedParameterException'
  what():  Statically typed parameter 'name' must be initialized.
[ros2run]: Aborted

In Nav2 and other lifecycle nodes the same problem shows up during configure, wrapped in the lifecycle log:

[ERROR] [map_server]: Caught exception in callback for transition 10
[ERROR] [map_server]: Original error: parameter 'yaml_filename' is not initialized
[WARN] [map_server]: Callback returned ERROR during the transition: configure

Short answer: the node declared a parameter with a type but no default value, and nothing supplied a value at startup. ROS 2 lets you declare a parameter that way, but reading it, or in C++ even declaring it with the template form, throws until a value arrives. Give it a value that actually reaches this node:

ros2 run my_pkg my_node --ros-args -p name:=hello
ros2 run my_pkg my_node --ros-args --params-file params.yaml   # top-level key must be this node's full name, or /**

If you passed a params file and still get the error, the file almost certainly didn't match the node. In my runs a wrong top-level key, a namespace the key didn't include, a node renamed with __node, and a --params-file placed without --ros-args all loaded silently and then produced exactly this exception. If the value is optional, declare it with a default instead (declare_parameter('name', 'default')), or read it with get_parameter_or.

One detail matters for C++. After declare_parameter<std::string>("name") threw and I caught the exception, has_parameter("name") still returned true, and get_parameter("name") threw the "is not initialized" exception. So catching the declare error and carrying on doesn't give you a usable parameter. It leaves a declared one with no value.

Cause 1: nothing gave the parameter a value

This is the plain case. Code like this is common when a value has no sensible default, such as a map file, a serial port or a robot name:

self.declare_parameter('name', Parameter.Type.STRING)   # type, no default
value = self.get_parameter('name').value                 # raises if nothing set it
auto value = declare_parameter<std::string>("name");     // throws here if nothing set it

Since Galactic, parameters are statically typed by default. A typed parameter with no value is allowed to exist, but reading it is treated as an error rather than handing you None or an empty string. That is the point of the exception. The code author wanted the value supplied from outside and made a missing value fail loudly. The rclcpp docs say UninitializedStaticallyTypedParameterException is "Thrown if user attempts to create an uninitialized statically typed parameter" (API reference). The notes on statically typed parameters cover the design.

The two C++ forms behave differently, and that changes where you see the error. The template form, declare_parameter<std::string>("name"), throws inside the declare call, usually in a constructor. Uncaught, that aborts the process before it spins. The enum form, declare_parameter("name", rclcpp::PARAMETER_STRING), declares without complaint. The error comes later, from whichever get_parameter call reads it first. Nav2's map_server reads in on_configure, which is why its message appears as "Original error" during the configure transition and not at startup. In rclpy only the read throws, and the declare call always succeeds.

The fix is to supply the value. -p name:=hello after --ros-args worked in every run, and so did a params file whose key matched.

Cause 2: a params file that loaded but didn't match the node

This is the cause behind most reports, because people pass a file and assume it applied. rcl doesn't warn when a params file contains no entry for the node that loads it. In my runs, each of these loaded with no message and then hit the "is not initialized" error:

  • The top-level key was a different name (/my_node: for a node called pnode).
  • The node ran in a namespace (/robot1) and the key had only the bare name (/pnode:). Multi-robot launch files that push a namespace hit exactly this.
  • The node was renamed at launch (-r __node:=renamed) and the key still had the original name.
  • The --params-file came without --ros-args in front of it, so rcl never parsed it.

The same happened with Nav2. A file with a /map_server: key configured the map server fine. The same file with the server started in /robot1 gave Original error: parameter 'yaml_filename' is not initialized on Humble and Jazzy. The key has to be /robot1/map_server:, or /**: if you want it to match any name. The node name and wildcard rules are covered in my params YAML errors post.

To see which name your node really has, run ros2 node list while it is up, and use that string as the YAML key.

Cause 3: a wrong type, which looks similar but isn't

With -p name:=5 for a string parameter, the declare call itself failed with InvalidParameterTypeException: Trying to set parameter 'name' to '5' of type 'INTEGER', expecting type 'STRING' in rclpy. In rclcpp it said Wrong parameter type, parameter {name} is of type {string}, setting it to {integer} is not allowed. The parameter was then not declared at all: has_parameter returned false and later reads raised ParameterNotDeclaredException. If your log shows "not declared" or "invalid type" and not "not initialized", you're on this path. Quote the value in YAML (name: "5") or fix the type in the code.

Empty strings, ~ and null

An empty string is a value. YAML name: "" initialized the parameter with no error in rclpy and rclcpp, and -p "name:=''" did the same in rclpy. You can use that if your node treats empty as "not configured". Nav2's map server does: with yaml_filename:='' it configured on all three distros and logged yaml-filename parameter is empty, set map through 'load_map'-service.

You can't unset a typed string parameter from YAML. name: ~ and name: null didn't leave it unset or empty. The rclpy node received the literal strings ~ and null, with no error, on all three distros. The rclcpp node got ~ as a string as well, also when it was declared with dynamic typing. If a launch file writes null to mean "nothing", your node gets four characters.

For Nav2, set yaml_filename in the map server's params. Don't patch the code. In launch files built on nav2_bringup that means passing the map argument, which ends up as yaml_filename. I didn't run the full bringup launch, only map_server on its own.

Version notes

The rclcpp behavior was identical on Humble, Jazzy and Lyrical. That covers the exception classes, the messages and exit code 250 for an uncaught declare. The differences were in rclpy, the CLI and Nav2:

  • rclpy on Jazzy and Lyrical appends the name to the message: The parameter 'name' is not initialized: name. Humble stops after initialized. Search for the part before the colon.
  • declare_parameter('name') with no default and no type: on Humble and Jazzy it printed a UserWarning that this form "is deprecated" and declared a parameter whose get_parameter('name').value was None, with no exception. On Lyrical the same call raised TypeError: ... declaring a parameter only providing its name is not allowed and nothing was declared. declare_parameter('name', None) behaved the same way. Code that relied on this form breaks on Lyrical.
  • ros2 param get wording changed on Lyrical, and ros2 param dump drops everything on Jazzy and Lyrical (table above).
  • nav2_map_server 1.1.20 (Humble) and 1.3.13 (Jazzy) failed configure without yaml_filename. 1.5.2 (Lyrical) configured, logged yaml-filename parameter is empty, set map through 'load_map'-service, and ros2 param get showed an empty string. On Lyrical a missing map no longer stops the map server, so look for that line if the map never appears.
  • On Jazzy the first ros2 param list /pnode, 6 seconds after the node started, printed Node not found. An immediate retry worked. That is discovery timing, not the parameter.

FAQ

What does "The parameter is not initialized" mean in ROS 2?

The node declared the parameter with a type but no default, and no value was supplied at startup, so reading it raised ParameterUninitializedException. Supply it with --ros-args -p name:=value or a params file whose key matches the node's full name.

What is "Statically typed parameter must be initialized" in rclcpp?

It is UninitializedStaticallyTypedParameterException. declare_parameter<T>("name") throws it when no override exists. Uncaught, the node aborts and ros2 run exits with code 250. Pass a value or declare it with a default.

I passed a params file but still get "is not initialized". Why?

The file didn't match the node. A wrong top-level key, a missing namespace, a node renamed with __node, or a --params-file without --ros-args all loaded silently and then gave this error. Use the name from ros2 node list, or /**.

How do I fix "parameter 'yaml_filename' is not initialized" in Nav2 map_server?

Give the map server a yaml_filename under its exact node name, including any namespace. On Humble and Jazzy configure failed without it. On Lyrical configure succeeded with an empty value and a hint to use the load_map service.

Can I read an optional parameter without an exception?

Yes. get_parameter_or returned the fallback in rclpy and rclcpp, and rclcpp's get_parameter(name, out) returned false. Declaring with a default, even an empty string, avoids the problem.
