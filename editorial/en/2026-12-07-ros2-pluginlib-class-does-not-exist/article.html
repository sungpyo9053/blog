  what():  According to the loaded plugin descriptions the class p_noexport::Square with base class type pbase::RegularPolygon does not exist. Declared types are  p_badpath::Square p_good::Square p_libprefix::Square ...

Nav2, MoveIt, ros2_control and rviz2 print the same sentence with their own names in it, for example the class teb_local_planner::TebLocalPlannerROS with base class type nav2_core::Controller does not exist or the class gazebo_ros2_control/GazeboSystem with base class type hardware_interface::SystemInterface does not exist.

Short answer: pluginlib never opened your library. It looked up the name you asked for in the plugin XML files registered for the base class's package and didn't find it. The list after "Declared types are" is everything it did find. If your plugin isn't in that list, the XML wasn't registered: add this line to the plugin package's CMakeLists.txt, with the package that owns the base class as the first argument, rebuild, and open a new shell or source install/setup.bash again:

pluginlib_export_plugin_description_file(pbase plugins.xml)   # pbase = package of the base class, not your package

If your plugin is in the list but spelled differently, ask for the exact string in the list. That string is the name attribute from your XML, or the type attribute when there is no name. In my runs every cause gave the same result on Humble, Jazzy and Lyrical. The other pluginlib errors, "no factory exists for it", "Could not find library corresponding to plugin" and "Failed to load library ... undefined symbol", come from later steps and have different fixes. They're in the table below.

How pluginlib finds a plugin

It helps to know the order, because each error comes from a different step.

  1. The ClassLoader constructor asks the ament index for every package that registered a file under <base package>__pluginlib__plugin. In my workspace the index had 12 entries under pbase__pluginlib__plugin and one under p_ownpkg__pluginlib__plugin.
  2. It parses those XML files and keeps the classes whose base_class_type matches the loader's base class. This is the "Declared types" list.
  3. When you ask for a name, it looks it up in that list. Not there: "does not exist".
  4. It finds the library named in <library path> under the package's lib directory. Not found: "Could not find library corresponding to plugin".
  5. It opens the library with dlopen. Unresolved symbol: "Failed to load library ... undefined symbol".
  6. It asks the library for a factory for the XML type. The factory only exists if PLUGINLIB_EXPORT_CLASS registered that type: otherwise "no factory exists for it".

The time spent was small. The constructor took 1.9 to 5.0 ms. A "does not exist" failure came back in under 0.1 ms. A first successful load took under 0.7 ms, and loading the same class again took about 0.01 ms.

"Does not exist" and the plugin is missing from the list

This is the registration step. Four of my mistakes ended here, and they look the same from outside.

No export call. In ROS 2, a plugins.xml file in your package does nothing on its own. pluginlib_export_plugin_description_file() installs it and creates the ament index entry. Without the call, colcon build succeeded and the plugin wasn't in the list. When I added the call and rebuilt that one package, the plugin loaded in the same shell without re-sourcing, because the package was already on AMENT_PREFIX_PATH.

Wrong first argument. The first argument is the package that owns the base class, because that's the package name the loader is built with. pluginlib_export_plugin_description_file(p_ownpkg plugins.xml) registered the file under p_ownpkg__pluginlib__plugin, where a loader for pbase never looks. For Nav2 the first argument is nav2_core. For ros2_control hardware it's hardware_interface, and for rviz2 displays and panels it's rviz_common. The package that owns the base class is the one named in the loader, so check what the error says your base class is and which package declares it.

ROS 1 export tag. <export><pbase plugin="${prefix}/plugins.xml"/></export> in package.xml is how ROS 1 registered plugins. With only that line and no CMake call, the plugin wasn't found on any of the three distros.

Wrong base_class_type. With base_class_type="pbase::Polygon" the file was registered, 12 entries were in the index, and the class still didn't appear in the list. The loader skips classes declared for another base. Copy the base class from the error message, including its namespace.

Two more causes are about the environment. A package built after the shell was sourced isn't on AMENT_PREFIX_PATH, so its index entry is invisible. In my run p_late was missing until I sourced install/setup.bash again. And if the plugin package isn't installed at all, you get the same message. That matches the TEB question below: TEB wasn't installed for Humble, so the declared list held only the four Nav2 controllers that were.

"Does not exist" but the plugin is in the list

Then the string you asked for differs from the one in the list. pluginlib looks up the name attribute. The type attribute is used only when name is missing. With name="p_named/Square" type="p_named::Square", asking for p_named/Square worked and asking for p_named::Square failed. This is how gazebo_ros2_control/GazeboSystem is written: a slash, not ::. Copy the string from the list or from the XML, not from the C++ class name.

A typo in the XML can give a second error. When the XML said p_typo::Sqaure and I asked for that exact string, pluginlib found it in the list, opened the library, and threw "no factory exists for it", because the macro had exported p_typo::Square. The type attribute has to match the class in PLUGINLIB_EXPORT_CLASS exactly.

"No factory exists for it"

The library opened, but nothing in it registered the requested type. I got this with no PLUGINLIB_EXPORT_CLASS at all, and with an XML type naming a class the macro didn't export. The fix is one line at the end of the .cpp, outside any namespace, with the same fully qualified names as the XML:

#include <pluginlib/class_list_macros.hpp>
PLUGINLIB_EXPORT_CLASS(p_good::Square, pbase::RegularPolygon)

"Could not find library corresponding to plugin"

The class is declared, but the file named in <library path="..."> isn't in the package's install. In ROS 2 the value is the CMake target name, p_good for libp_good.so. A wrong name failed. So did a missing install(TARGETS ...): the library was built in build/ but never copied to install/. The ROS 1 form lib/libp_ros1path failed on all three distros after a warning that it "should be '/libp_ros1path'". The form with only the lib prefix, libp_libprefix, loaded with a warning. Use the bare target name and the warning goes away.

The install line that worked:

install(TARGETS p_good LIBRARY DESTINATION lib ARCHIVE DESTINATION lib RUNTIME DESTINATION bin)

"Failed to load library" with an undefined symbol

The text says to check PLUGINLIB_EXPORT_CLASS, but the cause in my run was something else. The last part, after Error string:, holds the real reason: undefined symbol: _ZTVN7p_undef6SquareE. That symbol is the vtable of p_undef::Square. I declared one non-pure virtual function and never defined it. A shared library is allowed to have undefined symbols at link time, so the build passed, and the failure only came when dlopen ran. Giving the function a body fixed it. The symbol is mangled. _ZTV means a vtable, and c++filt turns it back into a readable name. If you are moving CMake off ament_target_dependencies, the linking pattern I used is the one from the ament_target_dependencies replacement post.

Version notes

Every message, exception type and declared list was the same on Humble (pluginlib 5.1.5, class_loader 2.2.0), Jazzy (pluginlib 5.4.6, class_loader 2.7.1) and Lyrical (pluginlib 5.8.5, class_loader 2.9.4). Only two things differed. The dlopen error ends with at ./src/shared_library.c:99 on Humble and Jazzy and :96 on Lyrical, so drop that part when you search. And on Lyrical, CMake 4.2.3 printed CMake Deprecation Warning at CMakeLists.txt:1 (cmake_minimum_required) for each of my packages, which declared VERSION 3.8. The build still succeeded. Humble had CMake 3.22.1 and Jazzy 3.28.3, and neither warned.

FAQ

What does "According to the loaded plugin descriptions the class X with base class type Y does not exist" mean?

pluginlib searched the plugin XML files registered for Y's package and found no entry named X. It never opened your library. The list after "Declared types are" shows what it did find, so check first whether your plugin is in it.

My plugin builds but is not in "Declared types are". Why?

In my run, four mistakes did that: no pluginlib_export_plugin_description_file call, the call naming your own package instead of the base class package, a ROS 1 export tag in package.xml only, and a wrong base_class_type. A package built after you sourced the workspace was also missing until I re-sourced.

My plugin is listed, but I still get "does not exist". Why?

The string you request is different from the listed one. pluginlib looks up the XML name attribute, and only falls back to type when there is no name. p_named/Square loaded and p_named::Square did not.

What does "no factory exists for it" mean?

The library opened but no PLUGINLIB_EXPORT_CLASS registered that class. Add the macro, and make sure the XML type is exactly the class it exports.

Do I need to source the workspace again after fixing a plugin?

Not after rebuilding a package that was already built when the shell was sourced. My fixed p_noexport loaded in the same shell. A package built for the first time after sourcing needed source install/setup.bash.
