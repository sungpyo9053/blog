The same traceback ends in No module named 'utils', No module named 'imp_pkg.utils' or No module named 'configs', depending on how you import and how setup.py lists your packages. If the module file itself was never installed, from imp_pkg import late fails with ImportError: cannot import name 'late' from 'imp_pkg' instead. (imp_pkg is my test package. Yours will show its own name.)

Short answer: ros2 run doesn't run your source file. It runs a wrapper script in install/<pkg>/lib/<pkg>/, which imports your node from site-packages. Your src/ folder isn't on the path. Two things have to be true. First, every import of your own code must go through the package name. Second, setup.py must install every subfolder you import. This setup worked on Humble, Jazzy and Lyrical, with and without --symlink-install:

# my_pkg/my_node.py
from my_pkg import helper            # not: import helper
from my_pkg.utils import common      # not: from utils import common
# from . import helper also works under ros2 run
# setup.py
from setuptools import setup, find_packages
setup(
    name='my_pkg',
    packages=find_packages(exclude=['test']),   # not: packages=[package_name]
    ...
)
# and put an empty __init__.py in every subfolder you import (my_pkg/utils/__init__.py)

Then rebuild once without --symlink-install and run the node again. A symlink build can hide a missing subfolder (see below). If the module that fails is a third-party library such as torch, this isn't your problem. Read ros2 run ignores your conda or venv instead.

Cause 1: a bare import of a sibling file

import helper works when you start the file yourself from its folder. In my run, python3 n_bare.py from src/imp_pkg/imp_pkg/ printed OK helper ok with sys.path[0] set to that source folder. Python always puts the started script's folder first on the path. ros2 run starts a different script. It runs a generated wrapper (#!/usr/bin/python3, marked EASY-INSTALL-ENTRY-SCRIPT) in install/imp_pkg/lib/imp_pkg/. In every run, sys.path[0] was install/imp_pkg/lib/imp_pkg, which holds only the wrappers. helper.py sits in site-packages/imp_pkg/, and only site-packages is on the path, not the folder inside it. So import helper finds nothing, while from imp_pkg import helper and from . import helper both loaded site-packages/imp_pkg/helper.py.

That's also what the 13,000-view Stack Overflow question asks: how to keep writing import SimpleOneTrailerSystem instead of import planner_pkg.SimpleOneTrailerSystem. The prefix is the fix, not a workaround. The package name is the only name for your code that's on the path at run time.

Cause 2: the subfolder is never installed

packages=[package_name] names one package and nothing below it. In V1 copy mode, site-packages/imp_pkg/ got __init__.py, helper.py and the node files, but no utils/ directory. So from imp_pkg.utils import common failed with No module named 'imp_pkg.utils', even though utils/__init__.py existed in the source.

Three fixes all installed utils/common.py and made n_sub work in copy mode:

  • packages=find_packages(exclude=['test']) with an __init__.py in utils/ (V2).
  • An explicit list, [package_name, package_name + '.utils'] (V4). Every new subfolder needs a new entry.
  • find_namespace_packages(include=['imp_pkg*']) (V5). This one worked without an __init__.py in utils/.

find_packages() only counts folders with an __init__.py. In V3, I deleted utils/__init__.py. The build succeeded, site-packages had no utils/, and n_sub failed with the same No module named 'imp_pkg.utils'. If you switch to find_packages and the error doesn't change, check for that file.

from utils import common failed in all 12 builds. Even when utils/ was installed, it sat inside imp_pkg/, so its import name is imp_pkg.utils. That's the case in the Robotics Stack Exchange question with from utils import common_utils.

Cause 3: a folder beside the package

The configs/ folder in the "No module named 'configs'" question sits next to the package folder, not inside it. packages=[package_name], the explicit list and find_namespace_packages(include=['imp_pkg*']) all left it out, and from configs import settings failed. find_packages(exclude=['test']) picked it up, because it has an __init__.py. It was installed as a second top-level package, site-packages/configs/, and the import worked.

That works, but your package now ships a module called configs on the shared Python path. I didn't test what happens when two packages in one workspace both install a top-level configs. The safer move is to put the folder inside the package as imp_pkg/configs/ and import from imp_pkg.configs import settings. If the folder holds YAML or JSON rather than Python, install it with data_files to share/ instead. I didn't measure that here.

Cause 4: --symlink-install hides the mistake

This one explains "it works on my machine, but not in Docker or CI". With --symlink-install, colcon didn't copy anything into site-packages. It wrote one file, imp-pkg.egg-link, pointing at build/imp_pkg. And build/imp_pkg/imp_pkg was a symlink to src/imp_pkg/imp_pkg. Python then sees the whole source folder, whatever packages= says. In V1, V3 and V6, n_sub failed in copy mode but printed OK common ok with --symlink-install, loaded from build/imp_pkg/imp_pkg/utils/common.py. Nothing tells you that the release build will fail.

The top-level configs/ didn't get that pass. In symlink mode it was found only when find_packages had listed it (V2, V3). In V1, V4, V5 and V6 it failed as in copy mode.

The same link changes when new files show up. I created imp_pkg/late.py after the build and ran n_late again without rebuilding:

  • Copy mode: still ImportError: cannot import name 'late' from 'imp_pkg', in all six variants. After colcon build, it printed OK late ok.
  • Symlink mode: OK late ok right away, from build/imp_pkg/imp_pkg/late.py.

So when an import fails right after you add a file, and you don't use --symlink-install, rebuild first. To check a setup.py before you ship it, build once without the flag in a clean workspace (rm -rf build install) and start every node.

Another sourced workspace can hide it too

I sourced the V2 workspace and then the V1 workspace in one shell. ros2 pkg prefix imp_pkg reported the V1 install. But n_cfg printed OK settings ok, loaded from /ws_V2copy/install/.../site-packages/configs/settings.py, because the V2 path was still on PYTHONPATH. The broken V1 package only looked fine because of the other workspace. If an import works in one terminal and fails in a fresh one, open a new shell and source only the workspace you mean.

FAQ

Why does my node import its helper file fine with python3 but not with ros2 run?

python3 node.py puts the source folder first on sys.path. ros2 run starts a wrapper in install/<pkg>/lib/<pkg>/, and that folder was sys.path[0] in every run. Your modules are in site-packages/<pkg>/, so they can only be reached as <pkg>.helper. Write from my_pkg import helper.

How do I import a module from a subfolder in a ROS 2 Python package?

Import it as from my_pkg.utils import common. Add an empty __init__.py to utils/ and use packages=find_packages(exclude=['test']) in setup.py. The default packages=[package_name] didn't install utils/ at all.

Why does it work with --symlink-install but fail in Docker or CI?

With --symlink-install, Python reads your source folder through a link, so subfolders missing from packages= still import. A normal build copies only the listed packages. In my run, packages=[package_name] passed with the flag and failed without it on all three distros.

I added a new .py file and get cannot import name from my package. Why?

Without --symlink-install, ros2 run uses the copy in install/, made at the last build. A file added later isn't there until you run colcon build again. With the flag, the new file worked right away.

Should I add my source folder to sys.path or PYTHONPATH?

It isn't needed. Importing through the package name with a complete packages= line worked in every build I ran. I didn't test sys.path edits. A leftover path from another sourced workspace was enough to make a broken package look fine in my run.
