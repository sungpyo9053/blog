The Python and node-name versions look like this:

rclpy.exceptions.InvalidTopicNameException: Invalid topic name: topic name must not contain characters other than alphanumerics, '_', '~', '{', or '}':
  '/cmd-vel'
       ^
rclpy.exceptions.InvalidNodeNameException: Invalid node name: node name must not contain characters other than alphanumerics or '_':
  'my-node'
     ^

Short answer: ROS 2 checks every node name, namespace, topic and service name when you create it. The caret under the name points at the first character it rejected. Node names may only use letters, digits and _. Topic and service names may also use / between tokens, ~/ at the start and {node}-style substitutions. No token may start with a digit. Replace dashes, dots and spaces with _, put a letter before any token that starts with a digit, and remove doubled or trailing slashes. For names built at runtime from a hostname, an IP address or a serial number, clean them up first:

import re

def ros_token(s):
    s = re.sub(r'[^A-Za-z0-9_]', '_', s)
    return 'n' + s if (not s or s[0].isdigit()) else s

def ros_topic(s):
    toks = [ros_token(t) for t in s.split('/') if t]  # drops empty tokens from //, leading or trailing /
    return '/'.join(toks) if toks else 'n'

ros_token('ros-pc-01')                 # 'ros_pc_01'
ros_topic('livox/192_168_0_155/imu')   # 'livox/n192_168_0_155/imu'

Both outputs passed rclpy's validators on Humble, Jazzy and Lyrical. Use any prefix you like instead of n. The only requirement is that the token starts with a letter or _.

Topic and service names

A topic name is split on / into tokens. Every token may only contain letters, digits and _, and it may not start with a digit. The token rule is what catches names built from data. In my run /robot/1/imu failed on the 1 token, and livox/192_168_0_155/imu failed on the 192_168_0_155 token. That second name is the one from the Livox driver issue below, where the topic held the lidar's IP address. Gazebo's joint controller topics hit the same rule with a numeric joint index as one of the tokens.

An empty topic name gets its own message, and it usually means the name came from a parameter that was never set. That was the cause in the ZED wrapper issue, where a missing entry in the YAML file left the topic name empty. If you see topic name must not be empty string, print the parameter that holds the topic name before you look at anything else.

A tilde is allowed only as ~/ at the very start. It expands to the node's own name, so ~/imu on node probe_base became /probe_base/imu. ROS 1 style ~image_captured without the slash failed, as it did in the MAVROS issue below. Curly braces only take substitutions that rcl knows. {node}/status worked and {bad}/x failed. In Python that last one raised a plain ValueError: topic name '{bad}/x' is invalid: unknown substitution: {bad}. In C++ it raised a std::runtime_error with the confusing text topic name unexpectedly valid.

The length limit is 247 characters for the fully expanded name, including the leading slash and any namespace. The error prints the limit as the expression '255U - 8U' instead of a number. The 8 characters are kept back for the DDS prefix, and 255 minus 8 is 247. A topic of 247 characters was accepted and one of 248 failed on every distro.

Service names follow the topic rules exactly. The message just starts with Invalid service name: and keeps the word "topic" in the rest. reset-odom and /1reset failed with the same texts as topics.

Node names and namespaces

Node names are stricter than topic names. Only letters, digits and _ are allowed, with no slash and no tilde, and the name can't start with a digit. The usual way to hit this is a name built at runtime. The fkie multi-agent daemon in the list below names its node after the computer, and a hostname such as robot-pc-01 contains dashes. In my container with that hostname, socket.gethostname() returned robot-pc-01 and failed validate_node_name. The same cleanup turned ros-pc-01 into ros_pc_01, which passed. A hostname that starts with a digit would also break the digit rule.

If you want a node inside a namespace, don't put the slash in the name. Node('ns/node') failed. Passing namespace='/robot1' separately worked and gave /robot1/probe_ns.

The node name length limit isn't 255 in practice. Every node creates parameter services named /<node>/set_parameters_atomically and similar, and those names also have to fit in 247 characters. A node name of 220 characters worked. Every length from 221 to 255 failed with an Invalid service name error, not a node name error. The C++ message printed the service that broke the limit, for example .../set_parameters_atomically at 221 characters and .../get_parameters at 255. Only 256 characters and above gave node name length should not exceed '255'. This applies to nodes at the root namespace. A namespace adds to the service name length, so the safe node name length in a namespace is shorter.

Namespaces use the topic character rules without ~ and {}. /robot-1, /robot.1, /1robot, /robot1/ and //robot1 all failed.

Parameter names are not checked the same way

Parameter names don't go through these checks. declare_parameter accepted max-speed, max.speed, 1speed, max speed and a/b in both rclpy and rclcpp on all three distros. Only an empty name failed, with InvalidParameterException in Python and parameter name must not be empty in C++. A dash in a parameter name won't cause this error. A dash in a topic name that you read from that parameter will.

Version notes

The rules, the exception classes, the 247-character topic limit and the 220-character practical node limit were the same on Humble (rcl 5.3.13, rclpy 3.3.22, rclcpp 16.0.21), Jazzy (rcl 9.2.11, rclpy 7.1.12, rclcpp 28.1.22) and Lyrical (rcl 10.4.5, rclpy 10.0.11, rclcpp 32.0.3). Four differences showed up:

  • ros2 topic echo with an invalid name: Humble printed only topic name is invalid. Jazzy and Lyrical printed the rule that failed.
  • Jazzy and Lyrical printed RuntimeWarning: Failed to fini rosout publisher: rcl node implementation is invalid once, before the first InvalidNodeNameException in the Python probe. It doesn't change the error. Humble didn't print it.
  • The empty parameter name: Humble's message was ('Invalid parameter name', ''), while Jazzy and Lyrical printed Invalid parameter name:.
  • Line numbers in arguments.c and lexer_lookahead.c changed between distros. The remap error text did not.

Not tested

  • Other RMWs. Every run used the default Fast DDS. The 247-character limit comes from rmw and rcl, but I didn't check Cyclone DDS or Zenoh.
  • Action names. I didn't create an action server or client with a bad name.
  • Names given in a params YAML file and read by a real driver (ZED, Livox, MAVROS). I reproduced their error texts with my own nodes, not with their packages.
  • Bridges such as ros_gz_bridge and ros1_bridge, and how they rename topics that break these rules.
  • Rolling and Kilted.

FAQ

Can I use a dash in a ROS 2 topic or node name?

No. A dash failed in topic names, service names, node names and namespaces on Humble, Jazzy and Lyrical, in both rclpy and rclcpp. Use an underscore. Dashes were accepted in parameter names, which aren't checked the same way.

Why does "topic name token must not start with a number" fire on /robot/1/imu?

The rule applies to every token between slashes, not only to the first character of the name. The 1 token broke it. Join the token to the one before it or put a letter first. robot_1/imu and the sanitizer's robot/n1/imu both passed.

What causes "topic name must not be empty string"?

The code passed an empty string as the topic. In driver bug reports this usually comes from a topic-name parameter missing from the YAML file. Print or log that parameter and give it a value.

What is the maximum length of a ROS 2 topic or node name?

The expanded topic name can be 247 characters, which is what the '255U - 8U' message means. A node name in the root namespace failed from 221 characters, because its parameter service names went past 247. 220 worked.

Does ros2 launch catch an invalid node name before starting the process?

For name= and namespace=, yes. Launch printed "Error while expanding or validating node name or namespace" and exited with 1. A bad remap target didn't get that check. The process started, died with exit code -6, and ros2 launch exited with 0.
