[INFO] [1795046662.530581543] [fmt_py]: hello from rclpy

$ export RCUTILS_CONSOLE_OUTPUT_FORMAT='{date_time_with_ms} {time} {message}'
2026-11-19 00:01:25.698 1795046485.006982476 hello from rclpy

The first line is the default ROS 2 console format. The number in the second bracket is seconds since 1970, which nobody can read at a glance. The second line is the token that is supposed to fix that, {date_time_with_ms}, printed next to {time} for the same message on Jazzy. The clock time is right. The milliseconds are not: .006 came out as .698.

Short answer: set the format in the environment before the node starts. Every token is fixed by rcutils, and there is no strftime-style option. {time:%H:%M:%S} and similar guesses are printed literally. For a readable time that you can also trust, print both:

export RCUTILS_CONSOLE_OUTPUT_FORMAT='[{severity}] [{date_time_with_ms}] [{time}] [{name}]: {message}'

{date_time_with_ms} worked on Humble, Jazzy and Lyrical, in rclpy and rclcpp, on screen, in ros2 launch and in the node's log file. But on all three, every line whose milliseconds were below 100 got a wrong millisecond field, so about one line in ten (46 of 400 in my test). Keep {time} next to it, or log {time} only and convert it later with the script further down. The bug is fixed upstream in rcutils, but the Humble, Jazzy and Lyrical packages I tested did not have the fix yet.

What I ran

On 2026-11-19 I ran one script in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one distro after the other, each container with --network none and TZ=UTC. The Python test node is five lines: it creates a node called fmt_py, logs one INFO and one WARN, and exits. For C++ I didn't compile anything. static_transform_publisher from tf2_ros logs one INFO line through rclcpp when it starts, so I ran it with --x 1 --frame-id a --child-frame-id b and stopped it after 3 seconds. Each test changed one thing:

  • 13 single tokens, including five that don't exist, each tested in rclpy and rclcpp.
  • Seven full format strings, among them an empty one, one with no tokens and one with an unclosed brace.
  • {date_time_with_ms} under three TZ values.
  • Colors with RCUTILS_COLORIZED_OUTPUT unset, 0 and 1, through a pipe and under a pseudo-terminal.
  • The node's log file under ROS_LOG_DIR.
  • Five ros2 launch variants.
  • A node with use_sim_time and a /clock at 100.5 s.
  • 20,000 info() calls per format, three rounds, to see if the format costs time.
  • 400 lines logged about 4 ms apart with {time} and {date_time_with_ms} on the same line, then a check of every line, plus 15 C++ starts with the same format.

Edge cases from the same runs:

  • An empty RCUTILS_CONSOLE_OUTPUT_FORMAT='' gave the default [{severity}] [{time}] [{name}]: {message}.
  • A format with no {message} drops the message. 'plain text no tokens' printed that text once per log call, and ' ' printed lines with one space.
  • An unclosed '{message' printed {message and no message.
  • '{{time}} {message}' printed {1795046730.429716628} hello from rclpy. Doubling a brace doesn't escape it. The outer braces stay and the inner token is still replaced.

The Humble documentation page (About logging) doesn't list {date_time_with_ms}. The Jazzy page does, and calls it "The time in ISO format, e.g. 2024-06-11 09:29:19.304". The Humble packages I tested still had it. The output has a space between date and time, not a T, and it has no time zone offset.

The millisecond bug in {date_time_with_ms}

This is the part to read before you rely on readable timestamps. I logged 400 lines about 4 ms apart, each with {time} {date_time_with_ms}, and compared the two fields with Python. The result was the same on every distro:

DistrorcutilsLinesLines with milliseconds below 100Wrong {date_time_with_ms}
Humble5.1.104004646
Jazzy6.7.64004646
Lyrical7.1.34004646

Every line with milliseconds from 000 to 099 was wrong, and every other line was right. Some samples from Humble:

{time}                  {date_time_with_ms}       should be
1795046838.001415242    2026-11-19 00:07:18.141   2026-11-19 00:07:18.001
1795046838.005797156    2026-11-19 00:07:18.579   2026-11-19 00:07:18.005
1795046838.010242319    2026-11-19 00:07:18.102   2026-11-19 00:07:18.010
1795046838.019029199    2026-11-19 00:07:18.190   2026-11-19 00:07:18.019

The pattern is the first three digits of the nanosecond part with its leading zeros removed. 001415242 becomes 1415242, and the first three digits are 141. The date and the seconds come from a separate calculation and were right in every sample. C++ nodes are affected the same way, because rclcpp and rclpy both format through rcutils. Of 15 static_transform_publisher starts, the wrong lines were exactly the ones below 100 ms: 2 on Humble (.078 printed as .780, .038 as .381), 3 on Jazzy (.062 as .628, .076 as .763, .091 as .916) and 1 on Lyrical (.000600654 printed as .600).

In practice, lines can look out of order. On Jazzy, a line logged at .017 printed as .171, so it would show a later time than a line logged at .150 in the same second. The largest error in the samples I printed was on Jazzy, .008463174 shown as .846, 838 ms off. If you match ROS logs against another system's timestamps, an error that size in about one line in ten is enough to send you looking at the wrong event.

The cause is in rcutils' time.c. On the Humble and Jazzy branches, the nanoseconds are printed with "%" PRIu64 (no zero padding) and then cut with ".%.3s". rcutils PR #570, "Fix date_time_with_ms millisecond formatting", changed this to compute milliseconds and print them with %03. It was merged into Rolling on 2026-07-31, and the backport to the Lyrical branch (#608) on 2026-10-05. When I read them on 2026-11-19, the Humble and Jazzy branch sources still had the old code. The Lyrical package I measured was rcutils 7.1.3, built 2026-08-31, before the backport, so it still showed the bug. A newer Lyrical sync should have the fix. I didn't test that.

Workarounds that worked

The first is to print both fields. The format '{date_time_with_ms} {time} {message}' worked on all three distros. You read the date part and trust the seconds, and you check the milliseconds against {time} when they matter.

The second is to keep {time} and convert later. This one-liner rewrites the first [1234567890.123...] field of each line as a UTC date with milliseconds. Unlike rcutils, it slices the fraction string, so it keeps the leading zeros:

python3 -c "import re,sys,datetime as d
for l in sys.stdin: sys.stdout.write(re.sub(r'\[(\d{10})\.(\d+)\]', lambda m: '['+d.datetime.fromtimestamp(int(m.group(1)), d.timezone.utc).strftime('%Y-%m-%d %H:%M:%S')+'.'+m.group(2)[:3]+']', l, 1))" < node.log

On all three distros, [INFO] [1795046837.140108342] [fmt_py]: hello from rclpy became [INFO] [2026-11-19 00:07:17.140] [fmt_py]: hello from rclpy. On Lyrical, Python 3.14 also printed DeprecationWarning: 'count' is passed as positional argument. The output was still correct, and writing count=1 instead of the last 1 should silence it. I ran it only as shown.

The format didn't change logging cost in any way I could measure. For 20,000 rclpy info() calls with stderr sent to /dev/null, the default format, the same with {date_time_with_ms}, and {message} alone all landed in the same range. That was 318 to 336 µs per line on Humble, 309.6 to 331.2 on Jazzy and 244.3 to 256.6 on Lyrical, with no format consistently faster.

{date_time_with_ms} is local time for the process. On Humble, the same node run three times gave:

The output has no offset, so a log file alone doesn't tell you which zone it was written in. All three images had /usr/share/zoneinfo, so TZ passed to the container was enough. If logs from several machines end up in one place, {time} is the safer field.

Sim time does not reach the console

I started a node with use_sim_time set to true and published /clock at 100.5 s from the same process. The node's clock then read 100500000000 ns, but its log line on Humble was stamped [1795046774.679288081] [2026-11-19 00:06:14.679], which is wall time. Jazzy and Lyrical did the same. The console time comes from the system clock and ignores the node's clock. To see sim time in a log line, put self.get_clock().now() in the message. The earlier measurement in Subtraction leads to negative time in rclpy showed that this clock reads 0 until the first /clock arrives. And if you are comparing wall-time log lines with message stamps from a simulator, the gap of billions of seconds described in Message Filter dropping message: find the mismatched clock is that same wall-versus-sim difference.

This cuts both ways. A C++ node run with RCUTILS_CONSOLE_OUTPUT_FORMAT='{message}' wrote a file with only the messages: no severity, no time and no node name. If you strip the console format to make the terminal quieter, you also strip the files you might need later. All three distros did this.

Colors

With RCUTILS_COLORIZED_OUTPUT unset, output through a pipe had no escape codes, and output under a pseudo-terminal (script) had them. 0 turned them off. 1 turned them on even through a pipe: WARN lines were wrapped in ^[[33m ... ^[[0m (yellow) and INFO lines in ^[[0m ... ^[[0m. That is why a log redirected from a forced-color run shows ^[[33m in a text editor. Set RCUTILS_COLORIZED_OUTPUT=0 when you write to files, and 1 when a docker run without -t should still show colors.

Version notes

Token handling, the unknown-token behavior, launch propagation, the log file, colors and the millisecond bug were the same on Humble (rcutils 5.1.10), Jazzy (6.7.6) and Lyrical (7.1.3). Only small things differed. {line_number} for the same static_transform_publisher message was 397 on Humble and Jazzy and 331 on Lyrical. The cost per line was lower on Lyrical's Python 3.14. And Jazzy and Lyrical print a deprecation WARN at startup if ROS_LOCALHOST_ONLY is set. I set it only on Humble so it wouldn't fill the samples, and used ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST everywhere.

FAQ

How do I get a human-readable timestamp in ROS 2 logs?

Before starting the node, set RCUTILS_CONSOLE_OUTPUT_FORMAT='[{severity}] [{date_time_with_ms}] [{name}]: {message}'. It worked in rclpy and rclcpp on Humble, Jazzy and Lyrical. Add {time} too if the milliseconds matter, because of the bug below.

Can I use a strftime pattern like {time:%H:%M:%S}?

No. {time:%H:%M:%S}, {datetime}, {date_time} and {TIME} were all printed literally, with no warning. The time tokens are {time}, {time_as_nanoseconds} and {date_time_with_ms}.

Why are the milliseconds in {date_time_with_ms} wrong sometimes?

The installed rcutils drops the leading zeros of the nanosecond value before taking three digits, so .001415242 prints as .141. All 46 lines below 100 ms out of 400 were wrong on all three distros. rcutils PR #570 fixes it. The packages I tested didn't have it yet.

Does ROS 2 log time follow use_sim_time?

No. With /clock at 100.5 s, the node clock read 100.5 s but the log line showed wall time on all three distros.

Does RCUTILS_CONSOLE_OUTPUT_FORMAT work with ros2 launch?

Yes. Exporting it before ros2 launch, using SetEnvironmentVariable in the launch file, and Node(additional_env=...) for one node all worked. Launch's own [launch] lines kept their own format.
