RESULT default idle once0                 cpu_pct= 100.0 events_per_s=    0.0 os_threads=13 total_events=0

That line is from my Humble run: an rclpy node with no timers and no subscriptions, using a full core. There is no error message for this problem. An rclpy node sits at 100% of a core, or much higher than a C++ node doing the same work, and nothing in the log says why. I measured the usual suspects on Humble, Jazzy and Lyrical: spin loops, timers, subscriptions at 10 to 1000 Hz, and the three executors.

Short answer: if an idle node is at 100%, look for rclpy.spin_once(node, timeout_sec=0) inside a while loop. That single line measured 100.0 to 102.6% CPU with nothing to do, on all three distros. rclpy.spin(node) measured 0.0%. If you need your own loop, give spin_once a real timeout, or move the work into a timer:

# 100% of a core while idle
while rclpy.ok():
    rclpy.spin_once(node, timeout_sec=0)

# 0.0% while idle: let the executor block
rclpy.spin(node)

# 4.2 to 4.5% while idle: blocks up to 10 ms per call
while rclpy.ok():
    rclpy.spin_once(node, timeout_sec=0.01)
    do_other_work()

If the node is busy because it handles a lot of messages, the cost is real work, about 5 to 7% of a core per 100 callbacks per second in my runs. Two things changed that number a lot. MultiThreadedExecutor with the default Fast DDS made a 500 Hz subscriber use about a full core and drop messages. EventsExecutor (Jazzy and Lyrical only) handled the same 500 Hz stream with about 6%.

What I ran

On 2026-11-16 I ran one script, repro.sh, in the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one distro after another, on a 2 vCPU cloud VM with no Docker CPU limit. Each case is a separate Python process running one node. A background thread runs the spin pattern under test. The main thread sleeps 2 seconds, then reads time.process_time() (CPU time of all threads in the process) and counts callbacks over the next 8 seconds. For subscriber cases, a second rclpy process publishes a 16-character std_msgs/String from a timer at 10, 100, 500 or 1000 Hz, and its own CPU and send rate are measured the same way.

The patterns were: rclpy.spin, four spin_once loops, MultiThreadedExecutor().spin() with the default thread count, and rclpy.experimental.EventsExecutor().spin(). Every case ran 3 times on the default RMW. I then installed rmw_cyclonedds_cpp in the same container and repeated the timer and subscriber cases under Cyclone DDS. All DDS traffic stayed on loopback with ROS_DOMAIN_ID=88. The 1-minute load average of the host stayed at or below 1.37 at every checkpoint, so the two cores were never both saturated by something else.

The spin_once(timeout_sec=0) loop

timeout_sec=0 means "check once and return immediately". Inside while rclpy.ok() the loop never waits, so it uses a full core even when the node has no timers, no subscriptions and nothing to do. I measured 100.0 to 100.1% on Humble, 100.1, 101.1 and 102.6% on Jazzy, and 100.0 to 100.2% on Lyrical. Values slightly above 100 are possible because the measurement counts every thread in the process, including the DDS threads.

Adding time.sleep(0.001) after each call brought it down to 11.8 to 15.5%. That's better, but it's still a polling loop: about a thousand wakeups per second for nothing. spin_once(node, timeout_sec=0.01) polls at most 100 times per second while idle and measured 4.2 to 4.5%. Calling spin_once(node) without a timeout measured 0.0%. On all three distros the default is timeout_sec=None, which blocks until something is ready. That is cheap, but it also means the rest of your loop only runs when a callback arrives, which is why people add timeout_sec=0 in the first place.

If you wrote the loop to do periodic work, a timer is the cleaner fix. A 10 Hz timer with an empty callback measured 0.5 to 0.8%. If the loop also sleeps with a rate object, see why rclpy rate.sleep() blocks forever without a spinning thread.

Timers: the cost scales with the rate

An empty timer callback isn't free in Python. On the default executor, 10 Hz cost about 0.6%, 100 Hz about 5%, and 1000 Hz about 25% on Humble and Jazzy and 28.6 to 31.0% on Lyrical. That is roughly 0.25 to 0.3 ms of CPU per callback, all executor overhead because the callback body only adds 1 to a counter. Lyrical's 1000 Hz timer also delivered 991.4 to 1000 callbacks per second, while Humble and Jazzy stayed at 999.5 to 1000.

The same 1000 Hz timer on MultiThreadedExecutor cost 38.7 to 48.7% on Humble and Jazzy and 42.2 to 54.5% on Lyrical, about 1.4 to 1.6 times the single-threaded cost (comparing medians). On EventsExecutor it cost 6.2% on Jazzy and 11.7 to 12.0% on Lyrical.

The coroutine busy-wait from rclpy issue 1405

rclpy issue 1405 reported that an async timer callback awaiting a Future makes every later rclpy.spin_once(node) return immediately, so the loop spins at 100%. It was closed after a fix was merged in December 2025. I ran the issue's pattern, without its debug logging: a 1-second timer whose coroutine awaits a Future() that never completes, driven by a spin_once(node) loop, by rclpy.spin, and by a SingleThreadedExecutor.spin_once() loop. All three measured 0.0 to 0.2% on all three distros, and the coroutine started once per run. These package versions don't show that busy-wait.

FAQ

Why is my idle rclpy node using 100% CPU?

The most likely cause is a loop around rclpy.spin_once(node, timeout_sec=0). It returns immediately, so the loop never waits. That measured 100.0 to 102.6% with no work on Humble, Jazzy and Lyrical. rclpy.spin(node) measured 0.0%.

What timeout should I give spin_once?

Any real timeout stops the busy loop. timeout_sec=0.01 measured 4.2 to 4.5% while idle, and no timeout (the default, which blocks until work arrives) measured 0.0%. A timer callback with rclpy.spin is usually the cleaner design.

Why does MultiThreadedExecutor use more CPU than SingleThreadedExecutor?

With the default Fast DDS in these images, a 500 Hz subscriber used about a full core under MultiThreadedExecutor and received only 190 to 477 of 500 messages per second, depending on the distro. The single-threaded executor used 21 to 28% and received all of them. With Cyclone DDS the multi-threaded executor kept up at 25 to 31%.

How much CPU does an rclpy subscriber need at 1 kHz?

About 38 to 47% of one core on this 2 vCPU VM with the default executor, for a small message and an almost empty callback. The rclpy publisher cost about the same. EventsExecutor cut the subscriber to 10.0 to 10.9% on Jazzy and Lyrical.

Is EventsExecutor available on ROS 2 Humble?

Not in the image I tested. from rclpy.experimental import EventsExecutor failed on Humble with rclpy 3.3.22 and worked on Jazzy (rclpy 7.1.12) and Lyrical (rclpy 10.0.11).
