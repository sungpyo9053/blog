[pnode-1] RESULT py node=/pnode a=f1 b=f1 c=default
[pnode-1] ARGV --ros-args -p a:=rosarg --ros-args --params-file /cfg/f1.yaml

That is the usual way a ROS 2 parameter override fails. There's no error. The node starts, logs the value from the YAML file, and your launch argument or -p value is gone. The second line is the command line that launch_ros built for the node. It put my -p rule first and the params file after it, so the file won.

Short answer: a node collects every parameter source into one ordered list, and for each parameter name the last source in that list wins. A /** entry and an entry with the exact node name rank the same. Only the position counts. To let a launch argument override a YAML file, put the dict after the file:

DeclareLaunchArgument('a', default_value='argdefault'),
Node(package='pk', executable='pnode',
     parameters=['/cfg/f1.yaml', {'a': LaunchConfiguration('a')}])   # file first, dict last

With a:=fromcli on the command line the node got a=fromcli and kept b=f1 from the file. With the dict first, the same command gave a=f1. One catch: once the dict is in the list, the launch argument always replaces the file value. Without a:=... the node got a=argdefault, not f1. The one source that beat everything else was parameter_overrides passed in the node's own code.

What I ran

On 2026-11-22 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro after another, on a 2 vCPU machine with no network in the container. One ament_cmake package held both nodes. The Python node, pnode, also printed its own argv and the content of every params file it received. That's how I saw what launch_ros passes. The C++ node, cnode, uses rclcpp::NodeOptions and the same names. The package built in 5.4 s on Humble, 5.6 s on Jazzy and 7.4 s on Lyrical.

Each distro got 23 command-line cases through ros2 run and 17 launch cases through ros2 launch, each run once with each node. That makes 80 runs per distro. 70 printed a result on Humble and Jazzy, and 72 on Lyrical. The other runs failed on purpose, in the type cases further down. The order results were identical on all three distros and in both languages.

The rule: last source wins, per parameter

The --ros-args part of a command line is read from left to right. Every --params-file and every -p adds overrides to one list, and a later entry for the same name replaces an earlier one. Inside a single YAML file, entries are taken from top to bottom. A /** entry doesn't lose to an entry with the exact node name just because it's less specific. In my run, a /** entry below a /pnode entry in the same file won, and so did a /** file passed after an exact-name file.

When a node isn't matched, the entry is skipped. -p other:a:=prefixed left a=default and printed nothing. The same happened when the launch file renamed the node with name='imu' and the YAML still said /pnode. The node became /imu and kept every default. The params YAML and -p errors post measured that silent skip for a wrong node-name key, plus each parse error rcl prints for broken params files. If your values never apply at all, start there. If they apply but the wrong one wins, this post is about that case.

What launch_ros builds from your Node()

You don't write the node's command line in a launch file, so the order is set for you. My node printed it:

parameters=[f1, {'a': 'dict'}]                      -> --ros-args --params-file /cfg/f1.yaml --params-file /tmp/launch_params_X
parameters=[{'a': 'dict'}, f1]                      -> --ros-args --params-file /tmp/launch_params_X --params-file /cfg/f1.yaml
SetParameter('a', 'global'), Node(parameters=[f1])  -> --ros-args -p a:=global --params-file /cfg/f1.yaml
ros_arguments=['-p', 'a:=rosarg'], parameters=[f1]  -> --ros-args -p a:=rosarg --ros-args --params-file /cfg/f1.yaml
arguments=['--ros-args', '-p', 'a:=arg'], [f1]      -> --ros-args -p a:=arg --ros-args --params-file /cfg/f1.yaml
SetParametersFromFile(f2), Node(parameters=[f1])    -> --ros-args --params-file /cfg/f2.yaml --params-file /cfg/f1.yaml
name='imu', parameters=[f1]                         -> --ros-args -r __node:=imu --params-file /cfg/f1.yaml

Four things follow from that:

  • The parameters list keeps its order. Each dict becomes a temporary YAML file under /**, placed where the dict was in the list. That's why a dict after a file wins and a dict before it loses.
  • Your parameters always come last. -p rules from ros_arguments or arguments were put in front of the params files. So they can't override anything the node's parameters set. They only work for names the node's parameters don't set.
  • SetParameter and SetParametersFromFile are defaults, not overrides. They go in front too. SetParameter set a=global only when the node's own list didn't set a. It also had to come before the Node action. Placed after, it was missing from the command line.
  • The node name is part of the match. Renaming the node in the launch file changes which YAML keys apply.

Launch arguments that never override the file

This is the setup from the most viewed question below. A YAML file holds the defaults, and the launch argument is meant to change one of them. In my run, the order of the parameters list was the whole difference:

parameters=CommandNode got
[f1, {'a': LaunchConfiguration('a')}]ros2 launch ... a:=fromclia=fromcli b=f1
[f1, {'a': LaunchConfiguration('a')}]ros2 launch ...a=argdefault b=f1
[{'a': LaunchConfiguration('a')}, f1]ros2 launch ... a:=fromclia=f1 b=f1

The second row is easy to miss. A launch argument with a default always has a value, either the one you typed or the default. A dict after the file therefore replaces the file's value on every launch. If the YAML file should stay the source of truth for that key, make the argument's default the same value or leave that key out of the file. I didn't test a conditional that adds the dict only when the argument is given.

The question was asked on Foxy, which I didn't test. One answer there says that changing the YAML key from the node name to /** made the override work. On Humble, Jazzy and Lyrical the key made no difference. Order alone decided.

Launch arguments are strings, and launch does no arithmetic on them. The LaunchConfiguration value as int post measured that [a, b] with values 2 and 5 became the string '25' and reached a node as the integer 25. The next section shows the same thing for yes.

parameter_overrides in code beats everything

Both client libraries let the node's own code pass overrides: Node('pnode', parameter_overrides=[Parameter('a', value='code')]) in rclpy and NodeOptions().parameter_overrides(...) in rclcpp. In my run that value won over -p a:=cli, over a params file and over a launch dict. The file still set b=f1, because the code only overrode a. With use_global_arguments set to false as well, -p a:=cli was ignored and a=code again.

That makes parameter_overrides handy in tests, where you build the same node several times with different values in one process. That's what one of the questions below asks for. It's the wrong tool for a value someone should be able to change at launch time, because nothing outside the code can replace it.

My first precedence test used -p a:=x -p a:=y, and it didn't test precedence at all. The node crashed:

Version notes

The order results were the same on Humble, Jazzy and Lyrical, in rclpy and rclcpp. Four things differed:

  • A launch dict string such as 'y' stayed a string on Lyrical and became BOOL on Humble and Jazzy, as shown above.
  • Lyrical's launch_ros wrote the temporary params file with every key and value in double quotes. Humble and Jazzy wrote plain YAML.
  • On Jazzy and Lyrical, rclpy's InvalidParameterTypeException message ends with : a, the parameter name repeated. Humble's ends after expecting type 'STRING'.

FAQ

Which wins in ROS 2, the YAML params file or the launch file parameters?

Whichever comes later in the node's parameters list. parameters=[file, {'a': 'dict'}] gave a=dict, and parameters=[{'a': 'dict'}, file] gave the file's value. That held on Humble, Jazzy and Lyrical, in Python and C++ nodes.

Why doesn't my launch argument override the value in my YAML file?

Most likely the dict with the LaunchConfiguration is before the file, or the value is passed with ros_arguments or arguments. Both end up in front of the params file on the node's command line, so the file wins. Put the dict after the file in parameters.

Does a node-specific YAML entry beat a /** entry?

Not on Humble, Jazzy or Lyrical. The later entry won, whether both were in one file or in two files. A /** entry below a /pnode entry replaced it.

Does SetParameter override a node's parameters?

No. launch_ros passed it as a -p rule before the node's params files, so a value set in the node's own parameters won. SetParameter also has to come before the Node action. Placed after it, it didn't reach the node.

Why does -p a:=y or yes fail on a string parameter?

The value is parsed as YAML, and y, yes and on become a bool. The node then fails with InvalidParameterTypeException. Quote it: -p "a:='y'" on the command line, or a: "yes" in a YAML file.
