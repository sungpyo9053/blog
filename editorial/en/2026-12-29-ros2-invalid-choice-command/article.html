$ ros2 control list_controllers
usage: ros2 [-h] [--use-python-default-buffering]
            Call `ros2 <command> -h` for more detailed usage. ...
ros2: error: argument Call `ros2 <command> -h` for more detailed usage.: invalid choice: 'control' (choose from 'action', 'bag', 'component', 'daemon', 'doctor', 'extension_points', 'extensions', 'interface', 'launch', 'lifecycle', 'multicast', 'node', 'param', 'pkg', 'plugin', 'run', 'security', 'service', 'topic', 'wtf')

The related message is Failed to load entry point 'record': ..., which you see when a command is installed but its Python code can't be imported.

Short answer: "invalid choice" means no installed Python package told ros2 about that command, so the list in brackets is every command ros2 knows. Compare your word against that list. If it's a typo, fix the spelling. If the command is missing, install the package that provides it, or source the workspace that contains it. For ros2 control that is:

sudo apt install ros-$ROS_DISTRO-ros2controlcli
ros2 control -h      # worked in the same shell, no re-source needed

"Failed to load entry point 'x'" is a different problem. The command is registered, but importing its module failed. The text after the colon is the real error, for example No module named ... or a missing shared library. Fix that import and the command comes back.

What I ran

One script, repro.sh, ran as root inside each image on a 2 vCPU Linux host, one distro after another. It:

  • printed the command list from ros2 --help and which package registers each command,
  • called a command that isn't installed (ros2 control), three typos and a subcommand typo,
  • installed ros2controlcli with apt and called it again in the same shell,
  • built a one-file workspace package that adds a ros2 hello command, then called it unsourced, sourced, with a broken import and with a wrong class name,
  • removed LD_LIBRARY_PATH, PYTHONPATH and AMENT_PREFIX_PATH one at a time, and ran ros2 through sudo,
  • timed ros2 --help and an invalid command five times each.

The ros-base images list the same 20 command names on all three distros: action, bag, component, daemon, doctor, extension_points, extensions, interface, launch, lifecycle, multicast, node, param, pkg, plugin, run, security, service, topic and wtf. The one you most often need beyond that, control, isn't there.

A command that isn't installed

ros2 has no built-in list of commands. Every command is a Python entry point in the group ros2cli.command, and each comes from a separate package. This one-liner printed which package registered each command in my images:

python3 -c "from importlib.metadata import distributions as d; [print(e.name, '->', x.metadata['Name']) for x in d() for e in x.entry_points if e.group == 'ros2cli.command']" | sort
action -> ros2action
bag -> ros2bag
...
plugin -> ros2plugin
run -> ros2run
security -> sros2
service -> ros2service
topic -> ros2topic
wtf -> ros2doctor

The apt name is that package name with ros-<distro>- in front and underscores turned into dashes. To find the package for a command you don't have yet, search apt:

apt-cache search --names-only "^ros-$ROS_DISTRO-ros2[a-z]"

On all three distros that search listed ros2controlcli, ros2plugin, ros2test, ros2trace, ros2acceleration and ros2nodl among others. Installing ros2controlcli took this much:

Install time is the apt-get install alone, after an apt-get update that took another 7.3 to 9.9 s. Right after the install, ros2 control -h worked in the same shell on all three distros. I didn't re-source anything. ros2 scans the installed packages each time it starts, so a new apt package shows up on the next call. Jazzy and Lyrical listed one more subcommand than Humble, cleanup_controller.

With nothing else running, ros2 control list_controllers printed waiting for service /controller_manager/list_controllers to become available... and then Could not contact service after 10 seconds. That's a different problem: the command exists, but no controller manager is running. If you get that message, start your ros2_control launch first.

ros2 plugin is worth a mention because one of the questions below asks why it's missing. In the ros-base images it was present on all three distros, provided by ros2plugin. If your install doesn't have it, ros-<distro>-ros2plugin is the package to install. I didn't test a minimal install where it's missing.

Typos: no suggestions, exact case

ros2 topics list and ros2 Topic list both failed with "invalid choice", exit code 2, on every distro. No version printed a "did you mean" hint, not even Lyrical, which runs Python 3.14. Matching is case-sensitive, so Topic doesn't match topic.

The prefix of the message tells you which word was wrong. ros2: error: refers to the first word. ros2 topic: error: or ros2 bag: error: refers to the second word, and the list in brackets is that command's subcommands:

ros2 bag: error: argument Call `ros2 bag <command> -h` for more detailed usage.: invalid choice: 'recrod' (choose from 'burst', 'convert', 'info', 'list', 'play', 'record', 'reindex')

That output is from Jazzy. Humble's list was the same without burst. A subcommand list is a quick way to check whether a tutorial was written for a newer distro than yours.

Your own command: build, then source

A package can add its own ros2 command through an entry point in setup.py. Mine was:

entry_points={'ros2cli.command': ['hello = my_cli.command.hello:HelloCommand']}

HelloCommand subclasses ros2cli.command.CommandExtension and prints one line. colcon build finished in 1.33 s on Humble and 1.70 s on Jazzy and Lyrical. Then:

StateResult of ros2 helloExit
Built, install/setup.bash not sourcedinvalid choice: 'hello'2
Sourcedhello from my_cli, and hello appeared in ros2 --help0
Sourced, import this_module_does_not_exist at the top of the moduleFailed to load entry point 'hello': No module named 'this_module_does_not_exist', then a traceback ending in KeyError: 'hello'1
Sourced, entry point says HeloCommandFailed to load entry point 'hello': module 'my_cli.command.hello' has no attribute 'HeloCommand', then KeyError: 'hello'1

The build finished without errors in both broken cases. colcon doesn't import your command module, so a broken import only shows up when you run the command.

The KeyError traceback looks like a bug in ros2cli, but it's a side effect. The first line already gave the cause. Fix that import and the traceback goes away.

A broken command didn't break the others. With the bad import in place, ros2 topic list, ros2 topic list --no-daemon and ros2 node list all ran normally with exit 0 and no warning. ros2 --help printed the Failed to load entry point line, then left hello out of the list. So if one command has disappeared from ros2 --help, run ros2 --help and look for that line at the top.

The same message appears when the failing import is inside an installed package. In the Windows question below, it was DLL load failed while importing _reader for ros2 bag record. I didn't reproduce that one, because it needs a Windows install. The fix follows the same logic: read the text after Failed to load entry point 'x': and fix that import.

Missing environment variables

The setup script sets PATH, LD_LIBRARY_PATH, PYTHONPATH and AMENT_PREFIX_PATH. I removed them one at a time after sourcing:

RemovedResult
LD_LIBRARY_PATHEvery command, even ros2 --help, failed with ImportError: librcl_action.so: cannot open shared object file and a note that the rclpy C extension "failed to be imported while being present on the system". Exit 1
PYTHONPATHimportlib.metadata.PackageNotFoundError: No package metadata was found for ros2cli. Exit 1
AMENT_PREFIX_PATHros2 topic list and ros2 --help still worked. Exit 0

That last row matters. The command list comes from Python package metadata on PYTHONPATH, not from the ament index. So "invalid choice" is never caused by a missing AMENT_PREFIX_PATH.

On Humble the LD_LIBRARY_PATH traceback was 31 lines, on Jazzy 38 and on Lyrical 34. Jazzy and Lyrical point to their own troubleshooting page. Humble's link still has a literal {distro} in it.

sudo

Running ros2 under sudo is the most common way to lose these variables. Inside the containers, sudo -E kept AMENT_PREFIX_PATH, set PATH to its own secure path and emptied LD_LIBRARY_PATH and PYTHONPATH. The -E flag did not stop that. The results:

CommandResult
sudo -E ros2 topic listsudo: ros2: command not found
sudo env PATH=$PATH ros2 topic listPackageNotFoundError: ... ros2cli
sudo -E env PATH=$PATH LD_LIBRARY_PATH=$LD_LIBRARY_PATH PYTHONPATH=$PYTHONPATH ros2 topic listworked
sudo bash -c 'source /opt/ros/$ROS_DISTRO/setup.bash ...'worked

Sourcing inside the sudo shell is shorter and also picks up any workspace you add to the same line. The same problem shows up in cron jobs, systemd units and IDE run configurations that don't source anything. Source the setup file in the command that runs ros2. If ros2 itself is not found, see ros2: command not found and local_setup.bash vs setup.bash.

Version notes

  • The failing call itself is fast. ros2 nosuchverb exited after 136 to 141 ms on Humble, 183 to 189 ms on Jazzy and 285 to 289 ms on Lyrical. A full ros2 --help took 396 to 406 ms, 470 to 496 ms and 488 to 496 ms.
  • Lyrical prints the choices without quotes, for example (choose from action, bag, component, ...). Humble and Jazzy quote each name. If you search for the error text, try both forms.
  • ros2 bag on Jazzy and Lyrical has a burst subcommand that Humble lacks.
  • ros2 control on Jazzy and Lyrical has cleanup_controller. Humble's ros2controlcli 2.54.3 doesn't.
  • The ros-base images ship the same 20 command names on all three distros, including plugin.

FAQ

What does "invalid choice" mean in ros2?

No installed Python package registered that command, so argparse rejected it with exit code 2. The list in brackets is every command ros2 found. Your word is either misspelled or its package isn't installed or sourced.

How do I fix ros2: invalid choice: 'control'?

Install ros-$ROS_DISTRO-ros2controlcli. In my test, ros2 control -h worked in the same shell right after the install, without re-sourcing, on Humble, Jazzy and Lyrical.

My own ros2 command says invalid choice after colcon build. Why?

The workspace wasn't sourced. After source install/setup.bash the command ran and appeared in ros2 --help. Without it, I got invalid choice with exit code 2.

What does "Failed to load entry point" mean?

The command is registered, but importing its module failed. The text after the colon is the real error, such as No module named ... or a missing class. The KeyError traceback that follows is a side effect. Other ros2 commands kept working.

Why does ros2 fail under sudo?

sudo reset PATH and emptied LD_LIBRARY_PATH and PYTHONPATH, even with -E. The result was sudo: ros2: command not found or PackageNotFoundError. Running sudo bash -c 'source /opt/ros/$ROS_DISTRO/setup.bash ...' fixed it.
