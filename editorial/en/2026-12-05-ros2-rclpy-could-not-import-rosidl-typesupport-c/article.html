Short answer: the last line is a wrapper. rclpy tried to load the compiled C part of your message package and failed. The real reason is the first exception, above "During handling of the above exception". In my runs it was one of two things. Either the interface package was built while a different Python was first on PATH (a venv, conda or uv environment), or the workspace's lib directory was missing from LD_LIBRARY_PATH. For the first case, this fixed it on Humble, Jazzy and Lyrical:

deactivate            # or: conda deactivate
cd ~/ws
rm -rf build/my_msgs install/my_msgs
colcon build --packages-select my_msgs
source install/setup.bash

A plain colcon build after deactivate does not fix it. CMake keeps the old Python in its cache, and the rebuilt package was still broken on all three distros. For the second case, source install/setup.bash instead of adding the workspace to PYTHONPATH by hand.

What I ran

On 2026-11-03 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images, one container per distro, run one after another on a 2 vCPU Linux host. The workspace had one ament_cmake interfaces package, my_msgs, with msg/Num.msg containing int64 num. The test script imports my_msgs.msg.Num, creates a node and a publisher, publishes once and prints OK publisher created and published my_msgs.msg.Num(num=5).

For the "other Python" case I installed CPython 3.11.11 with uv 0.5.31 and made a venv with empy (the same version as the distro's system package), catkin_pkg, lark, numpy and setuptools. With those installed, colcon builds the interfaces without any error. That is what makes this case hard to spot. The build is green and the failure only shows up at runtime. Python 3.11 differs from the system Python on all three distros: 3.10.12 on Humble, 3.12.3 on Jazzy, 3.14.4 on Lyrical.

The baseline build with the system Python worked on every distro. It took 8.0 s on Humble, 10.4 s on Jazzy and 11.7 s on Lyrical, and the script printed the OK line.

Cause 1: interfaces built with a different Python

I activated the 3.11 venv and ran a clean colcon build --packages-select my_msgs. It finished with exit code 0 on all three distros (8.9 s, 10.4 s and 14.3 s). Then I deactivated the venv, sourced the workspace in a new shell and ran the script with /usr/bin/python3. It failed at create_publisher with the error at the top of this page, exit code 1.

The install tree shows why. CMake had picked up python3 from the venv. On Humble the cache said so directly:

PYTHON_EXECUTABLE:FILEPATH=/venv311/bin/python3 Python3_EXECUTABLE:FILEPATH=/venv311/bin/python3

The Python package went to install/my_msgs/lib/python3.11/site-packages/my_msgs on all three distros, instead of the system Python's directory (local/lib/python3.10/dist-packages on Humble, lib/python3.12/site-packages on Jazzy, lib/python3.14/site-packages on Lyrical). After sourcing install/setup.bash, the system Python still imported the message class from that 3.11 directory (the traceback shows .../lib/python3.11/site-packages/my_msgs/msg/_num.py), and from my_msgs.msg import Num worked on its own. The pure-Python message class loaded. Only the compiled part did not.

On Humble the compiled modules carry the Python version in their names:

my_msgs_s__rosidl_typesupport_c.cpython-311-x86_64-linux-gnu.so
my_msgs_s__rosidl_typesupport_fastrtps_c.cpython-311-x86_64-linux-gnu.so
my_msgs_s__rosidl_typesupport_introspection_c.cpython-311-x86_64-linux-gnu.so

Python 3.10 only looks for .cpython-310-x86_64-linux-gnu.so, .abi3.so and .so. It skips these files, so the inner error is No module named 'my_msgs.my_msgs_s__rosidl_typesupport_c', even though a file with that name is in the directory.

On Jazzy and Lyrical the modules have no version tag. They are just my_msgs_s__rosidl_typesupport_c.so. The system Python finds the file and tries to load it, and the loader fails because the module was linked against the other interpreter:

ImportError: libpython3.11.so.1.0: cannot open shared object file: No such file or directory

That line is a strong hint. If the number in libpython3.X is not your ROS Python version, the package was built with another Python.

The CLI fails the same way. ros2 topic pub --once /num my_msgs/msg/Num "{num: 1}" exited with code 1 and the same UnsupportedTypeSupport line on all three distros. ros2 interface show my_msgs/msg/Num worked and printed int64 num, because it only reads the interface definition. A working interface show doesn't prove that the build is usable from Python.

Running the script with the venv still active gave a different error. On Humble and Lyrical it was ModuleNotFoundError: No module named 'rclpy._rclpy_pybind11', because rclpy itself is compiled for the system Python. On Jazzy it failed even earlier, with ModuleNotFoundError: No module named 'yaml'. If that is what you see, the rclpy import post covers it.

Check it in ten seconds

Source the workspace and run this with the same python3 you use for your nodes:

import importlib.util, importlib.machinery, glob, os
spec = importlib.util.find_spec('my_msgs')
d = os.path.dirname(spec.origin)
print('package dir:', d)
print('this python wants:', importlib.machinery.EXTENSION_SUFFIXES[0])
for f in sorted(glob.glob(d + '/*.so')): print('found:', os.path.basename(f))

On the broken Humble build it printed:

package dir: /ws/install/my_msgs/lib/python3.11/site-packages/my_msgs
this python wants: .cpython-310-x86_64-linux-gnu.so
found: libmy_msgs__rosidl_generator_py.so
found: my_msgs_s__rosidl_typesupport_c.cpython-311-x86_64-linux-gnu.so
found: my_msgs_s__rosidl_typesupport_fastrtps_c.cpython-311-x86_64-linux-gnu.so
found: my_msgs_s__rosidl_typesupport_introspection_c.cpython-311-x86_64-linux-gnu.so

On Jazzy and Lyrical the file names don't show the version, so look at the package directory instead. python3.11 in that path, when your ROS Python is 3.12 or 3.14, is the same problem.

Cause 2: the workspace lib directory is not on LD_LIBRARY_PATH

This one comes from setting up the environment by hand, as some IDE run configurations do. I built my_msgs normally with the system Python. Then I sourced only /opt/ros/<distro>/setup.bash and added the package's Python directory to PYTHONPATH myself. The import worked, and create_publisher failed with the same outer error on all three distros. The first exception was:

ImportError: libmy_msgs__rosidl_generator_py.so: cannot open shared object file: No such file or directory

The compiled module depends on three libraries from the package itself, and it has no RPATH or RUNPATH. ldd without the workspace on LD_LIBRARY_PATH showed:

libmy_msgs__rosidl_generator_py.so => not found
libmy_msgs__rosidl_typesupport_c.so => not found
libmy_msgs__rosidl_generator_c.so => not found

Adding /ws/install/my_msgs/lib to LD_LIBRARY_PATH made the script print the OK line on all three distros. Sourcing install/setup.bash does the same thing for every package in the workspace. After sourcing it, LD_LIBRARY_PATH had the my_msgs entry on every distro, and the script worked. In an IDE, the simplest fix is to start the IDE from a shell where the workspace is already sourced.

What did not give this error

These came up in the questions I read. In my runs each one failed with a different error, so you can rule them out when you see UnsupportedTypeSupport.

  • No LD_LIBRARY_PATH at all (env -u LD_LIBRARY_PATH python3 t.py). rclpy failed first with ImportError: librcl_action.so: cannot open shared object file. A plain std_msgs script failed the same way. A missing LD_LIBRARY_PATH breaks your message package only if /opt/ros is still on it, as in cause 2.
  • sudo. Inside the containers, running as root, both sudo and sudo -E dropped PYTHONPATH and LD_LIBRARY_PATH. The script failed with ModuleNotFoundError: No module named 'rclpy'. Passing LD_LIBRARY_PATH through sudo -E env ... still failed the same way, because PYTHONPATH was gone. This worked: sudo bash -c "source /opt/ros/$ROS_DISTRO/setup.bash && source /ws/install/setup.bash && python3 /ws/t.py".
  • Missing DEPENDENCIES in rosidl_generate_interfaces. I added msg/Pose2.msg with a geometry_msgs/Point field and left out DEPENDENCIES geometry_msgs. The build failed on every distro, so nothing reached runtime. On Humble the error was fatal error: geometry_msgs/msg/detail/point__struct.hpp: No such file or directory. On Jazzy and Lyrical it was KeyError: 'geometry_msgs' from rosidl_generator_type_description. With DEPENDENCIES geometry_msgs the build finished and a Pose2 publisher was created. Older answers that blame missing dependencies for the runtime error come from older distros. I did not test those.

For cause 1 I went back to the broken 3.11 build before each fix, deactivated the venv (except in the last row), ran the fix and then the script. Times are colcon wall time on Humble / Jazzy / Lyrical.

The fast commands are fast because they skip the step that matters. Anything that keeps CMakeCache.txt keeps the wrong Python. The two fixes that worked after deactivate cost about as much as a clean build of the package, and rm -rf also removes the stale 3.11 files. If you must keep a venv active while building, pass both -D flags. I only tested that from a clean build.

For cause 2 the fix is to source install/setup.bash, or to add install/<pkg>/lib to LD_LIBRARY_PATH. Both worked on all three distros, and no rebuild was needed.

Version notes

  • Humble (rclpy 3.3.22, rosidl_generator_py 0.14.6): the typesupport modules carry the cpython-310 tag, so a mismatch shows up as ModuleNotFoundError for my_msgs_s__rosidl_typesupport_c. CMakeCache has PYTHON_EXECUTABLE and Python3_EXECUTABLE, both set to the venv path.
  • Jazzy (rclpy 7.1.12, rosidl_generator_py 0.22.2): the modules are plain .so files with no version tag, so a mismatch shows up as ImportError: libpython3.11.so.1.0. Running with the venv active failed on No module named 'yaml' before reaching rclpy's C extension.
  • Lyrical (rclpy 10.0.11, rosidl_generator_py 0.27.2, Python 3.14.4): same as Jazzy for both causes. The traceback is longer because of Python 3.14's caret markers, but the first exception and the last line were the same.
  • The fix results were the same on all three distros.

Not tested

Not tested: conda environments (I used a uv venv, which I expect to behave the same but did not check), a venv with the same Python minor version as ROS, ament_python packages run through ros2 run, rclcpp, building in one image and running in another, overlays where a dependency message package was rebuilt underneath, --symlink-install, --merge-install, Windows, macOS, ARM, distros older than Humble, Cyclone DDS and other RMWs, and sudo as a non-root user with custom env_keep rules.

FAQ

What does Could not import 'rosidl_typesupport_c' for package mean?

rclpy found the Python message class but could not load its compiled typesupport module. The first exception in the traceback says why. In my runs it was either a build made with another Python, or a missing workspace lib directory on LD_LIBRARY_PATH.

The build succeeded. Why does it fail only at runtime?

colcon reported success with a venv Python 3.11 on all three distros. The import also worked. The compiled part is only loaded when you create a publisher, subscription or service, or run ros2 topic pub, so that is where it failed.

I deactivated conda or the venv and rebuilt. Why is it still broken?

CMakeCache.txt still holds the old interpreter. A plain rebuild and --cmake-force-configure both left the package broken. --cmake-clean-cache or deleting build/<pkg> and install/<pkg> fixed it on Humble, Jazzy and Lyrical.

What does ImportError: libpython3.11.so.1.0 mean here?

On Jazzy and Lyrical the typesupport module was linked against Python 3.11 while ROS runs a different Python. Rebuild the interface package with the system Python. On Humble the same mismatch shows up as No module named ..._s__rosidl_typesupport_c.

Is ros2 interface show working enough to prove the package is fine?

No. In the broken 3.11 build, ros2 interface show my_msgs/msg/Num printed int64 num on all three distros, while ros2 topic pub and the Python publisher failed.
