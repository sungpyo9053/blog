import message_filters
sa = message_filters.Subscriber(node, PointStamped, 'a')
sb = message_filters.Subscriber(node, PointStamped, 'b')
ts = message_filters.TimeSynchronizer([sa, sb], 10)
ts.registerCallback(callback)   # never called, no error printed

Most of the time a message_filters synchronizer that never fires prints nothing. In two of the cases I measured you get one of these instead:

[WARN] [sync_py]: New publisher discovered on topic 'a', offering incompatible QoS. No messages will be received from it. Last incompatible policy: RELIABILITY

[WARN] [message_filters_approx]: can not use message filters for messages without timestamp infomation when 'allow_headerless' is disabled. auto assign ROSTIME to headerless messages once enabling constructor option of 'allow_headerless'.

Short answer: check three things in this order. First, does each input Subscriber get messages at all? Register a plain callback on each one. If the count is 0, it's QoS: pass the publisher's QoS to the message_filters Subscriber. Second, if both inputs get messages, compare the header.stamp values. TimeSynchronizer needs stamps that are equal to the nanosecond. If yours differ even by 1 ms, use ApproximateTimeSynchronizer with a slop larger than the real gap. Third, if one topic lags the other, make queue_size bigger than lag times rate. This Python setup fired on every message in my runs, on Humble, Jazzy and Lyrical:

from rclpy.qos import qos_profile_sensor_data
sa = message_filters.Subscriber(node, PointStamped, 'a', qos_profile=qos_profile_sensor_data)
sb = message_filters.Subscriber(node, PointStamped, 'b', qos_profile=qos_profile_sensor_data)
ts = message_filters.ApproximateTimeSynchronizer([sa, sb], queue_size=10, slop=0.1)
ts.registerCallback(callback)

In C++, also keep the Subscriber objects and the synchronizer as class members. A synchronizer created as a local variable in the constructor got 0 callbacks, and local subscribers crashed the node on Humble.

What I ran

On 2026-11-04 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after another, with the default RMW (Fast DDS). A Python publisher sent geometry_msgs/PointStamped on /a and /b at 10 Hz for 5 seconds. Its arguments set the stamp offset of /b, the QoS, the two rates, a zero stamp, or a header-less std_msgs/String. Two subscribers ran against it, one in rclpy and one in rclcpp. Each started 1 second before the publisher and ran for 7 seconds. Each counted the raw messages on both inputs and the synchronized callbacks. The script ran 19 Python cases and 11 C++ cases per distro. It also built eight small C++ packages that only check whether a given API call compiles. The script, repro.sh, is in the evidence folder.

Exact time means the same nanosecond

TimeSynchronizer uses the ExactTime policy. It only pairs messages whose header.stamp values are equal. A 1 ms difference gave 0 callbacks, and so did the common pattern of stamping each message with its own get_clock().now() call in the same timer callback. Those two calls are microseconds apart, which is enough. Nothing warns you. Both input subscribers kept counting up to 50 while the synchronized count stayed at 0.

Exact sync only fits when both messages get their stamp from one source. The stereo pair from one driver or an image with its camera_info are examples. If the stamps come from two sensors or two now() calls, switch to ApproximateTimeSynchronizer. If you control the publisher, the other fix is to read the clock once and copy the stamp into both messages. That's the case that gave 50 out of 50 above.

slop is a hard limit in Python, and C++ has none by default

In rclpy, ApproximateTimeSynchronizer(fs, queue_size, slop) drops any set whose stamps are further apart than slop seconds. With stamps 50 ms apart, slop=0.1 gave 50 callbacks and slop=0.01 gave 0. Two separate now() calls were close enough for slop=0.01, which gave 50. Set slop above the real gap between your sensors and below the period of the fastest topic, so each message can only pair with one partner.

The C++ sync_policies::ApproximateTime constructor takes only a queue size. In my runs it paired messages 50 ms apart (49 callbacks) and also messages 900 ms apart (41 callbacks) on all three distros. So in C++ the usual problem isn't a missed pair. You may get pairs that are too far apart. The policy has a setMaxIntervalDuration() call for a hard limit, but I didn't test it.

Both languages gave 0 callbacks when one topic left header.stamp at zero, and neither printed a warning. If one of your drivers doesn't fill in the stamp, approximate sync can't fix that. Fill in the stamp at the source.

QoS: the input Subscriber has its own QoS

A message_filters.Subscriber creates a normal subscription. In Python its default is QoSProfile(depth=10), which is reliable. In my run, a best-effort publisher, which is what most sensor drivers use, was rejected before message_filters saw anything. Both inputs counted 0 messages, and the only sign was one "incompatible QoS" warning per topic at startup. Passing qos_profile=qos_profile_sensor_data fixed it (50 / 50 / 50). A best-effort subscriber also received from a reliable publisher in my run, so the sensor profile is the safer choice when you don't know the publisher's QoS. Run ros2 topic info -v /your_topic to see what the publisher offers.

C++ gave the same 0 / 0 / 0 result with a warning ending in RELIABILITY_QOS_POLICY. Which QoS type the C++ API takes depends on the distro:

#if __has_include(<message_filters/subscriber.h>)   // Humble, Jazzy
  sub_a_.subscribe(this, "a", rmw_qos_profile_sensor_data);
#else                                                 // Lyrical
  sub_a_.subscribe(this, "a", rclcpp::SensorDataQoS());

queue_size has to cover the lag

When one topic arrives late, for example a processed point cloud stamped with the time its scan started, the synchronizer has to keep the other topic's messages until the late one shows up. I stamped /b 500 ms in the past at 10 Hz, so the matching /a message was 5 messages back. With slop=0.1, queue sizes 1 and 3 gave 0 callbacks in Python. Queue size 10 gave 45, and the first callback came about 0.5 s later than in the no-lag cases. The C++ ApproximateTime policy behaved the same way: 0 with queue 1, 44 or 45 with queue 10.

The rule from this run is simple: queue_size has to be more than lag times rate. Here that's 0.5 s × 10 Hz = 5. When the rates differ, the synchronizer can't fire faster than the slowest topic. With /a at 10 Hz and /b at 1 Hz, approximate sync gave 4 callbacks for the 4 /b messages received, and exact sync gave 0.

Messages without a header

Python's ApproximateTimeSynchronizer printed one warning per message for std_msgs/String, 100 in total, and never fired. With allow_headerless=True it gave 50 callbacks, pairing by arrival time. That's only useful when the arrival time is a good enough timestamp. Note the typo "infomation" if you search for this warning. Lyrical also changed the quoting from 'allow_headerless' to "allow_headerless". I didn't test header-less types in C++.

C++: object lifetime and the callback form

This is the answer to the C++ questions where the callback is "never called" or "stops after a while". A TimeSynchronizer declared as a local variable in the node constructor connected to the inputs and was destroyed when the constructor returned. Both inputs still received 50 messages, but the synchronized callback ran 0 times and nothing was logged. Making the message_filters::Subscriber objects locals was worse. Humble ended with [ros2run]: Segmentation fault (exit code 245). Jazzy received nothing and exited normally. Lyrical received nothing, printed its result, and was still running when my 20-second timeout killed it (exit 124). Keep the subscribers as members and the synchronizer as a member or a std::shared_ptr member.

In Python, deleting the synchronizer object after registerCallback made no difference: 50 out of 50. The input subscribers hold a reference to it. Storing it on self is still the clean way to write it.

The callback form matters too. On Humble and Jazzy, sync.registerCallback([](const P::ConstSharedPtr &, const P::ConstSharedPtr &) {...}) with a lambda did not compile. The error was long, from signal9.h: no matching function for call to ... addCallback, then wrong number of template arguments (9, should be 1). On Humble it starts with forming pointer to reference type. The member function form, sync->registerCallback(&MyNode::callback, this), built and ran on all three distros. On Lyrical, the lambda form built too.

Version notes

The Python counts were the same on Humble, Jazzy and Lyrical. The only difference was one lost /b message in the Humble header-less run (50 / 49). The Python API grew on Lyrical. ApproximateTimeSynchronizer takes queue_offset=False and sync_arrival_time=False after allow_headerless, and Subscriber takes keyword-only callback_group, event_callbacks and qos_overriding_options. On Humble and Jazzy, Subscriber takes **kwargs that it passes on to create_subscription. I didn't test any of these new arguments.

The C++ API changed a lot on Lyrical (message_filters 7.4.2):

  • The .h headers are gone. #include <message_filters/subscriber.h> gives fatal error: message_filters/subscriber.h: No such file or directory. Humble and Jazzy ship both .h and .hpp, and the .h include built without a warning on both. Use .hpp everywhere.
  • The TimeSynchronizer queue size moved to the front. TimeSynchronizer<A, B> s(sub_a, sub_b, 10) builds on Humble and Jazzy and fails on Lyrical with no matching function for call to ... TimeSynchronizer(... Subscriber&, ... Subscriber&, int). s(10, sub_a, sub_b) is the reverse: it builds only on Lyrical.
  • subscribe() takes rclcpp::QoS and no longer has a default QoS, as in the table above.

The runtime behavior of the C++ policies was the same on all three: exact 50 and 0, approximate 49 and 41, and queue 1 vs 10 gave 0 vs 44 or 45.

Not tested

ApproximateTime::setMaxIntervalDuration(), the Lyrical-only queue_offset and sync_arrival_time arguments, TimeSequencer, Cache, three or more inputs, image topics through image_transport subscribers, use_sim_time and bag playback, multi-threaded executors and callback groups, Cyclone DDS and Zenoh, header-less types in C++, Foxy, Iron and Rolling.

FAQ

Why is my message_filters TimeSynchronizer callback never called?

In my runs there were three causes. The stamps weren't exactly equal (even 1 ms apart gave 0 callbacks), the input subscribers got no messages because of a QoS mismatch, or, in C++, the synchronizer was a local variable that went out of scope. Count messages on each input first to tell these apart.

How do I set QoS for a message_filters Subscriber in ROS 2?

Python: message_filters.Subscriber(node, Msg, 'topic', qos_profile=qos_profile_sensor_data). C++ on Humble and Jazzy: sub.subscribe(this, "topic", rmw_qos_profile_sensor_data). C++ on Lyrical: sub.subscribe(this, "topic", rclcpp::SensorDataQoS()). Passing the other type is a compile error on each distro.

What slop should I use for ApproximateTimeSynchronizer?

Larger than the real gap between your stamps and smaller than the period of the fastest topic. With stamps 50 ms apart, slop 0.1 gave 50 callbacks and slop 0.01 gave 0. The C++ ApproximateTime policy has no slop argument and paired stamps 900 ms apart.

How big should queue_size be?

More than the lag between the topics times the message rate. With one topic 500 ms behind at 10 Hz, queue sizes 1 and 3 gave 0 callbacks and 10 gave 44 or 45.

Why does my C++ message_filters code not compile on ROS 2 Lyrical?

Lyrical's message_filters 7.4.2 removed the .h headers, moved the TimeSynchronizer queue size to the first argument, and takes rclcpp::QoS in subscribe() with no default. Use the .hpp headers, write TimeSynchronizer(10, sub_a, sub_b), and pass a QoS object.
