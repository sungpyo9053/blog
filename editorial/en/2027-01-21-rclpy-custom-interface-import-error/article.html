Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'my_interfaces'

The second form of the same problem names the message instead of the package:

ImportError: cannot import name 'Extra' from 'my_interfaces.msg' (/w/ws_humble/install/my_interfaces/local/lib/python3.10/dist-packages/my_interfaces/msg/__init__.py)

Short answer: No module named 'my_interfaces' means Python can't see the generated package at all. In my runs that came from a shell that never sourced the workspace, or one that sourced install/setup.bash before the interface package had been built. Build it, then source again in the same terminal:

colcon build --packages-select my_interfaces
source install/setup.bash
python3 -c "from my_interfaces.msg import Num; print(Num(num=3))"
# my_interfaces.msg.Num(num=3)

cannot import name 'X' from 'my_interfaces.msg' means the package was found but has no type called X. Either the .msg file isn't listed in rosidl_generate_interfaces(), or the import spells the name differently from the file. The class name is the file name, Num.msg gives Num, and it lives in .msg, .srv or .action, never in the package root.

Three other causes gave different text. A msg/ folder inside an ament_python package built without errors and generated nothing. A script with the same name as its package gave 'my_server' is not a package. And a local file named std_msgs.py gave 'std_msgs' is not a package.

Find your error

Every row behaved the same on Humble, Jazzy and Lyrical unless the last column says otherwise. my_interfaces is an ament_cmake package with msg/Num.msg and srv/AddTwoInts.srv listed, plus a msg/Extra.msg that wasn't listed at first.

The quickest test is the difference between the two errors. No module named 'pkg' is about your environment: build, source, spelling. cannot import name is about the package contents, so look at CMakeLists.txt and the import line.

What I ran

On 2026-11-15 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one at a time, with no network. These images already include colcon, ament_cmake and rosidl_default_generators, so nothing was installed. One script built a workspace with these packages:

  • my_interfaces: ament_cmake, Num.msg (int64 num), AddTwoInts.srv, and an unlisted Extra.msg.
  • nogroup_interfaces: the same package with the member_of_group line removed from package.xml.
  • py_msgs: an ament_python package with msg/Point2.msg.
  • consumer: an ament_python node that imports Num. Its package.xml doesn't list my_interfaces.
  • my_server, my_server2, my_server3: ament_cmake packages with a Ping.msg and a Python script, set up like this question.

Each import was a fresh python3 -c process, and I kept the last line of its output. Builds ran with one colcon worker and MAKEFLAGS=-j1. The full script is repro.sh in the evidence folder.

Cause 1: the workspace isn't sourced, or was sourced too early

The generated Python code lives under your workspace's install/, not under /opt/ros. These are the paths it landed in:

DistroPythonPath of _num.py
Humble3.10.12install/my_interfaces/local/lib/python3.10/dist-packages/my_interfaces/msg/
Jazzy3.12.3install/my_interfaces/lib/python3.12/site-packages/my_interfaces/msg/
Lyrical3.14.4install/my_interfaces/lib/python3.14/site-packages/my_interfaces/msg/

Python finds that folder only through PYTHONPATH, and source install/setup.bash is what adds it. With only /opt/ros/<distro>/setup.bash sourced, the import failed with No module named 'my_interfaces' on all three distros. After sourcing the workspace, PYTHONPATH had exactly one new entry, the folder in the table, and the import printed my_interfaces.msg.Num(num=3).

The case that confuses people is the order. I built a workspace with only the consumer node, sourced it, then added my_interfaces and built it. In that same shell:

  • python3 -c "from my_interfaces.msg import Num": ModuleNotFoundError: No module named 'my_interfaces'
  • ros2 run consumer node: the same ModuleNotFoundError, then [ros2run]: Process exited with failure 1
  • ros2 interface show my_interfaces/msg/Num: Unknown package 'my_interfaces'

After one more source install/setup.bash, the import worked and the node logged built Num num=42. The reason is that the default isolated layout gives each package its own prefix. setup.bash adds the prefixes that exist when you source it, so a package built later stays invisible until you source again. A new terminal that sources the workspace works the same way.

Two related results:

  • With --merge-install and the same order, Humble still needed a second source. Jazzy and Lyrical imported the new package straight away. I didn't dig into why. If you rely on that, test it on your distro first.
  • Sourcing only the package's own install/my_interfaces/share/my_interfaces/local_setup.bash on top of /opt/ros was enough to import it.

Rebuilding a package that was already sourced is different. After I added Extra.msg to rosidl_generate_interfaces() and rebuilt, the import of Extra worked in the same shell without a new source, on all three distros. The prefix was already on the path, and only the files inside it changed.

The consumer package had no <depend>my_interfaces</depend>, and ros2 run consumer node still worked, because both packages were in the same sourced workspace. That doesn't make the depend line optional. colcon uses it to build packages in the right order, and I didn't test a clean build of both packages at once without it.

One more check: after I moved src/my_interfaces away, the import still worked from the old install/ folder. It failed only after I deleted install/my_interfaces. If you renamed or deleted an interface package and old types still import, look in install/.

Cause 2: the message isn't generated, or the import names it wrong

rosidl_generate_interfaces() generates only the files you list. Extra.msg sat in msg/ next to Num.msg, the build finished with no warning, and from my_interfaces.msg import Extra failed with cannot import name 'Extra'. Adding the line fixed it:

rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/Num.msg"
  "msg/Extra.msg"
  "srv/AddTwoInts.srv"
)

The other cannot import name cases were all import lines:

  • from my_interfaces import Num fails. Messages are in my_interfaces.msg, services in my_interfaces.srv, actions in my_interfaces.action.
  • num and NUM fail. The class name matches the file name exactly, Num.
  • A service imported from .msg fails. from my_interfaces.srv import AddTwoInts printed my_interfaces.srv.AddTwoInts_Request(a=1, b=2) for AddTwoInts.Request(a=1, b=2).
  • import my_interfaces.msg.Num fails with No module named 'my_interfaces.msg.Num'. Use from my_interfaces.msg import Num, or import my_interfaces.msg as m and then m.Num, which worked.

The path in the error is useful. cannot import name 'Extra' from 'my_interfaces.msg' (.../install/my_interfaces/...) tells you which install/ folder Python used. If that isn't the workspace you just built, you have an older copy on the path.

Cause 3: .msg files in an ament_python package

This is the case in ROS2.Jazzy Python Custom Messages. The py_msgs package had a msg/Point2.msg, a setup.py and even the member_of_group line. colcon built it in about a second with no error. The install folder had 0 files with point2 in their name. Then:

  • from py_msgs.msg import Point2: ModuleNotFoundError: No module named 'py_msgs.msg'
  • ros2 interface show py_msgs/msg/Point2: Could not find the resource 'py_msgs' of type 'rosidl_interfaces'
  • ros2 interface packages didn't list py_msgs.

Message generation runs from CMake, and setup.py never calls it. The usual fix is a separate ament_cmake package that holds only the interfaces, like my_interfaces here, and your Python package imports from it.

A related error appeared when I tried to keep Python code in the interface package. my_server3 called ament_python_install_package(${PROJECT_NAME}) after rosidl_generate_interfaces(). On Humble and Jazzy the build stopped with:

CMake Error at /opt/ros/humble/share/ament_cmake_python/cmake/ament_python_install_package.cmake:122 (add_custom_target):
  add_custom_target cannot create target "ament_cmake_python_copy_my_server3"

On Lyrical the same package built, and its script imported Ping. The rosidl generator already installs a Python package with the project's name, so on Humble and Jazzy you can't install a second one with that name. A separate package is the layout that built on all three.

Cause 4: a file shadows the package name

'x' is not a package means Python found something called x, but it was a single .py file, so it had no .msg inside.

In my_server the script was my_server/my_server.py, installed with install(PROGRAMS ... DESTINATION lib/${PROJECT_NAME}). ros2 run my_server my_server.py printed sys.path[0] = install/my_server/lib/my_server twice and then ModuleNotFoundError: No module named 'my_server.msg'; 'my_server' is not a package. Python puts the script's own folder first on the path, so import my_server found the script itself. The script ran a second time as a module, and its from my_server.msg import Ping failed. my_server2 was identical except the script was named server_node.py, and it printed imported Ping, data field: True. The generated package was fine the whole time: the same import worked from /tmp.

This question has the same pattern with a file named turtlesim.py. I reproduced it with a std_msgs.py next to a script that imports std_msgs.msg. It failed with 'std_msgs' is not a package. After I deleted std_msgs.py, the script printed ok std_msgs.msg.String(data='a'), even though __pycache__/std_msgs.cpython-310.pyc was still there. Python 3 ignores a cached file once its source is gone.

Cause 5: the package.xml is missing member_of_group

Without <member_of_group>rosidl_interface_packages</member_of_group>, the build stopped in CMake on all three distros:

CMake Error at /opt/ros/humble/share/rosidl_cmake/cmake/rosidl_generate_interfaces.cmake:229 (message):
  Packages installing interfaces must include
  '<member_of_group>rosidl_interface_packages</member_of_group>' in their
  package.xml

Jazzy and Lyrical reported it at line 223. You only see No module named for this package if you missed the failed build. colcon printed Failed <<< nogroup_interfaces [0.46s, exited with code 1] on Humble, so read the build output before you debug the import.

None of these fixes takes long to try. A full build of my_interfaces with one worker took 10.5 s on Humble, 14.5 s on Jazzy and 16.6 s on Lyrical. Importing Num in a fresh interpreter took about 16 ms on Humble, about 19 ms on Jazzy and 74 to 110 ms on Lyrical.

Version notes

  • Install path: Humble uses local/lib/python3.10/dist-packages. Jazzy and Lyrical use lib/python3.X/site-packages. If you hard-code PYTHONPATH or an editor path, this changes between distros.
  • The Did you mean: 'Num'? hint appeared only on Jazzy (Python 3.12.3). Humble (3.10.12) and Lyrical (3.14.4) printed the plain cannot import name line for the same import.
  • ament_python_install_package(${PROJECT_NAME}) in an interface package failed on Humble and Jazzy and built on Lyrical.
  • --merge-install: a package added after sourcing was importable without a second source on Jazzy and Lyrical, but not on Humble.
  • On Lyrical, CMake printed a deprecation warning for cmake_minimum_required(VERSION 3.8), so colcon reported 1 package had stderr output even though the build passed.
  • Everything else, including all the error texts in the first table, matched on the three distros.

If the import fails only inside a virtual environment or conda, that's a different problem. Python then looks for the right files under a different interpreter. See No module named 'rclpy' or 'rclpy._rclpy_pybind11'.

FAQ

Why do I get "No module named" for my custom message when colcon build succeeded?

The shell can't see the workspace. In my runs this happened when only /opt/ros was sourced, and when install/setup.bash was sourced before the interface package was first built. Run source install/setup.bash again in that terminal. Also check the colcon summary, because a failed build gives the same error.

What does "cannot import name ... from my_interfaces.msg" mean?

Python found the package but not that type. Either the .msg file isn't listed in rosidl_generate_interfaces(), or the name in the import doesn't match the file name exactly. A service imported from .msg instead of .srv also gives this error.

Can I put custom messages in an ament_python package?

Not in my test. The build passed, nothing was generated, and the import failed with No module named 'py_msgs.msg'. Put the interfaces in a separate ament_cmake package and import them from your Python package.

What does "'my_server' is not a package" mean?

A plain .py file with that name is earlier on the path than the real package. A script named after its own package did this, and so did a local std_msgs.py. Rename the file.

Do I need to source again after adding a new .msg to an existing package?

No, not in my runs. After listing Extra.msg and rebuilding, it imported in the same shell on Humble, Jazzy and Lyrical. You only need to source again when a new package appears in install/.
