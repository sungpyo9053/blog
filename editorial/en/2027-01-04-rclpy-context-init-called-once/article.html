RuntimeError: Context.init() must only be called once

The C++ version of the same mistake aborts the process:

terminate called after throwing an instance of 'rclcpp::ContextAlreadyInitialized'
  what():  context is already initialized

Short answer: something called rclpy.init() (or rclcpp::init()) a second time while the default context was still running. A shut-down context can be initialized again, and that worked on Humble, Jazzy and Lyrical. So either call init once per process, or make sure every init has a matching shutdown before the next one. If you can't control who calls it first, guard it:

import rclpy

def main():
    if not rclpy.ok():          # False before init and after shutdown
        rclpy.init()
    node = rclpy.create_node('my_node')
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()    # safe even if something already shut it down
if (!rclcpp::ok()) {
  rclcpp::init(argc, argv);
}
// ... nodes ...
rclcpp::shutdown();

In tests, put the shutdown in tearDown (or TearDown in gtest), or move init and shutdown to the class level. In notebooks, wrap the cell in try/finally with rclpy.try_shutdown(). The sections below show which pattern produces the error and which fix cleared it, measured on all three distros.

What I ran

Each distro ran in its own ros:<distro>-ros-base container with --network none, ROS_DOMAIN_ID=88, one CPU, 1 GiB of memory and the default RMW (Fast DDS). One after another, not in parallel.

The Python side is one script, exp_py.py, with one case per run, and every case starts in a fresh interpreter. The cases are: init twice; init, shutdown and init again; an rclpy.ok() guard; try_shutdown() twice; with rclpy.init() twice; a second Context object; running a "notebook cell" file twice with runpy; three unittest classes with different setup and teardown; and a timing loop. A final case calls rclpy.init() twice without catching anything, to get the real traceback and exit code.

The C++ side is one small executable, init_twice.cpp, built with colcon in the same container. It runs the same ideas: init twice, re-init after shutdown, an rclcpp::ok() guard, a gtest-style loop of three "tests" with and without shutdown in teardown, a second rclcpp::Context, timing, and an uncaught double init. I didn't link gtest. The loop does what SetUp() and TearDown() would do.

I ran the timing loops three times on each distro. Everything else ran once per distro, because those cases are pass or fail and came out the same everywhere.

Init called twice: the first context survives

The simplest case is two rclpy.init() calls in one process. The second one raised RuntimeError: Context.init() must only be called once on all three distros. Left uncaught, the script exited with code 1.

The failed call didn't damage anything. After catching it, rclpy.ok() was still True, and the script still created a node and published a message on the original context. C++ behaved the same way. rclcpp::init() threw rclcpp::ContextAlreadyInitialized, rclcpp::ok() stayed at 1, and a node created afterwards published normally.

That matters for the fix. The second call is redundant, not harmful, so a guard that skips it is enough. You don't need to tear anything down and start over.

In real code the two calls are rarely next to each other. These are the shapes that produce them:

  • Each node class calls rclpy.init() or rclcpp::init() in its constructor, and one process creates two of those classes.
  • A library you import creates a node at import time and calls init itself. Then your own main() calls init again. One reported case: crazyswarm2 discussion #608.
  • Two plugins loaded into the same host process each call rclcpp::init(). That is the Gazebo case in gazebo_ros_pkgs PR #859, which fixed it by checking first.

In C++ the uncaught version is harsher. The process printed terminate called after throwing an instance of 'rclcpp::ContextAlreadyInitialized' and exited with code 134, which is SIGABRT.

Tests that call init in setup

This is the pattern in the Robotics Stack Exchange question about initializing rclcpp inside a test class. Each test's setup calls init, so the first test works, and every later test starts with a context that is already up.

I ran three Python unittest classes, each with three tests that create and destroy a node:

Test classHumbleJazzyLyrical
setUp calls rclpy.init(), no teardown3 ran, 2 errors3 ran, 2 errors3 ran, 2 errors
setUp init, tearDown calls rclpy.shutdown()3 ran, 0 errors3 ran, 0 errors3 ran, 0 errors
setUpClass init, tearDownClass shutdown3 ran, 0 errors3 ran, 0 errors3 ran, 0 errors

Both errors in the first class were RuntimeError: Context.init() must only be called once. The C++ loop gave the same split. Without a shutdown in teardown, 1 of 3 "tests" passed and 2 threw context is already initialized. With rclcpp::shutdown() in teardown, all 3 passed on every distro.

Re-init after shutdown is what makes per-test setup work. After rclpy.shutdown(), a new rclpy.init() succeeded and a node could be created on it. In C++, rclcpp::ok() returned 0 after shutdown, and the next rclcpp::init() succeeded. This held on all three distros.

The same error has hit ROS 2's own test suites. launch_ros issue #407 and ros2/examples issue #391 are 2024 buildfarm reports of this RuntimeError in launch tests. aerostack2 issue #184 is a 2023 test failure from more than one rclpy context being initialized.

Re-running code in the same interpreter

Notebooks, IPython and anything that re-executes a script inside one Python process hit this all the time. The usual sequence: the cell spins a node, you interrupt it, and the rclpy.shutdown() at the bottom never runs. The context stays initialized, and the next run fails on its first line.

I simulated that with two small files run twice each through runpy.run_path in one interpreter. Each file raises KeyboardInterrupt where a real cell would be interrupted during spin.

  • No finally: run 1 ended with the KeyboardInterrupt. Run 2 failed at rclpy.init() with Context.init() must only be called once. rclpy.ok() was still True afterwards.
  • try/finally with rclpy.try_shutdown(): both runs got past init and reached the interrupt. rclpy.ok() was False at the end, so the next run starts clean.

The result was the same on Humble, Jazzy and Lyrical. I used try_shutdown() rather than shutdown() because calling it twice in a row raised nothing on any distro. The shutdown post below shows why: on Humble and Jazzy, plain rclpy.shutdown() raises an error if Ctrl+C already shut the context down.

On Humble and Jazzy, rclpy.init() returns None. On Lyrical it returned an rclpy.InitContextManager object. The trap on the older distros is the order. rclpy.init() runs and initializes the context before Python finds out it can't use the result as a context manager. So the first error is about __enter__, the context is left initialized, and the next attempt gets the init-once error. If you copied a with rclpy.init(): example onto Humble or Jazzy, replace it with an explicit init and a try/finally.

On Lyrical, two context managers in a row worked, and each one shut the context down on exit. rclpy PR #1314 fixed a bug with multiple rclpy.init context managers in one process. The version I tested didn't have that problem.

FAQ

What does "Context.init() must only be called once" mean?

rclpy.init() ran while the default context was still initialized. Some earlier code called it and never called rclpy.shutdown(). The first context keeps working, so you can skip the second call with if not rclpy.ok(): rclpy.init().

Can I call rclpy.init() again after rclpy.shutdown()?

Yes. Init, shutdown and init again worked on Humble, Jazzy and Lyrical, and a node could be created on the new context. The same is true for rclcpp::init() after rclcpp::shutdown().

Why does only my first unit test pass?

Each test calls init in its setup and nothing shuts down in teardown. In my run, 2 of 3 tests failed that way. Adding rclpy.shutdown() to tearDown, or moving init and shutdown to setUpClass and tearDownClass, made all 3 pass. The same applies to rclcpp::shutdown() in gtest's TearDown().

Why does my Jupyter cell fail the second time I run it?

The first run was interrupted before rclpy.shutdown(), so the context stayed up. Put the node code in a try block with rclpy.try_shutdown() in finally. Then every run starts with a clean context.

Why does with rclpy.init() fail with __enter__ or NoneType?

On Humble and Jazzy, rclpy.init() returns None, so it can't be used with with. It still initializes the context before the error, which is why your next attempt fails with the init-once error. Only Lyrical supported with rclpy.init(): in my test.
