$ ros2 component load /C comp_demo comp_demo::Unregistered
Failed to load component: Failed to find class with the requested plugin name.

[ERROR] [C]: Failed to find class with the requested plugin name 'comp_demo::Unregistered' in the loaded library

The other common one, from the same container, is Could not find requested resource in ament index. In a launch file both show up as [ERROR] [launch_ros.actions.load_composable_nodes]: Failed to load node 'typo_one' of type 'comp_demo::Talkr' in container '/mixed': ... followed by the same text.

Short answer: a component container finds your class through the ament index, not through your executable or your library name. Two things have to be there. CMake must register the class, and the .cpp must have the export macro. The package must also be visible to the container process. This layout loaded on Humble, Jazzy and Lyrical:

// src/Talker.cpp, at the end of the file, outside the namespace
#include <rclcpp_components/register_node_macro.hpp>
RCLCPP_COMPONENTS_REGISTER_NODE(comp_demo::Talker)
add_library(Talker_lib SHARED src/Talker.cpp)
target_link_libraries(Talker_lib rclcpp::rclcpp rclcpp_components::component)
rclcpp_components_register_node(Talker_lib PLUGIN "comp_demo::Talker" EXECUTABLE talker_exec)
install(TARGETS Talker_lib LIBRARY DESTINATION lib ARCHIVE DESTINATION lib RUNTIME DESTINATION bin)
ros2 component load /C comp_demo comp_demo::Talker
Loaded component 1 into '/C' container node as '/talker'

The plugin name is the full C++ class name with its namespace, written with ::, exactly as in the macro and in CMake. To see what the index really holds, run ros2 component types in the same environment as the container. A class that isn't listed there won't load.

The split is simple. Could not find requested resource in ament index means the container found no component list at all for that package name. Failed to find class with the requested plugin name means the package has a list, but your name isn't on it, or the library has no factory for it.

What I ran

On 2026-11-07 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro at a time, each in a container with --network none and ROS_DOMAIN_ID=88. Three packages were built with colcon build:

  • comp_demo (ament_cmake): five shared libraries, one class each. Talker is correct. Unregistered has the macro but no CMake registration. NoMacro has CMake registration but no macro. Undef reads an extern int that is never defined. Thrower throws in its constructor. Each constructor logs constructed, build v1, and the version string comes from a CMake variable so I could rebuild with v2.
  • comp_static: the same talker as a STATIC library with registration.
  • py_demo (ament_python): an rclpy node with a console script.

I started rclcpp_components component_container as /C and ran ros2 component load 15 times with the inputs in the table. Then I tried a container started without the workspace, a rebuild while the container was running, and two launch files. Most loads took 1.0 to 1.4 seconds, whether they worked or failed. A few took 2.1 to 3.8 seconds on Jazzy and Lyrical, with no pattern by case. The build of comp_demo took 18.9 s on Humble, 20.5 s on Jazzy and 27.1 s on Lyrical on a 2 vCPU machine.

After the build, ros2 component types printed this for comp_demo on all three distros:

comp_demo
  comp_demo::Talker
  comp_demo::NoMacro
  comp_demo::Undef
  comp_demo::Thrower

Unregistered is missing, and NoMacro is listed even though it can't load. The command reads the index file, not the library. That file is plain text, one line per class:

install/comp_demo/share/ament_index/resource_index/rclcpp_components/comp_demo
comp_demo::Talker;lib/libTalker_lib.so
comp_demo::NoMacro;lib/libNoMacro_lib.so
comp_demo::Undef;lib/libUndef_lib.so
comp_demo::Thrower;lib/libThrower_lib.so

py_demo and comp_static have no such file, so they never appear in ros2 component types.

Cause 1: the class isn't registered in CMake

The RCLCPP_COMPONENTS_REGISTER_NODE macro alone isn't enough. It puts a factory into the library, but the container never opens the library unless the index file names it. With the macro and no CMake call, the container log had no Load Library line at all. It went straight to the error, which says "in the loaded library" even though no library was loaded. Don't let that wording send you looking at the .so.

The fix is one line per class, after add_library:

rclcpp_components_register_nodes(Unregistered_lib "comp_demo::Unregistered")

Or use the singular form, rclcpp_components_register_node(target PLUGIN "ns::Class" EXECUTABLE name). It registers the class and also builds a standalone executable. ros2 run comp_demo talker_exec started the same Talker and logged Talker constructed, build v1 on all three distros. Use it when you also want to run the node outside a container.

If your package has no registered classes at all, you get Could not find requested resource in ament index instead. Your package has no index file, so the container doesn't know it as a component package.

Cause 2: the macro is missing

This one looks fine in ros2 component types, because CMake wrote the class into the index. The container then loads the library, looks for a factory called rclcpp_components::NodeFactoryTemplate<comp_demo::NoMacro>, doesn't find one, and logs Failed to find class with the requested plugin name 'comp_demo::NoMacro' in the loaded library. The Load Library line right before the error tells you this case apart from cause 1. Add the macro at the end of the .cpp, outside any namespace, with the fully qualified class name.

The name in the macro and the name in CMake must be the same string. If they differ, you're in cause 1 or 2, depending on which name you load.

Cause 3: the plugin name is wrong

The lookup is an exact string match against the index file. Talker, comp_demo::talker, comp_demo/Talker, the library target Talker_lib and the executable talker_exec all failed with Failed to find class with the requested plugin name. Only comp_demo::Talker worked. The same applies to plugin= in a launch file. A typo there (comp_demo::Talkr) gave:

[ERROR] [launch_ros.actions.load_composable_nodes]: Failed to load node 'typo_one' of type 'comp_demo::Talkr' in container '/mixed': Failed to find class with the requested plugin name.

Copy the name from ros2 component types instead of typing it.

Cause 4: the container can't see the package

The container uses its own environment, not the shell you run ros2 component load from. I started one container with only /opt/ros/<distro>/setup.bash sourced, then loaded comp_demo::Talker from a shell that had sourced the workspace. It failed with Could not find requested resource in ament index, while the same command worked against a container started after source install/setup.bash. The CLI shell was fine. The container wasn't.

In practice that means: source the workspace in the terminal that runs component_container, or start the container from a launch file run in a sourced shell. Also check the package name. A typo (comp_dem) gives the same message. So does a package that failed to build: comp_static never installed, and loading from it said Could not find requested resource in ament index too.

Cause 5: a Python node

rclcpp_components loads C++ shared libraries. An ament_python package has nothing it can load. Loading py_demo with plugin py_demo.node:PyTalker failed with Could not find requested resource in ament index, and so did rclpy as the package name. On all three images, ros2 pkg list showed only rclcpp_components and ros2component with "component" in the name. No Python container was installed. Run Python nodes as normal processes with Node in the launch file, next to the container.

Cause 6: the library itself won't load

Three failures happen after the name check passes.

Undefined symbol. A shared library links even with symbols it doesn't define. The error shows up only when the container calls dlopen. The container logged Failed to load library: Could not load library dlopen error: /ws/install/comp_demo/lib/libUndef_lib.so: undefined symbol: never_defined_value. The CLI printed the same message with the path in lowercase (libundef_lib.so), so use the container log when you look for the file. The usual fix is a missing source file in add_library or a missing target_link_libraries entry. Run ldd -r on the library to list unresolved symbols before loading. I didn't run ldd -r in this test.

Constructor exception. The library loaded and the factory was found, then Component constructor threw an exception: camera not found. The text after the colon is what() of your exception, so this one points at your own code.

STATIC library. One of the questions below reports invalid ELF header from a library built without SHARED. I couldn't get that far. On Humble, Jazzy and Lyrical, rclcpp_components_register_nodes refused the target at configure time: first argument 'static_talker' is not a shared library target. Add SHARED to add_library. The runtime ELF error is "Not tested".

A rebuild doesn't reach a running container

I rebuilt comp_demo with the version string set to v2 while container /C was running, then loaded comp_demo::Talker again into /C. It loaded, and it logged Talker constructed, build v1. The library was already open in that process, and the container didn't open it again. A new container started after the rebuild logged build v2. Same result on all three distros. If your change "doesn't do anything", restart the container.

Adding a registration is different. I added the missing rclcpp_components_register_nodes line for Unregistered, rebuilt, and loaded it into the same running /C without sourcing anything again. It loaded (Loaded component 5 into '/C' container node as '/unregistered'). The index file is read on each load, and that library had never been opened before.

Loading a second Talker under the same node name worked, but logged Publisher already registered for provided node name on Humble. On Jazzy and Lyrical the text was Publisher already registered for node name: 'talker'. Pass --node-name to ros2 component load or name= in ComposableNode to keep names apart.

In a launch file

I launched one ComposableNodeContainer with three nodes: a good Talker, a misspelled plugin and the Thrower. The good one loaded (Loaded node '/good_one' in container '/mixed'). The other two each logged a Failed to load node error. Launch didn't exit, and the container kept running with /good_one in ros2 component list until I stopped it with SIGINT after 15 seconds. A bad component doesn't stop the launch, so read the log above the running output.

A wrong container name in LoadComposableNodes is quieter. With target_container='/my_containr' and the real container named my_container, launch printed nothing about the node until I stopped it at 20 seconds. No error and no waiting message appeared on any distro. On SIGINT it ended with Caught exception in launch (see debug for traceback): cannot use Destroyable because destruction was requested. If a node from LoadComposableNodes never shows up and launch says nothing, compare target_container with ros2 component list. The name needs the namespace and the leading slash as the container reports it.

FAQ

What does "Failed to find class with the requested plugin name" mean?

The package has a component list in the ament index, but the name you asked for isn't on it, or the library has no factory for it. Check the name against ros2 component types. If the class is missing there, add rclcpp_components_register_nodes in CMake. If it's listed but still fails, the RCLCPP_COMPONENTS_REGISTER_NODE macro is missing.

What does "Could not find requested resource in ament index" mean when loading a component?

The container found no component list for that package name. In my run that came from a package name typo, a package with no registered classes, an ament_python package, a package that failed to build, and a container started without sourcing the workspace.

Can I load a Python node into a component container?

Not into rclcpp_components component_container. Loading an ament_python package failed with Could not find requested resource in ament index on Humble, Jazzy and Lyrical, and none of the three images had a Python component container installed. Run the Python node as its own process.

I rebuilt my component but the container runs the old code. Why?

The container had already opened the library and kept using it. A load into the same container after the rebuild still logged build v1. A new container logged build v2. Restart the container after rebuilding.

Why does LoadComposableNodes do nothing without an error?

In my run, a target_container name that didn't match any container produced no message for 20 seconds on any distro. Compare it with ros2 component list, including the leading slash and the namespace.
