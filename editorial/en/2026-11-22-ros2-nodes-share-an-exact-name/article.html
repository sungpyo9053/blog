$ ros2 node list
/dup_node
/dup_node
WARNING: Be aware that there are nodes in the graph that share an exact name, which can have unintended side effects.

The warning goes to stderr and ros2 node list still exits with code 0. ros2 node info prints a different message for the same situation: There are 2 nodes in the graph with the exact name "/dup_node". You are seeing information about only one of them., also with exit code 0.

Short answer: two running nodes have the same fully qualified name (namespace plus name). ROS 2 doesn't stop you from doing that. It only warns in the CLI. Topics keep working, but anything addressed to the node name stops being predictable. ros2 param get answered from either node at random, ros2 param set changed both, and lifecycle transitions and action goals reached both. The fix is to give every node its own name or namespace. On the command line:

ros2 run my_pkg my_node --ros-args -r __node:=my_node_b
# or
ros2 run my_pkg my_node --ros-args -r __ns:=/robot1

In a launch file, set a different name= or namespace= on each Node, or wrap each copy in GroupAction([PushRosNamespace('robot1'), Node(...)]). With each of these the warning was gone and every ros2 param get call reached the node I asked for (10 of 10 per name for the command-line fixes, 5 of 5 for the launch fixes), on Humble, Jazzy and Lyrical.

What I ran

On 2026-10-31 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro after another, all with the default RMW (rmw_fastrtps_cpp). One package held:

  • an rclpy node named dup_node. It declares a tag parameter, publishes its tag on /chatter twice a second, subscribes to /chatter, and prints a line from its parameter callback whenever a parameter is set,
  • an rclcpp component dupn::Talker (default name cpp_talker) that does the same, plus an executable that creates it twice in one process,
  • an rclcpp lifecycle node dup_lc that prints a line in on_configure,
  • an rclpy node dup_act with an action server on /lookup (tf2_msgs/action/LookupTransform, which ships in the base image) that prints its tag for each goal and returns the tag in the result,
  • launch files for the causes and fixes below.

For each case I started the nodes, waited for discovery, and called the CLI 10 or 20 times in a row. The tag in each answer shows which node replied. The script and full output are linked at the end.

What breaks when two nodes share a name

I started the rclpy node twice with ros2 run, once with -p tag:=A and once with -p tag:=B. Both came up as /dup_node.

CallHumbleJazzyLyrical
ros2 param get /dup_node tag, 20 callsA 9, B 11A 5, B 15A 9, B 11
ros2 service call /dup_node/get_parameters, 20 callsA 10, B 10A 13, B 7A 7, B 13
ros2 param set /dup_node note vN, 10 calls: callbacks that ran in A / B10 / 108 / 1010 / 10
ros2 topic echo /chatter for 5 s8 from A, 8 from B8, 89, 9

Parameter reads are a coin flip. Every param get exited with 0 and printed a clean String value is: ..., but the value came from either node. Calling the get_parameters service by hand behaved the same way, so this isn't a CLI quirk. Both nodes offer a service named /dup_node/get_parameters, and the client takes whichever reply comes first. ros2 param dump has the same problem. On Humble, one param get returned A, and the param dump right after it returned tag: B.

Parameter writes go to both. All 10 param set calls printed Set parameter successful. The callback logs show the request reached both nodes in most calls. On Jazzy, node A's callback ran for 8 of the 10. So a set call can change two nodes, or only one, and the CLI looks the same in both cases.

Listings merge or hide. On Humble, ros2 param list /dup_node printed one parameter list. On Jazzy and Lyrical it printed the list twice, one after the other, and ros2 param list with no argument showed a /dup_node: header twice. ros2 node info shows one node and tells you so. ros2 lifecycle nodes listed /dup_lc only once, with no warning.

Topics are fine. ros2 topic info /chatter showed Publisher count: 2 and Subscription count: 2, the echo got messages from both nodes in equal numbers, and each node's subscription received messages from both. Topics are matched by topic name, not node name, so a duplicate node name doesn't affect them.

Lifecycle nodes

Two copies of the rclcpp lifecycle node /dup_lc both started unconfigured. I sent ros2 lifecycle set /dup_lc configure once, read the state 10 times, then sent configure twice more.

  • Humble and Lyrical: the first configure printed Transitioning successful, and both nodes logged CONFIGURED. All 10 reads showed inactive [2]. The next configure failed with Unknown transition requested, available ones are: ... and exit code 1.
  • Jazzy: the first configure also printed Transitioning successful, but only one node changed. The 10 reads showed inactive [2] 7 times and unconfigured [1] 3 times. The second configure printed Transitioning failed with exit code 0. The already configured node logged [rcl_lifecycle]: No transition matching configure found for current state inactive. The other node logged CONFIGURED, and every read after that showed inactive [2]. Only the third call failed with Unknown transition requested.

So a lifecycle manager that drives nodes by name can get a success reply while a node stays behind, or a failure reply while the node did transition.

Action servers

Two /dup_act nodes each served /lookup. ros2 action info /lookup listed Action servers: 2, with /dup_act twice. I sent 10 goals with ros2 action send_goal. Every goal was accepted and finished with SUCCEEDED, but both servers ran most of them:

HumbleJazzyLyrical
Goals executed by server A / B (out of 10)10 / 89 / 1010 / 10
Result the client got came from A / B8 / 21 / 94 / 6

Strictly, this is a duplicate action name, not a duplicate node name. Two nodes with different names serving the same action name would probably behave the same, but I didn't test that. In practice the two come together, because a node started twice serves the same action twice. If the action moves a robot, that means two executions of every goal.

Every case below printed the ros2 node list warning on all three distros.

The first four cases are separate processes, and nothing warns when they start. You only find out from ros2 node list, or when parameters start acting up. Launch's own duplicate check only fired for composable nodes. The one-file case with two Node(name='dup_node') started without that warning on all three distros.

The launch override case is easy to miss. The C++ executable's default name was cpp_talker, and name='dup_node' in the launch file renamed it onto the Python node's default name. ros2 param get /dup_node tag then returned the C++ node's tag 8, 7 and 5 times out of 10 (Humble, Jazzy, Lyrical), and the Python node's tag the rest of the time.

Within one process the answer was stable but still wrong for one of the nodes. With two dup_comp components in the same container, 10 out of 10 param get calls returned the first component's tag on Humble and Lyrical, and 9 out of 10 on Jazzy. With two cpp_talker nodes in one rclcpp process, all 10 calls on every distro returned the first one. The second node's parameters couldn't be reached by name.

The last row matters when you apply the fix. __node:= without a node prefix renames every node in the process, so a process that holds several nodes gets duplicates from it. The issue ros2/rclcpp#843 describes this for the extra nodes that libraries create inside a process. If the process has more than one node, rename it with a namespace instead, or use a remap rule with a node-name prefix. I didn't test the prefix form.

The results were the same on all three distros. There's one difference between the two command-line fixes. __ns also moves relative topics: ros2 topic list showed /robot1/chatter next to /chatter, so the second node no longer publishes where the first one listens. That's what you want for two robots. It's not what you want if you only meant to rename a node. __node changes the name only, so topics stay where they are. For composable nodes, give each ComposableNode its own name=. The renaming fixes above apply there too, but I only measured them on standalone nodes.

Can ROS 2 refuse a duplicate name?

Not found. I listed every setter in rclcpp's NodeOptions and every argument of rclpy's Node.__init__ on all three distros. None of them is about name uniqueness. The extras on newer distros were enable_logger_service, clock_type, log_level and rosout_qos_profile. The rcl header says it plainly. rcl/node.h contains \todo TODO(wjwwood): node name uniqueness is not yet enforced on Humble, Jazzy and Lyrical. Creating a second node with a name already in use never threw in my runs, in C++ or in Python, in the same process or in another one. If you need a guard, you have to write it yourself. One way is to check the graph for your own name at startup, as in the Duplicate node names question. I didn't measure a check like that.

Version notes

The ros2 node list and ros2 node info texts were identical on Humble, Jazzy and Lyrical. Three things differed:

  • ros2 param list /dup_node printed one list on Humble and both lists on Jazzy and Lyrical. Newer distros also add a start_type_description_service parameter and a get_type_description service to every node.
  • The Publisher already registered text names the node on Jazzy and Lyrical (for node name: 'dup_node') and doesn't on Humble (for provided node name). Search for the part before that.
  • Lifecycle: one configure reached both nodes on Humble and Lyrical, and only one on Jazzy. That's one run per distro. I wouldn't read it as a fixed version difference, since the parameter calls show the same kind of randomness everywhere.

Which node answered changed from run to run on every distro. Treat the counts as "both, unpredictably", not as a ratio.

FAQ

What does "nodes in the graph that share an exact name" mean?

At least two running nodes have the same namespace and name. ros2 node list prints the warning on stderr and still exits with 0. ROS 2 lets both nodes run. Topics work, but parameter calls, lifecycle transitions and action goals sent to that name reach either node or both.

Is the warning harmless if my topics still work?

No. In my runs 20 ros2 param get calls split between the two nodes, anywhere from 5/15 to 10/10, param set changed both nodes, and both action servers ran most goals. The CLI reported success every time.

How do I fix duplicate node names in a launch file?

Give each Node a unique name=, or a different namespace=, or wrap each copy in GroupAction with PushRosNamespace. Both namespace methods removed the warning, and every param get went to the right node.

Why do I get "Publisher already registered for provided node name"?

One process created a second node with a name it already had. That happened with two composable nodes with the same name in one container, with a class created twice, and with __node:= applied to a process that holds two nodes. Rename the extra node. Use a namespace if a global __node remap caused it.

Can rclcpp or rclpy refuse to start a node whose name is taken?

Not found. No NodeOptions setter or rclpy Node argument does that on Humble, Jazzy or Lyrical, and rcl/node.h says "node name uniqueness is not yet enforced".
