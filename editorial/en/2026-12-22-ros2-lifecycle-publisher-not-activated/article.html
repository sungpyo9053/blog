[WARN] [1793845263.836121682] [LifecyclePublisher]: Trying to publish message on the topic '/chatter', but the publisher is not activated

Short answer: a publisher created with a lifecycle node only sends messages while it is activated. It starts inactive, and it gets activated when the node goes through the activate transition. Two things go wrong in practice. The node is never configured and activated, because nothing sent those transitions. Or the node is active, but your on_activate override never activated the publisher. Call the base class in your override, and start the node with configure and activate events (or autostart=True on Jazzy and Lyrical):

CallbackReturn on_activate(const rclcpp_lifecycle::State & state) override
{
  LifecycleNode::on_activate(state);   // activates every lifecycle publisher of this node
  // or: pub_->on_activate();
  return CallbackReturn::SUCCESS;
}
def on_activate(self, state):
    super().on_activate(state)   # rclpy: same job, and the warning above never appears in Python
    return TransitionCallbackReturn.SUCCESS
ros2 lifecycle set /my_node configure
ros2 lifecycle set /my_node activate

Two details make this harder to spot. In C++ the warning was printed once per inactive stretch, not once per dropped message. In my run one line stood for 64 to 91 lost messages. In Python nothing was printed at all: the messages were dropped without any log line.

What I ran

On 2026-11-05 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one after the other, on a 2 vCPU Ubuntu host. One package held two lifecycle nodes: a C++ node (rclcpp_lifecycle::LifecycleNode, name lc_cpp) and a Python node (rclpy.lifecycle.Node, name lc_py). In on_configure each node creates a lifecycle publisher on /chatter, a 100 ms timer that publishes on it, and a subscription on /in. An environment variable picks one of three on_activate styles:

  • base: the override calls the base class (LifecycleNode::on_activate(state) in C++, super().on_activate(state) in Python), and the same for on_deactivate.
  • none: the override only returns SUCCESS.
  • manual (C++ only): the override calls pub_->on_activate() and pub_->on_deactivate().

For each node and style the script walked the node through every state with ros2 lifecycle set. In each state it ran ros2 topic echo /chatter for about 3 seconds while ros2 topic pub -r 10 /in fed the subscription. The node logged how many timer ticks and /in messages it had seen since the last transition. I then started the C++ node from six launch files and read its state 7 seconds later. The full script is repro.sh in the evidence folder.

The publisher starts inactive, even after configure

Right after create_publisher in on_configure, the C++ node logged pub_is_activated=0. A lifecycle publisher is created inactive, whatever state the node is in. While the node was inactive, the timer kept ticking and calling publish(), between 61 and 93 times per stretch, and ros2 topic echo received nothing. The node does not stop your code from running. It only stops the publisher from sending.

After a successful activate transition in the base style, the C++ node logged on_activate done, pub_is_activated=1, and messages arrived. After deactivate they stopped again, and the publisher reported pub_is_activated=0 in on_cleanup.

An active node with an inactive publisher

This is the case that wastes the most time. In the none style every ros2 lifecycle set printed Transitioning successful, and ros2 lifecycle get said active [3]. The C++ node logged on_activate done, pub_is_activated=0, and the topic stayed empty for the whole active period on all three distros. The state machine moved, but the publisher was never told.

When you override on_activate, the base class version doesn't run unless you call it. That base version is what activates the node's lifecycle publishers. Two fixes worked the same way in my run:

  • Call LifecycleNode::on_activate(state) (C++) or super().on_activate(state) (Python) inside the override. This covers every lifecycle publisher the node created.
  • In C++, call pub_->on_activate() for each publisher yourself (the manual style), and pub_->on_deactivate() in on_deactivate.

Do the same in on_deactivate. The base and manual styles both called the deactivate side too, and both stopped sending after deactivate.

One warning line, many lost messages

In C++ the warning comes from the logger named LifecyclePublisher, not from your node's logger. In the base and manual styles it appeared exactly twice per run: once in the first inactive stretch and once after deactivate. Each stretch had 64 to 91 publish calls. In the none style it appeared once, although the publisher stayed inactive through 220 to 245 publish calls across three states. So a single warning at startup doesn't mean only one message was lost. It means the publisher was inactive from that point until it was activated.

If you filter logs by node name, you will also miss it, because the line is tagged [LifecyclePublisher] instead of your node's name.

Python drops messages without a word

The rclpy node used create_lifecycle_publisher. While it was inactive, and in the none style while the node was active, publish() raised nothing and logged nothing on any distro. The log file had zero lines containing not activated. If you search for the warning text because your Python topic is empty, you won't find it in your output. Check the state with ros2 lifecycle get /node_name and check that your on_activate calls super().

Timers and subscriptions keep running while inactive

Only publishers are managed. In every run the timer fired while the node was inactive, and the subscription received between 7 and 31 of the roughly 30 messages fed to /in in each inactive stretch. The lower counts are probably discovery delay at the start of a feed; I didn't measure that. This held for C++ and Python on all three distros. If your node must be quiet while inactive, create the timer and subscription in on_activate and destroy them in on_deactivate, or check the state in the callback. An open rclcpp issue asks for lifecycle-managed timers: Support lifecycle-managed timers in rclcpp_lifecycle::LifecycleNode.

Transitions from the command line

A transition that is not allowed from the current state fails with exit code 1. Sending activate to an unconfigured node printed:

Unknown transition requested, available ones are:
- configure [1]
- shutdown [5]

A valid one printed Transitioning successful with exit code 0. The order that worked on all three distros was configure, activate, deactivate, cleanup, shutdown, ending in finalized [4]. ros2 lifecycle list /node_name prints the transitions allowed right now, and ros2 lifecycle nodes lists every lifecycle node it can see. The node name must be unique. Two nodes with the same name answer the same lifecycle services, which I covered in nodes that share an exact name.

Configure and activate from a launch file

launch_ros.actions.LifecycleNode only starts the process. On all three distros, the node from a launch file with nothing else was still unconfigured [1] after 7 seconds.

A common pattern registers an OnStateTransition handler that activates the node when it reaches inactive, but never emits the first configure event. That node also stayed unconfigured [1], because nothing ever moved it to inactive. You need both parts:

import lifecycle_msgs.msg
from launch import LaunchDescription
from launch.actions import EmitEvent, RegisterEventHandler
from launch.events import matches_action
from launch_ros.actions import LifecycleNode
from launch_ros.event_handlers import OnStateTransition
from launch_ros.events.lifecycle import ChangeState

def generate_launch_description():
    node = LifecycleNode(package='lc', executable='lc_cpp', name='lc_cpp',
                         namespace='', output='screen')
    configure = EmitEvent(event=ChangeState(
        lifecycle_node_matcher=matches_action(node),
        transition_id=lifecycle_msgs.msg.Transition.TRANSITION_CONFIGURE))
    activate = RegisterEventHandler(OnStateTransition(
        target_lifecycle_node=node, goal_state='inactive',
        entities=[EmitEvent(event=ChangeState(
            lifecycle_node_matcher=matches_action(node),
            transition_id=lifecycle_msgs.msg.Transition.TRANSITION_ACTIVATE))]))
    return LaunchDescription([activate, node, configure])

With this file the node was active [3]. on_activate finished 0.623 s after ros2 launch started on Humble, 0.696 s on Jazzy and 0.696 s on Lyrical. A version that emitted only the configure event, placed before the node in the list, left the node in inactive [2], so the order in the list didn't block the event. That node printed the warning once, as expected.

Leave out namespace= and the file doesn't load on any of the three distros: TypeError: LifecycleNode.__init__() missing 1 required keyword-only argument: 'namespace'. Use namespace='' if you don't need one.

autostart=True: Jazzy and Lyrical only

On Jazzy and Lyrical, LifecycleNode(..., autostart=True) did both transitions without any event code. The node was active [3] after 0.696 s on Jazzy and 0.703 s on Lyrical, the same as the event version. On Humble the launch file failed to load with TypeError: Action.__init__() got an unexpected keyword argument 'autostart'. The feature came from launch_ros PR 430, merged into rolling on 2025-02-19. The Humble backport was closed without merging. On Humble, use the events above.

FAQ

What does "the publisher is not activated" mean in ROS 2?

A lifecycle publisher was asked to publish while inactive, so the message was dropped. The publisher starts inactive and only sends after the node's activate transition activated it. In my run the C++ warning appeared once per inactive stretch, while 64 to 91 messages were dropped in each one.

My lifecycle node is active but still publishes nothing. Why?

Your on_activate override probably doesn't call the base class. With an override that only returned SUCCESS, the node reported active [3] and the topic stayed empty on Humble, Jazzy and Lyrical. Call LifecycleNode::on_activate(state) in C++ or super().on_activate(state) in Python, or pub_->on_activate() per publisher.

How do I configure and activate a lifecycle node automatically in a launch file?

Emit a ChangeState event with TRANSITION_CONFIGURE, and register an OnStateTransition handler for goal_state='inactive' that emits TRANSITION_ACTIVATE. On Jazzy and Lyrical you can pass autostart=True to LifecycleNode instead. Both reached the active state in about 0.7 s.

Why does my rclpy lifecycle node not print the warning?

The rclpy lifecycle publisher dropped messages without any log line on all three distros. Check the state with ros2 lifecycle get and check that on_activate calls super().on_activate(state).

Do timers and subscriptions stop when a lifecycle node is inactive?

No. Only lifecycle publishers are managed. Timers fired and subscriptions received messages while the node was inactive, in C++ and Python. Create them in on_activate and destroy them in on_deactivate if they must stop.
