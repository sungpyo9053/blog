Short answer: on one machine, ROS 2 already keeps the message data off your network. In my test, 50 messages a second of 1 KB each produced only DDS discovery traffic on eth0: 3–4 KB in 10 seconds, while the 500 KB of messages never left the host. To stop even that, set ROS_LOCALHOST_ONLY=1 on Humble or ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST on Jazzy and newer. With either one, eth0 sent 0 bytes with both Fast DDS and Cyclone DDS. If ros2 topic list then shows nothing, call it again after a few seconds. The first call ran before discovery finished.

What I ran

On 2026-10-27 I used the official ros:humble-ros-base and ros:jazzy-ros-base Docker images on a Linux host. Each container gets a normal network interface (eth0) plus loopback (lo). Inside one container, ros2 topic pub -r 50 published a std_msgs/String with 1,000 characters, and ros2 topic hz subscribed for 10 seconds. I read the kernel's transmit counters for eth0 and lo (/sys/class/net/*/statistics/tx_*) before and after those 10 seconds. Every run received the messages at 50 Hz.

The messages themselves would be about 500 KB in 10 seconds (500 × 1 KB). Nothing close to that crossed eth0 in any configuration. The few packets in the default rows are discovery announcements, which go out every few seconds so that other machines can find the nodes.

So why is my network slow?

The question this answers describes a router slowing down while all nodes run on one machine. In my single-host test, the message data stayed on the host and only a few KB of discovery went out. If you see much more than that, something on another machine is probably subscribed. Examples are RViz on a laptop, ros2 bag record on another host, or a second robot on the same ROS_DOMAIN_ID. Once a subscriber exists on another machine, the data has to cross the network to reach it. I didn't measure that multi-machine case here. Either way, the localhost settings above stop it, because they also stop other machines from discovering your nodes.

To check quickly, compare your interface counters before and after 10 seconds, the same way I did:

cat /sys/class/net/eth0/statistics/tx_bytes; sleep 10; cat /sys/class/net/eth0/statistics/tx_bytes

Replace eth0 with your interface name (ip link lists them). Other programs on the machine count too, so stop large downloads before you test.

Cyclone DDS: "selected interface "lo" is not multicast-capable"

With Cyclone DDS and ROS_LOCALHOST_ONLY=1 on Humble, every command printed:

selected interface "lo" is not multicast-capable: disabling multicast

In my test this was only a warning. The subscriber still got 50 Hz, and eth0 sent nothing. You don't need the ifconfig lo multicast / route add workaround from the question for nodes on one host to talk. On Jazzy with Cyclone DDS 2.2.4 the warning didn't appear.

ros2 topic list shows nothing

The other half of that question is that ros2 topic list stayed empty. I tested this on Jazzy with Fast DDS, three times per setting, with a publisher already running:

SettingFirst ros2 topic list--no-daemonAgain 3 s later
defaultfound it 1 of 31 of 33 of 3
ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST0 of 30 of 33 of 3
ROS_LOCALHOST_ONLY=10 of 30 of 33 of 3

The first call after the ROS 2 daemon starts often comes back empty, because the daemon hasn't finished discovery yet. With the localhost settings it was empty every time. A second call a few seconds later listed the topic every time. Before you change network settings, run the command twice. Also make sure the shell running ros2 has the same RMW_IMPLEMENTATION, ROS_DOMAIN_ID and localhost variables as your nodes. I ran ros2 daemon stop before every test so that each one started a fresh daemon. Do the same after you change any of these variables.
