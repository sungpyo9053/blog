AssertionError: The 'data' field must be of type 'float'

On Jazzy and Lyrical the same mistake usually shows no AssertionError. The process dies when you publish:

python3: ./.obj-x86_64-linux-gnu/rosidl_generator_py/std_msgs/msg/_float64_s.c:58: std_msgs__msg__float64__convert_from_py: Assertion `PyFloat_Check(field)' failed.

Short answer: a Python message field takes exactly one Python type. A float64 or float32 field needs a float, an integer field needs an int, a string field needs a str, and a sub-message field needs that message class. Python's 1 is an int, so msg.data = 1 fails on a Float64. Convert at the point where you assign:

msg.data = float(value)                    # float64 / float32 fields, also for numpy.float32 and numpy.int64
msg.data = int(value)                      # int32, uint8, ... fields
msg.header.stamp = node.get_clock().now().to_msg()   # not time.time(), not clock.now()
point.time_from_start = Duration(seconds=1).to_msg()  # rclpy Duration -> builtin_interfaces Duration
arr_msg.data = np_array.astype(float).tolist()        # float64[] from numpy on Humble

On Humble the check runs in the setter, so you get the AssertionError at the line that assigns the value. On Jazzy and Lyrical the setter check is off unless you set ROS_PYTHON_CHECK_FIELDS=1. A wrong scalar type then reaches the C conversion code and aborts the interpreter with exit code 134 and no Python traceback. Some wrong values don't fail at all. They arrive changed. Turn the checks on while you develop on Jazzy and Lyrical:

export ROS_PYTHON_CHECK_FIELDS=1

What I ran

On 2026-11-02 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images with no extra packages. One script assigned 69 different values to fields of std_msgs, geometry_msgs, sensor_msgs and trajectory_msgs messages and printed either the stored type or the exception. I ran it twice per distro: with the default environment, and with ROS_PYTHON_CHECK_FIELDS=1. A second script took 24 of the wrong values, assigned one, then ran serialize_message and deserialize_message, which use the same C conversion as publish(). Each of these ran in its own process, because a wrong type can abort the interpreter. I ran that set in three modes: default, ROS_PYTHON_CHECK_FIELDS=1, and python3 -O. Three of the cases also went through a real publisher.publish(). I also printed the generated setter for std_msgs/Float64.data on each distro.

This is the setter on Humble:

                isinstance(value, float), \
                "The 'data' field must be of type 'float'"

Lyrical has the same _check_fields switch and adds a type hint (def data(self, value: float) -> None). The check is a plain isinstance, so it has no tolerance. An int is not a float, and numpy.float32 is not a float either. numpy.float64 passed on all three distros, and so did an element taken from a float64 numpy array, because that type is a subclass of Python float. Int32.data = True also passed, because bool is a subclass of int. The reverse, Bool.data = 1, failed.

Arrays: numpy, lists of ints and fixed sizes

Sequence fields such as float64[] behaved differently from scalars. On Jazzy and Lyrical with the default environment, the setter turned the value into array.array('d', value). That conversion accepts ints and numpy arrays. A list [1, 2, 3], a float64, float32 or int64 numpy array, a raveled 2-D array and a generator were all stored as array('d'), and the list and the numpy array serialized without error. array.array('f', ...) was stored as array('d') on Jazzy but kept as array('f') on Lyrical. I didn't serialize that one. A 2-D array still failed, with TypeError: only length-1 arrays can be converted to Python scalars.

On Humble, and on Jazzy and Lyrical with checks on, the check asks for a Sequence whose items are all float. A numpy array is not a Sequence, so even a float64 array failed with the long "set or sequence" message. These forms worked everywhere:

msg.data = arr.tolist()                     # float64 array -> list of float
msg.data = arr.astype(float).tolist()       # int array -> list of float
msg.data = array.array('d', arr)            # skips the per-item check (typecode must be 'd')
msg.data = [1.0, 2.0, 3.0]                  # or a tuple

Fixed-size fields like Imu.orientation_covariance (float64[9]) are stored as a numpy array. Here the checks accepted a 9-element list of floats, np.zeros(9), np.eye(3).flatten(), and setting one element with an int (cov[0] = 1). A float32 array was rejected with the dtype message. One case slipped past the checks on every distro: np.eye(3), a 3x3 array. The setter accepted it, even with checks on, and serialize_message then aborted with Assertion `PyArray_NDIM(seq_field) == 1' failed. Flatten 2-D arrays before you assign them.

Fix options compared

The fix is always a conversion. For a single value it costs nothing you'd notice. 1,000 Float64.data = 1.0 assignments took 1.003 ms on Humble, 0.518 ms on Jazzy and 0.405 ms on Lyrical. For a 100,000-element Float64MultiArray.data the choice matters a bit more. Best of five, per assignment, including the conversion:

Assignment (100,000 values)HumbleJazzy, defaultJazzy, checks onLyrical, default

numpy float64 array, as isAssertionError10.793 msAssertionError11.430 ms
arr.tolist()18.736 ms5.455 ms15.328 ms5.085 ms
array.array('d', arr)10.442 ms10.956 ms10.722 ms11.402 ms

The per-item check is most of the cost of a big list: on Jazzy, turning it on raised the plain-list case from 2.955 ms to 12.780 ms. array.array('d', arr) stayed between 10.4 and 11.4 ms in every mode, because the setter takes an array('d') without checking each item. On Humble that made it the fastest fix that works. With checks off, arr.tolist() was faster. A list comprehension with float(x) was the slowest everywhere. If large arrays are slow in your node for other reasons, such as arrays of nested messages, that is a different problem, measured in rclpy publish() slow with large custom message arrays.

The fix options in short:

  • Convert at assignment with float(), int(), .to_msg() or .tolist(). Works on every distro and in every mode.
  • Write float literals: 2022.0, not 2022; Vector3(x=1.0, ...), not x=1.
  • Turn checks on during development on Jazzy and Lyrical with ROS_PYTHON_CHECK_FIELDS=1, or per message with the check_fields=True constructor keyword. Float64(data=1, check_fields=True) raised the usual AssertionError on Jazzy and Lyrical. On Humble that keyword doesn't exist and gave AssertionError: Invalid arguments passed to constructor: check_fields.
  • Don't fix it with python3 -O. On Humble, -O removes the setter checks (they sit under if __debug__:). The result matched the Jazzy default exactly: the same aborts and the same silent wraps.

Version notes

The main change is when the check runs. On Humble (rosidl_generator_py 0.14.6) it runs whenever Python runs without -O. On Jazzy (0.22.2) and Lyrical (0.27.2) it runs only with ROS_PYTHON_CHECK_FIELDS=1 or check_fields=True, and it is off by default. python3 -O had no extra effect on Jazzy or Lyrical. With checks on, the AssertionError texts were identical on all three, with one exception. For sequence and fixed-array fields, Lyrical says must be sequence and each value where Humble and Jazzy say must be a set or sequence and each value. If you search for the error, use the part before that wording. The C abort lines moved from _float64_s.c:58 on Humble and Jazzy to _float64_s.c:55 on Lyrical, and _imu_s.c:106 to :103. numpy was 1.21.5, 1.26.4 and 2.3.5, and the numpy results matched across all three versions. Lyrical only prints numpy scalars differently (np.float64(1.5)).

FAQ

What does "The 'data' field must be of type 'float'" mean?

You assigned something that isn't a Python float to a float32 or float64 field. Most often it is an int literal like 1 or 2022, or a numpy.float32. Wrap the value in float() or write 1.0.

Why does my code work on Jazzy but fail on Humble?

Humble checks field types in every setter by default. Jazzy and Lyrical skip the check unless ROS_PYTHON_CHECK_FIELDS=1 is set. A wrong scalar type on Jazzy then crashes at publish() with a convert_from_py assertion, and a list of ints in a float64[] field is converted silently, so it can look like it works.

What is "Assertion `PyFloat_Check(field)' failed" in ROS 2 Jazzy?

It is the same type error, caught later in C code instead of in the Python setter. The process exits with code 134 and no traceback. Run with ROS_PYTHON_CHECK_FIELDS=1 to get an AssertionError that names the field, then convert the value.

How do I put a numpy array into a ROS 2 message field?

For float64[], use arr.tolist() or array.array('d', arr). On Humble a numpy array is rejected as is, even with dtype float64. For fixed-size fields like a covariance, a 1-D float64 numpy array of the right length works directly. Flatten 2-D arrays first, because a 3x3 array passed the check and then aborted at serialization.

How do I fix "The 'stamp' field must be a sub message of type 'Time'"?

Assign a builtin_interfaces message, not a float or an rclpy Time. Use node.get_clock().now().to_msg(). For Duration fields, use Duration(seconds=1).to_msg() or builtin_interfaces.msg.Duration(sec=1).
