[INFO] [spawner_joint_state_broadcaster]: waiting for service /controller_manager/list_controllers to become available...
[FATAL] [spawner_joint_state_broadcaster]: Could not contact service /controller_manager/list_controllers
[ros2run]: Process exited with failure 1

Older launch files that call ros2 control load_controller print the same thing for /controller_manager/load_controller. Without --controller-manager-timeout the spawner prints the line as a [WARN] every 10 seconds and keeps waiting.

Short answer: the spawner can't find the controller manager's services under the name it is using. Most of the time the manager is running, but it hasn't created those services yet, because it is still waiting for the robot description. On Humble that happens when robot_state_publisher publishes /robot_description but the manager listens on /controller_manager/robot_description. The setup that worked on Humble, Jazzy and Lyrical was robot_state_publisher plus this remap on the manager:

ros2 run robot_state_publisher robot_state_publisher --ros-args -p robot_description:="$(cat robot.urdf)"
ros2 run controller_manager ros2_control_node --ros-args \
  -r '~/robot_description:=robot_description' --params-file controllers.yaml
ros2 run controller_manager spawner joint_state_broadcaster --controller-manager-timeout 30

I ran everything with ros2 run. In a Python launch file the same remap would be remappings=[("~/robot_description", "robot_description")] on the ros2_control_node Node, which I didn't test. If the manager runs in a namespace or under another name, pass the full name with -c. Then read the manager's own log, not the spawner's. The real error (a missing hardware plugin, an unreceived URDF) is printed there.

The manager doesn't offer its services until it has a URDF

This explains most of the confusing cases. ros2_control_node starts, logs its update rate and spawns its real-time thread, but it creates list_controllers, load_controller and the other controller services only after it has a robot description and has loaded the hardware. Until then the node shows up in ros2 node list, but the services aren't there. With no robot description, ros2 service list showed 6 services on Humble and 9 on Jazzy and Lyrical, and none of them were /controller_manager/list_controllers. A direct ros2 service call /controller_manager/list_controllers printed waiting for service to become available... until I stopped it at 15 seconds on all three distros. So "Could not contact" doesn't mean the manager is dead. It often means the manager is alive and waiting for its URDF.

The message itself comes from controller_manager_services.py. When you pass --controller-manager-timeout, it calls wait_for_service(service_timeout) once and raises ServiceNotFoundError on failure. Without the option it calls wait_for_service(10.0) in a loop and logs a warning each time. That is why the default spawner never exits. In my runs it was still waiting at 35 seconds on every distro. In a launch file that looks like a hang with one warning every 10 seconds.

Humble listens on ~/robot_description

On Humble (controller_manager 2.54.3) the manager logged Subscribing to '~/robot_description' topic for robot description file. The ~ makes that /controller_manager/robot_description. robot_state_publisher publishes /robot_description. With no remap, ros2 topic list showed both topics, the manager never logged Received robot description file., and the spawner failed after its 10-second timeout. With -r ~/robot_description:=robot_description the manager received the URDF, loaded the mock hardware, and the spawner finished in 0.73 seconds.

On Jazzy (4.48.1) and Lyrical (6.10.1) the manager logged Subscribing to '/robot_description' topic for robot description. and worked without the remap. The remap did no harm there, so the same launch file works on all three. I used the relative form (robot_description, not /robot_description) so it follows a namespace. In /abc the manager subscribed to /abc/robot_description, which is where a namespaced robot_state_publisher publishes.

The robot_description parameter only works on Humble

Many older tutorials pass the URDF to ros2_control_node as a parameter. On Humble that still worked, with this warning: [Deprecated] Passing the robot description parameter directly to the control_manager node is deprecated. Use '~/robot_description' topic from 'robot_state_publisher' instead. On Jazzy and Lyrical the manager didn't use the parameter. It kept logging Waiting for data on 'robot_description' topic to finish initialization and the spawner failed after 10.74 seconds (Jazzy) and 10.89 seconds (Lyrical). If you moved a Humble launch file to Jazzy and the spawner stopped working, check this first. Start robot_state_publisher with the URDF and let the manager read it from the topic.

A broken URDF looks the same from the spawner

I changed the hardware plugin to my_hw/DoesNotExist. The manager received the URDF and failed to load the plugin, and the spawner printed the usual Could not contact service line. The cause was only in the manager's log. On Humble it was The published robot description file (urdf) seems not to be genuine. The following error was caught:According to the loaded plugin descriptions the class my_hw/DoesNotExist with base class type hardware_interface::SystemInterface does not exist. On Jazzy and Lyrical it was Caught exception of type : N9pluginlib20LibraryLoadExceptionE while loading hardware with the same plugin text. Jazzy then added Could not load and initialize hardware. Please check previous output for more details. After you have corrected your URDF, try to publish robot description again. and went back to Waiting for data on 'robot_description' topic. My script kept only the first lines of the Lyrical manager log, so I can't say whether Lyrical prints the same follow-up. In a launch file these lines are mixed with the spawner's output, so search the log for [controller_manager] and ERROR.

Namespace, node name and domain

The spawner looks for /controller_manager unless you tell it otherwise. The namespace question in the list below is this case: the manager runs as /abc/controller_manager, and the spawner, started outside the namespace, still asked for /controller_manager/list_controllers. Three fixes worked on every distro: -c /abc/controller_manager, starting the spawner in the same namespace (--ros-args -r __ns:=/abc), and, for ros2 control commands, -c /abc/controller_manager too. A manager renamed with -r __node:=my_cm needed -c my_cm.

A spawner on a different ROS_DOMAIN_ID failed the same way, and the same spawner on the manager's domain worked in 3.40 to 3.58 seconds. This can happen in Docker when the spawner and the manager run in different shells or containers with different settings. The same goes for ROS_AUTOMATIC_DISCOVERY_RANGE, which I covered in ROS 2 nodes can't see each other.

Start order and timeouts

Starting the spawner before the manager was fine. With the default timeout the spawner kept waiting and loaded the controller once the manager appeared: after 5.84 to 7.67 seconds when the manager started 5 seconds late, and after 16.27 to 16.94 seconds when it started 15 seconds late. On Humble, Jazzy and Lyrical the default spawner never gave up, so a late manager is a problem only if you set a short --controller-manager-timeout. With --controller-manager-timeout 30 and a 15-second delay it worked on all three. I'd still set a timeout in launch files, long enough for your simulator to start, so a real failure ends with exit code 1 instead of a warning every 10 seconds forever.

use_sim_time without a clock: a different message

In Gazebo setups the manager often runs with use_sim_time:=true. I ran it that way with nothing publishing /clock, which is what you get when the simulator is paused, still starting, or its clock bridge is missing. The spawner reached the services, so there was no "Could not contact" line. On Humble each load call timed out: Failed getting a result from calling /controller_manager/load_controller in 10.0. (Attempt 1 of 3.), three times, then RuntimeError: Could not successfully call service /controller_manager/load_controller after 3 attempts. after 30.58 seconds. ros2 control list_controllers failed the same way. On Jazzy and Lyrical the controller loaded but didn't activate. The spawner printed Failed to activate controller : joint_state_broadcaster, the manager printed Switch controller timed out after 5 seconds!, and list_controllers showed the controller as inactive. Jazzy and Lyrical also logged Using ROS clock for triggering controller manager cycles. instead of the usual Steady (Monotonic) clock. If you see these lines, check that /clock is being published.

Version notes

The spawner's message was the same on all three distros. ros2 control load_controller changed: on Humble it waited on /controller_manager/load_controller and was still waiting when I stopped it at 35 seconds, and on Jazzy and Lyrical it checked list_controllers first and stopped with ServiceNotFoundError after 21.14 seconds. The spawner's options changed too. Jazzy and Lyrical no longer have -t (controller type) or --stopped, and both added --controller-ros-args and --switch-asap. Lyrical also dropped -n NAMESPACE, so use --ros-args -r __ns:=... or -c there. On Lyrical, the manager in the use_sim_time case printed terminate called after throwing an instance of 'std::runtime_error' when I stopped it. I saw that once and didn't look into it.

FAQ

What does "Could not contact service /controller_manager/list_controllers" mean?

The spawner waited for the controller manager's list_controllers service and didn't find it in time. Either no manager was running under that name, or the manager was running but hadn't created its services yet because it had no usable robot description. Look at the manager's log to see which.

The controller_manager node is running. Why can't the spawner contact it?

In my runs the manager created its controller services only after it had loaded the URDF and the hardware. Before that it appears in ros2 node list, but /controller_manager/list_controllers doesn't exist yet. On Humble remap ~/robot_description to robot_description. On Jazzy and Lyrical make sure robot_state_publisher is publishing the URDF.

Why does my Humble launch file fail on Jazzy?

If it passes the URDF to ros2_control_node as the robot_description parameter, Jazzy and Lyrical ignore it and keep waiting for the topic. Publish the URDF with robot_state_publisher instead. If it uses the spawner's -t option, that option was removed too.

How do I use the spawner with a namespaced controller manager?

Pass -c /your_ns/controller_manager, or start the spawner in the same namespace. Both worked on Humble, Jazzy and Lyrical. A spawner outside the namespace looks for /controller_manager and fails.

Will increasing --controller-manager-timeout fix it?

Only if the manager starts late. A spawner started 15 seconds before the manager worked with a 30-second timeout. If the manager never gets a robot description, or the hardware plugin fails, a longer timeout only makes the spawner fail later.
