$ ros2 run image_transport republish --ros-args -p in_transport:=compressed -p out_transport:=raw -r in/compressed:=/cam/compressed -r out:=/image
Usage: /opt/ros/humble/lib/image_transport/republish in_transport in:=<in_base_topic> [out_transport] out:=<out_base_topic>

On Jazzy and Lyrical the opposite mistake fails without any error. The old positional form starts, logs The 'in_transport' parameter is set to: raw, and publishes nothing on your output topic.

Short answer: Humble's republish reads the transports from positional arguments and ignores the in_transport and out_transport parameters. Jazzy and Lyrical read only the parameters and ignore the positional words. So each distro needs its own command to turn /cam/compressed into a raw /image. Both commands below delivered decoded 640x480 images in my runs:

# Humble
ros2 run image_transport republish compressed raw --ros-args \
  -r in/compressed:=/cam/compressed -r out:=/image

# Jazzy and Lyrical
ros2 run image_transport republish --ros-args \
  -p in_transport:=compressed -p out_transport:=raw \
  -r in/compressed:=/cam/compressed -r out:=/image

Remap in/compressed, not in. On Humble and Jazzy a remap of the base name in doesn't reach the in/compressed topic, and the node waits on a topic nobody publishes. The decoder also needs the plugin package: sudo apt install ros-$ROS_DISTRO-compressed-image-transport. Without it every distro aborts with TransportLoadException. For a launch file that works on all three, give the node both the positional arguments and the parameters. That layout worked on Humble, Jazzy and Lyrical.

What I ran

On 2026-11-13 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base Docker images, one distro at a time. Each container installed ros-$ROS_DISTRO-image-transport first and ros-$ROS_DISTRO-compressed-image-transport later in the run. DDS traffic stayed inside the container (domain 88, localhost-only discovery).

A small rclpy node published a 640x480 rgb8 test pattern on /camera/image_raw at 10 Hz. Python nodes publish plain sensor_msgs/Image, so there was no compressed topic until a republish made one. A second republish made /cam/compressed from it, and each test command then tried to turn /cam/compressed back into raw images on /image. A probe node counted the messages on /image for 5 seconds. Every command got SIGINT after about 12 seconds, so the shutdown messages are part of the output too.

Humble: transports are positional, parameters are ignored

Humble's republish (image_transport 3.1.13) takes the input transport as its first plain argument and the optional output transport as the second. If the first one is missing, it prints the Usage line and returns. It doesn't look at in_transport or out_transport, so the parameter form from newer docs gets the Usage line every time. That is the situation in two of the questions linked below. The askers had the right parameter names for a newer image_transport. They were running Humble's.

The positional words can go before --ros-args, and the remaps after it with -r. That form gave 38 messages and no deprecation warnings. The older form with in/compressed:=... as a bare argument also worked (39 messages), but rcl printed Found remap rule 'in/compressed:=/cam/compressed'. This syntax is deprecated. for each remap.

On Ctrl+C, every Humble run that had loaded the compressed subscriber ended with [ros2run]: Segmentation fault. Under launch it showed as process has died [pid 4646, exit code -11, ...]. This happened after the images had already been delivered, and a raw-to-raw republish shut down without it. If you see exit code -11 only when you stop the launch, this is the likely source.

Jazzy and Lyrical: parameters only, positional words ignored

On Jazzy (image_transport 5.1.8) and Lyrical (6.4.10) republish logs the two parameters at startup:

[INFO] [image_republisher]: The 'in_transport' parameter is set to: compressed
[INFO] [image_republisher]: The 'out_transport' parameter is set to: raw

With the Humble command, those lines say raw and an empty string. The words compressed raw are dropped without a warning, and the node subscribes to raw images on in. Check those two log lines first. If in_transport says raw when you meant compressed, the node didn't get your setting.

This produced one false success on Jazzy. compressed in:=/cam raw out:=/image delivered 35 images, because the source in that run also published raw images on /cam. The node just copied raw /cam to /image, and nothing was decompressed. On Lyrical, where the source published only the compressed topic, the same command gave 0.

If out_transport is left empty, the node publishes every installed transport on the output. With in_transport:=compressed and no out_transport, /image still got raw images (51 on Jazzy, 49 on Lyrical). Set out_transport:=raw anyway if you only want the raw topic.

On Ctrl+C both distros printed Warning: class_loader.ClassLoader: SEVERE WARNING!!! Attempting to unload library while objects created by this loader exist in the heap! for the compressed cases. The process still exited cleanly, and launch reported process has finished cleanly.

Remap in/compressed, not in

image_transport builds the real topic name from a base name plus the transport. The compressed subscriber listens on in/compressed. On Humble and Jazzy a remap of in didn't change in/compressed. With in:=/cam and a compressed input, nothing arrived on either distro, and the node gave no error. Remapping in:=/cam/compressed with the compressed input (tested on Humble) also gave 0. The likely reason is that the transport suffix is added after the remap, so the node looks one level too deep. I didn't capture the subscribed topic name to confirm that.

Lyrical behaves differently. There, -r in:=/cam with in_transport:=compressed delivered 49 images, so the base remap carried over to the transport topic. -r in/compressed:=/cam/compressed also worked on Lyrical (31). That makes the in/compressed remap the one form that worked on all three.

Missing plugin: TransportLoadException

Before the plugin package was installed, ros2 run image_transport list_transports listed only image_transport/raw on all three distros. Asking for the compressed input then aborted the node:

terminate called after throwing an instance of 'image_transport::TransportLoadException'
  what():  Unable to load plugin for transport 'image_transport/compressed_sub', error string:
According to the loaded plugin descriptions the class image_transport/compressed_sub with base class type image_transport::SubscriberPlugin does not exist. Declared types are  image_transport/raw_sub
[ros2run]: Aborted

On Humble this came from the positional form. On Jazzy and Lyrical it came from -p in_transport:=compressed. The Humble command on Jazzy and Lyrical didn't abort, because the positional words were ignored and the node stayed on raw. Installing ros-$ROS_DISTRO-compressed-image-transport fixed it. list_transports then showed image_transport/compressed as well, with no rebuild or restart of anything else.

The other direction: raw to compressed, and where the topic lands

Making a compressed topic from raw images showed a second remap problem. With out:=/cam on Humble and Jazzy, the raw output went to /cam but the compressed output went to /out/compressed. Adding -r out/compressed:=/cam/compressed put it where expected on both. On Lyrical, out:=/cam alone gave /cam/compressed.

The commands that produced /cam/compressed:

# Humble (and it also works on Jazzy, where "raw compressed" is ignored and all transports are published)
ros2 run image_transport republish raw compressed --ros-args \
  -r in:=/camera/image_raw -r out:=/cam -r out/compressed:=/cam/compressed

# Lyrical
ros2 run image_transport republish --ros-args \
  -p in_transport:=raw -p out_transport:=compressed -r in:=/camera/image_raw -r out:=/cam

My test pattern compressed from 921,600 bytes to about 20,200 bytes per frame as format="rgb8; jpeg compressed bgr8". It is a smooth gradient, which JPEG handles well, so a real camera image will come out larger. Over 10 seconds the raw source and /cam/compressed were received at about the same rate: 79 and 81 messages on Humble, 99 and 101 on Jazzy, 101 and 95 on Lyrical. If you are compressing because of bandwidth, the numbers in this measurement of camera bandwidth in ROS 2 show how much raw images cost.

Turning off transports you don't want

A publisher made with image_transport advertises every installed transport. The enable_pub_plugins parameter limits that, but the name it is read under differed by distro. I set it on the raw-to-all republish with -r out:=/cam:

Humble and Jazzy read the parameter under the name in the code (out). Lyrical read it under the remapped topic name (cam). For your own node that publishes camera/image_raw, that would point to camera.image_raw.enable_pub_plugins, with the slash replaced by a dot. I only tested it on republish, so check the topic list after you set it.

The launch file that worked everywhere:

from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([Node(
        package='image_transport', executable='republish', name='decompress',
        arguments=['compressed', 'raw'],                          # read by Humble
        parameters=[{'in_transport': 'compressed',
                     'out_transport': 'raw'}],                    # read by Jazzy and Lyrical
        remappings=[('in/compressed', '/cam/compressed'), ('out', '/image')])])

Each distro ignored the half it doesn't use and didn't complain. Under launch, Humble passed the arguments as republish compressed raw --ros-args -r __node:=decompress --params-file .... I didn't run that combined form directly with ros2 run.

Version notes

The split is between Humble and the newer two. Humble's image_transport 3.1.13 reads positional arguments only. Jazzy 5.1.8 and Lyrical 6.4.10 read the parameters only and log them at startup. Lyrical also applies a base-name remap to the transport topics (in:= and out:=). Humble and Jazzy don't, and they read enable_pub_plugins under the code name rather than the remapped one. The TransportLoadException text and the found unknown ROS arguments text were the same on all three. The shutdown crash with exit code -11 happened only on Humble. Jazzy and Lyrical printed the class_loader warning instead.

FAQ

Why does republish print "Usage: republish in_transport in:=..." and exit?

You are on Humble and didn't pass the transports as positional words. Humble's republish ignores -p in_transport and -p out_transport. Run ros2 run image_transport republish compressed raw --ros-args -r in/compressed:=/your/topic/compressed -r out:=/your/raw_topic.

republish runs on Jazzy but my raw topic is empty. Why?

The positional compressed raw words are ignored on Jazzy and Lyrical. The startup log shows The 'in_transport' parameter is set to: raw. Pass -p in_transport:=compressed -p out_transport:=raw and remap in/compressed.

How do I decompress a compressed image topic to raw in ROS 2?

Install ros-$ROS_DISTRO-compressed-image-transport, then run republish with the input transport set to compressed and the output set to raw, using the form for your distro. Remap in/compressed to your compressed topic and out to the raw topic you want.

What does "Unable to load plugin for transport 'image_transport/compressed_sub'" mean?

The compressed plugin isn't installed, so only the raw transport exists. ros2 run image_transport list_transports shows which ones are available. Installing ros-$ROS_DISTRO-compressed-image-transport fixed it on Humble, Jazzy and Lyrical.

How do I write a republish launch file that works on Humble and Jazzy?

Give the Node both arguments=['compressed', 'raw'] and parameters=[{'in_transport': 'compressed', 'out_transport': 'raw'}], plus remappings for in/compressed and out. Humble used the arguments, Jazzy and Lyrical used the parameters, and all three delivered raw images.
