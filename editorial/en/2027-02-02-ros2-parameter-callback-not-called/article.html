terminate called after throwing an instance of 'rclcpp::exceptions::ParameterModifiedInCallbackException'
  what():  cannot set or declare a parameter, or change the callback from within set callback

That is the loud version. The quiet version is worse: you register a callback with add_on_set_parameters_callback, run ros2 param set, get Set parameter successful, and your callback never runs.

Short answer: in C++, store the handle that add_on_set_parameters_callback returns in a member variable. If you drop it, the callback is gone right away and no error tells you. In both C++ and Python, register the callback before declare_parameter, or it never sees the start-up values from -p or a params file. Make sure something spins the node. And never set or declare a parameter from inside the callback in C++. On Humble, defer that change to a timer. On Jazzy and Lyrical, use a pre-set callback instead:

// member: rclcpp::node_interfaces::OnSetParametersCallbackHandle::SharedPtr handle_;
handle_ = add_on_set_parameters_callback(
  [this](const std::vector<rclcpp::Parameter> & ps) {
    rcl_interfaces::msg::SetParametersResult r;
    r.successful = true;
    for (auto & p : ps) {
      if (p.get_name() == "gain" && p.as_double() > 2.5) {
        r.successful = false;
        r.reason = "gain must be <= 2.5";
      }
    }
    return r;   // validate only: no set_parameter() or declare_parameter() here
  });
declare_parameter("gain", 1.0);   // after the callback, so it sees the -p value

In Python, the callback must return a SetParametersResult. Returning None or True killed the node at start-up in every run.

What I ran

On 2026-11-20 I used the official ros:humble-ros-base, ros:jazzy-ros-base and ros:lyrical-ros-base images on a 2 vCPU Linux host. Each container ran with --network none and ROS_DOMAIN_ID=88. One Python script and one C++ executable, both a node named pcb, declare gain (default 1.0) and mode (default "idle"). They log every callback call with the parameters it received. A command-line argument picks the case.

Each case started the node with --ros-args -p gain:=2.0 (gain:=5.0 for one case). Two seconds after the node was up, the script ran ros2 param set /pcb gain 3.0 twice, then ros2 param get for both parameters. Every CLI call had a 15-second limit. Then it stopped the node with SIGINT. That made 14 Python cases and 13 C++ cases per distro.

Cause 1: the C++ handle was dropped

add_on_set_parameters_callback returns a shared_ptr to a handle. The node doesn't keep the callback alive for you. When your copy of the handle is gone, so is the callback. In my discard case the call's result was thrown away. Both ros2 param set calls printed Set parameter successful, ros2 param get showed Double value is: 3.0, and the node exited with on_set_calls=0. Nothing validated the value and nothing logged an error.

The compiler did warn. On all three distros, colcon build printed this for the line that dropped the handle:

warning: ignoring return value of ‘rclcpp::node_interfaces::OnSetParametersCallbackHandle::SharedPtr rclcpp::Node::add_on_set_parameters_callback(OnSetParametersCallbackType)’, declared with attribute ‘warn_unused_result’ [-Wunused-result]

That is the Jazzy and Lyrical text. On Humble the argument type reads rclcpp::Node::OnParametersSetCallbackType.

If your build log has this line, that is your bug. The ros2/demos discussion on the parameter callback demo spells it out: keep the pointer, or the callback is unregistered immediately. I only tested a discarded return value. A handle in a local variable that goes out of scope should behave the same, but I didn't test it. rclpy has no handle to lose. In my runs the Python callback kept working without storing anything.

Cause 2: the callback was registered after declare

declare_parameter runs the on-set callbacks that exist at that moment. With the callback registered first, the first two calls in every run were gain=2.0 (the -p override) and mode=idle (the plain default). Registered after the declares, the callback started with zero calls. It only saw the later ros2 param set values.

This is the launch parameter question exactly: the value from the launch file or a params file arrives during declare_parameter, before a late callback exists. I tested -p, not a launch file or a params file. My params YAML post measured how those overrides are parsed and when they are silently skipped, on the same three distros. If your callback also validates start-up values, register it first. Then a rejected start-up value fails loudly, as the next section shows.

Cause 3: nothing spins the node

ros2 param set is a service call to the node. Services are handled by the executor, so a node that never spins can't answer. My no_spin case declared the parameters and then sat in while rclpy.ok(): time.sleep(0.1) (C++: sleep_for(100ms)). On all three distros, all four ros2 param calls hit the 15-second limit (exit code 124). They printed no result. On Lyrical, the Python CLI printed !rclpy.ok() as the limit killed it. The callback count stayed at 2, both from start-up.

This is the "not trigger with open loop" question. Run the loop body in a timer and call spin, or spin in another thread. The same rule explains a related hang I measured in rclpy rate.sleep() blocks forever: a rate waits on a timer callback that only an executor runs. A callback that blocks the executor has the same effect on parameter services. My rclpy and asyncio post measured an awaited service call that hung on a single-threaded executor until it moved to a reentrant callback group.

Cause 4: setting or declaring inside the callback

In C++ this is the error at the top. My set_inside case called set_parameter(rclcpp::Parameter("mode", "changed")) inside the on-set callback when gain became 3.0. declare_inside called declare_parameter("extra", 0) there instead. Both threw ParameterModifiedInCallbackException. Nothing caught it, and the process aborted with exit code 134. The client side looked like a network problem. The first ros2 param set hung until my 15-second limit. The next one failed after about 6 seconds with Wait for service timed out on Humble and Wait for service timed out waiting for parameter services for node /pcb on Jazzy and Lyrical. If ros2 param set hangs once and the node is then gone, read the node's own log.

rclpy has no such guard. In Python, set_parameters inside the callback worked on every distro. The callback was entered again for mode=changed, the inner call returned successful=True, and mode ended as changed. declare_parameter inside the callback also worked once. On the second ros2 param set it raised ParameterAlreadyDeclaredException: Parameter(s) already declared: ['extra'], the node died, and the CLI hung until the limit. So Python lets you do it, but the nested call runs your validation again in the middle of the outer one. The runtime declare question hits the C++ wall from the ros2_control side.

Cause 5: Python callbacks must return a result

A callback that logs and falls off the end returns None. With the callback registered before declare_parameter, this ended the node before it was ready, on every distro:

UserWarning: Callback returned an invalid type, it should return SetParameterResult.
rclpy.exceptions.InvalidParameterValueException: Invalid parameter value (2.0) for parameter. Reason: Callback returned an invalid type: gain

Returning True gave the same two lines. On Humble the exception text is a tuple, ('Invalid parameter value (2.0) for parameter. Reason: Callback returned an invalid type', 'gain'), so search without the trailing : gain. The fix is return SetParametersResult(successful=True) from rcl_interfaces.msg.

A rejected value is a different story. When my callback returned successful=False with a reason, ros2 param set printed Setting parameter failed: gain must be <= 2.5 and gain stayed 2.0. The CLI still exited with code 0, so a script can't detect the failure from the exit status. Parse the output. At start-up a rejected -p value is fatal. Python raised InvalidParameterValueException ... Reason: gain must be <= 2.5. C++ printed terminate called after throwing an instance of 'rclcpp::exceptions::InvalidParameterValueException' with what(): parameter 'gain' could not be set: gain must be <= 2.5.

Two smaller surprises

Setting the same value again still runs the callback. Both of my sets used gain=3.0, and the second one was logged and validated like the first, in both languages. A callback that does real work on every call will redo it.

With two on-set callbacks, both ran on every set, and the one registered last ran first. That held in Python and C++ on all three distros. The maintainers in the demos discussion advise against relying on that order, so treat it as an observation, not an API promise.

The pre-set callback is the clean option. It gets the list of parameters about to be set and may change it. In my runs it was not called during declare_parameter, only for later sets, while the on-set and post-set callbacks were. The post-set callback answers the "callback for when the parameters are already set" question. It runs after the change is accepted, so it is the place to reconfigure. On Humble the timer is the only one of these that works in C++. My timer added a call because the deferred set_parameter goes through the on-set callback like any other set.

Version notes

  • Humble: rclpy 3.3.22 has only add_on_set_parameters_callback. The postcheck package failed with has no member named ‘add_pre_set_parameters_callback’; did you mean ‘add_on_set_parameters_callback’? and the same for add_post_set_parameters_callback.
  • Jazzy (rclpy 7.1.12, rclcpp 28.1.22) and Lyrical (rclpy 10.0.11, rclcpp 32.0.3): all three callback types exist in both languages and behaved identically.
  • The warn_unused_result warning for a dropped handle appeared on all three.
  • Successful ros2 param set and get calls took a median of 1.14 s on Humble, 1.73 s on Jazzy and 1.29 s on Lyrical (range 1.06 to 4.02 s) on this 2 vCPU host.
  • Stopping a Python node with SIGINT was not always clean, which is unrelated to callbacks. Five of 42 Python runs needed SIGKILL after 5 seconds, and one Lyrical run ended in RCLError: failed to initialize wait set: the given context is not valid.
  • A first Jazzy pass with ros2 param set --no-daemon printed Node not found 65 times, often for nodes that were running. The runs above use the daemon. With it, Node not found only appeared after a node had crashed.

FAQ

Why is my add_on_set_parameters_callback never called in C++?

The most common cause in my runs was a dropped handle. Store the returned OnSetParametersCallbackHandle::SharedPtr in a member. Without it, ros2 param set still reported success and changed the value, but the callback ran 0 times. The build log warned with -Wunused-result.

Why doesn't my parameter callback see the value from the launch file?

Start-up overrides are applied inside declare_parameter. In my runs a callback registered after the declare never saw the -p value. I didn't test a launch file. Register the callback first, and it gets one call per declared parameter, with the override or the default.

How do I fix "cannot set or declare a parameter, or change the callback from within set callback"?

Don't call set_parameter or declare_parameter from an on-set or post-set callback in C++. On Jazzy and Lyrical, add the extra parameter in a pre-set callback. On Humble, set a flag and apply the change from a timer.

Why does ros2 param set hang?

In my runs it hung when the node never spun, and when a C++ node aborted inside the callback. Both ran into the 15-second limit. Check that the node spins and that it is still alive.

Is a parameter callback called if the value doesn't change?

Yes. Setting gain to 3.0 twice ran the callback twice, in Python and C++, on Humble, Jazzy and Lyrical.
