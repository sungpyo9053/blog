CvBridgeError: [16UC1] is not a color format. but [bgr8] is. The conversion does not make sense

In C++ the same text comes from cv_bridge::Exception thrown by cv_bridge::toCvCopy. The sibling error on the publishing side is CvBridgeError: encoding specified as bgr8, but image has incompatible type 8UC1.

Short answer: you asked cv_bridge to turn an image into a color or mono format, and the message's encoding is not one cv_bridge treats as color or mono. Depth images (16UC1, 32FC1) and generic OpenCV types (8UC1, 8UC3) all hit it. Ask for the image as it is, then convert it yourself:

depth = bridge.imgmsg_to_cv2(msg, desired_encoding='passthrough')   # uint16, millimetres for 16UC1
view = cv2.convertScaleAbs(depth, alpha=255.0 / 5000)                # 0..5000 mm -> 0..255 for display
# or: view = cv2.normalize(depth, None, 0, 255, cv2.NORM_MINMAX, dtype=cv2.CV_8U)

If you publish the image yourself, name its encoding: bridge.cv2_to_imgmsg(frame, encoding='bgr8'). Without it, a uint8 3-channel array goes out as 8UC3, and every subscriber that asks for bgr8 gets this error. The rules below were identical on Humble, Jazzy and Lyrical.

Cause 1: a depth image asked for as bgr8 or mono8

This is the case in the RealSense question and in most GitHub issues about the error. A depth topic such as /camera/depth/image_raw or an aligned depth topic is 16UC1 (millimetres) or 32FC1 (metres). Code copied from a color callback asks for bgr8, and cv_bridge refuses.

The rule is about labels, not bytes. cv_bridge knows which names mean color or mono (bgr8, rgb8, mono8, mono16 and the like) and which are generic OpenCV types (8UC1, 16UC1, 32FC1, 8UC3). A generic source can't go to a color or mono target. That is why [8UC1] is not a color format. but [mono8] is appears even though both are one 8-bit channel, the case in vision_opencv issue 175. It is also why mono16 is refused for a 16UC1 depth image. Swapping bgr8 for mono16 doesn't help.

The same data labelled mono16 converts without complaint, and that shows what you would get. A mono16 pixel of 1500 became 6 in mono8 and [6, 6, 6] in bgr8. The value is divided by about 256. At that factor a depth range of 500 to 4500 mm would land between 2 and 18 out of 255, which looks black. Relabelling a depth message as mono16 silences the error but doesn't give you a usable picture.

Numeric targets do work for depth, but read the values:

Asking for 16UC1 from a 32FC1 depth image turns 1.5 m into 2, not 1500. If you need millimetres from a float image, multiply first: (depth_m * 1000).astype(np.uint16). The units part is the same one that matters when you turn a depth pixel into a 3D point.

Cause 2: the publisher sent 8UC3 instead of bgr8

cv2_to_imgmsg defaults to encoding='passthrough', and passthrough names the OpenCV type, not the color order. In my run a uint8 HxWx3 array was published as 8UC3. Reading that message back with imgmsg_to_cv2(msg, 'bgr8') failed with [8UC3] is not a color format. but [bgr8] is. The conversion does not make sense, the error in fiducials issue 208. The fix belongs on the publisher: cv2_to_imgmsg(frame, encoding='bgr8'). If you can't change the publisher, read with passthrough and treat the array as BGR yourself.

What passthrough wrote for each array type:

The int64 case is common. np.zeros((h, w), dtype=int) and many NumPy operations give int64, and the resulting KeyError doesn't mention cv_bridge at all. Cast before publishing.

Cause 3: cv2_to_imgmsg with an encoding that doesn't fit the array

On the publishing side the check is strict: dtype and channel count must match the encoding. A 2D uint8 array as bgr8 failed with encoding specified as bgr8, but image has incompatible type 8UC1. A 4-channel array as bgr8 gave incompatible type 8UC4. A float64 array as 32FC1 gave incompatible type 64FC1, and a uint16 array as mono8 gave incompatible type 16UC1. Unlike imgmsg_to_cv2, cv2_to_imgmsg never converts. It only labels. Convert with OpenCV first (cv2.cvtColor(gray, cv2.COLOR_GRAY2BGR), cv2.cvtColor(bgra, cv2.COLOR_BGRA2BGR), arr.astype(np.float32)) and then publish with the matching name.

Cause 4: rgb8 vs bgr8, the silent one

No error here, just wrong colors. A message labelled rgb8 with pixel (10, 20, 30) came back as [30, 20, 10] when I asked for bgr8, which is correct: cv_bridge swapped the channels for OpenCV. With passthrough it stayed [10, 20, 30], still RGB, so cv2.imshow or cv2.imwrite would show red and blue swapped. If you plan to use OpenCV functions, ask for bgr8, not passthrough.

Cause 5: a broken encoding field or buffer

Hand-built sensor_msgs/Image messages and some drivers get the header fields wrong. An empty encoding gave Unrecognized image encoding [] both with passthrough and with bgr8, which matches the C++ report in this IR camera question. BGR8 in upper case was also unrecognized. The names are case-sensitive and lower case. A typo in desired_encoding gave a slightly different message, Unknown encoding bgr. A buffer half the declared size gave TypeError: buffer is too small for requested array. A mono8 message with two padding bytes per row (step 8 for width 6) converted fine to shape (4, 6), so row padding is handled.

None of these will bottleneck a 30 Hz camera. The choice is about what the picture shows. With a test image of 500 to 4499 mm and one zero pixel, convertScaleAbs(alpha=255/5000) gave a maximum of 229 and kept 0 as 0, so brightness means the same distance in every frame. normalize with NORM_MINMAX stretched the frame to the full 0 to 255, which shows more detail but changes from frame to frame, and the zero "no depth" pixels pull the minimum down. For metres, divide in NumPy: depth.astype(np.float32) / 1000.0 gave 1.140 for a 1140 mm pixel.

In C++ there is a helper for exactly this. cv_bridge::cvtColorForDisplay(cv_bridge::toCvCopy(msg), "bgr8") accepted the 16UC1 message that toCvCopy(msg, "bgr8") rejected and returned a bgr8 image. With default options the 1500 pixel became [6, 6, 6], the same divide-by-256 as mono16. With CvtColorForDisplayOptions.do_dynamic_scaling = true the brightest pixel became 255 and the darkest 0. The Python CvBridge class had no cvtColorForDisplay on any distro, so in Python you do the scaling with OpenCV as shown above.

One C++ trap: toCvCopy(msg, "passthrough") threw Unknown encoding passthrough as a std::exception, not a cv_bridge::Exception. A catch (cv_bridge::Exception &) block won't catch it. In C++, passthrough is an empty string: toCvCopy(msg) or toCvCopy(msg, "") returned the 16UC1 image unchanged.

Version notes

All error messages and the full 110-cell matrix matched across Humble (cv_bridge 3.2.1, OpenCV 4.5.4, NumPy 1.21.5), Jazzy (cv_bridge 4.1.0, OpenCV 4.6.0, NumPy 1.26.4) and Lyrical (cv_bridge 4.1.0, OpenCV 4.10.0, NumPy 2.3.5). Two things differed:

  • A 16UC1 message with is_bigendian=1 converted correctly (1500 stayed 1500) on Humble and Jazzy. On Lyrical it raised AttributeError: `newbyteorder` was removed from the ndarray class in NumPy 2.0. Little-endian messages worked on all three. If you see this on Lyrical, the sender set is_bigendian.
  • The C++ header: on Humble my script did not find cv_bridge/cv_bridge.hpp and compiled against cv_bridge/cv_bridge.h. Jazzy and Lyrical had cv_bridge/cv_bridge.hpp.

Timings were close on all three. Lyrical was fastest for the 16UC1 paths, but differences of a few hundredths of a millisecond on a shared 2 vCPU host are not a reason to pick a distro.

FAQ

What does "[16UC1] is not a color format. but [bgr8] is" mean?

You asked cv_bridge to convert a depth image (16-bit, one channel) into a color image. cv_bridge only converts between color and mono encodings, and 16UC1 is neither. Use desired_encoding='passthrough' and scale the values with OpenCV if you want to display them.

Why does 8UC1 to mono8 fail when they are the same format?

The check uses the encoding names, not the bytes. 8UC1 is a generic OpenCV type and mono8 is a mono format, so the conversion is refused on Humble, Jazzy and Lyrical. Read with passthrough, or have the publisher send mono8.

How do I fix "encoding specified as bgr8, but image has incompatible type 8UC1"?

The array you passed to cv2_to_imgmsg is grayscale. Either publish it as mono8, or convert it first with cv2.cvtColor(img, cv2.COLOR_GRAY2BGR) and then publish as bgr8. cv2_to_imgmsg labels data but never converts it.

Why does my subscriber get "[8UC3] is not a color format"?

The publisher called cv2_to_imgmsg(frame) without an encoding, so the message says 8UC3. Add encoding='bgr8' on the publisher. On the subscriber side, passthrough works in the meantime.

Does converting 32FC1 depth to 16UC1 give millimetres?

No. In my run 1.5 became 2. cv_bridge rounds the value and does not rescale it. Multiply by 1000 in NumPy and cast to uint16 yourself.
