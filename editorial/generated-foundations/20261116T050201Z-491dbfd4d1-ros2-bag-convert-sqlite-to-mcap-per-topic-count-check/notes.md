# Purpose-built educational example

설명용으로 가정한 bag 하나를 둡니다. 60초 동안 /imu 200 Hz, /scan 10 Hz, /camera/image_raw 15 Hz를 sqlite3 저장소로 녹화했다고 봅니다. 단위는 메시지 수(개)와 초(s)입니다. 기대 개수는 발행 주기가 정확하고 녹화 시작과 끝에서 빠진 메시지가 없다는 이상적인 조건에서 'Hz × 초'로 정했습니다. 주기를 크게 다르게 고른 데는 이유가 있습니다. 개수가 많은 /imu가 총합을 지배하는 동안, 개수가 적은 토픽 하나가 사라져도 총합 비교에서는 잘 드러나지 않는다는 점을 보이려는 것입니다. 반례는 둘을 둡니다. 하나는 카메라 토픽 900개가 통째로 빠진 경우이고, 다른 하나는 같은 900개가 /imu에서 빠진 경우입니다. 이 둘로 총합이 같아도 토픽별 판정이 달라진다는 점을 보입니다. 실제 실험에서는 ROS 2 Jazzy 컨테이너에서 합성 토픽을 sqlite3로 녹화하고, --help로 확인한 옵션 형식에 따라 ros2 bag convert로 mcap 저장소에 다시 씁니다. 그런 다음 두 bag에 ros2 bag info를 실행해 출력에 나온 필드와 개수를 이 표와 맞춥니다. 변환이 메시지를 보존하는지, info가 토픽별 개수를 보여 주는지는 이 실험에서 잴 대상이며 여기서 미리 단정하지 않습니다.

기대 개수는 토픽별로 12000, 600, 900개이고 총합은 13500개입니다. 변환 후 토픽별 개수가 모두 기대값과 같아 차이가 0일 때만 개수 기준 통과입니다. 반례 A처럼 카메라 토픽이 통째로 빠지면 총합은 12600개로 6.7%만 줄어 눈에 잘 띄지 않지만, 토픽 단위로 보면 손실이 100%입니다. 반례 B처럼 같은 900개가 /imu에서 빠져도 총합은 똑같이 12600개입니다. 그래서 총합만으로는 문제가 있는지도, 어느 토픽인지도 확정할 수 없고 토픽별 표와 하나씩 맞춰야 합니다. 독자는 자기 bag의 토픽, Hz, 녹화 시간으로 같은 표를 만듭니다. 실제 bag에서는 변환 전 ros2 bag info에서 읽은 값으로 기대값을 바꾼 뒤, 변환 직후 토픽별 차이를 확인하면 됩니다.

이 예제는 발행 주기가 정확하다고 가정한 산술 모델이며, rosbag2를 실행해 얻은 결과가 아닙니다. 실제 bag의 개수는 녹화 시작 지연이나 메시지 누락 때문에 Hz × 시간과 다를 수 있으므로, 기대값은 변환 전 bag에서 읽은 값으로 바꿔 쓰는 것이 원칙입니다. 다음 내용은 제공된 README 발췌에 없어서 이 글에서 단정하지 않으며, --help와 실험으로 확인해야 합니다. convert의 입력·출력 옵션 형식과 출력 분할 옵션이 있는지 여부, 저장소별 최소 분할 크기, ros2 bag info가 보여 주는 필드(토픽별 개수, duration의 정의)가 여기에 해당합니다. 개수가 같다고 해서 메시지 내용, 타임스탬프, QoS 메타데이터까지 같다고 볼 수는 없습니다. 배포판 사이(예: Jazzy→Humble)나 CPU 아키텍처 사이의 bag 호환성, 파일 크기와 압축률도 이 계산으로는 판단할 수 없습니다.
