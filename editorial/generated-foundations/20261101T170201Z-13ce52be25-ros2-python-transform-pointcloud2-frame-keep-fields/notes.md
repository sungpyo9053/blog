# Purpose-built educational example

설명용 산술 모델이다. 센서 프레임 laser의 점 p_laser = (1.0, 0.5, 0) m를 base_link 좌표로 바꾼다. laser 프레임은 base_link에 대해 z축 기준 반시계 90° 돌아 있고 원점은 (0.25, 0, 0.125) m에 있다고 가정한다. 데이터 변환은 p_base = R·p_laser + t이며, 90° 회전은 (x, y) → (−y, x)다. 회전각을 90°로 고른 이유는 삼각함수 없이 사칙연산만으로 따라갈 수 있어서이고, 0.25와 0.125는 이진수로 정확히 표현돼 반올림 오차가 생기지 않는 값이다. 바이트 계산은 x·y·z·intensity가 모두 float32이고 offset이 0·4·8·12, point_step이 16인 width 1000·height 1 클라우드를 가정한다. 사례 1~3은 변환된 좌표, 사례 4는 회전을 빠뜨리고 이동만 더했을 때의 제곱 오차(m²)를 구한다. 사례 5~7은 원본과 xyz만으로 다시 만든 클라우드의 data 바이트와 줄어든 비율, 사례 8~9는 새 클라우드에서 옛 intensity offset이 가리키는 바이트 위치다.

사례 1~3에서 laser 앞쪽 1 m 점은 base_link에서 (−0.25, 1.0, 0.125) m가 된다. 회전을 빠뜨리면 제곱 오차가 2.5 m²(약 1.58 m)로, 이동만 맞춘다고 변환이 끝나지 않는다. 사례 5~7은 좌표를 맞게 바꿨더라도 x·y·z 필드만 넘겨 다시 만들면 data가 16000바이트에서 12000바이트로 25% 줄어든다는 것을 보여 준다. 줄어든 만큼이 intensity가 사라진 몫이다. 사례 8과 9의 값이 둘 다 36이라는 것은, 옛 offset을 그대로 믿고 intensity를 읽는 코드가 오류 없이 다음 점의 x를 읽는다는 뜻이다. 그래서 변환 노드에는 세 가지 확인을 넣는다. 원본 fields와 point_step을 그대로 넘겨 다시 만들고, len(data) == width × height × point_step이 원본과 같은지 비교하고, header.frame_id가 target 프레임인지 확인한다.

하드웨어나 라이브러리를 실행하지 않은 산술 교육 모델이다. 실제 변환은 쿼터니언과 임의 각도를 쓰므로 90° 회전만 다룬 이 계산을 일반 변환 코드의 검산으로 쓸 수는 없다. 공급된 sensor_msgs_py 소스는 'Point step size in bytes. Calculated from the given fields by default'라고 적고 있다. 다만 fields에 x·y·z만 있을 때 point_step이 정확히 12가 된다는 것은 numpy dtype 규칙에서 나온 추론이므로 실행으로 확인해야 한다. 실제 드라이버는 패딩 때문에 point_step이 32인 경우도 있어 바이트 수가 달라진다. tf2의 published transform은 frame 표현이라 data 변환의 역이라는 점도 주의해야 한다. 이 모델은 R·t를 data 변환으로 이미 갖고 있다고 가정한다. tf2_sensor_msgs의 doTransform이나 C++ 경로, 메시지 시각(stamp)에 맞춘 lookup, NaN 점 처리는 공급된 소스에 없어 다루지 않는다. 이 계산만으로는 실제 노드가 어떤 클라우드를 발행하는지 말할 수 없다.
