# Purpose-built educational example

설명용 가정이다. 카메라는 시뮬레이션 시간 기준 16 Hz로 발행하고(sim 주기 1/16 = 0.0625 s), 인식 노드는 프레임 하나를 처리하는 데 벽시계로 0.25 s(최악 0.375 s)를 쓴다. 구독은 keep last depth 1이고, 처리가 끝나면 큐에 남은 가장 최신 프레임 하나를 처리한다. 단위는 초(s)이고 RTF는 단위가 없는 비율이다. 처리 시간은 RTF와 상관없이 벽시계로 일정하다고 본다. 사례는 상한(경계), 상한보다 빠른 RTF 1과 0.5(반례), 처리 시간 변동, 여유, 벽시계 비용을 차례로 확인하도록 골랐다. 후속 실험에서는 rclpy로 목표 RTF에 맞춰 /clock을 발행하는 노드, sim 타이머로 16 Hz 메시지를 보내는 노드, 콜백에서 0.25 s를 쓰는 구독 노드를 ROS 2 Jazzy 컨테이너에서 실행한다. RTF 1, 0.5, 0.25, 0.2에서 발행 수 대비 처리 수를 세어 계산과 비교한다.

처리 시간이 0.25 s인 노드가 16 Hz 프레임을 하나도 놓치지 않으려면 RTF를 0.25 이하로 낮춰야 한다. RTF 1에서는 처리 한 번 동안 프레임 4개가 쌓여 keep last 1 기준 4개 중 1개만 처리되고, RTF 0.5에서는 2개 중 1개가 처리된다. 처리 시간이 프레임마다 흔들리면 평균이 아니라 최악값으로 상한을 잡아야 한다. 최악 0.375 s를 반영하면 상한은 약 0.167이고, 평균 기준 0.25를 쓰면 최악 프레임에서 1.5개가 쌓여 다시 뒤처진다. 대신 기다리는 시간은 벽시계로 치른다. 60 s 시뮬레이션이 240 s 걸린다. 독자는 먼저 자기 노드의 최악 처리 시간을 잰 뒤 RTF를 정하면 된다.

순수 산술 모델이다. 처리 시간이 벽시계로 일정하다고 가정했고, CPU를 시뮬레이터와 나눠 쓰면서 처리 시간이 RTF에 따라 바뀌는 효과, /clock 전달 지연과 발행 간격, executor 스케줄링, 통신 지연은 넣지 않았다. 센서가 sim 시간 기준으로 발행한다는 점과 시뮬레이터가 목표 RTF를 실제로 달성한다는 점도 가정이며, Gazebo 설정 항목(real_time_factor 등)은 공급된 공식 자료로 확인하지 않았으므로 다루지 않는다. 처리 비율 식은 keep last 1에서 최신 프레임만 처리할 때의 근사이고, depth가 크거나 KEEP_ALL이면 프레임이 버려지는 대신 지연이 누적된다. 시뮬레이션 일시정지로 결과를 기다리는 방식도 공식 설계 문서에 언급되지만 이 계산 범위 밖이다. 실제 로봇은 시간을 늦출 수 없으므로 이 방법은 시뮬레이션에만 해당하며, 실물에서 처리 시간이 센서 주기를 넘는 문제는 따로 다뤄야 한다.
