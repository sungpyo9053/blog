# Purpose-built educational example

rclpy Jazzy time.py의 생성·분해 규칙을 사칙연산으로 따라가는 교육용 모델이다. 생성 규칙은 total_nanoseconds = int(seconds × 10^9) + nanoseconds, 분해 규칙은 seconds_nanoseconds()가 10^9로 나눈 몫과 나머지를 돌려주는 것, 기본값은 seconds=0·nanoseconds=0이다. Time + Duration은 나노초를 더하고 clock_type을 유지한다. 단위는 초(s)와 나노초(ns)다. 1.5초, 2초+500000000 ns, 250000000 ns는 이진 부동소수점으로 정확히 표현돼 int() 절삭 오차가 없는 설명용 값이다. 측정값이 아니다. 마지막 사례는 clock_type 불일치 시 TypeError를 직접 던지도록 소스에 적힌 메서드 수를 센다.

Time()은 현재 시각을 읽는 함수가 아니다. 0 ns짜리 SYSTEM_TIME 시각 객체를 만드는 생성자다. 같은 클래스의 from_msg()는 기본으로 ROS_TIME을 붙이므로, Time(seconds=1.5)를 메시지로 보냈다가 from_msg로 되돌리면 나노초 차이가 0인데도 == 비교가 TypeError로 실패한다. Time - Time과 <, <=, >, >=도 같은 규칙을 따른다. 반대로 Time + Duration이나 Time - Duration은 clock_type을 검사하지 않고 원래 clock_type을 유지한다. 독자가 할 일은 두 가지다. 기준 시각을 직접 만들 때 Time(seconds=…, clock_type=…)처럼 비교 상대와 같은 clock_type을 명시한다. 그리고 자기 노드의 get_clock().now()가 어떤 clock_type인지 추측하지 말고 출력해 확인한다. 설계 문서는 ROSTime을 기본으로 쓸 것을 '기대'한다고만 적고 있다. 실험 계획은 다음과 같다. ROS 2 Jazzy 컨테이너에서 use_sim_time을 끈 노드와 켠 노드 각각에 대해 Time(), Time.from_msg(msg), node.get_clock().now()의 clock_type을 출력한다. 이어서 세 객체를 짝지어 빼고 비교해 어느 조합이 TypeError를 내는지 표로 기록한다.

산술은 rclpy Jazzy time.py 소스에 적힌 생성·분해 규칙을 따라간 것이며, ROS 노드를 실행한 결과가 아니다. Node.get_clock()이 돌려주는 시계의 clock_type은 공급된 소스에 직접 나오지 않으므로 이 글에서는 사실로 단정하지 않고 측정 대상으로 남긴다. use_sim_time 설정에 따라 그 값이 달라지는지도 마찬가지다. TypeError의 실제 메시지 문구는 소스 문자열("Can't subtract times with different clock types", "Can't compare times with different clock types")까지만 확인했고 실행 출력은 보지 않았다. Humble 등 다른 배포판의 rclpy 기본값은 확인하지 않았다. __ne__는 __eq__를 거쳐 간접적으로 같은 예외를 낼 것으로 읽히지만 6개 집계에는 넣지 않았다. 1.5초 같은 값은 int() 절삭 오차가 생기지 않도록 고른 것이며, 이진수로 정확히 표현되지 않는 초 값에서는 1 ns 단위 차이가 생길 수 있다. /clock 수신 전 0초 문제와 SteadyTime 사용법은 다루지 않는다.
