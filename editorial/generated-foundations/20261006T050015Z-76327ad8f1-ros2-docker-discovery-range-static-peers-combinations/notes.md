# Purpose-built educational example

공식 문서 'Using Improved Dynamic Discovery'의 두 표를 O=1, X=0으로 바꿔 칸을 세는 산술 모델이다. 행은 노드 A의 설정, 열은 노드 B의 설정이고, 각각 정적 피어 유무 2가지 × 발견 범위 3가지(OFF, LOCALHOST, SUBNET)라서 표 하나는 6×6=36칸이다. 각 수식은 표의 한 행씩 O의 개수를 더하거나, 특정 조합 칸의 0/1 값을 더한 것이다. 행 순서는 A=정적 피어 없음·OFF, 없음·LOCALHOST, 없음·SUBNET, 있음·OFF, 있음·LOCALHOST, 있음·SUBNET이다. 같은 호스트 표의 행별 O 개수는 0, 4, 4, 0, 4, 4이고, 다른 호스트 표는 0, 2, 3, 0, 4, 4다. 단위는 '조합 칸 수'이며 비율 하나만 단위가 없다. 이 입력을 고른 이유는 세 가지다. 질문자의 증상인 '같은 PC에서는 되고 경계를 넘으면 안 됨'이 두 표의 차이에 해당하고, OFF와 LOCALHOST라는 두 경계 사례가 결론을 가르며, 정적 피어를 한쪽에만 넣는 경우가 실무에서 고칠 행동과 직결되기 때문이다.

공식 표대로라면 노드를 다른 호스트로 나눴을 때 통신하는 조합은 16칸에서 13칸으로 줄고, 줄어드는 3칸은 모두 정적 피어 없이 LOCALHOST를 쓴 경우다. 그러니 경계를 넘자 노드가 안 보인다면 먼저 양쪽 컨테이너의 ROS_AUTOMATIC_DISCOVERY_RANGE가 OFF나 LOCALHOST인지 확인한다. LOCALHOST로 두고 싶다면 적어도 한쪽의 ROS_STATIC_PEERS에 상대 주소를 넣으면 표상 O가 된다. 어느 한쪽이 OFF라면 피어 목록과 상관없이 통신하지 않으므로 그 노드의 범위부터 바꿔야 한다. 기본값인 SUBNET끼리는 표에서 항상 O이므로, 이 경우에도 안 보인다면 원인은 이 두 환경변수 밖에 있다고 보고 다음 점검으로 넘어간다.

이 계산은 공식 문서 표의 O/X를 옮겨 센 것일 뿐 네트워크 측정이 아니다. Docker 브리지 네트워크의 컨테이너가 표의 '다른 호스트'에 해당하는지, SUBNET 설정에서 컨테이너 사이에 멀티캐스트가 실제로 전달되는지, host 네트워크 모드에서 어떻게 동작하는지는 문서가 말하지 않으므로 컨테이너 실험으로 따로 확인해야 한다. 정적 피어 표의 O는 상대 주소를 목록에 올바르게 넣었다는 가정 위의 값이다. 문서에 따르면 이 두 환경변수는 rmw_zenoh에서 지원되지 않는다. 질문자가 쓴 Foxy에서 이 변수들을 쓸 수 있는지, 질문자 사례의 실제 원인이 무엇이었는지는 이 근거로 판정할 수 없다. 방화벽, 네트워크 인터페이스 선택, 공유 메모리 전송, QoS 불일치, 서로 다른 배포판이나 RMW 간 통신 같은 다른 원인도 이 표로는 걸러지지 않는다. 표의 칸 수는 설정 조합의 개수일 뿐 실제로 어떤 설정이 얼마나 자주 쓰이는지나 장애 빈도를 뜻하지 않는다.
