# Purpose-built educational example

카메라 이미지 토픽의 데이터량을 사칙연산만으로 계산하는 교육용 모델이다. 로봇 벤치마크나 Gazebo 측정값이 아니다. 단위는 픽셀, 바이트, MB(=1,000,000바이트), 초다. 픽셀당 3바이트는 컬러 rgb8 인코딩을 가정한 값이고, 제공된 공식 소스에 적힌 값이 아니다. 해상도는 흔히 쓰는 1920×1080(Full HD), 640×480, 3840×2160(4K)을 골랐고 fps는 30으로 고정했다. 2×2 binning 사례에는 CameraInfo 주석의 (width/binning_x)×(height/binning_y) 규칙을 그대로 적용했다. 같은 규칙으로 받은 이미지의 가로 크기가 얼마여야 하는지도 계산해, CameraInfo와 실제 이미지 크기를 맞춰 보는 점검 기준으로 쓴다. depth 사례는 QoS 문서의 기본값 keep last 10과, 경계 비교를 위해 고른 depth 1이다. sensor data 프로필의 정확한 depth 값은 제공된 소스에 없으므로 쓰지 않았다. 각 사례가 질문의 어느 부분에 답하는지는 다음과 같다. 픽셀 수와 프레임 바이트는 고해상도가 얼마나 무거운지, MB/s는 초당 부담, 비율은 해상도를 낮췄을 때 얼마나 줄어드는지, depth 상한은 큐가 붙잡을 수 있는 메모리, binning 출력 폭은 CameraInfo 점검 기준에 해당한다.

해상도를 가로·세로 각각 절반으로 줄이거나 2×2 binning을 쓰면 픽셀 수와 데이터량이 1/4로 준다. 1920×1080에서 640×480으로 내리면 6.75배 준다. 4K 30 fps 컬러 토픽은 Full HD의 4배인 초당 약 746.5 MB다. 기본 QoS keep last 10은 Full HD 컬러 이미지를 큐 하나에 최대 약 62.2 MB까지 보관할 수 있고, depth를 1로 두면 이 상한이 한 프레임 크기인 약 6.2 MB로 내려간다. 보정 width가 1920이고 binning_x가 2라면 받은 이미지의 가로는 960이어야 한다. 이 값이 맞지 않으면 CameraInfo와 이미지가 서로 다른 설정을 가리키고 있다는 신호다. 따라서 고해상도 카메라 때문에 느려졌다고 느낄 때는 이렇게 진행한다. 먼저 자기 설정값으로 MB/s와 depth 상한을 계산한다. 다음으로 같은 해상도의 합성 이미지를 시뮬레이터 없이 발행해 메시지 쪽 부담만 따로 잰다. 이어서 받은 이미지 크기와 CameraInfo의 width·height·binning·K[0]을 대조한다. 그 결과를 보고 해상도·fps·depth를 줄일지, 렌더링 설정을 따로 볼지 정한다.

이 계산은 메시지에 담기는 원시 이미지 바이트만 센다. Gazebo의 렌더링·물리 계산 비용, GPU 사용 여부, real time factor 변화는 전혀 계산하지 않으므로 질문자의 시뮬레이션이 느려진 원인을 확정하지 못한다. 픽셀당 3바이트는 rgb8 가정이고, 다른 인코딩이나 압축 이미지 토픽에서는 값이 달라진다. 메시지 헤더, 직렬화 복사, RMW·DDS 내부 버퍼, 프로세스 간 복사 횟수는 포함하지 않았다. keep last depth로 구한 값은 문서 정의에 따른 보관 개수의 상한일 뿐 실제 메모리 사용량이 아니다. sensor data 프로필의 depth 숫자는 제공된 소스에 없어서 쓰지 않았다. CameraInfo 점검 기준은 메시지 정의 주석에 적힌 의미만 따른다. Gazebo나 특정 드라이버가 해상도를 바꿀 때 CameraInfo의 width·height·binning·K를 실제로 어떻게 채우는지는 제공된 소스로 확인하지 않았으며, 이 부분은 후속 ROS 2 컨테이너 실험에서 직접 확인해야 한다. ROI 설정이 출력 크기에 미치는 영향도 이 계산에는 넣지 않았다.
