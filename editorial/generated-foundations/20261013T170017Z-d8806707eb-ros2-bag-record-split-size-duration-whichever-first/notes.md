# Purpose-built educational example

설명용 녹화 두 가지를 가정한다. 하나는 메시지 하나가 1,000,000바이트이고 30 Hz로 발행되는 카메라 토픽 녹화(데이터율 30,000,000 B/s), 다른 하나는 IMU와 tf를 합쳐 200,000 B/s인 저속 녹화다. 두 녹화 모두 ros2 bag record -b 900000000 -d 60으로 녹화한다고 본다. 단위는 바이트, 초, 개다. 입력값은 나눗셈이 정수로 떨어지도록 골랐다. 실제 센서에서 잰 값이 아니며, 압축과 저장 플러그인 오버헤드는 0으로 둔다. 마지막 두 사례에서는 /tf_static 하나를 5,000바이트로 가정하고, --repeat-transient-local로 파일마다 한 번씩 다시 기록될 때의 추가 용량을 계산한다.

같은 -b 900000000 -d 60 설정에서도 카메라 녹화는 30초마다 크기 기준으로 잘려 1시간에 파일 120개가 되고, 저속 녹화는 크기가 차려면 4500초가 걸리므로 60초마다 시간 기준으로 잘려 60개가 된다. 분할 주기를 정하는 쪽은 옵션이 아니라 토픽 데이터율이다. 데이터율이 높은 녹화에서 파일 길이를 일정하게 맞추고 싶다면 -d만 바꿔서는 소용이 없다. -b를 데이터율 × 원하는 초 이상으로 키워야 한다. /tf_static을 파일마다 다시 기록해도 늘어나는 용량은 전체의 극히 일부라서, 분할된 파일을 하나씩 따로 재생할 계획이라면 켜 두는 비용이 작다. 독자는 ros2 topic bw 같은 도구로 실제 데이터율을 잰 뒤 같은 나눗셈을 해 보고, 짧은 녹화에서 생성된 파일 수가 계산과 맞는지 확인하면 된다.

이 산술은 데이터율이 일정하고 압축, 메타데이터, 저장 플러그인(sqlite3·mcap) 오버헤드가 0이라고 가정한 교육용 모델이다. 실제 분할 시점은 메시지 경계와 쓰기 캐시 때문에 계산값과 어긋날 수 있고, 파일 크기가 -b를 정확히 맞춘다는 보장도 없다. README는 rolling 브랜치 문서라서 사용하는 배포판의 옵션 이름과 동작은 ros2 bag record --help로 따로 확인해야 한다. --repeat-transient-local의 존재와 동작도 rolling README에서 확인한 내용이다. ros2 bag convert로 SQLite bag을 MCAP으로 옮길 때 어떻게 분할되는지, MCAP 자체 압축을 쓰면 크기가 얼마나 달라지는지는 이 계산으로 알 수 없다. ROS 2 노드, rosbag2, 시뮬레이터나 로봇을 실행해 확인한 값도 아니다.
