# Purpose-built educational example

설명용 산술 모델이다. 8 Hz Rate를 쓰는 rclpy 루프를 가정하고, 이진 부동소수점으로 정확히 표현되는 값만 골랐다. 시간 단위는 초(타이머 주기만 ns), 주파수는 Hz다. 가정은 다섯 가지다. 타이머의 시계는 벽시계 속도로 흐른다. 타이머는 주기 격자에 맞춰 발화한다. 루프 본문의 작업 시간은 매번 같다. executor는 별도 스레드에서 지연 없이 타이머 콜백을 실행한다. 지터와 GIL 경합은 없다. 경우는 일곱 가지다. 타이머에 넘길 주기(ns), 정상 주기와 대기 시간, 반복 횟수, 작업 시간이 주기와 정확히 같은 경계, 작업이 주기보다 긴 경우, executor가 없을 때 첫 sleep에서 멈추는 반례다. 마지막 두 경우는 timer.py 원문에서 끌어낸 예측이다. 원문 근거는 콜백이 _event.set으로 바뀌는 점, _num_sleepers가 0일 때만 이벤트를 지우는 _postsleep, 단일 스레드 executor 경고다. 측정으로 확인할 가설로 둔다.

작업 시간이 주기보다 짧고 executor가 별도 스레드에서 타이머 콜백을 실행하면, rate.sleep()은 남은 시간만큼 기다리고 루프는 목표 주파수를 지킨다. 이 예제에서는 매번 0.0625초를 기다리고 5초에 40회를 돈다. 작업 시간이 주기와 같아지면 대기 시간이 0이 되어 여유가 사라진다. 작업이 주기보다 길면 sleep이 기다리지 않고 바로 돌아온다. 그러면 루프는 목표 8 Hz가 아니라 작업 시간이 정하는 4 Hz로 내려간다고 예측된다. 타이머 콜백을 실행해 줄 executor가 없으면 이벤트가 세워지지 않으므로 첫 sleep에서 멈춘다. 그래서 '멈춤'은 주기 계산으로 풀리지 않고, executor 구성 문제로 따로 진단해야 한다. 독자는 자기 루프의 Hz와 작업 시간을 넣어 같은 계산을 해 본 뒤 고른다. spin을 별도 스레드나 MultiThreadedExecutor로 분리할지, 아니면 Rate 대신 create_timer 콜백 하나에 루프 본문을 넣을지다.

이 예제는 교육용 산술 모델이다. ROS 2 노드, 시뮬레이터, 로봇을 실행한 결과가 아니다. 타이머 시계가 벽시계 속도로 흐른다고 가정했다. 제공된 timer.py는 Timer가 clock 인자를 받는다는 사실만 보여 준다. Node.create_rate가 기본으로 어떤 시계를 넘기는지, 그래서 use_sim_time을 켜면 Rate 주기가 /clock 시간을 따르는지는 이 글의 근거로 확인되지 않는다. 같은 이미지에서 측정해 볼 질문으로 남긴다. 반영하지 않은 요소도 있다. 타이머 발화 지터, executor의 콜백 처리 지연, rcl 타이머가 놓친 주기를 처리하는 방식, Python GIL 경합, 운영체제 스케줄링이다. 작업이 길 때의 4 Hz와 executor가 없을 때의 1회 후 정지는 Jazzy rclpy timer.py를 읽고 끌어낸 예측이며 측정값이 아니다. 다른 배포판의 Rate 구현은 다를 수 있다. 주기를 지킨다는 결과가 실시간 마감 보장이나 실물 로봇 제어의 안전성을 뜻하지도 않는다.
