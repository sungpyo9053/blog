# Purpose-built educational example

설명용 산술 모델이며 ROS 노드나 로봇을 실행한 결과는 아니다. rclpy Jazzy time.py에 따르면 Time은 정수 nanoseconds를 보관하고, seconds_nanoseconds()는 그 값을 정수 (초, 나노초)로 나눠 준다. Time끼리 빼면 정수 나노초 차를 담은 Duration이 나온다. 이와 달리 사용자가 각 시각을 float 초(nanoseconds/1e9)로 바꾼 뒤 빼면 64비트 부동소수점으로 계산하게 된다. 이 차이를 초 단위 표현식으로 비교한다. 시스템 시각은 2026년 무렵 값으로 고른 설명용 가정 1790000000초이고, 시뮬레이션 시각은 125초로 가정했다. 1790000000은 2^30과 2^31 사이에 있으므로 이 구간의 float 간격은 2^-22초, 125는 2^6과 2^7 사이라서 간격이 2^-46초라는 전제로 입력을 골랐다. 나노초 정수 그대로는 2^53을 넘으므로, 정수 방식은 seconds_nanoseconds()가 돌려주는 (초, 나노초) 쌍으로 나눠 표현했다. 단위는 모두 초이며 비율 사례만 단위가 없다.

seconds_nanoseconds()로 정수 쌍을 먼저 빼거나 Time끼리 뺀 Duration을 마지막에 초로 바꾸면 1 µs와 1 ms가 각각 1e-06초와 0.001초로 정확히 남는다. 시스템 시각 규모의 float 초를 먼저 만들어 빼면 결과가 2^-22초의 정수배로 반올림되어 1 µs는 약 0.954 µs, 1 ms는 약 0.99993 ms가 된다. 0 근처의 시뮬레이션 시각에서는 간격이 2^24배 작아 이 차이가 거의 드러나지 않는다. 그래서 시뮬레이션에서 통과한 dt 계산이 실제 시스템 시계에서 어긋날 수 있다. 실천 기준은 시각을 초로 바꾸는 시점을 뺄셈 뒤로 미루는 것이다. 표시나 로그용으로 현재 시각 하나만 초로 볼 때는 nanoseconds / 1e9로도 충분하다.

부동소수점 반올림 결과는 공식 ROS 문서가 아니라 호스트가 계산한 산술로 확인하는 내용이다. 실제 루프에서 얼마나 문제가 되는지는 측정하지 않았다. 1790000000초와 125초는 설명용 가정이며 실제 시스템 시각이나 /clock 값이 아니다. rclpy 소스는 Jazzy 브랜치만 확인했으므로 다른 배포판이나 rclcpp의 seconds() 구현이 같다고 가정할 수 없다. clock type이 다른 Time끼리 비교하거나 뺄 때 나는 TypeError, 음수 Duration, Time(seconds=float) 생성 시 int() 절삭으로 나노초가 잘리는 경우, 시뮬레이션 시간 점프는 이 예제 밖이다. 0.24 µs 양자화가 특정 제어기나 적분기의 성능을 얼마나 바꾸는지도 이 계산으로는 알 수 없으며, 실물 로봇의 안전이나 제어 품질을 보증하지 않는다.
