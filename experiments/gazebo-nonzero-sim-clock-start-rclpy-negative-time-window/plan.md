# 실험 계획: 0이 아닌 시각에서 시작하는 시뮬레이션 시계와 rclpy `now() − W`

## 질문

`use_sim_time` 노드가 "지금부터 W초 전"을 `now() − Duration(W)`로 계산할 때 rclpy Jazzy에서
언제 `ValueError`가 나는가? 시뮬레이션 시계를 0이 아닌 시각 S에서 시작하면 이 예외가 모두
사라지는가, 아니면 `/clock`을 받기 전 구간이 여전히 남는가?

Gazebo는 쓰지 않는다. 이 실험은 rclpy·rcl의 시간 처리만 확인한다. Gazebo의
`--initial-sim-time`이 실제로 어떤 첫 `/clock`을 내는지는 확인하지 않는다.

## research.md 기준 예측값

- 정적 확인: `Time(0, ROS_TIME) − Duration(1 s)` → `ValueError('Subtraction leads to negative time.')`,
  원인 예외 `Nanoseconds value must not be negative`. `1 s − 1 s` → 0 ns, 예외 없음.
  `Time − 더 늦은 Time` → 음수 `Duration`, 예외 없음. `Time < Duration` → `TypeError`.
- tf2: 시각 0(ROS_TIME)으로 `lookup_transform`을 부르면 "최신 변환"이 나온다
  (98·99·100 s 변환 중 100 s).
- `/clock` 전 구간(모든 S): 생성자의 `now()`는 0이고 `now() − 1 s`는 예외다. STEADY(벽시계)
  타이머 콜백에서도 now = 0이라 매번 예외다. 시뮬레이션 시계 타이머는 이 구간에 한 번도
  호출되지 않는다(rcl `timer.c` 해석).
- S = 0: 시뮬레이션 시계 f Hz 타이머의 예외 틱 수 = ⌈W·f⌉ − 1, W·f가 정수이면 시각 0을 만드는
  틱 1개. 이 실험의 조합에 대입하면
  - f = 10: W = 0.25 → 예외 2, 0 틱 0 / W = 1 → 9, 1 / W = 2 → 19, 1
  - f = 20: W = 0.25 → 4, 1 / W = 1 → 19, 1 / W = 2 → 39, 1
  (W = 1, f = 10의 9는 verification.json 사례, 나머지는 같은 식에 대입한 값)
- S = 100: 첫 `/clock`(100 s)이 오면 타이머가 즉시 한 번 깨어나고 그때 now = 100 s,
  `now − 1 s` = 99 s. 첫 `/clock` 이후 예외 0.
- S = 0.5, W = 1: 첫 콜백 결과 −0.5 → 예외. S = 1, W = 1: 첫 콜백 결과 0 → 예외 없음, 0 틱.
- 가드: `now.nanoseconds <= W.nanoseconds`이면 건너뛰는 가드는 예외 0, 0 결과 0.
  "now가 0이거나 W 미만"이면 건너뛰는 가드는 예외 0이지만 now = W 틱에서 0 결과가 남는다.
- 벽시계 길이: 실시간 배율 r이 일정하면 W초 구간은 벽시계 W ÷ r초.

계획 작성 중 추가 도출(research.md에 없는 값, 위 rcl 해석과 rcl 타이머의 "놓친 주기 건너뛰기"를
그대로 따른 예측): S = 0.5, W = 1, f = 10이면 틱이 0.5, 0.6, …로 이어져 예외 5, 0 틱 1.

## 무엇을 어떻게 재는가

- 환경: 하네스의 `ros:jazzy-ros-base` 컨테이너, 네트워크 없음, rclpy·rosgraph_msgs·
  geometry_msgs·tf2_ros만 사용. 한 프로세스, `SingleThreadedExecutor` 하나.
- 가짜 시뮬레이터 노드(`use_sim_time` 꺼짐)가 `/clock`을 발행한다. S에서 시작해 메시지마다
  시뮬레이션 10 ms씩 올리고, STEADY 시계 5 ms 주기로 보낸다(명목 r = 2). 대상 노드의
  `/clock` 구독이 매칭된 뒤 벽시계 0.5초 동안은 일부러 `/clock`을 보내지 않는다
  (= `/clock` 전 구간). S + 2.5 s까지 진행한다.
- 대상 노드(`use_sim_time` = true)가 기록하는 것:
  - 생성자에서 `now()` 값과 `now() − 1 s`의 결과(예외 메시지 포함).
  - STEADY 20 Hz 타이머: now = 0인 호출 수와 그중 예외 수, 첫 `/clock` 이후 호출 수와 예외 수.
  - 시뮬레이션 시계 10 Hz·20 Hz 타이머(생성자에서 now = 0일 때 생성): 매 호출의 `now()`
    나노초와 벽시계 시각. 첫 `/clock` 전 호출 수, 첫 호출의 now.
- 사후 집계(같은 실행 안에서, 기록된 now 값으로 실제 rclpy 뺄셈을 다시 수행):
  W = 0.25, 1, 2 s 각각에 대해 예외(neg)·0 결과(zero)·양수(pos) 개수, 첫 양수 틱의 now와
  첫 `/clock` 이후 벽시계 경과, 두 가드(`<=` 가드, "0이거나 미만" 가드)를 적용했을 때의
  예외·0 결과 수. S = 0에서는 ⌈W·f⌉ − 1 모델값을 함께 출력해 나란히 비교한다.
- 타이머 콜백의 now가 주기 격자에서 벗어난 호출 수와 최대 지연(ms)을 출력한다.
  `/clock`이 다음 값으로 이미 넘어간 뒤 콜백이 돌면 경계 0 틱이 작은 양수로 바뀔 수 있으므로,
  이 값으로 모델 가정(촘촘한 `/clock`, 콜백 now = 틱 시각)이 실행마다 성립했는지 판단한다.
- 측정 r = (도달한 시뮬레이션 시각 − 첫 `/clock` 값) ÷ 그 사이 벽시계 시간.
- S = 0, 0.5, 1, 100 네 시나리오를 서로 다른 ROS 도메인 ID(40~43)와 rclpy Context로
  분리해 순서대로 돌린다. 모든 숫자는 실행 중에 측정·계산해 JSON 한 줄씩 출력한다.
- 판정: 예측과 측정이 다르면 측정값을 그대로 보고하고, 격자 이탈 값으로 원인을 구분한다.

## 한계

- Gazebo, `ros_gz_bridge`, 실제 `/clock` 발행 간격(예: 10 Hz처럼 거친 발행)은 재현하지 않는다.
  `/clock` 간격이 타이머 주기보다 거칠면 경계 틱 결과가 달라질 수 있다.
- 단일 executor라 `/clock` 수신과 타이머 콜백 순서가 실제 다중 프로세스 구성보다 규칙적이다.
- rclcpp, Humble 등 다른 배포판, 실물 로봇은 범위 밖이다. 시뮬레이션 산술·라이브러리 동작 확인이다.

## 시행착오

- 첫 시험 실행: 스크립트는 정상 종료했지만, 시나리오마다 W별 상세 dict를 길게 출력해서
  하네스가 저장하는 stdout 마지막 8000자를 넘었다. 앞쪽 줄(env·정적 확인·S = 0 시나리오)이
  잘려 결과에서 사라졌다. 키를 줄이고 W별 결과를 짧은 dict와 [예외, 0 결과] 쌍으로 바꿔
  전체 출력을 한도 안으로 줄였다. 두 번째 시험 실행에서 모든 줄이 남는 것을 확인했다.
- 두 번째 시험 실행에서 일부 시나리오의 20 Hz 타이머에 격자 이탈 호출이 나왔다
  (콜백이 다음 `/clock` 뒤에 실행된 경우). 판정 기준에 영향을 주는 항목이라 숨기지 않고
  출력에 남겼다. 정식 실행에서 경계 0 틱 수가 모델과 다르면 이 값부터 확인한다.
