# 실험 계획: 센서 토픽과 tf2 자료는 다른 길로 오고, 시각 0은 "지금"이 아니라 "최신"인가

## 질문

글(`research.md`)의 핵심 주장을 ROS 2 Jazzy rclpy·tf2_ros로 한 프로세스 안에서 직접 확인한다.

1. 센서 관측 토픽을 구독해 점이 도착해도, 좌표 관계를 공급하는 broadcaster가 없으면 `map ← sensor_link`
   조회는 실패하는가? `TransformListener`는 관측 토픽과 별개로 `/tf`·`/tf_static`을 구독하는가?
2. 몸체–센서 고정 관계(정적 변환)만 있으면 여전히 실패하고, 지도–몸체 관계까지 공급해야 성공하는가?
3. 정적 변환은 로봇이 움직여도(지도–몸체 관계가 바뀌어도) 어느 시각으로 조회하든 같은 값인가?
4. `lookup_transform`에 시각 0(`Time()`)을 주면 "지금 시각"이 아니라 버퍼의 **최신 변환**이 오는가?
   10.0초 관측을 최신 10.2초 변환으로 지도에 놓으면 관측 시각 변환과 얼마나 달라지는가?
5. `frame_id`만 `map`으로 고쳐 적으면 숫자가 변환되지 않는가? 인수 순서(목표, 출발)를 뒤집으면 역변환이 오는가?
6. timeout은 늦게 도착하는 자료는 기다려 주지만, 없는 연결이나 버퍼보다 오래된 시각의 자료는 만들어 주지 않는가?
   노드 시계의 현재 시각으로 조회하면 실패하는가?
7. (보조) 같은 토픽 이름이라도 QoS가 호환되지 않으면 메시지가 오지 않는가?
   늦게 붙은 listener는 `/tf_static`(정적)은 받고 이미 지나간 `/tf`(동적)는 못 받는가?

## 글이 주장한 예측값

글은 수치 측정을 하지 않았다("ROS 설치·통신·실물 로봇 실행은 검증하지 않았다"). 글의 예시 시각
10.0초(관측)·10.2초(최신 변환)를 그대로 입력으로 쓰고, 아래 기하 입력에서 손으로 계산한 값을 예측으로 둔다.
실험 전 값이며 실측이 아니다.

입력: `base_link → sensor_link` 고정 관계 = 이동 (0.2, 0, 0.1) m, yaw 90°. `map → base_link`는 x = 0.5 × t (m),
회전 없음, 시각 9.8·10.0·10.2초에 발행. 관측 점 = `sensor_link` 기준 (1, 0, 0), 시각 10.0초.

| 항목 | 글의 주장 | 예측 |
|---|---|---|
| broadcaster 없음, `map ← sensor_link` | 조회할 자료가 없다 | 실패(`LookupException` 계열), timeout 1초를 줘도 약 1초 기다린 뒤 실패 |
| 관측 토픽 수신 | 데이터 전달은 별개의 연결 | 점은 정상 도착, frame_id `sensor_link`, 시각 10.0 |
| listener 구독 | `/tf`와 `/tf_static`을 구독 | listener 추가 후 구독에 `/tf`, `/tf_static`이 더해짐, `/tf_static`은 TRANSIENT_LOCAL |
| 정적만 있을 때 `map ← sensor_link` | 두 관계가 모두 필요 | 실패(`map` 프레임 없음). `base_link ← sensor_link`는 성공 |
| 정적 관계를 시각 0, 9.8, 10.0, 10.2, 1000초로 조회 | 상대관계는 고정 | 모두 (0.2, 0, 0.1), 같은 회전 |
| `Time()` 조회의 변환 시각 | 시각 0 = 최신 | 10.2초, 이동 (5.3, 0, 0.1) |
| 10.0초 조회 | 관측 시각 변환 | 10.0초, 이동 (5.2, 0, 0.1) |
| 10.1초 조회 | (글에 없음) 보간 | 이동 x = 5.25 |
| 관측 점의 지도 좌표(관측 시각) | — | (5.2, 1.0, 0.1) |
| 관측 점의 지도 좌표(최신 변환) | 의미가 달라질 수 있음 | (5.3, 1.0, 0.1), 차이 0.1 m (= 0.5 m/s × 0.2 s) |
| frame_id만 `map`으로 바꾼 점 | 숫자는 그대로 | (1, 0, 0), 올바른 값과 약 4.32 m 차이 |
| 인수 순서 뒤집기 `sensor_link ← map` @10.0 | 순서가 의미를 정함 | 역변환, 이동 (0, 5.2, −0.1). 지도 점을 되돌리면 (1, 0, 0) |
| 10.5초(최신 이후) 조회 | 아직 없는 자료 | `ExtrapolationException` |
| 9.0초(가장 오래된 9.8초 이전) 조회, timeout 0.5초 | timeout은 과거 자료를 만들지 않음 | 약 0.5초 뒤에도 `ExtrapolationException` |
| 노드 시계 now()로 조회 | 지금 시각 ≠ 최신 | `ExtrapolationException`(변환 시각은 10초 근처) |
| 10.4초 자료를 0.3초 뒤 발행, timeout 2초 | timeout은 늦은 자료를 기다림 | timeout 없이 실패, timeout 2초로는 약 0.3초 뒤 성공 |
| 그 뒤 `Time()` 조회 | 최신을 따라감 | 10.4초 변환 |
| 늦게 붙은 listener | (보조) | 정적 관계 수신, 동적 관계 미수신 |
| BEST_EFFORT 발행 → RELIABLE 구독 | QoS 비호환이면 연결 안 됨 | RELIABLE 구독 수신 0, BEST_EFFORT 구독은 수신, incompatible QoS 이벤트 ≥ 1(RELIABILITY) |

## 측정 방법

- 환경: 하네스의 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB). 이미지에 든 `rclpy`, `tf2_ros`,
  `geometry_msgs`, `tf2_geometry_msgs`만 쓴다. rclpy·tf2_ros_py 버전은 package.xml에서 읽어 출력한다.
- 한 프로세스에 노드 두 개(`tf2_roles_talker`: 관측·변환 발행, `tf2_roles_app`: 관측 구독 + `Buffer` +
  `TransformListener`)를 `MultiThreadedExecutor`로 백그라운드 스레드에서 spin한다. 조회는 메인 스레드에서 한다.
- 단계(모든 줄은 `kind` 필드가 있는 JSON 한 줄):
  1. 관측 구독만 만든 뒤와 `TransformListener`를 붙인 뒤의 구독 토픽·QoS(`subscriptions`).
     관측 점을 받을 때까지 0.1초마다 재발행(최대 10초), 수신 여부·대기·frame_id·시각(`sensor_topic`).
     버퍼 프레임 목록, `map ← sensor_link` 조회(timeout 없음/1초).
  2. `StaticTransformBroadcaster`로 고정 관계 발행 → 버퍼에 들어올 때까지 대기 → `base_link ← sensor_link`,
     `map ← sensor_link` 조회.
  3. `TransformBroadcaster`로 9.8/10.0/10.2초 지도–몸체 관계 발행(구독자가 그래프에 보일 때까지 기다린 뒤,
     3초 안에 안 들어오면 한 번 재발행하고 `retried`에 기록). 이후 `Time()`, 10.0, 10.1, 10.5, 9.0(timeout 0/0.5초),
     노드 시계 now(), 역순, 정적 관계의 여러 시각 조회. 각 조회는 성공 여부, 예외 클래스·메시지, 돌려받은 변환의
     시각·이동·회전, 걸린 시간(`time.monotonic`)을 기록한다.
  4. 관측 점에 관측 시각 변환과 최신 변환을 각각 적용(직접 쿼터니언 계산과 `tf2_geometry_msgs.do_transform_point`
     둘 다)하고, frame_id만 바꾼 점과 함께 관측 시각 결과와의 거리를 잰다. 역변환으로 왕복 결과도 잰다.
  5. 10.4초 자료 조회(timeout 없음) → `threading.Timer(0.3)`로 발행 예약 후 timeout 2초 조회 → `Time()` 재조회.
  6. 모든 발행이 끝난 뒤 새 노드에 새 Buffer·listener를 붙여 정적(최대 3초)·동적(최대 2초) 관계 수신 여부.
  7. `obs_qos`에 BEST_EFFORT 발행자, RELIABLE·BEST_EFFORT 구독자 하나씩. 발행자의 구독자 수가 1 이상이 될 때까지
     기다리고 1초를 더 둔 뒤 0.05초 간격 20개 발행, 0.5초 뒤 각 구독자의 수신 개수, 발행자가 센 구독자 수,
     incompatible QoS 이벤트 수·정책 이름.
- 스크립트의 숫자(0.2, 0.1, 90°, 0.5 m/s, 9.8/10.0/10.1/10.2/10.4/10.5/9.0초, 1000초, timeout 0.5/1/2초,
  0.3초 지연, 20개, 대기 상한)는 입력값과 제한값이다. 결과 숫자는 미리 적지 않는다.
- 판정은 위 표의 예측과 실측 줄을 대조한다. 시각·거리 비교는 실측값을 그대로 쓰고, 대기·경과 시간은 실행마다
  달라지므로 "timeout 근처에서 실패했는가 / 지연 근처에서 성공했는가"만 본다.

## 해석 경계

- 순수 소프트웨어 실측이다. 실물 로봇·센서·시뮬레이터·위치 추정기는 없다. 지도–몸체 관계는 스크립트가
  정한 등속 이동을 직접 발행한 값이고, 정적 관계도 입력값이다. "tf2가 관계를 알아내지 않는다"는 것은
  공급 전후의 조회 실패·성공으로 보여 줄 뿐, 실제 보정 절차를 측정하지 않는다.
- 같은 프로세스·같은 컨테이너 안 통신이다. 여러 컴퓨터, 실제 네트워크 지연, 시계 동기화 오차는 측정하지 않는다.
  관측과 변환은 같은 시계 기준(스크립트가 정한 시각)을 쓴다.
- Python(rclpy, tf2_ros_py) 동작만 본다. rclcpp·C++ 버퍼는 측정하지 않았다.
- QoS 항목은 신뢰성(reliability) 비호환 한 가지 조합만 본다.

## 시행착오

- 하네스(`--try`)는 plan.md가 없으면 실행을 거부하므로, 이 계획을 시험 실행 전에 썼다.
- 설계 단계: 동적 변환을 `TransformBroadcaster` 생성 직후 바로 보내면 DDS 매칭 전에 메시지가 버려질 수 있다
  (`/tf`는 VOLATILE). 그래서 구독자가 그래프에 보일 때까지 기다리고 0.5초를 더 둔 뒤 발행하며, 그래도
  3초 안에 안 들어오면 한 번만 재발행하고 그 사실(`retried`)을 출력하도록 했다. 정적 변환은 TRANSIENT_LOCAL이라
  이 대기가 필요 없다고 보고 넣지 않았다.
- 시험 실행 1회차: 종료 코드 0이었지만 하네스는 stdout의 끝 8000자만 `results.json`에 남긴다. 버퍼 프레임
  YAML 원문, 조회마다 붙인 목표·출발 프레임과 긴 예외 문구 때문에 출력이 그보다 길어서, 앞부분
  (환경, 구독 목록, 관측 수신, broadcaster 없음·정적만 있을 때의 조회)이 잘려 나갔다. 질문 1·2의 근거가
  기록에서 빠지는 문제라 출력을 줄였다: 프레임 목록은 `프레임: [부모, 가장 오래된 시각, 최신 시각]`으로 요약,
  조회 줄은 `pair`(목표<-출발) 하나로 합치고 예외 문구는 앞 120자, 메모 필드 제거, 소수 6자리 반올림.
  측정 항목 자체는 바꾸지 않았다.
- 같은 실행에서 QoS 단계가 "구독자 수 2 이상"을 5초 동안 기다리다 시간만 쓰고 넘어갔다. 발행자의
  `get_subscription_count()`에 QoS가 맞지 않는 구독자는 잡히지 않았기 때문이다. 대기 조건을 1 이상으로
  고치고, 발행자가 센 구독자 수(`graph_subscription_count`)는 측정값으로 그대로 출력한다.
- 시험 실행 2·3회차: 종료 코드 0, 출력 전체가 `results.json`에 남았고 한 번 실행이 60초보다 훨씬 짧게 끝났다.
  동적 변환 재발행(`retried`)은 일어나지 않았다. 시험 실행의 수치는 이 문서에 옮기지 않는다.
  실측값의 근거는 하네스 본 실행의 `results.json`뿐이다.
