# 실험 계획: ROS 2 토픽으로 흘려 보낸 장치 속도가 입력 경계에서 어떻게 m/s가 되는가

## 질문

이 글(`research.md`)은 `Δx = v × Δt`의 산술만 Python 3.12.3으로 검산했고 "ROS 노드, 시뮬레이터, 물리 엔진,
실제 하드웨어를 실행하지 않았다"고 적었다. 또 실제 어댑터는 "격리된 ROS 노드로 변환 전후의 토픽 값, timestamp,
frame, 실제 `Δt`를 봐야 한다"고 했다. 이 실험은 그 단계를 ROS 2 Jazzy 노드로 실제로 실행한다.

1. `geometry_msgs/Twist`·`Vector3`·`TwistStamped`·`nav_msgs/Odometry`에 단위를 운반하는 필드가 정말 없는가?
   `250`과 `0.25`는 둘 다 같은 길이로 직렬화되고 비트 그대로 전달되는가? rclpy가 막는 것은 무엇(자료형)이고
   막지 않는 것은 무엇(단위)인가?
2. 장치 원시값(`TwistStamped`, 장치 단위 숫자)을 받아 `source_unit` 파라미터로 m/s로 정규화하는 어댑터 노드와,
   그 출력의 header stamp로 `Δx = vΔt`를 적분하는 오도메트리 노드를 거치면 글의 표 A·B·D·E 거리가 나오는가?
   거리는 오도메트리 노드가 보낸 `/tf`(`odom_<구현> → base_<구현>`)를 tf2 버퍼에서 조회해 읽는다.
3. 일부러 틀린 구현 네 가지가 글이 적은 실패 신호를 내는가?
   - `no_convert`(변환 누락) → A가 100 m, 배율 1000
   - `always_div`(모든 입력에 `/1000`) → B가 0.0001 m
   - `silent_default`(단위 없음·미지원을 m/s로 간주) → C가 오류 없이 숫자를 냄
   - `dt_ms`(정규화는 맞고 오도메트리가 stamp 차이를 ms 숫자로 쓴 경우) → A와 B가 함께 틀림
4. 테스트 묶음 "A만", "A+B", "A+B+C", "전체"가 각각 어떤 틀린 구현을 잡는가?
   (글: A 하나만으로는 `/1000` 누락만 잡고 무조건 `/1000`인 구현은 통과시킨다)
5. 같은 계산을 실제 시계(20 Hz 제어 주기, `time.sleep` 스케줄)로 돌리면 `Δt`가 정확히 0.4 s가 아니다.
   header stamp 기준 거리와 수신 시각 기준 거리는 0.1 m에서 얼마나 벗어나는가? 글이 경고한 대로
   `math.isclose`의 산술 허용오차를 이 값에 그대로 쓰면 어떻게 되는가? 그래도 틀린 구현의 배율은 유지되는가?

## 글이 주장한 예측값

글의 수치는 설명용 입력의 산술이다. 실측이 아니라 실행 전 예측·주장으로 둔다. 스크립트는 이 값을
"글의 주장(oracle)"으로만 갖고, 측정값과 일치 여부(bool)를 출력한다. 측정값 자체는 실행 중에 계산된다.

| 사례 | 입력 | 유지 시간 | 글의 예상 거리 | 글의 실패 신호 |
|---|---|---|---|---|
| A | `250 mm/s` | 0.4 s | 0.1 m | 변환 누락이면 100 m (1000배, 차이 99.9 m) |
| B | `0.25 m/s` | 0.4 s | 0.1 m | `/1000` 중복이면 0.0001 m |
| C | 단위 없음 / 미지원 단위 | — | 숫자 대신 명시적 오류 | 숫자를 조용히 반환하면 실패 |
| D | `500 mm/s` | 0.2 s | 0.1 m | 변환 누락이면 100 m |
| E | `80 cm/s` | 0.5 s | 0.4 m | 변환 누락이면 40 m (100배) |

그 밖의 주장:

- Vector3에는 `float64 x, y, z`만 있고 단위 필드가 없다. 전달 성공만으로 의도한 단위를 알 수 없다.
- A만 시험하면 `no_convert`는 잡히고 `always_div`는 통과한다. A+B를 함께 넣어야 `always_div`도 잡힌다.
- A와 B가 모두 틀리면 변환 위치뿐 아니라 시간 단위·거리 계산을 의심한다.
- `math.isclose` 허용오차는 부동소수점 비교용이며 실물(실시간) 허용 오차로 쓰면 안 된다.
- Odometry의 pose와 twist는 서로 다른 좌표계(`header.frame_id`, `child_frame_id`)에 표현된다.

실행 전 가설(측정이 아니다):

- 합성 stamp(정확히 50 ms 간격)에서는 올바른 구현이 A·B·D·E를 부동소수점 반올림 수준 오차로 통과할 것이다.
- 실제 시계에서는 sleep 지연 때문에 stamp 기준 `Δt`가 0.4 s보다 약간 길고, 거리도 0.1 m보다 약간 클 것이다.
  `rel_tol=1e-9`의 `isclose`는 거의 매번 실패할 것이다. 그래도 모든 구현이 같은 원시 stamp를 받으므로
  `no_convert`/`correct` 거리 비는 실시간에서도 1000 근처일 것이다.
- 수신 시각 기준 적분은 전달 지연의 흔들림이 더해져 stamp 기준보다 0.1 m에서 더 벗어날 수 있다.

## 측정 방법

- 환경: 하네스의 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB). `rclpy`, `tf2_ros`, `std_msgs`,
  `geometry_msgs`, `nav_msgs`만 쓴다. 패키지 버전은 `package.xml`, rmw 이름은 실행 중에 읽는다.
- 노드(한 프로세스, 백그라운드 스레드의 `SingleThreadedExecutor`):
  - `device`: `/device/raw_twist`(`TwistStamped`)에 장치 단위 숫자를 그대로 넣어 보낸다. 제어 주기 50 ms로
    유지 시간 동안 같은 값을 보내고, 마지막에 0 속도 정지 명령을 보낸다.
  - `adapter_<구현>` 4개(`correct`, `no_convert`, `always_div`, `silent_default`): 파라미터 `source_unit`으로
    값을 m/s로 바꿔 `/<구현>/cmd_vel`(`TwistStamped`, stamp 유지)로 보낸다. `correct`는 SI 접두어 지수
    (centi −2, milli −3)로 나누며, 단위가 없거나 표에 없으면 `ValueError`를 내고 숫자 대신 `/unit_error`
    (`std_msgs/String`)를 보낸다.
  - `odom_<구현>` 5개: 위 4개 + `dt_ms`(`correct` 출력을 받아 stamp 차이를 ms 숫자로 씀). 직전 명령 속도를
    다음 stamp까지 유지한다고 보고 적분한다(`x += v_prev × (t_k − t_{k−1})`). 수신 시각 기준 적분도 함께 한다.
    `nav_msgs/Odometry`와 `/tf`를 보낸다.
  - `checker`: `TransformListener`가 채운 `tf2_ros.Buffer`에서 정지 stamp의 `odom_<구현> → base_<구현>`
    변환을 조회해 거리를 읽고, `/odom_<구현>` 메시지의 `pose.pose.position.x`와도 대조한다.
- 진행: 사례마다 어댑터 파라미터를 바꾸고, 모든 어댑터·오도메트리 콜백이 보낸 메시지를 다 처리할 때까지
  `threading.Condition`으로 기다린다(락스텝). 두 모드로 돈다.
  - 합성 stamp 모드: stamp를 정확한 50 ms 정수 ns 간격으로 넣고 기다리지 않고 보낸다(논리 검사).
  - 실제 시계 모드: `node.get_clock().now()` stamp, 절대 시각 스케줄 sleep으로 50 ms마다 보낸다. 6개 사례 1회씩,
    그리고 A를 10회 반복해 실제 `Δt`와 거리 편차의 분포를 잰다.
- 판독값:
  - `schema`: 각 메시지의 필드 이름·자료형, 이름에 `unit`이 든 필드 수.
  - `wire`: `serialize_message` 바이트 길이, 왕복 후 비트 일치. 그리고 `Vector3(x=정수)`, `Vector3(x="250 mm/s")`,
    `Vector3(x=실수)`를 기본 설정과 `check_fields=True`로 각각 만들고 직렬화할 때 어느 단계에서 어떻게 거부되는지
    (생성 시 예외 이름, 또는 직렬화 시 자식 프로세스의 종료 코드와 stderr 마지막 줄). 이 탐침은 잘못된 자료형이
    C 직렬화기를 중단시킬 수 있어 `subprocess`로 자식 프로세스에서 돌린다. 환경 변수 `ROS_PYTHON_CHECK_FIELDS` 값도 적는다.
  - `synthetic.raw_bits_equal`: `/device/raw_twist`로 받은 값이 보낸 값과 비트 단위로 같은지.
  - `synthetic`: 구현×사례별 TF 거리, Odometry 거리와의 차이, 글 예상값과의 비, `isclose` 판정, 오류 메시지 수.
  - `suites`: 테스트 묶음별로 각 구현이 잡혔는지(사례 하나라도 실패) 여부.
  - `realtime`: 사례별 실제 stamp `Δt`, stamp 기준·수신 기준 거리, `isclose` 판정, `no_convert/correct` 거리 비.
  - `realtime_repeat`: A 10회의 `Δt` 초과량, 거리 편차의 최소·중앙·최대.
- 스크립트의 숫자는 모두 입력·정의·제한값이다(사례 입력값, 유지 시간, 제어 주기, SI 접두어 지수, `always_div`의
  1000, 대기 상한, 반복 횟수, 그리고 비교용으로만 쓰는 글의 주장값). 출력은 `kind` 필드가 있는 JSON 줄이다.

## 판정 기준

- 질문 1: `schema.unit_fields`가 0이고 `wire`의 두 길이가 같으며 비트 일치가 `true`면 글의 주장 성립.
  `wire.default`/`wire.check_fields`는 rclpy가 자료형을 언제(생성 또는 직렬화) 어떻게 거부하는지를 그대로 읽는다.
  단위는 어느 경우에도 검사 대상이 아니다.
- 질문 2: `synthetic`의 `correct` 행에서 A·B·D·E가 `isclose=true`, C 두 사례가 거리 없음 + 오류 메시지.
- 질문 3: 틀린 구현의 측정 거리가 글의 실패 신호와 `isclose`로 일치하는지(`matches_article_failure`) 본다.
- 질문 4: `suites`에서 "A만"이 `always_div`를 놓치고 "A+B"가 잡는지 본다.
- 질문 5: `realtime`의 `isclose`, `dt_s`, 편차를 그대로 읽는다. 예측과 다르면 결과를 그대로 보고하고
  글의 설명을 결과에 맞춘다. `timeouts`가 0이 아니면 그 사실을 먼저 보고한다.

## 한계

- 실제 장치 드라이버, 시뮬레이터, 물리 엔진, 실물 로봇이 아니다. 1차원 일정 속도 명령을 직전값 유지로 적분했을 뿐이며
  가감속, 회전, 미끄럼, 엔코더 분해능, 누적 오도메트리 오차는 없다.
- 노드는 한 프로세스·한 executor에서 돌았다. 프로세스 간·호스트 간 전달 지연, 다른 rmw, 부하가 있는 시스템의
  타이밍은 재지 않았다. 실시간 결과는 1 CPU 컨테이너의 Python `sleep` 스케줄에 한정된다.
- `/clock`과 `use_sim_time`은 쓰지 않았다. 합성 stamp는 header에 직접 넣은 값이다.
- 실물 장치를 움직이는 단계가 없으므로 정지 절차가 필요한 동작은 없다.

## 시행착오

- 하네스(`--try`)는 plan.md가 없으면 실행을 거부하므로 이 계획을 시험 실행 전에 썼다.
- 설계 단계: 같은 저장소의 다른 실험 기록에서 가져온 점. `/tf`는 VOLATILE이라 구독 매칭 전 첫 메시지가 버려질 수 있어
  모든 구독자가 그래프에 보인 뒤 시작한다. 바쁜 대기 대신 `threading.Condition`으로 기다린다. 종료는
  `rclpy.try_shutdown()` → 스핀 스레드 join → executor 종료 → 노드 파괴 순서로 하고 `ExternalShutdownException`만 잡는다.
- 설계 단계: tf2에서 stamp 0은 "가장 최근 변환"을 뜻하므로 합성 stamp는 1000 s부터 시작하고, 사례마다 10 s씩 띄워
  같은 child frame의 stamp가 줄어들지 않게 했다. 실제 시계 모드는 그 뒤(현재 시각)라 단조 증가한다.
- 설계 단계: 단위 없음(C) 사례에서 `correct` 어댑터는 숫자를 내보내지 않으므로 그 하류 오도메트리(`correct`, `dt_ms`)는
  메시지를 받지 않는다. TF 조회를 기다리면 시간 초과가 나므로, 사례마다 받은 명령 수가 0이면 조회하지 않고
  "명령 없음 + 오류 메시지 수"로 기록한다.
- 설계 단계: 수신 시각 기준 적분은 합성 모드에서는 메시지를 몰아 보내 의미가 없으므로 실제 시계 모드에서만 출력한다.
- 시험 실행 1회차(`--try`): 종료 코드 0, 대기 시간 초과 0, stderr 비어 있음, stdout은 8000자 한도 안이었다.
  예상과 달리 `Vector3(x="250 mm/s")`와 `Vector3(x=250)`이 생성 단계에서 **받아들여졌다**. Jazzy의 생성 메시지 클래스는
  필드 자료형 검사를 `ROS_PYTHON_CHECK_FIELDS` 환경 변수(이 컨테이너에서는 미설정)나 생성자 인자 `check_fields`로 켜는
  것으로 보였다. 그래서 측정을 넓혔다: 기본 설정과 `check_fields=True` 두 경우에, 생성 다음 직렬화까지 해 본다.
- 시험 실행 2회차: 기본 설정에서 문자열을 넣은 메시지를 `serialize_message`하자 C 확장의 `Assertion PyFloat_Check(field)`
  실패로 프로세스 전체가 중단됐다(하네스 기록 종료 코드 139, stdout은 첫 `env` 줄뿐). Python 예외로 잡을 수 없는
  중단이라 이 탐침만 `subprocess` 자식 프로세스로 옮기고, 자식의 종료 코드와 stderr 마지막 줄을 결과로 남기게 했다.
  다른 측정 코드는 바꾸지 않았다.
- 시험 실행 3~4회차(자식 프로세스 탐침): 두 번 모두 종료 코드 0, 대기 시간 초과 0, stderr 비어 있음이었다. 컨테이너 기동을
  포함한 한 번 실행이 60초보다 훨씬 짧았다. 자료형 거부 결과는 기본 설정에서는 직렬화 단계의 프로세스 중단,
  `check_fields=True`에서는 생성 단계의 `AssertionError`였다. 어느 쪽도 단위는 검사하지 않는다.
- 시험 실행에서 본 판독 주의점(수치는 옮기지 않음): 실제 시계 모드에서는 올바른 구현도 글의 산술 허용오차(`isclose`)를
  매번 통과하지 못했다. stamp 기준 `Δt`가 sleep 지연만큼 0.4 s보다 길었기 때문이다. 반면 모든 구현이 같은 원시 stamp를
  받으므로 `no_convert`/`correct` 거리 비는 실시간에서도 그대로 유지됐다. 수신 시각 기준 적분은 stamp 기준보다
  0.1 m에서 더 벗어났다. 본문은 이 셋을 구분해 써야 한다(배율 진단은 실시간에서도 유효, 허용 오차는 별도로 정해야 함).
- `suites` 판독: `silent_default`는 A·B만으로는 잡히지 않고 C를 넣어야 잡혔다. `dt_ms`는 A와 B를 함께 실패시켜
  글의 "둘 다 틀리면 시간 단위를 의심한다"에 맞는 모양을 보였다. `always_div`는 C 사례에서도 숫자를 냈다.
- 시험 실행의 수치는 이 문서에 옮기지 않는다. 본문의 실측 숫자는 하네스 정식 실행의 `results.json`만 근거로 한다.
