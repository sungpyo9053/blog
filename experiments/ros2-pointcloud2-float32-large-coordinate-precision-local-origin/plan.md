# 실험 계획: 큰 지도 좌표를 PointCloud2 FLOAT32 필드에 넣으면 몇 m 단위로 저장되나

## 질문

GPS·대형 지도 좌표(원점에서 약 4,000,000 m)를 ROS 2 Jazzy rclpy의
`sensor_msgs_py.point_cloud2.create_cloud`로 FLOAT32 x·y·z 필드에 넣은 뒤 직렬화·발행·수신하고
`read_points`로 다시 읽으면,

1. 값은 몇 m 간격으로 저장되고 오차는 최대 얼마인가?
2. 5 cm 떨어진 두 점이 같은 좌표가 되는가?
3. 원점을 float64 단계에서 먼저 빼는 경우와 float32로 저장한 뒤 빼는 경우의 오차는 어떻게 다른가?
4. 변환은 가장 가까운 값으로 반올림인가, 0 쪽으로 버림인가? 정확한 중간값은 어디로 가는가?
5. 입력 경로(파이썬 튜플 목록, NumPy 비구조화 float64 배열, NumPy 구조화 float64 배열,
   `create_cloud_xyz32`)에 따라 경고나 실패가 있는가?

## research.md 기준 예측값

research.md의 손계산 표(verification.json 산술 검산)와 그 규칙(크기 x가 [2^k, 2^(k+1))이면
간격 2^k ÷ 2^23)에서 나온 값이다. 실측이 아니다.

| 항목 | 예측 |
| --- | --- |
| 400만 m대(k=21) 간격 | 0.25 m |
| 최대 반올림 오차(가장 가까운 값 전제) | 0.125 m |
| [4000000, 4000001) 안의 float32 값 개수 | 4개 |
| 4000000.3 저장값 / 오차 | 4000000.25 / 약 0.05 m |
| 4000000.05와 4000000.10 저장 후 차이 | 0 (둘 다 4000000.0) |
| 3,000,000 m 간격 | 0.25 m (같은 구간) |
| 2^22 = 4,194,304 m 초과, 5,000,000 m 간격 | 0.5 m |
| float64에서 원점 3,999,900 m 먼저 빼기 | 100.3 m, 그 크기(k=6)의 간격 7.62939453125e-06 m(약 7.6 μm) |
| float32 저장 뒤 빼기 | 100.25 m (오차 약 0.05 m 유지) |
| 간격이 줄어드는 배수 | 32768배 |
| FLOAT64 필드의 xyz 크기 | 점당 12바이트 → 24바이트 |
| 반올림 방식, 정확한 중간값 처리 | research.md는 단정하지 않음 (구별용 입력을 이 실험에서 추가) |
| NumPy 구조화 float64 배열 + FLOAT32 필드 | 코드 읽기 기준 AssertionError (실행 미확인) |

규칙에서 덧붙여 예상한 값(같은 공식을 적용한 것):

- 1 mm 간격 1000점 스윕 [4000000.000, 4000000.999]: 0.875 m 이상은 4000001.0으로 올라가므로
  저장값 종류는 4 + 1 = 5개, 저장값 사이 간격 0.25 m, 최대 오차 0.125 m.
- 같은 스윕을 5,000,000 m에서 하면 종류 3개(5000000.0, .5, 5000001.0), 간격 0.5 m.
- 5,000,000 m대 점에서 원점 3,999,900 m를 빼면 남는 크기가 약 1,000,100 m라
  [2^19, 2^20) 구간 → 간격 0.0625 m. 원점이 데이터에서 멀면 원점 이동 효과가 줄어든다.
- 4194303.9처럼 2^22 바로 아래 값은 4194304.0으로 올라가 다음 구간 경계에 저장될 수 있다.

## 무엇을 어떻게 재나

환경: 하네스가 `ros:jazzy-ros-base` 컨테이너에서 네트워크 없이 실행한다. rclpy, sensor_msgs,
sensor_msgs_py, std_msgs, NumPy(이미지 기본)만 쓴다. 한 번 실행은 수 초 안에 끝난다.

기준값 계산: 스크립트가 실행 중 `fractions.Fraction`으로 입력 float64의 정확한 값을 잡고,
구간 k와 간격 2^(k−23)을 구한 뒤 "가장 가까운 격자점(중간값은 짝수 쪽)"과 "0 쪽 버림" 두 기준을
계산한다. 저장값과 오차는 모두 `read_points`로 실제로 다시 읽은 값에서 계산한다. 결과 숫자는
코드에 적지 않았다. 코드의 숫자는 입력 좌표, 원점, 스윕 간격, 대기 시간뿐이다.

출력(JSON 줄, `kind`별):

1. `environment`: RMW, NumPy·Python 버전, `finfo.nmant`, PointField 상수, sensor_msgs_py의 FLOAT32 dtype.
2. `cloud_layout`: FLOAT32 클라우드의 point_step·data 길이, CDR 직렬화 길이, 직렬화 왕복 뒤 바이트 동일 여부,
   read_points가 돌려준 x·y·z dtype.
3. `case` (11개 입력): 입력, 저장값, 오차, 입력 크기의 구간 k와 그 구간 간격(`band_spacing_m`),
   저장값 기준 `np.spacing`, 저장값 아래·위 이웃 float32 값까지 거리, 반올림/버림 기준 일치 여부.
   입력에는 반올림과 버림이 갈리는 4000000.2, 정확한 중간값 4000000.125·4000000.375, 구간 경계 양쪽
   4194303.9·4194304.3을 넣었다.
4. `rounding_rule`: 11개 중 각 기준과 일치한 개수.
5. `pair_5cm`: 4000000.05와 4000000.10의 저장값과 저장 후 차이.
6. `sweep_1m`: 1 mm 간격 1000점을 4,000,000 m와 5,000,000 m에서 그대로 넣은 경우와 float64에서 원점을
   먼저 뺀 경우. 저장값 종류 수, 저장값 사이 간격, 최대·평균 오차(원점을 다시 더해 정확한 입력과 비교).
7. `origin_order`: 4개 입력에 대해 float32 저장 뒤 빼기와 float64에서 먼저 빼기의 결과와 오차.
8. `float64_fields`: 같은 입력을 FLOAT64 필드로 넣은 point_step, data 길이, 직렬화 길이, 최대 오차.
9. `input_path`: 4가지 입력 경로의 성공 여부, 경고 개수·종류, 예외 이름·메시지, 저장값.
10. `pubsub`: 한 노드 안의 publisher/subscriber(rmw_fastrtps_cpp, loopback)로 원좌표 클라우드와 원점을 뺀
    클라우드를 보내고 받은 바이트가 보낸 바이트와 같은지, 받은 값과 오차.

실패 판정: 실행이 0이 아닌 코드로 끝나거나, `pubsub`이 15초 안에 받지 못하면(`received=false`로 기록)
해당 부분은 실패로 본다. 실측이 예측과 다르면 예측에 맞추지 않고 그대로 보고한다.

한계: 숫자 표현(float32 저장)만 잰다. GPS·라이다 측정 오차, 투영 정확도, RViz 렌더링, tf2 내부 정밀도는
재지 않는다. pub/sub은 같은 프로세스·같은 노드 안 전달이며 다른 프로세스나 다른 컴퓨터 간 전달은 아니다
(전달 경로는 바이트를 그대로 옮기므로 값 변화는 `create_cloud`에서 생긴다는 점을 확인하는 용도).
`waited_s`는 전달 속도 측정이 아니다. 실물 로봇·시뮬레이터는 쓰지 않는다.

## 시행착오 (시험 실행 `--try`에서 실제로 겪은 것)

1. 첫 시험 실행은 성공(exit 0)했지만 출력이 길어서 하네스가 남기는 stdout 끝 8000자 안에 다 들어가지
   않았다. results.json에서 `environment`, `cloud_layout`과 첫 `case` 줄이 잘려 나갔다. 키 이름을 줄이고
   중복 필드(케이스 이름, 저장값/간격 비율)를 빼서 두 번째 시험 실행에서 약 6.8천 자로 줄였고, 모든 줄이 남았다.
2. 첫 실행 출력에서 4194303.9의 "공식 간격"(입력 크기 기준 0.25 m)과 `np.spacing`(저장값 4194304.0 기준
   0.5 m)이 달라 보였다. 계산 오류가 아니라 저장값이 다음 구간 경계로 올라간 결과였다(아래 이웃까지는
   0.25 m, 위 이웃까지는 0.5 m). 원래 필드 이름 `spacing_formula_m`이 저장값의 간격처럼 읽혀서
   `band_spacing_m`(입력 크기가 속한 구간의 간격)으로 바꾸고, 아래·위 이웃까지 거리 필드도
   `gap_below_m`, `gap_above_m`으로 이름을 바꿨다. 측정 방법 자체는 바꾸지 않았다.
