# 실험 계획: rclpy `now().nanoseconds`를 float 초로 먼저 바꿔 빼면 dt가 얼마나 어긋나는가

## 질문

ROS 2 Jazzy rclpy 노드에서 `self.get_clock().now().nanoseconds`를 시각마다 `/ 1e9`로 float 초로
바꾼 뒤 두 값을 빼서 dt를 구하면(float 선변환), 정수 나노초로 먼저 빼고 마지막에 `/ 1e9`하는
방식(정수 선감산)과 비교해 dt가 실제로 얼마나, 어떤 모양으로 어긋나는가? 같은 간격을
0 근처 시각(시뮬레이션 시계 규모)에서 계산하면 그 차이가 사라지는가?

## research.md 기준 예측값 (실행 전 선언, 실측 아님)

- 2026년 시스템 시각(약 1.79×10⁹초) 근처 float 간격은 2⁻²²초 = 2.384185791015625e-07초다.
  float 선변환 dt는 모두 이 간격의 정수배가 된다.
- 정확히 1 ms(1,000,000 ns)를 float 선변환하면 시작 시각에 따라 4194·4195·4196 × 2⁻²²초,
  즉 0.0009999275207519531 / 0.0010001659393310547 / 0.0010004043579101562초 중 하나가 된다.
  `/ 10**9`(단일 반올림)는 4194·4195배 두 값만 나온다. 정수 선감산은 항상 0.001이다.
- 정확히 1 µs(1000 ns)는 3·4·5 × 2⁻²²초(7.152557373046875e-07 / 9.5367431640625e-07 /
  1.1920928955078125e-06) 중 하나가 된다. 정수 선감산은 항상 1e-06이다.
- |dt_float − dt_int|는 대략 0.5 µs 이하다. 상대 오차는 1 ms 주기에서 최대 약 0.04%,
  1 µs 구간에서 최대 약 28%다.
- 오차는 누적되지 않는다. float 선변환 dt의 합은 망원 합이라 전체 경과 시간과 거의 같다.
- 125초 근처(시뮬레이션 규모) 간격은 2⁻⁴⁶초 = 1.4210854715202004e-14초로, 같은 계산의
  오차가 사실상 드러나지 않는다.
- 0.5 m/s 등속 차분 속도는 float 선변환 dt로 나누면 주기마다 흔들린다(research.md의 설명용
  산술 예: 약 0.49980~0.50004 m/s, 시작 시각에 따라 다름).
- rclpy Jazzy `Time`·`Duration`에 `seconds` 속성이 없고, `Time − Time`은 정수 nanoseconds를
  가진 `Duration`이다.

## 무엇을 어떻게 재는가

환경: 하네스의 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB). rclpy만 사용한다.
`use_sim_time`은 기본값(false)이므로 노드 시계는 ROS_TIME 형식이지만 시스템 시각을 읽는다.
실행 중 측정한 값만 출력하며, 결과 숫자를 코드에 미리 적지 않는다. 출력은 `kind` 필드를 가진
JSON 줄이다.

1. `api_surface`: 노드 시계의 clock type, `ros_time_is_active`, `use_sim_time`,
   `now().nanoseconds`의 타입과 2⁵³ 초과 여부, `Time`/`Duration`의 `seconds` 속성 유무,
   `Time − Time` 결과 타입을 실행 중 확인한다.
2. 1 ms 타이머 콜백(`create_timer(0.001)`)에서 `now().nanoseconds`를 2000개 기록한다.
   이어서 콜백 없이 `now()`를 연속 20000번 호출해 µs 규모 간격 시각을 기록한다.
3. `interval_compare`: 각 시각 열에 대해 이웃 두 시각으로
   - dt_float = `t[i+1]/1e9 - t[i]/1e9` (float 선변환)
   - dt_int = `(t[i+1]-t[i])/1e9` (정수 선감산)
   을 계산하고 다음을 출력한다.
   - 시작 시각의 `math.ulp`와 그 log2
   - dt_float가 모두 그 ulp의 정수배인지(`fractions.Fraction`으로 정확히 판정)
   - 서로 다른 dt 값 개수
   - |dt_float − dt_int|의 최대·평균(ns), 상대 오차 최대·평균
   - dt 합과 전체 경과 시간(누적 여부)
4. 같은 실측 정수 간격을 첫 시각이 125초가 되도록 옮겨(125×10⁹ ns 더하기) 같은 비교를 한다.
   실제 /clock 시뮬레이션 실행이 아니라 "값의 크기만 시뮬레이션 규모로 바꾼" 계산임을 글에 밝힌다.
5. `fixed_interval_from_real_starts`: 실측 시각 22000개 각각을 시작점으로 정확히 1,000,000 ns와
   1000 ns를 더해 `/1e9` 선변환 결과 값의 분포(히스토그램)와 2⁻²² 배수, `/10**9` 결과 분포,
   `/1e9`와 `/10**9`가 다른 시작 시각 개수를 출력한다. 타이머 지터와 분리해 "같은 간격이 시작
   시각에 따라 몇 가지 값이 되는가"를 실제 `now()` 하위 비트로 확인하는 단계다.
6. `finite_difference_velocity`: 0.5 m/s 등속 물체의 위치 변화는 정수 나노초 간격으로 정확히
   두고, dt만 두 방식으로 나눠 차분 속도의 최소·최대·표준편차를 출력한다.

판정:
- 정상(예측과 일치): 시스템 시각 계열 dt_float가 모두 2⁻²²초의 정수배이고 서로 다른 값 개수가
  dt_int보다 적다. 125초 계열은 오차가 ns 이하 규모다. 1 ms 고정 간격은 4194~4196배 안에 있다.
- 실패: dt_float가 2⁻²²의 정수배가 아니면 시각 규모(epoch) 가정이 틀린 것이다(예: use_sim_time
  활성). 실행 실패, 샘플 부족(30초 안에 2000개 미달)도 실패로 본다.

한계:
- 타이머 콜백 지연(지터)은 float 양자화와 별개다. 1 CPU 제한 컨테이너라 타이머 간격 자체가
  1 ms에서 벗어날 수 있으며, 이 값은 양자화 결과로 해석하지 않는다.
- 실제 시뮬레이터 /clock, 실물 로봇·하드웨어는 사용하지 않는다. 제어 성능 영향은 재지 않는다.
- rclcpp는 실행하지 않는다.

## 시행착오 (시험 실행에서 실제로 겪은 점)

- 첫 시험 실행은 성공(종료 코드 0)했지만 `clock_type`이 `"1"`처럼 숫자로 출력됐다. Python 3.12에서
  IntEnum의 `str()`이 이름이 아니라 정수 문자열을 돌려주기 때문이다. enum의 `.name`을 출력하도록
  바꾸고, 시계가 실제로 시스템 시각을 읽는지 판단할 수 있게 `ros_time_is_active`를 추가했다.
  두 번째 시험 실행에서 `ROS_TIME`과 `ros_time_is_active=false`가 출력되는 것을 확인했다.
- 첫 시험 실행에서는 1 CPU 제한 때문에 타이머 간격이 1 ms보다 크게 흔들린 콜백이 있었다(두 번째
  실행은 덜 흔들림). 양자화 판정은 타이머 지터와 무관하게 하도록 5번 단계(실측 시작 시각 + 정확한
  고정 간격)를 처음부터 넣어 두었으므로 코드는 바꾸지 않았다. 실행마다 타이머 지터 값이 다를 수
  있다는 점만 한계로 남긴다.
