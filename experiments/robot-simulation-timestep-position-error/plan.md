# 실험 계획: 시간 간격을 줄이면 위치 계산이 달라진다는 글의 계산이 ROS 2 TF 경로에서도 그대로 나오는가

## 질문

글은 초기 위치 0 m, 초기 속도 0 m/s, 일정 가속도 2 m/s², 전체 시간 1초인 1차원 예제를 Python 산술로만 검산했다.
같은 갱신식을 ROS 2 시뮬레이터 노드가 단계마다 TF(`world → <시나리오 프레임>`)로 방송하고, 다른 노드가
`tf2_ros.Buffer`로 t=1.0 s의 위치를 조회하면 다음이 성립하는가?

1. 전진 오일러(위치 먼저, 속도 나중)에서 1초 뒤 위치가 Δt에 따라 달라지고, 최종 속도는 모두 같으며,
   절대 오차가 `aTΔt/2`(이 예제에서는 Δt와 같은 수치)인가? Δt를 절반으로 줄일 때마다 오차도 절반이 되는
   관계가 Δt=2⁻¹부터 2⁻⁸까지(ROS TF 경로), 2⁻¹⁶까지(ROS 없는 같은 반복문) 계속되는가?
2. 갱신 순서를 뒤집은 준암시적 오일러는 기준값보다 크게, 구간 안 일정 가속도를 반영한
   `x+vΔt+½aΔt²`는 기준값과 같게 나오는가?
3. 글이 경고만 한 경우: `int(1.0/dt)` 단계 수를 쓰고 `T/Δt`가 정수가 아니거나 Δt가 2진수로 정확히 표현되지 않을 때
   (Δt=0.3, 0.1, 1/3) 마지막 시각과 위치는 어떻게 되는가? 시각을 `t += dt`로 누적해 TF stamp를 만들면
   t=1.0 s 조회가 성공하는가? 부동소수점 오차는 글의 assertion 허용치 1e-12 안에 드는가?
4. 글의 "프레임률을 높였다는 말만으로 적분 오차가 줄었다고 판단할 수 없다": TF 방송 주기와 적분 Δt를 분리하면
   t=1.0 s 위치는 어느 쪽을 따르는가? 방송 사이 시각(t=0.75 s)을 조회하면 tf2는 무엇을 돌려주는가?
5. Δt를 줄일 때 계산 시간은 어떻게 늘어나는가(글이 인용한 MuJoCo 문서의 "계산이 느려진다")?

## 글이 주장한 예측값 (research.md)

| 항목 | 입력 | 글의 주장·예측 |
| --- | --- | --- |
| 연속시간 기준 | a=2, T=1 | x(1)=1 m, v(1)=2 m/s |
| 전진 오일러 | Δt=0.5 / 0.25 / 0.125 | x=0.5 / 0.75 / 0.875 m, v=2 m/s, 오차 0.5 / 0.25 / 0.125 m |
| 전진 오일러 일반식 | T/Δt 정수 | `x_E=(a/2)(T²−TΔt)`, 오차 `aTΔt/2`. Δt 절반 → 오차 절반(1차) |
| 전진 오일러 단계표 | Δt=0.25 | t=0.25, 0.5, 0.75, 1.0에서 x=0, 0.125, 0.375, 0.75 m |
| 준암시적 오일러 | Δt=0.5 / 0.25 | x=1.5 / 1.25 m (기준보다 크다). 0.125는 글에 수치 없음 |
| 일정 가속도 운동학식 | Δt=0.5 / 0.25 | 둘 다 x=1 m |
| 비정수 단계 | `int(1.0/dt)`, T/Δt 비정수 | "마지막 시간을 정확히 맞추지 못할 수 있다"(수치 없음) |
| 부동소수점 | 글의 assertion | `|x − (1−dt)| ≤ 1e-12`, `|v − 2| ≤ 1e-12` (Δt=0.5, 0.25, 0.125에서) |
| 방송 주기 vs 적분 Δt | — | 프레임·제어·센서 주기와 적분 timestep은 다른 설정일 수 있다(수치 없음) |
| 계산 비용 | — | timestep 감소는 계산을 느리게 한다(MuJoCo 문서 인용, 수치 없음) |

가설(실행 전): 2의 거듭제곱 Δt는 2진수로 정확하므로 float64 결과가 분수 계산과 똑같을 것이다. Δt=0.1은 그렇지 않아
누적 시각이 1.0에 못 미치거나 넘을 수 있고, 그러면 stamp가 1 ns 어긋나 t=1.0 s 조회가 실패할 수 있다.
실제로 그런지는 실측으로만 말한다.

## 측정 방법

- 환경: 하네스가 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB)에서 실행한다. 사용 패키지는
  `rclpy`, `tf2_ros`, `std_msgs`, `geometry_msgs`뿐이다. rmw 이름은 실행 중에 읽는다.
- 노드 두 개를 `MultiThreadedExecutor`가 백그라운드 스레드에서 돌린다.
  - sim: 시나리오마다 (적분기, Δt, 단계 수, stamp 방식, 방송 간격)으로 상태를 갱신한다. 방송하는 단계마다
    `world → <시나리오>` TF(translation.x=x)와 `/sim_state`(Float64MultiArray [시나리오 번호, 단계, x, v])를 보낸다.
    관찰 노드가 그 단계 TF와 상태를 모두 받은 것을 확인한 뒤 다음 단계로 간다(락스텝, 메시지 유실 방지).
  - observer: `TransformListener`가 채운 `tf2_ros.Buffer`에서 시나리오가 끝난 뒤 t=1.0 s, t=0.75 s(일부),
    최신(`Time()`)을 조회한다. 실패하면 예외 이름을 기록한다. `/sim_state`로 받은 속도를 기록한다.
- 단계 수는 글의 코드처럼 `int(T/dt)`로 실행 중에 계산한다. stamp 방식은 둘이다.
  `count`: 단계 번호 × Δt를 나노초로 반올림. `accum`: `t += dt`로 누적한 float 초를 `Time(seconds=t)`로 변환.
- 기준값은 모두 실행 중에 `Fraction`으로 계산한다: 연속시간 기준 `x₀+v₀T+½aT²`, 글의 식 `(a/2)(T²−TΔt)`,
  같은 갱신식을 분수로 다시 돌린 결과(float 반올림 오차 분리용, 실제 float Δt의 정확한 2진 값과 의도한 Δt 둘 다).
- 시나리오(입력만 정한다):
  - `fe_k`: 전진 오일러, Δt=2⁻ᵏ (k=1..8), count stamp. Δt=0.25는 단계별 TF 조회로 글의 표와 대조.
    t=0 행은 `Time(nanoseconds=0)`으로 조회하는데, tf2는 시각 0을 "최신"으로 해석하므로 그 행의 `x_tf`는
    t=0 위치가 아니라 마지막 위치다(tf2 규약 확인용으로 그대로 남긴다).
  - `si_k`, `kin_k`: 준암시적 오일러와 운동학식, Δt=2⁻¹, 2⁻², 2⁻³.
  - `nd_*`: 전진 오일러, Δt=0.3(count), 0.1(count/accum), 1/3(count/accum).
  - `pub_*`: 전진 오일러 Δt=0.5 매 단계 방송, Δt=0.125를 4단계마다(0.5 s 간격) 방송, Δt=0.125 매 단계 방송.
    t=1.0 s와 t=0.75 s를 조회한다.
- 계산 비용: ROS 없이 같은 전진 오일러 반복문만 Δt=2⁻¹..2⁻¹⁶에서 `time.perf_counter`로 여러 번 재고 중앙값과
  1초 뒤 오차를 기록한다. 락스텝 ROS 시나리오의 벽시계 시간도 함께 기록한다(통신 포함, 참고용).
- 출력: JSON 줄 6개(`forward_convergence`, `integrators`, `nondividing`, `publish_rate`, `cpu_cost`, `summary`).
  하네스가 stdout 끝 8000자만 저장하므로 행은 열 이름 + 배열로 압축한다. 판정용 값은 반올림하지 않는다.

## 판정 기준

- 질문 1: `forward_convergence`의 `x_tf_at_1`이 글의 값과 같고, `minus_formula`가 0이며, `ratio`가 연속해서 2인지 본다.
  `v`가 모두 같은지 본다. 하나라도 다르면 결과대로 쓴다.
- 질문 2: `integrators`의 si 위치가 1보다 크고 Δt가 줄면 1에 가까워지는지, kin이 1과 같은지(차이 값 그대로) 본다.
- 질문 3: `nondividing`의 `steps`, `last_stamp_ns`, t=1.0 조회 성공 여부, 1초 대비 오차, 분수 재계산과의 float 차이를
  그대로 보고한다. 1e-12 허용치 비교도 출력값으로 판정한다.
- 질문 4: `publish_rate`에서 t=1.0 위치가 방송 간격이 아니라 적분 Δt를 따르는지, t=0.75 조회값이 시뮬레이터가
  실제로 계산한 값과 다른지(보간) 본다.
- 질문 5: `cpu_cost`의 단계당 시간과 Δt 절반당 시간 비율, 오차 감소를 함께 보고한다. 1 CPU 컨테이너의 Python 반복문
  시간일 뿐이며 물리 엔진 성능 수치로 쓰지 않는다.
- 락스텝 대기 시간 초과(`timeouts`)가 0이 아니면 그 시나리오의 TF 조회 결과보다 이 사실을 먼저 보고한다.
- 예측과 다르면 결과를 그대로 보고하고 글의 결론을 결과에 맞춘다.

## 한계

- 물리 엔진(Gazebo, MuJoCo 등)이나 실물 로봇이 아니다. 글과 같은 1차원 갱신식을 ROS 2 노드가 계산해 TF로 전달했을 뿐이다.
  접촉, 마찰, 강성, 제약 해법은 다루지 않는다.
- TF 경로가 값을 바꾸지 않는지, tf2가 stamp와 보간을 어떻게 다루는지를 보는 실험이며 통신 지연·시계 동기화는 재지 않는다.
- 시간은 벽시계가 아니라 stamp로 정한 시뮬레이션 시각이다. `/clock`과 `use_sim_time`은 쓰지 않는다.
- 실물 장치를 움직이는 단계가 없으므로 정지 절차가 필요한 동작은 없다.

## 시행착오

- 하네스(`--try`)는 plan.md가 없으면 실행을 거부하므로 이 계획을 시험 실행 전에 썼다.
- 설계 단계: `/tf`는 VOLATILE이라 구독 매칭 전에 보낸 첫 TF가 버려질 수 있다. 그래서 `/tf`와 `/sim_state` 구독자가
  그래프에 보이고 0.5초를 더 기다린 뒤 시작한다. 단계를 쉬지 않고 방송하면 TransformBroadcaster의 history depth를 넘겨
  샘플이 덮어써질 수 있어 락스텝으로 바꿨다.
- 시험 실행 1회차: 종료 코드 0, 출력 6개 줄 모두 8000자 안에 들어갔고 stderr에 오류는 없었다. 그러나 컨테이너 안
  소요 시간이 60초 한도에 가까웠다. Δt=2⁻⁸~2⁻¹⁰ 락스텝 구간이 대부분을 차지했다. 원인은 관찰 노드 수신을
  0.1 ms 간격 바쁜 대기(busy polling)로 확인한 데 있었다. 1 CPU 컨테이너에서 executor 스레드와 GIL을 다퉈
  단계당 왕복이 크게 늘었다. 두 가지를 고쳤다. `/sim_state` 수신은 `threading.Condition`으로 기다리고,
  TF 확인 폴링 간격은 0.5 ms로 늘렸다. ROS 경로의 전진 오일러는 Δt=2⁻⁸까지로 줄였다. 더 작은 Δt의 오차·비용은
  `cpu_cost` 반복문(2⁻¹⁶까지)이 맡는다. 측정 항목과 판정 기준은 바꾸지 않았다.
- 같은 실행에서 단계별 추적(Δt=0.25)의 t=0 조회가 t=0 위치가 아니라 마지막 위치를 돌려줬다. tf2에서 `Time(0)`은
  "가장 최근 변환"을 뜻하기 때문이다. 버그로 고치지 않고 `trace_note`로 표시해 남겼다. 본문에서 이 행을 t=0
  위치로 쓰지 않는다.
- 시험 실행 2회차: 종료 코드 0, 대기 시간 초과 0, 컨테이너 기동 포함 한 번 실행이 60초보다 훨씬 짧게 끝났다.
  락스텝 `wall_ms`는 실행마다 크게 흔들리므로 계산 비용 판단에 쓰지 않고 `cpu_cost`만 쓴다. 시험 실행 수치는
  이 문서에 옮기지 않는다. 본문의 실측 숫자는 하네스 정식 실행 `results.json`만 근거로 한다.
