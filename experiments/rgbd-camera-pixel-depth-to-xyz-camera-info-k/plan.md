# 실험 계획: RGB-D 픽셀 + 깊이 → optical 프레임 X, Y, Z와 재투영 검산의 한계

## 질문

ROS 2 Jazzy에서 `sensor_msgs/CameraInfo`의 K로 fx, fy, cx, cy를 꺼내고, 깊이 영상(`32FC1` m / `16UC1` mm)에서
공의 픽셀과 깊이를 읽어 `X = (u − cx)·Z/fx`, `Y = (v − cy)·Z/fy`, `Z = 깊이(m)`로 되돌리면 정답 좌표가 나오는가?
그리고 "다시 투영해서 원래 픽셀이 나오는지 보는 재투영 검산"은 흔한 실수 중 어떤 것을 잡고 어떤 것을 놓치는가?
놓친 실수는 "계산한 Z가 깊이(m)와 같은가" 검사로 잡히는가?

## research.md 기준 예측값 (실행 전 기록, 손계산 산술 유도이며 실측이 아님)

장면 입력: fx = fy = 500 px, cx = 320 px, cy = 240 px, 640×480, 왜곡 없음, 공 중심 (0.4, −0.2, 2.0) m, 반지름 0.05 m.

1. 받은 CameraInfo에서 K[0], K[2], K[4], K[5] = 500, 320, 500, 240. P에서는 P[0], P[2], P[5], P[6]이 같은 값이다.
   P에 K 인덱스(4, 5)를 쓰면 fy 자리에 P[4] = 0이 들어가 0으로 나누게 된다.
2. 합성 깊이 영상에서 찾은 공 중심 픽셀 (420, 190), 깊이 2.0 m(16UC1에서는 원시값 2000) → (0.4, −0.2, 2.0) m.
3. 사례별 결과:
   - 정답: 재투영 잔차 0 px, Z 일치.
   - 주점 누락: (1.68, 0.76, 2.0) → 재투영 (740, 430), 잔차 u 320 px · v 240 px. 재투영으로 잡힘.
   - 16UC1 원시값(mm)을 m로 바꾸지 않고 X, Y, Z에 똑같이 사용: (400, −200, 2000) → 재투영 잔차 0 px(통과). Z 2000 ≠ 2.0이라 Z 검사로 잡힘.
   - X, Y만 mm, Z는 m: 재투영 u = 100320. 재투영으로 잡힘.
   - 단위 광선 × 깊이: (0.39036, −0.19518, 1.95180) → 재투영 잔차 0 px(통과). Z가 1.9518이라 Z 검사로 잡힘.
4. 깊이 = Z 성분: 단위 광선 × 깊이로 얻은 Z가 (420, 190)에서 2.41% 짧고, (0, 0)에서는 1.5617로 21.91% 짧다.
5. 1 px 검출 오차가 만드는 X 변화: Z = 0.5, 1, 2, 4 m에서 0.001, 0.002, 0.004, 0.008 m.
6. K[0] = 0인 CameraInfo는 미보정으로 판정해 계산을 거부한다.
7. 16UC1의 0(무효)을 그대로 쓰면 Z = 0 → 재투영에서 0으로 나누기. 무효 마스크로 거르면 건너뛴다.
8. (편집자 추론) 공 중심 픽셀의 깊이는 공 표면까지의 Z라서 공 중심 Z보다 반지름(약 0.05 m)만큼 가깝다.
9. research.md에 예측이 없는 항목: 다른 카메라의 K(fx = fy = 610, cx = 316, cy = 244, 설명용 가정)를 잘못 짝지은 경우의
   재투영 잔차. 재투영에 같은 틀린 K를 쓰면 잔차 0이고, 메시지의 K로 재투영하면 잔차가 생길 것으로 예상한다(산술적 추론).

## 무엇을 어떻게 재는가

- 환경: 하네스가 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB)에서 `rclpy`, `sensor_msgs`, `numpy`만 쓴다.
  `image_geometry`와 `cv2`는 이미지에 없으므로 역투영과 `project_pixel_to_3d_ray`(단위 벡터 반환)를 직접 구현했다.
- 한 프로세스에 노드 두 개를 둔다. `fake_rgbd_camera`가 CameraInfo(보정됨 / K[0] = 0) 두 개와 깊이 영상 세 개
  (평판 원판 32FC1, 같은 장면 16UC1 mm, 광선 추적한 구 32FC1)를 실제 rclpy 토픽(rmw_fastrtps_cpp)으로 발행하고,
  `ball_locator`가 구독한다. 모든 계산은 **받은 메시지**에서 시작한다.
- 장면 생성: 원판은 3D 정의(Z = 2.0 m 평면에서 중심으로부터 0.05 m 이내)로 픽셀마다 판정해 그린다. 배경은 4.0 m.
  (100, 100) 픽셀 하나를 무효(16UC1 = 0, 32FC1 = NaN)로 만든다. 구는 픽셀 광선과 구의 첫 교점 Z를 넣어 그린다.
- 측정(모두 실행 중 계산, JSON 한 줄씩 출력):
  - `transport`: 탐색(discovery) 시간, 메시지별 발행→콜백 지연(ms), 받은 바이트 수.
  - `k_indices`, `p_indices`: 받은 K, P에서 인덱스로 꺼낸 값, rclpy가 돌려주는 필드 타입.
  - `p_with_k_indices`: P에 K 인덱스를 쓴 실수. 메시지 원소 그대로(numpy)와 Python float로 바꾼 경우를 각각 실행해
    예외가 나는지, 결과가 무엇인지 기록한다.
  - `uncalibrated_guard`: K[0] = 0 가드 동작.
  - `ball_detection`: 각 깊이 영상에서 `encoding`으로 단위를 정해 무효를 거르고, 3.0 m보다 가까운 픽셀의 무게중심으로
    공 중심 픽셀을 찾고 그 깊이를 읽는다.
  - `case`: 정답, 주점 누락, mm 일관 사용, mm/m 혼합, 단위 광선 × 깊이, 단위 광선을 Z로 다시 맞춘 경우, 틀린 K(같은 K로
    재투영 / 메시지 K로 재투영). 각 사례에서 재투영 픽셀, 잔차, 재투영 통과(잔차 < 0.5 px), Z − 깊이, Z 검사
    통과(|차이| < 0.005 m), 장면 정답과의 3D 거리 오차를 잰다.
  - `encoding_agreement`: 32FC1과 16UC1에서 얻은 좌표 차이.
  - `depth_is_z`: (420, 190)과 (0, 0)에서 단위 광선 × 깊이의 Z, 짧아진 비율, 직선 거리 √(X²+Y²+Z²).
  - `one_pixel_error`: Z = 0.5, 1, 2, 4 m에서 u를 1 px 옮겼을 때 X 변화.
  - `invalid_depth`: 무효 픽셀을 그대로 썼을 때(16UC1 0, 32FC1 NaN) 재투영 결과와, 무효 마스크가 거르는지.
  - `sphere_surface_vs_center`: 구 중심이 투영되는 픽셀의 깊이와 실제 구 중심 Z의 차이, 마스크 무게중심.
  - `timing`: 한 점 역투영 평균 시간(µs), 640×480 전체 점 구름 numpy 계산 시간(ms).
- 판정: 사례마다 `caught_by_reprojection`, `caught_by_z_check`를 출력해, 재투영만으로는 놓치고 Z 검사로 잡히는 경우를 구분한다.

## 시행착오 (시험 실행에서 실제로 실패하거나 고친 점)

1. 첫 시험 실행이 종료 코드 1로 실패했다. 재투영 통과 여부가 `numpy.bool_`로 계산되어 `json.dumps`가
   `TypeError: Object of type bool_ is not JSON serializable`로 멈췄다. 깊이 값을 `float()`로, 판정을 `bool()`로 바꿔 고쳤다.
2. 같은 실행의 stderr에 `RuntimeWarning: divide by zero encountered in scalar divide`가 찍혔다. research.md는
   "P에 K 인덱스를 쓰면 0으로 나누기"를 예외처럼 예측했지만, Jazzy rclpy는 `CameraInfo.k`, `.p`를 `numpy.ndarray`(float64)로
   돌려준다. 그래서 메시지 원소를 그대로 쓰면 예외 없이 경고만 남기고 Y가 무한대가 된다. Python float로 바꾸면
   `ZeroDivisionError`가 난다. 예측을 고치지 않고, 두 경우를 모두 실행해 기록하는 측정 항목(`p_with_k_indices`)으로 바꿨다.
   본 계산 경로는 K, P 원소를 Python float로 바꿔 쓴다.
3. 같은 이유로 무효 깊이 검사도 결과를 미리 "0으로 나누기"로 가정하지 않고, 실제로 나온 예외나 값(NaN 등)을 그대로 출력하게 바꿨다.
4. 두 번째 시험 실행은 종료 코드 0, stderr 없이 1회 성공했다. 시험 실행의 수치는 여기에 옮기지 않는다. 글에 쓸 수치의 근거는 하네스의 정식 실행 results.json뿐이다.

## 한계

- 합성 깊이 영상과 설명용 K를 썼다. 실제 RGB-D 카메라, Gazebo 같은 시뮬레이터, 렌즈 왜곡, 깊이 노이즈, 컬러-깊이 정합 오차는 실험 범위 밖이다.
- 공 검출은 깊이 임계값 + 무게중심이다. 실제 컬러 영상 검출(Hough 등)은 하지 않았다.
- 시간 측정값은 컨테이너 CPU 상태에 따라 실행마다 달라진다. 비교용이지 성능 기준이 아니다.
- 실물 로봇·카메라를 움직이지 않았다. 이 계산 결과만으로 로봇 동작이 안전하다고 판단할 수 없다.
