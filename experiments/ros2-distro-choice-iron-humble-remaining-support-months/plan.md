# 실험 계획: Jazzy 컨테이너 안에서 배포판 선택 조건을 실행 시점에 재기

## 질문

"2026년 10월에 새 로봇 프로젝트를 시작하면 어떤 ROS 2 배포판이 프로젝트가 끝날 때까지
지원되는가"를 다룬다. research.md는 이 질문을 세 조건으로 정리한다.

1. `남은 개월 − 프로젝트 기간 ≥ 0`
2. 그 배포판의 Tier 1 Ubuntu가 장비와 맞는가
3. 모든 기기를 한 배포판으로 맞춘다

이 실험은 공식 `ros:jazzy-ros-base` 이미지 하나로 이 세 조건 중 실제로 잴 수 있는 부분을 잰다.

- (가) 이 이미지가 실제로 어떤 배포판과 어떤 Ubuntu에 묶여 있는가. 배포판 선택이 곧 OS
  선택이라는 주장을 설치된 바이너리로 확인한다.
- (나) 실행하는 날의 컨테이너 시계를 기준으로 계산하면 남은 개월과 여유가 research.md의
  표와 같은가.
- (다) 같은 배포판 안에서 별도 프로세스의 두 노드가 실제로 메시지를 주고받는가. 이것은
  "한 배포판으로 통일"한 상태의 기준선이다.

배포판 간 통신(Humble↔Jazzy)은 이 이미지 하나로 시험할 수 없으므로 시험하지 않는다.

## research.md 기준 예측값

- 이미지 환경: `ROS_DISTRO=jazzy`, Ubuntu `24.04`(noble). research.md는 공식 Jazzy 페이지를
  근거로 Jazzy의 Tier 1을 Ubuntu 24.04로 적는다. `/opt/ros` 아래 배포판은 jazzy 하나이고,
  ros-* 바이너리는 모두 `ros-jazzy-` 이름과 noble 빌드일 것으로 예측한다.
- 2026년 10월 기준 남은 개월(research.md 표·example.py 값):
  - Humble 7, Jazzy 31, Kilted 2, Lyrical 55, Iron −22
- 공식 표로 계산한 지원 기간: Humble·Jazzy·Lyrical 60, Iron·Kilted·Makoa 19
- 18개월 프로젝트의 여유: Humble −11, Jazzy +13, Kilted −16, Lyrical +37
  - 18개월 프로젝트를 만족하는 출시 배포판은 Jazzy와 Lyrical이다.
- 파생 예측: Jazzy EOL(2029년 5월)에서 18개월을 빼면 18개월 프로젝트를 Jazzy로 시작할 수
  있는 마지막 달은 2027-11이다.
- 같은 배포판 통신: 보낸 메시지를 모두 받을 것으로 예측한다(받은 개수 = 보낸 개수).
  research.md에는 지연 시간 기준값이 없으므로 지연은 예측하지 않고 측정만 한다.

## 무엇을 어떻게 재는가

스크립트는 `experiment.py` 하나다. 네트워크 없이(`--network none`) 1 CPU·1 GiB
컨테이너에서 실행되며, 측정값은 모두 실행 중에 얻어 JSON 한 줄씩 출력한다.
결과 숫자를 코드에 적어 두지 않는다. 코드에 들어 있는 숫자는 입력값뿐이다. 입력값은
공식 Releases 표의 출시·EOL 연·월, 프로젝트 기간 가정 6·12·18·24·36개월, 보낼 메시지 수 100이다.

1. `kind=platform`
   - `ROS_DISTRO` 환경 변수, `/etc/os-release`의 `VERSION_ID`·`VERSION_CODENAME`, `/opt/ros/*` 디렉터리 목록
   - `dpkg-query`로 설치 상태(`ii`)인 `ros-*` 패키지만 센다.
     - 배포판 접두사별 개수
     - 데비안 버전 접미사(`-<rev><codename>.<YYYYMMDD>.<HHMMSS>`)의 Ubuntu codename 분포
     - 가장 오래된·가장 최근 빌드 날짜와 서로 다른 빌드 날짜 수
   - 이름만 알려진 미설치 항목은 따로 기록한다.
   - apt 소스의 packages.ros.org suite를 읽는다.
   - 공식 표의 Jazzy Tier 1(24.04)과 실제 Ubuntu 버전이 같은지 판정한다.
2. `kind=months`
   - 실행 시점의 `datetime.now(timezone.utc)`로 기준 연·월을 잡는다. 계산식은
     `(EOL 연 − 기준 연) × 12 + (EOL 월 − 기준 월)`이며 각 배포판에 대해 다음을 계산한다.
     - 남은 개월
     - 프로젝트 기간별 여유
     - 지원 기간(출시 → EOL)
   - 기준 월에 아직 출시되지 않은 Makoa는 남은 개월 판정에서 뺀다.
   - 실행 중인 배포판(`ROS_DISTRO`)의 남은 개월과 18개월 프로젝트를 시작할 수 있는 마지막 달도 계산한다.
   - 결과는 실행 날짜에 따라 달라진다. 본문은 results.json의 `clock_utc`와 함께 인용해야 한다.
3. `kind=same_distro_pubsub`
   - 구독 노드는 본 프로세스에서 실행한다. 발행 노드는 같은 스크립트를 `--publisher`로 띄운 별도 프로세스에서 실행한다.
   - 둘 다 기본 RMW(rmw_fastrtps_cpp), RELIABLE QoS, depth 100을 쓴다.
   - 발행 노드는 구독이 매칭되면 `std_msgs/String` 100개를 약 10 ms 간격으로 보낸다. 각 메시지에는
     `ROS_DISTRO|seq|monotonic_ns`를 담는다.
   - 다음 값을 잰다.
     - 받은 개수, 고유 seq 수, 순서 유지 여부, 메시지에 담긴 발행 측 배포판
     - 구독 생성부터 첫 수신까지 걸린 시간(초)
     - 지연(받은 시각 − 보낸 시각, 같은 컨테이너의 CLOCK_MONOTONIC)의 중앙값·p95·최댓값(ms)
   - `get_publishers_info_by_topic`으로 발행 측 endpoint 정보를 읽는다. 노드 이름, 타입, 타입 해시, reliability를 기록한다.
4. `kind=summary`: 판정과 전체 소요 시간. 받은 개수가 0이거나 발행 측 배포판이 실행 배포판과
   다르면 종료 코드 1로 실패 처리한다.

정상 판정은 종료 코드 0과 `summary.ok=true`다. 실패 판정은 종료 코드가 0이 아니거나
수신 0개이거나 배포판 불일치인 경우다.

## 해석 한계

- 컨테이너 시계는 호스트 시계다. 남은 개월은 실행한 달에 따라 바뀌므로 공식 지원 기간을
  "측정"한 값이 아니다. 공식 표 날짜를 실행 시점 기준으로 계산한 값이다.
- 같은 배포판·같은 컨테이너·기본 RMW 하나만 확인한다. 배포판 간 통신 실패나 성공은 이 실험의
  결과가 아니다. 지연 수치는 1 CPU 컨테이너 안 루프백 기준이며 실제 로봇 네트워크 성능이 아니다.
- endpoint 타입 해시(`RIHS01_…`)는 관측값으로만 기록한다. research.md에는 이 값이 배포판 간
  호환성과 어떤 관계인지에 관한 출처가 없다. 근거를 확인하기 전에는 본문에서 배포판 간
  통신 문제의 원인으로 해석하지 않는다.
- 빌드 날짜는 이미지에 설치된 바이너리가 언제 빌드됐는지 보여 줄 뿐이다. 앞으로 업데이트가
  계속된다는 보장이나 EOL 이후 저장소 동작을 증명하지 않는다.
- 실물 로봇·시뮬레이터는 쓰지 않는다. 하드웨어 안전 조건은 해당 없다.

## 시행착오(`--try` 시험 실행에서 실제로 겪은 일)

1. 첫 시험 실행은 종료 코드 0으로 끝났지만 출력 두 곳이 잘못됐다.
   - 발행 측 endpoint의 노드 이름이 `_NODE_NAME_UNKNOWN_`으로 기록됐다. 발견 직후 첫 조회에서는
     노드 이름이 아직 전파되지 않았기 때문이다. 이름이 잡힐 때까지 endpoint 정보를 다시 읽도록 고쳤다.
   - reliability가 enum 정수로 찍혔다. enum 이름(`RELIABLE`)으로 기록하도록 고쳤다.
2. 두 번째 시험 실행에서 버전 문자열에 빌드 스탬프가 없는 ros-* 항목 두 개가 보였다.
   `ros-jazzy-rmw-connextdds`와 `ros-jazzy-rmw-cyclonedds-cpp`이며 둘 다 버전이 빈 값이었다.
   dpkg가 이름만 알고 있는 미설치 항목이 패턴 조회에 섞인 것이다. 설치 상태가 `ii`인 패키지만
   세고, 미설치 항목은 `ros_packages_known_not_installed`에 따로 기록하도록 고쳤다.
3. 세 번째 시험 실행은 수정 사항이 모두 반영된 채 종료 코드 0으로 끝났다. 한 번 실행에 걸린 시간은 60초 제한보다 훨씬 짧았다.
