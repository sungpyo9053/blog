# 실험 계획: IP 조각 재조립 버퍼가 차는 속도와 큰 메시지가 막히는 시간

## 질문

큰 ROS 2 메시지를 실은 UDP 데이터그램이 IP 조각을 하나씩 잃으면(ROS 2 DDS tuning 문서의 최악 가정),
리눅스 커널의 IP 조각 재조립 메모리(`ipfrag_high_thresh`)는 얼마나 빨리 차고, 찬 뒤에는 조각난 큰
데이터그램이 얼마 동안 전달되지 않는가? 그동안 조각나지 않는 작은 데이터그램은 계속 전달되는가?

## research.md 기준 예측값 (실행 전에 적음)

- `ipfrag_high_thresh` = 4194304(4 MiB, Linux 3.9 이후 기본값), `ipfrag_time` = 30. ROS 2 문서의 256KB(262144)가 아니다.
- 커널은 조각마다 페이로드가 아니라 `skb->truesize`를 센다. 커널 커밋 예시는 조각당 2944 bytes,
  불완전 64K 데이터그램 하나당 (44 × 2944) + 200 = 129736 bytes, 계정 배율 f = 2944 / 1480 ≈ 1.989.
  loopback과 raw 소켓에서는 skb 할당이 NIC 드라이버와 다르므로 조각당 값은 2944와 다를 수 있다.
- 4 MiB에는 불완전 64K 데이터그램이 약 32개(커밋 원문 32.34), 문서의 256KB에는 약 2개(2.02) 들어간다.
- 1 MiB·10 Hz 토픽이 모든 데이터그램에서 조각 하나를 잃으면 4 MiB는 약 0.2초(페이로드만 세면 0.4초)에 찬다.
- 찬 뒤에는 새 조각이 모두 거부되어(`ReasmFails` 증가) 완전한 큰 데이터그램도 전달되지 않고, 먼저 만들어진
  불완전 묶음이 `ipfrag_time`(30초) 뒤 만료되어야 다시 전달된다. 막힌 시간은 30초에서 "채우는 데 걸린
  시간"을 뺀 값, 즉 약 29.8초로 예상한다. 작은(조각나지 않는) 데이터그램은 재조립을 거치지 않으므로 계속 전달된다.
- 같은 배율로 30초 대기 시 보관량은 약 597 MiB로 128 MiB를 넘고, 3초 대기 시 약 60 MiB로 128 MiB 안에 든다.
- rclpy로 직렬화한 1 MiB `std_msgs/msg/UInt8MultiArray`는 1048576바이트 + CDR 헤더·길이 필드 수십 바이트이며,
  65500바이트 UDP 페이로드로 나누면 17개 데이터그램, 데이터그램마다 IP 조각 45개(⌈65508/1480⌉)가 된다.

## 무엇을 어떻게 재는가

환경: 하네스의 `ros:jazzy-ros-base` 컨테이너, `--network none`, 1 CPU, 1 GiB. 모든 패킷은 컨테이너 자신의
loopback(127.0.0.1)으로만 오간다. Docker 기본 권한(CAP_NET_RAW)으로 raw 소켓을 열어 IPv4 조각을 직접
만들어 보낸다. loopback MTU는 65536이라 커널이 스스로 조각내지 않으므로, 1500바이트 MTU(조각당 IP 페이로드
1480바이트)를 가정해 조각을 손으로 만든다. sysctl은 읽기만 하고 바꾸지 않는다(컨테이너에서 쓰기 불가 여부도 기록).

1. 환경: 이 네트워크 네임스페이스의 `ipfrag_high_thresh`, `ipfrag_low_thresh`, `ipfrag_time`, `ipfrag_max_dist`,
   loopback MTU, 커널 릴리스를 읽는다.
2. 메시지: rclpy `serialize_message`로 1 MiB `UInt8MultiArray`를 직렬화해 실제 바이트 수와 데이터그램 수를 잰다.
   이 바이트가 이후 모든 데이터그램의 내용이다. DDS/RTPS 헤더는 붙이지 않는다(DDS를 실행하지 않음).
3. 기준선: 버퍼가 빈 상태에서 작은 UDP 데이터그램(100바이트, 조각 없음)과 완전한 큰 데이터그램(45조각)이
   UDP 수신 소켓에 도착하는지 확인한다.
4. 계정 방식: 조각 1개만 보낸 묶음과 44/45개를 보낸 묶음을 만들고 `/proc/net/sockstat`의 `FRAG: memory`
   증가량으로 조각당 truesize 추정값, 묶음 오버헤드, 불완전 64K 데이터그램 하나의 계정 크기, 계정 배율
   (계정 바이트 ÷ 보관된 IP 페이로드)을 잰다.
5. 채우기: 1 MiB 메시지를 실제 10 Hz 간격으로 10개(1초) 보내되 각 데이터그램의 마지막 조각을 빼서 보낸다.
   데이터그램마다 `/proc/net/snmp`의 `ReasmFails`를 읽어 커널이 처음 조각을 거부한 시점(채우기 시작 기준 초,
   그때까지 보낸 IP 페이로드 바이트, FRAG 메모리)을 기록한다. 메시지마다 FRAG 묶음 수·메모리·Reasm 카운터 증가량을 남긴다.
   메시지의 마지막 데이터그램처럼 1500바이트 패킷 하나에 들어가는 데이터그램은 IP 조각화가 일어나지 않으므로
   조각을 빼지 않고 그대로 보내며 그 개수(`unfragmented_datagrams`)를 따로 기록한다.
6. 멈춤: 0.1초마다 작은 데이터그램 1개와 완전한 큰 데이터그램 1개를 보내 각각 0.05초 안에 도착하는지 본다
   (둘 다 도착하면 즉시 다음 단계로). 큰 데이터그램이 다시 도착한 시각(첫 거부 기준 막힌 시간), FRAG 묶음 수가
   처음 줄어든 시각(첫 만료, 첫 묶음 생성 기준), 0이 된 시각(모든 묶음 만료)을 잰다. 시간 해상도는 탐침 간격인
   약 0.1초다. 대기 상한은 채우기 시작 + `ipfrag_time` + 4초이며, 한 번 실행은 약 31초 걸린다.
7. 파생 계산: 이번 실행에서 잰 계정 배율로 4 MiB·256KB에 들어가는 불완전 64K 데이터그램 수,
   1 MiB·10 Hz에서 4 MiB가 차는 시간, 30초·3초 대기 시 보관량과 128 MiB 비교를 계산해 출력한다(측정이 아닌 산술).

판정: 첫 거부가 관측되고, 막힌 동안의 모든 탐침에서 작은 데이터그램은 도착하고 큰 데이터그램은 도착하지 않으며,
상한 안에 큰 데이터그램이 다시 도착하면 `summary.ok=true`, 종료 코드 0이다. 아니면 종료 코드 1이다.

한계: loopback·raw 소켓의 truesize는 실제 이더넷·Wi-Fi 드라이버 값과 다르다. 패킷 손실은 실제 무선 손실이
아니라 "데이터그램마다 마지막 조각 하나를 보내지 않는" 인위적 최악 가정이다. ROS 2 노드·DDS 발견·QoS·재전송은
실행하지 않으므로 실제 토픽의 멈춤 시간과 유실 개수는 이 실험이 말하지 않는다. sysctl 값을 바꾼 상태(3초, 128 MiB)는
컨테이너 권한상 실측하지 않고 계산으로만 비교한다.

## 시행착오

시험 실행은 하네스 `--try`로 두 번 했고 두 번 모두 종료 코드 0이었다. 첫 시험 뒤 두 가지를 고쳤다.

1. 메시지 꼬리 데이터그램을 통째로 버리고 있었다. 직렬화한 메시지를 65500바이트씩 자르면 마지막 데이터그램은
   약 600바이트라 IP 조각이 하나뿐이다. "마지막 조각 하나를 뺀다"는 규칙을 그대로 적용하니 이 데이터그램은
   아무것도 보내지 않게 되었다. 조각화가 일어나지 않는 데이터그램은 손실 가정 대상이 아니므로 그대로 보내고
   개수를 따로 기록하도록 고쳤다(재조립 버퍼 측정값에는 영향 없음: 조각화되지 않은 패킷은 재조립을 거치지 않는다).
2. 멈춤 시간 해상도가 거칠었다. 첫 시험은 0.5초 간격 탐침에 매번 0.2초 수신 대기를 해서, 큰 데이터그램이 다시
   도착한 시각을 약 0.5초 단위로만 알 수 있었다. 탐침 간격을 0.1초, 수신 대기를 0.05초(둘 다 오면 즉시 종료)로
   줄이고, 첫 묶음 생성 시각을 기록해 "첫 만료" 시점을 `ipfrag_time`과 직접 비교할 수 있게 했다.

관찰했지만 원인을 확인하지 않은 점: 두 번째 시험에서 약 0.2초에 걸쳐 만들어진 묶음들이 같은 0.1초 탐침 구간에서
한꺼번에 사라졌고, 첫 만료가 `ipfrag_time`보다 조금 늦게 관측됐다. 커널 타이머의 만료 단위가 원인일 수 있으나
이 실험은 그 원인을 검증하지 않았으므로 본문에서 단정하지 않는다.

컨테이너 안에서 `/proc/sys/net/ipv4/ipfrag_*`는 쓰기 불가로 확인되어(`sysctl_writable=false`), 3초·128 MiB 설정은
실측하지 않고 측정한 계정 배율로 계산만 한다.
