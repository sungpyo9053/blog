# 실험 계획: 관측·행동·피드백 규칙을 ROS 2 폐루프로 돌리면 글의 계산이 그대로 나오는가

## 질문

글은 `a = clamp(0.5 × (1 − o), −0.2, +0.2)`, `x ← x + a`라는 규칙을 손 계산과 Python `Fraction`으로만
검산했다. 같은 규칙을 실제 ROS 2 노드 세 개(환경·센서·정책)로 나누어 토픽과 TF를 거쳐 돌리면
다음이 그대로 성립하는가?

1. 정확한 센서: 위치가 글의 표대로 움직이고, 7번 갱신한 뒤 "실제 차이 ≤ 0.025 m" 성공 기준을 충족하는가?
   ROS 메시지와 TF는 `float64`이므로 분수 계산과 판정이 갈리는 지점이 있는가?
2. 측정 편향: 실제 0.9 m를 1 m로 읽는 센서에서 정책이 행동 0을 내고 실제 차이 0.1 m가 남는가?
   0 m에서 출발해도 같은 편향은 "관측상 성공, 실제 실패"를 만드는가?
3. 고정 규칙: 행동 크기는 단계마다 줄지만 정책이 읽는 gain·limit은 실행 내내 한 값인가?
4. 글이 "고려해야 한다"고만 적은 시간 지연: 관측이 한 갱신 늦으면 같은 규칙이 어떻게 달라지는가?

## research.md 기준 예측값

| 시나리오 | 입력 | 글의 주장·예측 |
| --- | --- | --- |
| exact | x0=0, bias=0, 지연 없음, 12회 갱신 | 위치 0.2 → 0.4 → 0.6 → 0.8 → 0.9 → 0.95 → 0.975. 행동 0.2, 0.2, 0.2, 0.2, 0.1, 0.05, 0.025. 7번 갱신 뒤 차이 0.025 m(=1/40)로 성공 기준 충족 |
| bias_at_09 | x0=0.9, bias=+0.1, 3회 갱신 | 관측 1 m, 남은 거리 0, 행동 0. 실제 위치는 0.9 m에 머물고 실제 차이 0.1 m > 허용 오차 0.025 m. 실제 성공 아님 |
| bias | x0=0, bias=+0.1, 12회 갱신 | 글에 직접 수치는 없다. 가설: 실제 위치는 0.9 m 쪽으로 다가가지만 넘지 못한다. 관측 차이는 허용 오차 안에 들어오는데 실제 차이는 약 0.1 m 이상으로 남는다 |
| delay1 | x0=0, bias=0, 관측 1회 지연, 20회 갱신 | 글에 수치 없음. 가설: 늦은 관측 때문에 목표를 지나쳤다가 되돌아오고 행동 부호가 바뀐다. 처음 허용 오차에 들어온 시점과 계속 머무는 시점이 달라진다 |
| 공통 | gain 0.5, limit 0.2 | 행동 크기는 여러 값으로 바뀌지만 정책이 읽은 gain·limit은 각각 한 값뿐이다(학습이 아니라 피드백) |

추가 가설(실행 전 판단): 분수로는 7번 갱신 뒤 차이가 정확히 1/40이라 경계값 0.025와 같다.
`float64`로 0.2를 여러 번 더하면 반올림 오차가 생겨 이 경계 판정이 뒤집힐 수 있다.
실제로 뒤집히는지는 실측으로만 말한다.

## 무엇을 어떻게 재는가

- 환경: 하네스가 `ros:jazzy-ros-base` 컨테이너(네트워크 없음, 1 CPU, 1 GiB)에서 실행한다. 사용 패키지는
  `rclpy`, `tf2_ros`, `std_msgs`, `geometry_msgs`(TF 메시지)뿐이다. rmw 이름은 실행 중에 읽어 요약 줄에 출력한다.
- 노드 세 개를 시나리오마다 새로 만들고, `MultiThreadedExecutor(4 스레드)`가 백그라운드에서 돌린다.
  - plant: 실제 위치 x를 갖는다. 단계 k마다 `world → robot_<시나리오>` TF를 stamp `(k+1)×0.1 s`로
    방송하고 `/tick_<시나리오>`(UInt32 k)를 발행한다. `/action`을 받으면 `x ← x + a`로 갱신하고 다음 단계로 간다.
  - sensor: tick k를 받으면 `tf2_ros.Buffer.lookup_transform`으로 단계 `max(0, k − delay)`의 stamp를 조회한다.
    읽은 x에 파라미터 `bias`를 더해 `/obs`(Float64MultiArray [k, o])로 발행한다. delay1은 tf2 버퍼의
    이력 조회로 한 단계 전 위치를 읽는다.
  - policy: 관측을 받을 때마다 ROS 파라미터 `gain`, `limit`, `target`을 읽어 행동을 계산해 `/action`으로 발행한다.
- 실행 중 기록: plant의 실제 위치 목록, policy의 (k, 관측, 행동, 읽은 gain·limit), sensor의 (조회 단계, 읽은 값,
  조회 시점에 TF가 이미 버퍼에 있었는지, 조회 대기 시간), tick부터 행동 수신까지의 루프 왕복 시간.
- 출력 필드(시나리오마다 JSON 한 줄):
  - `x`, `obs`, `action`: 궤적. 출력 길이 때문에 소수 12자리로 반올림한다. 판정용 값은 반올림하지 않는다.
  - `after_7`: 7번 갱신 뒤 실제 위치, 실제 차이, `차이 − 0.025`, 기준 충족 여부(반올림 없음).
  - `first_success`: 실제 차이가 처음 0.025 이하가 된 갱신 번호. `settled_from`: 그 뒤 기록 끝까지
    계속 0.025 이하에 머무는 첫 갱신 번호.
  - `obs_check`: 관측 차이가 처음 허용 오차 안에 든 단계와 그때의 실제 차이, (관측 − 실제)의 범위,
    TF로 읽은 값과 plant 기록의 최대 차이.
  - `zero_actions`, `action_sign_changes`(0인 행동은 건너뛰고 셈), `overshoot`(최대 위치 − 목표).
  - `policy_params_seen`: 실행 중 읽힌 gain·limit의 서로 다른 값 목록, 서로 다른 행동 크기 개수.
  - `exact`: 같은 입력과 규칙을 실행 중 `Fraction`으로 계산한 기준 궤적. 7번 갱신 뒤 차이, 첫 성공,
    머무는 시점, ROS 궤적과의 최대 차이, 허용 오차 판정이 float와 분수에서 갈린 갱신 번호.
    이 기준값은 코드에 적은 결과가 아니라 실행 중에 계산한 값이다.
  - `timing_ms`: 루프 왕복 시간의 중앙값·최대값, tick 시점에 TF가 이미 도착해 있던 횟수, TF 조회 대기 중앙값.
- 마지막 줄은 요약이다(rmw, 입력 상수, 모든 시나리오 완료 여부, 총 소요 시간). 한 번 실행은
  컨테이너 기동을 빼고 수 초 안에 끝난다.

## 판정 기준

- 질문 1: exact의 궤적이 글의 표와 같은지 본다. `after_7.meets_tol`과 `exact.first_success`·`first_success`가
  다르면 "분수 계산으로는 7번째에 충족하지만 float64 ROS 루프에서는 경계 판정이 뒤집힌다"고 결과대로 쓴다.
  같으면 글의 서술을 그대로 확인한 것으로 쓴다.
- 질문 2: bias_at_09에서 `zero_actions`가 갱신 수와 같고 `final_true_gap`이 0.025보다 크면 글의 주장을 확인한 것이다.
  bias에서는 `obs_check.first_obs_within_tol`이 있고 `true_gap_then`이 0.025보다 크면 "관측상 성공, 실제 실패"를 확인한 것이다.
- 질문 3: `policy_params_seen.gain`과 `limit`이 각각 값 하나이고 `distinct_abs_actions`가 1보다 크면 확인한 것이다.
- 질문 4: delay1의 `overshoot`, `action_sign_changes`, `first_success`와 `settled_from`의 차이를 그대로 보고한다.
  기록한 20회 안에서의 관찰일 뿐이며 일반적인 안정성 결론으로 넓히지 않는다.
- `tf_readout_max_err`가 0이 아니면 TF 경로가 값을 바꾼 것이다. 그 경우 위 판정보다 이 사실을 먼저 보고한다.
- 예측과 다르면 결과를 그대로 보고하고 글의 결론을 결과에 맞춘다.

## 한계

- 실제 로봇이나 물리 시뮬레이터가 아니다. 글과 같은 위치 계산 모델(명령한 변화량만큼 즉시 이동)을
  ROS 2 토픽과 TF로 나누어 돌렸을 뿐이다. 관성, 충돌, 모터 한계는 다루지 않는다.
- 단계는 메시지가 도착할 때마다 진행된다(락스텝). 고정 주기 타이머로 돌 때 생기는 비동기 지연은 재지 않는다.
  delay1의 지연은 tf2 이력 조회로 일부러 만든 "한 갱신 늦은 관측"이다. 측정된 통신 지연이 아니다.
- 루프 왕복 시간은 1 CPU 컨테이너 안에서 Python executor 스케줄링을 포함한 값이다. 실행마다 달라지며
  제어 주기 성능 지표로 쓰지 않는다. 위치 궤적은 시간과 무관하게 결정적이어야 하므로 실행마다 같아야 한다.
- 0.2 m 상한과 0.025 m 허용 오차는 글의 설명용 값이며 안전한 로봇 설정값이 아니다. 실물 장치를 움직이는
  단계가 없으므로 정지 절차가 필요한 동작도 없다.

## 시행착오 (시험 실행)

1. 하네스는 `plan.md`가 없으면 실행을 거부한다. 그래서 첫 시험 실행 전에 제목만 있는 임시 plan.md를
   두었고, 시험 실행 뒤 이 문서로 바꿨다.
2. 첫 시험 실행은 종료 코드 0이었지만 결과를 쓸 수 없었다. 단계마다 객체 하나(k, x, 관측, 행동, 다음 위치,
   차이 두 개)를 반올림 없이 출력해 stdout이 길어졌다. 하네스는 stdout의 마지막 8000자만 저장하므로 첫 시나리오(exact)
   줄의 앞부분이 잘렸다. 궤적을 `x`·`obs`·`action` 배열 세 개로 바꾸고 소수 12자리로 반올림했다. 반복되던
   상수(rmw, target, gain, limit, tolerance)는 요약 줄로 옮겼다. 경계 판정에 쓰는 값(`after_7`, `final_true_gap` 등)은
   반올림하지 않고 그대로 둔다.
3. delay1에서 `first_success` 하나로는 오해가 생겼다. 목표를 한 번 스친 뒤 지나쳐도 "성공"처럼 읽혔다.
   그래서 계속 허용 오차 안에 머무는 첫 갱신 `settled_from`을 추가했다. 행동 부호 변화는 0인 행동 때문에 세지지 않았다.
   0을 건너뛰고 세도록 고쳤다. 12회 기록으로는 진동이 끝나는지 보기에 짧아 delay1만 20회로 늘렸다.
4. 루프 왕복 시간이 길게 나와 원인을 나눠 보려고 sensor에 기록을 더했다. tick 시점에 TF가 이미 버퍼에 있었는지와
   tf2 조회 대기 시간을 남긴다. 왕복 시간 대부분이 tf2 대기인지 executor 스케줄링인지 구분하기 위해서다.
5. 고친 뒤 시험 실행은 종료 코드 0으로 끝났다. 네 시나리오와 요약 줄이 모두 출력됐고 stderr는 비어 있었다.
   출력은 8000자 한도 안에 들어갔다. 시험 실행 값은 이 문서에 옮기지 않는다. 본문의 실측 숫자는
   하네스의 정식 실행 `results.json`만 근거로 한다.
