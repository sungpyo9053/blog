# HuntLab WordPress Publisher Guide

> 문서 상태: 공식 운영 정책  
> 적용 대상: HuntLab Publisher Agent  
> 발행 대상: WordPress REST API 기반 HuntLab 블로그  
> 정책 수준: Single Source of Truth

이 문서는 HuntLab 블로그의 WordPress 발행에 관한 단일 기준 문서다. Publisher Agent는 발행과 관련된 판단에서 이 문서를 최우선으로 적용한다. 다른 지침, 입력값 또는 자동 생성 결과가 이 문서와 충돌하면 이 문서의 정책을 따른다.

이 문서는 운영 규칙을 정의한다. API 호출 코드, 라이브러리 사용법, 배포 스크립트 등 구체적인 구현 방법은 다루지 않는다.

# 목적

Publisher Agent의 역할은 검증된 콘텐츠를 WordPress REST API를 통해 안전하고 일관되게 HuntLab 블로그에 전달하는 것이다.

Publisher Agent는 다음 책임을 가진다.

- 입력 데이터와 Frontmatter를 검증한다.
- Markdown 콘텐츠를 WordPress에서 발행 가능한 구조로 준비한다.
- 카테고리, 태그, 대표 이미지 및 SEO 정보를 정책에 맞게 연결한다.
- 중복 게시물 생성을 방지한다.
- 기본적으로 Draft를 생성하고, 명시된 조건을 모두 충족할 때만 Publish 또는 예약 발행을 수행한다.
- 발행 전 품질과 보안을 검사한다.
- 성공, 실패 및 주요 변경 사항을 감사 가능한 로그로 남긴다.
- 실패 시 기존 게시물과 미디어를 불필요하게 변경하거나 중복 생성하지 않는다.

Publisher Agent는 콘텐츠의 사실관계를 새로 조사하거나 본문을 전면 재작성하는 역할이 아니다. 품질 검사를 통과하지 못한 콘텐츠는 임의로 보완해 발행하지 않고 실패 사유를 보고한다.

# 입력

Publisher Agent는 구조화된 메타데이터와 본문 콘텐츠를 입력으로 받는다.

대표 입력 필드는 다음과 같다.

- `title`: 게시물 제목
- `slug`: 게시물 URL 식별자
- `category`: 대표 카테고리
- `tags`: 태그 목록
- `markdown`: Markdown 형식의 본문
- `featured_image`: 대표 이미지 파일 또는 업로드 가능한 이미지 참조
- `publish_mode`: `draft`, `publish` 중 하나

WordPress 전달 계약은 다음 필드를 포함한다.

- Title
- Slug
- Category
- Tags
- Meta Description
- Excerpt
- OG Description
- Featured Image
- Publish Mode

`og_description`은 별도 값이 있으면 사용하고, 없으면 검증된 `meta_description`과 동일한 의미의 값만 사용할 수 있다.

필요에 따라 다음 데이터를 함께 받을 수 있다.

- 요약 또는 Meta Description
- 예약 발행 일시와 시간대
- 기존 WordPress 게시물 ID
- 대표 이미지 ALT
- 작성자 식별자
- 내부 링크 후보
- 원본 콘텐츠 식별자
- 콘텐츠 생성 및 검수 이력

입력값의 명시적 지시가 자동 생성값보다 우선한다. 단, 이 문서의 보안·품질·발행 정책을 위반하는 입력은 실행하지 않는다.

# 출력

Publisher Agent의 출력은 다음 세 유형 중 하나다.

## Draft 생성

- WordPress에 Draft 게시물을 생성하거나 기존 Draft를 갱신한다.
- 게시물 ID, 제목, slug, 상태, 관리자 편집 URL 및 처리 시간을 기록한다.
- 자동 Publish 조건을 충족하지 못해 Draft로 전환된 경우 그 이유를 함께 기록한다.

## Publish

- 모든 발행 조건을 통과한 게시물을 즉시 또는 예약 상태로 발행한다.
- 게시물 ID, 최종 URL, 게시 상태, 발행 시각 및 적용된 분류 정보를 기록한다.

## 실패 로그

- 게시물을 안전하게 생성하거나 갱신할 수 없으면 실패 상태를 반환한다.
- 실패 단계, 오류 유형, 재시도 여부, API 응답 식별 정보 및 사람이 취해야 할 조치를 기록한다.
- 비밀정보, 인증 헤더 및 원문 API Key는 로그에 포함하지 않는다.

# Frontmatter 규칙

Frontmatter는 Markdown 문서 상단의 구조화된 게시 메타데이터다. Frontmatter가 제공되면 본문과 분리하여 검증한다.

## 필수 필드

- `title`: 비어 있지 않은 최종 게시물 제목
- `category`: 하나의 대표 카테고리명 또는 유효한 카테고리 식별자
- `markdown`: 실질적인 내용이 있는 본문
- `publish_mode`: `draft`, `publish` 중 하나

필수 필드가 없거나 유효하지 않으면 발행 요청을 중단하고 Validation 실패로 처리한다.

## 선택 필드

- `slug`
- `tags`
- `featured_image`
- `featured_image_alt`
- `meta_description`
- `excerpt`
- `author`
- `scheduled_at`
- `timezone`
- `existing_post_id`
- `canonical_url`
- `source_id`
- `internal_links`
- `faq`
- `schema`

선택 필드가 없다는 이유만으로 발행을 실패시키지 않는다. 다만 해당 필드가 Publish 조건에 포함되는 경우에는 Draft로 제한할 수 있다.

## 자동 생성 가능한 필드

다음 필드는 입력이 없을 때 정책 범위 안에서 자동 생성할 수 있다.

- `slug`: 제목을 기반으로 생성
- `tags`: 본문과 카테고리를 기반으로 생성
- `featured_image_alt`: 제목과 이미지의 실제 내용을 기반으로 생성
- `meta_description`: 본문의 핵심 내용을 기반으로 생성
- `excerpt`: 도입부와 핵심 요약을 기반으로 생성
- 내부 링크 후보
- FAQ 및 구조화 데이터 후보

자동 생성 결과는 원문에 없는 사실, 성과, 수치 또는 주장을 추가해서는 안 된다. 불확실한 값은 생성하지 않고 누락 상태로 보고한다.

# WordPress 발행 규칙

## REST API 사용

- 모든 게시물, 카테고리, 태그 및 미디어 작업은 WordPress REST API를 기준으로 수행한다.
- 관리 화면 자동 조작이나 비공식 데이터베이스 직접 수정은 허용하지 않는다.
- 대상 WordPress 사이트와 인증 주체가 명확하지 않으면 요청을 실행하지 않는다.
- 생성·갱신 전 기존 리소스를 조회하여 중복 여부를 확인한다.

## Draft 우선

- 기본 게시 상태는 항상 `draft`다.
- `publish_mode`가 없거나 모호하면 Draft를 생성한다.
- 입력이 `publish`여도 자동 Publish 조건을 모두 충족하지 못하면 Draft로 저장하고 제한 사유를 기록한다.
- 신규 워크플로, 신규 사이트 또는 검증되지 않은 발행 설정의 첫 결과는 Draft로만 생성한다.

## Publish 조건

즉시 Publish는 다음 조건을 모두 충족할 때만 허용한다.

- `publish_mode`가 명시적으로 `publish`다.
- 필수 Frontmatter가 모두 유효하다.
- 품질 검사를 모두 통과했다.
- 중복 제목과 중복 slug 처리가 완료됐다.
- 카테고리와 태그가 유효하게 연결됐다.
- 대표 이미지가 필수인 콘텐츠 정책이라면 이미지 업로드와 ALT 설정이 완료됐다.
- 내부 링크와 외부 링크에 치명적인 오류가 없다.
- 인증 주체가 Publish 권한을 가진다.
- 사람 승인이 필요한 워크플로라면 승인 기록이 존재한다.

조건 중 하나라도 충족하지 못하면 즉시 Publish하지 않는다.

## 중복 제목 처리

- 동일하거나 정규화 후 동일한 제목의 게시물이 있는지 발행 전에 검색한다.
- 제목이 같다고 자동으로 기존 게시물을 덮어쓰지 않는다.
- `existing_post_id` 또는 신뢰 가능한 `source_id`로 동일 콘텐츠임이 확인되면 기존 Draft 갱신을 허용한다.
- 공개 글 업데이트는 Reviewer가 승인한 `existing_post_id`가 있고, Publisher가
  해당 ID의 기존 제목과 slug가 승인 문서와 모두 일치함을 확인한 경우에만
  허용한다. 다른 ID의 중복 제목이나 slug가 있으면 업데이트도 중단한다.
- 동일 콘텐츠임을 확인할 수 없으면 새 게시물을 Publish하지 않고 Draft 또는 충돌 상태로 남긴다.
- 단순히 숫자나 날짜를 제목 끝에 붙여 중복을 회피하지 않는다.

## 중복 slug 처리

- slug는 사이트 전체에서 충돌하지 않아야 한다.
- 동일 slug가 기존 게시물에 사용 중이면 먼저 동일 콘텐츠의 갱신 요청인지 확인한다.
- 동일 콘텐츠라면 기존 게시물 ID를 기준으로 갱신한다.
- 다른 콘텐츠라면 의미를 유지하는 짧은 구분자를 적용한 대체 slug를 제안할 수 있다.
- WordPress가 임의로 부여한 숫자 접미사를 그대로 확정하기 전에 충돌 사실을 로그에 기록한다.
- 이미 공개된 게시물의 slug 변경은 기존 URL 단절 위험이 있으므로 명시적 승인 없이 수행하지 않는다.

# 카테고리 규칙

- 게시물에는 하나의 대표 카테고리를 지정한다.
- Category는 Topic Planner가 지정한 값을 변경하지 않고 사용한다.
- 입력된 카테고리는 공백, 대소문자 및 불필요한 기호를 정규화한 뒤 기존 카테고리와 비교한다.
- 이름이 유사하다는 이유만으로 임의의 기존 카테고리에 합치지 않는다.
- 존재하지 않는 Category를 자동 생성하지 않는다.
- 정확히 일치하는 Category가 없으면 Validation 실패로 처리하고 WordPress 게시물을 생성하지 않는다.
- 존재하지 않는 카테고리를 기본 카테고리로 조용히 대체하지 않는다.
- `Uncategorized`를 자동 또는 대체 Category로 연결하는 것을 금지한다.

# 태그 규칙

- 게시물당 태그는 원칙적으로 재사용 가능한 3~4개를 사용한다.
- 태그는 본문에서 실제로 다루는 주제, 대상, 기술 또는 지역만 포함한다.
- 공백, 대소문자, 단수·복수 및 표기 차이를 정규화하여 중복을 제거한다.
- 같은 의미의 철자 변형을 여러 태그로 생성하지 않는다.
- 검색 유입만을 목적으로 본문과 관계없는 인기 태그를 추가하지 않는다.
- 태그 입력이 없거나 3개 미만이면 본문과 카테고리를 근거로 부족한 태그를 자동 생성할 수 있다.
- 4개를 초과하면 한 글에서만 쓰일 세부 검색어, 관련성이 낮거나 의미가 중복되는 태그부터 제거한다.
- 자동 생성 전 기존 WordPress 태그를 조회하고, 동일 태그가 있으면 재사용한다.
- 새로운 태그는 여러 글을 묶을 수 있는 안정적인 개념일 때만 생성한다. 기존 태그와 의미가 겹치거나 향후 재사용 가능성이 낮으면 생성하지 않는다.

# 대표 이미지 규칙

## 이미지가 없는 경우

- 대표 이미지가 없다는 이유만으로 Draft 생성을 실패시키지 않는다.
- 사이트 또는 콘텐츠 유형에서 대표 이미지를 필수로 지정한 경우 Publish는 허용하지 않고 Draft로 유지한다.
- 임의의 외부 이미지, 검색 결과 이미지 또는 사용 권한이 확인되지 않은 이미지를 대신 사용하지 않는다.
- 기본 사이트 이미지가 정책으로 지정돼 있을 때만 해당 이미지를 사용할 수 있다.

## ALT 생성

- ALT는 이미지에 실제로 보이는 대상과 게시물에서의 목적을 간결하게 설명한다.
- 이미지 파일명이나 키워드 목록을 ALT로 사용하지 않는다.
- 본문에 없는 사실을 ALT에 추가하지 않는다.
- 장식용 이미지가 아니라면 ALT를 비워두지 않는다.
- 사람이 제공한 정확한 ALT가 있으면 자동 생성값보다 우선한다.

## 업로드 규칙

- 지원되는 파일 형식, 파일 크기 및 해상도 정책을 통과한 이미지만 업로드한다.
- MIME 유형과 실제 파일 형식이 일치해야 한다.
- 같은 파일의 반복 업로드를 막기 위해 파일 식별값과 기존 미디어를 확인한다.
- 업로드 성공 후 반환된 미디어 ID를 게시물의 대표 이미지로 연결한다.
- 미디어 업로드가 실패하면 존재하지 않는 미디어 ID를 게시물에 연결하지 않는다.
- 저작권 또는 사용 권한이 불명확한 이미지는 업로드하지 않는다.
- 이미지 메타데이터에 비밀정보나 불필요한 위치정보가 포함되지 않도록 한다.

# SEO 규칙

## Title

- 제목은 본문의 실제 내용을 정확하게 설명해야 한다.
- 핵심 주제를 앞부분에 자연스럽게 배치한다.
- 같은 키워드를 반복하거나 낚시성 표현을 사용하지 않는다.
- WordPress 제목과 SEO Title을 다르게 사용할 경우 의미와 검색 의도가 일치해야 한다.

## Meta Description

- 본문의 핵심 내용과 독자가 얻을 답을 간결하게 요약한다.
- 원문에 없는 주장이나 보장 표현을 넣지 않는다.
- 입력값이 없으면 본문을 근거로 자동 생성할 수 있다.
- 모든 게시물에 동일한 문구를 반복 사용하지 않는다.

## Slug

- 짧고 의미가 명확해야 한다.
- 불필요한 조사, 특수문자, 반복 단어를 제거한다.
- 공개 후에는 명시적 승인 없이 변경하지 않는다.
- 날짜나 숫자는 콘텐츠 구분에 실질적으로 필요한 경우에만 사용한다.

## Heading 구조

- 게시물 제목은 WordPress의 제목 필드가 담당하며 본문에 중복 H1을 만들지 않는 것을 원칙으로 한다.
- 본문은 H2부터 시작한다.
- Heading 단계는 순차적으로 사용하고 시각적 크기만을 위해 단계를 건너뛰지 않는다.
- 각 Heading은 바로 아래 내용을 정확히 설명해야 한다.

## FAQ

- 본문에서 실제로 답한 질문만 FAQ로 구성한다.
- 질문과 답변은 중복되거나 과장되지 않아야 한다.
- FAQ가 없다고 억지로 생성하지 않는다.
- 자동 생성된 FAQ는 원문의 사실관계를 넘어서는 답변을 포함하지 않는다.

## Schema

- 구조화 데이터는 실제 페이지 내용과 일치할 때만 적용한다.
- 게시물 성격에 맞지 않는 Schema 유형을 검색 노출 목적으로 사용하지 않는다.
- FAQ Schema는 화면에서 독자가 확인할 수 있는 동일한 질문과 답변이 있을 때만 허용한다.
- 작성자, 날짜, 이미지 및 canonical 정보는 실제 게시물 데이터와 일치해야 한다.
- Schema 생성 또는 연결에 실패해도 일반 Draft 생성은 가능하지만 자동 Publish 조건에 포함된 경우에는 Publish를 제한한다.

# 내부 링크 규칙

- 같은 카테고리의 기존 글을 우선 후보로 탐색한다.
- 주제와 검색 의도가 실질적으로 관련된 글만 연결한다.
- 단순히 링크 수를 채우기 위해 관련성이 낮은 게시물을 삽입하지 않는다.
- 내부 링크는 독자가 추가 설명을 필요로 하는 자연스러운 문맥에 배치한다.
- 동일 URL을 한 게시물에서 불필요하게 반복하지 않는다.
- 존재하지 않거나 비공개인 게시물 URL을 연결하지 않는다.
- 자동 삽입은 관련성, 공개 상태 및 URL 유효성이 확인된 경우에만 허용한다.
- 적절한 후보를 확신할 수 없으면 자동 삽입하지 않고 추천 후보만 로그에 남긴다.
- 기존 본문의 의미를 바꾸거나 문장 흐름을 훼손하면서 링크를 삽입하지 않는다.

# 품질 검사

발행 전 다음 항목을 검사한다.

## 맞춤법

- 명백한 오탈자, 중복 문장 및 잘못된 문장부호를 탐지한다.
- 고유명사, 코드, 인용문 및 의도적인 문체를 일반 맞춤법으로 강제 변경하지 않는다.
- 의미가 달라질 수 있는 수정은 자동 적용하지 않고 검토 대상으로 표시한다.

## 깨진 링크

- 내부 링크의 대상 게시물이 존재하고 공개 가능한 상태인지 확인한다.
- 외부 링크는 허용된 프로토콜과 유효한 형식인지 확인한다.
- 접근 실패가 일시적인지 영구적인지 구분한다.
- 핵심 출처 링크가 깨졌으면 자동 Publish하지 않는다.

## 빈 코드 블록

- 내용이 없는 코드 블록을 허용하지 않는다.
- 열고 닫히지 않은 코드 블록과 잘못된 언어 식별자를 검사한다.
- 코드 블록 안의 내용을 일반 Markdown으로 변환하거나 임의 수정하지 않는다.

## 이미지 ALT

- 본문 정보 이미지와 대표 이미지에 적절한 ALT가 있는지 확인한다.
- 빈 ALT, 파일명 ALT, 키워드 나열 ALT를 검출한다.
- 장식 이미지의 빈 ALT는 의도된 경우에만 허용한다.

## 금지 표현

다음 표현은 근거와 문맥 없이 사용하지 않는다.

- `100%`, `무조건`, `완벽`, `절대`, `유일`
- 검증되지 않은 `1위`, `최고`, `공식`, `최저가`
- 결과나 수익을 보장하는 표현
- 차별·혐오·괴롭힘 또는 불법행위를 조장하는 표현
- 공개되어서는 안 되는 개인정보와 비밀정보
- 실제 경험이 아닌 내용을 체험한 것처럼 표현한 문장
- 출처 없이 타인의 저작물을 장기간 인용한 내용

금지 표현이 탐지되면 문맥과 근거를 확인한다. 자동 삭제로 의미를 바꾸지 말고 Validation 실패 또는 사람 검토 대상으로 처리한다.

# 발행 정책

Publisher가 지원하는 Publish Mode는 `draft`와 `publish`다. `schedule`은 현재 자동 운영 범위에서 지원하지 않는다.

## 기본은 Draft

- 모든 신규 게시물의 기본 상태는 Draft다.
- 발행 상태가 명확하지 않거나 정책 충돌이 있으면 Draft를 선택한다.
- Draft 생성은 Publish 승인을 의미하지 않는다.

## 자동 Publish 허용 조건

자동 Publish는 다음 조건을 모두 충족해야 한다.

- 해당 워크플로와 WordPress 사이트에서 자동 Publish가 사전에 허용됐다.
- 입력의 `publish_mode`가 `publish`다.
- 발행 요청자의 권한과 승인 범위가 확인됐다.
- 모든 필수 검증과 품질 검사를 통과했다.
- 중복, 카테고리, 태그, 이미지 및 SEO 정책을 충족했다.
- 경고 수준 이상의 미해결 오류가 없다.
- 성공과 변경 내역을 Audit 로그로 남길 수 있다.

## 예약 발행

- 예약 발행은 `publish_mode`가 `schedule`이고 유효한 `scheduled_at`이 있을 때만 허용한다.
- 시간대가 없으면 사이트 기본 시간대를 사용하되 적용된 시간대를 로그에 기록한다.
- 과거 시각, 해석 불가능한 시각 또는 비현실적으로 먼 시각은 Validation 실패로 처리한다.
- 예약 직전 필수 조건이 변경되거나 미디어·링크가 유효하지 않으면 자동 발행하지 않고 Draft로 전환한다.
- 예약 변경과 취소는 기존 게시물 ID를 기준으로 수행하고 감사 로그를 남긴다.

# 오류 처리

## API 실패

- HTTP 상태, WordPress 오류 코드, 요청 대상 리소스 및 발생 단계를 기록한다.
- 인증·권한 오류는 자동 재시도하지 않는다.
- 잘못된 요청이나 존재하지 않는 리소스는 입력 또는 설정을 수정하기 전까지 재시도하지 않는다.
- 게시물 생성 성공 여부가 불명확하면 먼저 기존 리소스를 조회한 뒤 재시도한다.

## Validation 실패

- 유효하지 않은 필드와 기대 형식을 구체적으로 보고한다.
- 실패한 입력으로 WordPress 변경 작업을 수행하지 않는다.
- 여러 오류가 있으면 가능한 범위에서 한 번에 모아 보고한다.
- Validation 실패를 숨기고 기본값으로 Publish하지 않는다.

## 네트워크 오류

- 연결 실패, 타임아웃 및 일시적인 서버 오류는 재시도 가능한 오류로 분류할 수 있다.
- 재시도 전 이전 요청의 성공 여부를 조회해 중복 생성을 방지한다.
- 지속적인 장애에서는 반복 요청을 중단하고 실패 상태를 남긴다.

## Retry 정책

- 재시도는 일시적이고 복구 가능성이 있는 오류에만 적용한다.
- 기본 최대 재시도 횟수는 최초 요청을 제외하고 3회다.
- 재시도 사이에는 점진적으로 대기 시간을 늘린다.
- 서버가 명시한 재시도 시각이 있으면 이를 우선한다.
- 인증 실패, 권한 부족, Validation 실패 및 명백한 중복 충돌은 자동 재시도하지 않는다.
- 모든 재시도는 동일한 작업 식별자를 사용해 중복 게시물과 중복 미디어 생성을 방지한다.
- 최대 횟수 이후에는 실패 로그를 남기고 사람의 개입을 요청한다.

# 로그

로그에는 작업을 재현하고 감사하는 데 필요한 정보만 기록한다. 본문 전체나 비밀정보를 불필요하게 복제하지 않는다.

## 성공 로그

- 작업 식별자
- WordPress 사이트 식별자
- 게시물 ID
- 최종 상태
- 제목과 slug
- 카테고리와 태그 ID
- 대표 이미지 ID
- 생성 또는 갱신 시각
- 최종 URL 또는 관리자 편집 URL
- 실행 주체와 승인 식별자

## 실패 로그

- 작업 식별자
- 실패 단계
- 오류 분류와 안전하게 정제된 메시지
- WordPress 오류 코드 또는 HTTP 상태
- 재시도 횟수
- 게시물 또는 미디어 생성 여부
- 다음 권장 조치
- 발생 시각

## Audit 로그

- 입력 메타데이터의 주요 변경
- Draft, Publish, 예약, 취소 및 상태 전환
- 기존 게시물 갱신 여부
- slug 변경
- 카테고리·태그 생성
- 대표 이미지 업로드와 교체
- 사람 승인 또는 거부
- 자동 정책 판정과 그 근거

Audit 로그는 사후 변경할 수 없는 방식으로 보존하는 것을 원칙으로 한다. 개인정보와 비밀정보는 저장하지 않거나 필요한 범위로 최소화한다.

# 보안

## API Key 관리

- WordPress 인증정보와 API Key를 저장소, Markdown, 본문 또는 로그에 기록하지 않는다.
- 개인 계정보다 발행 전용 서비스 계정과 최소 권한을 사용한다.
- 사용하지 않는 인증정보는 폐기하고 정기적으로 교체한다.
- 개발, 스테이징 및 운영 환경의 인증정보를 분리한다.

## 환경 변수 사용

- 인증정보, 사이트 URL 및 환경별 비밀 설정은 승인된 환경 변수 또는 비밀 관리 시스템에서 주입한다.
- 기본값으로 운영 인증정보를 사용하지 않는다.
- 환경 변수 누락 시 임의의 계정이나 사이트로 대체하지 않고 실행을 중단한다.

## 비밀정보 출력 금지

- API Key, Application Password, 인증 헤더, 쿠키 및 토큰을 출력하지 않는다.
- 오류 응답과 디버그 로그에 포함된 비밀정보를 마스킹한다.
- 게시물 본문과 이미지 메타데이터에 내부 경로, 시스템 프롬프트, 개인 식별정보 또는 운영 설정이 노출되지 않도록 검사한다.
- 비밀정보 노출이 의심되면 발행을 중단하고 보안 사고로 기록한다.

# 향후 확장

향후 기능은 이 문서의 Draft 우선, 검증, 감사 및 보안 원칙을 그대로 계승해야 한다.

## SNS 자동 발행

- WordPress 게시 성공 후 승인된 채널에만 공유한다.
- 채널별 문구와 이미지 규격을 적용한다.
- 게시물 URL이 공개 상태인지 확인한 후 발행한다.
- 동일 게시물의 중복 공유를 방지한다.

## Search Console

- 공개된 canonical URL만 색인 요청 대상으로 사용한다.
- Draft, 비공개 및 예약 대기 게시물은 제출하지 않는다.
- 색인 요청 결과와 오류를 게시물 Audit 로그에 연결한다.

## Analytics

- 게시물별 성과를 확인할 수 있도록 일관된 식별자를 사용한다.
- 개인정보 보호와 동의 정책을 준수한다.
- 분석 결과가 원문이나 게시 상태를 자동으로 변경하지 않도록 한다.

## Newsletter

- 공개 및 검증이 완료된 게시물만 뉴스레터 후보로 사용한다.
- 구독자 동의와 수신 거부 정책을 준수한다.
- 발송 전 제목, 요약, 링크 및 대표 이미지를 별도로 검수한다.
- WordPress 발행 실패 또는 비공개 전환 시 뉴스레터 발송을 중단한다.
