# Hunt News WordPress 설명형 콘텐츠 문체 가이드

> 적용 대상: Hunt News의 생활, 경제, 부동산, 사회, 정치, 문화·엔터, IT 글
> 목표: 복잡한 변화가 독자의 돈·시간·일·권리·소비·선택에 무엇을 바꾸는지
> 쉬운 말과 검증 가능한 근거로 설명한다.

## 1. 문체의 우선순위

다음 순서를 지킨다.

1. 사실과 검증 범위
2. 검색 의도에 대한 명확한 답
3. 독자가 따라갈 수 있는 구조
4. 자연스러운 문장 리듬
5. 작성자의 판단과 개성

문장을 멋있게 보이게 하려고 사실을 흐리거나, 검색 키워드를 넣으려고 같은 말을 반복하지 않는다. 독자가 글을 읽고 무엇을 이해하고 결정할 수 있는지가 문체보다 우선한다.

## 2. 기본 목소리

- 기본 종결은 `-다`, `-한다`를 사용하는 차분한 설명체다.
- 한 글 안에서는 종결어미를 일관되게 유지한다.
- 친근함은 쉬운 설명과 솔직한 판단에서 만든다. `ㅋㅋㅋ`, 과도한 느낌표, 억지 유행어로 만들지 않는다.
- 제품 소개문, 보도자료, 교과서처럼 모든 장점을 균등하게 나열하지 않는다.
- 직접 확인한 사실, 공식 자료로 확인한 사실, 작성자의 해석을 구분한다.
- 실제로 하지 않은 경험이나 실패를 1인칭 체험처럼 만들지 않는다.

Build Log에서는 `직접 실행해보니`, `여기서 막혔다` 같은 1인칭을 사용할 수 있다. 단, Research에 환경·명령·로그·관측 결과가 있을 때만 쓴다.

## 3. 글의 시작

첫 두 문단에서 다음 세 가지에 답한다.

1. 독자에게 어떤 변화가 생겼는가
2. 누구에게 언제부터 적용되는가
3. 이 글을 읽고 무엇을 확인하거나 결정할 수 있는가

형식적인 인사나 긴 배경 설명 없이 대상을 바로 정의한다. 첫 문단은 핵심 키워드를 자연스럽게 포함하되 키워드 정의문처럼 딱딱하게 쓰지 않는다. 두 번째 문단에서는 기능 목록보다 그 기술이 바꾸는 흐름, 해결하는 문제 또는 흥미로운 설계 선택을 짚는다.

피해야 할 시작:

- `안녕하세요. 오늘은 ... 알아보겠습니다.`
- `요즘 AI가 정말 핫한데요.`
- 독자의 고민을 근거 없이 연기하는 질문 세 개
- 결론을 말하지 않은 채 시대 배경만 길게 설명하는 도입

## 4. 구조는 글의 질문에 맞춰 선택한다

모든 글을 같은 H2 개수와 순서로 만들지 않는다. 다음 구조는 기본 경로이며, 검색 의도에 필요 없는 단계는 뺀다.

Harness가 `content_type`을 지정한 일일 파이프라인에서는 이 문서의 공통 문체와
`guides/content-types/` 아래 선택된 가이드 한 개만 함께 적용한다. 카테고리와 글
유형은 별개이며, 선택되지 않은 유형의 필수 항목을 가져와 모든 글을 복합
체크리스트로 만들지 않는다.

### 오픈소스·기술 프로젝트 딥다이브

`대상과 핵심 명제 → 한눈에 보기 → 해결하려는 문제 → 핵심 개념과 mental model → 전체 처리 흐름 → 구현·코드 진입점 → 제약 → 도입 판단 → 참고 링크`

새로운 라이브러리, 개발자 도구, AI 에이전트, 오픈소스 런타임을 소개할 때의 기본 구조다. 기능을 빠짐없이 나열하기보다 이 프로젝트를 이해하게 만드는 하나의 핵심 명제를 먼저 세운다. 독자가 구조를 머릿속에 그릴 수 있도록 데이터, 요청, 상태 또는 빌드 산출물이 어디에서 어디로 이동하는지 설명한다.

저장소를 다룬다면 README 요약에서 끝내지 않는다. 주요 디렉터리와 코드 진입점, 먼저 읽을 파일, 설계 선택이 드러나는 구현 경계를 연결한다. 직접 실행 증거가 있으면 핵심 명제를 강화하는 위치에 사용하되, 검증 기록 자체가 글의 주인공이 되지 않게 한다.

### 기술·AI 제품 또는 아키텍처 해설

`대상 정의 → 해결하려는 문제 → 구조와 데이터 흐름 → 핵심 구현 → 사용 또는 코드 탐색 순서 → 제약 → 운영 판단`

기능 목록보다 구성 요소가 어떻게 연결되는지 설명한다. 디렉터리, 요청 흐름, 상태 변화, API 경계처럼 독자가 시스템을 머릿속에 그릴 수 있는 정보를 우선한다.

### ML Algorithms

`문제 정의 → 데이터와 표현 → 알고리즘 직관 → 핵심 가정 → 평가 지표와 오류 비용 → 비교 기준 → 실패 조건 → 적용 판단`

수식이나 용어를 먼저 나열하지 않는다. 어떤 관측값을 무엇으로 예측·분리하려는지,
라벨과 실제 결과가 어떻게 다른지, 어떤 베이스라인과 비교해야 하는지를 먼저 밝힌다.
장점은 적용 조건과 함께, 단점은 실패 사례와 함께 설명한다.

### Harness Engineering

`운영 문제 → 상태와 책임 경계 → 실패 모드 → 품질 게이트 → 재시도·멱등성 → 관측 결과 → 사람 승인과 롤백`

프롬프트 문구보다 시스템이 실패를 감지하고 중복·오염·품질 저하를 막는 과정을
보여준다. 성공 경로만 설명하지 않고 timeout, 부분 실패, 재개와 비용 경계를 포함한다.

### System Architecture

`요구사항과 제약 → 시스템 경계 → 데이터 흐름 → 선택한 구성 → 대안과 trade-off → 병목·장애 격리 → 확장·운영 판단`

박스와 화살표를 나열하는 데서 끝내지 않는다. 동기·비동기, 일관성·가용성, 비용·복잡성처럼
서로 교환되는 조건과 언제 설계를 바꿔야 하는지를 구체적으로 설명한다.

### 설치·튜토리얼·장애 해결

`원하는 결과 또는 증상 → 검증 환경 → 최소 절차 → 원인 → 수정 → 확인 방법 → 되돌리기와 한계`

명령어만 나열하지 않는다. 각 단계가 필요한 이유, 정상 출력, 실패했을 때 먼저 볼 지점을 함께 쓴다.

### Build Log·개발 경험

`목표와 제약 → 선택한 접근 → 실패 또는 버린 선택지 → 실제 변경 → 전후 결과 → 남은 문제`

성공담만 매끈하게 정리하지 않는다. Research에 남은 실패 로그, 환경 차이, 예상과 달랐던 결과가 있으면 문제 해결의 근거로 사용한다.

### 비교·선택 가이드

`선택 기준 → 후보별 차이 → 조건별 적합성 → 비용·제약 → 추천 대상과 비추천 대상`

모든 후보에 같은 점수를 억지로 매기지 않는다. 독자가 자신의 조건에 따라 선택할 수 있는 기준을 남긴다.

### 생활·경제·부동산·사회·정치·문화·엔터

`독자의 실제 질문 → 확인된 변화 → 적용 대상 → 금액·시간·권리·선택의 전후 차이 → 시행일과 예외 → 지금 확인할 행동`

속도보다 출처와 적용 범위를 우선한다. 발표명과 기관명을 옮기는 데서 멈추지
않고 `그래서 내 생활에 무엇이 달라지는가`에 답한다. 정치 글은 진영 논평이 아니라
법·정책·예산·권리의 영향을, 문화·엔터 글은 루머가 아니라 요금·계약·플랫폼·관람·
소비 선택의 변화를 중심에 둔다.

부동산 글은 전월세·청약·대출 규제·세금·정비사업에서 지역, 면적, 소득, 보유 주택
수와 시행일처럼 결론을 바꾸는 조건을 먼저 밝힌다. 집값을 단정하거나 매수·매도를
추천하지 않고 독자의 계약·현금흐름·거주 선택에 생기는 변화를 설명한다.

제목은 `9차 석유 최고가격 발표`보다 `9차 석유 최고가격 얼마? 내일부터 주유소
가격은 어떻게 달라지나`처럼 독자의 조건과 영향을 드러낸다. 건강보험료·대출금리
같은 숫자는 공식 산식과 기준일로 재현할 수 있을 때만 제목에 쓴다.

## 5. 한눈에 보기는 선택 사항이다

독자가 본문을 읽기 전에 네 개 이상의 구성 요소, 결정 기준 또는 단계를 파악해야 할 때만 `한눈에 보기`를 쓴다.

- 3~6개 항목으로 제한한다.
- 뒤의 본문을 대신하지 않고 탐색 지도로 사용한다.
- 모든 글에 반복해서 붙이지 않는다.
- 제목을 바꾼 같은 요약을 도입과 결론에 중복하지 않는다.
- 복잡한 기술 프로젝트 딥다이브에서는 독자가 뒤의 아키텍처 설명을 읽기 전에 핵심 구성과 현재 성숙도를 잡을 수 있어 유용하다.

## 6. 섹션과 문단

- H2는 아래 내용을 구체적으로 예고하는 질문 또는 판단으로 쓴다.
- H3는 하나의 H2 안에 구분해야 할 독립 요소가 둘 이상일 때만 쓴다.
- 소제목에 핵심 키워드를 기계적으로 반복하지 않는다.
- 한 문단에는 하나의 핵심 주장만 둔다.
- 보통 2~4문장으로 설명하되, 문단 길이를 인위적으로 맞추지 않는다.
- 짧은 판단 문장 뒤에는 근거를 붙인다. 긴 설명 뒤에는 독자가 기억해야 할 의미를 짚는다.
- `또한`, `한편`, `결론적으로` 같은 접속어보다 원인, 변화, 대비가 드러나는 연결을 쓴다.

좋은 섹션은 `무엇인가`에서 멈추지 않고 `어떻게 연결되는가`, `왜 이 선택이 필요한가`, `어떤 조건에서는 달라지는가`까지 답한다.

## 7. 기술적 구체성

주장에 맞는 근거가 Research에 있다면 다음 가운데 필요한 것을 사용한다.

- 검증 날짜와 환경
- OS, 런타임, 프레임워크 또는 제품 버전
- 핵심 파일 경로와 코드 진입점
- 요청·데이터·상태의 흐름
- 실행 명령과 기대 결과
- 실패 로그와 원인
- 변경 전후 측정값
- 공식 문서와 직접 검증 결과의 차이

코드 블록, 표, 목록은 정보를 더 짧고 정확하게 전달할 때만 사용한다. 두 문장으로 설명할 수 있는 내용을 표로 늘리거나, 연속된 단계를 산문 한 문단에 묻지 않는다.

구체적인 사실을 제시한 뒤에는 그 사실이 독자의 구현 또는 운영 판단에 왜 중요한지 설명한다.

### 독자가 안다고 가정하지 않는다

- 낯설 수 있는 기술 용어와 약어는 처음 등장한 문장에서 쉬운 한국어 뜻을 먼저
  설명하고, 현재 흐름에서 맡는 역할과 필요한 이유를 덧붙인다.
- 용어를 다른 전문 용어만으로 정의하지 않는다. 앞에서 설명하지 않은 개념을 다음
  문단의 전제로 사용하지 않는다.
- 설명의 출발점은 독자가 실제로 하는 행동과 기대하는 결과다. 내부 구현은 그 경험이
  왜 가능하거나 왜 실패하는지 답할 때 소개한다.
- 순서, 상태 변화, 분기 또는 대안 차이가 산문만으로 잘 보이지 않으면 이미지, 흐름도,
  상태도 또는 비교표를 사용한다. 시각 자료 앞뒤에는 읽는 시작점과 핵심 결론을 적는다.

## 8. 검증 범위와 판단

사람다운 기술 글은 과장된 체험담이 아니라 검증 범위가 선명한 글이다.

- 직접 실행했다면 환경, 방법, 관측 결과를 함께 쓴다.
- 공식 문서만 확인했다면 `공식 문서 기준`이라고 밝힌다.
- 재현하지 못했거나 조건이 부족한 항목은 미검증으로 남긴다.
- 장점과 함께 비용, 보안, 성능, 호환성, 운영 부담 중 실제 관련된 제약을 쓴다.
- 마지막에는 사실의 반복이 아니라 작성자의 적용 판단을 남긴다.

판단은 `좋다` 또는 `추천한다`로 끝내지 않는다. 누구에게 맞는지, 어떤 조건에서는 피해야 하는지, 도입 전에 무엇을 확인해야 하는지까지 적는다.

검증 범위는 신뢰를 위한 안전장치이지 모든 섹션의 반복 주제가 아니다. 도입에서 범위를 짧게 밝히고, 실제 결론이 달라지는 지점에서만 다시 언급한다. 공식 문서 기반 글은 `직접 검증하지 않았다`는 같은 문장을 섹션마다 반복하지 않고 한계 또는 도입 판단에서 한 번 더 정리한다.

### 직접 검증 글의 실행 증거 묶음

Build Log, 설치, 튜토리얼, 장애 해결처럼 직접 검증을 약속한 글은 다음 다섯
요소를 서로 연결해 보여준다.

1. `command_and_output`: 실제 실행한 명령과 판단에 필요한 출력, 종료 상태
2. `failed_attempt`: 실패한 접근, 관측된 오류와 실패 원인
3. `before_after`: 같은 환경·입력으로 비교한 변경 전후 결과
4. `operator_judgment`: 결과를 바탕으로 운영자가 선택할 행동과 선택하지 않을 조건
5. `docs_vs_observed`: 공식 문서가 약속한 범위와 실제 관측이 같거나 달랐던 지점

다섯 항목을 억지로 별도 H2로 만들지 않는다. 문제 해결 흐름 안에서 명령,
짧은 출력, 비교표, 실패 기록과 최종 판단 중 가장 자연스러운 형식으로 배치한다.
출력은 핵심 줄만 남기고 비밀값, 사용자명, 사설 주소와 불필요한 식별자는
제거한다.

직접 검증은 보조 각주로 숨기지 않는다. 독자의 판단을 바꾸는 실제 명령과 출력은
본문 앞쪽의 문제 재현 또는 해결 확인 지점에 배치하고, 동일 원문을 보여주는
터미널 캡처를 최소 1장 함께 제공한다. 실패와 변경 전후가 핵심이면 최대 2장까지
사용한다. 캡처 전후에는 각각 실행 조건과 관측의 의미를 설명해 이미지가 본문을
대신하지 않게 한다.

캡처는 실제 출력의 시각적 증거다. 보기 좋게 만들기 위해 수치, 오류 문구,
종료 상태를 바꾸거나 여러 실행을 하나의 결과처럼 합치지 않는다. 민감정보를
제거한 경우 그 사실을 캡션에 짧게 밝히며, 재구성한 인포그래픽을 실제 터미널
캡처라고 부르지 않는다.

안전하게 직접 실행할 수 없는 주제는 결과를 만들기 위해 운영 환경을 변경하지
않는다. 이 경우 `not_directly_tested`를 밝히고 공식 자료 대조형 글로 전환한다.
직접 검증을 약속한 제목과 Build Log는 다섯 요소가 없으면 발행하지 않는다.
실제 명령·출력 캡처가 없거나 캡처와 본문 수치가 다르면 역시 발행하지 않는다.

## 9. AI가 쓴 티를 줄이는 규칙

다음 패턴을 반복하지 않는다.

- 매번 질문형 도입 뒤 `결론부터 말하면`으로 시작
- 모든 글에 같은 수와 길이의 H2·H3 사용
- 모든 문단을 비슷한 세 문장으로 구성
- `핵심은`, `정리하면`, `결론적으로`를 섹션마다 사용
- `단순히 A가 아니라 B다` 구조를 반복
- 근거 없이 `혁신적`, `강력한`, `매우 중요하다`라고 평가
- 세 항목짜리 목록을 문단마다 생성
- 같은 내용을 도입, 요약, 결론, FAQ에서 네 번 반복
- 검색 의도와 무관한 FAQ를 정해진 개수를 채우려고 추가
- 실제 경험이 없는데 `직접 써보니`, `현업에서는`이라고 단정
- 굵은 글씨와 콜아웃으로 거의 모든 문장을 강조

표현을 피하는 것만으로 사람다운 글이 되지는 않는다. 각 글마다 고유한 질문, 구체적인 증거, 버린 선택지, 환경별 조건, 독자적인 판단 중 적어도 하나가 본문 중심에 있어야 한다.

### 편집 흔적을 남긴다

글마다 출발점, 한 문장 명제, 깊게 다룰 한 가지, 버릴 관점을 먼저 정한다. 실제
프로젝트·공개 코드·관측 질문에서 출발할 수 있다면 합성 실험보다 우선한다. 합성
실험은 실제 선택을 바꾸는 좁은 질문에만 사용하고 그 결과를 일반 성능으로 키우지
않는다. 독자가 기억해야 할 것은 조사 범위의 크기가 아니라 작성자가 무엇을 보고
어떤 선택을 했는지다.

사이트 전체에서 반복해도 되는 고정 형식은 `20초 핵심 요약` 상자뿐이다. `무엇`,
`왜`, `어떻게`를 모두 채우되 본문 H2와 결론을 같은 삼단 구조로 복제하지 않는다.
로그는 판단에 필요한 5~20줄만 보여주고 바로 해석을 붙인다. 검증 범위와 면책은
필요한 지점에 한두 번만 두며 모든 문장을 방어적으로 닫지 않는다.

### 사이트 차원의 변주

Hunt News는 여러 명의 가짜 작성자를 연기하지 않는다. 작성자 표시는 일관되게 유지하고,
글의 차이는 실제 근거와 독자의 행동에서 만든다. Harness가 제공한 최근 글 5개의 도입,
H2와 마무리를 비교해 다음 세 요소가 한꺼번에 반복되지 않게 한다.

- 첫 문단의 출발점: 증상, 선택, 실험, 코드 진입점, 현장 관측
- 본문 진행 논리: 원인 해결, 대안 비교, 실험 순서, 코드 흐름, 운영 메모
- 마지막 판단: 채택 조건, 비추천 조건, 다음 실험, 남은 문제

주제의 근거가 같은 구조를 요구하면 `structure_mode` 자체는 반복할 수 있다. 이때도 최근
글의 문장, 비유, 경험이나 수치를 가져오지 않는다. 무작위로 말투를 바꾸거나 가짜 실패를
추가하는 방식은 사람다운 변주로 인정하지 않는다.

이 상자는 글마다 정확히 한 번만 쓴다. `왜`는 기능 이름이나 요약 제목을 되풀이하지
말고 실제 손실, 오작동 또는 선택 이유를 말한다. `문제 또는 판단 기준을 놓치지 않기
위해서입니다`, `순서로 확인합니다` 같은 범용 문구는 사용하지 않는다.

Build Log는 완성된 해설이 아니라 실제 작업 흔적을 편집한다. 작업을 시작한 사건,
처음 내린 판단, 막힌 지점이나 틀린 예상, 실제 변경, 채택한 결정과 아직 남은 불편을
시간순으로 보존한다. 글을 위해 새로 만든 실험만 있으면 Build Log로 부르지 않는다.
코드의 함수명·값·화면 증상으로 설명할 수 있는 내용을 `계약`, `경계`, `게이트`,
`관측`, `범위` 같은 추상 명사로 덮지 않는다.

## 10. 마무리

결론은 본문을 축약해서 다시 쓰는 자리가 아니다. 다음 가운데 검색 의도에 맞는 두 가지 정도로 닫는다.

- 이 기술을 한 문장으로 다시 판단
- 적합한 사용자와 적합하지 않은 사용자
- 실제 적용 전에 확인할 조건
- 남아 있는 한계 또는 다음 검증 항목
- 바로 실행할 수 있는 다음 단계

`도움이 되었길 바랍니다`, `여러분의 생각은 어떤가요`, `공감과 댓글 부탁드립니다` 같은 상투적인 마무리는 쓰지 않는다.

오픈소스·기술 프로젝트 딥다이브는 본문에서 실제 사용한 1차 자료를 `참고 링크`로 짧게 묶을 수 있다. 참고 링크는 본문을 대신하는 링크 모음이 아니라 독자가 코드와 설계를 이어서 확인할 진입점이어야 한다.

## 11. Writer 체크리스트

- 첫 두 문단에서 대상, 중요성, 글의 범위를 알 수 있는가?
- 글 유형에 맞는 구조를 선택했으며 고정 템플릿을 강요하지 않았는가?
- 소제목만 읽어도 설명의 진행 방향이 보이는가?
- 기능 목록보다 구조, 작동 원리와 선택 이유가 드러나는가?
- 실제 검증, 공식 자료, 해석과 미검증 영역이 구분되는가?
- 직접 검증 글이라면 명령·출력, 실패 원인, 전후 비교, 운영 판단과 공식 문서 대비가 모두 근거로 연결되는가?
- 독자가 구현 또는 운영 판단에 사용할 구체적인 정보가 있는가?
- 한계와 비추천 조건을 숨기지 않았는가?
- 같은 도입, 접속어, 문단 길이와 결론 패턴이 반복되지 않는가?
- 연구에 없는 경험이나 수치를 만들지 않았는가?
- 마지막에 대상 독자를 위한 실용적인 판단이 남는가?
- 프로젝트 딥다이브라면 핵심 명제, mental model, 전체 흐름과 코드 진입점이 서로 이어지는가?
- FAQ가 있다면 본문 뒤에 자연스럽게 남는 후속 질문인가? 없다면 억지로 만들지 않았는가?

## 12. 참고 원칙

이 가이드는 공개된 우수 기술 글에서 관찰한 `빠른 대상 정의`, `점진적 구조 설명`, `구체적인 구현 경로`, `한계와 적용 판단의 분리`를 HuntLab 운영 목적에 맞게 일반화한 것이다. 특정 작성자의 문장, 비유, 소제목 또는 반복 표현을 복제하지 않는다.
