# HuntLab 편집 컨셉 — 2026-09-15

WordPress 자동발행을 실제로 운영하며 실패 원인과 해결 방법을 공개하는 실전 운영 노트.

## 독자와 범위

독자는 WordPress를 코드·AI로 운영하는 개발자와 1인 운영자다.
일반 생활·경제 뉴스, 제품 발표 요약, 광범위한 시스템 설계나 AI 유행어는 독립 글의 주제가 아니다.
뉴스·검색 신호는 이미 관측한 문제를 설명할 참고 자료일 뿐 발행 슬롯을 채우는 근거가 아니다.

카테고리는 REST API 발행, 자동화·테스트, WordPress 운영 세 가지다.
같은 WordPress 운영 문제를 다루는 코드·테스트·로그 변경만 새 후보로 평가한다.

## 주제 결정

작성 전에 다음 질문에 구체적인 답을 남긴다.

- 실제로 무엇이 바뀌거나 실패했는가? 추적 가능한 변경·테스트·로그는 무엇인가?
- 독자가 겪는 증상은 무엇이며, 어떤 환경에서 적용되는가?
- 기존 공개 글과 초안 중 같은 문제를 해결하는 글은 무엇인가? 새 글보다 그 글의 정정·보강이 나은가?
- 이 글에서만 얻을 새로운 판단은 무엇인가? 기존 글과 다른 결론 없이 제목만 바꾸지 않는다.
- 독자가 실행할 명령·예제·검사 절차가 있는가? 필요한 환경과 정상/실패 기준이 있는가?
- 예제 재현, 운영 관측, 코드 검토 중 어디까지 확인했는가? 근거가 공개 가능하고 비밀정보가 없는가?

위 답이 없으면 READY가 아니다. 날짜나 글 수를 위해 내용을 늘리지 않는다.
단순 테마 색상/문구 변경, 사이트 개편 자체의 일지는 독자가 재사용할 기술적 발견 없이는 후보로 삼지 않는다.

## 글의 형태

실제 변경 → 실패 근거 → 해결 과정 → 독자가 실행할 방법 → 남은 한계의 논리를 갖춘다.
모든 글에 동일한 제목·H2·FAQ를 강제로 붙이지 않는다. 짧게 답할 수 있는 문제는 짧게 쓴다.
수치, 장애 경험과 사람의 검수 여부를 만들지 않는다. 자연스러운 문체가 근거를 대신하지 않는다.
일반론·중복 요약 대신 해당 입력에서 왜 실패했고 무엇을 바꿨는지 설명한다.

## 운영

10:00 KST는 평가 시각이며 하루 최대 1건, 후보 없으면 `no_publishable_topic`이다.
기존 글 업데이트도 변경 전 백업·정정 이유·검토·공개 확인을 남긴다.
브리핑은 참고 기록으로 분리하며 독립 글의 원본인 것처럼 대량 분할하지 않는다.
AdSense 승인 확률을 자체 점수로 만들거나 콘텐츠 수를 승인 요건처럼 제시하지 않는다.
