# 시스템 설계 사례 유형

## 목적

대규모 시스템 설계·가상 면접형 글은 제품이나 컴포넌트를 나열하는 글이 아니다.
독자가 하나의 요구사항을 설계 판단으로 바꾸는 과정을 따라가도록 작성한다.
설명의 출발점과 진행축은 서비스 사용자다. 서버 컴포넌트나 클라이언트 구현을
먼저 나열하지 않고, 사용자가 무엇을 하며 무엇을 기대하고 어떤 실패를 겪는지에서
설계 이유를 꺼낸다.

## 필수 전개 순서

`사용자와 대표 행동 → 요구사항과 범위 → 규모 추정과 가정 → 사용자 행동별 API·데이터 흐름 → 상세 데이터 모델과 컴포넌트 → 병목·용량 → 사용자에게 보이는 실패와 시스템 복구 → 보안·비용 → 대안과 트레이드오프 → 단계별 확장`

모든 수치는 실제 관측값인지 설계 가정인지 표시한다. 근거 없는 QPS, 지연시간,
사용자 수를 실제 성능처럼 쓰지 않는다. 규모 추정은 입력·공식·결과·민감도까지
보여주고, 가정이 바뀌면 어떤 선택이 바뀌는지 설명한다.

## Writer 규칙

- 도입 뒤 `## 20초 핵심 요약`에 무엇·왜·어떻게를 포함한다.
- 먼저 서버 기능 목록이 아니라 서비스 사용자의 대표 행동 2~3개와 기대 결과,
  실패 시나리오를 고정한다.
- 개략 설계는 각 사용자 행동에서 시작해 요청이 이동하고 결과가 돌아오는 순서를
  번호로 설명한다. 컴포넌트는 그 흐름에서 맡는 역할을 한 문장으로 소개한다.
- 독자가 안다고 가정하는 용어를 남기지 않는다. 낯설 수 있는 용어와 약어는 첫
  등장 문장에서 쉬운 한국어 뜻, 이 글에서 맡는 역할, 필요한 이유를 함께 설명한다.
  앞에서 정의하지 않은 개념을 뒤에서 전제로 사용하지 않는다.
- API와 데이터 모델은 대표 요청·응답, 키·인덱스·보존 정책까지 최소 예시를 든다.
- 구성도는 컴포넌트 이름보다 요청·이벤트·재시도·저장 경계를 설명한다.
- 문장만으로 순서·상태 변화·분기·대안 차이를 이해하기 어렵다면 본문 설명 이미지를
  넣는다. 이미지 앞뒤 문장에서 시작점, 읽는 순서와 결론을 안내한다.
- 병목은 읽기/쓰기 비율, 핫키, 순서 보장, 중복, 외부 의존성처럼 관측 가능한
  조건으로 표현한다.
- 장애 대응은 감지→완화→복구→데이터 정합성 확인 순서로 쓴다.
- 마지막에는 선택한 설계와 선택하지 않은 대안을 비용·복잡도·운영 부담으로 비교한다.

## Reviewer 거절 조건

- 요구사항·규모 가정 없이 추상적인 아키텍처 그림만 제시한다.
- 서버 컴포넌트 또는 클라이언트 구현부터 시작해 서비스 사용자의 행동과 기대
  결과가 글의 진행축에서 사라진다.
- 처음 나온 기술 용어·약어를 정의하지 않거나, 정의하지 않은 개념을 뒤 문단의
  전제로 사용해 설명 흐름이 끊긴다.
- 복잡한 순서·상태·분기를 글만으로 이해하기 어려운데 설명 이미지나 동등한 시각적
  보조 수단이 없거나, 이미지의 읽는 방법을 본문이 설명하지 않는다.
- API, 데이터 모델, 장애 대응 또는 트레이드오프 중 하나라도 빠진다.
- 통제된 설계 가정을 실제 운영 경험이나 성능 결과처럼 표현한다.
- 특정 기업·서비스의 내부 구조를 확인하지 않고 사실처럼 단정한다.
